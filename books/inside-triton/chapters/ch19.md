整个过程在 `compile()` 里只有一个循环（`python/triton/compiler/compiler.py`）：

```python-norun
    stages = dict()
    backend.add_stages(stages, options, src.language)
    ...
    module = src.make_ir(target, options, codegen_fns, module_map, context)
    ...
    for ext, compile_ir in list(stages.items())[first_stage:]:
        next_module = compile_ir(module, metadata)
        ...
        metadata_group[ir_filename] = fn_cache_manager.put(next_module, ir_filename)
        ...
        module = next_module
```

`stages` 是一个有序字典，键是扩展名，值是「把上一级变成这一级」的函数，由各个后端的 `add_stages` 填写。NVIDIA（`third_party/nvidia/backend/compiler.py`）填的是 `ttir`、`ttgir`、`llir`、`ptx`、`cubin` 五段；Intel（`third_party/intel/backend/compiler.py`）填的是 `ttir`、`ttgir`、`llir`、`spv` 四段，只有设了 `TRITON_XPU_GEN_NATIVE_CODE=1` 时，才多一段 `zebin`（在 `compile()` 里用 `ocloc` 编出机器码）。每一段的结果都写进磁盘缓存，所以 `kernel.asm` 里能拿到的就是这几个键，缓存目录里也正好是这几个文件。

## 第 0 段：Python → TTIR

`make_ir` 不经过任何 pass。它在 `python/triton/compiler/code_generator.py` 里：一个 `CodeGenerator(ast.NodeVisitor)`，用 Python 自带的 `ast` 模块把 kernel 的源码解析成语法树，再逐个节点地访问，一边访问一边用 builder 生成 MLIR op。`visit_For` 里调用 `self.builder.create_for_op(lb, ub, step, init_handles)` 生成 `scf.for`；`visit_If` 生成 `scf.if`。第 18 章的那些现象都在这里决定：

- **循环里改过的变量变成 `iter_args`**：`visit_For` 先用 `_find_carries` 找出循环体里重新赋过值、循环外面也要用的变量，把它们的初值收集成 `init_handles`，再创建 `scf.for`。
- **`tl.constexpr` 的 `if` 不进 IR**：条件是 constexpr 时，`visit_If` 直接在 Python 里求值，只访问被选中的那个分支。
- **全局变量必须是 constexpr**：kernel 里引用的全局变量，在这一步被当成编译期常量读进来。不是 `tl.constexpr` 的全局变量会报 `NameError: Cannot access global variable ...`，错误信息建议把它写成 `x = triton.language.constexpr(42)`。这样限制的一个原因是：普通全局变量的值变了，已经编译好的 kernel 并不知道。

TTIR 是唯一一级「Triton 自己用 Python 生成」的 IR，之后所有的变换都是 C++ 写的 MLIR pass。

## 每一段做了什么

第 18 章用 `MLIR_ENABLE_DUMP` 数过：`row_sum` 编到 sm_86 是 73 个 pass，在 Max 1100 上是 71 个。按段分开（每一段在后端代码里是一个独立的 `pass_manager`）：

| 段 | sm_86 | Max 1100 | 做什么 |
| --- | ---: | ---: | --- |
| `ttir` | 10 | 20 | 和硬件无关的清理：inline、canonicalize、CSE、`triton-combine`、`triton-reorder-broadcast`、循环展开。Intel 多了十来个自己的 TTIR pass（去掉不必要的 mask、按 stride 做版本化等） |
| `ttgir` | 44 | 32 | 第一个 pass 就是 `convert-triton-to-tritongpu`：给每个张量加上 layout。之后是 coalesce、选矩阵指令（accelerate-matmul）、去掉多余的 `convert_layout`、软件流水（第 13 章）、预取……以及 NVIDIA 的 TMA、warp specialization，Intel 的 2D block IO、`ReduceVariableLiveness`（第 15、17 章） |
| `llir` | 19 | 19 | `scf` 变成 `cf`（结构化控制流变成跳转）、分配 shared memory、把所有 `tt` / `ttg` / 后端方言的 op 换成 LLVM 方言，转成 LLVM IR，再跑 LLVM 自己的优化（NVIDIA 是 `llvm.optimize_module`，Intel 是 `optimize_llvm_mod`） |
| 最后一级 | `ptx`、`cubin` | `spv` | NVIDIA：LLVM 的 NVPTX 后端生成 PTX，再调用 `ptxas` 生成 cubin。Intel：LLVM IR 翻译成 SPIR-V |

（`llir` 那 19 个只是 MLIR 的 pass，不包括 LLVM 优化里那上百个 LLVM pass。）

**`ttgir` 段是 Triton 的核心**：layout、矩阵指令、流水、访存方式，第三部分讲的所有性能现象，几乎都是这一段里的某个 pass 决定的。第 20、21 章讲 layout，第 22 章挑几个关键的 pass 细看。

## 时间花在哪

`compile()` 留了一个钩子：设置 `triton.knobs.compilation.listener`，每次编译结束时 Triton 会调用它，传进来一个 `CompileTimes`，里面有每一段的耗时（`python/triton/knobs.py`）。用它测 minillm 的三个 kernel，同时记下「第一次调用一共花了多久」：

```triton
# arch: sm80 xpu
import os
import time

import torch
import triton
from triton import knobs

from minillm import DEVICE
from minillm.kernels.attention import attention
from minillm.kernels.matmul import matmul_grouped
from minillm.kernels.pointwise import add

gpu = getattr(torch, DEVICE.type)
times = []                                   # 每次真正编译时，Triton 回调这个函数（python/triton/compiler/compiler.py）


def listener(*, src, metadata, metadata_group, times: knobs.CompileTimes, cache_hit):
    if not cache_hit:
        listener.last = (src.name, times, metadata_group)


knobs.compilation.listener = listener
knobs.compilation.always_compile = True      # 等价于 TRITON_ALWAYS_COMPILE=1：不用磁盘缓存，每次都重新编译
triton.runtime.driver.active.get_current_target()   # 先把 driver 初始化掉，别算进第一个 kernel
add(torch.ones(16, device=DEVICE), torch.ones(16, device=DEVICE))   # 再编一个，把每个进程只做一次的准备工作排除掉

bf = dict(device=DEVICE, dtype=torch.bfloat16)
x, y = torch.randn(1 << 20, **bf), torch.randn(1 << 20, **bf)
a, b = torch.randn(4096, 4096, **bf), torch.randn(4096, 4096, **bf)
q, k, v = (torch.randn(1, 8, 1024, 128, **bf) for _ in range(3))
print(f"{gpu.get_device_name()}，triton {triton.__version__}；单位：毫秒")
print(f"  {'kernel':24} {'Python→TTIR':>11} " + " ".join(f"{s:>7}" for s in ("ttir", "ttgir", "llir", "最后一级")) +
      f" {'写缓存':>6} {'第一次调用一共':>12}")
for name, fn in (("add（第 4 章）", lambda: add(x, y)), ("matmul_grouped（第 12 章）", lambda: matmul_grouped(a, b)),
                 ("attention（第 17 章）", lambda: attention(q, k, v, causal=True))):
    gpu.synchronize()
    t = time.perf_counter(); fn(); gpu.synchronize()
    total = (time.perf_counter() - t) * 1e3
    kname, ct, group = listener.last
    stages = dict(ct.lowering_stages)
    last = [s for s in stages if s not in ("ttir", "ttgir", "llir")]
    cells = [stages["ttir"], stages["ttgir"], stages["llir"], sum(stages[s] for s in last)]
    print(f"  {name:24} {ct.ir_initialization / 1e3:11.1f} " + " ".join(f"{c / 1e3:7.1f}" for c in cells) +
          f" {ct.store_results / 1e3:6.1f} {total:12.1f}    （最后一级：{'、'.join(last)}）")
print(f"缓存里的文件（{kname}）：" + "  ".join(sorted(os.path.basename(p) for p in group.values())))
```

- **`llir` 这一段最贵**，占了 `compile()` 的一半以上：TTGIR 到 LLVM IR 的转换要把每一个张量 op 展开成每个线程的标量指令，然后 LLVM 还要优化一遍。kernel 越复杂（attention 有两个 `tl.dot`、一堆逐元素运算），这一段越长。
- **Python → TTIR 也不便宜**：遍历 AST、调用 builder，十几到二十几毫秒。第一次编译时它还要多花将近一秒做每个进程只做一次的准备工作，所以脚本先编了一个小 kernel 把它排除掉。
- **「第一次调用一共」比各段加起来多出来的部分**，是加载二进制、建立启动器、第一次启动。在 Intel 上，SPIR-V 到机器码的编译就发生在加载这一步：驱动里的 IGC（第 14 章那个内部错误就是它报的）这时才真正编译 kernel。

可是上面的表里，matmul 和 attention「多出来的」只有十几到二十几毫秒，IGC 编一个 256×256 的 GEMM 怎么会这么快？原因是**驱动有自己的缓存**。Intel GPU 的计算运行时（compute-runtime）默认把编译结果存在 `~/.cache/neo_compiler_cache` 下，同一份 SPIR-V 第二次加载时直接用缓存。设环境变量 `NEO_CACHE_PERSISTENT=0` 关掉它，再跑一次：

`compile()` 里各段的时间几乎不变，matmul 和 attention 的第一次调用却多了 0.3 到 0.5 秒：**IGC 编译 SPIR-V 的时间，比 `compile()` 里所有的段加起来还长**。这对测量和调试都有影响：

- 第 4 章说「第二次运行时命中磁盘缓存，第一次调用很快」，在 Intel 上其实有**两层**磁盘缓存：Triton 的（`~/.triton/cache`，存 TTIR 到 SPIR-V），和驱动的（存机器码）。清掉 Triton 的缓存、不清驱动的，看到的编译时间会偏短。
- 反过来，用 `TRITON_ALWAYS_COMPILE=1` 测编译时间时，驱动缓存照样生效，量不到 IGC 的时间。

NVIDIA 上没有这一层：`ptxas` 在 `compile()` 里就把 PTX 编成了 cubin，存进 Triton 的缓存；加载 cubin 只是把它交给驱动。（这一点本书还没有在 A10 上实测。）

## 在任何一级停下来看，或者改写它

四个环境变量，从粗到细：

| 环境变量 | 作用 |
| --- | --- |
| `TRITON_ALWAYS_COMPILE=1` | 不用磁盘缓存，每次都从头编译（`compile()` 里的 `always_compile`）。改了 Triton 本身、想确认新的 pass 生效时用 |
| `TRITON_KERNEL_DUMP=1` | 把每一级的结果另存一份到 `TRITON_DUMP_DIR`（默认 `~/.triton/dump`）。和缓存目录的区别是：子目录名只由源码、参数类型和 constexpr 的值决定（`ASTSource.hash()`），不随 Triton 版本、`num_warps` 这类编译选项变，方便对比 |
| `TRITON_KERNEL_OVERRIDE=1` | 编译到某一级时，如果 `TRITON_OVERRIDE_DIR`（默认 `~/.triton/override`）里有同名文件，就**用文件里的 IR 替换**这一级的结果，后面的段接着从它编下去 |
| `MLIR_ENABLE_DUMP=1` 或 `=<kernel 名>` | 每个 MLIR pass 之前打印整个 module（第 18 章），配合 `MLIR_DUMP_PATH` 写进文件 |

`TRITON_KERNEL_OVERRIDE` 是一个很有用的调试手段：怀疑某个 pass 生成的 IR 有问题，或者想试试「如果编译器这样做会不会更快」，可以直接改 IR，不必改 Triton 的 C++ 再重新编译。试一个最简单的：一个 `out = x + y` 的 kernel，先导出各级 IR，把 TTGIR 里的 `arith.addf` 改成 `arith.subf`，再用它覆盖：

```python-norun
# axpy.py
import torch
import triton
import triton.language as tl

from minillm import DEVICE


@triton.jit
def axpy(x_ptr, y_ptr, out_ptr, n, BLOCK: tl.constexpr):
    offs = tl.program_id(0) * BLOCK + tl.arange(0, BLOCK)
    mask = offs < n
    tl.store(out_ptr + offs, tl.load(x_ptr + offs, mask=mask) + tl.load(y_ptr + offs, mask=mask), mask=mask)


x = torch.full((8,), 5.0, device=DEVICE)
y = torch.full((8,), 2.0, device=DEVICE)
out = torch.empty(8, device=DEVICE)
axpy[(1,)](x, y, out, 8, BLOCK=8)
print(out.tolist())
```


```bash
# 1. 导出：每一级都存一份到 dump/<源码的 hash>/
TRITON_KERNEL_DUMP=1 TRITON_DUMP_DIR=dump python axpy.py
find dump -type f | sort
# 2. 只留下 TTGIR，把加法改成减法
mkdir -p ovr && cp -r dump/* ovr/ && find ovr -type f ! -name '*.ttgir' -delete
sed -i 's/arith.addf/arith.subf/' ovr/*/axpy.ttgir
# 3. 覆盖。换一个空的缓存目录，否则缓存命中，根本不会走到编译
TRITON_CACHE_DIR=fresh TRITON_KERNEL_OVERRIDE=1 TRITON_OVERRIDE_DIR=ovr python axpy.py
```

（第一行是第 1 步的输出；中间四行是 `find dump -type f | sort` 列出的导出文件；最后两行是第 3 步的输出。）

源码一个字没改，kernel 算出了 5 − 2 = 3。注意替换发生在「`ttgir` 这一段的 pass 都跑完之后」：Triton 先照常编出 TTGIR，再丢掉它、换成文件里的版本，然后 `llir` 段从这个版本接着编。所以你改的是 TTGIR 段的**输出**。改 `ttir` 文件，TTGIR 段的所有 pass 会在你的版本上重新跑一遍；改 `llir` 文件，就只剩最后一级。

两个容易踩的地方：一是第 3 步必须换一个空的缓存目录（或者设 `TRITON_ALWAYS_COMPILE=1`），否则磁盘缓存命中，`compile()` 在查缓存那一步就返回了；二是覆盖目录里只放你想替换的那一级，其余的文件删掉，否则每一级都会被「替换」成原样，看不出效果，还容易混淆。

autotune 也支持类似的事情：`triton.Config(..., ir_override="path/to/kernel.ttgir")`，对某一个配置用指定的 IR（`compile()` 里的 `ir_override` 那一段）。

## 动手

1. **在你的 GPU 上测各段的时间。** 跑本章的脚本。NVIDIA 上多了 `ptx`、`cubin` 两段，`ptxas` 要花多久？「第一次调用一共」比各段之和多出来的部分，是不是比 Intel 关掉驱动缓存时小得多？
2. **用 override 验证一个猜想。** 第 17 章说「因果 attention 在关掉 `ReduceVariableLiveness` 时更快」。导出默认设置和 `reduce_variable_liveness=False` 两种 TTGIR，对比 Q 的 `descriptor_load` 在循环里还是循环外。再把关掉时的 TTGIR 用 `TRITON_KERNEL_OVERRIDE` 塞给默认设置的 kernel，速度是不是也变快了？这样就能确认，差别完全来自 TTGIR 这一级，而不是后面的段。
3. **数你的 kernel 有多少个 pass。** 用 `MLIR_ENABLE_DUMP` 看第 17 章的 attention kernel，按本章的表分段数一数。和 `row_sum` 比，哪一段的 pass 数变了？（提示：pass 的个数基本是固定的，变的是每个 pass 做了多少事。）

---

**这一章的要点**

- `compile()`（`python/triton/compiler/compiler.py`）：算缓存键、查磁盘缓存；不命中就 `make_ir`（`code_generator.py` 遍历 Python AST 生成 TTIR），再按后端 `add_stages` 填好的顺序逐段编译，每一段的结果写进缓存。NVIDIA：`ttir → ttgir → llir → ptx → cubin`；Intel：`ttir → ttgir → llir → spv`（设 `TRITON_XPU_GEN_NATIVE_CODE=1` 时再加 `zebin`）。
- 按段分：`row_sum` 在 sm_86 上是 10 + 44 + 19 个 MLIR pass，在 Max 1100 上是 20 + 32 + 19 个。`ttgir` 段（layout、矩阵指令、流水）是 Triton 的核心。
- `triton.knobs.compilation.listener` 拿到每段的耗时。Max 1100 上 `llir` 段最贵；而 Intel 上真正把 SPIR-V 编成机器码的 IGC，在加载时才运行，还有驱动自己的磁盘缓存（`~/.cache/neo_compiler_cache`）。用 `NEO_CACHE_PERSISTENT=0` 关掉它，第一次调用多了 0.3–0.5 秒，比 `compile()` 本身还长。
- 四个环境变量：`TRITON_ALWAYS_COMPILE`（不用缓存）、`TRITON_KERNEL_DUMP` + `TRITON_DUMP_DIR`（导出每一级）、`TRITON_KERNEL_OVERRIDE` + `TRITON_OVERRIDE_DIR`（用你的文件替换某一级的输出，后面接着编）、`MLIR_ENABLE_DUMP`（每个 pass）。override 时要换空的缓存目录，覆盖目录里只放要替换的那一级。

下一章开始讲 `ttgir` 段的核心：layout。`#blocked`、`#mma`、`#dot_op`、`#linear` 各自描述了什么，为什么 GPU 编译器需要这层抽象，并配一个浏览器里的模拟器，画出每个元素归哪个线程。
