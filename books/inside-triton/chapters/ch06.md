## 一行放得进一个 program

先写最直接的版本：一个 program 处理一整行，`BLOCK` 取不小于行长的 2 的幂，一次读进来，归约，写出去。这就是第 1 章那个 softmax，minillm 里稍作加固：

```triton-norun
@triton.jit
def _softmax_fused_kernel(x_ptr, y_ptr, n_cols, stride_x, stride_y, BLOCK: tl.constexpr):
    row = tl.program_id(0).to(tl.int64)          # 行号转成 int64：行数 × stride 可能超过 2^31（第 5 章）
    cols = tl.arange(0, BLOCK)
    mask = cols < n_cols
    x = tl.load(x_ptr + row * stride_x + cols, mask=mask, other=-float("inf")).to(tl.float32)
    x = x - tl.max(x, axis=0)                    # 减去最大值：exp 不会溢出
    e = tl.exp(x)
    y = e / tl.sum(e, axis=0)
    tl.store(y_ptr + row * stride_y + cols, y, mask=mask)   # store 会转回 y 的 dtype
```

和第 1 章相比多了三处，每一处都对应前一章的一条规则：

- **行号转成 int64。** `row * stride_x` 在一个几十亿元素的 logits 张量上会溢出 int32。
- **`stride_x` 作为参数传进来**，而不是假设行与行紧挨着。从一个更大的张量里切出来的视图（`big[:, :2000]`）也能处理，只要最后一维是连续的。
- **在 fp32 里算**，最后由 `tl.store` 转回输入的 dtype。

为什么要先减去最大值？softmax 的值只和各元素之间的**差**有关：`exp(x_i) / Σ exp(x_j)` 的分子分母同乘 `exp(-m)`，结果不变。但 `exp` 本身很容易溢出：fp32 的 `exp(89)` 就已经是 `inf`，而 logits 上百是常有的事。减去最大值以后，指数的参数都 ≤ 0，`exp` 落在 (0, 1] 之间，永远不会溢出。这一节后面的模拟器会演示这一点。

RMSNorm 的结构一样：一个 program 一行，求平方和，乘上 `rsqrt`，再乘权重：

```triton-norun
@triton.jit
def _rmsnorm_kernel(x_ptr, w_ptr, y_ptr, n_cols, stride_x, stride_y, eps, BLOCK: tl.constexpr):
    row = tl.program_id(0).to(tl.int64)
    cols = tl.arange(0, BLOCK)
    mask = cols < n_cols
    # 在 fp32 里求平方和：bf16 的平方和很容易丢精度
    x = tl.load(x_ptr + row * stride_x + cols, mask=mask, other=0.0).to(tl.float32)
    mean_sq = tl.sum(x * x, axis=0) / n_cols     # other=0：被 mask 掉的位置不影响平方和
    rstd = tl.rsqrt(mean_sq + eps)
    w = tl.load(w_ptr + cols, mask=mask, other=0.0).to(tl.float32)
    tl.store(y_ptr + row * stride_y + cols, x * rstd * w, mask=mask)
```

注意两个 kernel 的 `other` 不一样：softmax 要求最大值，填 `-inf`；RMSNorm 求平方和，填 0（第 5 章：`other` 要填归约运算的单位元）。

## 多长才算「放不下」：寄存器

一个 program 一次装下一整行，这一行的数据放在哪里？放在执行这个 program 的那些线程的**寄存器**里。一行 `BLOCK` 个元素、`num_warps` 个 warp，平均每个线程要放 `BLOCK / (32 × num_warps)` 个元素。寄存器是有限的：寄存器不够，编译器只好把一部分值暂存到慢得多的内存里，用的时候再读回来，这叫**寄存器溢出（register spill）**。

Triton 加载 kernel 时会从驱动拿到这个 kernel 用了多少寄存器、溢出了多少，记在 `CompiledKernel` 的 `n_regs` 和 `n_spills` 上（`python/triton/compiler/compiler.py`）。下面的实验把行长从 1024 加到 32768，`num_warps` 取 4、8、16，把这两个数和带宽一起打出来：

```triton
# arch: sm80 xpu
import torch
import triton
import triton.language as tl

DEVICE = triton.runtime.driver.active.get_active_torch_device()


@triton.jit
def softmax_kernel(x_ptr, y_ptr, n_cols, BLOCK: tl.constexpr):
    row = tl.program_id(0)
    cols = tl.arange(0, BLOCK)
    mask = cols < n_cols
    x = tl.load(x_ptr + row * n_cols + cols, mask=mask, other=-float("inf"))
    x = x - tl.max(x, axis=0)
    e = tl.exp(x)
    tl.store(y_ptr + row * n_cols + cols, e / tl.sum(e, axis=0), mask=mask)


for n in (1024, 4096, 8192, 16384, 32768):
    x = torch.randn(4096, n, device=DEVICE); y = torch.empty_like(x)
    for nw in (4, 8, 16):
        k = softmax_kernel[(4096,)](x, y, n, BLOCK=n, num_warps=nw)     # 返回编译好的 kernel
        ms = triton.testing.do_bench(lambda: softmax_kernel[(4096,)](x, y, n, BLOCK=n, num_warps=nw))
        flags = getattr(k.metadata, "build_flags", "")                    # Intel 后端才有这个字段
        print(f"n={n:6} num_warps={nw:2}  每线程 {n // (32 * nw):4} 个元素  n_regs={k.n_regs} n_spills={k.n_spills}"
              f"  {2 * x.numel() * 4 / ms / 1e6:5.0f} GB/s  {flags.strip()}")
```

规律一目了然：

- **每个线程分到的元素越多，越容易溢出，溢出越多，带宽越低。** 最糟的一行是 32768 列、4 个 warp：每个线程 256 个元素，溢出 210，带宽只剩 376 GB/s。同样的行长换成 16 个 warp，每个线程 64 个元素，不溢出，带宽 717 GB/s，是这张表里最快的。第 1 章那个手写 softmax 在 32768 列时掉到 382 GB/s，原因就在这里：它用的是默认的 4 个 warp。
- **Intel 后端会自己想办法。** `n_regs` 在 Intel 上是每个硬件线程的通用寄存器（GRF）个数，默认 128。编译后一旦发现溢出，后端会加上 `-cl-intel-256-GRF-per-thread` 重新编译一次，让每个线程拿到 256 个寄存器，代价是同时驻留的线程变少（第 2 章的占用率）。上表里所有 `n_regs=256` 的行都是这么来的。判断要不要重编的逻辑在 Intel 后端的 `third_party/intel/backend/compiler.py`，函数是 `extract_spill_size_from_zebin` 和 `accepts_default_grf`。NVIDIA 后端没有这一步，寄存器的分配完全交给 `ptxas`。
- **加 warp 是最直接的办法**，但有上限：一个 program 最多 32 个 warp（1024 个线程）。所以一次装下的行长也有上限。

minillm 据此定了一条简单的规则：`num_warps = max(4, min(32, BLOCK // 512))`，让每个线程大约拿 8–32 个元素；`BLOCK` 超过 16384 就不再一次装下，改走下一节的循环版本。这条规则不是最优的，第 14 章讲 autotune 时再回来调它。

## 放不下的时候：沿着行循环

行再长，比如词表维度上的 softmax，一行有十几万个元素，就只能分段处理：每次读 `BLOCK` 个，循环到行尾。问题是 softmax 要用到**整行**的最大值和指数和，读完第一段时还不知道后面有没有更大的值。

最直接的办法是**扫三遍**：第一遍求最大值，第二遍用这个最大值求指数和，第三遍算结果、写出去。第 1 章里 Inductor 生成的 kernel 就是这么做的。每一遍都要把这一行从头读一次，加上写，一共 4 趟。

能不能少读一遍？关键在于：指数和 `l = Σ exp(x_j - m)` 依赖最大值 `m`，但**换一个基准是很便宜的**。假设已经读完前几段，手上有「到目前为止的最大值 `m`」和「以 `m` 为基准的指数和 `l`」。新读进一段，它的最大值让 `m` 变成了 `m_new`。之前累加的每一项 `exp(x - m)` 换到新基准下都是 `exp(x - m_new) = exp(x - m) · exp(m - m_new)`，所以整个 `l` 乘上同一个因子 `exp(m - m_new)` 就行了：

```
m_new = max(m, max(这一段))
l     = l · exp(m − m_new) + Σ exp(这一段 − m_new)
```

扫完一遍，`m` 就是整行的最大值，`l` 就是整行的指数和。再扫第二遍写出结果，一共读 2 遍、写 1 遍，3 趟。这就是 **online softmax**（Milakov 和 Gimelshein 在 2018 年的论文里提出）。

下面的模拟器把一行 12 个数分成 3 段，一段一段地更新 `m` 和 `l`，最后和普通的两遍算法比较。只用标准库，直接点运行；可以改 `row` 和 `CHUNK`：

```python
# online softmax：一边扫一边维护最大值 m 和指数和 l，扫完一遍就得到整行的 m 和 l。只用标准库。
import math

row = [3.0, 1.0, 4.0, 1.0, 5.0, 9.0, 2.0, 6.0, 5.0, 3.0, 5.0, 8.0]
CHUNK = 4                      # 一次只能「装下」4 个元素：相当于 kernel 里的 BLOCK


def softmax_two_pass(xs):
    m = max(xs)
    l = sum(math.exp(x - m) for x in xs)
    return m, l


def softmax_online(xs, chunk):
    m, l = -math.inf, 0.0
    for start in range(0, len(xs), chunk):
        block = xs[start:start + chunk]
        m_new = max(m, max(block))
        # 基准从 m 换成 m_new：之前累加的每一项 exp(x - m) 都要乘上 exp(m - m_new)
        l = l * math.exp(m - m_new) + sum(math.exp(x - m_new) for x in block)
        print(f"  读到第 {start:2}–{start + len(block) - 1:2} 个：block 最大 {max(block):3}，"
              f"m {m:4} -> {m_new:3}，l = {l:.6f}")
        m = m_new
    return m, l


print("online，逐段更新：")
m1, l1 = softmax_online(row, CHUNK)
m2, l2 = softmax_two_pass(row)
print(f"online：m = {m1}，l = {l1:.12f}")
print(f"两遍：  m = {m2}，l = {l2:.12f}")
print("两者的 softmax 最大差：", max(abs(math.exp(x - m1) / l1 - math.exp(x - m2) / l2) for x in row))

# 为什么一定要减最大值：logit 大一点，exp 就超出浮点数的范围
big = [x + 1000 for x in row]
try:
    print(sum(math.exp(x) for x in big))
except OverflowError as e:
    print("不减最大值：exp(1003) ->", e)
m, l = softmax_two_pass(big)
print(f"减了最大值：m = {m}，l = {l:.12f}（和上面的 l 一样：softmax 只和差值有关）")
```

运行结果：

```
  读到第  4– 7 个：block 最大 9.0，m  4.0 -> 9.0，l = 1.078902
  读到第  8–11 个：block 最大 8.0，m  9.0 -> 9.0，l = 1.485892
```

第二段读进来时，最大值从 4 变成了 9，之前的 `l` 被乘上 `exp(4 − 9)`，一下子从 1.467 缩到了零点几，再加上新的一段，变成 1.079。最后的 `l` 和两遍算法完全一样。最后几行演示了为什么一定要减最大值：给每个数都加上 1000，直接求 `exp` 就溢出了；减去最大值以后，`l` 和原来一模一样。

写成 Triton，就是 minillm 里的 `_softmax_online_kernel`。第一遍的循环里，`m` 和 `l` 是跨循环迭代的标量：

```triton-norun
    m = -float("inf")
    l = 0.0
    for start in range(0, n_cols, BLOCK):
        cols = start + tl.arange(0, BLOCK)
        x = tl.load(x_row + cols, mask=cols < n_cols, other=-float("inf")).to(tl.float32)
        m_new = tl.maximum(m, tl.max(x, axis=0))
        # 最大值变大了：之前累加的和要按新的基准缩小 exp(m - m_new) 倍
        l = l * tl.exp(m - m_new) + tl.sum(tl.exp(x - m_new), axis=0)
        m = m_new
    # 第二遍：有了整行的 m 和 l，再读一遍，写出结果
    for start in range(0, n_cols, BLOCK):
        cols = start + tl.arange(0, BLOCK)
        mask = cols < n_cols
        x = tl.load(x_row + cols, mask=mask, other=-float("inf")).to(tl.float32)
        tl.store(y_row + cols, tl.exp(x - m) / l, mask=mask)
```

`for start in range(0, n_cols, BLOCK)` 是 Triton 里的普通循环，`n_cols` 是运行时的值，循环次数在运行时才知道（编译成 IR 里的 `scf.for`，第 18、19 章）。

online softmax 的价值远不止「少读一遍」。第 1 章说过，FlashAttention 要把 `QKᵀ`、softmax、乘 `V` 融进一个 kernel，难点就在于 softmax 需要整行的统计量。online softmax 让「一段一段地处理、随时修正之前的结果」成为可能：第 17 章，那个 `l · exp(m − m_new)` 的修正因子，会同时乘到已经累加的输出上。

```
    online（读 2 遍）        2.510 ms   有效带宽   428 GB/s
    三遍（读 3 遍）            3.357 ms   有效带宽   320 GB/s
    torch.softmax        2.485 ms   有效带宽   432 GB/s
```

分三档看：

- **32768 列**：三种写法差得不多。一行只有 128 KiB，第二遍、第三遍读的时候，数据大多还在缓存里，多读的那几遍几乎不走显存。这一档三种写法里一次装下最快，和 `torch.softmax` 打平。
- **131072 列**：一行 512 KiB，几百个 program 同时在跑，缓存装不下了，预测开始应验。online 比三遍快 1.32 倍（预测 4/3 ≈ 1.33），一次装下比 online 快 1.52 倍（预测 3/2 = 1.5）。
- **262144 列**：一次装下的版本崩了（每个线程 256 个元素，溢出），只剩 356 GB/s。online 和 `torch.softmax` 打平，三遍仍然慢 1/3。

结论是 minillm 的那条规则：**放得下就一次装下，放不下就用 online，不要用三遍**。`softmax` 函数会根据行长自动选择。

## RMSNorm：融合省下的是 fp32 的中间结果

RMSNorm 的 hidden 维通常在 2048 到 16384 之间，一次装下就够了。和它比的是三种现成的写法：照着公式写的 eager 版、交给 `torch.compile` 的同一段代码，以及 PyTorch 自带的 `F.rms_norm`。

先预测 eager 版有多慢。它的写法是：

```python-norun
def rmsnorm_eager(x, w, eps=1e-6):
    xf = x.float()
    return (xf * torch.rsqrt(xf.pow(2).mean(-1, keepdim=True) + eps) * w.float()).to(x.dtype)
```

数一数每个元素要搬多少字节（每行一个数的那些、以及 `w` 很小，忽略）：`x.float()` 读 bf16 写 fp32，6 字节；`pow(2)` 读写 fp32，8 字节；`mean` 读 4 字节；乘 `rsqrt` 读写 8 字节；乘 `w` 读写 8 字节；`.to(x.dtype)` 读 fp32 写 bf16，6 字节。一共 40 字节。融合版只读 bf16、写 bf16，4 字节。**预测慢 10 倍。** 注意 eager 版的中间结果都是 fp32，比输入大一倍，这让它的流量又翻了一番。

---

**这一章的要点**

- 按行归约的算子（softmax、RMSNorm）是访存受限的，好坏看**一行读几遍**。`other` 填归约的单位元：softmax 求最大值填 `-inf`，RMSNorm 求平方和填 0。
- 一个 program 装下一整行，数据放在寄存器里，每个线程 `BLOCK / (32 × num_warps)` 个元素。**放不下的意思是寄存器溢出**：`CompiledKernel.n_spills` 会告诉你。Max 1100 上，32768 列、4 个 warp 溢出 210，带宽 376 GB/s；换成 16 个 warp 不溢出，717 GB/s。Intel 后端发现溢出会自动换成 256 个 GRF 的模式重编。
- 行太长就循环。三遍算法读 3 遍；**online softmax** 边扫边维护最大值 `m` 和指数和 `l`，最大值变大时把 `l` 乘上 `exp(m − m_new)`，只读 2 遍。实测在 131072 列时，online 比三遍快 1.32 倍，几乎正好是 4/3。
- 一定要先减去最大值再求 `exp`：结果不变，而且永远不会溢出。
- RMSNorm 的 eager 写法每个元素要搬 40 字节（中间结果都是 fp32），融合后 4 字节。Max 1100 上实测慢 8.3 倍。
