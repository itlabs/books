## `ttgir` 段的 pass 地图

第 19 章数过，`row_sum` 在 sm_86 上 `ttgir` 段有 44 个 pass，Max 1100 上 32 个。其中很多是 canonicalize、CSE 这种清理，真正决定性能的是下面这些（大致按执行顺序）：

| pass | 后端 | 做什么 | 本书哪里见过它的效果 |
| --- | --- | --- | --- |
| `convert-triton-to-tritongpu` | 共用 | 给每个张量一个初始的 `#blocked` layout，module 上加 `num-warps` 等属性 | 第 18 章 |
| `tritongpu-coalesce` | 共用 | 按「最内维连续、每个线程 16 字节」给访存选 layout | 第 20 章（fp32 选 4 个，fp16 选 8 个） |
| `tritongpu-remove-layout-conversions` | 各有一份 | 沿数据流传播 layout，删掉多余的 `convert_layout`，必要时重算 | 第 21 章（FlashAttention 从 39 个降到 2 个） |
| `tritongpu-accelerate-matmul` | 各有一份 | 把 `tt.dot` 换到矩阵单元：结果用 `#mma` / `#ttig.dpas`，输入插入到 `#dot_op` 的转换 | 第 15 章（`num_warps < 4` 丢了 `wgmma`）、第 20 章 |
| `tritongpu-optimize-dot-operands` | 各有一份 | 整理 `tl.dot` 输入前面的 layout 转换 | |
| `TritonIntelGPUMaterializeBlockPointer` | Intel | 证明对齐以后，给 descriptor 读写标上 `ttig.block_io` | 第 15 章（两个对齐的坑） |
| `tritongpu-assign-latencies` → `schedule-loops` → `pipeline` | NVIDIA | 软件流水：多缓冲、`cp.async` / TMA | 第 13 章 |
| `TritonIntelGPUPipeline` | Intel | 软件流水：提前 `num_stages − 1` 轮发预取 | 第 13 章 |
| `TritonIntelGPUReduceVariableLiveness` | Intel | 寄存器压力大时，把大张量的 load 挪到用它的地方 | 第 17 章 |
| `nvgpu-warp-specialization` | NVIDIA | 按 `warp_specialize=True` 的提示拆分 warp | 第 15 章（只在 sm_100 上生效） |
| `tritongpu-prefetch` | NVIDIA | 把 `tl.dot` 的输入提前从 shared memory 读进寄存器 | |
| `tritongpu-reduce-data-duplication`、`reorder-instructions` | 共用 | 减少重复的数据、调整指令顺序 | |

（pass 的名字是 `MLIR_ENABLE_DUMP` 打印出来的那种；C++ 源码在 `lib/Dialect/TritonGPU/Transforms/` 和各后端的 `third_party/<后端>/lib/` 下。）

这张表里有两种 pass：一种是「每个 kernel 都一样」的，比如 coalesce 总是在找连续的那一维；另一种是**启发式**的，根据寄存器压力、形状、目标架构做取舍，`ReduceVariableLiveness` 就是。启发式的 pass 有时会做出对这个 kernel 不好的决定，这正是性能定位最常见的起点。

## 定位一个性能问题的步骤

不管问题出在哪，大致都是这几步：

1. **复现，并把它缩小**。确认差距稳定（第 11 章：多测几次，看分位数；第 17 章：注意降频），然后找到「刚好有问题」和「刚好没问题」的两个版本，差别越小越好。
2. **对比 IR**。用 `kernel.asm["ttgir"]` 或 `TRITON_KERNEL_DUMP`（第 19 章）拿到两个版本的 TTGIR，看差在哪。
3. **做控制变量的实验**。IR 里的差别往往不止一处，一次只改一个，看哪个和性能对得上。
4. **往下看一级**。TTGIR 差不多、性能却差很多时，问题在后面：LLVM IR、PTX / SASS，Intel 上是 IGC 生成的汇编。
5. **读源码**。找到是哪个 pass（或者哪一级编译器）的哪个决定，弄明白它为什么这么做。

下面把这五步完整地走一遍。

## 案例：因果 attention 的 24%

### 第 1 步：复现，缩小

第 17 章的现象（Max 1100，D = 128，256 × 64，32 个 warp）：

| | `ReduceVariableLiveness` 打开（默认） | 关掉 |
| --- | ---: | ---: |
| 非因果 | 93.8 TFLOP/s | 92.1 |
| 因果 | 78.0 | 96.4 |

非因果时这个 pass 无关紧要，因果时关掉它快 24%。两个版本的差别只是一个编译选项，已经足够小了。

### 第 2 步：对比 TTGIR

第 17 章已经做过：打开这个 pass 时，Q 的 `descriptor_load` 被挪进了循环，每一轮重读；关掉时 Q 在循环外读一次。TTGIR 里其余的部分几乎一样。可问题是，**非因果的 kernel 也有完全相同的差别**，却没有变慢。所以「Q 在不在循环里」只是一半原因，另一半要到「因果」和「非因果」的差别里去找。

### 第 3 步：控制变量

因果和非因果在 kernel 里有两处不同：

- **mask**：对角线上要用 `tl.where(offs_m >= offs_n, qk, -inf)` 屏蔽上三角；
- **循环次数**：只循环到对角线（`hi = (pid_m + 1) · BLOCK_M`），每个 program 平均 34 轮，而不是 64 轮。

把它们拆成两个独立的开关：`MASK` 只管加不加 mask，`SKIP` 只管跳不跳上三角。`MASK = True, SKIP = False` 是一个「每块都算、但都做 mask」的版本：结果和因果一样，只是白算了一半。四种组合，每种都开、关 `ReduceVariableLiveness` 各测一次。

第 4 步要看 IGC 的汇编，所以这个实验顺便把它也导出来。Intel 后端有一个环境变量 `TRITON_INTEL_ENABLE_IGC_SHADER_DUMP=1`：设了以后，Triton 改用 `ocloc` 在 `compile()` 里生成机器码（第 19 章的 `zebin` 那一级），同时让 IGC 把中间结果和最终的汇编（`*.asm`）写进这个 kernel 的缓存目录。下面的脚本每种组合用一个空的缓存目录，测完速度，再从汇编里读三样东西：寄存器分配用了哪种策略、溢出了多少字节、主循环（有 `dpas` 的那个循环）里有多少条指令：

```triton
# arch: xpu
import glob
import os
import re
import tempfile
import time

os.environ["TRITON_INTEL_ENABLE_IGC_SHADER_DUMP"] = "1"   # 让 IGC 把汇编导出到缓存目录（第 22 章）
import torch                                              # noqa: E402
import triton                                             # noqa: E402
import triton.language as tl                              # noqa: E402

from minillm import DEVICE                                # noqa: E402


@triton.jit
def attn_var(q_ptr, k_ptr, v_ptr, o_ptr, sm_scale, N_CTX, ROWS, HEAD_DIM: tl.constexpr, BLOCK_M: tl.constexpr,
             BLOCK_N: tl.constexpr, MASK: tl.constexpr, SKIP: tl.constexpr):
    """第 17 章的 _attn_fwd_kernel，把「因果」拆成两个开关：MASK（对角线 mask）和 SKIP（跳过上三角的块）。"""
    pid_m = tl.program_id(0)
    hz = tl.program_id(1)
    q_desc = tl.make_tensor_descriptor(q_ptr, [ROWS, HEAD_DIM], [HEAD_DIM, 1], [BLOCK_M, HEAD_DIM])
    k_desc = tl.make_tensor_descriptor(k_ptr, [ROWS, HEAD_DIM], [HEAD_DIM, 1], [BLOCK_N, HEAD_DIM])
    v_desc = tl.make_tensor_descriptor(v_ptr, [ROWS, HEAD_DIM], [HEAD_DIM, 1], [BLOCK_N, HEAD_DIM])
    o_desc = tl.make_tensor_descriptor(o_ptr, [ROWS, HEAD_DIM], [HEAD_DIM, 1], [BLOCK_M, HEAD_DIM])
    base = hz * N_CTX
    offs_m = pid_m * BLOCK_M + tl.arange(0, BLOCK_M)
    q = q_desc.load([base + pid_m * BLOCK_M, 0])
    qk_scale = sm_scale * 1.4426950408889634
    m_i = tl.full([BLOCK_M], -float("inf"), tl.float32)
    l_i = tl.zeros([BLOCK_M], tl.float32)
    acc = tl.zeros([BLOCK_M, HEAD_DIM], tl.float32)
    hi = tl.minimum((pid_m + 1) * BLOCK_M, N_CTX) if SKIP else N_CTX
    for start_n in range(0, hi, BLOCK_N):
        k = k_desc.load([base + start_n, 0])
        qk = tl.dot(q, tl.trans(k)) * qk_scale
        if MASK:
            offs_n = start_n + tl.arange(0, BLOCK_N)
            qk = tl.where(offs_m[:, None] >= offs_n[None, :], qk, -float("inf"))
        m_new = tl.maximum(m_i, tl.max(qk, 1))
        p = tl.math.exp2(qk - m_new[:, None])
        alpha = tl.math.exp2(m_i - m_new)
        l_i = l_i * alpha + tl.sum(p, 1)
        v = v_desc.load([base + start_n, 0])
        acc = tl.dot(p.to(v.dtype), v, acc * alpha[:, None])
        m_i = m_new
    o_desc.store([base + pid_m * BLOCK_M, 0], (acc / l_i[:, None]).to(o_desc.dtype))


def read_asm(cache_dir):
    """IGC 导出的汇编：寄存器分配用了哪种策略、溢出了多少字节、主循环里有多少条指令。"""
    path = sorted(glob.glob(f"{cache_dir}/*/*_1_simd16_entry_0001.asm"))[-1]   # 最终用的那一份
    text = open(path).read()
    lines = text.splitlines()
    labels = {m.group(1): i for i, l in enumerate(lines) if (m := re.match(r"^([_A-Za-z0-9]+):\s*$", l))}
    loops = [(labels[m.group(1)], i) for i, l in enumerate(lines)
             if (m := re.search(r"jmpi\s+(\S+)", l)) and labels.get(m.group(1), i) < i]
    body = max((lines[a:b + 1] for a, b in loops), key=lambda b: sum("dpas" in x for x in b))   # 有 dpas 的那个循环
    n_instr = sum(1 for x in body if re.match(r"^\s*(\([^)]*\)\s*)?[a-z]", x))
    ra = re.search(r"//\.RA type\s+(\S+)", text).group(1).replace("GRAPH_COLORING_SPILL_", "")
    return ra, int(re.search(r"//\.spill size (\d+)", text).group(1)), n_instr


Z, H, N, D = 4, 32, 4096, 128
q, k, v = (torch.randn(Z, H, N, D, device=DEVICE, dtype=torch.bfloat16) for _ in range(3))
o = torch.empty_like(q)
print(f"{torch.xpu.get_device_name()}，triton {triton.__version__}，attention 256×64，D=128，32 个 warp")
print(" MASK  SKIP  ReduceVariableLiveness    TFLOP/s   IGC 的寄存器分配   溢出（字节）  主循环指令数")
for mask, skip in ((False, False), (True, False), (False, True), (True, True)):
    for rvl in (True, False):
        os.environ["TRITON_CACHE_DIR"] = tempfile.mkdtemp()      # 每种组合一个空的缓存目录，汇编不会混在一起
        run = lambda: attn_var[(N // 256, Z * H)](q, k, v, o, D ** -0.5, N, Z * H * N, HEAD_DIM=D, BLOCK_M=256,
                                                  BLOCK_N=64, MASK=mask, SKIP=skip, num_warps=32,
                                                  reduce_variable_liveness=rvl)
        run(); time.sleep(3)
        flops = 4 * Z * H * N * N * D * (0.5 if skip else 1)
        tflops = flops / triton.testing.do_bench(run) / 1e9
        ra, spill, n_instr = read_asm(os.environ["TRITON_CACHE_DIR"])
        print(f" {mask!s:5} {skip!s:5} {'开' if rvl else '关':^22} {tflops:9.1f}   {ra:16} {spill:9}   {n_instr:9}")
```

运行结果（Max 1100）：

```
Intel(R) Data Center GPU Max 1100，triton 3.9.0，attention 256×64，D=128，32 个 warp

 False False           关                 92.0   FF_RA                 5440         818

 False True            开                 83.1   FF_RA                 3712         865

 True  True            关                 96.1   RR_BC_RA              5824         873
```

（`SKIP = True` 的两组按「只算下三角」计算 FLOP，所以 TFLOP/s 可以和 `SKIP = False` 的直接比。）

先只看 TFLOP/s 那一列：

- 没有 mask 时（第 1、2 行，第 5、6 行），开不开这个 pass 只差 2%–3%，不管跳不跳上三角。
- **有 mask 时（第 3、4 行，第 7、8 行），关掉 pass 都快了 20% 以上**：不跳上三角时从 90.4 到 110.0，跳的时候从 78.3 到 96.1。

所以触发条件是 **mask**，和循环次数无关。第 4 行还有一个更奇怪的数：**多做了 mask 的 kernel（110.0）比不做 mask 的（92.0）还快**。mask 只会增加指令，不可能让计算本身变快，只能是它改变了编译的结果。

### 第 4 步：往下看一级

TTGIR 的层面已经解释不了了，往下看 IGC 的汇编。最直接的指标是溢出的字节数和主循环的指令数，但它们和速度对不上：最快的两种（110.0 和 96.1）溢出反而最多（5632、5824 字节），主循环的指令数也不是最少的。

对得上的是倒数第三列，IGC 在汇编开头记录的**寄存器分配策略**（`//.RA type` 那一行）：八种组合里，**快的那两种是 `RR_BC_RA`，其余六种全是 `FF_RA`**，一个例外也没有。

### 第 5 步：读源码

这两个名字在 IGC 的源码里（GitHub 上的 intel/intel-graphics-compiler，`visa/G4_Kernel.hpp` 列出所有的 RA 类型，`visa/GraphColor.cpp` 决定用哪一种）。记录类型的那段代码是：

```cpp
  if (liveAnalysis.livenessClass(G4_GRF)) {
    if (colorHeuristicGRF == ROUND_ROBIN) {
      kernel.setRAType(doBankConflict ? RA_Type::GRAPH_COLORING_RR_BC_RA
                                      : RA_Type::GRAPH_COLORING_RR_RA);
    } else {
      kernel.setRAType(doBankConflict ? RA_Type::GRAPH_COLORING_FF_BC_RA
                                      : RA_Type::GRAPH_COLORING_FF_RA);
    }
  }
```

RR 是 round robin（轮流分配寄存器），FF 是 first fit（用第一个空闲的），BC 是 bank conflict（减少寄存器文件的 bank 冲突）。选择的逻辑在同一个文件里，注释写得很清楚：

```cpp
  //
  // assign registers for GRFs, GRFs are first attempted to be assigned using
  // round-robin and if it fails then we retry using a first-fit heuristic.
  //
```

后面的代码是：先用 round robin 加 bank 冲突优化（`assignColors(ROUND_ROBIN, doBankConflictReduction, ...)`）；失败了，再用 first fit 加 bank 冲突优化试一次；还不行，就退回**不做 bank 冲突优化的 first fit**。我们看到的 `FF_RA`（没有 `BC`）就是最后这一档。

这就解释了整件事：

- 寄存器文件分成几个 bank，一条指令的几个源操作数如果落在同一个 bank 上，就要多花周期去读。DPAS 一条指令要读一大块寄存器，对 bank 冲突格外敏感。
- 六个慢的版本，寄存器分配的第一次尝试都失败了，一路退到了不考虑 bank 冲突的那一档；两个快的版本第一次就成功了，溢出虽多，指令却排得好。
- 至于「为什么偏偏是 mask 加上 Q 留在寄存器里时，round robin 能成功」，那取决于每个变量的活跃区间怎样交错，是一个对输入非常敏感的结果。IR 稍微变一点（多一个 `where`、Q 的 load 挪个位置），着色的结果就可能翻转。我没有再往下追是哪个变量导致了失败。

所以，第 17 章那 24% 的差别，**不是 `ReduceVariableLiveness` 做了一件「坏事」**。它确实减少了寄存器压力（溢出从 5824 字节降到 3840），只是 IGC 的寄存器分配器在它给出的 IR 上，恰好没能用上更好的策略。决定性能的那个分支，在 Triton 下面两级。

### 结论：作为 kernel 的作者能做什么

- **把编译选项当成调参的一维。** 你没法从 Triton 里直接指定 IGC 的寄存器分配策略，但能改变它的输入。`reduce_variable_liveness`、`grf_mode`（第 17 章）都是 `triton.Config` 里可以放的选项，交给 autotune 去测，比猜更可靠。minillm 的 `launch_config` 在因果、D = 128 时关掉这个 pass，就是测出来的结果。
- **性能和「溢出了多少」不一定单调。** 第 17 章、本章都看到了溢出更多反而更快的例子。溢出数是一个线索，不是结论。
- **一个快的配置可能很脆弱。** 这种「过不过一道阈值」的现象，换一个 Triton 版本、换一个驱动、改一行 kernel，都可能翻转。值得为关键 kernel 留一个性能回归测试。
- 如果确认是编译器的问题，带着最小的复现（这一章的脚本就是）去报告给上游。

## NVIDIA 上往下看什么

本章的工具在 NVIDIA 上对应的是：

- **PTX 和 SASS**：`kernel.asm["ptx"]` 是 PTX；`TRITON_KERNEL_DUMP=1` 时，`compile()` 会把 cubin 反汇编成 SASS，另存一份 `.sass`（第 19 章那段 `compile()` 的代码里，`if ext == "cubin"` 那两行）。
- **寄存器和溢出**：`kernel.n_regs`、`kernel.n_spills`（第 12 章）来自 `ptxas`。
- **ptxas 的决定**：和 IGC 一样，`ptxas` 的寄存器分配、指令调度也是 Triton 管不到的一层。SASS 里 `LDL` / `STL`（local memory 的读写）就是溢出。

本书还没有在 A10 上做过类似的定位。

## 动手

**这一章的要点**

- `ttgir` 段里决定性能的 pass：convert-triton-to-tritongpu（初始 layout）、coalesce（访存 layout）、remove-layout-conversions（删转换）、accelerate-matmul（选矩阵指令）、pipeline（流水）、Intel 的 MaterializeBlockPointer（block IO）和 ReduceVariableLiveness（寄存器压力）、NVIDIA 的 warp specialization。其中有不少是启发式的，可能对某个 kernel 做出不好的取舍。
- 定位五步：复现并缩小、对比 IR、控制变量、往下看一级、读源码。
- 第 17 章的案例：触发条件是对角线的 mask，不是循环次数；TTGIR 只差在 Q 的 load 在循环里还是循环外。往下看 IGC 的汇编（`TRITON_INTEL_ENABLE_IGC_SHADER_DUMP=1`），八种组合里快的两种恰好是寄存器分配成功用上了 round robin 加 bank 冲突优化（`RR_BC_RA`），其余全部退回了不做 bank 冲突优化的 first fit（`FF_RA`），和溢出量无关。
- 决定性能的分支可能在 Triton 之下（IGC、ptxas），你改变不了它的策略，但能改变它的输入：把 `reduce_variable_liveness`、`grf_mode` 这类选项当成 autotune 的一维，为关键 kernel 留性能回归测试。
