# 第 2 章 够用的 GPU 硬件模型

## 这一章想让你带走什么

<div class="goal-box">
<p>上一章说「GPU 在等数据，不在等计算」。这一章把这句话变成数字。写 Triton 不需要你懂 GPU 的每一个细节，但有四件事必须心里有数：<strong>计算单元有多少、每一层存储有多大多快、什么时候撞上带宽墙、什么时候撞上算力墙</strong>，以及 GPU 为什么要同时养着成千上万个线程。</p>
<p>读完你会拿到三样东西。一是你自己 GPU 的一张「体检表」：用一个 60 行的脚本量出缓存和显存的带宽、fp32 和矩阵单元的峰值，并且知道怎么从硬件参数把峰值推算出来。二是一条线：<strong>算术强度</strong>（每搬一个字节做几次运算）决定了一个 kernel 受带宽限制还是受算力限制，拐点在哪里可以直接算出来，这就是第 11 章 roofline 模型的直觉。三是一个浏览器里能跑的 warp 调度模拟器，看清「warp 越多越能藏住访存延迟」到底是怎么回事。后面讲 <code>num_warps</code>、<code>BLOCK_SIZE</code> 为什么会影响性能，靠的都是这一章的模型。</p>
</div>

## 先看一眼：量一量你的 GPU

先不讲结构，直接测。下面这个脚本做三个实验，每一个都对应本章后面的一节：

1. **拷贝**不同大小的数据，看带宽怎么随数据量变化：这是存储层级；
2. 让每个元素在寄存器里做 1 到 1024 次乘加，看耗时什么时候开始上涨：这是带宽墙和算力墙；
3. 用 fp32 和 fp16 各做一次大矩阵乘：这是矩阵单元。

```triton
# arch: sm80 xpu
import torch
import triton
import triton.language as tl

DEVICE = triton.runtime.driver.active.get_active_torch_device()
gpu = getattr(torch, DEVICE.type)


@triton.jit
def copy_kernel(x_ptr, y_ptr, n, BLOCK: tl.constexpr):
    offs = tl.program_id(0) * BLOCK + tl.arange(0, BLOCK)
    mask = offs < n
    tl.store(y_ptr + offs, tl.load(x_ptr + offs, mask=mask), mask=mask)


@triton.jit
def fma_kernel(x_ptr, y_ptr, n, ITERS: tl.constexpr, BLOCK: tl.constexpr):
    offs = tl.program_id(0) * BLOCK + tl.arange(0, BLOCK)
    mask = offs < n
    a = tl.load(x_ptr + offs, mask=mask)
    for _ in range(ITERS):             # 每次循环一个乘加（2 次浮点运算），全在寄存器里
        a = a * 0.999 + 0.001
    tl.store(y_ptr + offs, a, mask=mask)


def time_ms(fn, reps=50):
    """不清缓存的计时：同一份数据反复读，装得进缓存就会命中缓存。"""
    fn(); gpu.synchronize()
    start, end = gpu.Event(enable_timing=True), gpu.Event(enable_timing=True)
    start.record()
    for _ in range(reps):
        fn()
    end.record(); gpu.synchronize()
    return start.elapsed_time(end) / reps


drv = triton.runtime.driver.active
props = drv.utils.get_device_properties(drv.get_current_device())
print(f"{gpu.get_device_name()}，torch {torch.__version__}，triton {triton.__version__}")
print(f"  SM（Intel：Xe-core）{props['multiprocessor_count']} 个，频率 {props['sm_clock_rate'] / 1e6:.2f} GHz，"
      f"每个 program 最多 {props['max_shared_mem'] // 1024} KB shared memory")
print("实验 1：拷贝 n 字节（读 n + 写 n），不清缓存")
for mib in (1, 4, 16, 64, 256, 1024, 4096):
    x = torch.empty(mib * 2**20 // 4, device=DEVICE); y = torch.empty_like(x)
    ms = time_ms(lambda: copy_kernel[(triton.cdiv(x.numel(), 1024),)](x, y, x.numel(), BLOCK=1024))
    print(f"  {mib:5} MiB  {2 * x.numel() * 4 / ms / 1e6:6.0f} GB/s")
    del x, y

print("实验 2：64 Mi 个 fp32，每个元素读 4 字节、写 4 字节，中间做 ITERS 次乘加")
n = 64 * 2**20
x = torch.rand(n, device=DEVICE); y = torch.empty_like(x)
for iters in (1, 4, 16, 64, 256, 1024):
    ms = time_ms(lambda: fma_kernel[(triton.cdiv(n, 1024),)](x, y, n, ITERS=iters, BLOCK=1024), reps=20)
    flops = 2 * iters * n
    print(f"  ITERS={iters:5}  {flops / (8 * n):7.2f} FLOP/字节  {ms:7.3f} ms  "
          f"{8 * n / ms / 1e6:5.0f} GB/s  {flops / ms / 1e9:6.2f} TFLOP/s")

print("实验 3：矩阵乘（torch.matmul，4096×4096×4096）")
for dtype in (torch.float32, torch.float16):
    a = torch.randn(4096, 4096, device=DEVICE, dtype=dtype); b = torch.randn_like(a)
    ms = triton.testing.do_bench(lambda: a @ b)
    print(f"  {str(dtype):14} {2 * 4096**3 / ms / 1e9:6.1f} TFLOP/s")
```

这张图里有几个词，下面会反复出现：

- **SM（streaming multiprocessor）**：GPU 的计算单元，相当于 CPU 的一个核，但要宽得多。A10 有 72 个，Max 1100 有 56 个（Intel 叫 **Xe-core**）。一个 Triton program 从头到尾只在一个 SM 上跑。
- **warp**：SM 调度的最小单位，32 个线程绑在一起，**同一时刻执行同一条指令**，各自处理自己的数据。这种执行方式叫 **SIMT（single instruction, multiple threads）**，相当于 CPU 上 32 路的 SIMD。Intel GPU 上对应的是 **sub-group**，宽度是 16 或 32；Triton 在 Intel 上也沿用「warp」这个词。
- **shared memory**：每个 SM 上一小块由程序管理的高速存储，同一个 thread block 里的线程可以通过它交换数据（Intel 叫 **SLM，shared local memory**）。CUDA 程序员要亲手管理它；在 Triton 里，它由编译器替你分配，你在源码里看不到它（第 3 章、第 20 章）。
- **L2**：所有 SM 共享的缓存；**显存（HBM / GDDR）**：板子上的大内存，你的张量住在这里。

和 Triton 的概念对应起来：

| Triton | NVIDIA（CUDA） | Intel（SYCL） |
| --- | --- | --- |
| 一个 program | 一个 thread block（CTA） | 一个 work-group |
| `num_warps`（默认 4） | 每个 block 的 warp 数 | 每个 work-group 的 sub-group 数 |
| （看不见） | warp 里的一个线程 | sub-group 里的一个 work-item |
| （编译器替你分配） | shared memory | SLM |

`num_warps` 的默认值写在 Triton 的 NVIDIA 后端里：`third_party/nvidia/backend/compiler.py` 的 `CUDAOptions` 有 `num_warps: int = 4`、`warp_size: int = 32`。所以在 NVIDIA 上，一个 Triton program 默认由 4 × 32 = 128 个线程执行。在第 1 章那个 `triton-ir` 块里点开 Compiler Explorer，TTGIR 的第二行就是它们：`"ttg.num-warps" = 4 : i32`、`"ttg.threads-per-warp" = 32 : i32`。

Intel 上有一个细节值得先记一笔：同一台 Max 1100 上，逐点和归约 kernel 的 TTGIR 里是 `"ttg.threads-per-warp" = 32`，而用了 `tl.dot` 的 kernel 是 `"ttg.threads-per-warp" = 16`，因为 Intel 的矩阵指令要求 sub-group 宽度为 16。同一个 kernel 换后端，连「一个 warp 几个线程」都会变，这是第 23 章「性能可移植性」的第一个例子。

## 计算：峰值是怎么来的

GPU 的 fp32 峰值可以直接从硬件参数推出来：**计算单元数 × 每个单元的 fp32 通道数 × 每个周期 2 次运算（一次乘加算两次）× 频率**。

- A10：72 个 SM × 128 条通道 × 2 × 1.695 GHz ≈ **31.2 TFLOP/s**，和 NVIDIA 数据手册上的数字一致；
- Max 1100：448 个 EU × 16 条通道 × 2 × 1.55 GHz ≈ **22.2 TFLOP/s**。实验 2 实测 21.9，实验 3 的 fp32 矩阵乘也是 21.9。

实验 3 里，fp16 矩阵乘快了近八倍，因为它走的是另一套硬件：**矩阵单元**（NVIDIA 叫 **Tensor Core**，Intel 叫 **XMX**）。它们一条指令就算一小块矩阵乘，吞吐比普通 fp32 通道高一个数量级。A10 的 fp16 Tensor Core 标称 125 TFLOP/s，是它 fp32 峰值的 4 倍；Max 1100 上实测 172 TFLOP/s，是 fp32 的 7.8 倍。要用上它们，Triton 里只有一个入口：**`tl.dot`**（第 7 章）。附录 A 的体检脚本里，`tl.dot` 那一项打印的 `#ttg.nvidia_mma`、`#ttig.dpas`，就是「这块数据要喂给矩阵单元」的 layout。

## 存储：从寄存器到显存

实验 1 的那条曲线，把存储层级直接画了出来：

- **1 MiB：带宽很低。** 数据太少，时间花在了别处。我单独测过：在 Max 1100 上，用同一个 `copy_kernel` 拷贝 4 KiB 和拷贝 1 MiB，每次都要 12 微秒左右，数据量差了 256 倍，耗时几乎一样。这 12 微秒是**启动一次 kernel 的固定开销**，包括 Python 一侧 Triton 准备参数、提交 kernel 的时间。kernel 启动开销是微秒级的，所以**太小的 kernel 不值得单独启动**，这也是融合的另一个好处。
- **16 MiB：2006 GB/s。** 读加写共 32 MiB，全部装在 L2 里，反复拷贝时根本不碰显存。这是 L2 的带宽。
- **256 MiB 及以上：774 GB/s 左右。** 装不进 L2 了，每次都要走显存。这就是这块卡能跑到的显存带宽，大约是标称值的 63%。离标称值还有多远、为什么，第 11 章会讲。
- 64 MiB（1106 GB/s）是过渡区：读加写共 128 MiB，比 L2 小，但已经有相当一部分被挤出了缓存。

还有两层这个实验看不见，因为它们不能被「拷贝」：**寄存器**是每个线程私有的，**shared memory** 是每个 SM 私有的。它们都在 SM 内部，容量很小（A10 一个 SM 只有 256 KB 寄存器、最多 100 KB shared memory），但几个周期就能拿到数据。

<div class="warn">
<strong>别拿驱动报告的显存位宽算带宽</strong>
<p>Triton 的 <code>get_device_properties</code> 会返回 <code>mem_clock_rate</code> 和 <code>mem_bus_width</code>。在 Max 1100 上它们是 3200 MHz 和 64 位，按「位宽 × 频率 × 2」一算只有约 51 GB/s，比实测的 774 GB/s 差了一个数量级。显存带宽，以数据手册和实测为准。</p>
</div>

## 带宽墙与算力墙

实验 2 是这一章最重要的实验。每个元素读 4 字节、写 4 字节，中间做 `ITERS` 次乘加（每次 2 次浮点运算）。于是**每搬一个字节，做 ITERS / 4 次运算**。这个比值叫**算术强度（arithmetic intensity）**，单位是 FLOP/字节。

看耗时那一列：ITERS 从 1 涨到 64，计算量涨了 64 倍，**耗时一动不动**，都是 0.70 ms 左右。这段时间里，GPU 在等显存，多算的那些乘加是「白送」的，藏在等数据的空档里。ITERS 到 256 以后，耗时开始随计算量线性上涨，TFLOP/s 封顶在 22 左右。此时 GPU 在全力计算，显存反而闲了下来（带宽掉到 339、86 GB/s）。

**拐点**的位置可以直接算：算力峰值 ÷ 显存带宽。Max 1100 是 21.9 TFLOP/s ÷ 774 GB/s ≈ 28 FLOP/字节，实测的转折正好落在 16 和 64 之间。A10 是 31.2 TFLOP/s ÷ 600 GB/s ≈ 52 FLOP/字节。

有了拐点，就能给任何一个 kernel 先下判断：

- **第 1 章的 softmax**：每个元素做五六次运算，搬 8 个字节，强度不到 1，比拐点低了一个多数量级。**它注定受带宽限制**，所以优化它的唯一办法是少搬数据，也就是融合。算得再快也没用。
- **4096×4096×4096 的 fp16 矩阵乘**：2 × 4096³ 次运算，最少只要搬三个矩阵，共 3 × 4096² × 2 字节，强度约 1365 FLOP/字节。**它注定受算力限制**，所以要用矩阵单元，让算力墙抬高到 172 TFLOP/s。这时拐点也跟着右移，到 172 ÷ 0.774 ≈ 222 FLOP/字节。GEMM 的 tile 为什么要分得足够大，答案就在这里：tile 越大，每搬一个字节能做的运算越多（第 7、12 章）。

<div class="keypoint">
<strong>写 kernel 之前先算强度</strong>
<p>拿到一个算子，先估它的算术强度，和你 GPU 的拐点比一比。在拐点左边，优化的目标是<strong>少搬字节</strong>：融合、避免重复读、用更小的数据类型。在拐点右边，目标是<strong>算得快</strong>：用 <code>tl.dot</code> 喂饱矩阵单元、减少无用的指令。方向搞反了，再怎么调参都是白费力气。</p>
</div>

## 藏延迟：为什么要养几万个线程

还有一个问题没回答：实验 1 里，显存能跑到 774 GB/s，前提是**同时有足够多的访存请求在路上**。一次显存访问要几百纳秒才能回来，这段时间里，发出请求的线程什么也做不了。GPU 的办法不是让线程等得更快，而是**让别的线程顶上**：一个 SM 上同时驻留几十个 warp，一个 warp 卡在访存上，调度器就换另一个准备好的 warp 发指令。只要随时都有 warp 准备好，计算单元就不会空着。

下面这个模拟器把这件事算了出来。它只用标准库，直接点运行；改一改 `COMPUTE`、`LATENCY`，或者把 `GREEDY` 改成 `False`：

```python
# 一个 SM 上的 warp 调度：warp 越多，越能把访存延迟藏起来。只用标准库。
#
# 模型（故意做得很简单）：
#   - 调度器每个周期最多发射 1 条指令。它是「贪心」的：上一个 warp 还能发就接着发它，
#     卡住了才按顺序找下一个准备好的 warp（真实 GPU 的调度器也大致如此）；
#   - 每个 warp 反复执行同一段程序：COMPUTE 条计算指令，最后一条是访存；
#   - 访存发出去以后，这个 warp 要等 LATENCY 个周期，数据回来才能继续。
#   没有 warp 准备好的周期，计算单元就空着。利用率 = 发射了指令的周期 / 总周期。
#
# 把 GREEDY 改成 False 试试：调度器改成每个周期换一个 warp（纯轮询），
# warp 们会「排成一队」同时去等访存，利用率明显变差。

GREEDY = True


def simulate(n_warps, compute, latency, cycles=12000):
    ready_at = [0] * n_warps          # 每个 warp 最早在哪个周期能再发射
    left = [compute] * n_warps        # 这一段程序还剩几条指令
    issued, cur = 0, 0
    for t in range(cycles):
        for k in range(n_warps):      # 先看当前 warp，卡住了再往后找
            w = (cur + k) % n_warps
            if ready_at[w] <= t:
                issued += 1
                left[w] -= 1
                if left[w] == 0:      # 刚发出去的是访存：等 latency 个周期
                    ready_at[w] = t + 1 + latency
                    left[w] = compute
                else:
                    ready_at[w] = t + 1
                cur = w if GREEDY else w + 1
                break
    return issued / cycles


def table(title, compute, latency):
    print(f"{title}：每 {compute} 条指令一次访存，访存延迟 {latency} 个周期")
    print("  warp 数   模拟的利用率   估算 min(1, W·C/(C+L))")
    for w in (1, 2, 4, 8, 16, 32, 48):
        est = min(1.0, w * compute / (compute + latency))
        print(f"  {w:6}   {simulate(w, compute, latency):10.0%}   {est:12.0%}")
    print()


table("访存走显存", compute=8, latency=400)
table("访存命中 shared memory", compute=8, latency=30)
table("计算更密集（每次访存之间 32 条指令）", compute=32, latency=400)
```

几件事一眼可见：

- **访存走显存时（延迟 400 个周期），48 个 warp 才能把利用率拉到 94%。** 每个 warp 每 408 个周期里只有 8 个周期在干活，要几十个 warp 轮流顶上，才填得满。估算公式 `W · C / (C + L)` 说的就是这个：每个 warp 能贡献的「忙」的比例是 C/(C+L)，要凑够 1，就需要 (C+L)/C 个 warp。
- **访存命中 shared memory 时（延迟 30 个周期），8 个 warp 就够了。** 延迟越低，需要的并行度越少。这正是编译器愿意把数据搬进 shared memory 再用的原因之一。
- **每次访存之间的计算越多，需要的 warp 越少。** 计算本身也能藏延迟，这和上一节的算术强度是同一回事。

把 `GREEDY` 改成 `False`，调度器就变成每个周期换一个 warp。48 个 warp 时，利用率会从 94% 掉到 53%：所有 warp 的计算几乎同时做完，又一起去等访存，像排成一队的车，谁也藏不住谁。真实 GPU 的调度器更接近默认的贪心策略：一个 warp 能发就一直发，卡住了才换。

同样的道理，可以从带宽的角度再算一遍。**在路上的数据量 = 带宽 × 延迟**（这叫 **Little 定律**）。按显存延迟 500 纳秒的量级估算（不同 GPU 在几百纳秒到一微秒之间），要跑满 A10 的 600 GB/s，全芯片随时要有约 300 KB 的数据在路上，平均每个 SM 约 4 KB；要跑满 Max 1100 实测的 774 GB/s，要约 390 KB，每个 Xe-core 约 7 KB。一个线程一次读 16 字节的话，每个 SM 要有几百个线程同时在等数据。

这就引出了一个真实的约束：**一个 SM 能同时驻留多少个 warp，是有上限的**。A10（sm_86）每个 SM 最多驻留 48 个 warp；但寄存器和 shared memory 是这些 warp 共用的，每个线程用的寄存器越多、每个 program 用的 shared memory 越多，能同时驻留的 warp 就越少。比如一个线程用 128 个 32 位寄存器，A10 一个 SM 的 64K 个寄存器只够 512 个线程，也就是 16 个 warp。实际驻留的 warp 数占上限的比例，叫**占用率（occupancy）**。

在 Triton 里，你不直接控制占用率，但你选的参数直接决定它：

- `BLOCK_SIZE` 越大，每个 program 要放在寄存器里的数据越多，每个线程的寄存器用量就越高；
- `num_warps` 决定一个 program 有几个 warp；
- `num_stages`（第 13 章）决定要在 shared memory 里同时放几份数据。

这三个参数一改，占用率跟着变，「藏延迟」的能力就跟着变，性能会忽高忽低。第 12、13 章会用这一章的模型，**先预测**它们会怎样影响性能，再测。

---

**这一章的要点**

- GPU 是几十个 **SM**（Intel 叫 Xe-core）拼起来的。一个 Triton program 在一个 SM 上跑，默认 4 个 **warp**，每个 warp 32 个线程同步执行同一条指令（Intel 的 sub-group 是 16 或 32）。
- fp32 峰值 = 单元数 × fp32 通道数 × 2 × 频率：A10 约 31.2 TFLOP/s，Max 1100 约 22.2 TFLOP/s（实测 21.9）。**矩阵单元**（Tensor Core / XMX）快一个数量级，Triton 里只能通过 `tl.dot` 用到它们。
- 存储层级：寄存器、shared memory（每个 SM 私有，极快，极小）→ L2（全芯片共享）→ 显存。Max 1100 实测：L2 约 2000 GB/s，显存约 774 GB/s。kernel 启动开销是微秒级的。
- **算术强度**（FLOP/字节）决定一个 kernel 撞的是**带宽墙**还是**算力墙**。拐点 = 算力峰值 ÷ 显存带宽：Max 1100 约 28，A10 约 52。softmax 远在拐点左边，GEMM 远在右边。**先算强度，再决定往哪个方向优化。**
- GPU 靠**同时驻留大量 warp**来藏访存延迟：延迟越长、计算越少，需要的 warp 越多。寄存器和 shared memory 的用量限制了能驻留多少 warp（**占用率**）。Triton 的 `BLOCK_SIZE`、`num_warps`、`num_stages` 都会改变它。
