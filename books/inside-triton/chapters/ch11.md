# 第 11 章 性能模型与测量

## 这一章想让你带走什么

<div class="goal-box">
<p>第三部分的目标是把 kernel 写快。在动手优化之前，先要回答两个问题：<strong>我测到的数字可信吗？</strong>以及<strong>这个数字离上限还有多远？</strong>前一个问题决定了你会不会被自己的测量骗；后一个决定了值不值得继续优化、往哪个方向优化。</p>
<p>读完你会拿到三样东西。一是测量的正确姿势：把四种常见的测法放在同一个 kernel 上，你会看到它们给出的带宽从 353 GB/s 到 22 TB/s 不等，以及 <code>triton.testing.do_bench</code> 到底做了什么、为什么它测出来的有时比「连跑 100 次取平均」还慢。二是 minillm 每个 kernel 在 roofline 上的位置：访存受限的 kernel 达到了上限的 58%–83%，指针版矩阵乘只有 7%，descriptor 版 90%。三是 proton：Triton 自带的 profiler，告诉你一次前向的时间花在了哪个 kernel 上。</p>
</div>

## 先测对：同一个 kernel 的四种测法

拿第 2 章那个最简单的拷贝 kernel，用四种方法各测一次：

```triton
# arch: sm80 xpu
import time

import torch
import triton
import triton.language as tl

DEVICE = triton.runtime.driver.active.get_active_torch_device()
gpu = getattr(torch, DEVICE.type)


@triton.jit
def copy_kernel(x_ptr, y_ptr, n, BLOCK: tl.constexpr):
    offs = tl.program_id(0) * BLOCK + tl.arange(0, BLOCK)
    mask = offs < n
    tl.store(y_ptr + offs, tl.load(x_ptr + offs, mask=mask), mask=mask)


def copy(x, y):
    copy_kernel[(triton.cdiv(x.numel(), 1024),)](x, y, x.numel(), BLOCK=1024)


print(f"{gpu.get_device_name()}，triton {triton.__version__}")
for mib in (16, 256):
    x = torch.randn(mib * 2**20 // 4, device=DEVICE); y = torch.empty_like(x)
    gbs = lambda ms: f"{2 * x.numel() * 4 / ms / 1e6:6.0f} GB/s"
    print(f"拷贝 {mib} MiB：")

    t = time.perf_counter(); copy(x, y); gpu.synchronize()          # ① 第一次调用：包含了编译
    print(f"  ① 第一次调用就计时        {(time.perf_counter() - t) * 1e3:9.3f} ms")

    t = time.perf_counter(); copy(x, y)                              # ② 没有同步：只量到了「提交」
    print(f"  ② 不同步就停表            {(time.perf_counter() - t) * 1e3:9.3f} ms  {gbs((time.perf_counter() - t) * 1e3)}")
    gpu.synchronize()

    start, end = gpu.Event(enable_timing=True), gpu.Event(enable_timing=True)
    start.record()
    for _ in range(100):                                             # ③ 不清缓存，连着跑 100 次
        copy(x, y)
    end.record(); gpu.synchronize()
    ms = start.elapsed_time(end) / 100
    print(f"  ③ 连跑 100 次取平均        {ms:9.3f} ms  {gbs(ms)}")

    q = triton.testing.do_bench(lambda: copy(x, y), quantiles=[0.0, 0.2, 0.5, 0.8, 1.0])   # ④ do_bench
    print(f"  ④ do_bench（每次清 L2）   {q[2]:9.3f} ms  {gbs(q[2])}   "
          f"最快 {q[0]:.3f}，20% {q[1]:.3f}，80% {q[3]:.3f}，最慢 {q[4]:.3f}")
```

运行结果（Max 1100；用一个空的 `TRITON_CACHE_DIR` 跑的，所以第一次调用要初始化 driver）：

```

拷贝 16 MiB：
  ① 第一次调用就计时         6485.403 ms
  ② 不同步就停表                0.094 ms     353 GB/s
  ③ 连跑 100 次取平均            0.016 ms    2076 GB/s
  ④ do_bench（每次清 L2）       0.074 ms     454 GB/s   最快 0.073，20% 0.073，80% 0.075，最慢 0.094
拷贝 256 MiB：
  ① 第一次调用就计时            1.179 ms
  ② 不同步就停表                0.024 ms   21848 GB/s
  ③ 连跑 100 次取平均            0.696 ms     771 GB/s
  ④ do_bench（每次清 L2）       0.779 ms     689 GB/s   最快 0.774，20% 0.778，80% 0.782，最慢 0.802
```

逐条看：

- **① 第一次调用就计时。** 16 MiB 那一次花了 6 秒多，里面是 driver 初始化、给 Triton 自己算指纹、编译（第 4 章）。256 MiB 那一次只有 1 毫秒多，因为 kernel 已经编译好了，只是第一次用这个大小的张量。无论哪种，**第一次调用的时间都不代表 kernel 的速度**。
- **② 不同步就停表。** GPU 是异步执行的：`copy(x, y)` 返回的时候，kernel 只是被提交到了队列里，可能还没开始跑。这时停表，量到的只是 CPU 提交 kernel 的时间，算出 22 TB/s 这种荒唐的数字。**CPU 端计时之前，一定要 `synchronize()`。**
- **③ 连跑 100 次取平均。** 这是很多人自己写的计时方式：用 GPU 事件把 100 次调用框起来。16 MiB 时它测出了 2076 GB/s，比显存带宽高三倍，因为第 2 章说过，16 MiB 的数据读写合计 32 MiB，全部留在 L2 里，第二次以后根本不碰显存。如果你的 kernel 在真实场景里每次处理的都是新数据，这个数字就是在骗你。
- **④ `do_bench`。** Triton 自带的计时函数，每次运行之前都把 L2 清掉。16 MiB 时它测出 454 GB/s，256 MiB 时 689 GB/s。

`do_bench` 的实现在 `python/triton/testing.py`，不长，值得读一遍：

1. 先调用一次 `fn`（预热，顺便把编译做掉）；
2. 用 5 次调用估算一次要多久，据此决定预热多少次、测量多少次。默认预热 25 ms、测量 100 ms（`warmup=25, rep=100`）；
3. 每一次测量之前，调用 `driver.clear_cache(cache)` 把 L2 清掉。`cache` 是 `get_empty_cache_for_benchmark()` 分配的一块 256 MB 的缓冲区，NVIDIA 和 Intel 的 driver 都是 256 MB；「清掉」的办法就是把这块缓冲区整个写一遍 0，把原来留在 L2 里的数据挤出去；
4. 每次调用前后各记一个 GPU 事件，最后按 `return_mode` 汇总：默认 `"mean"`（均值），也可以是 `"median"`、`"min"`、`"max"`；或者给 `quantiles=[0.2, 0.5, 0.8]` 拿分位数。

上面第 ④ 行打印了分位数：20% 分位和 80% 分位只差 3% 左右，分布很集中；最慢的那一次可能慢得多（16 MiB 那一档慢了将近 30%），所以只看「最快」或「最慢」都不可靠。分布很散的时候（比如 GPU 上同时还有别的任务），看中位数比看均值稳。

注意 256 MiB 那一档：**`do_bench` 测出的 689 GB/s，比 ③ 的 771 GB/s 还慢了 11%**。256 MiB 的数据本来就装不进 L2，清不清缓存应该没区别才对。原因在清缓存的方式上：把 256 MB 的缓冲区写一遍 0，会在 L2 里留下大量「脏」数据，它们要在接下来那次被测 kernel 运行的时候写回显存，和 kernel 抢带宽。另外，连着跑 100 次时，前一个 kernel 的收尾和后一个的开头可以重叠，每次单独计时就没有这个好处。

所以，**`do_bench` 测的是「冷缓存、单独运行」时的时间**，这个口径偏保守，但稳定、可比，本书所有的性能数字都用它。如果你关心的是「这个 kernel 在模型里连着跑的时候有多快」，③ 那种测法（或者下面的 proton）更接近真实情况，前提是数据量大到不会被缓存。**两种口径不要混着比。**

## roofline：每个 kernel 离上限多远

第 2 章画过 roofline：一个 kernel 的性能上限，取决于它的算术强度落在拐点的哪一边。现在把 minillm 的 kernel 都放上去，算一算每个达到了上限的百分之几：

```triton
# arch: sm80 xpu
import torch
import triton

import minillm.ops as ops
from minillm import DEVICE
from minillm.kernels.matmul import matmul, matmul_desc

# 这台 GPU 的三条「墙」：第 2 章实测（Max 1100）。换了 GPU，先用 hw_probe.py 量出你自己的
BW = 774e9           # 显存带宽，字节/秒
VEC = 21.9e12        # fp32 向量单元，FLOP/秒（逐点、归约 kernel 用的是它）
MMA = 172e12         # bf16 矩阵单元，FLOP/秒（tl.dot 用的是它）

bf = dict(device=DEVICE, dtype=torch.bfloat16)
x, y = torch.randn(4096, 4096, **bf), torch.randn(4096, 4096, **bf)
g, u = torch.randn(4096, 14336, **bf), torch.randn(4096, 14336, **bf)
h, w = torch.randn(8192, 4096, **bf), torch.randn(4096, **bf)
s = torch.randn(4096, 32768, device=DEVICE)
a, b = torch.randn(4096, 4096, **bf), torch.randn(4096, 4096, **bf)

# 名字、函数、浮点运算数、最少要搬的字节、用的是哪种计算单元
cases = [
    ("add 4096×4096", lambda: ops.add(x, y), x.numel(), 3 * x.numel() * 2, VEC),
    ("silu_mul 4096×14336", lambda: ops.silu_mul(g, u), 6 * g.numel(), 3 * g.numel() * 2, VEC),
    ("rmsnorm 8192×4096", lambda: ops.rmsnorm(h, w, 1e-6), 4 * h.numel(), 2 * h.numel() * 2, VEC),
    ("softmax 4096×32768 fp32", lambda: ops.softmax(s), 5 * s.numel(), 2 * s.numel() * 4, VEC),
    ("matmul 指针版 4096³", lambda: matmul(a, b), 2 * 4096**3, 3 * 4096**2 * 2, MMA),
    ("matmul descriptor 4096³", lambda: matmul_desc(a, b), 2 * 4096**3, 3 * 4096**2 * 2, MMA),
]
print(f"{getattr(torch, DEVICE.type).get_device_name()}，triton {triton.__version__}")
print(f"  {'kernel':24} {'强度':>8} {'实测':>9} {'上限':>9}  {'受谁限制':6} {'达到':>5}")
for name, fn, flops, nbytes, peak in cases:
    ms = triton.testing.do_bench(fn)
    intensity = flops / nbytes
    t_bound = max(nbytes / BW, flops / peak) * 1e3            # roofline：搬数据和计算，哪个慢就是下限
    who = "带宽" if nbytes / BW > flops / peak else "算力"
    print(f"  {name:24} {intensity:8.2f} {ms:7.3f}ms {t_bound:7.3f}ms  {who:6} {t_bound / ms:5.0%}")
```

运行结果（Max 1100）：

```
Intel(R) Data Center GPU Max 1100，triton 3.9.0
  kernel                         强度        实测        上限  受谁限制      达到
  add 4096×4096                0.17   0.223ms   0.130ms  带宽       58%
  silu_mul 4096×14336          1.00   0.560ms   0.455ms  带宽       81%
  rmsnorm 8192×4096            1.00   0.256ms   0.173ms  带宽       68%
  softmax 4096×32768 fp32      0.62   1.663ms   1.387ms  带宽       83%
  matmul 指针版 4096³          1365.33  10.685ms   0.799ms  算力        7%
  matmul descriptor 4096³   1365.33   0.891ms   0.799ms  算力       90%
```

算法很简单。对每个 kernel，先数两样东西：

- **浮点运算数**：`add` 每个元素 1 次；`silu_mul` 记 6 次（sigmoid 的 exp、加、除，再乘两次，粗略估计）；rmsnorm 记 4 次（平方、累加、乘 rsqrt、乘权重）；softmax 记 5 次；矩阵乘是 2·M·N·K。逐点和归约的运算数只是估计，反正它们远在拐点左边，算力那一项不起作用。
- **最少要搬的字节**：每个输入读一遍、每个输出写一遍，按 dtype 算。`add` 是读两个、写一个 bf16；矩阵乘是三个 4096×4096 的 bf16 矩阵各一遍。

搬数据最快要 `字节 ÷ 带宽`，计算最快要 `运算数 ÷ 算力`，**哪个更慢，哪个就是这个 kernel 的下限时间**，这就是 roofline 的全部内容。实测时间和下限一比，就是「达到了上限的百分之几」。

关于「上限」这两个字要说清楚：上面的带宽和算力都是**第 2 章实测出来的可达峰值**，不是数据手册上的标称值。显存带宽用的是拷贝 kernel 实测的 774 GB/s，标称值是约 1.2 TB/s；矩阵单元用的是 `torch.matmul` 实测的 172 TFLOP/s。Max 1100 矩阵单元的理论峰值，本书没有找到可靠的公开数据来核实，所以没有用它。这意味着上表里矩阵乘的「90%」是「达到了 oneDNN 水平的 90%」，不代表离硬件极限只差 10%。

图上一眼能看出两件事：

- **四个访存受限的 kernel 都挤在左下角的斜坡附近**，离斜坡最近的是 `silu_mul` 和 softmax（81%、83%）。剩下的那一截，第 2 章那个拷贝 kernel 也只跑到 774 GB/s 的「可达」带宽而已，它们其实已经很接近这块卡能给的了。`add` 只有 58%，原因是数据量小：我把它放大到 4096×14336 和 4096×32768 又测了一次，分别达到 82% 和 91%。数据量小的时候，每次启动、清缓存留下的写回这些固定开销，占的比例就大了。
- **两个矩阵乘在同一个强度上，高度差了一个数量级。** 指针版远远低于屋顶，是第 8 章讲的访存写法问题；descriptor 版已经贴近 oneDNN 的水平。

这就是 roofline 的用法：**它不告诉你怎么优化，但告诉你还有没有优化的空间、该往哪个方向使劲**。左边的点离斜坡很近，再优化也挤不出多少；想更快，只能减少要搬的字节，也就是融合（第 1、6 章）。右边的点离屋顶还远，问题在 kernel 内部：tile 的大小、数据复用、流水，这是接下来三章的内容。

## proton：时间花在哪个 kernel 上

`do_bench` 只能测一个函数的总时间。一次 Transformer 层的前向要启动好几种 kernel，想知道时间花在哪里，要用 profiler。Triton 自带一个，叫 **proton**，在 `triton.profiler` 里。它在 NVIDIA 上用 CUPTI，在 AMD 上用 rocprofiler / roctracer，在 Intel 上用 XPUPTI（`triton/profiler/profile.py` 的 `_select_backend` 会根据当前的后端自动选择）。

用法是在要分析的代码前后加 `proton.start` 和 `proton.finalize`，可以用 `proton.scope` 给一段代码起个名字：

```triton
# arch: sm80 xpu
import torch
import triton.profiler as proton

import minillm.ops as ops
from minillm import DEVICE

t, d, i = 4096, 4096, 14336
mk = lambda *s: torch.randn(*s, device=DEVICE, dtype=torch.bfloat16)
x, wn, w1, w3, w2 = mk(t, d), mk(d), mk(d, i) * 0.02, mk(d, i) * 0.02, mk(i, d) * 0.02


def mlp(x):
    h = ops.rmsnorm(x, wn, 1e-6)
    return ops.add(x, ops.mm(ops.silu_mul(ops.mm(h, w1), ops.mm(h, w3)), w2))


mlp(x)                                      # 先跑一次：把编译排除在 profile 之外
getattr(torch, DEVICE.type).synchronize()
proton.start("mlp", hook="triton")          # 结果写进 mlp.hatchet；hook="triton" 按 Triton kernel 记录
for _ in range(10):
    with proton.scope("mlp"):               # 给这一段起个名字，结果里会成为一个节点
        mlp(x)
getattr(torch, DEVICE.type).synchronize()
proton.finalize()
```

运行完会在当前目录生成 `mlp.hatchet`，用 `proton-viewer` 查看：

```bash
proton-viewer -m time/ms mlp.hatchet
```

`proton-viewer` 依赖两个不随 Triton 一起安装的包，第一次用之前要装上：`uv pip install pandas llnl-hatchet`（附录 A 第 5 节）。

这是 10 次前向加起来的时间：一共约 87 ms，也就是每次 8.7 ms 左右，其中矩阵乘占了 92%。这和第 10 章用 `do_bench` 逐个 kernel 测出来的结论一致：**这一层的性能几乎完全取决于 GEMM**。

但细看单个 kernel 的数字，和 `do_bench` 对不上：proton 里 `_rmsnorm_kernel` 10 次一共 0.460 ms，平均每次 0.046 ms；第 10 章用 `do_bench` 测的是 0.140 ms。原因还是缓存：proton 记录的是**连续运行时**每个 kernel 的实际耗时，rmsnorm 的输入 x 是 32 MiB，在两次前向之间一直留在 L2 里；`do_bench` 每次都先清掉 L2。这就是上一节说的两种口径：**proton 告诉你「在这个程序里，时间实际花在哪」，`do_bench` 告诉你「这个 kernel 本身有多快」**。优化之前用 proton 找热点，优化之后用 `do_bench` 衡量效果。

## 动手

1. **在你的 GPU 上跑「四种测法」。** NVIDIA 的 L2 小得多（A10 只有 6 MB），16 MiB 那一档的 ③ 还会比 ④ 快那么多吗？256 MiB 那一档，`do_bench` 是不是同样比 ③ 慢？
2. **把你的 GPU 的三道墙填进 roofline 脚本。** 用第 2 章的 `hw_probe.py` 量出你自己的显存带宽、fp32 峰值、矩阵乘峰值，改掉 `BW`、`VEC`、`MMA` 三个常数，再跑一遍。哪个 kernel 离上限最远？
3. **给 proton 加一个 scope。** 在 `mlp` 函数里给每个算子各包一个 `proton.scope("…")`，再用 `proton-viewer` 看。能不能看出两次 `h @ w1`、`h @ w3` 和最后一次 `@ w2` 各花了多少时间？它们的形状不同，强度一样吗？

**这一章的要点**

- 四种常见的错误测法：第一次调用就计时（含编译）、不同步就停表（只量到提交）、不清缓存连跑（小数据全在 L2 里）、只看一个数（不看分布）。在 Max 1100 上，同一个拷贝 kernel 测出了从 353 GB/s 到 22 TB/s 的各种「带宽」。
- `triton.testing.do_bench`（`python/triton/testing.py`）：先跑一次、估算、预热，每次测量前用一块 256 MB 的缓冲区把 L2 清掉，默认返回均值，可以要分位数。它测的是冷缓存、单独运行的时间，偏保守但稳定；清缓存留下的脏数据会让大 kernel 也慢一点。本书的性能数字都用它。
- roofline 的用法：数浮点运算和最少字节，`max(字节/带宽, 运算/算力)` 就是下限时间。在 Max 1100 上（按实测可达的峰值），minillm 访存受限的 kernel 达到 58%–83%，`add` 偏低是因为数据量小；矩阵乘指针版 7%，descriptor 版 90%。离斜坡近的，想更快只能少搬字节；离屋顶远的，问题在 kernel 内部。
- proton（`triton.profiler`）在 NVIDIA、AMD、Intel 上都能用：`proton.start(..., hook="triton")`、`proton.scope(...)`、`proton.finalize()`，再用 `proton-viewer` 看（要装 `pandas`、`llnl-hatchet`）。它测的是连续运行时的实际耗时，和 `do_bench` 是两种口径：先用 proton 找热点，再用 `do_bench` 衡量优化效果。
