# 第 27 章 CIR 上的 CUDA/HIP：offloading 在新一层里怎么长

## 这一章想让你带走什么

<div class="goal-box">
<p>前两章讲的是「同一门语言，换一种中间表示」。这一章要看的是<strong>异构</strong>：CUDA 和 HIP 这种「一份源码、主机和设备各编一趟」的模型，在 CIR 这一层里长成了什么样。你会看到第 26 章那个套式（<strong>高层构造记录事实 → 专门的 pass 降级</strong>）被原封不动地搬到 offloading 上：<code>&lt;&lt;&lt;&gt;&gt;&gt;</code>、<code>__device__</code> 变量、fatbin 注册，全都先变成 CIR 上的一条属性，再由 pass 展开成 <code>cudaLaunchKernel</code> / <code>__cudaRegisterVar</code> 这些运行时调用。</p>
<p>三个具体收获：一是 <code>cu.kernel_name</code> / <code>cu.var_registration</code> / <code>cu.binary_handle</code> 这套「记账属性」，它们让主机端 IR 变成可读、可 <code>grep</code>、可写测试的；二是双地址空间设计——<code>lang_address_space(offload_global)</code> 和 <code>target_address_space(1)</code> 为什么要分成两个属性，中间那个 <code>cir-target-lowering</code> 又在做什么；三是这一层带来的一个新可能：主机端和设备端的表示<strong>在同一层里共存</strong>，于是「跨越主机—设备边界的优化」第一次有了落脚点。最后我们看一眼 PolyBench/GPU 的完整体检数据——它是「这条路走通了没有」的当前答案。</p>
</div>

## 先接上第 12 章那条线

第 12 章讲 SYCL 的时候，你已经建立过「一份 `.cpp` 编两趟」的模型：主机端一趟、设备端一趟，各有各的 `clang -cc1` 调用，最后由 offload 工具链（第 9 章）把设备端产物塞进主机端目标文件。CUDA/HIP 是同一个模型的另一种语法——`__global__` / `__device__` / `__constant__` 关键字加上 `<<<>>>` 启动语法。

CIR 不改这个模型。它改的是**每一趟里 AST → LLVM IR 那一段**（第 25 章的图 25-1）。所以这一章的所有内容都发生在一趟编译的内部，而「两趟」这个骨架、`clang-offload-bundler` 那套工具、CUDA 运行时的行为，一个字都不动。

<div class="note">
<strong>这一章的源码锚点</strong>
CIR 侧：<code>clang/lib/CIR/CodeGen/CIRGenCUDANV.cpp</code>、<code>CIRGenCUDARuntime.{h,cpp}</code>；属性定义在 <code>clang/include/clang/CIR/Dialect/IR/CIRCUDAAttrs.td</code>（注意——不在 <code>CIRAttrs.td</code> 里，这是一个独立文件，我第一次 <code>grep</code> 就找错了地方）；测试在 <code>clang/test/CIR/CodeGenCUDA/</code>（21 个 <code>.cu</code>）和 <code>clang/test/CIR/CodeGenHIP/</code>（29 个 <code>.hip</code>）。经典侧的对应物是 <code>clang/lib/CodeGen/CGCUDANV.cpp</code> 和 <code>CGCUDARuntime.{h,cpp}</code>。
</div>

## 第一件事：发射过滤

两趟编译的第一个问题是「这一趟该发射哪些函数」。设备端那趟带 `-fcuda-is-device`，主机端那趟不带；同一份 AST，两趟要产出**不同的函数集合**。

`clang/test/CIR/CodeGenCUDA/filter-decl.cu` 把这件事做成了一个四前缀矩阵——一份源码，四条 RUN 线，`CIR-HOST` / `CIR-DEVICE` / `OGCG-HOST` / `OGCG-DEVICE`，每个函数在四个前缀下各自被 `CHECK` 或 `CHECK-NOT`。结论是这张表：

| 源码里的声明 | 主机端这一趟 | 设备端这一趟 |
|---|---|---|
| `void hostfunc()`（隐式 `__host__`） | 发射 | 不发射 |
| `__host__ void hostfunc()` | 发射 | 不发射 |
| `__device__ void devicefunc()` | 不发射 | 发射 |
| `__host__ __device__ void hdfunc()` | 发射 | 发射（两份独立的实体） |
| `__global__ void globalfunc()` | 发射 `@_Z25__device_stub__globalfuncv` | 发射 `@_Z10globalfuncv` |

最后一行是全章的枢纽。`__global__` 函数在两趟里**名字都不一样**：设备端是它自己的 mangled name，主机端是一个前缀了 `__device_stub__` 的存根函数（stub）。你在主机端 `kernel<<<...>>>(...)` 写下的那次「调用」，调的是这个 stub；stub 的职责是把参数打包好、把配置取回来，然后交给运行时。

于是一个信息断链出现了：主机端的 stub 需要知道**设备端那个 kernel 叫什么名字**，才能在注册时把两者对上。经典 CodeGen 靠 IRGen 内部的数据结构记住这件事。CIR 的做法是——把它写在 IR 上。

```cir-norun
def CIR_CUDAKernelNameAttr : CIR_Attr<"CUDAKernelName", "cu.kernel_name"> {
  let summary = "Device-side function name for this stub.";
  let description =
  [{
    This attribute is attached to function definitions and records the
    mangled name of the kernel function used on the device.
    ...
    Preserving the device-side kernel name is crucial for performing its
    respective function runtime registration on the host.
  }];

  let parameters = (ins "mlir::StringAttr":$kernel_name);
  let assemblyFormat = "`<` $kernel_name `>`";
}
```

这是本章的第一条属性，也是整套设计的样板：**一个前端知道、后端不需要、但降级过程中要用到的事实，被记成 IR 上的一条属性。**

## `<<<>>>` 展开成了什么

`clang/test/CIR/CodeGenCUDA/kernel-call.cu` 的源码只有两行：

```cuda-norun
__global__ void kernel(int x, float y) {}
int main(void) { kernel<<<1, 1>>>(42, 1.0f); }
```

五条 RUN 线覆盖 CUDA/HIP × 新旧驱动路径。我们只看主机端 CIR。调用点被展开成这样（CHECK 行原文，`{{.*}}` 是 FileCheck 的通配）：

```cir-norun
cir.alloca {{.*}} ["agg.tmp0"] : !cir.ptr<!rec_dim3>
cir.alloca {{.*}} ["agg.tmp1"] : !cir.ptr<!rec_dim3>
cir.call @_ZN4dim3C1Ejjj(...) {uniform_work_group_size}     // grid  = dim3(1,1,1)
cir.call @_ZN4dim3C1Ejjj(...) {uniform_work_group_size}     // block = dim3(1,1,1)
%shmem  = cir.const #cir.int<0> : !u64i
%stream = cir.const #cir.ptr<null> : !cir.ptr<!rec_cudaStream>
%r = cir.call @__cudaPushCallConfiguration(...) -> !s32i
%b = cir.cast int_to_bool %r : !s32i -> !cir.bool
cir.if %b {
} else {
  %x = cir.const #cir.int<42> : !s32i
  %y = cir.const #cir.fp<1.000000e+00> : !cir.float
  cir.call @_Z21__device_stub__kernelif(%x, %y)
      {cu.kernel_name = #cir.cu.kernel_name<"_Z6kernelif">,
       uniform_work_group_size}
}
```

读一遍就能看懂 `<<<1, 1>>>` 到底是什么：**两个 `dim3` 临时对象 + 一次 `__cudaPushCallConfiguration` + 一个「推成功了才真调 stub」的 `if`**。注意 `cir.if` 的 then 分支是空的——push 返回非 0（真）表示失败，什么都不做；返回 0 才走 else 去调 stub。这个「空的 then」在 LLVM IR 里会变成一个跳到 continuation 的空块，读起来完全不知道它想干什么；在 CIR 里它就是一个 `cir.if`，第 26 章讲的结构化控制流在这里直接兑现成了可读性。

stub 内部是配置的另一半：

```cir-norun
cir.func {{.*}} @_Z21__device_stub__kernelif(%arg0: !s32i, %arg1: !cir.float) {
  cir.alloca {{.*}} ["x", init]
  cir.alloca {{.*}} ["y", init]
  cir.alloca {{.*}} ["kernel_args"] : !cir.ptr<!cir.array<!cir.ptr<!void> x 2>>
  cir.alloca {{.*}} ["grid_dim"]   : !cir.ptr<!rec_dim3>
  cir.alloca {{.*}} ["block_dim"]  : !cir.ptr<!rec_dim3>
  cir.alloca {{.*}} ["shared_mem"] : !cir.ptr<!u64i>
  cir.alloca {{.*}} ["stream"]     : !cir.ptr<!cir.ptr<!rec_cudaStream>>
  // 把两个参数的地址塞进 kernel_args 数组
  %p = cir.cast array_to_ptrdecay {{.*}}
  cir.ptr_stride {{.*}}
  cir.cast bitcast {{.*}} -> !cir.ptr<!void>
  // 取回刚才 push 进去的配置
  cir.call @__cudaPopCallConfiguration(%grid, %block, %shmem, %stream)
      : (!cir.ptr<!rec_dim3>, !cir.ptr<!rec_dim3>, !cir.ptr<!u64i>,
         !cir.ptr<!cir.ptr<!rec_cudaStream>>) -> !s32i
  cir.call @cudaLaunchKernel(...) -> (!u32i {llvm.noundef})
}
```

`kernel_args` 就是那个「函数指针数组」——CUDA 运行时的 `cudaLaunchKernel` 接受的是 `void **`，每个元素指向一个实参的**地址**。整条链是：*调用点把配置 push 到一个线程局部的栈 → 调 stub → stub 把配置 pop 回来、把实参地址打包成数组 → 一次 `cudaLaunchKernel`*。

设备端那一趟就朴素得多。`ptx-kernels.cu` 里，`__global__` 函数只是多了一个调用约定：

```cir-norun
cir.func {{.*}} @global_function() cc(ptx_kernel)
// 降到 LLVM IR：
// define ptx_kernel void @global_function()
```

`cuda-builtin-vars.cu` 显示 `threadIdx.x` 这类内建变量走的是通用的内建函数机制：

```cir-norun
cir.call_llvm_intrinsic "nvvm.read.ptx.sreg.tid.x" : () -> !u32i
// → call i32 @llvm.nvvm.read.ptx.sreg.tid.x()
```

也就是说 CIR 并不为 NVPTX 造新概念，它借道 `cir.call_llvm_intrinsic` 直通 LLVM 的 intrinsic。这是一个刻意的选择：**只在「前端知道的事实会丢」的地方加抽象，其它地方老老实实转发。**

## 双地址空间：一个变量的两种身份

现在来看这一章最值得学的一处设计。

CUDA 里 `__device__` / `__constant__` / `__shared__` 三个限定符，最终会变成 LLVM IR 上的 `addrspace(1)` / `addrspace(4)` / `addrspace(3)`——这三个数字是 **NVPTX 后端的约定**，换成 AMDGCN 就是另一套数字。经典 CodeGen 的做法是在 IRGen 里直接查表、直接写下数字。

CIR 把这一步**拆成了两个属性**。`clang/include/clang/CIR/Dialect/IR/CIRAttrs.td`：

```cir-norun
def CIR_LangAddressSpaceAttr : CIR_Attr<"LangAddressSpace", "lang_address_space", [
    DeclareAttrInterfaceMethods<MemorySpaceAttrInterface>]> {
  // 例：!cir.ptr<!s32i, lang_address_space(offload_local)>
  //   取值：Default / offload_global / offload_constant / offload_local /
  //         offload_private / offload_generic ...
}

def CIR_TargetAddressSpaceAttr : CIR_Attr<"TargetAddressSpace", "target_address_space", [
    DeclareAttrInterfaceMethods<MemorySpaceAttrInterface>]> {
  let parameters = (ins "unsigned":$value);
  let assemblyFormat = "`<` `target` `<` $value `>` `>`";
  // "A value of zero represents the default address space"
}
```

两者都实现 MLIR 的 `MemorySpaceAttrInterface`，所以在 `!cir.ptr<...>` 的语法位置上可以互换。区别是**语义层级**：前者说的是「这是 CUDA 语言意义上的 global 内存」，后者说的是「这是目标机器的第 1 号地址空间」。中间的翻译由一个 pass 完成，它的名字你在第 26 章的 12 个 pass 列表里见过：**`cir-target-lowering`**。

`clang/test/CIR/CodeGenCUDA/address-spaces.cu` 把这件事测得极其到位——它有**九条 RUN 线**，其中两条专门用来在同一个测试里同时看到 pass 前和 pass 后：

```bash
# 看 cir-target-lowering 跑之前的 CIR
# RUN: %clang_cc1 ... -fcuda-is-device -fclangir -emit-cir \
# RUN:   -mmlir -mlir-print-ir-before=cir-target-lowering %s -o %t.cir \
# RUN:   2>&1 | FileCheck %s --check-prefix=CIR-PRE
# 看跑完之后的 CIR
# RUN: %clang_cc1 ... -fcuda-is-device -fclangir -emit-cir %s -o %t.cir
# RUN: FileCheck --input-file=%t.cir %s --check-prefix=CIR-POST
```

`-mmlir -mlir-print-ir-before=<pass>` 就是第 25 章介绍的那个「在管线中间截一刀」的开关。截出来的两份 IR 摆在一起：

<div class="keypoint">
<strong>为什么值得拆成两个属性</strong>
这是「把决策推迟到必要的那一刻」的又一例——第 26 章的 <code>!cir.data_member</code> / <code>!cir.method</code> 把 ABI 决策推迟到 <code>cir-cxxabi-lowering</code>，这里把地址空间编号推迟到 <code>cir-target-lowering</code>。收益是具体的：<code>offload_local</code> 这个信息「这块内存是一个 block 内共享的」是可以用来做优化的（比如证明同步边界），而 <code>addrspace(3)</code> 只是一个数字，任何优化都得先反查目标手册才知道它意味着什么。同一份 CIR 换个 target 就能重新编译——因为编号还没写进去。
</div>

顺带一个细节，它是「parity 不是文本相同」的又一个漂亮例证。`address-spaces.cu` 里有个函数作用域的 `__shared__` 变量，两条路径产出的 LLVM IR 不一样：

```llvm-norun
; CIR 路径
store i32 %val, ptr @_ZZ2fnvE1j
; 经典路径（OGCG-DEVICE）
store i32 %val, ptr addrspacecast (ptr addrspace(3) @_ZZ2fnvE1j to ptr)
```

两者语义等价（NVPTX 后端都能正确处理），但文本不同。测试用两个不同的前缀分别 `CHECK`，而不是强求一致——这就是第 25 章说的「验收线是语义等价，不是文本相同」在具体现场的样子。

## 属性先记账，pass 再展开

现在把这一章最有代表性的机制讲完：**主机端的注册代码**。

CUDA 的运行模型要求主机端在程序启动时告诉运行时三件事：设备二进制在哪、有哪些 kernel、有哪些 `__device__`/`__constant__` 变量。这套「注册基础设施」在经典 CodeGen 里由 `CGCUDANV.cpp` 的 `makeModuleCtorFunction()` 在 IRGen 收尾时直接吐成 LLVM IR。

CIR 换了个顺序：CIRGen 只在 IR 上**挂属性**，展开留给降级阶段。`CIRCUDAAttrs.td` 里一共四个属性，除了前面见过的 `cu.kernel_name`，还有：

```cir-norun
def CIR_CUDAExternallyInitializedAttr
    : CIR_Attr<"CUDAExternallyInitialized", "cu.externally_initialized"> {
  let description = [{
    CUDA __device__ and __constant__ variables, along with surface and
    textures, might be initialized by host, hence "externally initialized".
    Therefore they must be emitted even if they are not referenced.
  }];
}

def CIR_CUDABinaryHandleAttr : CIR_Attr<"CUDABinaryHandle", "cu.binary_handle"> {
  let description = [{
    This attribute is attached to the ModuleOp and records the binary file
    name passed to host.
  }];
  let parameters = (ins "mlir::StringAttr":$name);
}

def CIR_CUDAVarRegistrationInfoAttr
    : CIR_Attr<"CUDAVarRegistrationInfo", "cu.var_registration"> {
  let summary = "Device variable registration flags.";
  let parameters = (ins
    "std::string":$device_side_name,
    "CUDADeviceVarKind":$kind,        // Variable / Surface / Texture
    "bool":$isExtern,
    "bool":$isConstant,
    "bool":$isManaged
  );
  let hasCustomAssemblyFormat = 1;
}
```

三个层级的记账都齐了：**函数上**记 kernel 名，**全局变量上**记注册标志，**模块上**记 fatbin 文件名。加上 `CIRDialect.td` 里的模块级属性 `cir.offload.kind`（这一趟是 CUDA 还是 HIP）、`cir.offload.container`、`cir.cu.binary_handle`，一次 offloading 编译的全部「元信息」都在 IR 上，可打印、可 `grep`、可写 FileCheck。

于是 `address-spaces.cu` 里主机端那一侧看起来是这样——注意主机端的 `@i` 只是个**影子**（`#cir.undef`），真正的存储在设备上：

```cir-norun
// CIR-HOST: cir.global {{.*}} @i = #cir.undef : {{.*}}
// CIR-HOST-SAME: {cu.var_registration = #cir.cu.var_registration<i, Variable>}
// LLVM-HOST:     @i = internal global i32 undef

// __constant__ int j; 主机端多一个属性：
// CIR-HOST-SAME: {cu.externally_initialized = #cir.cu.externally_initialized,
// CIR-HOST-SAME:  cu.var_registration = #cir.cu.var_registration<j, Variable, constant>}
```

`device-stub.cu` 则给出属性被消费之后的完整形态。`__cuda_module_ctor` 的骨架（CHECK 行原文，串起来读）：

```cir-norun
// 模块级：把 ctor 注册成优先级 65535 的全局构造函数
cir.global_ctors = [#cir.global_ctor<"__cuda_module_ctor", 65535>]

// 设备二进制本体和它的包装结构（注意 section）
cir.global "private" constant cir_private @__cuda_fatbin_str
    = #cir.const_array<"GPU binary would be here." : !cir.array<!u8i x 25>>
      {alignment = 8 : i64, section = ".nv_fatbin"}
cir.global constant cir_private @__cuda_fatbin_wrapper
    = #cir.const_record<{#cir.int<1180844977> : !s32i,     // magic
                         #cir.int<1> : !s32i,              // version
                         #cir.global_view<@__cuda_fatbin_str> : !cir.ptr<!void>,
                         #cir.ptr<null> : !cir.ptr<!void>}>
      : !rec_anon_struct {section = ".nvFatBinSegment"}
cir.global "private" internal @__cuda_gpubin_handle = #cir.ptr<null>

// 名字字符串：每个 kernel / 变量一条
cir.global "private" constant cir_private @".stra"
    = #cir.const_array<"a" : !cir.array<!u8i x 2>, trailing_zeros>
cir.global "private" constant cir_private @".str_Z10kernelfunciii" = ...

// 注册函数：属性在这里被消费
cir.func internal private @__cuda_register_globals(%fatbin: !cir.ptr<!cir.ptr<!void>>)
cir.func private @__cudaRegisterFunction(...)   -> !s32i     // 10 个参数
cir.func private @__cudaRegisterVar(!cir.ptr<!cir.ptr<!void>>, !cir.ptr<!void>,
    !cir.ptr<!void>, !cir.ptr<!void>, !s32i, !u64i, !s32i, !s32i)

// 收尾：注册 + atexit 反注册
cir.func private @__cudaRegisterFatBinaryEnd(...)
cir.func private @atexit(!cir.ptr<!cir.func<()>>) -> !s32i
cir.func internal private @__cuda_module_dtor()               // 调 __cudaUnregisterFatBinary
cir.func private @__cudaUnregisterFatBinary(!cir.ptr<!cir.ptr<!void>>)
```

那个 magic number `1180844977` 是 `0x466243B1`——CUDA fatbin 的魔数，和经典路径产出的 `i32 1180844977, i32 1, ptr @…, ptr null` 完全一致。

<div class="note">
<strong>没有 fatbin 就一行都不生成</strong>
<code>device-stub.cu</code> 里有一条 <code>NOGPUBIN</code> 前缀，专门验证「这次编译没拿到设备二进制」时的行为：<code>NOGPUBIN-NOT: fatbin</code> / <code>NOGPUBIN-NOT: gpubin</code>——整套注册基础设施一条不生成。这个行为在属性驱动的设计下几乎是免费的：模块上没有 <code>cu.binary_handle</code>，展开 pass 直接返回。
</div>

## 与经典路径对照

第 25 章立了四层对照的框架（目录、管线、测试、代价）。这一章的内容落在同一个框架里：

| 关注点 | 经典 CodeGen | CIR |
|---|---|---|
| 运行时抽象基类 | `clang/lib/CodeGen/CGCUDARuntime.{h,cpp}` | `clang/lib/CIR/CodeGen/CIRGenCUDARuntime.{h,cpp}` |
| NVIDIA / HIP 实现 | `CGCUDANV.cpp` | `CIRGenCUDANV.cpp` |
| kernel 名怎么从设备端传到主机端 stub | IRGen 内部数据结构 | IR 上的 `cu.kernel_name` 属性 |
| 变量注册信息 | 生成调用时现算 | IR 上的 `cu.var_registration` 属性 |
| 地址空间 | IRGen 里直接写 `addrspace(N)` | 两段：`lang_address_space` → `cir-target-lowering` → `target_address_space(N)` |
| 注册代码何时生成 | IRGen 收尾，直接吐 LLVM IR | 降级阶段展开属性 |
| 测试目录 | `clang/test/CodeGenCUDA/` | `clang/test/CIR/CodeGenCUDA/`（21 个 `.cu`）、`clang/test/CIR/CodeGenHIP/`（29 个 `.hip`） |

最能说明「对齐做到了什么程度」的，是 `clang/test/CIR/CodeGenHIP/device-var-registration.hip`。它有三条 RUN 线，但只有**两个** FileCheck 前缀：一个 `CIR` 看中间形态，一个 `LLVM`——而这个 `LLVM` 前缀的 CHECK 行**同时验证 `-fclangir -emit-llvm` 和不带 `-fclangir` 的经典 `-emit-llvm` 的输出**。同一批 CHECK，两条路径都得过：

```cir-norun
// CIR: cir.func private @__hipRegisterVar(...)
// CIR: cir.func internal private @__hip_register_globals(...)
// CIR:   cu.var_registration = #cir.cu.var_registration<device_var, Variable>
// CIR:   cu.var_registration = #cir.cu.var_registration<constant_var, Variable, constant>

// 下面这两行 CIR 路径和经典路径产出的字节完全相同：
// LLVM: call void @__hipRegisterVar(ptr %handle, ptr @device_var, ptr @name, ptr @name, i32 0, i64 4, i32 0, i32 0)
// LLVM: call void @__hipRegisterVar(ptr %handle, ptr @constant_var, ptr @name, ptr @name, i32 0, i64 4, i32 1, i32 0)
```

一个测试文件里「同一批 CHECK 行验两条管线」，是 parity 最强的一种表达方式——比写两套 CHECK 再靠人眼比对可靠得多。

## 主机与设备表示共存

前面所有内容都还只是「把旧路径重做一遍，做对」。这一节讲的是**旧路径做不到的事**。

注意一件容易被忽略的事：在 CIR 这一层，主机端和设备端的表示是**同一种 IR**。区别只是模块上挂的属性（`cir.offload.kind`）、函数上的调用约定（`cc(ptx_kernel)`）、指针上的地址空间。这意味着——原则上你可以把两个模块**放进同一个 MLIR 上下文里**，让一个 pass 同时看到 `main` 里的 `cudaLaunchKernel` 调用点和设备端 kernel 的函数体。

经典管线做不到这件事，因为两趟编译产出的是两份独立的 LLVM Module，彼此之间只有一个不透明的 fatbin 字节块。而 CIR 这一层还留着足够的语言级信息（哪个 stub 对应哪个 kernel——`cu.kernel_name` 就是那根绳子），把两边接起来是有意义的。

上游社区把这条方向叫 **host–device co-optimization**，目前处在「先把基础设施搭起来」的阶段：能把主机和设备的表示组合在一起，之后才谈得上在这个组合视图上做优化。可以想象的机会包括：把 `<<<>>>` 的 grid/block 常量传播进 kernel 里（于是 kernel 内的边界检查可以被消掉）、跨边界的常量与形状信息传播、按调用点特化 kernel。

<div class="warn">
<strong>这一节讲的是可能性，不是现状</strong>
co-optimization 目前是<strong>探索性工作</strong>，不是上游已经落地的优化。写在这里是因为它解释了「为什么值得在 AST 和 LLVM IR 之间加一层」——如果 CIR 的全部价值只是「把旧路径重写一遍」，那它的成本是不划算的。真正的赌注在这类「只有在这一层才可能做」的事情上。这也是为什么第 25 章反复强调：CIR 的意义不在于它更抽象，而在于它<strong>保留了一批前端知道、后端不需要的事实</strong>——这些事实在别处已经丢了。
</div>

## PolyBench/GPU：一次完整体检

「这条路走通了没有」需要数据回答。2026 年 6 月，上游社区在 LLVM Discourse 上公布了一次 PolyBench/GPU 全套跑分（`ClangIR PolyBench GPU results (CUDA/HIP)`），把 CIR 路径和经典路径（OG）放在一起比覆盖率、编译时间和运行时性能：

| 维度 | 结果 |
|---|---|
| 覆盖率 | 21 个 benchmark × 4 个架构 = **84/84 两条路径都编译成功**，无退化 |
| CUDA 编译时间（sm_80/86/89/90 平均） | 前端 + IRGen：CIR 0.752s vs OG 0.744s（+0.008s）；总计 0.803s vs 0.799s |
| HIP 编译时间（gfx906/908/90a/942 平均） | 前端 + IRGen：1.070s vs 1.048s（+0.021s）；总墙钟 10.77s vs 10.22s（+0.55s，方差偏大，待查） |
| 运行时性能（CIR/OG 比值，PolyBench 自带计时器） | CUDA sm_86 几何平均 ≈ 1.00；HIP gfx942 ≈ 1.05；长跑 benchmark 分别在 1% / 3% 以内 |

三句话读完这张表：**编得出来、编得不慢、跑得不慢**。多一层 IR、多十来个 pass，编译时间的代价在 CUDA 上是 0.4% 量级——这个数字本身就是一个重要结论，因为「加一层会不会太慢」是这类设计最常被质疑的一点。

同一个帖子里也点出了缺口。上游维护者列出的优先事项是「先补特性覆盖、继续和经典管线对齐」，明确点名的空白包括 **texture memory**（纹理内存）和 **RDC 编译**（relocatable device code，跨翻译单元的设备代码链接）；OpenCL 支持在探索中；**SYCL 支持还基本没开始**——虽然 `clang/lib/CIR/CodeGen/` 里已经有一个 `CIRGenSYCL.cpp` 文件。追踪 issue 是 `llvm/llvm-project#179278`（`[CIR][TRACKING] CUDA/HIP Support for ClangIR`），里面是一串复选框。

## 动手：属性记账 → pass 展开

下面这个模拟器把这一章的核心机制走一遍。它先摆出「CIRGen 之后的主机端模块」——里面只有 `cu.kernel_name` 和 `cu.var_registration` 属性，**一条运行时调用都没有**；然后模拟展开 pass，把属性读出来，生成注册基础设施。跑三遍：CUDA、HIP、以及「没拿到设备二进制」的情形。

```python
# CIR 的「属性先记账，pass 再展开」套式，用主机端 CUDA/HIP 注册代码做例子。
# 第一步（CIRGen）：主机端模块里只有属性，没有任何运行时调用。
# 第二步（lowering pass）：遍历模块，把属性展开成 __cudaRegister* / __hipRegister* 序列。

# ---- 第一步：CIRGen 产出的主机端模块（只记账，不展开）----
module_attrs = {
    "cir.offload.kind": "cuda",                            # cuda 还是 hip
    "cir.cu.binary_handle": "a.out-nvptx64-sm_80.fatbin",  # 设备二进制在哪
}

# 每个 __global__ 函数在主机端变成一个 stub，用 cu.kernel_name 记住设备端名字
stubs = [
    # (主机端 stub 符号,                    设备端 mangled name)
    ("_Z21__device_stub__kernelif",        "_Z6kernelif"),
    ("_Z24__device_stub__reduce_sumPfi",   "_Z10reduce_sumPfi"),
]

# 每个 __device__ / __constant__ 变量在主机端变成一个影子全局，带 cu.var_registration。
# 字段顺序照 CIRCUDAAttrs.td 里的 parameters 来：
#   device_side_name, kind, isExtern, isConstant, isManaged
device_vars = [
    # (主机端符号, 设备端名, kind,       extern, constant, managed, 字节数)
    ("i",         "i",      "Variable", False,  False,    False,   4),  # __device__ int i;
    ("j",         "j",      "Variable", False,  True,     False,   4),  # __constant__ int j;
    ("c",         "c",      "Variable", False,  False,    False,   8),  # __device__ _BitInt(36) c;
]

def show_cirgen_module():
    print("=== 第一步：CIRGen 之后的主机端 CIR（全是属性，零条运行时调用）===")
    print("module attributes {")
    for k, v in module_attrs.items():
        print('  %s = "%s",' % (k, v))
    print("} {")
    for host, dev in stubs:
        print('  cir.func @%s(...) {cu.kernel_name = #cir.cu.kernel_name<"%s">}' % (host, dev))
    for host, dev, kind, ext, const, mgd, _sz in device_vars:
        flags = [dev, kind]
        if ext:   flags.append("extern")
        if const: flags.append("constant")
        if mgd:   flags.append("managed")
        head = "cu.externally_initialized = #cir.cu.externally_initialized, " if const else ""
        print("  cir.global internal @%s = #cir.undef {%scu.var_registration = "
              "#cir.cu.var_registration<%s>}" % (host, head, ", ".join(flags)))
    print("}")
    print("→ 一共 %d 条 cu.* 属性（%d 个 kernel_name + %d 个 var_registration）"
          % (len(stubs) + len(device_vars), len(stubs), len(device_vars)))
    print()

# ---- 第二步：lowering pass 消费属性，生成注册基础设施 ----
def lower(offload_kind, has_binary_handle=True):
    P = "__cuda" if offload_kind == "cuda" else "__hip"
    # 两条路唯一的实质差别：fatbin wrapper 的 magic/section，以及 CUDA 多一个
    # RegisterFatBinaryEnd 调用。其余全靠换前缀。
    wrapper_note = ('magic=0x466243b1, section=".nvFatBinSegment"' if offload_kind == "cuda"
                    else 'magic/section 用 HIP 自己的一套')
    needs_end_call = (offload_kind == "cuda")

    print("=== 第二步（cir.offload.kind = %s）===" % offload_kind)
    if not has_binary_handle:
        print("  模块上没有 cir.cu.binary_handle —— 这次编译没有设备二进制。")
        print("  pass 什么都不做：没有 fatbin 全局、没有 register_globals、")
        print("  没有 module_ctor/dtor，一条运行时调用都不生成。")
```

## 小结与下一步

- CUDA/HIP 的**两趟编译骨架不变**，CIR 换掉的只是每一趟里 AST → LLVM IR 那一段。发射过滤（哪一趟发射哪些函数）在 `filter-decl.cu` 里被做成一个四前缀矩阵，`__global__` 函数在两趟里名字不同——主机端是 `__device_stub__` 前缀的存根。
- `<<<>>>` 展开成**调用点 + stub 两半**：`__cudaPushCallConfiguration` → `cir.if`（推失败就不启动）→ 调 stub → `__cudaPopCallConfiguration` → `kernel_args` 数组 → `cudaLaunchKernel`。HIP 只换符号，不换骨架。
- **双地址空间**是这一章最值得学的设计：`lang_address_space(offload_global/constant/local)` 说语言语义，`target_address_space(N)` 说目标编号，两者都实现 `MemorySpaceAttrInterface`，中间由 `cir-target-lowering` 翻译。好处是前半段的 IR 与目标无关。
- **属性先记账，pass 再展开**：`cu.kernel_name`（函数上）、`cu.var_registration` / `cu.externally_initialized`（全局上）、`cu.binary_handle` / `cir.offload.kind`（模块上）。这些属性可打印、可 `grep`、可写 FileCheck——这是相对经典路径最直接的可观察性收益。
- parity 用测试制度化到了极致：`device-var-registration.hip` 里**同一批 `LLVM` CHECK 行同时验证两条管线**。
- PolyBench/GPU 全套体检：**84/84 覆盖，CUDA 编译时间 +0.4%，运行时几何平均 ≈ 1.00**。缺口是 texture memory、RDC，以及基本还没开始的 SYCL 支持。
- 主机与设备表示在同一层共存，为 **host–device co-optimization** 留出了落点——这是探索性工作，也是「为什么值得加一层」最有说服力的那个答案。

这一部分到这里结束，整本书也到这里结束。回头看，你走过了三段路：LLVM 的 IR 中心哲学与 Pass 框架（第一部分）、异构世界里 IR 怎么跨设备走（第二部分）、SYCL 在 `intel/llvm` 里的真实实现与怎么给它加扩展（第三、四部分）。第五部分是一次视角切换——不是「已经这样了」，而是「有人正在改」。ClangIR 这条路会不会最终成为 Clang 的默认路径，写这本书的时候还没有答案；但你现在有了读懂它的全部工具：一个 MLIR 方言长什么样、怎么用 `-emit-cir` / `cir-opt` 观察它、怎么去 `clang/test/CIR/` 里查一个特性支持到什么程度。

**这一章的要点**

- **发射过滤**：`-fcuda-is-device` 决定这一趟发射哪些函数。`__host__ __device__` 两趟各发一份；`__global__` 在主机端是 `@_Z25__device_stub__globalfuncv`，在设备端是 `@_Z10globalfuncv`。测试用 `CIR-HOST` / `CIR-DEVICE` / `OGCG-HOST` / `OGCG-DEVICE` 四个前缀交叉验证。
- **`cu.kernel_name`** 把「主机端 stub ↔ 设备端 kernel」这根绳子写在 IR 上，供后续注册代码消费。
- **`<<<>>>` 的形状**：`dim3` 临时对象 + `__cudaPushCallConfiguration` + `cir.cast int_to_bool` + `cir.if`（then 空、else 调 stub）；stub 里 `__cudaPopCallConfiguration` + `kernel_args : !cir.array<!cir.ptr<!void> x N>` + `cudaLaunchKernel`。per-thread 流走 `cudaLaunchKernel_ptsz` / `hipLaunchKernel_spt`。
- **双地址空间**：`CIR_LangAddressSpaceAttr`（`offload_global` / `offload_constant` / `offload_local` …）与 `CIR_TargetAddressSpaceAttr`（`target_address_space(N)`，0 表示默认），都实现 `MemorySpaceAttrInterface`，由 **`cir-target-lowering`** 转换。`__device__`→1、`__constant__`→4、`__shared__`→3（NVPTX）。用 `-mmlir -mlir-print-ir-before=cir-target-lowering` 可以在同一个测试里看到转换前后。
- **注册基础设施**：`cu.var_registration<name, Variable[, constant][, managed]>` → `__cudaRegisterVar` / `__hipRegisterVar`；`cu.binary_handle` → fatbin 全局 + wrapper（magic `1180844977`，section `.nv_fatbin` / `.nvFatBinSegment`）+ `__cuda_module_ctor`（`cir.global_ctors` 优先级 65535）+ `atexit(@__cuda_module_dtor)`。没有 `cu.binary_handle` 就一行都不生成。
- **源码位置**：`CIRGenCUDANV.cpp` / `CIRGenCUDARuntime.{h,cpp}`（对应经典的 `CGCUDANV.cpp` / `CGCUDARuntime.{h,cpp}`），属性定义在 `CIRCUDAAttrs.td`（不是 `CIRAttrs.td`），测试在 `clang/test/CIR/CodeGenCUDA/` 与 `clang/test/CIR/CodeGenHIP/`。
- **现状**：PolyBench/GPU 84/84 编译通过，编译时间开销 CUDA 约 +0.4%、HIP 略高，运行时性能与经典路径持平。缺口：texture memory、RDC、OpenCL（进行中）、SYCL（基本未开始，但已有 `CIRGenSYCL.cpp`）。追踪 issue：`llvm/llvm-project#179278`。
