# 第 25 章 ClangIR：把 AST → LLVM IR 那一段切开

## 这一章想让你带走什么

<div class="goal-box">
<p>第 1 章立起的那条链是「源码 → IR →（优化）→ IR → 机器码」，并且给了 IR 三条硬指标：能落盘、有独立命令行工具、能人肉审查。这一章要指出这条链上一处一直没被满足的断崖：<strong>从 Clang AST 到 LLVM IR 的那一步</strong>。它是一个几万行的单体翻译过程，中间没有任何可观察、可落盘、可用工具处理的形态。<strong>ClangIR（简称 CIR）</strong>就是社区正在往这个断崖里填的一层。</p>
<p>读完你会知道：<code>cir</code> 是一个 <strong>MLIR 方言</strong>，它和 MLIR、LLVM IR 是三层「基础设施 / 客户 / 目标」的关系，谁也不替代谁；<code>-fclangir</code> 和 <code>-emit-cir</code> 怎么用；<code>cir-opt</code> / <code>cir-translate</code> 如何把第 1 章图 1-2 那套 <code>opt</code> / <code>llc</code> 的对称性复制到新一层上。而贯穿整章的主线是一个对照：<strong>CIR 路径和经典 CodeGen 路径的差别到底在哪，社区又用什么标准判定新路径是对的</strong>。这条主线会在目录、管线、测试、代价四个层面各走一遍。</p>
</div>

## 先说清楚：这一部分的源码锚点变了

前面 24 章的每条路径都能在 `intel/llvm` 里 `cd` 进去。这一部分不行——你要换一个仓库。

ClangIR 是**上游 LLVM 正在进行中的工作**，代码在 `llvm/llvm-project` 的主干上，主要落在 `clang/lib/CIR/`、`clang/include/clang/CIR/` 和 `clang/test/CIR/`。另有一个孵化器仓库 `llvm/clangir`，里面是尚未上游化的部分（比如后面会提到的 `ThroughMLIR/` 路径）。`intel/llvm` 会周期性地从上游拉取，所以这些目录在 DPC++ 树里也可能出现，但**它不是 DPC++ 的功能**，别把两者的进度混在一起看。

<div class="warn">
<strong>这一部分讲的是活的靶子</strong>
ClangIR 每周都在变：操作会改名（孵化器里叫 <code>!cir.record</code> 的类型，上游是 <code>!cir.struct</code>）、pass 会增删、追踪 issue 里的复选框会更新。本章给出的每个名字都取自写作时的上游源码与 lit 测试，但你读到时最可靠的做法是：以你手上那份 <code>llvm-project</code> 为准，用 <code>grep</code> 复核一遍。方法比清单更耐用——本章重点是让你会自己去 <code>clang/test/CIR/</code> 里找答案。
</div>

## 第 1 章那条链上的一处断崖

回到第 1 章的三段式。你会说：前端是 Clang，输入源码、输出 LLVM IR，清楚得很。

但把镜头推近到「前端」这个盒子内部，它自己也是分段的：源码 →（词法/语法分析）→ **AST** →（Sema 语义检查）→ AST →（CodeGen）→ **LLVM IR**。前两步之间的产物 AST 是一等公民：你能用 `clang -Xclang -ast-dump` 把它打印出来看，clang-tidy、clangd 这些工具就活在 AST 上。

问题出在最后一步。`clang/lib/CodeGen/` 那几万行代码（社区管它叫 **OG**，original CodeGen 的意思）做的事是：一边遍历 AST，一边**直接**往 `llvm::IRBuilder` 里吐指令。C++ 的 `for` 循环、虚函数调用、异常处理、构造函数——所有这些高层结构，在一次遍历里就被同时降级成了基本块 + `br` + `getelementptr`。中间**没有任何形态**。你没法说「给我看看降级到一半的样子」，因为不存在这样的东西。

对着第 1 章那三条指标一条条比：能落盘？不能。有独立工具？没有——你不能像 `opt` 那样把 AST→IR 这一段单独拎出来跑。能人肉审查？只能读 C++ 源码，不能读数据。

## `cir` 是一个 MLIR 方言

「ClangIR 和 MLIR、LLVM IR 是什么关系」是最容易搞混的一点。直接看方言定义文件的开头（`clang/include/clang/CIR/Dialect/IR/CIRDialect.td`）：

```tablegen-norun
include "mlir/IR/OpBase.td"

def CIR_Dialect : Dialect {
  let name = "cir";
  let summary = "A high-level dialect for analyzing and optimizing Clang "
                "supported languages";
  let cppNamespace = "::cir";
  let hasConstantMaterializer = 1;
  // ...
}
```

第一行就说明了一切：它 `include` 的是 MLIR 的 `OpBase.td`。**MLIR 不是一种 IR，而是一套「造 IR」的框架**——它提供操作/类型/属性的声明式定义（TableGen）、通用的 pass 管理器、通用的文本格式解析与打印、通用的验证器。任何人都能用它定义自己的一套操作，这套操作叫一个**方言（dialect）**。`cir` 就是这样一个方言，`name = "cir"` 决定了你在文本里看到的所有操作都带 `cir.` 前缀。

所以三者是三个不同层次上的东西：

| | 是什么 | 在这条链里的角色 |
|---|---|---|
| **MLIR** | 造 IR 的框架 / 基础设施 | 提供地基：TableGen 定义、pass 管理、文本格式、验证 |
| **`cir` 方言** | 用 MLIR 造出来的一种 IR | 新的中间层：贴近 C/C++ 语义，位于 AST 与 LLVM IR 之间 |
| **LLVM IR** | LLVM 原生的低层 IR | 终点：CIR 最后降级到它，之后一切照旧 |

<div class="note">
<strong>CIR 和 Flang 的 FIR 是同一种做法</strong>
如果你看过 Flang，这个套路会很熟：Flang 也在 AST 和 LLVM IR 之间放了一个 MLIR 方言，叫 <strong>FIR</strong>（Fortran IR），用来表达 Fortran 特有的高层概念（数组描述符、<code>do concurrent</code> 之类）。CIR 之于 Clang，就是 FIR 之于 Flang。这不是某个人的奇思妙想，而是 LLVM 生态里已经被验证过的一条路。
</div>

<div class="keypoint">
<strong>三句话，别再搞混</strong>
CIR <strong>不是</strong> MLIR 的替代品，它是 MLIR 的<strong>客户</strong>——用 MLIR 的基础设施造出来的一个方言。CIR <strong>不是</strong> LLVM IR 的替代品，LLVM IR 是它的<strong>降级目标</strong>。CIR 也<strong>不改变</strong>第 1 章那条链的下半段：中端的 Pass、后端的 Target、SPIR-V/PTX 的产出路径，一个字都不动。
</div>

## 看一眼真正的 CIR

最快建立直觉的办法是看同一段代码的三种形态。下面这段 C++：

```cpp-norun
int *f5() {
  int *p = nullptr;
  {
    int x = 0;
    p = &x;
    *p = 42;
  }
  *p = 43;
  return p;
}
```

它的 CIR 长这样（取自 `clang/test/CIR/CodeGenCXX/basic.cpp` 的 CHECK 行，为可读性去掉了 FileCheck 的变量捕获语法）：

```cir-norun
cir.func @_Z2f5v() -> (!cir.ptr<!s32i>) {
  %0 = cir.alloca "__retval" align(8) : !cir.ptr<!cir.ptr<!s32i>>
  %1 = cir.alloca "p" align(8) init : !cir.ptr<!cir.ptr<!s32i>>
  %2 = cir.const #cir.ptr<null> : !cir.ptr<!s32i>
  cir.store %2, %1 : !cir.ptr<!s32i>, !cir.ptr<!cir.ptr<!s32i>>
  cir.scope {
    %3 = cir.alloca "x" align(4) init : !cir.ptr<!s32i>
    %4 = cir.const #cir.int<0> : !s32i
    cir.store %4, %3 : !s32i, !cir.ptr<!s32i>
    cir.store %3, %1 : !cir.ptr<!s32i>, !cir.ptr<!cir.ptr<!s32i>>
    %5 = cir.const #cir.int<42> : !s32i
    %6 = cir.load deref %1 : !cir.ptr<!cir.ptr<!s32i>>, !cir.ptr<!s32i>
    cir.store %5, %6 : !s32i, !cir.ptr<!s32i>
  }
  %7 = cir.const #cir.int<43> : !s32i
  %8 = cir.load deref %1 : !cir.ptr<!cir.ptr<!s32i>>, !cir.ptr<!s32i>
  cir.store %7, %8 : !s32i, !cir.ptr<!s32i>
  %9 = cir.load %1 : !cir.ptr<!cir.ptr<!s32i>>, !cir.ptr<!s32i>
  cir.store %9, %0 : !cir.ptr<!s32i>, !cir.ptr<!cir.ptr<!s32i>>
  %10 = cir.load %0 : !cir.ptr<!cir.ptr<!s32i>>, !cir.ptr<!s32i>
  cir.return %10 : !cir.ptr<!s32i>
}
```

即使你从没见过 MLIR，也能读出至少四件在 LLVM IR 里看不到的东西：

- **变量名还在**。`cir.alloca "p"`、`cir.alloca "x"`——源码里的标识符被当作 alloca 的一部分保留了下来。LLVM IR 里 `-O0` 下你只能靠调试信息把 `%1` 关联回 `p`。
- **有符号性写在类型里**。`!s32i` 是「有符号 32 位整数」，对应的还有 `!u32i`。LLVM IR 的 `i32` 不带符号信息，符号性藏在指令上（`sdiv` 还是 `udiv`）。CIR 把它放回了类型，因为 C 的类型系统本来就有。
- **常量是有类型的属性**。`#cir.int<0> : !s32i`、`#cir.ptr<null>`——这是 MLIR 的属性系统，不是一串裸位。
- **作用域还在**。那对 `cir.scope { ... }` 花括号就是源码里的那对花括号。它是一个**带 region 的操作**，`x` 的生命周期显式地被框在里面。到了 LLVM IR，这层结构会消失，`x` 的 alloca 被提到函数入口块。

把它和同一个函数在 `-O0` 下的 LLVM IR 摆在一起对照：

<div class="note">
<strong>「更高层」的准确含义</strong>
别把 CIR 想成「更抽象所以更模糊」。它和 LLVM IR 一样是 SSA、一样有显式的 load/store、一样能验证。差别在于它<strong>额外保留了一批前端知道、后端不需要的事实</strong>：作用域、有符号性、变量名、类的继承结构、异常的作用域嵌套（第 26 章）、CUDA 的地址空间语义（第 27 章）。这些事实在降到 LLVM IR 的过程中会被逐步丢弃——但在丢弃之前，它们可以被利用。
</div>

## 上手：`-fclangir` 和 `-emit-cir`

驱动层的开关定义在 `clang/include/clang/Options/Options.td`（注意这个文件从 `clang/include/clang/Driver/` 搬过来了）。核心的两个：

```bash
# 用 CIR 路径编译（默认关闭；关掉是 -fno-clangir）
clang -fclangir -c foo.cpp -o foo.o

# 只走到 cir 方言就停下，把 .cir 文本打印出来
clang -fclangir -Xclang -emit-cir -S foo.cpp -o foo.cir

# cc1 层直接调用（lit 测试里最常见的写法）
clang -cc1 -triple x86_64-unknown-linux-gnu -fclangir -emit-cir foo.cpp -o -
```

`-fclangir` 在 Options.td 里是一个 `BoolFOption`，绑到 `FrontendOpts<"UseClangIRPipeline">`，`DefaultFalse`；它的正向说明是「Use the ClangIR pipeline to compile」，反向是「Use the AST -> LLVM pipeline to compile」——**社区自己就把这两条路径写成了一对开关**。`-emit-cir` 的帮助文本是「Build ASTs and then lower to ClangIR」。

除此之外还有一组调试与实验用的开关，值得记住，因为它们直接对应「CIR 是可观察的」这个卖点：

| 开关 | 作用 |
|---|---|
| `-fclangir-disable-passes` | 跳过所有 CIR → CIR pass，看最原始的 CIRGen 输出 |
| `-fclangir-disable-verifier` | 关掉 MLIR 验证器（调试半成品 pass 时用） |
| `-fclangir-enable-idiom-recognizer` | 打开惯用法识别 pass |
| `-fclangir-lib-opt[=all]` | 打开库感知优化 pass |
| `-fno-clangir-call-conv-lowering` | 关掉调用约定降级（目前只实现了 x86_64） |
| `-mmlir -mlir-print-ir-before=<pass>` | 借 MLIR 的通用能力，打印某个 pass 前的 IR |

最后那一行尤其值得注意：`-mmlir` 后面跟的是 **MLIR 自己的命令行选项**。因为 CIR 是个 MLIR 方言，它免费继承了 MLIR 那套 pass 插桩设施——打印每个 pass 前后的 IR、统计、计时、崩溃复现。这是「当客户而不是自己造框架」的直接回报。第 27 章会用 `-mlir-print-ir-before=cir-target-lowering` 来观察地址空间是怎么变的。

## 对照第一层：两棵目录树是一一对应的

现在进入本章的主线。CIR 和经典路径的第一层对照，是**文件级的**。列一下两个目录，规律一眼就能看出来：

| 经典 `clang/lib/CodeGen/` | CIR `clang/lib/CIR/CodeGen/` | 管什么 |
|---|---|---|
| `CodeGenModule.cpp` | `CIRGenModule.cpp` | 翻译单元级别：全局变量、函数声明 |
| `CodeGenFunction.cpp` | `CIRGenFunction.cpp` | 单个函数的生成状态 |
| `CGStmt.cpp` | `CIRGenStmt.cpp` | 语句（`if`/`for`/`return`…） |
| `CGExpr*.cpp` | `CIRGenExpr*.cpp` | 表达式（标量、聚合、常量…） |
| `CGClass.cpp` | `CIRGenClass.cpp` | 类：构造/析构、基类布局 |
| `CGVTables.cpp` | `CIRGenVTables.cpp` | 虚表 |
| `CGException.cpp` / `CGCleanup.cpp` | `CIRGenException.cpp` / `CIRGenCleanup.cpp` | 异常与清理 |
| `CGCXXABI.cpp` / `CGItaniumCXXABI.cpp` | `CIRGenCXXABI.cpp` / `CIRGenItaniumCXXABI.cpp` | C++ ABI |
| `CGCall.cpp` / `ABIInfo.h` / `TargetInfo.cpp` | `CIRGenCall.cpp` / `ABIInfo.h` / `TargetInfo.cpp` | 调用约定与目标 ABI |
| `CGCUDANV.cpp` / `CGCUDARuntime.cpp` | `CIRGenCUDANV.cpp` / `CIRGenCUDARuntime.cpp` | CUDA/HIP（第 27 章） |

这个 `CG*` → `CIRGen*` 的机械命名不是巧合，是**有意的工程决策**：让每一个新文件都有一个明确的「对照物」。做 CIR 的人写 `CIRGenClass.cpp` 时，手边打开的就是 `CGClass.cpp`；评审的人也知道该拿哪个文件比。这把一个庞大的重写工程切成了几十个可以独立推进、独立评审的小工程。

有几个文件只在 CIR 一侧存在，它们标出了这条新路径想吃下的新东西：

- `CIRGenSYCL.cpp` —— 是的，SYCL。里面有 `CIRGenFunction::emitSYCLKernelCallStmt` 和 `emitSYCLKernelCaller`，处理 `SYCLKernelCallStmt` 与 outlined kernel。对读这本书的你来说，这是第五部分和前面 12 章真正接起来的地方。
- 六个 `CIRGenOpenACC*` 文件 —— OpenACC 在 CIR 上的支持面积相当大，`clang/test/CIR/CodeGenOpenACC/` 有 85 个测试文件。
- `CIRGenBuiltinNVPTX.cpp` / `CIRGenBuiltinAMDGPU.cpp` / `CIRGenAMDGPU.cpp` —— GPU 目标的内建函数。

## 对照第二层：管线

经典路径里，「AST → LLVM IR」是一次遍历。CIR 路径里，它变成了**一层 IR + 一串 pass**。这串 pass 的顺序不是猜的，就写在 `clang/lib/CIR/Lowering/CIRPasses.cpp` 的 `runCIRToCIRPasses()` 里：

```cpp-norun
mlir::PassManager pm(&mlirContext);
pm.addPass(mlir::createCIRCanonicalizePass());          // 规范化
if (enableCIRSimplify)
  pm.addPass(mlir::createCIRSimplifyPass());            // 化简
if (enableIdiomRecognizer)
  pm.addPass(mlir::createIdiomRecognizerPass());        // 惯用法识别（可选）
if (enableLibOpt)
  pm.addPass(std::move(libOptPass));                    // 库感知优化（可选）
pm.addPass(mlir::createTargetLoweringPass());           // 目标相关降级
pm.addPass(mlir::createCXXABILoweringPass());           // C++ ABI 降级
pm.addPass(mlir::createLoweringPreparePass(&astContext));// 降级准备
if (enableCallConvLowering)
  pm.addPass(mlir::createCallConvLoweringPass(...));    // 调用约定降级（x86_64）
```

再往下，临降到 LLVM 方言之前还有一组，在同一个文件的 `populateCIRPreLoweringPasses()` 里：

```cpp-norun
void populateCIRPreLoweringPasses(OpPassManager &pm) {
  pm.addPass(createHoistAllocasPass());     // alloca 提到入口块
  pm.addPass(createCIRFlattenCFGPass());    // 结构化控制流 → 基本块 + 分支
  pm.addPass(createCIREHABILoweringPass()); // 异常 ABI 降级
  pm.addPass(createGotoSolverPass());       // 解决 goto
}
```

请留意这两段代码里那些**顺序约束的注释**，它们是这套设计里最有信息量的部分。比如源码里明确写着：`LoweringPrepare` 必须跑在 `CallConvLowering` 之前，因为它会合成 `__divsc3` 这类运行时辅助函数、并把动态全局初始化器外提成函数——如果顺序反了，这些新函数的签名就没被分类过，调用方和被调方对 ABI 的理解会不一致。又比如 `CallConvLowering` 必须跑在 `CXXABILowering` 之后，因为分类器只认得已经被降成普通记录类型的东西。

这些约束在经典路径里也存在，但它们**隐含在 `clang/lib/CodeGen/` 里几万行代码的调用顺序中**，你只能靠读代码推断。在 CIR 里，它们变成了 pass 之间的显式顺序 + 一句解释顺序理由的注释。这就是「把一段代码拆成一层 IR + 若干 pass」在工程上的实际收益：**隐含的顺序契约变成了显式的、有文档的、可以单独测试的顺序契约**。

<div class="note">
<strong>只有一条降级路径上游了</strong>
<code>clang/lib/CIR/Lowering/</code> 下目前只有 <code>DirectToLLVM/</code>：从 <code>cir</code> 方言直接降到 MLIR 的 LLVM 方言，再出 LLVM IR。孵化器 <code>llvm/clangir</code> 里还有一条 <code>ThroughMLIR/</code>，先降到 MLIR 的通用方言（<code>scf</code>、<code>memref</code>、<code>affine</code> 之类）再往下走——那条路才是「用上 MLIR 生态里现成的循环/多面体优化」的野心所在，但它没有上游，也不是当前的主线。本章讲的一切都走 <code>DirectToLLVM</code>。
</div>

## 对照第三层：三条 RUN 线把对照制度化

前两层对照是「作者写代码时的参照」。第三层最关键：对照被**写进了测试的形状里**，成了制度。

打开 `clang/test/CIR/` 下几乎任何一个 CodeGen 测试，开头都是这样三条 RUN 线：

```bash
// RUN: %clang_cc1 ... -fclangir -emit-cir  %s -o %t.cir
// RUN: FileCheck --input-file=%t.cir %s --check-prefix=CIR
// RUN: %clang_cc1 ... -fclangir -emit-llvm %s -o %t-cir.ll
// RUN: FileCheck --input-file=%t-cir.ll %s --check-prefix=LLVM
// RUN: %clang_cc1 ...           -emit-llvm %s -o %t.ll
// RUN: FileCheck --input-file=%t.ll %s --check-prefix=OGCG
```

同一个源文件，编译三遍，三组 CHECK 前缀：

- **`CIR`** —— CIR 路径停在 `cir` 方言时的样子。这是「新表示对不对」。
- **`LLVM`** —— CIR 路径一直走到 LLVM IR 的样子。这是「降级对不对」。
- **`OGCG`** —— 经典路径产出的 LLVM IR。**OGCG 就是 original CodeGen 的缩写**，社区把「旧路径」这个概念直接做成了一个 FileCheck 前缀。

`LLVM` 和 `OGCG` 两组 CHECK 盯着的是同一件事的两种实现，于是每个测试都在回答那个核心问题：**新路径产出的 LLVM IR，和旧路径一样吗？** 这就是 CIR 的正确性定义。有些测试更进一步，让**同一组 CHECK 行**同时校验两个输出文件——两条路径必须产出逐字符相同的那部分，就用这种写法钉住。

但「一样」不等于「逐字符相同」，这是理解 CIR 的另一个关键点。看一个真实例子：虚函数调用中取虚表地址那一步，两条路径产出的 LLVM IR 是这样的（来自 `clang/test/CIR/CodeGenCXX/virtual-function-calls.cpp`）：

<div class="compare">
<div class="known">
<div class="compare-head">CIR 路径产出</div>

```llvm-norun
getelementptr inbounds nuw
  (i8, ptr @_ZTV1A, i64 16)
```

</div>
<div class="cpp-side">
<div class="compare-head">经典路径（OGCG）产出</div>

```llvm-norun
getelementptr inbounds
  inrange(-16, 8)
  ({ [3 x ptr] }, ptr @_ZTV1A,
   i32 0, i32 0, i32 2)
```

</div>
</div>

文本完全不同：一个是按字节偏移的扁平 GEP，一个是按结构层次走下去、还带 `inrange` 注解的 GEP。测试文件里有一条注释明确说这两者**是等价的**——指向同一个地址。所以判定标准是**语义等价（parity）**，不是文本相同。类似的情况在循环上更明显：`-O0` 下同一个空 `for` 循环，CIR 路径产出的 LLVM IR 有 6 个标签，经典路径只有 1 条 `br`，因为两者对「循环这个结构」的降级策略不同，但优化过后行为一致。

<div class="warn">
<strong>parity 是一条极苛刻的验收线</strong>
「产出等价的 LLVM IR」听起来温和，实际上意味着：CIR 必须把 C++ 的每一个阴暗角落——位域布局、虚基类偏移、异常表、各目标的调用约定分类规则、<code>__attribute__</code> 的语义——全部重新实现一遍，而且结果要和一个演化了二十年、里面塞满了「为了兼容某版 GCC 的某个行为」的实现对齐。这就是为什么进度以「支持了哪些 C++ 特性」为单位缓慢推进，而不是一口气切换。也是为什么 <code>-fclangir</code> 默认是关的。
</div>

## 对照第四层：代价和收益

把上面三层放在一起，你就能自己判断这件事值不值得，而不是听结论。

**代价，很直白。** 一是要重新实现一遍 CodeGen，工作量以人年计；二是编译时间和内存会增加——多了一层 IR、多了一串 pass、多了 MLIR 的验证器；三是维护面变宽，在 `-fclangir` 默认打开之前，任何 CodeGen 的改动理论上都要考虑两条路径；四是引入了对 MLIR 的依赖，Clang 的构建不再只依赖 LLVM 核心。

**收益，需要分成三类看。**

第一类是**已经拿到的**。`.cir` 是可落盘、可读、可手写的文本格式，配上 `cir-opt` 和 `cir-translate` 两个工具，你可以像调试中端 Pass 一样调试前端降级过程——写一个 `.cir` 文件，跑单个 pass，看输出。这一点已经改变了开发体验，而且第 1 章那三条指标现在全部满足了。

第二类是**在做的**：在高层做那些在 LLVM IR 上做不了或做起来很别扭的分析和优化。惯用法识别（把 `std::find` 这类库调用识别成一个高层操作）、库感知优化，都属于这一类。它们依赖的正是那些 LLVM IR 里已经丢掉的事实。

第三类是**结构性的**：新增一个「可以挂东西的地方」。这一点在第 27 章会看得最清楚——CUDA/HIP 的主机端和设备端表示可以在同一层里共存，让「主机-设备协同优化」第一次有了一个自然的落点。经典路径里没有这样的地方，因为主机和设备的 LLVM IR 从一开始就是两个独立的 Module。

<div class="keypoint">
<strong>一句话总结这四层对照</strong>
目录上一一对应（<code>CG*</code> → <code>CIRGen*</code>），管线上从「一次遍历」变成「一层 IR + 一串有显式顺序契约的 pass」，测试上用三条 RUN 线和 <code>OGCG</code> 前缀把「和旧路径对齐」做成了制度，代价上换来了一个可观察、可挂载高层信息的中间层。CIR 不是「更好的 LLVM IR」，它是<strong>把前端最不透明的那一段变透明</strong>。
</div>

## 工具链的对称：`cir-opt` 与 `cir-translate`

第 1 章图 1-2 的核心洞察是：因为 IR 能落盘，三段就能拆成 `clang` / `opt` / `llc` 三个工具。CIR 把这个洞察在新一层上复制了一遍。`clang/tools/` 下有三个新目录：

| LLVM IR 世界 | CIR 世界 | 干什么 |
|---|---|---|
| `opt` | `cir-opt` | 读 `.cir`，跑指定的 pass，写 `.cir` |
| `llc` | `cir-translate --cir-to-llvmir` | 读 `.cir`，翻成 LLVM IR |
| （clangd 的一部分） | `cir-lsp-server` | 在编辑器里给 `.cir` 文件提供跳转/补全 |

于是一个 CIR pass 的测试可以完全不碰 C++ 源码，就像这样（`clang/test/CIR/Transforms/` 下的测试都是这个样子）：

```bash
// RUN: cir-opt %s -cir-flatten-cfg -o - | FileCheck %s
```

输入是手写的 `.cir`，输出用 FileCheck 校验。你甚至可以手写一个只有几行的模块，把目标三元组和数据布局直接写在模块属性上：

```cir-norun
module attributes {
  cir.triple = "spirv64-unknown-unknown",
  dlti.dl_spec = #dlti.dl_spec<...>
} {
  cir.func @foo() {
    cir.return
  }
}
```

然后：`cir-translate --cir-to-llvmir --target x86_64-unknown-linux-gnu %s`。这种「手写中间表示、单跑一个 pass」的能力，在经典路径上是不存在的——那里唯一的输入是 C++ 源码，唯一的输出是 LLVM IR，中间无法插手。

## 动手：结构化 vs 扁平，同一个函数的两种形态

CIR 最核心的一个差别是**控制流是结构化的**：`for` 就是一个 `cir.for` 操作，它的循环体是一个 region，嵌在里面。LLVM IR 里没有这种东西，只有基本块和分支。下面这个能在浏览器里跑的小程序，把这件事变成你看得见的数字：它先按 CIR 的样子写一个函数（嵌套的结构化操作），再按经典路径的做法把它扁平化成基本块，然后对比在这两种形态上回答同一个问题各要做多少事。点 **▶ 运行**。

```python
# CIR 的结构化形态 vs LLVM IR 的扁平形态：同一个函数，两种表示

# ---- 形态一：结构化（CIR 的 region 就是这个形状，嵌套和源码一一对应）----
FUNC = ("sum", [
    ("op", "alloca acc"),
    ("for", [
        ("op", "add acc"),
        ("for", [("op", "add acc")]),      # 内层循环
        ("if", [("op", "add acc")], []),   # 只有 then，没有 else
    ]),
    ("op", "return acc"),
])

def show(body, depth=1):
    pad = "  " * depth
    for node in body:
        if node[0] == "op":
            print(pad + "cir." + node[1])
        elif node[0] == "for":
            print(pad + "cir.for {")
            show(node[1], depth + 1)
            print(pad + "}")
        elif node[0] == "if":
            print(pad + "cir.if {")
            show(node[1], depth + 1)
            print(pad + "}")

print("=== 形态一：结构化（CIR）===")
print("cir.func @%s {" % FUNC[0])
show(FUNC[1])
print("}")

# ---- 形态二：扁平化（LLVM IR）。这正是 cir-flatten-cfg 干的事 ----
blocks, edges, counter = [], [], [0]

def fresh():
    counter[0] += 1
    return "bb%d" % counter[0]

def start(label):
    blocks.append((label, []))

def cur():
    return blocks[-1][0]

def emit(text):
    blocks[-1][1].append(text)

def link(a, b):
    edges.append((a, b))

def lower(body):
    for node in body:
        if node[0] == "op":
            emit(node[1])
        elif node[0] == "for":
            cond, body_l, done = fresh(), fresh(), fresh()
            emit("br ^%s" % cond)
            link(cur(), cond)
            start(cond)
            emit("brcond %%c -> ^%s, ^%s" % (body_l, done))
            link(cond, body_l)
            link(cond, done)
            start(body_l)
            lower(node[1])
            emit("br ^%s" % cond)
            link(cur(), cond)
            start(done)
        elif node[0] == "if":
            then_l, join = fresh(), fresh()
            emit("brcond %%c -> ^%s, ^%s" % (then_l, join))
            link(cur(), then_l)
            link(cur(), join)
            start(then_l)
            lower(node[1])
            emit("br ^%s" % join)
            link(cur(), join)
            start(join)

start("entry")
lower(FUNC[1])

print()
print("=== 形态二：扁平化（LLVM IR）===")
for label, instrs in blocks:
    print("^%s:" % label)
    for ins in instrs:
        print("  " + ins)

# ---- 同一个问题，两种形态各要做多少事 ----
def loop_depth(body):
    best = 0
    for node in body:
        if node[0] == "for":
            best = max(best, 1 + loop_depth(node[1]))
        elif node[0] == "if":
            best = max(best, loop_depth(node[1]))
    return best

order = {}
for i, (label, _) in enumerate(blocks):
    order[label] = i
back = [(a, b) for a, b in edges if order[b] <= order[a]]

print()
print("=== 问题：这个函数里循环最深套了几层？===")
print("结构化：一次递归遍历就读出来 = %d 层" % loop_depth(FUNC[1]))
print("扁平化：%d 个基本块 + %d 条边，先找回边（%d 条），" % (len(blocks), len(edges), len(back)))
print("        再算支配关系，才知道哪个循环套在哪个里面")
print()
print("源码里 3 个控制流构造 → 扁平化后 %d 个基本块、%d 条边。" % (len(blocks), len(edges)))
print("CIR 的价值不是「扁平形态丢了信息」，而是：在扁平之前，")
print("这些问题是「读出来」的，不是「算出来」的。")
```

运行结果：

## 小结与下一步

- 第 1 章那条链在前端内部有一处断崖：**AST → LLVM IR** 是一次单体遍历，中间没有可落盘、可用工具处理、可人肉审查的形态。CIR 就是往这里填的一层。
- **`cir` 是一个 MLIR 方言**（`name = "cir"`，`cppNamespace = "::cir"`）。三层关系是：MLIR 是造 IR 的框架，`cir` 是用它造出来的一种 IR，LLVM IR 是 `cir` 的降级目标。谁也不替代谁。这和 Flang 的 FIR 是同一种做法。
- CIR 里额外保留着前端知道、后端不需要的事实：变量名、有符号性（`!s32i` vs `!u32i`）、作用域（`cir.scope`）、结构化控制流。
- 与经典路径的对照有四层：**目录**（`CG*` → `CIRGen*` 一一对应）、**管线**（`CIRPasses.cpp` 里显式的 pass 顺序 + 顺序理由的注释）、**测试**（三条 RUN 线，`CIR` / `LLVM` / `OGCG` 三个前缀）、**代价与收益**。
- 正确性的定义是 **parity**：产出与经典路径**语义等价**的 LLVM IR，不是文本相同。虚表 GEP 那个例子就是明证。

下一章我们钻进 `cir` 方言内部，看 C++ 里最难的那几样东西在这一层长什么样：`cir.if` / `cir.for` / `cir.try` 这些带 region 的结构化操作，`cir-flatten-cfg` 怎么把它们拍平；`!cir.struct` / `!cir.vptr` / `!cir.method` 怎么承载类和虚表；以及异常处理为什么值得单独一个 pass。

**这一章的要点**

- 前端内部 `AST → LLVM IR` 这一步（`clang/lib/CodeGen/`，社区叫 **OG**）是单体的、无中间形态的，不满足第 1 章给 IR 立的三条指标。**ClangIR（CIR）** 是往这一段里插入的一层。
- `cir` 是一个 **MLIR 方言**：`include "mlir/IR/OpBase.td"`、`let name = "cir"`。**MLIR 是造 IR 的框架，不是一种 IR**；CIR 是它的客户，LLVM IR 是 CIR 的降级目标。
- 源码锚点：`clang/lib/CIR/`（`CodeGen/` + `Lowering/DirectToLLVM/`）、`clang/include/clang/CIR/Dialect/IR/*.td`、`clang/test/CIR/`、`clang/tools/cir-{opt,translate,lsp-server}`。仓库是上游 `llvm/llvm-project`，不是 `intel/llvm`。
- 开关：`-fclangir` 走新路径（默认关），`-emit-cir` 停在 `cir` 方言，`-fclangir-disable-passes` 看最原始的 CIRGen 输出，`-mmlir -mlir-print-ir-before=<pass>` 借 MLIR 的插桩能力观察每个 pass。
- 与经典路径的四层对照：**目录**一一对应（`CGClass.cpp` ↔ `CIRGenClass.cpp`）、**管线**从一次遍历变成显式 pass 序列、**测试**用 `CIR`/`LLVM`/`OGCG` 三前缀制度化、**代价**（重写工作量、编译开销）换**收益**（可观察的中间层、高层优化的落点）。
- 正确性标准是 **parity（语义等价）**，不是文本相同——虚表 GEP 的两种写法指向同一地址，测试里专门有注释说明。
- 工具链对称复制了第 1 章图 1-2：`opt` ↔ `cir-opt`，`llc` ↔ `cir-translate --cir-to-llvmir`。`.cir` 能手写、能落盘、能单跑一个 pass。
