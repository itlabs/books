## Region：控制流不用基本块表达

MLIR 的核心数据结构比 LLVM IR 多了一层。LLVM IR 是 Module → Function → BasicBlock → Instruction 四级（第 2 章）。MLIR 是 Operation → **Region** → Block → Operation，**可以无限嵌套**：一个操作可以带若干个 region，每个 region 里有若干个 block，每个 block 里又有若干个操作，其中任意一个又可以带 region。

这一层嵌套就是 CIR 能保留控制流结构的全部本钱。`for` 循环不必被拆成「条件块 + 循环体块 + 跳转」，它可以就是**一个操作**，循环的各个部分是这个操作的 region。

`clang/include/clang/CIR/Dialect/IR/CIROps.td` 里，这类操作有一个共同的基类 `CIR_RegionBranchOpBase`（或它的变体），带 region 的操作主要有：

| 操作 | region | 对应的 C/C++ 构造 |
|---|---|---|
| `cir.if` | then、（可选）else | `if` / `else` |
| `cir.scope` | 一个 | 一对花括号构成的作用域 |
| `cir.switch` + `cir.case` | 每个 case 一个 | `switch` / `case` / `default` |
| `cir.while` / `cir.do` | cond、body | `while` / `do-while` |
| `cir.for` | cond、body、step | `for` |
| `cir.ternary` | true、false | `?:` |
| `cir.global` | 一个（可选） | 带动态初始化的全局变量 |
| `cir.try` | try body + 每个 handler 一个 | `try` / `catch` |
| `cir.cleanup.scope` | body、cleanup | RAII 清理（没有源码对应物） |
| `cir.await` / `cir.coro.body` | 多个 | 协程 |

region 内部需要终结子，CIR 为此定义了一组专门的操作：`cir.yield`（把控制权交回外层操作，最常见）、`cir.condition`（在 cond region 末尾给出布尔结果）、`cir.break` / `cir.continue`（对应 C++ 的同名语句，直接就是操作，不需要在生成时就算出跳到哪个块）。

看一眼 `cir.for` 的实际形状（取自 `clang/test/CIR/CodeGen/loop.cpp`，一个空的 `for (;;) {}`）：

```cir-norun
cir.for : cond {
    %true = cir.const #true
    cir.condition(%true)
} body {
    cir.yield
} step {
    cir.yield
}
```

三个 region 一字排开，各自的角色写在关键字里。这和源码的 `for (init; cond; step) body` 是一一对应的。

## `cir-flatten-cfg`：结构消失的那一刻

结构化控制流迟早要变成基本块，因为 LLVM IR 只认基本块。做这件事的 pass 叫 **`cir-flatten-cfg`**，它在第 25 章那个 `populateCIRPreLoweringPasses()` 列表里排第二。

因为 `.cir` 能手写，这个 pass 的测试可以完全不碰 C++。下面是 `clang/test/CIR/Transforms/if.cir` 的全文（这是一个非常值得精读的文件，它把「一个 pass 做什么」讲得比任何文档都清楚）：

```cir-norun
// RUN: cir-opt %s -cir-flatten-cfg -o - | FileCheck %s

!s32i = !cir.int<s, 32>
module {
  cir.func @foo(%arg0: !s32i) -> !s32i {
    %4 = cir.cast int_to_bool %arg0 : !s32i -> !cir.bool
    cir.if %4 {
      %5 = cir.const #cir.int<1> : !s32i
      cir.return %5 : !s32i
    } else {
      %5 = cir.const #cir.int<0> : !s32i
      cir.return %5 : !s32i
    }
    cir.return %arg0 : !s32i
  }
}
```

跑完 pass 之后，`cir.if` 那个带两个 region 的操作消失了，换成了 `cir.brcond` 和三个基本块：

```cir-norun
//      CHECK: cir.func{{.*}} @foo(%arg0: !s32i) -> !s32i {
// CHECK-NEXT:   %0 = cir.cast int_to_bool %arg0 : !s32i -> !cir.bool
// CHECK-NEXT:   cir.brcond %0 ^bb1, ^bb2
// CHECK-NEXT: ^bb1:  // pred: ^bb0
// CHECK-NEXT:   %1 = cir.const #cir.int<1> : !s32i
// CHECK-NEXT:   cir.return %1 : !s32i
// CHECK-NEXT: ^bb2:  // pred: ^bb0
// CHECK-NEXT:   %2 = cir.const #cir.int<0> : !s32i
// CHECK-NEXT:   cir.return %2 : !s32i
// CHECK-NEXT: ^bb3:  // no predecessors
// CHECK-NEXT:   cir.return %arg0 : !s32i
// CHECK-NEXT: }
```

注意最后那个 `^bb3: // no predecessors`。原本 `cir.if` 之后的那条 `cir.return %arg0` 是**语法上可达**的（它就写在 if 后面），但因为两个分支都 return 了，扁平化之后它成了一个没有前驱的块。这个注释是 MLIR 打印器自动加的——**扁平化前后「可达性」这个概念的含义变了**：之前是嵌套关系，之后是图连通性。同一个 pass 目录下还有 `cir.switch` → `cir.switch.flat` 的降级，以及 `cir.goto` / `cir.label` 由 `cir-goto-solver` 单独处理（goto 是唯一无法用嵌套结构表达的控制流，所以它需要自己的 pass）。

<div class="note">
<strong>为什么值得单独做成一个 pass</strong>
在经典路径里，「把 <code>if</code> 变成基本块」和「生成 <code>if</code> 里面的代码」是同一次遍历里交织完成的：<code>CGStmt.cpp</code> 一边创建 <code>llvm::BasicBlock</code>、一边 <code>EmitBlock</code>、一边递归下降。在 CIR 里这两件事被分开：CIRGen 只负责造出结构化的 <code>cir.if</code>，扁平化是后面一个独立、可单独测试、输入输出都能落盘的 pass。代价是多跑一趟 IR；收益是在这两者之间，你有一个「控制流还是结构化的」时刻可以做事。
</div>

## 类：`!cir.struct` 把布局讲明白

C++ 的类在 LLVM IR 里是 `%class.Foo = type { i32, ptr, [3 x i8] }`——一串按顺序排列的字段类型，没有名字、没有继承关系、padding 和真实成员长得一样。CIR 的 `!cir.struct` 保留得多得多。

它有三种形态（`CIRTypes.td` 里明确列出）：**具名且完整**、**具名但不完整**、**匿名**。而且每个成员都带一个「种类」标记：

```cir-norun
!rec_complete   = !cir.struct<"complete" {data !u8i}>
!rec_class      = !cir.struct<class "MyClass" {data !s32i}>
!rec_incomplete = !cir.struct<"incomplete" incomplete>
!anonymous      = !cir.struct<{data !u8i}>
!rec_packed     = !cir.struct<"p1" packed {data !u8i, data !u8i}>
!rec_pad        = !cir.struct<"p3" {data !u8i, pad !cir.array<!u8i x 3>}>
!rec_empty      = !cir.struct<"e" {empty !u8i}>
!recursive      = !cir.struct<"Node" {data !cir.ptr<!cir.struct<"Node">>}>
```

四件事值得注意：

- **`class` 关键字被保留了**。`!cir.struct<class "MyClass" ...>` 和 `!cir.struct<"MyStruct" ...>` 在语义上完全一样（C++ 里 `class` 和 `struct` 只差默认访问权限，那是 Sema 的事），但 CIR 仍然记着源码里写的是哪个词。
- **padding 是显式的成员种类**。`pad !cir.array<!u8i x 3>` 明确说「这三字节是填充」。LLVM IR 里它就是普通的 `[3 x i8]`，你无法区分它和一个真的三字节数组成员。
- **不完整类型是一等形态**。`!cir.struct<"incomplete" incomplete>` 是一个合法的类型。LLVM IR 里没有这个概念——`clang/test/CIR/CodeGenCXX/class.cpp` 里有一条注释直接指出：对不完整的类，**LLVM 和 OGCG 两边都根本不发射类型**。CIR 却把它记下来了。
- **继承关系反映在成员上**。基类作为第一个 `data` 成员出现。

在 CIR 里访问成员用 `cir.get_member`（取地址）、`cir.extract_member` / `cir.insert_member`（按值取/放，用于聚合值），位域用专门的 `cir.get_bitfield` / `cir.set_bitfield`——而不是 LLVM IR 里那套「GEP 到字节 + load + 移位 + 掩码」。位域访问单元本身有一个类型 `!cir.bitfield`，把「这个访问单元里装了哪些位域声明」写在类型上。基类与派生类之间的指针调整也是专门的操作：`cir.base_class_addr` / `cir.derived_class_addr`，而不是一个裸的字节偏移 GEP。

## 虚表：一次虚调用被拆成四步

虚函数调用是 CIR「高层」体现得最漂亮的地方。CIR 定义了一个专门的类型 `!cir.vptr`，它不是 `ptr`，而是「C++ 对象里那个虚表指针成员」的专用类型——`CIRTypes.td` 里说得很直白，这么做是为了避免用任意指针类型来声明 vptr，从而**能对涉及 vptr 的操作做基于类型的检查**。

配套的操作有四个（`clang/include/clang/CIR/Dialect/IR/CIROps.td`）：

| 操作 | 干什么 | 返回 |
|---|---|---|
| `cir.vtable.address_point` | 取某个虚表全局变量的「地址点」 | `!cir.vptr` |
| `cir.vtable.get_vptr` | 取对象里 vptr 成员的地址 | `!cir.ptr<!cir.vptr>` |
| `cir.vtable.get_virtual_fn_addr` | 从 vptr 里按下标取虚函数指针的地址 | 指向函数指针的指针 |
| `cir.vtable.get_type_info` | 取类型信息条目（`dynamic_cast` / `typeid` 用） | — |

`address_point` 那个操作的属性尤其能说明问题。它带的不是一个字节偏移，而是 `address_point = <index = 0, offset = 2>` ——**`index` 是虚表组里的第几张虚表，`offset` 是这张虚表里的第几个地址点**，这两个概念直接来自 Itanium ABI 的术语。多重继承下一个类有多张虚表，这个二元组把它讲清楚了；换成一个字节数，信息就压扁了。

TableGen 文档里给的完整调用序列是这样（`!rec_C` 是某个带虚函数的类）：

```cir-norun
%2 = cir.load %0 : !cir.ptr<!cir.ptr<!rec_C>>, !cir.ptr<!rec_C>
%3 = cir.vtable.get_vptr %2 : !cir.ptr<!rec_C> -> !cir.ptr<!cir.vptr>
%4 = cir.load %3 : !cir.ptr<!cir.vptr>, !cir.vptr
%5 = cir.vtable.get_virtual_fn_addr %4[2] : !cir.vptr
              -> !cir.ptr<!cir.ptr<!cir.func<(!cir.ptr<!rec_C>) -> !s32i>>>
%6 = cir.load align(8) %5 : ...
%7 = cir.call %6(%2) : (..., !cir.ptr<!rec_C>) -> !s32i
```

读起来像一段说明文：取对象 → 取 vptr 地址 → 载入 vptr → 取第 2 号虚函数的槽位地址 → 载入函数指针 → 调用。而对象内 vptr 的初始化（构造函数里那一步）就是把 `cir.vtable.address_point` 的结果 store 进 `cir.vtable.get_vptr` 的结果。

这里正好接上第 25 章讲 parity 时用的那个例子：这套操作降到 LLVM IR 之后是 `getelementptr inbounds nuw (i8, ptr @_ZTV1A, i64 16)`，而经典路径产出的是 `getelementptr inbounds inrange(-16, 8) ({ [3 x ptr] }, ptr @_ZTV1A, i32 0, i32 0, i32 2)`。两者指向同一个地址，测试文件里专门有注释说明它们等价。**为什么会不同，现在你能解释了**：CIR 手里握着的是「index=0, offset=2」这个抽象坐标，它在降级时选择自己算出字节偏移 16；经典路径手里握着的是 IRBuilder 和虚表的 LLVM 结构类型，于是它顺手生成了一个按结构层次走的 GEP。同一个语义，两种表达，因为出发点不同。

## 成员指针：ABI 相关的东西先不落地

C++ 的成员指针是一个典型的「ABI 相关」构造：`int A::*` 在 Itanium ABI 下是一个偏移量，成员函数指针 `void (A::*)()` 是一个 `{ ptr, ptrdiff_t }` 结构，而 MSVC ABI 下的表示完全不同。经典路径在生成 IR 时就必须选定一种表示。

CIR 的做法是先给它们各自一个抽象类型，把 ABI 决策推迟：

- `!cir.data_member<!s32i in !rec_A>` —— 指向数据成员，语义是「`A` 里某个成员的偏移」。
- `!cir.method<!cir.func<...> in !rec_A>` —— 指向成员函数，`CIRTypes.td` 直接注明「这个类型的布局是 ABI 相关的」。

配套操作：`cir.get_runtime_member`（用成员指针取地址）、`cir.get_method`（从成员函数指针解出可调用的函数指针和调整后的 this）、`cir.base_data_member` / `cir.derived_data_member` / `cir.base_method` / `cir.derived_method`（成员指针在继承层次上的上下转换）。

这些抽象类型和操作在 **`cir-cxxabi-lowering`** 这个 pass 里被换成具体 ABI 的表示。于是「C++ ABI 的选择」从「散布在 CodeGen 各处的 `CGCXXABI` 虚函数调用」变成了「一个显式的 pass 边界」：pass 之前是与 ABI 无关的 CIR，pass 之后是绑定了某个 ABI 的 CIR。这是第 25 章说的「隐含契约变显式契约」的又一例。

## 异常：带类型的 token，和一串 `eh.*`

异常是这三样里最复杂的，也是 CIR 设计得最不像 LLVM IR 的地方。

LLVM IR 的异常模型是：`invoke` 指令 + `landingpad` 指令，landingpad 产出一个 `{ ptr, i32 }` 结构，你得自己知道第一个字段是异常对象、第二个是 selector，然后自己和 `llvm.eh.typeid.for` 的结果比较来决定进哪个 catch。**结构是扁平的，值是无类型的**。

CIR 的模型是：`cir.try` 是一个带 region 的操作，try 体和每个 handler 各占一个 region；handler region 接收一个**类型化的** `!cir.eh_token` 参数代表在飞的异常。直接看 `CIROps.td` 里给的例子：

```cir-norun
cir.try {
  cir.call exception @function() : () -> ()
  cir.yield
} catch [type #cir.global_view<@_ZTIPf> : !cir.ptr<!u8i>] (%eh_token : !cir.eh_token) {
  %catch_token, %exn_ptr = cir.begin_catch %eh_token
    : !cir.eh_token -> (!cir.catch_token, !cir.ptr<!cir.float>)
  cir.cleanup.scope {
    ...
    cir.yield
  } cleanup eh {
    cir.end_catch %catch_token : !cir.catch_token
    cir.yield
  }
  cir.yield
} unwind (%eh_token : !cir.eh_token) {
  cir.resume %eh_token : !cir.eh_token
}
```

几个设计点：

- **调用点上标 `exception`**。`cir.call exception @function()` 表示这次调用可能抛——对应 LLVM IR 的 `invoke`，但不需要在这一层就指定 unwind 目标块，因为目标由 region 的嵌套关系决定。另有一个 `cir.try_call` 操作用于已经扁平化之后的形态。
- **`!cir.eh_token` 和 `!cir.catch_token` 是类型**。异常状态不是一个 `{ ptr, i32 }`，而是两个各自有含义的 token 类型，验证器能检查你有没有把它们用错。`cir.begin_catch` 把 `eh_token` 换成 `catch_token` **和一个已经带了正确类型的异常对象指针**（例子里是 `!cir.ptr<!cir.float>`，因为 catch 的是 `float*`）。
- **`cir.end_catch` 必须放在 `cir.cleanup.scope` 的 cleanup region 里**。文档里明确写了这条规则，理由也写了：「这确保离开 catch handler 的**所有路径**都会执行 end_catch」。这一条约束用结构表达，比用「记得在每个出口都加一句」表达要安全得多。
- **`unwind` region** 处理「没有任何 handler 匹配」的情况，里面是 `cir.resume` 继续向调用者传播。

更能说明这个模型表达力的是**动态异常规范**（`void f() throw(int)`）。CIR 不为它新造语法，而是复用 `cir.try`，换一对 handler：

```cir-norun
cir.try {
  cir.call exception @function() : () -> ()
  cir.yield
} filter [#cir.global_view<@_ZTIi> : !cir.ptr<!u8i>]
    (%eh_token : !cir.eh_token) {
  cir.resume %eh_token : !cir.eh_token
} unexpected (%eh_token.1 : !cir.eh_token) {
  cir.eh.unexpected %eh_token.1 : !cir.eh_token
}
```

`filter` 列出允许的类型、并持有「异常被允许」时走的路（继续向调用者 unwind）；`unexpected` 持有「违反规范」时走的路。文档还讲清了两个边界情况：`throw()`（什么都不允许）时 filter region 里放的是 `cir.unreachable`；而为异常规范生成的这个 `cir.try` **包住整个函数体**，源码里写的每个 `try` 语句都成为嵌套在它里面的另一个 `cir.try`。这种「用嵌套关系表达包含关系」的做法，只有在有 region 的表示里才写得出来。

围绕异常的操作是这一章里最长的一串，值得列出来感受一下面积：

| 一组 | 操作 |
|---|---|
| 抛出 | `cir.throw`、`cir.try_throw`、`cir.alloc.exception` |
| 在飞的异常 | `cir.eh.inflight_exception`、`cir.eh.typeid`、`cir.eh.dispatch`、`cir.resume`、`cir.resume.flat` |
| catch 生命周期 | `cir.begin_catch`、`cir.end_catch`、`cir.catch_param`、`cir.init_catch_param`、`cir.construct_catch_param` |
| 清理 | `cir.begin_cleanup`、`cir.end_cleanup`、`cir.cleanup.scope` |
| 终止路径 | `cir.eh.terminate`、`cir.eh.unexpected`、`cir.eh.initiate` |
| SJLJ | `cir.eh.setjmp`、`cir.eh.longjmp` |

函数上还带 personality 信息，在文本里直接可见（来自 `clang/test/CIR/CodeGenCXX/try-catch.cpp`）：

```cir-norun
cir.func @_Z30try_catch_with_empty_catch_allv() personality(@__gxx_personality_v0)
```

这一整套最后由 **`cir-eh-abi-lowering`** 这个 pass 降到目标 ABI 的形态（Itanium 的 `invoke`/`landingpad`，或者别的）。它在 `populateCIRPreLoweringPasses()` 里紧跟着 `cir-flatten-cfg`——**先把普通控制流拍平，再降异常 ABI**，因为异常的降级需要知道扁平之后的块结构。

<div class="keypoint">
<strong>一条贯穿三节的规律</strong>
控制流、类布局、异常，CIR 的处理方式是同一个套式：<strong>先用一个「说得出名字」的高层构造记下前端知道的事实，再用一个专门的 pass 把它降成低层形态</strong>。<code>cir.if</code>/<code>cir.for</code> → <code>cir-flatten-cfg</code>；<code>!cir.data_member</code>/<code>!cir.method</code> → <code>cir-cxxabi-lowering</code>；<code>cir.try</code>/<code>eh.*</code> → <code>cir-eh-abi-lowering</code>。记住这个套式，你在 CIR 里遇到任何陌生操作都能猜出它归哪个 pass 管。
</div>

## 动手：两条退出路径，为什么清理代码要写两遍

`cir.cleanup.scope` 有两个 region：body 和 cleanup；`cir.try` 有一个 `cleanup` 属性，文档说它表示「即使异常没被捕获，从 try region 异常退出时也有清理要做」。为什么需要这些？下面这个能在浏览器里跑的小程序把原因摆出来：同一段带 RAII 对象的嵌套代码，正常退出和异常 unwind 走的是**两条不同的清理路径**，析构的对象集合和顺序都不一样。点 **▶ 运行**。

```python
# 两条退出路径：正常返回 vs 异常 unwind。同一段嵌套作用域，析构顺序各是什么

class CppThrow(Exception):
    pass

# 一段带 try / 嵌套作用域 / 局部对象的程序。("var", 名) 表示一个有析构函数的局部对象
PROGRAM = [
    ("var", "a"),
    ("try",
        [("var", "b"),
         ("scope", [("var", "c"),
                    ("maybe_throw", "std::bad_alloc"),
                    ("var", "d")]),          # 抛出后这一行不会执行
         ("var", "e")],
        [("var", "h")]),                     # catch 体里的局部对象
    ("var", "f"),
]

events = []

def emit(kind, name, note=""):
    events.append((kind, name, note))

def run(body, throwing):
    live = []                                # 本作用域里已构造、还活着的对象
    try:
        for node in body:
            kind = node[0]
            if kind == "var":
                live.append(node[1])
                emit("ctor", node[1])
            elif kind == "scope":            # cir.scope { ... }
                run(node[1], throwing)
            elif kind == "maybe_throw":      # cir.throw
                if throwing:
                    emit("throw", node[1])
                    raise CppThrow(node[1])
            elif kind == "try":              # cir.try { ... } catch { ... }
                try:
                    run(node[1], throwing)
                except CppThrow as e:
                    emit("catch", str(e))
                    run(node[2], throwing)
    except CppThrow:
        for name in reversed(live):          # unwind 路径的清理
            emit("dtor", name, "unwind")
        raise
    else:
        for name in reversed(live):          # 正常路径的清理
            emit("dtor", name, "normal")

def show(title, throwing):
    global events
    events = []
    try:
        run(PROGRAM, throwing)
    except CppThrow:
        emit("escape", "", "")
    print("=== %s ===" % title)
    for kind, name, note in events:
        if kind == "ctor":
            print("  ctor %s" % name)
        elif kind == "dtor":
            path = "正常退出" if note == "normal" else "unwind"
            print("  dtor %s          [%s]" % (name, path))
        elif kind == "throw":
            print("  throw %s   <-- 从这里开始 unwind" % name)
        elif kind == "catch":
            print("  catch %s" % name)
    ctors = [e for e in events if e[0] == "ctor"]
    dtors = [e for e in events if e[0] == "dtor"]
    unwind = [e for e in dtors if e[2] == "unwind"]
    print("  小计：%d 次构造，%d 次析构（其中 %d 次走 unwind 路径）"
          % (len(ctors), len(dtors), len(unwind)))
    print()

show("路径一：什么都没抛", False)
show("路径二：在最内层作用域抛出", True)

print("同一份嵌套结构，两条退出路径。每个作用域都要准备两套清理代码——")
print("这就是 cir.try 有一个 `cleanup` 属性、cir.cleanup.scope 有一个独立的")
print("`cleanup eh` region 的原因：正常路径和 unwind 路径必须分别落地。")
```

运行结果：

```
=== 路径一：什么都没抛 ===
  ctor a
  ctor b
  ctor c
  ctor d
  dtor d          [正常退出]
  dtor c          [正常退出]
  ctor e
  dtor e          [正常退出]
  dtor b          [正常退出]
  ctor f
  dtor f          [正常退出]
  dtor a          [正常退出]
  小计：6 次构造，6 次析构（其中 0 次走 unwind 路径）

=== 路径二：在最内层作用域抛出 ===
  ctor a
  ctor b
  ctor c
  throw std::bad_alloc   <-- 从这里开始 unwind
  dtor c          [unwind]
  dtor b          [unwind]
  catch std::bad_alloc
  ctor h
  dtor h          [正常退出]
  ctor f
  dtor f          [正常退出]
```

对着两段输出比：`d` 在异常路径下**根本没被构造**，`e` 也没有；`c` 和 `b` 的析构从「正常退出」变成了「unwind」，顺序是**由内到外**，这正是嵌套作用域结构直接给出的顺序。而 `a` 和 `f` 两条路径都是正常退出——因为 `try` 把异常挡在了里面。

请动手改两处：一是把 `("maybe_throw", ...)` 挪到 `("var", "b")` 前面，看 `b` 会不会被析构（不会——它还没构造）；二是把整个 `try` 节点换成一个普通 `("scope", ...)`（把 catch 体删掉），异常就会一路逃到最外层，`a` 和 `f` 的清理路径也会变。你会体会到：**「哪些对象要清理」完全由「抛出点在嵌套结构里的位置」决定**。在结构化的 CIR 里这个信息是现成的；扁平化之后，它变成了「哪些块能到达哪个 landing pad」这样的图问题——这也是 `cir-flatten-cfg` 必须和清理机制配合、而 `cir-eh-abi-lowering` 必须排在它之后的原因。

## 小结与下一步

- MLIR 的 **Operation → Region → Block → Operation** 可无限嵌套，这是 CIR 能保留结构的本钱。`cir.if` / `cir.scope` / `cir.switch` / `cir.while` / `cir.do` / `cir.for` / `cir.ternary` / `cir.try` / `cir.cleanup.scope` 都是带 region 的操作，region 用 `cir.yield` / `cir.condition` 收尾。
- **`cir-flatten-cfg`** 是结构消失的那一刻：`cir.if` → `cir.brcond` + 基本块。因为 `.cir` 能手写，这个 pass 的测试是一个 `cir-opt %s -cir-flatten-cfg` 加 FileCheck，完全不碰 C++。
- **`!cir.struct`** 有具名完整 / 具名不完整 / 匿名三种形态，成员带种类标记（`data` / `pad` / `empty` / `bitfield`），`class` 关键字被保留，不完整类型是一等形态——这些在 LLVM IR 里全都没有。
- **虚表**由四个具名操作表达，`cir.vtable.address_point` 用的是 Itanium ABI 的 `<index, offset>` 二元坐标而不是字节偏移。这解释了第 25 章那个 GEP 差异的来源。
- **异常**用 `cir.try` + 类型化 token（`!cir.eh_token` / `!cir.catch_token`）+ 一大串 `cir.eh.*`，动态异常规范复用同一个操作、换一对 `filter`/`unexpected` handler。约束（如「`cir.end_catch` 必须在 cleanup region 里」）用结构表达而不是靠人记。
- 贯穿的套式：**高层构造记录事实 → 专门的 pass 降级**。12 个 pass 就是 12 道这样的边界。

下一章走到这一部分的落点：CUDA/HIP。你会看到同一个套式被用在一个全新的地方——用 CIR 属性记下「这个全局变量要注册到 CUDA 运行时」「这个 kernel 的名字是什么」，再由一个 pass 展开成 `__cudaRegisterVar` / `cudaLaunchKernel` 这些运行时调用；以及一个只有在这层才可能出现的设计：主机端和设备端的表示**在同一层里共存**。

---

**这一章的要点**

- MLIR 的 **Region** 让操作可以嵌套，CIR 借此把控制流表达成结构化操作而非基本块：`cir.if`、`cir.scope`、`cir.switch`/`cir.case`、`cir.while`/`cir.do`、`cir.for`（cond/body/step 三个 region）、`cir.ternary`、`cir.try`、`cir.cleanup.scope`。终结子是 `cir.yield` / `cir.condition` / `cir.break` / `cir.continue`。
- **`cir-flatten-cfg`** 把它们拍成 `cir.brcond` + 基本块；`cir.switch` → `cir.switch.flat`；`goto` 由 `cir-goto-solver` 单独处理。扁平化后出现的 `^bb3: // no predecessors` 提醒你「可达性」的含义变了。
- **`!cir.struct`**：三种形态（完整/不完整/匿名）+ 成员种类（`data`/`pad`/`empty`/`bitfield`）+ 保留 `class` 关键字。成员访问用 `cir.get_member` / `cir.get_bitfield`，基类调整用 `cir.base_class_addr`。
- **虚表四操作**：`cir.vtable.address_point`（`<index, offset>` Itanium 坐标，返回 `!cir.vptr`）、`get_vptr`、`get_virtual_fn_addr`、`get_type_info`。专用类型 `!cir.vptr` 换来基于类型的检查。
- **成员指针** `!cir.data_member` / `!cir.method` 把 ABI 决策推迟到 `cir-cxxabi-lowering`。
