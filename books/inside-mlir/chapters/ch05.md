# 第 5 章 Trait 与 Interface：MLIR 复用的真正机关

## 这一章想让你带走什么

<div class="goal-box">
<p>第 4 章末尾那个问题，是理解 MLIR 的分水岭：<strong>既然 MLIR 核心不认识任何具体 op，<code>--cse</code>、<code>--canonicalize</code>、LICM 这些通用 pass 凭什么能正确地变换一个它从没见过的 <code>pix.convolve</code>？</strong></p>
<p>答案是本章的全部内容：它们<strong>不问"你是谁"，只问"你声明了什么"</strong>。声明的手段有两种——<strong>trait</strong>（编译期的静态标签，回答是/不是）和 <strong>interface</strong>（运行时的虚函数表，回答具体是多少、请你算一下）。你会亲手跑一个模拟器，看同一段 IR 只改 op 的声明，通用 pass 的行为差多少；也会用真 <code>mlir-opt</code> 验证一次：两条相同的 <code>memref.load</code> 中间插一条 <code>store</code>，<code>--cse</code> 就不敢合并了——而 CSE 从头到尾不知道 <code>memref.load</code> 是什么意思。</p>
<p>这一章也是第二部分的"需求说明书"：给 pix 的每个 op 挑对 trait、实现对接口，就是在给它解锁整条优化管线。</p>
</div>

## 问题：三种可能的答案，MLIR 选了第三种

假设你是 CSE pass 的作者。你要判断"这两个 op 是不是同一次计算，能不能合并"。摆在面前有三条路：

1. **写死一张表**：枚举所有 op，逐个规定。——那 MLIR 的可扩展性就没了，你的 `pix.convolve` 永远得不到 CSE。
2. **让每个 pass 认识每个 op**：N 个 pass × M 种 op。——这就是第 1 章那个 N×M 灾难的翻版。
3. **让 op 自己回答问题**：pass 只问几个抽象问题（"你有副作用吗"、"你的操作数可交换吗"、"你的循环边界是什么"），op 负责回答。

MLIR 选第三种。于是核心问题变成：**怎么让 op"能被问"？** 两种机制，分工明确。

## Trait：编译期的静态标签

**trait 回答的是"是/不是"这类不带参数的问题。** 它在 C++ 里是模板 mixin，附加在 op 类上；在 ODS 里就是 op 定义里那个方括号列表（第 8 章你会亲手写）：

```tablegen
def Pix_AddOp : Pix_Op<"add", [Pure, Commutative, SameOperandsAndResultType]> {
  // ...
}
```

trait 做两件事：

- **注入方法**：带 `Commutative` 的 op 自动获得相关能力，pass 可以用 `op->hasTrait<OpTrait::IsCommutative>()` 查询。
- **注入验证**：`SameOperandsAndResultType` 会自动生成"所有操作数和结果类型必须相同"的检查，你不用手写 verifier（第 10 章细讲验证的执行顺序）。

常用的一批，先认脸（ODS 名字 → C++ 名字）：

| ODS 里写 | C++ 里是 | 含义 |
| --- | --- | --- |
| `Pure` | 见下节（是个组合） | 无副作用、可自由移动/删除/合并 |
| `Commutative` | `OpTrait::IsCommutative` | 操作数可交换（`a+b == b+a`） |
| `Idempotent` | `OpTrait::IsIdempotent` | `f(f(x)) == f(x)` |
| `Involution` | `OpTrait::IsInvolution` | `f(f(x)) == x`（取反、转置） |
| `Terminator` | `OpTrait::IsTerminator` | 必须是 block 的最后一个 op |
| `IsolatedFromAbove` | `OpTrait::IsIsolatedFromAbove` | region 内不得引用外部值（第 2 章讲过） |
| `ConstantLike` | `OpTrait::ConstantLike` | 我是个常量 op（折叠时要用） |
| `SameOperandsAndResultType` | 同名 | 类型一致性，自动验证 |

源码位置值得记住：通用 trait 在 `mlir/include/mlir/IR/OpBase.td`（ODS 侧）与 `mlir/include/mlir/IR/OpDefinition.h`（C++ 侧）；跟类型推断有关的（比如 `SameOperandsAndResultType`）在 `mlir/include/mlir/Interfaces/InferTypeOpInterface.td`。

<div class="warn">
<strong>trait 的天花板</strong>
<p>trait 只能表达"有/没有这个性质"。它没法回答"你的循环下界是哪个值"、"你读了哪块内存"、"给这些输入类型，你的结果类型是什么"。这类<strong>带返回值的问题</strong>必须换一种机制——interface。</p>
</div>

## Interface：运行时的虚函数表

**interface 是一组方法签名，op（或类型、属性、方言）可以实现它。** pass 拿到一个 op，用 `dyn_cast` 问："你实现了这个接口吗？"实现了就能调用它的方法。

```cpp-norun
// 典型的 pass 代码长这样：不判断 op 是什么，只问它实现了什么
if (auto loopOp = dyn_cast<LoopLikeOpInterface>(op)) {
  // 现在可以调用接口方法，而完全不必知道这是 scf.for、affine.for 还是你的 pix.loop
  for (Value iv : loopOp.getLoopInductionVars().value_or(SmallVector<Value>{}))
    /* ... */;
}
```

这就是 MLIR 复用的**真正机关**：LICM 一个 pass，能提升 `scf.for`、`affine.for`、以及你自己写的循环 op 里的不变量——因为它只依赖 `LoopLikeOpInterface`。

几个你早晚会用到的接口（都在 `mlir/include/mlir/Interfaces/` 下，一个 `.td` 一个文件）：

| 接口 | 它让 pass 能问什么 | 文件 |
| --- | --- | --- |
| `MemoryEffectOpInterface` | 你读了/写了/分配了哪些资源？ | `SideEffectInterfaces.td` |
| `LoopLikeOpInterface` | 你的归纳变量、上下界、步长；能把东西移出循环吗？ | `LoopLikeInterface.td` |
| `InferTypeOpInterface` | 给定操作数，你的结果类型是什么？ | `InferTypeOpInterface.td` |
| `RegionBranchOpInterface` | 控制流在你的 region 之间怎么走？ | `ControlFlowInterfaces.td` |
| `DestinationStyleOpInterface` | 哪些操作数其实是"输出目的地"？ | `DestinationStyleOpInterface.td` |
| `TilingInterface` | 你的迭代空间是什么？能否切分？ | `TilingInterface.td` |
| `CallOpInterface` / `CallableOpInterface` | 你在调用谁？你是可调用的吗？ | `CallInterfaces.td` |
| `ViewLikeOpInterface` | 你是不是只是某块内存的一个视图？ | `ViewLikeInterface.td` |

第 2 章那个"空 else"的报错 `'scf.if' op along control flow edge ... region successor needs 1 inputs`，就是 `RegionBranchOpInterface` 在干活——它让通用机制能检查"region 之间传值的个数与类型对不对"，而不必认识 `scf.if`。

<div class="note">
<strong>四种 interface</strong>
<p>除了 op interface，还有 <strong>type interface</strong>（比如"我是个 shaped 类型，你可以问我形状"）、<strong>attribute interface</strong>、以及 <strong>dialect interface</strong>（整个方言实现的，比如"我这个方言的 op 该怎么内联"、"该怎么下降到 LLVM"）。第 16 章讲 dialect conversion 时会遇到 dialect interface 的实际用法。</p>
</div>

## `Pure` 到底是什么

`Pure` 是全书出现频率最高的 trait，但它其实是个**组合**。源码里只有一行（`mlir/include/mlir/Interfaces/SideEffectInterfaces.td`）：

```tablegen
def Pure : TraitList<[AlwaysSpeculatable, NoMemoryEffect]>;
```

拆开看：

- **`NoMemoryEffect`** = `MemoryEffects<[]>`：通过 `MemoryEffectOpInterface` 声明"我不读不写任何内存"。
- **`AlwaysSpeculatable`**：声明"我可以被无条件地提前执行"（不会崩、不会除零、不依赖执行到这里的前提）。它背后是 `ConditionallySpeculatable` 接口。

两者缺一不可，因为它们回答的是两个不同的问题：

- 「能不能**删掉**/**合并**？」——看有没有内存副作用。
- 「能不能**挪到别处**（比如提到循环外、提到分支前）？」——看能不能推测执行。一个整数除法不读不写内存，但它**可能除零**，所以不能随便提到分支之前。

这就是为什么 `arith.divsi` 不是 `Pure`（它可能除零），而 `arith.addi` 是。

配套的工具函数在 `mlir/include/mlir/Interfaces/SideEffectInterfaces.h`，名字直白，值得记住：`isPure(op)`、`isMemoryEffectFree(op)`、以及决定 DCE 的 **`wouldOpBeTriviallyDead(op)`**。

## 实测：CSE 从不认识 `memref.load`，但它知道该不该合并

两条一模一样的 `memref.load`，中间什么都没有：

```mlir
// RUN: mlir-opt %s --cse
func.func @two_loads(%m: memref<4xf32>, %i: index) -> f32 {
  %a = memref.load %m[%i] : memref<4xf32>
  %b = memref.load %m[%i] : memref<4xf32>
  %s = arith.addf %a, %b : f32
  return %s : f32
}
```

运行结果——合并了，第二次读没了：

```
module {
  func.func @two_loads(%arg0: memref<4xf32>, %arg1: index) -> f32 {
    %0 = memref.load %arg0[%arg1] : memref<4xf32>
    %1 = arith.addf %0, %0 : f32
    return %1 : f32
  }
}
```

现在中间插一条写：

```mlir
// RUN: mlir-opt %s --cse
func.func @two_loads_with_store(%m: memref<4xf32>, %i: index, %v: f32) -> f32 {
  %a = memref.load %m[%i] : memref<4xf32>
  memref.store %v, %m[%i] : memref<4xf32>
  %b = memref.load %m[%i] : memref<4xf32>
  %s = arith.addf %a, %b : f32
  return %s : f32
}
```

运行结果——不敢合并了，两次读都保留：

```
module {
  func.func @two_loads_with_store(%arg0: memref<4xf32>, %arg1: index, %arg2: f32) -> f32 {
    %0 = memref.load %arg0[%arg1] : memref<4xf32>
    memref.store %arg2, %arg0[%arg1] : memref<4xf32>
    %1 = memref.load %arg0[%arg1] : memref<4xf32>
    %2 = arith.addf %0, %1 : f32
    return %2 : f32
  }
}
```

<div class="keypoint">
<strong>关键在于 CSE 的代码里没有一个字提到 <code>memref</code>。</strong>
<p>它只做了三件事：问每个 op「你有没有写内存」（<code>MemoryEffectOpInterface</code>），问「你们两个是不是同一次计算」（op 名 + 操作数 + 属性，全是通用信息），然后调 <code>replaceAllUsesWith</code>（第 2 章你亲手实现过）。<strong>把 <code>memref.load</code> 换成你自己的 <code>pix.load_tile</code>，只要声明同样的副作用，你免费得到同样的优化。</strong></p>
</div>

再看一个 DCE 的实测。三个 op，都没人用它们的结果：

```mlir
// RUN: mlir-opt %s --canonicalize
func.func @dead(%m: memref<4xf32>, %i: index, %x: f32) {
  %unused_add = arith.addf %x, %x : f32
  %unused_load = memref.load %m[%i] : memref<4xf32>
  memref.store %x, %m[%i] : memref<4xf32>
  return
}
```

运行结果：

```
module {
  func.func @dead(%arg0: memref<4xf32>, %arg1: index, %arg2: f32) {
    memref.store %arg2, %arg0[%arg1] : memref<4xf32>
    return
  }
}
```

**没人用的 `arith.addf`（`Pure`）被删了，没人用的 `memref.load`（只读）也被删了，而 `memref.store`（写）留下了。** 判据正是 `wouldOpBeTriviallyDead`：没有用户 + 不写内存。注意"只读"也是可删的——读一块内存却不用结果，确实没有意义。

## 亲手跑一遍这套问答

下面的模拟器把上面全部串起来：定义一个 pass **从没见过**的 `pix.convolve`，只改它的声明，看通用 DCE / CSE 的行为怎么变。

```python
# 通用 pass 凭什么敢动一个它从没见过的 op？
# 答案：它不问"你是谁"，只问"你声明了什么"。下面把这套问答做出来。

class Op:
    def __init__(self, name, ins, out=None, traits=(), effects=()):
        self.name, self.ins, self.out = name, ins, out
        self.traits = set(traits)                 # 编译期静态声明，只能回答"是/不是"
        self.effects = list(effects)              # 接口回答的"具体内容"：[('read'|'write', 资源)]

    # —— pass 会问的几个问题，全部只基于声明，不基于 op 的身份 ——
    def is_pure(self):
        return "Pure" in self.traits

    def writes(self):
        return [r for kind, r in self.effects if kind == "write"] or \
               (["<任意内存>"] if not self.is_pure() and not self.effects else [])

    def reads(self):
        return [r for kind, r in self.effects if kind == "read"]

    def key(self):                                 # CSE 用它判断"是不是同一次计算"
        return (self.name, tuple(self.ins))

    def __repr__(self):
        lhs = f"{self.out} = " if self.out else ""
        return f"{lhs}{self.name}({', '.join(self.ins)})"


def dce(ops, used):
    """删掉没人用、且不写内存的 op。对应 wouldOpBeTriviallyDead()。"""
    kept, removed = [], []
    for op in ops:
        has_user = op.out in used
        if not has_user and not op.writes():
            removed.append(op)
        else:
            kept.append(op)
    return kept, removed


def cse(ops):
    """合并重复计算；遇到写内存的 op 就清空缓存（它可能让之前读到的值过期）。"""
    seen, out, merged = {}, [], []
    for op in ops:
        if op.writes():
            seen.clear()                           # 有写入 → 之前缓存的读全部作废
            out.append(op)
            continue
        k = op.key()
        if k in seen:
            merged.append((op, seen[k]))
            continue
        seen[k] = op
        out.append(op)
    return out, merged


def report(title, ops, used):
    print(f"=== {title} ===")
    for op in ops:
        t = "、".join(sorted(op.traits)) or "（没有声明任何 trait）"
        e = "、".join(f"{k} {r}" for k, r in op.effects) or "（没有声明副作用）"
        print(f"  {op!r:<38} trait: {t:<26} 副作用: {e}")
    after_cse, merged = cse(ops)
    for dup, orig in merged:
        print(f"  CSE：{dup!r} 与 {orig!r} 是同一次计算 → 合并")
    if not merged:
        print("  CSE：没有可合并的")
    after_dce, removed = dce(after_cse, used)
    print("  DCE：" + ("删掉 " + "、".join(repr(o) for o in removed) if removed else "没有可删的"))
    print(f"  最终剩下 {len(after_dce)} 个 op\n")


# 场景：一个 pass 完全不认识的自定义 op —— pix.convolve
used = {"%c1"}     # 只有第一个卷积结果被用到（被 return 用了）

print("同一段 IR，只改 pix.convolve 的声明，看通用 pass 的行为差多少\n")

# 声明了 Pure：告诉框架"我不碰内存、结果只由操作数决定"
report("pix.convolve 声明了 Pure", [
    Op("pix.convolve", ["%img", "%k"], "%c1", traits=["Pure"]),
    Op("pix.convolve", ["%img", "%k"], "%c2", traits=["Pure"]),   # 重复计算
    Op("pix.blur",     ["%img"],       "%b1", traits=["Pure"]),   # 没人用
], used)

# 什么都不声明：框架只能假设最坏情况
report("pix.convolve 什么都没声明", [
    Op("pix.convolve", ["%img", "%k"], "%c1"),
    Op("pix.convolve", ["%img", "%k"], "%c2"),
    Op("pix.blur",     ["%img"],       "%b1"),
], used)

# 精确声明"只读某块内存"：两次读之间没有写 → 可以合并
report("两次 read，中间没有 write", [
    Op("pix.load_tile", ["%buf"], "%t1", effects=[("read", "%buf")]),
    Op("pix.load_tile", ["%buf"], "%t2", effects=[("read", "%buf")]),
], {"%t1", "%t2"})

# 同样两次读，中间插一次写 → 第二次必须重新读
report("两次 read，中间插了一次 write", [
    Op("pix.load_tile", ["%buf"], "%t1", effects=[("read", "%buf")]),
    Op("pix.store_tile", ["%buf", "%t1"], None, effects=[("write", "%buf")]),
    Op("pix.load_tile", ["%buf"], "%t2", effects=[("read", "%buf")]),
], {"%t1", "%t2"})
print("最后两组正是真实 mlir-opt 的行为：memref.load 之间插一条 memref.store，--cse 就不再合并。")
print()

print("结论：pass 的能力不是'认识多少 op'，而是'op 声明了多少信息'。")
print("这就是为什么第二部分给 pix 的每个 op 挑 trait、实现接口，是在给它'解锁'整条优化管线。")
```

**改一改：**

1. 把 `two_loads_with_store.mlir` 里的 `store` 改成写**另一个** memref（给函数加一个参数 `%m2`，写 `%m2`）。`--cse` 现在敢合并那两次 `load` 吗？想一想：要敢合并，编译器必须知道 `%m` 和 `%m2` 不重叠——这就是别名分析的地盘（第 19 章）。
2. 把两次 `memref.load` 的下标改成不同的 `%i` 和 `%j`。CSE 还合并吗？为什么？（提示：CSE 的"同一次计算"包含操作数相同）
3. `arith.divsi %a, %b` 放在一个 `scf.if` 里面，`b` 可能为 0。试试 LICM 相关的 pass（`--loop-invariant-code-motion`）能不能把它提出去。结合本节讲的 `AlwaysSpeculatable`，解释你看到的结果。
4. 想象给 `pix.convolve` 加 `Commutative`。这个声明**对不对**？（卷积的两个输入是图像和卷积核，交换它们语义变吗？）这个问题说明：**trait 是承诺，声明错了框架会按错的来优化**——第 10 章会讲怎么用测试守住这些承诺。

---

**这一章的要点**

- 通用 pass 能变换未知 op，靠的不是认识它，而是**问它声明了什么**。这是 MLIR 全部复用能力的来源。
- **trait** 是编译期静态标签，回答"是/不是"，还能自动注入验证（`SameOperandsAndResultType`）。**interface** 是运行时虚表，回答"具体是多少/请你算一下"（`LoopLikeOpInterface` 的循环边界、`InferTypeOpInterface` 的结果类型）。
- `Pure` = `AlwaysSpeculatable` + `NoMemoryEffect`。前者管"能不能挪"，后者管"能不能删/合"。`arith.divsi` 不是 `Pure`，因为它可能除零。
- 决定 DCE 的函数就叫 `wouldOpBeTriviallyDead`（`SideEffectInterfaces.h`）：**没有用户 + 不写内存**。只读且结果没人用的 op 也会被删。
- 实测确认：两条相同 `memref.load` 中间插一条 `store`，`--cse` 立刻放弃合并——而 CSE 的代码里没有一个字提到 `memref`。
- 接口住在 `mlir/include/mlir/Interfaces/`，一个 `.td` 一个文件。想知道"某个通用变换要求我实现什么"，去那里找接口，比读 pass 源码快。
- 除 op interface 外还有 type / attribute / dialect interface。
- **对第二部分的意义**：给 pix 的 op 挑 trait、实现接口，等于给它解锁整条通用优化管线。挑错了不是没效果，而是**按错的语义优化**——这是承诺，不是标签。

下一章做第一部分的收尾：**方言全景**。把 `builtin`、`func`、`arith`、`scf`、`cf`、`memref`、`tensor`、`vector`、`linalg`、`gpu`、`spirv`、`llvm`、`transform` 这些内建方言摆成一座塔，看清每一层的抽象高度和它们之间的典型下降边——这张图就是第四部分那条下降路线的地图。
