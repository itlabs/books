## 先把 pass 的骨架搭出来

pix 到现在还没有任何 pass 基础设施。新增四个文件，结构照上游方言的惯例：

```
include/Pix/Transforms/Passes.td          ← 声明 pass（ODS）
include/Pix/Transforms/Passes.h           ← 两个 GEN_PASS_* 宏
include/Pix/Transforms/CostAnalysis.h     ← 我们的第一个分析
lib/Pix/Transforms/CostPasses.cpp         ← 三个 pass 的实现
```

ODS 那边异常简单，一个 pass 就是一行 `Pass<命令行名字, 作用在哪种 op 上>`：

```tablegen
def PixCostReport : Pass<"pix-cost-report", "::mlir::func::FuncOp"> {
  let summary = "统计本函数的 pix 计算量，写成属性";
  let description = [{ … }];
}
```

第二个参数就是这一章的第一个要点：**它决定了框架会把什么交给你**。写 `::mlir::func::FuncOp` 就是函数级 pass，生成的基类是 `OperationPass<func::FuncOp>`，`getOperation()` 的返回类型已经收窄成 `func::FuncOp`——不用 cast，也不可能拿到别的东西。写 `"::mlir::ModuleOp"` 就是模块级；两个参数都不给（`Pass<"name">`）则是"任意 op"。

`Passes.h` 里那两个宏和第 7 章的 `GET_OP_CLASSES` 是同一套把戏：

```cpp-norun
#define GEN_PASS_DECL
#include "Pix/Transforms/Passes.h.inc"        // createXxx() 的声明

#define GEN_PASS_REGISTRATION
#include "Pix/Transforms/Passes.h.inc"        // registerPixPasses()
```

`registerPixPasses()` 这个名字来自 CMake 里 `-gen-pass-decls -name Pix` 的那个 `-name`。在 `pix-opt` 里调一次就够了，以后 `Passes.td` 加了新 pass 会自动包含进来，**不用逐个登记**：

```cpp-norun
mlir::registerAllPasses();      // 内建的
mlir::pix::registerPixPasses(); // 我们的
```

实现文件里，每个 pass 用一个 `GEN_PASS_DEF_<全大写名字>` 宏切出自己的基类：

```cpp-norun
namespace mlir {
namespace pix {
#define GEN_PASS_DEF_PIXCOSTREPORT
#include "Pix/Transforms/Passes.h.inc"

namespace {
struct PixCostReportPass : impl::PixCostReportBase<PixCostReportPass> {
  void runOnOperation() override { /* 你只写这个 */ }
};
} // namespace
} // namespace pix
} // namespace mlir
```

生成的 `impl::XxxBase<DerivedT>` 是个 CRTP 模板，替你实现了 `getArgument()`、`getDescription()`、`getName()`、`clonePass()` 这些样板，**还以 friend 的形式把 `createXxx()` 也定义好了**。

## 嵌套：pass manager 的层级就是 op 树的层级

这是 MLIR 的 Pass 框架和 LLVM 最不一样的地方。LLVM 里 pass 分 `ModulePass` / `FunctionPass` / `LoopPass` 这几种固定层级；MLIR 里**层级是由你的 op 树决定的**，有多少层嵌套就能有多少层 pass manager。

命令行上那串括号就是层级：

```bash
pix-opt input.mlir --pass-pipeline='builtin.module(func.func(pix-cost-report))'
```

读法是从外到内：顶层 pass manager 锚在 `builtin.module` 上，里面嵌一个锚在 `func.func` 上的，`pix-cost-report` 装在后者里。

不确定自己写对了没有，让它自己说：

```bash
pix-opt p13.mlir --pix-cost-report --canonicalize --dump-pass-pipeline
```

运行结果：

```
Pass Manager with 2 passes:
builtin.module(
  func.func(
    pix-cost-report
  ),
  canonicalize{cse-between-iterations=false    max-iterations=10 max-num-rewrites=-1 region-simplify=normal test-convergence=false top-down=true}
)
```

两件事一眼看出来。**一**：我在命令行上只写了 `--pix-cost-report`，框架**自动补上了 `builtin.module(func.func(...))` 这两层嵌套**——因为它从 pass 的声明里知道这是个函数级 pass。**二**：`canonicalize` 被展开成了带全部选项的形式，其中 `max-num-rewrites=-1` 正是第 11 章那个坑的真身——我们当时从源码读到它默认是 `kNoLimit`，这里它作为 `-1` 直接摆在眼前。

## 分析：不用继承、不用注册，但要管好失效

MLIR 的"分析"轻得出人意料。**没有基类，不用注册**，唯一的约定是：**有一个接受 `Operation *` 的构造函数**。

```cpp-norun
class PixCostAnalysis {
public:
  /// 这个构造函数就是全部约定。op 是分析的**作用范围**——
  /// 函数级 pass 传进来的是那个 func.func，所以统计天然只覆盖本函数。
  explicit PixCostAnalysis(Operation *op) {
    op->walk([&](Operation *nested) {
      if (nested->getDialect() != op->getContext()->getLoadedDialect("pix"))
        return;
      ++numOps;
      for (Type ty : nested->getResultTypes())
        if (auto shaped = dyn_cast<ShapedType>(ty))
          if (shaped.hasStaticShape())
            elements += shaped.getNumElements();
    });
  }
  int64_t getNumOps() const { return numOps; }
  int64_t getElements() const { return elements; }
private:
  int64_t numOps = 0;
  int64_t elements = 0;
};
```

`AnalysisManager` 拿**类型本身**（`TypeID`）当键，第一次 `getAnalysis<T>()` 时构造一份并缓存。用起来就一行：

```cpp-norun
struct PixCostReportPass : impl::PixCostReportBase<PixCostReportPass> {
  void runOnOperation() override {
    func::FuncOp fn = getOperation();          // 类型已收窄，不用 cast
    const PixCostAnalysis &cost = getAnalysis<PixCostAnalysis>();

    OpBuilder b(fn);
    fn->setAttr("pix.num_ops", b.getI64IntegerAttr(cost.getNumOps()));
    fn->setAttr("pix.elements", b.getI64IntegerAttr(cost.getElements()));

    markAnalysesPreserved<PixCostAnalysis>();  // ← 这一章的重点
  }
};
```

先看它算得对不对：

```mlir-lower
// RUN: pix-opt %s --pix-cost-report
func.func @two_ops(%a: tensor<4x4xf32>, %b: tensor<4x4xf32>) -> tensor<4x4xf32> {
  %s = pix.add %a, %b : tensor<4x4xf32>
  %t = pix.mul %s, %b : tensor<4x4xf32>
  return %t : tensor<4x4xf32>
}
func.func @no_pix(%a: tensor<8x8xf32>) -> tensor<8x8xf32> {
  return %a : tensor<8x8xf32>
}
```

运行结果（只看函数头那两行）：

```
  func.func @two_ops(%arg0: tensor<4x4xf32>, %arg1: tensor<4x4xf32>) -> tensor<4x4xf32> attributes {pix.elements = 32 : i64, pix.num_ops = 2 : i64} {
  func.func @no_pix(%arg0: tensor<8x8xf32>) -> tensor<8x8xf32> attributes {pix.elements = 0 : i64, pix.num_ops = 0 : i64} {
```

2 个 pix op、两个 4×4 结果共 32 个元素。第二个函数是 0——**分析的作用域是本函数**，不会把上面那个的 2 个 op 算进来。这就是图 13-1 下半部分的意思。

### 把"缓存命中"变成一个可以看见的布尔值

分析缓存平时完全不可观察，导致"我这个 pass 到底有没有让分析白算一遍"几乎无法验证。解决办法很土：再写一个 pass，用 `getCachedAnalysis`（它**不会**在未命中时代劳计算，只返回一个空的 optional），把结果写成属性。

```cpp-norun
struct PixCostRecheckPass : impl::PixCostRecheckBase<PixCostRecheckPass> {
  void runOnOperation() override {
    func::FuncOp fn = getOperation();
    auto cached = getCachedAnalysis<PixCostAnalysis>();   // 不命中就是 nullopt
    OpBuilder b(fn);
    fn->setAttr("pix.cost_cached", b.getBoolAttr(cached.has_value()));
    markAnalysesPreserved<PixCostAnalysis>();
  }
};
```

现在可以做实验了。三条命令，三个结果：

```bash
# ① 只跑 recheck：分析从没算过
pix-opt p13.mlir --pix-cost-recheck | grep -o "pix.cost_cached = [a-z]*"
pix.cost_cached = false
pix.cost_cached = false

# ② report 之后紧跟 recheck
pix-opt p13.mlir --pix-cost-report --pix-cost-recheck | grep -o "pix.cost_cached = [a-z]*"
pix.cost_cached = true
pix.cost_cached = true

# ③ 中间插一个 canonicalize
pix-opt p13.mlir --pix-cost-report --canonicalize --pix-cost-recheck | grep -o "pix.cost_cached = [a-z]*"
pix.cost_cached = false
pix.cost_cached = false
```

② 之所以是 `true`，全靠 `pix-cost-report` 里那一行 `markAnalysesPreserved<PixCostAnalysis>()`。**把它注释掉重编，② 会变成 `false`**——我试过，两个函数都变。

为什么需要这一行？因为**框架默认假设你破坏了一切**。这个默认是对的：它没法知道你改了什么。而我们只挂了两个可丢弃属性，op 的构成一点没变，那份统计仍然成立——**这件事只有我们自己知道，所以必须说出来**。

③ 里 `canonicalize` 改了 IR、也没有声明保留我们这份分析，于是缓存被作废。这也是对的：函数真的被改了，元素数可能已经不一样了。

<div class="keypoint">
<strong>两个"声明保留"的 API，用途完全不同</strong>
<p><code>markAnalysesPreserved&lt;T&gt;()</code>——"我改了东西，但 <strong>T 这份分析</strong>不受影响"。用在"改动与某个分析无关"的场合，比如我们挂属性。</p>
<p><code>markAllAnalysesPreserved()</code>——"我<strong>什么都没改</strong>"。任何可能空跑的 pass 都该在空跑的分支上调它。<strong>漏掉它不会有任何报错</strong>，只是把后面所有分析的缓存白白冲掉；这是个纯性能问题，而性能问题不会自己报警。</p>
</div>

### 把这套机制自己跑一遍

上面那些道理，不如自己驱动一遍看得清。下面 50 行是 `AnalysisManager` 的模型：按作用域存缓存、pass 跑完按声明决定作废什么、并且**统计一共真正遍历了几次 IR**。最后两组对照就是"漏了声明保留"的实际代价：

```python
# 一个 50 行的 AnalysisManager 模型。要弄清三件事：
#   1. 分析是**按作用域**存的（module 一份，每个 func 各一份）
#   2. pass 跑完默认全部作废；要留下来必须显式声明
#   3. markAllAnalysesPreserved 和 markAnalysesPreserved<T> 的差别

class AnalysisManager:
    def __init__(self):
        self.cache = {}                      # (作用域名, 分析名) -> 值
        self.computed = 0                    # 真正遍历 IR 的次数

    def get(self, scope, name, compute):
        key = (scope, name)
        if key not in self.cache:
            self.cache[key] = compute()
            self.computed += 1
            print(f"      {name} {scope}：缓存未命中 → 遍历 IR 算一次")
        else:
            print(f"      {name} {scope}：命中缓存，白拿")
        return self.cache[key]

    def get_cached(self, scope, name):
        return self.cache.get((scope, name))  # 不命中就是 None，绝不代劳计算

    def invalidate(self, scope, preserved):
        """preserved=None 表示全保留；否则是保留的分析名集合。"""
        if preserved is None:
            print(f"      （{scope}：声明全部保留，缓存不动）")
            return
        dropped = [n for (s, n) in list(self.cache) if s == scope and n not in preserved]
        for n in dropped:
            del self.cache[(scope, n)]
        if dropped:
            print(f"      （{scope}：作废 {dropped}；保留 {sorted(preserved) or '无'}）")

FUNCS = {"@f": 3, "@g": 1}                   # 函数名 -> 里面有几个 pix op

def run_pipeline(passes, am):
    for name, behavior in passes:
        print(f"  -{name}")
        for fn, n in FUNCS.items():          # 函数级 pass：每个函数各跑一次
            behavior(am, fn, n)

# 三种 pass 的行为
def cost_report(preserve):
    def run(am, fn, n):
        am.get(fn, "PixCost", lambda: n)
        am.invalidate(fn, {"PixCost"} if preserve else set())
    return run

def cost_recheck(am, fn, n):
    hit = am.get_cached(fn, "PixCost") is not None
    print(f"      recheck {fn} → pix.cost_cached = {str(hit).lower()}")
    am.invalidate(fn, {"PixCost"})

def cost_user(preserve):
    """真正用分析的 pass（用 getAnalysis，不命中就会自己算）。"""
    def run(am, fn, n):
        am.get(fn, "PixCost", lambda: n)
        am.invalidate(fn, {"PixCost"} if preserve else set())
    return run

def canonicalize(am, fn, n):
    am.invalidate(fn, set())                 # 改了 IR，什么都不保留

for title, passes in [
    ("① 只跑 recheck", [("pix-cost-recheck", cost_recheck)]),

    am = AnalysisManager()
    print(f"\n【{title}】")
    run_pipeline(passes, am)

```

## 并发：函数之间是并行跑的

MLIR 的 pass manager 在跑嵌套 pass 时，**默认对同一层的多个 op 并发执行**（`mlir/lib/Pass/Pass.cpp` 里 `isMultithreadingEnabled()` 为真就走 `runOnOperationAsyncImpl`）。所以图 13-1 里 `@f` 和 `@g` 是可以同时被处理的，各用自己那份 `AnalysisManager`。

这件事的硬性前提，就是从第 2 章一路提到现在的 `IsolatedFromAbove`。准确的规矩不是"并发需要它"，而是更强的一条——**能锚定 pass manager 的 op，必须标 `IsolatedFromAbove`**。源码在 `mlir/lib/Pass/Pass.cpp:558`：

```cpp-norun
if (!opInfo->hasTrait<OpTrait::IsIsolatedFromAbove>()) {
  return op->emitOpError() << "trying to schedule a pass on an operation not "
                              "marked as 'IsolatedFromAbove'";
}
```

官方文档（`mlir/docs/PassManagement.md`）给的理由很直白：*"Passes are expected not to modify operations at or above the current operation being processed. If the operation is not isolated, it may inadvertently modify or traverse the SSA use-list of an operation it is not supposed to."* 并发只是这条隔离性顺带换来的红利——各自封闭，自然可以同时跑。

### 第 8 章那笔账，现在结了

定义 `pix.pipeline` 时我们**故意没加** `IsolatedFromAbove`，`.td` 里的注释写的是"region 内可以直接引用外面的值，代价是不能被直接抽成独立函数"。代价不止那一条。试着在它上面挂个 pass manager：

```bash
pix-opt pl.mlir --pass-pipeline='builtin.module(func.func(pix.pipeline(canonicalize)))'
```

运行结果：

```
pl.mlir:2:10: error: 'pix.pipeline' op trying to schedule a pass on an operation not marked as 'IsolatedFromAbove'
  %out = pix.pipeline : tensor<4x4xf32> {
         ^
```

**直接拒绝。** 所以"要不要加 `IsolatedFromAbove`"是一个有真实后果的设计决定：加了，region 内不能再直接引用外面的值（得改成显式传参），换来的是能被单独调度 pass、能并发、能被 outlining 成独立函数；不加则反过来。`func.func` 选了加，`scf.for` 选了不加——各有各的道理。第 25 章做 GPU kernel outlining 时会再碰到这笔账。

调试时想关掉并发（比如加了打印语句、输出串成一团），用这个：

```bash
pix-opt input.mlir --pix-cost-report --mlir-disable-threading
```

<div class="note">
<strong>pass 必须是线程安全的</strong>
<p>既然默认并发，你的 <code>runOnOperation()</code> 就不能有跨调用的共享可变状态——别在 pass 类里放会被改的成员变量当缓存（框架会 <code>clonePass()</code> 出多份，但别指望具体份数），更别用函数内的 <code>static</code>。需要跨函数共享的信息，走<strong>上一层的分析</strong>（模块级 pass 的分析作用域是整个模块），而不是自己攒全局状态。</p>
</div>

## 顺手写一个真的改 IR 的 pass

前两个 pass 都只挂属性，看不出"改动"和"保留"的张力。第三个：把散落的 `pix.kernel`（`ConstantLike` 常量）统一提到函数开头。

```cpp-norun
struct PixHoistKernelsPass : impl::PixHoistKernelsBase<PixHoistKernelsPass> {
  void runOnOperation() override {
    func::FuncOp fn = getOperation();
    if (fn.getBody().empty())
      return;
    Block &entry = fn.getBody().front();

    // 先收集再移动：边遍历边改 IR 是常见的崩溃来源。
    SmallVector<KernelOp> kernels;
    fn.walk([&](KernelOp k) { kernels.push_back(k); });

    // 已经在开头的不算改动。倒序插到最前面，好保持它们之间的原有顺序。
    bool changed = false;
    for (KernelOp k : llvm::reverse(kernels)) {
      if (k->getBlock() == &entry && k->getPrevNode() == nullptr)
        continue;
      k->moveBefore(&entry, entry.begin());
      changed = true;
    }

    if (!changed)
      markAllAnalysesPreserved();   // 什么都没做，就得说一声
  }
};
```

三个细节都是被真实教训逼出来的。**先收集再移动**：`walk` 的过程中改 IR 结构，行为未定义。**倒序插入**：每次都插到最前面，倒着来才能保持它们原有的相对顺序。**"已经在开头"不算改动**：否则这个 pass 永远声称自己改了 IR，第二次运行照样把缓存冲掉。

```mlir-lower
// RUN: pix-opt %s --pix-hoist-kernels
func.func @scattered(%img: tensor<8x8xf32>) -> tensor<8x8xf32> {
  %a = pix.add %img, %img : tensor<8x8xf32>
  %k1 = pix.kernel dense<1.0> : tensor<3x3xf32> -> !pix.kernel<3 x 3>
  %c1 = pix.convolve %a, %k1 : !pix.kernel<3 x 3>, tensor<8x8xf32>
  %k2 = pix.kernel dense<2.0> : tensor<3x3xf32> -> !pix.kernel<3 x 3>
  %c2 = pix.convolve %c1, %k2 : !pix.kernel<3 x 3>, tensor<8x8xf32>
  return %c2 : tensor<8x8xf32>
}
```

运行结果：

```

  func.func @scattered(%arg0: tensor<8x8xf32>) -> tensor<8x8xf32> {
    %0 = pix.kernel dense<1.000000e+00> : tensor<3x3xf32> -> <3 x 3>
    %1 = pix.kernel dense<2.000000e+00> : tensor<3x3xf32> -> <3 x 3>
    %2 = pix.add %arg0, %arg0 : tensor<8x8xf32>
    %3 = pix.convolve %2, %0 : <3 x 3>, tensor<8x8xf32>
    %4 = pix.convolve %3, %1 : <3 x 3>, tensor<8x8xf32>
    return %4 : tensor<8x8xf32>
  }
}
```

两个 kernel 都到了最前面，**1.0 仍然在 2.0 前面**。测试里那条"跑两遍结果必须一样"的 RUN 行守的就是幂等性。

## 和 LLVM 的新 PassManager 对照

| | LLVM（新 PM） | MLIR |
| --- | --- | --- |
| 层级 | 固定几种：Module / CGSCC / Function / Loop | **由 op 树决定**，想几层有几层 |
| pass 作用对象 | 预定义的 IR 单位 | 任意 op 类型（`Pass<"n", "your.op">`） |
| 分析 | `AnalysisManager<IRUnitT>`，分析要特化 | 任意类 + 一个 `Operation*` 构造函数 |
| 失效 | 返回 `PreservedAnalyses` | 调 `markAnalysesPreserved<T>()` |
| 并发 | 基本没有 | **默认并发**跑同层 op |
| 嵌套的前提 | 由 IR 结构固定 | 锚点 op 要标 `IsolatedFromAbove` |

抓住一条就够：**LLVM 的层级是语言给定的，MLIR 的层级是你自己设计出来的。** 这既是自由也是负担——你得想清楚"哪些 op 该是隔离的"，而这个决定同时决定了能不能并发、能不能单独调度 pass、能不能被 outlining。

## 动手：给 `pix-cost-report` 加一个 option

pass 可以带命令行选项。在 `Passes.td` 里给 `PixCostReport` 加一个：

```tablegen
def PixCostReport : Pass<"pix-cost-report", "::mlir::func::FuncOp"> {
  let summary = "统计本函数的 pix 计算量，写成属性";
  let options = [
    Option<"skipEmpty", "skip-empty", "bool", /*default=*/"false",
           "pix op 数为 0 的函数就不要挂属性了">
  ];
}
```

重新构建，生成的基类里会多一个 `skipEmpty` 成员，直接用。然后：

```bash
pix-opt p13.mlir --pix-cost-report=skip-empty=true
```

`@no_pix` 那个函数应当不再出现 `pix.num_ops`。顺手用 `--dump-pass-pipeline` 看看选项是怎么显示在管线里的（回想前面 `canonicalize{...}` 那一长串）。

**再改一处**：把 `pix-hoist-kernels` 里 `if (!changed) markAllAnalysesPreserved();` 那两行删掉，然后跑

```bash
pix-opt p13.mlir --pix-cost-report --pix-hoist-kernels --pix-cost-recheck
```

`pix.cost_cached` 会从 `true` 变成 `false`——即使那两个函数里一个 `pix.kernel` 都没有、pass 实际什么都没干。这就是"漏一句声明"的真实代价。

---

**这一章的要点**

- `Pass<"命令行名", "::mlir::func::FuncOp">` 的第二个参数决定**框架把什么交给你**。写了它，`getOperation()` 的返回类型就已经收窄，不用 cast。
- pass 的骨架全部由 TableGen 生成：`GEN_PASS_DECL` / `GEN_PASS_REGISTRATION` 在头文件里，`GEN_PASS_DEF_<全大写>` 在实现里给出 `impl::XxxBase<DerivedT>` CRTP 基类。**别自己写 `createXxx()`**（生成代码里已有，且名字没有 `Pass` 后缀），**pass 结构要放在方言的命名空间里**（否则 `impl` 有歧义，friend 也找不到你）。
- **MLIR 的 pass 层级由 op 树决定**，不像 LLVM 那样固定。`builtin.module(func.func(...))` 这串括号就是层级；写错了框架会问你"did you intend to nest?"。拿不准就 `--dump-pass-pipeline`，它还会把每个 pass 的选项展开给你看。
- **分析不用继承、不用注册**，只要有一个接受 `Operation *` 的构造函数。`AnalysisManager` 用 `TypeID` 当键，**按作用域**缓存——函数级 pass 拿到的分析只覆盖本函数。
- `getAnalysis<T>()` 不命中就现算；`getCachedAnalysis<T>()` 不命中就返回空。后者能把"缓存状态"这件看不见的事变成可观察的东西，值得在调试时用。
- **框架默认假设你破坏了一切。** 改动与某个分析无关时用 `markAnalysesPreserved<T>()`；什么都没改时用 `markAllAnalysesPreserved()`。**漏掉它们没有任何报错**，只是让后面的 pass 白白重算——实测同样三个 pass，声明保留是 2 次遍历，不声明是 6 次。
- **同一层的多个 op 默认并发跑**，所以 `runOnOperation()` 必须线程安全：别在 pass 里攒可变状态，别用函数内 `static`。调试时 `--mlir-disable-threading`。
- **能锚定 pass manager 的 op 必须标 `IsolatedFromAbove`**（`Pass.cpp:558`），理由是"pass 不许碰当前 op 之上的东西"。`pix.pipeline` 没加，所以在它上面挂 pass manager 会被直接拒绝——第 8 章那个决定的代价，到这里才完整显形。
- 改 IR 的 pass 三条经验：**先收集再遍历改**、**倒序插入保序**、**"本来就对"不算改动**。

**pix 进度**：有了自己的 pass 基础设施（`Transforms/` 目录、`MLIRPixTransforms` 库、`registerPixPasses()`）与第一个分析 `PixCostAnalysis`，三个 pass 各演示一个机制。新增 `cost_analysis.mlir`（四条 RUN 行靠 `--check-prefix` 做对照实验）与 `hoist_kernels.mlir`，`check-pix` 从 8 涨到 10 个文件。
