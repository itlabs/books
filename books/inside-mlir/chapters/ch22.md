# 第 22 章 Bufferization：从 tensor 的值语义到 memref 的内存语义

## 这一章想让你带走什么

<div class="goal-box">
<p>到现在为止，pix 降下来的 IR 一直在 <code>tensor</code> 上：<strong>值语义</strong>——每个 <code>tensor</code> 是一个不可变的值，"写"总是产生一个新值。这非常适合做变换（第 21 章那些 tile 和融合能成立，很大程度靠它），但机器不是这么工作的。</p>
<p>这一章走那一步：<strong>tensor → memref</strong>。难点不在 API——<code>--one-shot-bufferize</code> 一个 pass 的事。难在它要回答三个此前一直被回避的问题：<strong>谁拥有这块内存、什么时候能就地覆盖、别名怎么判。</strong></p>
<p>核心是**原地分析（in-place analysis）**。我们会用实测数字把它的价值钉死：同一份 tile+融合后的 IR，开分析是 <strong>2 个 alloc、1 次 copy</strong>，用 <code>copy-before-write=true</code> 跳过分析是 <strong>6 个 alloc、4 次 copy</strong>——而那些 copy 在循环里，是每次迭代都要付的。</p>
<p>还会回答第 20、21 章留下的问题：那些 <code>tensor.empty</code> 最终变成了什么？<code>tensor.extract_slice</code> 会不会真的拷数据？（答案：<strong>不会</strong>，它变成 <code>memref.subview</code>，一个零拷贝的视图。）</p>
</div>

## 为什么不能直接把类型换掉

先说清难在哪。天真的想法是"把所有 `tensor<8x8xf32>` 替换成 `memref<8x8xf32>` 就完了"。看一段 IR 就知道不行：

```mlir-norun
%1 = pix.add %a, %a : tensor<8x8xf32>
%2 = pix.scale %1, %f : tensor<8x8xf32>
%3 = pix.add %1, %2 : tensor<8x8xf32>   // ← %1 又被读了
```

值语义下这段代码毫无歧义：`%1` 是一个值，谁都可以读它。换成 memref 之后，问题立刻出来了——**`%2` 的计算能不能就地写在 `%1` 的 buffer 上？** 不能，因为 `%1` 后面还要被读。可如果第三行不存在，就地写是安全的，还省一次分配。

**这个判断需要活跃性分析**，而不是类型替换。这就是 bufferization 的实质。

MLIR 的答案叫 **One-Shot Bufferize**：一次 pass 里同时做分析和改写（"one-shot"就是这个意思，相对于早期那种"每个方言各自 bufferize、中间靠 cast 拼"的做法）。

## 先看结果

```mlir-lower
// RUN: pix-opt %s --pix-to-linalg --one-shot-bufferize="bufferize-function-boundaries=true" --canonicalize
func.func @two_steps(%a: tensor<8x8xf32>, %b: tensor<8x8xf32>, %f: f32) -> tensor<8x8xf32> {
  %s = pix.add %a, %b : tensor<8x8xf32>
  %m = pix.scale %s, %f : tensor<8x8xf32>
  return %m : tensor<8x8xf32>
}
```

运行结果：

```
#map = affine_map<(d0, d1) -> (d0, d1)>
module {
  func.func @two_steps(%arg0: memref<8x8xf32, strided<[?, ?], offset: ?>>, %arg1: memref<8x8xf32, strided<[?, ?], offset: ?>>, %arg2: f32) -> memref<8x8xf32> {
    %alloc = memref.alloc() {alignment = 64 : i64} : memref<8x8xf32>
    linalg.generic {indexing_maps = [#map, #map, #map], iterator_types = ["parallel", "parallel"]} ins(%arg0, %arg1 : memref<8x8xf32, strided<[?, ?], offset: ?>>, memref<8x8xf32, strided<[?, ?], offset: ?>>) outs(%alloc : memref<8x8xf32>) {
    ^bb0(%in: f32, %in_1: f32, %out: f32):
      %0 = arith.addf %in, %in_1 : f32
      linalg.yield %0 : f32
    }
    %alloc_0 = memref.alloc() {alignment = 64 : i64} : memref<8x8xf32>
    linalg.generic {indexing_maps = [#map, #map], iterator_types = ["parallel", "parallel"]} ins(%alloc : memref<8x8xf32>) outs(%alloc_0 : memref<8x8xf32>) {
    ^bb0(%in: f32, %out: f32):
      %0 = arith.mulf %in, %arg2 : f32
      linalg.yield %0 : f32
    }
    return %alloc_0 : memref<8x8xf32>
  }
}
```

四处变化，每处都有讲究：

**一、`tensor.empty` 变成了 `memref.alloc()`。** 第 20 章那些"目标张量"原来就是分配请求——destination-passing style 在这里兑现了：**bufferization 不用猜"结果该放哪"，`outs` 已经告诉它了。**

**二、`linalg.generic` 不再有返回值。** 看那一行末尾没有 `-> tensor<8x8xf32>` 了。它现在直接写进 `outs` 指向的 memref。这是值语义变成内存语义最直观的标志。

**三、函数入参带上了布局：`memref<8x8xf32, strided<[?, ?], offset: ?>>`。** 那个 `strided<...>` 说"我接受任何步长和偏移的视图"——因为调用者可能传进来一块大 buffer 的子视图。这是 `bufferize-function-boundaries=true` 的结果；不开这个选项，函数边界会保持 tensor，中间插 cast。

**四、返回的是 `memref<8x8xf32>`（没有布局）**，因为它是我们自己 alloc 的，布局确定。

<div class="warn">
<strong>那个 alloc 谁来释放？</strong>
<p>这段输出里 <code>memref.alloc</code> 没有配对的 <code>memref.dealloc</code>——它被 return 出去了，所有权交给了调用者。这是 bufferization 之后一个真实的问题：<strong>它只负责放置分配，不负责释放</strong>。</p>
<p>释放由另一个 pass 管：<code>--buffer-deallocation-pipeline</code>（老版本叫 <code>-buffer-deallocation</code>）。真实管线里它紧跟在 bufferization 后面。这一章不展开，但要知道<strong>缺了那一步就是内存泄漏</strong>——而且 IR 看起来完全正常，不会有任何报错。</p>
</div>

## 原地分析：这一章的核心

把第 21 章那份 tile + 融合过的 IR 拿来 bufferize，才看得出分析的分量：

```bash
pix-opt f21.mlir --pix-to-linalg --transform-interpreter --canonicalize --cse \
  --one-shot-bufferize="bufferize-function-boundaries=true" --canonicalize
```

运行结果（函数部分）：

```
  func.func @two_steps(%arg0: memref<8x8xf32, strided<[?, ?], offset: ?>>, %arg1: memref<8x8xf32, strided<[?, ?], offset: ?>>, %arg2: f32) -> memref<8x8xf32> {
    %c4 = arith.constant 4 : index
    %c8 = arith.constant 8 : index
    %c0 = arith.constant 0 : index
    %alloc = memref.alloc() {alignment = 64 : i64} : memref<8x8xf32>
    scf.for %arg3 = %c0 to %c8 step %c4 {
      scf.for %arg4 = %c0 to %c8 step %c4 {
        %subview = memref.subview %arg0[%arg3, %arg4] [4, 4] [1, 1] : memref<8x8xf32, strided<[?, ?], offset: ?>> to memref<4x4xf32, strided<[?, ?], offset: ?>>
        %subview_0 = memref.subview %arg1[%arg3, %arg4] [4, 4] [1, 1] : memref<8x8xf32, strided<[?, ?], offset: ?>> to memref<4x4xf32, strided<[?, ?], offset: ?>>
        %alloc_1 = memref.alloc() {alignment = 64 : i64} : memref<4x4xf32>
        linalg.generic {indexing_maps = [#map, #map, #map], iterator_types = ["parallel", "parallel"]} ins(%subview, %subview_0 : memref<4x4xf32, strided<[?, ?], offset: ?>>, memref<4x4xf32, strided<[?, ?], offset: ?>>) outs(%alloc_1 : memref<4x4xf32>) {
        ^bb0(%in: f32, %in_4: f32, %out: f32):
          %0 = arith.addf %in, %in_4 : f32
          linalg.yield %0 : f32
        }
        %subview_2 = memref.subview %alloc[%arg3, %arg4] [4, 4] [1, 1] : memref<8x8xf32> to memref<4x4xf32, strided<[8, 1], offset: ?>>
        linalg.generic {indexing_maps = [#map, #map], iterator_types = ["parallel", "parallel"]} ins(%alloc_1 : memref<4x4xf32>) outs(%subview_2 : memref<4x4xf32, strided<[8, 1], offset: ?>>) {
        ^bb0(%in: f32, %out: f32):
          %0 = arith.mulf %in, %arg2 : f32
          linalg.yield %0 : f32
        }
        %subview_3 = memref.subview %alloc[%arg3, %arg4] [4, 4] [1, 1] : memref<8x8xf32> to memref<4x4xf32, strided<[8, 1], offset: ?>>
        memref.copy %subview_2, %subview_3 : memref<4x4xf32, strided<[8, 1], offset: ?>> to memref<4x4xf32, strided<[8, 1], offset: ?>>
      }
    }
    return %alloc : memref<8x8xf32>
  }
```

这段输出值得逐条读：

**循环携带的张量变成了循环外的一个 `memref.alloc()`。** 第 21 章那个 `iter_args(%arg4 = %0)` 在值语义下是"每次迭代产生一个新的 8×8 张量"；bufferize 之后变成"一块 buffer，循环体直接往里写"。**每次迭代零分配。**

**`tensor.extract_slice` → `memref.subview`。** 这是关键：`subview` 是一个**视图**，不拷数据。第 21 章你可能担心过"每个 tile 都 extract 一次，是不是要拷来拷去"——不会。

**`tensor.insert_slice` → 直接写进 `%subview_2`。** 没有 copy。这是原地分析做的决定：那块 buffer 之后没人再读旧值，所以可以覆盖。

**唯一的 per-iteration 分配是那个 4×4 的中间结果**（`%alloc_1`）——融合把它从 8×8 缩到了 4×4，这正是第 21 章那笔账的兑现。

### 用数字说话

把 `copy-before-write=true` 打开（跳过分析，每次写都先拷一份），同一份输入：

| | `alloc` | `copy` | `subview` |
| --- | --- | --- | --- |
| 有原地分析（默认） | **2** | **1** | 4 |
| `copy-before-write=true` | 6 | 4 | 3 |

**3 倍的分配、4 倍的拷贝。** 而且那些 copy 在循环体里——是每次迭代都付的代价。

<div class="keypoint">
<strong>原地分析判的是什么：一条规则</strong>
<p><strong>把写操作就地做在某块 buffer 上，当且仅当那块 buffer 之后没人再读旧值。</strong></p>
<p>这就是读后写（RaW）冲突检测。它需要的信息是"活跃性"——而值语义的 IR 恰好把这件事表达得很清楚：<code>tensor</code> 的 def-use 链就是活跃性。<strong>这也解释了为什么 MLIR 选择"先在 tensor 上做完所有变换，最后一步才 bufferize"</strong>：越晚 bufferize，分析的信息越完整、越准。</p>
<p>反过来说也成立：<strong>bufferization 之后就很难再做 tiling 和融合了</strong>——那时别名信息已经丢进 memref 里，要重新分析出来非常贵。所以第 21 章那些变换必须在这一章之前做完，顺序不是随意的。</p>
</div>

### 它不是"一律原地"

分析会拒绝不安全的就地写。两个函数对照：

```mlir-norun
// %a 被写之后还要被读 → 不能就地
func.func @must_copy(%a: tensor<8x8xf32>) -> (tensor<8x8xf32>, tensor<8x8xf32>) {
  %c = arith.constant dense<1.0> : tensor<4x4xf32>
  %ins = tensor.insert_slice %c into %a[0, 0] [4, 4] [1, 1] : tensor<4x4xf32> into tensor<8x8xf32>
  return %ins, %a : tensor<8x8xf32>, tensor<8x8xf32>
}
// %a 写完之后没人再读 → 可以就地
func.func @can_inplace(%a: tensor<8x8xf32>) -> tensor<8x8xf32> {
  %c = arith.constant dense<1.0> : tensor<4x4xf32>
  %ins = tensor.insert_slice %c into %a[0, 0] [4, 4] [1, 1] : tensor<4x4xf32> into tensor<8x8xf32>
  return %ins : tensor<8x8xf32>
}
```

运行结果（只看分配与拷贝相关的行）：

```
  func.func @must_copy(%arg0: memref<8x8xf32, strided<[?, ?], offset: ?>>) -> (memref<8x8xf32>, memref<8x8xf32, strided<[?, ?], offset: ?>>) {
    %alloc = memref.alloc() {alignment = 64 : i64} : memref<8x8xf32>
    memref.copy %arg0, %alloc : memref<8x8xf32, strided<[?, ?], offset: ?>> to memref<8x8xf32>
    %subview = memref.subview %alloc[0, 0] [4, 4] [1, 1] : memref<8x8xf32> to memref<4x4xf32, strided<[8, 1]>>
    memref.copy %0, %subview : memref<4x4xf32> to memref<4x4xf32, strided<[8, 1]>>
  func.func @can_inplace(%arg0: memref<8x8xf32, strided<[?, ?], offset: ?>>) -> memref<8x8xf32, strided<[?, ?], offset: ?>> {
    %subview = memref.subview %arg0[0, 0] [4, 4] [1, 1] : memref<8x8xf32, strided<[?, ?], offset: ?>> to memref<4x4xf32, strided<[?, ?], offset: ?>>
    memref.copy %0, %subview : memref<4x4xf32> to memref<4x4xf32, strided<[?, ?], offset: ?>>
```

差别一目了然：

- `@must_copy`：先 `memref.alloc` 一块 8×8，再 `memref.copy %arg0, %alloc` **把整张图拷进去**，然后在副本上写。
- `@can_inplace`：**没有 alloc、没有整图 copy**，直接 `memref.subview %arg0` 然后往里写。

**两个函数的 tensor 代码几乎一样，差别只在"返回值里还有没有 `%a`"。** 分析读出了这个差别。

<div class="note">
<strong>那个小 <code>memref.copy %0, %subview</code> 是什么</strong>
<p>两个函数里都有它——那是把 4×4 的常量数据写进目标位置，是<strong>必要的数据搬运</strong>，不是分析失败。要分清两种 copy：<strong>整块 buffer 的防御性拷贝</strong>（分析失败的代价，<code>@must_copy</code> 里那个 8×8 的）和<strong>真正要搬的数据</strong>（这个 4×4 的）。看 <code>memref.copy</code> 的尺寸就能区分。</p>
</div>

## 三个此前被回避的问题

这一章开头说 bufferization 要回答三个问题。现在逐个收尾。

**谁拥有这块内存？** destination-passing style 回答了一半：`outs` 指向哪，结果就写哪。剩下的一半是"新分配的 buffer 归谁"——bufferization 放置 `memref.alloc`，但所有权（谁 dealloc）交给后续的 deallocation pass。**这是 MLIR 有意的分工**：分配位置是数据流问题，释放是控制流问题。

**什么时候能就地更新？** 上面那条规则：之后没人读旧值。实现上靠遍历 tensor 的 use 链做 RaW 检测。

**别名怎么判？** 这是最微妙的。`memref.subview` 创造别名——两个 memref 指向重叠的内存。One-Shot Bufferize 在 tensor 层面维护"别名集合"（alias set），把"这两个 tensor 会不会落到同一块 buffer"算清楚，再据此决定拷不拷。想看它算出了什么，有个专门的调试开关：

```bash
mlir-opt input.mlir --one-shot-bufferize="dump-alias-sets" ...
```

它会把别名集合作为属性标注在 IR 上。**调"为什么这里多了一次拷贝"时，这是第一个该看的东西。**

## 把判定规则自己跑一遍

那条规则（"之后没人读旧值才能就地"）跑一遍就清楚了。下面这个模型对三种 IR 各判一次，并对比"跳过分析"的代价：

```python
# One-Shot Bufferize 的原地分析在判什么？一条规则：
#   把写操作就地做在某块 buffer 上，当且仅当**那块 buffer 之后没人再读旧值**。
# 这个模型把判定过程打出来，并统计省下多少拷贝。

class Tensor:
    def __init__(self, name, buf): self.name, self.buf = name, buf

def analyze(ops, steps_desc, copy_before_write=False):
    """ops: (结果名, 被写的张量名 or None, 读到的张量名列表)"""
    live_after = {}                         # 张量名 -> 它最后一次被读的步号
    for i, (_, _, reads) in enumerate(ops):
        for r in reads:
            live_after[r] = i
    buffers, decisions, allocs, copies = {}, [], 0, 0
    for i, (res, written, reads) in enumerate(ops):
        if written is None:                 # 纯产出（对应 tensor.empty + 写满）
            allocs += 1
            buffers[res] = f"buf{allocs}"
            decisions.append(f"  {steps_desc[i]}：新 buffer {buffers[res]}（alloc）")
            continue
        # 要就地写 `written`。判据：written 在本步之后还会被读吗？
        later = live_after.get(written, -1) > i
        if copy_before_write or later:
            allocs += 1; copies += 1
            buffers[res] = f"buf{allocs}"
            why = "跳过分析，一律先拷" if copy_before_write else \
                  f"{written} 在第 {live_after[written]} 步还要被读 → 不能覆盖"
            decisions.append(f"  {steps_desc[i]}：拷一份再写（alloc+copy）—— {why}")
        else:
            buffers[res] = buffers.get(written, "入参 buffer")
            decisions.append(f"  {steps_desc[i]}：<<就地写 {buffers[res]}>>，零拷贝"
                             f" —— {written} 之后没人再读旧值")
    return decisions, allocs, copies

CASES = [
    ("三步链式（每步都产出新张量）",
     [("%1", None, ["%a"]), ("%2", None, ["%1"]), ("%3", None, ["%2"])],
     ["%1 = add(%a,%a)", "%2 = scale(%1)", "%3 = mul(%2,%2)"]),
    ("写入之后旧值还要被读 → 必须拷",
     [("%ins", "%a", ["%a"]), ("ret", None, ["%ins", "%a"])],
     ["%ins = insert_slice(.. into %a)", "return %ins, %a"]),
    ("写入之后旧值没人要 → 可以就地",
     [("%ins", "%a", ["%a"]), ("ret", None, ["%ins"])],
     ["%ins = insert_slice(.. into %a)", "return %ins"]),
]
for title, ops, desc in CASES:
    print(f"\n【{title}】")
    for cbw in (False, True):
        d, a, c = analyze(ops, desc, cbw)
        print(f"  {'跳过分析' if cbw else '有原地分析'}：alloc={a} copy={c}")
        if not cbw:
            for line in d: print("  " + line)
print("\n" + "=" * 62)
print("一句话：bufferization 的难点不是「把 tensor 换成 memref」，")
print("而是「谁拥有这块内存、什么时候能覆盖」。前者是类型替换，后者要活跃性分析。")
```

运行结果：

```

【三步链式（每步都产出新张量）】
  有原地分析：alloc=3 copy=0
    %1 = add(%a,%a)：新 buffer buf1（alloc）
    %2 = scale(%1)：新 buffer buf2（alloc）
    %3 = mul(%2,%2)：新 buffer buf3（alloc）
  跳过分析：alloc=3 copy=0

【写入之后旧值还要被读 → 必须拷】
  有原地分析：alloc=2 copy=1
    %ins = insert_slice(.. into %a)：拷一份再写（alloc+copy）—— %a 在第 1 步还要被读 → 不能覆盖
    return %ins, %a：新 buffer buf2（alloc）
  跳过分析：alloc=2 copy=1

【写入之后旧值没人要 → 可以就地】
  有原地分析：alloc=1 copy=0
    %ins = insert_slice(.. into %a)：<<就地写 入参 buffer>>，零拷贝 —— %a 之后没人再读旧值
    return %ins：新 buffer buf1（alloc）
  跳过分析：alloc=2 copy=1

而是「谁拥有这块内存、什么时候能覆盖」。前者是类型替换，后者要活跃性分析。
```

注意第三组：**同样的 IR，有分析是 1 个 alloc 0 次 copy，跳过分析是 2 个 alloc 1 次 copy**——和真 `mlir-opt` 在 `@can_inplace` / `@must_copy` 上的行为一致。前两组则完全相同，说明分析不是无条件省，它只在"确实安全"时才省。

## 常见问题与它们的成因

bufferization 是 MLIR 里最容易卡住的一步。几个高频问题：

| 症状 | 成因 | 怎么查 |
| --- | --- | --- |
| `op was not bufferized` | 那个 op 没实现 `BufferizableOpInterface` | 加 `allow-unknown-ops=true` 先跑通，再看是谁 |
| 多了很多 `memref.copy` | 原地分析判定不安全 | `dump-alias-sets` 看别名集合；检查是不是有多余的 use |
| 函数边界还是 tensor | 忘了 `bufferize-function-boundaries=true` | 默认是关的（选项名后面标着 experimental） |
| 内存泄漏 | 只做了 bufferization，没跑 deallocation | 管线里补 `--buffer-deallocation-pipeline` |
| 结果不对，但 IR 看着正常 | 就地写了不该写的地方 | 先用 `copy-before-write=true` 跑一遍——**如果结果变对了，就是分析或你的 op 接口实现有问题** |

最后那一行是很实用的二分法：**`copy-before-write=true` 是 bufferization 的"安全模式"**。它性能差但语义保守，用它来判断"问题在分析还是在别处"，能省很多时间。

<div class="keypoint">
<strong>自定义 op 要参与 bufferization，得实现 <code>BufferizableOpInterface</code></strong>
<p>pix 在这一章没遇到这个问题，因为我们在 bufferize 之前就把所有 pix op 降成了 linalg——<strong>而 linalg 已经实现了那个接口</strong>。这是个值得学的策略：<strong>让自己的方言尽早降到已经接好生态的方言上，就能白拿一整条下降链。</strong></p>
<p>如果确实需要让某个 pix op 直接 bufferize（比如它有独特的内存语义），那就要实现 <code>bufferize()</code>、<code>bufferizesToMemoryRead/Write()</code>、<code>getAliasingValues()</code> 这几个方法，告诉框架"我读什么、写什么、我的结果和哪个操作数共享 buffer"。第 27 章看 IREE 时会见到大量这种实现。</p>
</div>

```bash

  --one-shot-bufferize="bufferize-function-boundaries=true" --canonicalize \
  | grep -B3 -A1 memref.copy
```

看清它拷的是什么尺寸、在什么位置，然后想清楚：**它是"分析失败的代价"还是"必要的数据搬运"？**（提示：看它在不在循环里。）

**再改一处**：把 tile 大小从 `[4, 4]` 改成 `[8, 8]`（整张图一个 tile），重新跑整条管线并数 alloc。**alloc 数会变吗？为什么？** 这个实验能让你对"融合的收益来自哪里"有更准的感觉——tile 变大之后中间 buffer 也变大，融合省下的绝对量没变，但局部性变差了。

---

**这一章的要点**

- bufferization **不是把 `tensor` 换成 `memref`**，是一次活跃性分析。类型替换是结果，判断"能不能覆盖"才是内容。
- **一条规则**：把写操作就地做在某块 buffer 上，当且仅当**那块 buffer 之后没人再读旧值**（读后写冲突检测）。
- **值语义的 def-use 链就是活跃性信息**，所以越晚 bufferize，分析越准。反过来——bufferize 之后别名信息已经埋进 memref，重新分析非常贵。**所以第 20、21 章那些 tiling 与融合必须在这一步之前做完：管线顺序是约束，不是习惯。** 这也是 MLIR 把 tensor / memref 分成两层的根本原因。
- 实测收益：同一份 tile+融合后的 IR，有分析是 **2 alloc / 1 copy**，`copy-before-write=true` 是 **6 alloc / 4 copy**——3 倍分配、4 倍拷贝，而且那些 copy 在循环体里。
- **`tensor.empty` → `memref.alloc`**，**`tensor.extract_slice` → `memref.subview`（零拷贝视图）**，**`tensor.insert_slice` → 直接写进子视图**（分析允许的话）。`linalg.generic` 不再有返回值。
- destination-passing style 在这里兑现：**bufferization 不用猜"结果放哪"，`outs` 已经告诉它了。** 第 20 章那个看起来啰嗦的设计，价值在这一章显形。
- **bufferization 只放置分配，不负责释放**。缺了 `--buffer-deallocation-pipeline` 就是内存泄漏，而 IR 看起来完全正常、没有任何报错。
- 要分清两种 `memref.copy`：**整块 buffer 的防御性拷贝**（分析失败的代价）和**真正要搬的数据**。看尺寸和位置就能区分。
- **`copy-before-write=true` 是安全模式**：性能差但语义保守。"结果不对但 IR 看着正常"时先用它跑一遍——结果变对了说明问题在分析或你的接口实现。
- **让自己的方言尽早降到已接好生态的方言（如 linalg），就能白拿整条下降链。** pix 在这一章没碰到 `BufferizableOpInterface`，正是因为它已经变成 linalg 了。

**pix 进度**：这一章不给 pix 加 op，但把管线接通了一段关键的路：`pix → linalg → tile/fuse → memref`。新增 `bufferize.mlir`，两条 RUN 行对照"有分析"与"跳过分析"。`check-pix` 从 18 涨到 19 个文件。
