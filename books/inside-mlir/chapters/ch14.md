# 第 14 章 Pattern Rewrite 引擎：RewritePattern、benefit 与 greedy driver

## 这一章想让你带走什么

<div class="goal-box">
<p>第 11 章我们写过 canonicalize pattern，但把引擎当黑盒用了：<code>benefit</code> 没提、<code>PatternRewriter</code> 那些 <code>notify*</code> 回调没提、worklist 里到底发生了什么也只从调试输出瞥了一眼。这一章把它打开。</p>
<p>做法还是老办法——<strong>把看不见的东西变成可观察的</strong>。我们写一个 pass，里面装<strong>两条匹配完全相同输入、但结果不同</strong>的 pattern，靠 <code>benefit</code> 决胜负；再挂一个 <code>RewriterBase::Listener</code>，把 driver 发出的每一类通知（插入 / 替换 / 擦除 / 原地修改 / 试了几条 pattern / 赢了几条）计数后写成函数属性。于是"引擎在干什么"变成了 IR 里一串可以用 FileCheck 断言的数字。</p>
<p>你会看到三个反直觉的观察，全部有实测：<strong>高 benefit 的 pattern 成功后，低的根本不会被试</strong>（<code>tried = 1</code> 而不是 2）；<strong>一个 op 上没有以它为根的 pattern 时，一条都不会试</strong>（<code>tried = 0</code>，所以注册几百条 pattern 不会拖慢无关的 op）；以及第 11 章那个"被 erase 的地址立刻被复用"到底会怎么坑到你。</p>
</div>

## 三种写 pattern 的方式，先分清

| 写法 | 匹配什么 | 什么时候用 |
| --- | --- | --- |
| `OpRewritePattern<MyOp>` | 根 op 是 `MyOp` | 绝大多数情况。类型已收窄，`matchAndRewrite(MyOp op, ...)` |
| `OpInterfaceRewritePattern<MyInterface>` | 任何实现了该接口的 op | 想一次覆盖一批 op（第 5 章那种"面向接口变换"） |
| `RewritePattern`（裸基类） | 自己给 `MatchAnyOpTypeTag` 或一个 op 名列表 | 少用。丧失了按根 op 名索引的好处（见下） |

本章两条都是第一种：

```cpp-norun
struct AddSelfToScale : OpRewritePattern<AddOp> {
  // benefit 从构造函数传进来。OpRewritePattern 的第二个参数就是它，
  // 默认值是 1——这也是为什么"都不写 benefit"的 pattern 之间顺序不确定。
  AddSelfToScale(MLIRContext *ctx, PatternBenefit benefit)
      : OpRewritePattern<AddOp>(ctx, benefit) {}

  LogicalResult matchAndRewrite(AddOp op,
                                PatternRewriter &rewriter) const override {
    if (op.getLhs() != op.getRhs())
      return rewriter.notifyMatchFailure(op, "两个操作数不是同一个值");

    Value two = arith::ConstantOp::create(rewriter, op.getLoc(),
                                          rewriter.getF32FloatAttr(2.0));
    rewriter.replaceOpWithNewOp<ScaleOp>(op, op.getLhs(), two);
    return success();
  }
};
```

`AddSelfToMul` 只有结果不同（改写成 `pix.mul %x, <全 2 的图>`），**匹配条件一模一样**。两条同时注册，谁赢？

<div class="note">
<strong><code>return rewriter.notifyMatchFailure(op, "理由")</code> 值得养成习惯</strong>
<p>它返回的就是 <code>failure()</code>，所以写法上不多一个字，但那句理由会出现在 <code>--debug-only=greedy-rewriter</code> 的输出里（本章后面有实拍）。调"这条 pattern 为什么没匹配上"的时候，有没有这句话是两种体验——**没有它，你只能看到"failed to match"四个字**。</p>
</div>

## `benefit`：谁先被试

`PatternBenefit` 就是个小整数（`mlir/include/mlir/IR/PatternMatch.h:34`，内部用 65535 当"不可能匹配"的哨兵）。driver 拿它给 pattern 排序，**高的先试**。

pass 里把 benefit 做成可切换的，好做对照：

```cpp-norun
struct PixRewriteAddPass : impl::PixRewriteAddBase<PixRewriteAddPass> {
  using Base::Base;

  void runOnOperation() override {
    func::FuncOp fn = getOperation();
    MLIRContext *ctx = &getContext();

    // swap=false：scale 那条 benefit 2，赢；swap=true：反过来。
    PatternBenefit scaleBenefit = swap ? PatternBenefit(1) : PatternBenefit(2);
    PatternBenefit mulBenefit = swap ? PatternBenefit(2) : PatternBenefit(1);

    RewritePatternSet patterns(ctx);
    patterns.add<AddSelfToScale>(ctx, scaleBenefit);
    patterns.add<AddSelfToMul>(ctx, mulBenefit);

    CountingListener listener;
    GreedyRewriteConfig config;
    config.setListener(&listener);

    if (failed(applyPatternsGreedily(fn, std::move(patterns), config)))
      return signalPassFailure();
    // …把 listener 的计数写成属性
  }
};
```

注意这里是 **`applyPatternsGreedily`** 显式驱动，不是靠 `--canonicalize`。区别很实在：第 11 章那些是挂在 op 上的 canonicalizer，**全局生效**，谁跑 `--canonicalize` 都会用上；这一套只在这个 pass 里生效。**要做"只在某个阶段才该发生"的改写，就得用这条路。**

跑起来：

```mlir-lower
// RUN: pix-opt %s --pix-rewrite-add
func.func @self_add(%img: tensor<4x4xf32>) -> tensor<4x4xf32> {
  %r = pix.add %img, %img : tensor<4x4xf32>
  return %r : tensor<4x4xf32>
}
```

运行结果：

```
module {
  func.func @self_add(%arg0: tensor<4x4xf32>) -> tensor<4x4xf32> attributes {pix.erased = 1 : i64, pix.inserted = 2 : i64, pix.modified = 1 : i64, pix.patterns_tried = 1 : i64, pix.patterns_won = 1 : i64, pix.replaced = 1 : i64} {

    %0 = pix.scale %arg0, %cst : tensor<4x4xf32>
    return %0 : tensor<4x4xf32>

```

`pix.scale` 赢了。把 benefit 对调：

```bash
pix-opt b14.mlir --pix-rewrite-add=swap=true
```

运行结果（只看那一行）：

```
    %0 = pix.mul %arg0, %cst : tensor<4x4xf32>
```

同一份输入、同一套 pattern，只改了两个整数，结果不同。**benefit 不是"提示"，是决定性的。**

### `tried = 1`：成功即短路

上面那串属性里最值得盯的是 **`pix.patterns_tried = 1`**。我们注册了两条，却只试了一条——因为高 benefit 那条成功了，**driver 不会再试剩下的**。

这不是猜的。换一个两条都匹配不上的输入做对照：

```mlir-lower
// RUN: pix-opt %s --pix-rewrite-add
func.func @two_operands(%a: tensor<4x4xf32>, %b: tensor<4x4xf32>) -> tensor<4x4xf32> {
  %r = pix.add %a, %b : tensor<4x4xf32>
  return %r : tensor<4x4xf32>
}
```

运行结果：

```
module {
  func.func @two_operands(%arg0: tensor<4x4xf32>, %arg1: tensor<4x4xf32>) -> tensor<4x4xf32> attributes {pix.erased = 0 : i64, pix.inserted = 0 : i64, pix.modified = 0 : i64, pix.patterns_tried = 2 : i64, pix.patterns_won = 0 : i64, pix.replaced = 0 : i64} {
    %0 = pix.add %arg0, %arg1 : tensor<4x4xf32>
    return %0 : tensor<4x4xf32>
  }
}
```

`tried = 2, won = 0`。两条都试了、都失败了。**和上一个例子对照，才能确认 `tried = 1` 不是因为"只注册了一条"。**

### `tried = 0`：无关的 op 一条都不问

再换一个函数，里面只有 `pix.mul`，没有 `pix.add`：

```bash
pix-opt b14.mlir --pix-rewrite-add | grep untouched
```

实测 `pix.patterns_tried = 0`。

原因是 **pattern 按"根 op 名"分桶索引**。driver 处理一个 op 时，只从那个 op 名对应的桶里取 pattern；桶是空的，就一条都不问。这件事的实际意义不小：**一个大型方言注册几百条 pattern，不会让无关的 op 变慢**——代价是 O(桶里的条数)，不是 O(全部 pattern)。

（这也是上面那张表里"裸 `RewritePattern` 少用"的理由：用 `MatchAnyOpTypeTag` 的 pattern 进不了任何一个具体桶，每个 op 都得试它一遍。）

## 通知机制：driver 和 pattern 之间的那条线

`PatternRewriter` 的每一个改 IR 的方法，背后都会发一条通知。driver 就是靠这些通知知道"该把谁重新入队"的——第 11 章那句"新 op 重新入队"，底层就是 `notifyOperationInserted`。

接口在 `mlir/include/mlir/IR/PatternMatch.h:370`（`RewriterBase::Listener`，继承自 `OpBuilder::Listener`），完整回调见图 14-1 右下。挂一个上去就能全部数出来：

```cpp-norun
struct CountingListener : public RewriterBase::Listener {
  int64_t inserted = 0, replaced = 0, erased = 0, modified = 0;
  int64_t patternsTried = 0, patternsWon = 0;

  void notifyOperationInserted(Operation *, OpBuilder::InsertPoint) override {
    ++inserted;
  }
  void notifyOperationReplaced(Operation *, ValueRange) override { ++replaced; }
  void notifyOperationErased(Operation *) override { ++erased; }
  void notifyOperationModified(Operation *) override { ++modified; }
  void notifyPatternBegin(const Pattern &, Operation *) override {
    ++patternsTried;
  }
  void notifyPatternEnd(const Pattern &, LogicalResult status) override {
    if (succeeded(status))
      ++patternsWon;
  }
};
```

回头看 `@self_add` 那串计数，每个数字都对得上一件具体的事：

| 计数 | 值 | 谁造成的 |
| --- | --- | --- |
| `inserted` | 2 | 新建的 `arith.constant` 和 `pix.scale` |
| `replaced` | 1 | `replaceOpWithNewOp` 把 `pix.add` 的结果换掉 |
| `erased` | 1 | 被换掉的 `pix.add` 随后被删 |
| `modified` | 1 | `func.return` 的操作数被改成新值 |
| `patterns_tried` | 1 | 高 benefit 那条一次就成了 |
| `patterns_won` | 1 | 同上 |

`modified = 1` 那一条特别说明问题：**我们没写任何代码去改 `func.return`**，是 `replaceOpWithNewOp` 顺着 def-use 链把用户全改了。这正是第 2 章那条 `OpOperand` 双向链表在干活。

<div class="warn">
<strong><code>InsertPoint</code> 要写全限定名</strong>
<p><code>notifyOperationInserted</code> 的第二个参数类型是 <code>OpBuilder::InsertPoint</code>（<code>Builders.h:329</code> 里是 <code>OpBuilder</code> 的嵌套类）。我照文档上的签名写了裸 <code>InsertPoint</code>，得到 <code>'InsertPoint' has not been declared</code> 外加一句 <code>marked 'override', but does not override</code>——后半句才是真正的线索：<strong>参数类型不对，就不是覆盖，而是新增了一个同名函数</strong>，编译器只在你写了 <code>override</code> 时才会提醒你。没写 <code>override</code> 的话，这会变成一个静默失效的回调。<strong>覆盖虚函数一律写 <code>override</code></strong>。</p>
</div>

## `--debug-only=greedy-rewriter`：读懂它的自述

前面那些计数告诉你"发生了多少次"，调试时你还想知道"具体在哪一步、为什么"。开断言的本地构建上：

```bash
pix-opt b14c.mlir --pix-rewrite-add --debug-only=greedy-rewriter
```

运行结果（`pix.add %a, %b` 那一段）：

```
[greedy-rewriter:1] Processing operation : 'pix.add'(0x59142ff5ad80) {
[greedy-rewriter:1]   %0 = "pix.add"(%arg0, %arg1) : (tensor<4x4xf32>, tensor<4x4xf32>) -> tensor<4x4xf32>
[greedy-rewriter:1]
[greedy-rewriter:1]   * Pattern mlir::pix::{anonymous}::AddSelfToScale : 'pix.add -> ()' {
[greedy-rewriter:1]     ** Match Failure : 两个操作数不是同一个值
[greedy-rewriter:1]   } -> failure : pattern failed to match
[greedy-rewriter:1]
[greedy-rewriter:1]   * Pattern mlir::pix::{anonymous}::AddSelfToMul : 'pix.add -> ()' {
[greedy-rewriter:1]     ** Match Failure : 两个操作数不是同一个值
[greedy-rewriter:1]   } -> failure : pattern failed to match
[greedy-rewriter:1] } -> failure : all patterns failed to match
```

三件事一次看全：**顺序**——`AddSelfToScale`（benefit 2）确实排在 `AddSelfToMul`（benefit 1）前面；**理由**——我们 `notifyMatchFailure` 里写的那句话原样出现在 `** Match Failure` 后面；**结论**——`all patterns failed to match`。

`'pix.add -> ()'` 这个记号是"根 op → 产出的 op 名"，我们没声明产出（可以用 ODS 或构造函数声明），所以是空的。声明了的话 driver 能做更多静态检查。

<div class="warn">
<strong>别用地址判断"是不是同一个 op"</strong>
<p>第 11 章那段 ping-pong 输出里，被 erase 的 <code>pix.add</code> 的地址立刻被新建的 op 复用了——MLIR 的分配器就是这么工作的。所以调试时看到两行相同的地址，<strong>不能</strong>推断它们是同一个 op。真要跟踪某个 op 的一生，用 <code>--mlir-print-ir-after-each-pattern</code> 之类看 IR 内容，或者在 Listener 里按内容记录，<strong>别记指针</strong>。<code>notifyOperationErased</code> 之后那个指针就是悬垂的，连打印都不安全。</p>
</div>

## 把引擎自己跑一遍

上面三个观察（成功即短路、按根 op 名分桶、benefit 降序）都可以在一个小模型里复现。下面 55 行的 driver 会打出和真 pix-opt **完全一致**的 tried/won 计数：

```python
# 一个 55 行的 greedy driver，这次把 benefit 排序、按根 op 名索引、
# 成功即短路、以及通知机制都放进来——对着第 14 章正文那几组实测看。

class Pattern:
    def __init__(self, name, root, benefit, rewrite):
        self.name, self.root, self.benefit, self.rewrite = name, root, benefit, rewrite

class Op:
    def __init__(self, name, operands=()):
        self.name, self.operands = name, list(operands)
    def __repr__(self): return f"{self.name}({', '.join(self.operands)})"

class Driver:
    def __init__(self, patterns):
        # 关键一步：按根 op 名分桶，桶内按 benefit **降序**。
        # 这两件事解释了正文里两个观察：无关 op 一条 pattern 都不会试；
        # benefit 高的先试。
        self.by_root = {}
        for p in patterns:
            self.by_root.setdefault(p.root, []).append(p)
        for bucket in self.by_root.values():
            bucket.sort(key=lambda p: -p.benefit)
        self.tried = self.won = self.inserted = self.replaced = 0

    def process(self, ops):
        worklist = list(range(len(ops)))
        while worklist:
            i = worklist.pop(0)
            op = ops[i]
            bucket = self.by_root.get(op.name, [])
            if not bucket:
                print(f"    {op.name}：没有以它为根的 pattern，一条都不试")
                continue
            for p in bucket:                       # 已按 benefit 降序
                self.tried += 1
                new = p.rewrite(op)
                if new is None:
                    print(f"    {op.name} ← {p.name}(benefit={p.benefit}) 匹配失败")
                    continue
                self.won += 1
                self.inserted += 1
                self.replaced += 1
                ops[i] = new
                print(f"    {op.name} ← {p.name}(benefit={p.benefit}) 成功 → {new}")
                print(f"       后面 benefit 更低的 {len(bucket) - bucket.index(p) - 1} 条**不再试**")
                worklist.append(i)                 # 新 op 重新入队
                break
        return ops

def add_self_to(target):
    def rewrite(op):
        if op.name != "pix.add" or len(set(op.operands)) != 1:
            return None
        return Op(target, [op.operands[0], "%two"])
    return rewrite

def build(swap):
    return [Pattern("AddSelfToScale", "pix.add", 1 if swap else 2, add_self_to("pix.scale")),
            Pattern("AddSelfToMul",   "pix.add", 2 if swap else 1, add_self_to("pix.mul"))]

for title, swap, ops in [
    ("默认：scale 的 benefit 高", False, [Op("pix.add", ["%x", "%x"])]),
    ("swap：mul 的 benefit 高",  True,  [Op("pix.add", ["%x", "%x"])]),
    ("操作数不同：两条都失败",    False, [Op("pix.add", ["%a", "%b"])]),
    ("没有 pix.add：一条都不试",  False, [Op("pix.mul", ["%x", "%x"])]),
]:
    d = Driver(build(swap))
    print(f"\n【{title}】")
    result = d.process(list(ops))
    print(f"  结果 IR：{result}")
    print(f"  tried={d.tried} won={d.won} inserted={d.inserted} replaced={d.replaced}")
```

运行结果：

       后面 benefit 更低的 1 条**不再试**
    pix.scale：没有以它为根的 pattern，一条都不试

## 收敛：这一章要补的最后一块

第 11 章讲过 `--canonicalize` 跑到不动点，也踩过互逆 pattern 挂死的坑。`applyPatternsGreedily` 用的是同一个 driver，所以同一条规矩适用：**你装的这套 pattern 也必须能收敛**。

`GreedyRewriteConfig` 上几个和收敛直接相关的旋钮，值得记住位置（`mlir/include/mlir/Transforms/GreedyPatternRewriteDriver.h`）：

| 旋钮 | 默认 | 作用 |
| --- | --- | --- |
| `maxIterations` | 10 | 外层轮次上限 |
| `maxNumRewrites` | 无上限 | **内层**改写次数上限。第 11 章挂死就因为它没上限 |
| `useTopDownTraversal` | false | 自底向上还是自顶向下遍历 |
| `setListener` | 无 | 本章用的那个口子 |

调试自己的 pattern 集时，**先把 `maxNumRewrites` 设成一个有限值**（比如 100），挂死就变成了"到上限退出"，比让进程卡住好查得多。第 13 章讲过 `--dump-pass-pipeline` 会把 `canonicalize` 的这些选项原样展开给你看，那里就能看到 `max-num-rewrites=-1`。

## 动手：给两条 pattern 声明"产出什么"

`OpRewritePattern` 的构造函数还能声明这条 pattern 会**产出**哪些 op：

```cpp-norun
AddSelfToScale(MLIRContext *ctx, PatternBenefit benefit)
    : OpRewritePattern<AddOp>(ctx, benefit,
                              /*generatedNames=*/{ScaleOp::getOperationName(),
                                                  arith::ConstantOp::getOperationName()}) {}
```

改完重编，再跑一遍 `--debug-only=greedy-rewriter`，看那行 `'pix.add -> ()'` 变成了什么。

**再改一处**：把 `AddSelfToMul` 的 benefit 也改成 2（和 `AddSelfToScale` 相同），然后反复跑 `--pix-rewrite-add`。结果是 `pix.scale` 还是 `pix.mul`？换个顺序 `patterns.add` 再试。**结论应该让你不敢再依赖相同 benefit 时的顺序**——这正是"该写 benefit 就写 benefit"的理由。

---

**这一章的要点**

- `OpRewritePattern<MyOp>` 是常规选择；要一次覆盖一批 op 用 `OpInterfaceRewritePattern`。裸 `RewritePattern` + `MatchAnyOpTypeTag` 少用——它进不了按根 op 名分的桶，每个 op 都得试一遍。
- **`benefit` 是决定性的，不是提示。** 高的先试，**成功了低的根本不会被试**（实测 `tried = 1` 而非 2）。相同 benefit 时顺序不确定，别依赖。
- **pattern 按根 op 名分桶索引**：一个 op 上没有对应的 pattern，一条都不问（实测 `tried = 0`）。所以大方言注册几百条 pattern，不会拖慢无关的 op。
- `matchAndRewrite` 里失败时用 **`return rewriter.notifyMatchFailure(op, "理由")`**。不多写一个字，但那句理由会出现在 `--debug-only=greedy-rewriter` 里；没有它你只能看到"failed to match"。
- **`RewriterBase::Listener`（`PatternMatch.h:370`）是把引擎变透明的那个口子。** `notifyOperationInserted/Replaced/Erased/Modified` 对应改 IR 的四类动作，`notifyPatternBegin/End` 数得出试了几条、赢了几条。driver 自己也是靠这些通知维护 worklist 的。
- 覆盖虚函数**一律写 `override`**。`notifyOperationInserted` 的参数是 `OpBuilder::InsertPoint`（嵌套类，要写全限定名）；类型写错而没有 `override` 的话，你得到的是一个静默失效的回调。
- **`replaceOpWithNewOp` 会顺着 def-use 链把所有使用者改掉**——实测 `modified = 1` 就是 `func.return` 被改了，我们一行相关代码都没写。
- **别用地址判断 op 身份**：被 erase 的内存会立刻被复用。`notifyOperationErased` 之后那个指针是悬垂的。
- 自己装的 pattern 集**同样要保证收敛**。调试时先把 `maxNumRewrites` 设成有限值，挂死就变成"到上限退出"。
- **挂在 op 上的 canonicalizer 是全局生效的；`applyPatternsGreedily` 装的这套只在本 pass 生效。** 要做"只在某个阶段才该发生"的改写，走后一条路。

**pix 进度**：新增 `pix-rewrite-add`（两条抢同一个 op 的 pattern + 一个计数 Listener + `swap` 选项）与 `rewrite_add.mlir`（两条 RUN 行做 benefit 对照，靠 `CHECK-SAME` 断言挂在函数头上的计数属性），`check-pix` 从 10 涨到 11 个文件。
