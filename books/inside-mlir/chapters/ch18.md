# 第 18 章 Transform 方言：把「怎么变换」本身写成 IR

## 这一章想让你带走什么

<div class="goal-box">
<p>到这里，pix 已经有了 pass、pattern、分析、conversion。但有一个问题一直没解决：<strong>"什么时候做哪个变换、用什么参数"这些决定写在哪？</strong></p>
<p>传统答案是硬编码进 pass 里——tile 大小写成常量或 pass option，先融合还是先向量化写成 pass 顺序。transform 方言给的答案完全不同：<strong>把调度本身写成一段 IR</strong>。第 15 章讲 PDLL 时我们见过这个思路的一半（pattern 成了 IR），transform 方言把它推到了调度层面。</p>
<p>这一章讲清三件事。<strong>一、handle/payload 模型</strong>：transform IR 操作的不是值，而是"指向被变换 IR 里某组 op 的名字"；理解这一点，才能理解那个几乎人人都会撞一次的错误——<strong>handle 失效</strong>。<strong>二、真的跑一遍</strong>：用 <code>transform.structured.tile_using_for</code> 把一个 <code>linalg.matmul</code> tile 成嵌套 <code>scf.for</code>，输出是实测的。<strong>三、和 pix 接上</strong>：用 <code>transform.apply_registered_pass</code> 从调度里驱动我们第 13 章写的那个 pass——于是"调度"和"pass 实现"彻底解耦。</p>
<p>顺带会撞一个很误导人的报错：<code>custom op 'transform.structured.match' is unknown</code>。它不是"版本里没这个 op"。</p>
</div>

## 先理解模型：handle 指向 op，不是值

transform 方言里有两套 IR 同时存在，别混：

| | 叫什么 | 是什么 |
| --- | --- | --- |
| 被变换的那个 | **payload** | 你真正要编译的代码（我们的 `func.func`、`linalg.matmul`、`pix.add`） |
| 做变换的那个 | **schedule** | 一段 `transform` 方言的 IR，描述"对 payload 做什么" |

schedule 里的 SSA 值**不是运行时的数据**，而是 **handle**——指向 payload 里某一组 op 的名字。类型也说明了这一点：

| 类型 | 指向什么 |
| --- | --- |
| `!transform.any_op` | 一组任意 op |
| `!transform.op<"linalg.matmul">` | 一组特定名字的 op（带静态检查） |
| `!transform.any_value` | 一组 payload 里的 Value |
| `!transform.param<i64>` | 一个编译期参数（比如 tile 大小），不指向 op |

一段最小的 schedule：

```mlir-norun
transform.named_sequence @__transform_main(%root: !transform.any_op {transform.readonly}) {
  // 匹配：从 %root 里找出所有 linalg.matmul，得到一个 handle
  %mm = transform.structured.match ops{["linalg.matmul"]} in %root
    : (!transform.any_op) -> !transform.any_op

  // 变换：tile 成 4x4。它**产出新的 handle**，而 %mm 从此失效
  %tiled, %loops:2 = transform.structured.tile_using_for %mm tile_sizes [4, 4]
    : (!transform.any_op) -> (!transform.any_op, !transform.any_op, !transform.any_op)

  transform.yield
}
```

`@__transform_main` 是 `--transform-interpreter` 默认找的入口名（可以用 `entry-point=` 改）。`{transform.readonly}` 声明这个 handle 只读——**这类声明是失效分析的依据**，下面就会用到。

## 真的跑一遍：tile 一个 matmul

payload 和 schedule 可以放在同一个 module 里（上游测试就这么写，省掉一个 `--transform-preload-library`），module 上要标 `transform.with_named_sequence`：

```mlir-lower
// RUN: mlir-opt %s --transform-interpreter
module attributes {transform.with_named_sequence} {
  func.func @mm(%a: tensor<8x8xf32>, %b: tensor<8x8xf32>, %c: tensor<8x8xf32>) -> tensor<8x8xf32> {
    %r = linalg.matmul ins(%a, %b : tensor<8x8xf32>, tensor<8x8xf32>)
                       outs(%c : tensor<8x8xf32>) -> tensor<8x8xf32>
    return %r : tensor<8x8xf32>
  }

  transform.named_sequence @__transform_main(%root: !transform.any_op {transform.readonly}) {
    %mm = transform.structured.match ops{["linalg.matmul"]} in %root
      : (!transform.any_op) -> !transform.any_op
    %tiled, %loops:2 = transform.structured.tile_using_for %mm tile_sizes [4, 4]
      : (!transform.any_op) -> (!transform.any_op, !transform.any_op, !transform.any_op)
    transform.yield
  }
}
```

运行结果（payload 部分）：

```
  func.func @mm(%arg0: tensor<8x8xf32>, %arg1: tensor<8x8xf32>, %arg2: tensor<8x8xf32>) -> tensor<8x8xf32> {
    %c0 = arith.constant 0 : index
    %c0_0 = arith.constant 0 : index
    %c8 = arith.constant 8 : index
    %c8_1 = arith.constant 8 : index
    %c4 = arith.constant 4 : index
    %c4_2 = arith.constant 4 : index
    %0 = scf.for %arg3 = %c0 to %c8 step %c4 iter_args(%arg4 = %arg2) -> (tensor<8x8xf32>) {
      %1 = scf.for %arg5 = %c0_0 to %c8_1 step %c4_2 iter_args(%arg6 = %arg4) -> (tensor<8x8xf32>) {
        %extracted_slice = tensor.extract_slice %arg0[%arg3, 0] [4, 8] [1, 1] : tensor<8x8xf32> to tensor<4x8xf32>
        %extracted_slice_3 = tensor.extract_slice %arg1[0, %arg5] [8, 4] [1, 1] : tensor<8x8xf32> to tensor<8x4xf32>
        %extracted_slice_4 = tensor.extract_slice %arg6[%arg3, %arg5] [4, 4] [1, 1] : tensor<8x8xf32> to tensor<4x4xf32>
        %2 = linalg.matmul ins(%extracted_slice, %extracted_slice_3 : tensor<4x8xf32>, tensor<8x4xf32>) outs(%extracted_slice_4 : tensor<4x4xf32>) -> tensor<4x4xf32>
        %inserted_slice = tensor.insert_slice %2 into %arg6[%arg3, %arg5] [4, 4] [1, 1] : tensor<4x4xf32> into tensor<8x8xf32>
        scf.yield %inserted_slice : tensor<8x8xf32>
      }
      scf.yield %1 : tensor<8x8xf32>
    }
    return %0 : tensor<8x8xf32>
  }
```

一行 `tile_sizes [4, 4]` 换来两层 `scf.for` 加 `tensor.extract_slice`/`insert_slice`，里面那个 `linalg.matmul` 缩成了 4×4。**注意最内层仍然是 `linalg.matmul`**——tiling 不改变语义，只是把它切小了，所以还能继续 tile、继续融合。这正是第 20 章要讲的"linalg 为什么好变换"。

要改 tile 大小，**改的是 IR，不是重新编译**。这就是 transform 方言的全部卖点。

<div class="warn">
<strong><code>custom op 'transform.structured.match' is unknown</code> —— 不是版本问题</strong>
<p>我在 <code>pix-opt</code> 上跑同样的脚本，得到这个报错。第一反应是"23.1 里这个 op 改名了？"——不是。</p>
<p>真相是：<strong>transform 方言的大部分 op 住在<em>扩展</em>里，不在方言本体里</strong>。<code>transform.structured.*</code> 由 linalg 的 transform 扩展提供，<code>transform.apply_registered_pass</code> 由核心扩展提供。<code>registerAllDialects(registry)</code> 注册不到它们，还要加一句：</p>
<p><code>mlir::registerAllExtensions(registry);</code></p>
<p>（CMake 那边链上 <code>MLIRRegisterAllExtensions</code>。）<code>mlir-opt</code> 自己当然是两句都有的，所以这个坑只在你写自己的驱动时才会撞上——而报错措辞完全不会提示你这一点。</p>
</div>

## handle 失效：几乎人人撞一次

上面那段 schedule 里，`tile_using_for` 产出了 `%tiled` 和两个 loop handle。**原来的 `%mm` 从此失效**——因为那个 `linalg.matmul` 已经被替换掉了，handle 指向的东西不存在了。

故意用一次旧 handle：

```mlir-norun
%tiled, %loops:2 = transform.structured.tile_using_for %mm tile_sizes [4, 4] : …
// %mm 已经失效，再用它：
%tiled2, %loops2:2 = transform.structured.tile_using_for %mm tile_sizes [2, 2] : …
```

运行结果：

```
inv18.mlir:14:26: error: op uses a handle invalidated by a previously executed transform op
    %tiled2, %loops2:2 = transform.structured.tile_using_for %mm tile_sizes [2, 2]
                         ^
inv18.mlir:8:11: note: handle to invalidated ops
    %mm = transform.structured.match ops{["linalg.matmul"]} in %root
          ^
```

这个诊断质量很高：**既指出用错的地方，也指出那个 handle 是哪来的**。（对比第 16、17 章 dialect conversion 那些挂在 `builtin.module` 上的报错，差距很明显——transform 方言在设计时就把"可诊断性"当成了目标。）

正确写法是一路用新 handle：

```mlir-norun
%tiled, %loops:2 = transform.structured.tile_using_for %mm tile_sizes [4, 4] : …
%tiled2, %loops2:2 = transform.structured.tile_using_for %tiled tile_sizes [2, 2] : …
```

<div class="keypoint">
<strong>handle 失效不是 bug，是设计</strong>
<p>为什么不让框架"自动更新" handle？因为**变换之后"原来那个 op"往往已经没有对应物了**。tile 之后，原 matmul 变成了两层循环加一个小 matmul——旧 handle 该指向哪个？没有正确答案。</p>
<p>所以 transform 方言选择：<strong>让失效变成一个显式的、可诊断的错误</strong>，而不是悄悄给你一个语义模糊的 handle。这和第 14 章那个"被 erase 的地址被复用"的坑正好相反——那里是悄悄出错，这里是当场报错。</p>
<p>实践上记一条：**每个变换 op 都要看清它产出哪些 handle，然后只用新的。** 想保住某个 handle 不失效，用 <code>transform.readonly</code> 之类的声明告诉框架"我不会改它"。</p>
</div>

## 把模型自己跑一遍

handle 为什么会失效，用一个小模型看最清楚。下面这个解释器把 payload 里的 op 标上 id，变换时把旧 id 标死，用 handle 前检查它指向的 id 还活着——**这正是真解释器做的事**：

```python
# transform 方言的 handle/payload 模型，以及 handle 为什么会失效。
# 一句话：handle 是"指向 payload 里一组 op 的名字"，而变换会**替换** op，
# 于是旧 handle 指向的东西不存在了。

class Payload:
    """被变换的 IR。这里简化成一个 op 列表，每个 op 有名字和唯一 id。"""
    def __init__(self, ops): self.ops = list(ops); self.dead = set()
    def alive(self, ids): return [i for i in ids if i not in self.dead]
    def replace(self, old_id, new_ops):
        self.dead.add(old_id)
        base = max(i for i, _ in self.ops) + 1
        new = [(base + k, n) for k, n in enumerate(new_ops)]
        self.ops += new
        return [i for i, _ in new]
    def show(self):
        return ", ".join(f"{n}#{i}" for i, n in self.ops if i not in self.dead)

class Interp:
    def __init__(self, payload): self.p, self.handles = payload, {}

    def match(self, name, want):
        ids = [i for i, n in self.p.ops if n == want and i not in self.p.dead]
        self.handles[name] = ids
        print(f"    {name} = match {want!r} → 指向 {ids}")

    def use(self, name):
        """用一个 handle 之前必须检查它指向的 op 还活着——这就是失效检查。"""
        ids = self.handles.get(name, [])
        dead = [i for i in ids if i in self.p.dead]
        if dead:
            raise RuntimeError(
                f"op uses a handle invalidated by a previously executed transform op\n"
                f"      （{name} 指向 {ids}，其中 {dead} 已被替换掉）")
        return ids

    def tile(self, src, out, sizes):
        ids = self.use(src)
        produced = []
        for i in ids:
            new = self.p.replace(i, ["scf.for", "scf.for", "linalg.matmul"])
            produced += new[-1:]
            print(f"    tile {src}(id={i}) sizes={sizes} → 换成 {new}，"
                  f"{src} 从此**失效**")
        self.handles[out] = produced
        print(f"    {out} = 新 handle → {produced}")

for title, script in [
    ("正确：tile 之后用新 handle", [("match", "%mm", "linalg.matmul"),
                                   ("tile", "%mm", "%tiled", [4, 4]),
                                   ("tile", "%tiled", "%tiled2", [2, 2])]),
    ("错误：tile 之后又用旧 handle", [("match", "%mm", "linalg.matmul"),
                                     ("tile", "%mm", "%tiled", [4, 4]),
                                     ("tile", "%mm", "%tiled2", [2, 2])]),
]:
    print(f"\n【{title}】")
    p = Payload([(0, "func.func"), (1, "linalg.matmul"), (2, "func.return")])
    it = Interp(p)
    try:
        for step in script:
            if step[0] == "match":
                it.match(step[1], step[2])
            else:
                it.tile(step[1], step[2], step[3])
        print(f"  → 成功。payload 现在是：{p.show()}")
    except RuntimeError as e:
        print(f"  → error: {e}")
```

运行结果：

```

【正确：tile 之后用新 handle】
    %mm = match 'linalg.matmul' → 指向 [1]
    tile %mm(id=1) sizes=[4, 4] → 换成 [3, 4, 5]，%mm 从此**失效**
    %tiled = 新 handle → [5]
    tile %tiled(id=5) sizes=[2, 2] → 换成 [6, 7, 8]，%tiled 从此**失效**
    %tiled2 = 新 handle → [8]
  → 成功。payload 现在是：func.func#0, func.return#2, scf.for#3, scf.for#4, scf.for#6, scf.for#7, linalg.matmul#8

【错误：tile 之后又用旧 handle】
    %mm = match 'linalg.matmul' → 指向 [1]
    tile %mm(id=1) sizes=[4, 4] → 换成 [3, 4, 5]，%mm 从此**失效**
    %tiled = 新 handle → [5]
  → error: op uses a handle invalidated by a previously executed transform op
      （%mm 指向 [1]，其中 [1] 已被替换掉）
```

两组的区别只有最后一步用了 `%mm` 还是 `%tiled`。注意成功那组的 payload：tile 两次之后有四个 `scf.for` 和一个 `linalg.matmul`，**每次 tile 都是对上一次的结果做的**。

## 和 pix 接上：从调度里驱动自己的 pass

`transform.structured.*` 那些 op 只认实现了 `TilingInterface` 的 op（`linalg` 那批），pix 的 op 还不行——那是第 20 章的事。但有一个 op 让 transform 脚本能驱动**任何已注册的 pass**：

```mlir-lower
// RUN: pix-opt %s --transform-interpreter
module attributes {transform.with_named_sequence} {
  func.func @driven_by_schedule(%a: tensor<4x4xf32>, %b: tensor<4x4xf32>) -> tensor<4x4xf32> {
    %r = pix.add %a, %b : tensor<4x4xf32>
    return %r : tensor<4x4xf32>
  }

  transform.named_sequence @__transform_main(%root: !transform.any_op {transform.readonly}) {
    %fns = transform.structured.match ops{["func.func"]} in %root
      : (!transform.any_op) -> !transform.any_op
    %after = transform.apply_registered_pass "pix-cost-report" to %fns
      : (!transform.any_op) -> !transform.any_op
    transform.yield
  }
}
```

运行结果（payload 部分）：

```
  func.func @driven_by_schedule(%arg0: tensor<4x4xf32>, %arg1: tensor<4x4xf32>) -> tensor<4x4xf32> attributes {pix.elements = 16 : i64, pix.num_ops = 1 : i64} {
    %0 = pix.add %arg0, %arg1 : tensor<4x4xf32>
    return %0 : tensor<4x4xf32>
  }
```

那两个属性证明第 13 章写的 `pix-cost-report` 真的跑了——**而且是被一段 IR 驱动的，不是命令行**。

`apply_registered_pass` 还能带选项（`with options = { "key" = value }`），值可以是属性、**也可以是 transform 的 param SSA 值**。后者意味着：pass 的参数可以在调度里算出来，甚至由外层搜索循环生成。这一步跨出去，"自动调优"就有了落脚点。

## 这套东西解决了什么真问题

值得停下来问一句：为什么要发明这么一套？

**第一，调度和实现解耦。** 传统写法里，"tile 成 32×32"这个决定埋在某个 pass 的常量里。换成 64×64 要改代码、重编译、重跑。transform 方言里它是 IR 里的一个字面量。

**第二，调度可以被生成和搜索。** IR 就是数据。一个自动调优器可以生成上千份 schedule，跑一遍挑最快的——这是 Halide 和 TVM 那条路线在 MLIR 里的落地方式。第 15 章说 PDLL 的价值在"pattern 能运行时加载"，是同一个道理的另一半。

**第三，可诊断。** 调度是 IR，所以它有位置信息、能打印、能验证、能被 `mlir-opt` 检查。对比一长串 `--pass-pipeline='...'` 字符串——那个东西错一个括号，报错完全没法读。

**代价也要说清楚**：多了一层要学的东西；`transform.structured.*` 只覆盖 linalg/tensor 那套结构化 op，自己的方言要接进去得实现 `TilingInterface` 这类接口（第 20、21 章会做）；而且这套 API 还在动。上游文档自己也说得很直白——它是"面向调度专家"的工具，不是所有人都需要。

## 动手：把 tile 大小做成参数

schedule 里的 tile 大小可以不是字面量，而是一个 `!transform.param<i64>`：

```mlir-norun
%sz = transform.param.constant 4 : i64 -> !transform.param<i64>
%tiled, %loops:2 = transform.structured.tile_using_for %mm tile_sizes [%sz, %sz]
  : (!transform.any_op, !transform.param<i64>, !transform.param<i64>)
    -> (!transform.any_op, !transform.any_op, !transform.any_op)
```

改成 2、8、16 各跑一次，对比生成的 `scf.for` 的 `step`。**这一步是自动调优的雏形**：把这个 param 换成由外层逻辑生成的值，你就有了一个搜索空间。

**再改一处**：在 tile 之后加一句

```mlir-norun
transform.print %tiled {name = "tiled op"} : !transform.any_op
```

它会把 handle 指向的 op 打到 stderr。这是调 schedule 时最直接的工具——**transform 方言的调试手段就是往 IR 里插打印 op**，因为调度本身就是 IR。

---

**这一章的要点**

- **两套 IR 同时存在**：payload（你要编译的代码）和 schedule（transform 方言的 IR）。schedule 里的 SSA 值是 **handle**，指向 payload 里的一组 op，不是数据。
- 类型分工清楚：`!transform.any_op` / `!transform.op<"name">` 指 op，`!transform.any_value` 指 Value，`!transform.param<T>` 是编译期参数（**不指向 op**）。
- **handle 失效是设计，不是 bug**。变换会替换 op，旧 handle 没有唯一对应物，自动更新只会给出语义模糊的结果。所以：**看清每个变换 op 产出哪些新 handle，然后只用新的**。
- 那个报错质量很高——同时指出用错的位置**和 handle 的定义处**。transform 方言把可诊断性当成设计目标，这一点和 dialect conversion 形成鲜明对比。
- **`custom op 'transform.structured.match' is unknown` 不是版本问题**：transform 方言的大部分 op 住在**扩展**里。自己写驱动时除了 `registerAllDialects` 还要 `registerAllExtensions`（CMake 链 `MLIRRegisterAllExtensions`）。`mlir-opt` 自带两句，所以这坑只在你写自己的工具时出现。
- **tiling 不改变语义**：tile 之后最内层仍是 `linalg.matmul`，所以能继续 tile、继续融合。这是第 20 章"linalg 为什么好变换"的伏笔。
- **`transform.apply_registered_pass` 是接入自己方言的最短路径**：任何已注册的 pass 都能被调度驱动，选项值还能是 transform 的 param SSA 值——pass 参数可以在调度里算出来。
- 三个真实收益：**调度与实现解耦**（改 IR 不改代码）、**调度可被生成与搜索**（自动调优的落脚点）、**可诊断**（调度是 IR，有位置、能打印、能验证）。代价是多一层概念，且 `transform.structured.*` 目前只覆盖结构化 op。
- 调 schedule 的第一个工具是 `transform.print`——**往 IR 里插打印 op**，因为调度本身就是 IR。

**pix 进度**：`pix-opt` 补上 `registerAllExtensions`，于是它也能当 transform 方言的驱动器用。新增 `transform.mlir`：一段 schedule 用 `transform.apply_registered_pass` 驱动第 13 章那个 `pix-cost-report`，属性值证明它真的跑了。`check-pix` 从 14 涨到 15 个文件。

第三部分最后一章讲**分析与副作用**。第 13 章我们写过一个分析，但那是自己遍历数出来的；这一章看 MLIR 自带的那几个：`DominanceInfo`、`MemoryEffects`（很多变换的前提——没有它，编译器不敢动任何可能碰内存的东西），以及稀疏数据流分析框架 `DataFlowSolver`。
