# 第 11 章 fold 与 canonicalize：常量折叠、恒等化简与收敛

## 这一章想让你带走什么

<div class="goal-box">
<p>上一章把"不该出现的 IR"挡在门外。这一章反过来：把"能出现但没必要出现"的 IR 化简掉——加一张全零图、乘以系数 1、连续两次转置、对一张常量图求和。</p>
<p>MLIR 给了<strong>两个</strong>口子做这件事，而分界线只有一条，异常清晰：<strong>结果里需要新造 op 吗？</strong>不需要就写 <code>fold()</code>，需要就写 canonicalize pattern。想明白这一条，"该写哪个"就不再是问题。</p>
<p>另外三件事是这一章真正的收获，都是这次给 pix 写化简时<strong>实打实撞出来的</strong>：<code>fold()</code> 返回 Attribute 之后还差一步"落地"，少了它<strong>折叠会静默失效</strong>；pattern 要造别的方言的 op，方言必须声明依赖，否则<strong>直接 abort 而不是报诊断</strong>；以及最经典的那个坑——两条互逆的规则凑在一起，<code>--canonicalize</code> 不会报"没收敛"，它会<strong>挂死</strong>，而 <code>maxIterations = 10</code> 救不了你。</p>
</div>

## 先分清两件事

新手最容易卡在"我该写 `fold` 还是写 pattern"。判据只有一条：

| | `fold()` | canonicalize pattern |
| --- | --- | --- |
| ODS 开关 | `let hasFolder = 1;` | `let hasCanonicalizer = 1;` |
| 能不能造新 op | **不能** | 能 |
| 签名 | `OpFoldResult fold(FoldAdaptor)` | `LogicalResult matchAndRewrite(Op, PatternRewriter &)` |
| 看得到什么 | 本 op + 操作数的常量值 | 整个 IR，想往上下游走多远都行 |
| 谁会调用它 | `--canonicalize`、dialect conversion、`createOrFold`，以及各种 pass 顺手调 | `--canonicalize`，和显式装了这批 pattern 的 pass |
| 典型用途 | 恒等化简、常量折叠 | 改写结构、合并相邻 op、引入新 op |

最后两行值得多看一眼：**`fold` 的适用面比 pattern 广得多**——dialect conversion（第 16 章）在合法化过程中会调它，`OpBuilder::createOrFold` 在构造 IR 时就地调它。所以**能写成 `fold` 的就别写成 pattern**，白赚一堆调用点。而它"不许造 op"的限制是硬的，不是建议：有些调用它的地方根本没有 `OpBuilder` 可用。

## fold：`OpFoldResult` 的两种返回

返回类型一眼就说清了它能做什么。`mlir/include/mlir/IR/OpDefinition.h:273`：

```cpp-norun
class OpFoldResult : public PointerUnion<Attribute, Value> {
```

一个 `Attribute` 或一个 `Value` 的联合，加上"空"。三种可能，对应三句话：给 **`Value`**——「这个 op 其实等于那边那个已经存在的值」；给 **`Attribute`**——「我在编译期把答案算出来了」；给**空**——「折不动，别管我」。

### 返回一个已经存在的值

pix 里有三处：加全零图、乘系数 1、双重转置。ODS 那边只是开个开关：

```tablegen
def Pix_AddOp : Pix_Op<"add", [Pure, Commutative, SameOperandsAndResultType]> {
  // …
  let hasFolder = 1;        // 加一张全零图等于没加
  let hasCanonicalizer = 1; // add %x, %x → scale %x, 2.0（下一节）
}

def Pix_TransposeOp : Pix_Op<"transpose", [Pure]> {
  // …
  let hasVerifier = 1;      // 第 10 章：形状必须互为转置
  let hasFolder = 1;        // transpose(transpose(%x)) → %x
}
```

实现：

```cpp-norun
OpFoldResult AddOp::fold(FoldAdaptor adaptor) {
  auto isZeroImage = [](Attribute attr) {
    auto dense = dyn_cast_or_null<DenseFPElementsAttr>(attr);
    return dense && dense.isSplat() &&
           dense.getSplatValue<APFloat>().isZero();
  };
  if (isZeroImage(adaptor.getRhs()))
    return getLhs();
  if (isZeroImage(adaptor.getLhs()))
    return getRhs();
  return {};
}
```

三个细节，都藏在这十行里。**`adaptor` 给的是常量，不是值**：`adaptor.getRhs()` 的类型是 `Attribute`，右操作数是常量就给你属性，否则给 null——这正是 `fold` 不需要 `OpBuilder` 也能干活的原因，它要的信息已经被嚼碎喂过来了。因此要用 **`dyn_cast_or_null`**，`dyn_cast` 会在 null 上断言失败。最后，**`Commutative` 不会帮你把常量挪到右边**：那个 trait 只声明"两个操作数可交换"，把常量规范到右侧是 arith 自己写的 pattern 干的事。所以两边都得查——我一开始只查了右边，`pix.add %zero, %img` 就漏了。

双重转置要看"操作数是谁产生的"，`adaptor` 帮不上忙（它只管常量），直接顺 def-use 链问一句：

```cpp-norun
OpFoldResult TransposeOp::fold(FoldAdaptor adaptor) {
  auto inner = getImage().getDefiningOp<TransposeOp>();
  if (!inner)
    return {};
  // 防身：形状真的绕回来了才抵消。verifier 已保证每层都是逆序，
  // 但 fold 不该依赖"别人一定验过"这种假设。
  if (inner.getImage().getType() != getResult().getType())
    return {};
  return inner.getImage();
}
```

跑一下（`pix.scale` 系数为 1 的那条同理，实现就是查 `FloatAttr` 是否 `isExactlyValue(1.0)`）：

```mlir-lower
// RUN: pix-opt %s --canonicalize
func.func @add_zero(%img: tensor<4x4xf32>) -> tensor<4x4xf32> {
  %zero = arith.constant dense<0.0> : tensor<4x4xf32>
  %r = pix.add %img, %zero : tensor<4x4xf32>
  return %r : tensor<4x4xf32>
}

func.func @double_transpose(%img: tensor<4x8xf32>) -> tensor<4x8xf32> {
  %t1 = pix.transpose %img : tensor<4x8xf32> to tensor<8x4xf32>
  %t2 = pix.transpose %t1 : tensor<8x4xf32> to tensor<4x8xf32>
  return %t2 : tensor<4x8xf32>
}
```

运行结果：

```
module {
  func.func @add_zero(%arg0: tensor<4x4xf32>) -> tensor<4x4xf32> {
    return %arg0 : tensor<4x4xf32>
  }
  func.func @double_transpose(%arg0: tensor<4x8xf32>) -> tensor<4x8xf32> {
    return %arg0 : tensor<4x8xf32>
  }
}
```

两个函数都塌成一句 `return %arg0`。注意那个 `arith.constant` 也跟着没了——我们一行清理代码都没写，是 `Pure`（第 5 章）让通用的 DCE 敢删掉没人用的它。**声明换来的红利，又一次。**

### 返回一个算出来的 Attribute

这才是"常量折叠"的本义：`pix.reduce` 对一张常量图求和，编译期就得出标量。

```cpp-norun
OpFoldResult ReduceOp::fold(FoldAdaptor adaptor) {
  auto dense = dyn_cast_or_null<DenseFPElementsAttr>(adaptor.getImage());
  if (!dense)
    return {};

  // splat（所有元素相同）直接乘，省得遍历几十万个元素。
  APFloat sum(0.0f);
  if (dense.isSplat()) {
    APFloat v = dense.getSplatValue<APFloat>();
    sum = v * APFloat(static_cast<float>(dense.getNumElements()));
  } else {
    for (APFloat v : dense.getValues<APFloat>())
      sum = sum + v;
  }
  return FloatAttr::get(getResult().getType(), sum);
}
```

`isSplat()` 那个分支不是炫技。`dense<0.0> : tensor<1024x1024xf32>` 在内存里只存一个元素（第 4 章讲过 `DenseElementsAttr` 的 splat 优化），照 `getNumElements()` 遍历一百万次纯属自找。**折叠代码跑在编译期，它自己的复杂度就是编译时间的一部分。**

### 踩坑实录：折出来了，却没生效

写完上面那段我跑了一遍，`pix.reduce` **一动不动**——没有报错，没有警告，IR 原样输出。断点打进 `fold()`，它确实返回了正确的 `FloatAttr`。

问题在**下一步**。`fold` 交出一个 Attribute，框架要把它变成一条真的 op 才能替换原来的 op，而"怎么把 Attribute 变成 op"只有方言自己知道。这个钩子在 `mlir/include/mlir/IR/Dialect.h:83`：

```cpp-norun
virtual Operation *materializeConstant(OpBuilder &builder, Attribute value,
                                       Type type, Location loc) {
  return nullptr;
}
```

默认返回 `nullptr`，意思是"我落不了这个常量"。框架于是**放弃那次折叠**——它不能崩，也没什么可报的，就当没发生。于是你看到一个完全正常、却什么都没做的 `fold`。补上开关和实现：

```tablegen
def Pix_Dialect : Dialect {
  // …
  let hasConstantMaterializer = 1;
}
```

```cpp-norun
Operation *PixDialect::materializeConstant(OpBuilder &builder, Attribute value,
                                           Type type, Location loc) {
  auto typed = dyn_cast<TypedAttr>(value);
  if (!typed || typed.getType() != type)
    return nullptr;
  if (!isa<FloatType>(type))
    return nullptr;
  return arith::ConstantOp::create(builder, loc, typed);
}
```

pix 没有自己的标量常量 op，就借 `arith.constant` 落地。上游 arith 的实现在 `mlir/lib/Dialect/Arith/IR/ArithDialect.cpp:65`，长得差不多。再跑：

```mlir-lower
// RUN: pix-opt %s --canonicalize
func.func @reduce_splat() -> f32 {
  %img = arith.constant dense<2.5> : tensor<4x4xf32>
  %s = pix.reduce %img : tensor<4x4xf32> -> f32
  return %s : f32
}
```

运行结果：

```
module {
  func.func @reduce_splat() -> f32 {
    %cst = arith.constant 4.000000e+01 : f32
    return %cst : f32
  }
}
```

2.5 × 16 = 40，整张图消失了。逐元素那条路（`dense<[[1.0, 2.0], [3.0, 4.0]]>` 折成 10）由 `canonicalize.mlir` 里的 `reduce_dense` 守着。

<div class="warn">
<strong>返回 Attribute 的 fold 要配一个 materializeConstant</strong>
<p>这条值得单独记住：<strong>方言里只要有任何一个 <code>fold</code> 会返回 Attribute，就必须实现 <code>materializeConstant</code></strong>。少了它不会编译失败、不会运行时报错、不会有诊断，只是折叠悄悄作废——排查要一路跟到框架内部才看得见。反过来，如果你的 fold 全都只返回已有的 <code>Value</code>（像本章前半段那几个），就不需要这个钩子。</p>
</div>

## canonicalize：要造新 op，就只能走这条

pix 里有两条化简过不了"不许造 op"那道门：`scale(scale(%x, a), b)` → `scale(%x, a*b)`（多一个乘法），以及 `add(%x, %x)` → `scale(%x, 2.0)`（多一个常量）。只能写成 pattern：

```cpp-norun
// scale(scale(%x, a), b) → scale(%x, a * b)
struct MergeNestedScale : OpRewritePattern<ScaleOp> {
  using OpRewritePattern::OpRewritePattern;

  LogicalResult matchAndRewrite(ScaleOp op,
                                PatternRewriter &rewriter) const override {
    auto inner = op.getImage().getDefiningOp<ScaleOp>();
    if (!inner)
      return failure();

    Value merged = arith::MulFOp::create(rewriter, op.getLoc(),
                                        inner.getFactor(), op.getFactor());
    rewriter.replaceOpWithNewOp<ScaleOp>(op, inner.getImage(), merged);
    return success();
  }
};

void ScaleOp::getCanonicalizationPatterns(RewritePatternSet &patterns,
                                          MLIRContext *context) {
  patterns.add<MergeNestedScale>(context);
}
```

注册函数的签名照 `mlir/lib/Dialect/Arith/IR/ArithOps.cpp:439` 那个样子写就行。

<div class="warn">
<strong>造 op 的写法在基线 23.1 变了</strong>
<p>上面写的是 <code>arith::MulFOp::create(rewriter, loc, …)</code>。你在网上、在老书里看到的几乎都是 <code>rewriter.create&lt;arith::MulFOp&gt;(loc, …)</code>——那个写法在 23.1 的 <code>mlir/lib</code> 里已经<strong>一处都不剩</strong>（我数过：<code>rewriter.create&lt;</code> 与 <code>builder.create&lt;</code> 各 0 次，<code>OpTy::create(</code> 共 8445 次）。照老写法抄不一定编不过，但你会和整棵树的风格对不上。和第 10 章那个 <code>RegionSuccessor</code> 是同一类事：<strong>照你手上那份源码写，别照记忆写。</strong></p>
</div>

### 跨方言接力：arith 替我们把 2.0 × 3.0 折了

注意 `MergeNestedScale` 里**没有**检查 `a`、`b` 是不是常量，直接造了个 `arith.mulf`。这是故意的：

```mlir-lower
// RUN: pix-opt %s --canonicalize
func.func @nested_scale(%img: tensor<4x4xf32>) -> tensor<4x4xf32> {
  %a = arith.constant 2.0 : f32
  %b = arith.constant 3.0 : f32
  %s1 = pix.scale %img, %a : tensor<4x4xf32>
  %s2 = pix.scale %s1, %b : tensor<4x4xf32>
  return %s2 : tensor<4x4xf32>
}
```

运行结果：

```
module {
  func.func @nested_scale(%arg0: tensor<4x4xf32>) -> tensor<4x4xf32> {
    %cst = arith.constant 6.000000e+00 : f32
    %0 = pix.scale %arg0, %cst : tensor<4x4xf32>
    return %0 : tensor<4x4xf32>
  }
}
```

我们造的 `arith.mulf` 不见了，位置上是 `6.000000e+00`。**我们没写一行常量折叠的乘法代码**——arith 自己的 folder 在同一轮 `--canonicalize` 里把它折成了 6.0。把两个系数换成函数参数再跑，`arith.mulf` 就老实留在那儿（`canonicalize.mlir` 里的 `nested_scale_dynamic` 守着这条）。

这就是渐进式化简的样子：**每个方言只管好自己那一摊，凑在一起自动接力，谁都不用认识谁。** 如果我在 pattern 里非要自己判断常量、自己算乘积，代码更长，而且只覆盖常量这一种情况。

### 踩坑实录：`created with unregistered dialect`

第二条 pattern 要造一个 `arith.constant`。写完自测，前面那些例子都好；换一个输入就炸了：

```bash
$ cat loop.mlir
func.func @boom(%img: tensor<4x4xf32>) -> tensor<4x4xf32> {
  %r = pix.add %img, %img : tensor<4x4xf32>
  return %r : tensor<4x4xf32>
}

$ pix-opt loop.mlir --canonicalize
LLVM ERROR: arith.constant created with unregistered dialect. If this is intended,
please call allowUnregisteredDialects() on the MLIRContext, or use
-allow-unregistered-dialect with the MLIR tool used.
PLEASE submit a bug report to https://github.com/llvm/llvm-project/issues/
```

注意它**不是诊断**——是 `LLVM ERROR` 加 abort，直接把进程带走。

为什么前面的例子好好的？因为那些输入里**本来就有 `arith.constant`**，解析器读到它时顺手把 arith 加载进了 `MLIRContext`。这个 `loop.mlir` 一个 arith op 都没有，pattern 想创建时 arith 根本没被加载。**这个 bug 的欺骗性就在这里：它取决于输入 IR 长什么样。** 你的测试可能全绿，用户的第一个文件就炸。

正解是在方言上声明依赖：

```tablegen
def Pix_Dialect : Dialect {
  // …
  // 想创建某个方言的 op，那个方言必须已经加载进 MLIRContext。
  let dependentDialects = ["::mlir::arith::ArithDialect"];
}
```

改完重编，会撞上第二个错误：`PixOpsDialect.cpp.inc:18:37: error: 'arith' is not a member of 'mlir'`。因为生成的 `.cpp.inc` 里多了一句 `loadDialect<::mlir::arith::ArithDialect>()`，而 `PixDialect.cpp` 没 include arith 的头——把 `#include "mlir/Dialect/Arith/IR/Arith.h"` 放到 include 生成代码**之前**即可。CMake 那边也要给 `LINK_LIBS` 加上 `MLIRArithDialect`。

<div class="keypoint">
<strong>一条界线：解析别人的 op 不用依赖，创建别人的 op 才要。</strong>
<p><code>pix-opt</code> 一直能<strong>读</strong> <code>arith.constant</code>，那是因为驱动里调了 <code>registerAllDialects</code>。但"<code>pix</code> 这个方言自己会造 arith 的 op"是另一回事，必须由方言声明 <code>dependentDialects</code>——它保证的是"只要谁加载了 pix，arith 就一定也在"。第 16 章写 conversion pattern 时你会反复用到它，那里造的 op 更多。</p>
</div>

## 不动点与那个经典陷阱

`--canonicalize` 不是"把每条规则跑一遍"，而是**反复跑到 IR 不再变化**。驱动在 `mlir/lib/Transforms/Utils/GreedyPatternRewriteDriver.cpp`，两层循环：**外层**一轮一轮扫，上限 `maxIterations`，默认 **10**（`mlir/include/mlir/Transforms/GreedyPatternRewriteDriver.h:169`）；**内层** `processWorklist()` 从 worklist 取 op、试所有匹配的 pattern、成功就把受影响的 op 重新入队，注释写得很直白：*"Process ops until the worklist is empty or `config.maxNumRewrites` is reached."*

现在做那个经典实验。我们已有 A：`add %x, %x → scale %x, 2.0`。再写一条反向的 B：

```cpp-norun
// 千万别真注册这条。（匹配"系数是常量 2.0"那几行省略）
struct ScaleTwoToAdd : OpRewritePattern<ScaleOp> {
  using OpRewritePattern::OpRewritePattern;
  LogicalResult matchAndRewrite(ScaleOp op,
                                PatternRewriter &rewriter) const override {
    // …确认 op.getFactor() 是常量 2.0，否则 return failure();
    rewriter.replaceOpWithNewOp<AddOp>(op, op.getImage(), op.getImage());
    return success();
  }
};
```

两条都注册，喂一个 `pix.add %img, %img`。你可能期待一句"pattern 没收敛"的警告。实际发生的是：

```bash
$ pix-opt loop.mlir --canonicalize
# 没有输出。没有报错。进程再也不返回。
```

**它挂死了。** 为什么 `maxIterations = 10` 没兜住？因为那是**外层**的上限，而这场 ping-pong 发生在**内层** worklist 里：A 改完，新的 `pix.scale` 入队；B 把它改回 `pix.add`，又入队；worklist 永远不空，`processWorklist()` 永远不返回，外层那个计数器一次都轮不到。而内层唯一的刹车 `maxNumRewrites` 默认是 `kNoLimit`。

这句话有点绕，不如把那两层循环剥出来自己跑一遍。下面这个模型只有 40 行，结构和真驱动一一对应——点运行，然后试着改 `max_num_rewrites`、或者把 `diverging` 里的 B 去掉：

```python
# 一个 40 行的 greedy driver 模型，两层循环和 MLIR 里那两层一一对应。
# IR 简化成一串 op 名；pattern 就是"看到什么、换成什么"。

def run(patterns, ir, max_iterations=10, max_num_rewrites=None, trace_limit=6):
    """返回 (最终 IR, 结束原因)。max_num_rewrites=None 表示无上限（MLIR 的默认）。"""
    rewrites = 0
    for iteration in range(1, max_iterations + 1):
        worklist = list(range(len(ir)))          # 本轮要处理的 op 下标
        changed_this_iteration = False
        while worklist:                          # ← 内层：processWorklist()
            i = worklist.pop(0)
            if i >= len(ir):
                continue
            for name, (src, dst) in patterns.items():
                if ir[i] == src:
                    ir[i] = dst
                    rewrites += 1
                    if rewrites <= trace_limit:
                        print(f"  第 {rewrites:2d} 次改写  {name}: {src} -> {dst}")
                    worklist.append(i)           # 新 op 重新入队
                    changed_this_iteration = True
                    break
            if max_num_rewrites is not None and rewrites >= max_num_rewrites:
                return ir, f"内层撞上 max_num_rewrites={max_num_rewrites}"
            if rewrites > trace_limit + 200:     # 只为了让浏览器别卡死
                return ir, "worklist 永远排不空（真实 MLIR 会一直挂在这里）"
        if not changed_this_iteration:
            return ir, f"第 {iteration} 轮没有任何改动 —— 到达不动点"
    return ir, f"外层撞上 max_iterations={max_iterations}"

converging = {"A": ("add", "scale")}                                   # 单向
diverging  = {"A": ("add", "scale"), "B": ("scale", "add")}             # 互逆

print("【一】只注册 A：add -> scale")
ir, why = run(converging, ["add"])
print(f"  IR = {ir}\n  结束原因：{why}\n")

print("【二】A 和 B 都注册（互逆）")
ir, why = run(diverging, ["add"])
print(f"  IR = {ir}\n  结束原因：{why}")
print("  注意：max_iterations=10 一次都没轮到 —— 外层的刹车管不住内层的 worklist。\n")

print("【三】同样两条规则，但给内层设上限（MLIR 的 maxNumRewrites）")
ir, why = run(diverging, ["add"], max_num_rewrites=5)
print(f"  IR = {ir}\n  结束原因：{why}")
```

运行结果：

```
【一】只注册 A：add -> scale
  第  1 次改写  A: add -> scale
  IR = ['scale']
  结束原因：第 2 轮没有任何改动 —— 到达不动点

【二】A 和 B 都注册（互逆）
  第  1 次改写  A: add -> scale
  第  2 次改写  B: scale -> add
  第  3 次改写  A: add -> scale
  第  4 次改写  B: scale -> add
  第  5 次改写  A: add -> scale
  第  6 次改写  B: scale -> add
  IR = ['scale']
  结束原因：worklist 永远排不空（真实 MLIR 会一直挂在这里）
  注意：max_iterations=10 一次都没轮到 —— 外层的刹车管不住内层的 worklist。

【三】同样两条规则，但给内层设上限（MLIR 的 maxNumRewrites）
  第  1 次改写  A: add -> scale
  第  2 次改写  B: scale -> add
  第  3 次改写  A: add -> scale
  第  4 次改写  B: scale -> add
  第  5 次改写  A: add -> scale
  IR = ['scale']
  结束原因：内层撞上 max_num_rewrites=5
```

【二】里那个"永远排不空"是模型为了不卡死浏览器加的护栏；真的 `pix-opt` 没有这道护栏，所以它就停在那儿了。

想看真家伙在干什么，在开断言的本地构建上加个调试开关：

```bash
pix-opt loop.mlir --canonicalize --debug-only=greedy-rewriter
```

<div class="keypoint">
<strong>一条规则往哪个方向写，是设计决定，不是口味问题。</strong>
<p>A 和 B 在数学上等价，但只有一个方向能当 canonicalize：<strong>规范化必须有方向，而且全体规则要能定出一个"越走越简单"的序。</strong>判断方法很朴素——问自己"反复应用这条规则，IR 会不会停下来？"以及"它和别人合起来会不会停下来？"</p>
<p>真的需要双向怎么办（比如一个方向利于向量化、另一个利于 GPU）？<strong>别放进 canonicalize</strong>，写成独立的 pass 或显式 pattern 集，由管线决定何时用哪个。canonicalize 是所有人共享的公共设施，只该放无争议的方向。第 14 章讲怎么装自己的 pattern 集，第 18 章的 transform 方言更进一步——把"什么时候用哪条规则"本身写成 IR。</p>
</div>

## 动手：给 `pix.mul` 加两条化简

`pix.mul` 现在一条化简都没有，而它有两个明显的机会，都走 fold，但返回的东西不同：`mul(%x, 全一图)` → `%x`（返回**已有的值**），`mul(%x, 全零图)` → 全零图（返回**一个 Attribute**）。

给 `Pix_MulOp` 加 `let hasFolder = 1;`，然后照 `AddOp::fold` 的样子写。第 2 条有个岔子值得你亲自撞一下：它返回的是 `DenseFPElementsAttr`（tensor 类型），而我们的 `materializeConstant` 只认 `FloatType`——**第 1 条会立刻生效，第 2 条会静默失效**，正是本章那个坑。你得把钩子放宽才行。

```bash
MLIR_DIR=$LLVM/build/lib/cmake/mlir books/inside-mlir/verify/verify-pix.sh
pix-opt /tmp/mul.mlir --canonicalize    # 输入：pix.mul %img, dense<1.0>
```

预期结果：

```
module {
  func.func @mul_one(%arg0: tensor<4x4xf32>) -> tensor<4x4xf32> {
    return %arg0 : tensor<4x4xf32>
  }
}
```

**再改一处**：把 `MergeNestedScale` 的方向反过来（把一层 `scale` 拆成两层），注册上去跑 `--canonicalize`，亲眼看它挂死，再加 `--debug-only=greedy-rewriter` 看 ping-pong。看完记得改回来——`check-pix` 会因为超时而挂。

---

**这一章的要点**

- 分界线只有一条：**结果里需要新造 op 吗？** 不需要 → `fold()`；需要 → canonicalize pattern。
- **能写成 `fold` 的别写成 pattern**：它的调用点多得多——`--canonicalize`、dialect conversion 的合法化、`OpBuilder::createOrFold`。代价是不许造 op，因为有些调用点根本没有 `OpBuilder`。
- `OpFoldResult` 就是 `PointerUnion<Attribute, Value>`（`mlir/include/mlir/IR/OpDefinition.h:273`）。`FoldAdaptor` 喂给你的是**操作数的常量属性**（不是常量就是 null，用 `dyn_cast_or_null`）；要看"操作数是谁产生的"，自己走 `getDefiningOp<T>()`。
- **返回 Attribute 的 fold 必须配 `materializeConstant`**（`hasConstantMaterializer` + `Dialect.h:83`）。少了它没有任何报错，折叠**静默作废**——这一章最值钱的一条。
- **创建别的方言的 op，要声明 `dependentDialects`**。漏了它只在"输入 IR 里恰好没有那个方言"时才炸，而且是 `LLVM ERROR` + abort，不是诊断。解析不需要，创建才需要。
- 让化简**自动接力**：造 `arith.mulf` 而不是自己判断常量，arith 的 folder 会替你折。每个方言管好自己那一摊，凑起来比谁都聪明。
- `--canonicalize` 跑到**不动点**，两层上限：外层 `maxIterations` 默认 10，内层 `processWorklist` 的 `maxNumRewrites` 默认**无上限**。所以**互逆的 pattern 不会得到"没收敛"的警告，而是直接挂死**。规则必须有方向；真需要双向的，写成独立 pass 或显式 pattern 集。
- 基线 23.1 里 `rewriter.create<OpTy>(…)` 已被 `OpTy::create(rewriter, …)` 全面替换（`mlir/lib` 下前者 0 次、后者 8445 次）。

**pix 进度**：四个 op 有了化简——`add`（零图恒等 + `add %x,%x → scale`）、`scale`（系数 1 恒等 + 嵌套合并）、`transpose`（双重抵消）、`reduce`（常量图求和）。方言层面补上 `dependentDialects` 与 `materializeConstant` 两个声明。新增 `canonicalize.mlir`，16 个用例覆盖"该折的折了"和"不该动的没动"两侧，`check-pix` 6 个测试全绿。

下一章把 pix **收尾成一个能交付的项目**：补齐剩下的 op、把 `pix-opt` 的注册和诊断整理干净、把 lit 测试目录按上游惯例摆好，`ninja check-pix` 一条命令跑全套。第二部分到那里结束——你会有一个从零长出来、有类型有属性有 verifier 有化简有测试的完整方言，第三部分开始在它身上做真正的变换。
