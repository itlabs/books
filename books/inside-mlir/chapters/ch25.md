# 第 25 章 落到 GPU：gpu 方言、kernel outlining 与三个出口

## 这一章想让你带走什么

<div class="goal-box">
<p>第四部分最后一章。第 24 章把 pix 降到了 CPU 上的 LLVM IR 并跑出了数字；这一章换目标：<strong>GPU</strong>。</p>
<p>三件事。<strong>一、<code>gpu</code> 方言的形状</strong>：<code>gpu.launch</code> 怎么表达"这段代码在网格上并行跑"，为什么它和第 21 章那个 <code>scf.forall</code> 天然对应。</p>
<p><strong>二、kernel outlining——第 13 章那笔 <code>IsolatedFromAbove</code> 的账，最后一次出现，而这次是它的正面价值。</strong><code>gpu.launch</code> 的 region <strong>故意不隔离</strong>：你写 kernel 时能直接引用外面的值，自然得多。代价是它不能被单独编译成 kernel——而 outlining 就是把这笔代价补上的那一步：做一次捕获分析，把外部引用提成显式参数，生成一个真正隔离的 <code>gpu.func</code>。</p>
<p><strong>三、三个出口，一次实测到底。</strong><code>gpu</code> 方言往下分叉：NVVM→PTX、ROCDL、SPIR-V。我们会把 NVVM 那条走到底，<strong>拿到真正的 PTX 汇编</strong>——这是全书唯一一处断言目标机器汇编的地方。</p>
<p>这一章不重复《GPU 编程》和《深入 LLVM 与 SYCL》讲过的硬件细节（warp 调度、内存层次、SIMT 与 SIMD 的关系），只讲 MLIR 这一侧：<strong>抽象是怎么分层的、每一层丢掉了什么。</strong></p>
</div>

## `gpu.launch`：把网格写进 IR

```mlir-norun
gpu.launch blocks(%bx, %by, %bz) in (%gx = %c1, %gy = %c1, %gz = %c1)
           threads(%tx, %ty, %tz) in (%bsx = %c8, %bsy = %c1, %bsz = %c1) {
  memref.store %v, %out[%tx] : memref<8xf32>
  gpu.terminator
}
```

读法：`blocks(...)` 和 `threads(...)` 各声明三个归纳变量（x/y/z）与对应的范围。region 里的代码就是"一个线程做什么"。

**和第 21 章那个 `scf.forall` 的对应关系值得停一下。** `scf.forall (%i, %j) in (2, 2)` 的归纳变量是 tile 编号——正好对上 `gpu.launch` 的 block/thread 编号。这不是巧合：`scf.forall` 的设计目标之一就是"能映射到 GPU 的并行层级"。所以第 21 章那条并行 tiling 的调度，天然是通往这一章的路。

<div class="note">
<strong>三个层级，三种表达</strong>
<p>MLIR 里"并行"在不同抽象层有不同形式，别混：</p>
<p><strong><code>linalg</code> 的 <code>iterator_types = ["parallel", ...]</code></strong>（第 20 章）——声明"这个维度<em>可以</em>并行"，是一个语义属性，不决定怎么并行。</p>
<p><strong><code>scf.forall</code></strong>（第 21 章）——声明"这些迭代<em>确实</em>并行执行、互不干扰"，但不说映射到什么硬件。</p>
<p><strong><code>gpu.launch</code></strong>（本章）——说清"映射到 grid/block/thread 这个具体层级"。</p>
<p>三层各管一件事，又是"每一步只决定一件事"。从 <code>forall</code> 到 <code>gpu.launch</code> 有现成的映射 pass（<code>transform.gpu.map_forall_to_blocks</code> 那一族）。</p>
</div>

## kernel outlining：那笔账的正面

`gpu.launch` 的 region 里引用了外面的 `%v` 和 `%out`。这很方便——但 GPU kernel 必须是一个**独立的函数**：它要被单独编译成 PTX/GCN，不可能"引用宿主函数里的局部变量"。

`--gpu-kernel-outlining` 负责这次转换：

```bash
mlir-opt g25.mlir --gpu-kernel-outlining
```

运行结果：

```
module attributes {gpu.container_module} {
  func.func @launch(%arg0: memref<8xf32>) {
    %c1 = arith.constant 1 : index
    %c8 = arith.constant 8 : index
    %cst = arith.constant 1.500000e+00 : f32
    gpu.launch_func  @launch_kernel::@launch_kernel blocks in (%c1, %c1, %c1) threads in (%c8, %c1, %c1)  args(%cst : f32, %arg0 : memref<8xf32>)
    return
  }
  gpu.module @launch_kernel {
    gpu.func @launch_kernel(%arg0: f32, %arg1: memref<8xf32>) kernel attributes {known_block_size = array<i32: 8, 1, 1>, known_grid_size = array<i32: 1, 1, 1>} {
      %block_id_x = gpu.block_id x
      %block_id_y = gpu.block_id y
      %block_id_z = gpu.block_id z
      %thread_id_x = gpu.thread_id x
      %thread_id_y = gpu.thread_id y
      %thread_id_z = gpu.thread_id z
      %grid_dim_x = gpu.grid_dim x
      %grid_dim_y = gpu.grid_dim y
      %grid_dim_z = gpu.grid_dim z
      %block_dim_x = gpu.block_dim x
      %block_dim_y = gpu.block_dim y
      %block_dim_z = gpu.block_dim z
      memref.store %arg0, %arg1[%thread_id_x] : memref<8xf32>
      gpu.return
```

三件事同时发生：

**模块被打上 `gpu.container_module`。** 这个属性告诉后续 pass"这里面有 GPU 模块要单独编译"。

**`gpu.launch` 变成了 `gpu.launch_func`，捕获的值成了 `args`。** 看那一行：`args(%cst : f32, %arg0 : memref<8xf32>)`——正是 region 里引用的那两个外部值。

**kernel 住进了一个 `gpu.module`，签名是 `gpu.func @launch_kernel(%arg0: f32, %arg1: memref<8xf32>) kernel`。** 它现在是隔离的：所有输入都是显式参数。

<div class="keypoint">
<strong><code>IsolatedFromAbove</code>：第 13 章那笔账的完整两面</strong>
<p>第 13 章我们撞过它的反面：<code>pix.pipeline</code> 没加这个 trait，于是不能在它上面挂 pass manager（<code>trying to schedule a pass on an operation not marked as 'IsolatedFromAbove'</code>）。当时的说法是"代价以后再谈"。</p>
<p>正面在这里：<strong><code>gpu.launch</code> 也故意不隔离</strong>，因为让程序员写 kernel 时能直接用外面的值，比强迫他手工声明一堆参数自然得多。而"不隔离"带来的所有限制，由 <strong>outlining 这一个 pass 一次性补上</strong>。</p>
<p>所以这不是"该不该加 trait"的二选一，而是<strong>一个设计模式</strong>：<strong>面向作者的形式可以不隔离（好写），面向编译器的形式必须隔离（好处理），中间用一个 outlining pass 连接。</strong>pix 的 <code>pix.pipeline</code> 走的是同一条路——只是 gpu 方言已经把那个 pass 写好了，pix 的还没人写（本章动手题就是它）。</p>
</div>

## 出口一：NVVM → PTX

`gpu` 方言往下有几个平行的出口。先看 NVIDIA 这条：

```bash
mlir-opt g25.mlir --gpu-kernel-outlining --convert-gpu-to-nvvm
```

运行结果（关键几行）：

```
  gpu.module @launch_kernel {
    llvm.func @launch_kernel(%arg0: f32, %arg1: !llvm.ptr, %arg2: !llvm.ptr, %arg3: i64, %arg4: i64, %arg5: i64) attributes {gpu.kernel, gpu.known_block_size = array<i32: 8, 1, 1>, gpu.known_grid_size = array<i32: 1, 1, 1>, nvvm.kernel, nvvm.maxntid = array<i32: 8, 1, 1>} {
      %6 = nvvm.read.ptx.sreg.tid.x range <i32, 0, 8> : i32
```

两处值得看：

**`memref<8xf32>` 展成了五个标量**：`!llvm.ptr, !llvm.ptr, i64, i64, i64`——正是第 24 章那个 descriptor（allocated、aligned、offset、size、stride）。**同一个机制，换了目标。**

**`gpu.thread_id x` 变成了 `nvvm.read.ptx.sreg.tid.x`**——读 PTX 的特殊寄存器 `%tid.x`。`nvvm` 方言就是"LLVM 的 NVVM intrinsic 在 MLIR 里的样子"。

再往下一步，**真的生成 PTX**：

```bash
mlir-opt ptx25.mlir --convert-gpu-to-nvvm --gpu-module-to-binary=format=isa
```

它把汇编塞进一个 `gpu.binary` op 的属性里。把那个字符串解码出来：

```
//
// Generated by LLVM NVPTX Back-End
//

.version 7.0
.target sm_80
.address_size 64

	// .globl	fill

.visible .entry fill(
	.param .u64 .ptr .align 1 fill_param_0,
	.param .u64 .ptr .align 1 fill_param_1,
	.param .u64 fill_param_2,
	.param .u64 fill_param_3,
	.param .u64 fill_param_4,
	.param .f32 fill_param_5
)
{
	.reg .b32 	%r<3>;
	.reg .b64 	%rd<5>;

	ld.param.b64 	%rd1, [fill_param_1];
	cvta.to.global.u64 	%rd2, %rd1;
	mov.u32 	%r1, %tid.x;
	mul.wide.u32 	%rd3, %r1, 4;
	add.s64 	%rd4, %rd2, %rd3;
	ld.param.b32 	%r2, [fill_param_5];
	st.global.b32 	[%rd4], %r2;
	ret;

}
```

**这是真正的 PTX。** `.target sm_80`、`mov.u32 %r1, %tid.x`、`st.global.b32`——从 `pix` 一路到这里，中间没有任何手写的机器码。

注意那六个 `fill_param_*`：前五个是 memref descriptor 的字段，最后一个是 `f32`。**GPU kernel 的参数传递也走 descriptor 那套 ABI**（第 24 章）。

<div class="warn">
<strong><code>format=isa</code> 只出汇编，不出 cubin</strong>
<p><code>--gpu-module-to-binary</code> 的 <code>format</code> 有几档：<code>isa</code> 出 PTX 汇编（只需要 LLVM 的 NVPTX 后端）、<code>bin</code>/<code>fatbin</code> 出可直接加载的二进制（<strong>需要 <code>ptxas</code>，也就是要装 CUDA 工具链</strong>）。</p>
<p>另外这一步需要构建时带 NVPTX 后端（<code>LLVM_TARGETS_TO_BUILD</code> 含 <code>NVPTX</code>）。最小构建里没有的话会在这一步失败，而报错不会明确告诉你"缺后端"。附录 A 第 0 节写明了基线构建的配置。</p>
<p>还有一个容易漏的：<code>pix-opt</code> 这类自己写的驱动，除了 <code>registerAllDialects</code> 和 <code>registerAllExtensions</code>（第 18 章那个坑），<strong>还要 <code>registerAllToLLVMIRTranslations</code></strong>。少了它这一步报 <code>missing 'LLVMTranslationDialectInterface' registration for dialect for op: gpu.module</code>——<strong>三套注册是三件不同的事</strong>，而报错只在你用到那一套时才出现。</p>
</div>

## 另外两个出口

三条路的分叉点都在 `gpu` 方言，往下各走各的：

| 出口 | pass | 目标 | 最终产物 |
| --- | --- | --- | --- |
| **NVVM** | `--convert-gpu-to-nvvm` | NVIDIA | PTX → cubin |
| **ROCDL** | `--convert-gpu-to-rocdl` | AMD | GCN ISA → hsaco |
| **SPIR-V** | `--convert-gpu-to-spirv` | Vulkan / OpenCL / Intel GPU | SPIR-V 二进制 |
| **LLVM-SPV** | `--convert-gpu-to-llvm-spv` | Intel GPU（走 LLVM 的 SPIR-V 后端） | SPIR-V |

**共性**（这是值得记住的部分）：三条路都做同样四件事——
① 把 `gpu.thread_id` 那类内建变量换成目标的读寄存器 intrinsic；
② 把 `memref` 展成目标 ABI（descriptor 或它的变体）；
③ 把地址空间标注上（GPU 有 global/shared/local 之分，CPU 没有）；
④ 把 kernel 标记成入口（`nvvm.kernel`、`spirv.EntryPoint` 等）。

**差异**主要在两处：**地址空间的编号和语义**（谁是 shared memory，编号是几），以及**同步原语**（`gpu.barrier` 降成什么）。硬件层面的差别——warp 大小、内存合并规则、SIMT 与 SIMD 的关系——**这本书不重复**：《GPU 编程》讲过硬件模型，《深入 LLVM 与 SYCL》讲过 SPIR-V 与 SYCL 那条路。这里只需要知道：**MLIR 把这些差异收在最后一层，前面所有变换（tiling、融合、向量化）对三个目标是共享的。**

<div class="keypoint">
<strong>这才是 MLIR 在 GPU 编译上的真正价值</strong>
<p>不是"支持三个厂商"——那只是结果。价值在于<strong>分叉点被推到了尽可能晚的地方</strong>：第 20–23 章那些变换（indexing map、tile、融合、向量化、bufferization）完全不知道目标是谁，三条路共用。只有最后一层才分开。</p>
<p>对比传统做法：为每个厂商写一整条后端管线，tiling 逻辑抄三遍。第 20 章那笔"用冗长换通用性"的交易，最终的利息在这里——<strong>通用的不只是变换，还有整条管线。</strong></p>
</div>

## 把 outlining 的捕获分析跑一遍

outlining 的全部工作就是一次捕获分析。下面这个模型把它做出来，结果和真 `mlir-opt` 的 `args(...)` 一致：

```python
# kernel outlining 做的是一次**捕获分析**：找出 region 里引用了外面哪些值，
# 把它们提成参数。这正是把"不隔离的 region"变成"隔离的函数"所需的全部工作。

def outline(outer_defs, region_ops):
    """outer_defs: region 外面定义的值；region_ops: (结果, [用到的值]) 列表"""
    defined_inside = set()
    captured = []          # 按首次出现的顺序，保证参数顺序稳定
    for res, uses in region_ops:
        for u in uses:
            if u in defined_inside:
                continue                    # region 内部定义的，不用捕获
            if u in outer_defs and u not in captured:
                captured.append(u)          # 来自外面 → 必须捕获
        if res:
            defined_inside.add(res)
    return captured

CASES = [
    ("gpu.launch 引用了外面的 %v 和 %out",
     {"%v", "%out", "%c1", "%c8"},
     [("%tx", ["%tid_x"]),                  # region 自己产生的（gpu.thread_id）
      (None,  ["%v", "%out", "%tx"])]),     # memref.store %v, %out[%tx]
    ("region 里啥都自己算，无需捕获",
     {"%v", "%out"},
     [("%a", ["%tid_x"]), ("%b", ["%a"]), (None, ["%b"])]),
    ("同一个值被用两次，只捕获一次",
     {"%v", "%out"},
     [(None, ["%v", "%out"]), (None, ["%v", "%out"])]),
]
for title, outer, ops in CASES:
    cap = outline(outer, ops)
    print(f"\n【{title}】")
    print(f"  region 外的值：{sorted(outer)}")
    print(f"  需要捕获：{cap or '（无）'}")
    sig = ", ".join(f"%arg{i}" for i in range(len(cap)))
    print(f"  生成的 kernel 签名：gpu.func @k({sig}) kernel")
    if cap:
        print(f"  调用处：gpu.launch_func @k ... args({', '.join(cap)})")

print("\n" + "=" * 62)
print("这就是 IsolatedFromAbove 那笔账的两面（第 13 章）：")
print("  · gpu.launch 的 region **故意不隔离** —— 你写 kernel 时能直接用")
print("    外面的值，自然得多，不必手工声明一堆参数")
print("  · 代价是它不能被单独调度 pass、不能直接编译成独立 kernel")
print("  · outlining 就是把代价补上的那一步：捕获 → 提成参数 →")
print("    生成一个真正 IsolatedFromAbove 的 gpu.func")
print("\n对比 pix.pipeline（第 8 章也故意没加那个 trait）：它同样不隔离，")
print("所以同样需要一次 outlining 才能被当成独立单元处理。区别只是")
print("gpu 方言已经把那个 pass 写好了，而 pix 的还没人写。")
```

运行结果：

```

【gpu.launch 引用了外面的 %v 和 %out】
  region 外的值：['%c1', '%c8', '%out', '%v']
  需要捕获：['%v', '%out']
  生成的 kernel 签名：gpu.func @k(%arg0, %arg1) kernel
  调用处：gpu.launch_func @k ... args(%v, %out)

【region 里啥都自己算，无需捕获】
  region 外的值：['%out', '%v']
  需要捕获：（无）
  生成的 kernel 签名：gpu.func @k() kernel

【同一个值被用两次，只捕获一次】
  region 外的值：['%out', '%v']
  需要捕获：['%v', '%out']
  生成的 kernel 签名：gpu.func @k(%arg0, %arg1) kernel
  调用处：gpu.launch_func @k ... args(%v, %out)

==============================================================
这就是 IsolatedFromAbove 那笔账的两面（第 13 章）：
  · gpu.launch 的 region **故意不隔离** —— 你写 kernel 时能直接用
    外面的值，自然得多，不必手工声明一堆参数
  · 代价是它不能被单独调度 pass、不能直接编译成独立 kernel
  · outlining 就是把代价补上的那一步：捕获 → 提成参数 →
    生成一个真正 IsolatedFromAbove 的 gpu.func

对比 pix.pipeline（第 8 章也故意没加那个 trait）：它同样不隔离，
所以同样需要一次 outlining 才能被当成独立单元处理。区别只是
gpu 方言已经把那个 pass 写好了，而 pix 的还没人写。
```

第一组的答案 `['%v', '%out']` 和真实输出里 `args(%cst : f32, %arg0 : memref<8xf32>)` 是同一件事——**顺序也一致**，因为按首次出现的顺序捕获能保证参数顺序稳定（这很重要：否则每次编译生成的 kernel 签名都可能不同）。

第二组说明"不引用外面的值就不需要捕获"；第三组说明"同一个值用两次只捕获一次"。三条合起来就是 outlining 的完整规则。

## 动手：给 `pix.pipeline` 写一个 outlining pass

第 8 章我们故意没给 `pix.pipeline` 加 `IsolatedFromAbove`，第 13 章付了代价（不能挂 pass manager），这一章看到了补救办法。**现在把它补上**：

1. 新建一个 pass `pix-outline-pipelines`；
2. 对每个 `pix.pipeline`，做一次捕获分析（本章模拟器里那 10 行逻辑）——遍历 region，找出所有"定义在 region 外"的操作数；
3. 造一个新的 `func.func`，参数就是捕获到的那些值，body 是原 region 的内容（`rewriter.inlineRegionBefore` 能帮上）；
4. 把原 `pix.pipeline` 换成一次 `func.call`。

做完之后试试在生成的函数上挂 pass manager——**第 13 章那个报错应该消失了**。

**再改一处**：把 `gpu_ptx.mlir` 里的 `#nvvm.target<chip = "sm_80">` 改成 `sm_90`，对比生成的 PTX 有什么不同（提示：看 `.target` 那一行，以及有没有出现新指令）。然后把它改成一个不存在的 chip，看报错——**这是"目标描述写在属性里"的直接好处：换目标不用改任何 pass**。

---

**这一章的要点**

- `gpu.launch` 把网格写进 IR：`blocks(...)` / `threads(...)` 各三个归纳变量，region 里是"一个线程做什么"。
- **并行在三层各有形式，别混**：`linalg` 的 `iterator_types = ["parallel"]` 说"可以并行"；`scf.forall` 说"确实并行"；`gpu.launch` 说"映射到 grid/block/thread"。第 21 章 `scf.forall` 的归纳变量是 tile 编号，正是为了对上这一层。
- **kernel outlining 的全部工作是一次捕获分析**：找出 region 里引用的外部值，提成显式参数，生成隔离的 `gpu.func`。模型只要十行，规则三条（内部定义的不捕获、外部的捕获、重复的只捕获一次；按首次出现排序以保证签名稳定）。
- **`IsolatedFromAbove` 的完整两面**（第 13 章那笔账收尾）：这不是二选一，而是一个设计模式——**面向作者的形式可以不隔离（好写），面向编译器的形式必须隔离（好处理），中间用一个 outlining pass 连接。** `gpu.launch` 和 `pix.pipeline` 走的是同一条路，只是 gpu 方言已经把那个 pass 写好了。
- **memref 在 GPU 上也走 descriptor**：NVVM 输出里 `memref<8xf32>` 展成 `!llvm.ptr, !llvm.ptr, i64, i64, i64`，PTX 里就是那五个 `fill_param_*`。第 24 章那套 ABI 换了目标一样用。
- `gpu.thread_id x` → `nvvm.read.ptx.sreg.tid.x` → PTX 里的 `mov.u32 %r1, %tid.x`。**三层名字不同，是同一件事在不同抽象层的样子。**
- **`format=isa` 只出 PTX 汇编；出 cubin 要 `ptxas`（CUDA 工具链）**。这一步还需要构建时带 NVPTX 后端，缺了的话报错不会明说。
- 自己写的驱动要**三套注册**：`registerAllDialects`、`registerAllExtensions`（第 18 章）、`registerAllToLLVMIRTranslations`（本章）。三件不同的事，各自只在用到时才报错——最后这个缺失时报 `missing 'LLVMTranslationDialectInterface' registration`。
- 三条出口路做同样四件事（内建变量→intrinsic、memref→目标 ABI、地址空间、kernel 标记），差异只在**地址空间编号**与**同步原语**。
- **MLIR 在 GPU 编译上的真正价值不是"支持三家厂商"，而是分叉点被推到尽可能晚**：第 20–23 章那些变换完全不知道目标是谁，三条路共用。这是第 20 章那笔交易最终的利息——通用的不只是变换，是整条管线。

**pix 进度**：`pix-opt` 补上 `registerAllToLLVMIRTranslations`，于是它也能生成 PTX。新增 `gpu.mlir`（断言 outlining 的捕获结果与 NVVM 的 descriptor 展开）和 `gpu_ptx.mlir`（**断言 PTX 汇编内容本身**，全书唯一一处）。`check-pix` 从 22 涨到 24 个文件。

**第四部分结束。** pix 从第 7 章一行 ODS 长成了一个完整方言，又一路降到了 CPU 的机器码和 GPU 的 PTX。第五部分转向**真实世界**：第 26 章讲 Triton——它对 MLIR 最大的原创贡献是 layout 系统，那也是理解它性能的钥匙；第 27 章对照 IREE 与 flang 两种截然不同的用法；第 28 章讲 ClangIR，并诚实收尾——MLIR 还没解决的问题。
