# 第 9 章 ODS（二）：自定义类型与属性，!pix.kernel 是怎么来的

## 这一章想让你带走什么

<div class="goal-box">
<p>第 8 章造的都是 op，用的类型全是内建的。这一章补上 ODS 的另一半：<strong>自定义类型</strong>与<strong>自定义属性</strong>。pix 会新增一个参数化类型 <code>!pix.kernel&lt;3 x 3&gt;</code>（stencil 权重矩阵）和一个枚举属性 <code>#pix.border&lt;clamp|zero|wrap&gt;</code>（边界处理方式），再用它们定义真正的邻域运算 <code>pix.convolve</code>——它是第四部分做 tiling 和向量化的主角。</p>
<p>三个知识点：<strong>参数化类型</strong>怎么声明（参数、格式、额外方法）、<strong>枚举属性</strong>的两步写法（先枚举、再包成方言属性）、以及 <code>add_mlir_dialect</code> 覆盖不到的地方<strong>怎么手写 <code>mlir_tablegen</code></strong>。</p>
<p>另外这一章有四个"踩坑实录"。它们都是我把这套东西真编出来时撞到的，报错措辞看起来都跟真正的原因无关——比如 <code>!pix.kernel&lt;3x3&gt;</code> 为什么必须写成 <code>&lt;3 x 3&gt;</code>（答案在词法分析器那里）。</p>
</div>

## 先决定：什么该做成自定义类型

这个判断比语法重要得多。pix 处理图像，图像该不该做成 `!pix.image<8x8xf32>`？

**我们的答案是不。** 图像直接用内建的 `tensor<8x8xf32>`，理由有三条：

1. **下降会变麻烦。** 第四部分要把 pix 降到 `linalg`，而 `linalg` 本来就在 `tensor` 上工作。图像若是自定义类型，中间必须插一整套类型转换（第 16、17 章的活儿），而这套转换**什么语义都没增加**，纯属自找麻烦。
2. **会挡住现成的 trait。** `SameOperandsAndResultType`、`ElementwiseMappable` 这些都是围绕 shaped 类型设计的；换成自定义类型，很多现成能力要自己重做一遍。
3. **它不表达任何新约束。** 图像就是"二维 f32 数组"，`tensor<HxWxf32>` 说得完整、准确。

**那卷积核为什么值得自定义？** 因为它确实是个**不同的概念**：尺寸受限（通常是奇数边长）、语义不同（权重而非像素）、而且我们希望"尺寸在编译期已知"这件事写进类型里——第 21 章算 halo（分块时边界要多取几行）时直接读类型就有了，不必去分析数据。

<div class="keypoint">
<strong>判断标准</strong>
<p>该不该自定义一个类型，看它能不能回答"<strong>我比现成类型多表达了什么约束或语义</strong>"。答不出来，就用内建类型——每个自定义类型都会给你增加一笔"与内建生态对接"的税，必须有相应的收益。</p>
</div>

## 自定义类型：`!pix.kernel<R x C>`

类型定义放在一个新文件 `include/Pix/PixTypes.td`：

```tablegen
class Pix_Type<string name, string typeMnemonic, list<Trait> traits = []>
    : TypeDef<Pix_Dialect, name, traits> {
  let mnemonic = typeMnemonic;
}

def Pix_KernelType : Pix_Type<"Kernel", "kernel"> {
  let summary = "stencil 权重矩阵的类型";

  // 参数就是类型的"内容"。类型是唯一化的不可变值（第 4 章），
  // 所以参数一旦定下就不能改——要改只能造一个新类型。
  let parameters = (ins "int64_t":$rows, "int64_t":$cols);

  // 自定义格式，与 op 的 assemblyFormat 是同一套小语言
  let assemblyFormat = "`<` $rows `x` $cols `>`";

  let extraClassDeclaration = [{
    int64_t getNumWeights() const { return getRows() * getCols(); }
    bool isSquare() const { return getRows() == getCols(); }
  }];
}
```

几处要点：

- **`mnemonic`** 决定文本里的名字：`!pix.kernel<…>`。方言名 `pix` 是自动加的前缀。
- **`parameters`** 里可以是 C++ 类型（`"int64_t"`）、MLIR 的类型/属性（`"Type":$elementType`），或者数组（`ArrayRefParameter<"int64_t">:$shape`）。
- **`extraClassDeclaration`** 往生成的 C++ 类里塞你自己的方法。这是个常用口子：把"关于这个类型的小逻辑"放在类型身上，而不是散落在各个 pass 里。`getRows()` / `getCols()` 是 TableGen 按参数名自动生成的。
- 类型的参数**没有默认验证**。"行列必须是正奇数"这条规则要靠 `let genVerifyDecl = 1` + 手写 `verify()`，那是第 10 章的活。

### 踩坑实录一：为什么必须写 `<3 x 3>` 而不是 `<3x3>`

我一开始写的是 `!pix.kernel<3x3>`，解析直接失败：

```
error: expected 'x'
  ... : !pix.kernel<3x3>
                     ^
```

原因在**词法分析器**：MLIR 先把输入切成 token，`3x3` 会被切成整数 `3` 和标识符 `x3`——于是格式里那个字面量 `x` 永远匹配不上。

内建类型 `tensor<4x4xf32>` 能写得那么紧凑，是因为它有一套专门的 dimension-list 解析器。自定义类型要想要同样的紧凑写法，只能 `let hasCustomAssemblyFormat = 1;` 然后自己写 parser/printer。**上游 `!spirv.array<4 x f32>` 就是选了加空格这条省事的路**，我们跟它一致。

### 类型的两种打印形式

有意思的细节：同一个类型在不同位置打印得不一样（这是 `pix-opt` 的真实输出）。

```mlir
// RUN: pix-opt %s
func.func @kernel_in_signature(%k: !pix.kernel<1 x 5>) -> !pix.kernel<1 x 5> {
  return %k : !pix.kernel<1 x 5>
}
```

函数签名里是**完整形式** `!pix.kernel<1 x 5>`；而在 pix 自己的 op 里，同一个类型印成了简写 `<3 x 3>`：

```
%1 = pix.convolve %arg0, %0 border <zero> : <3 x 3>, tensor<8x8xf32>
```

因为在 pix 方言的 op 内部，方言前缀可以由上下文推出来，MLIR 于是省掉了它。两种形式都能被解析回去（`pix-opt … | pix-opt` 跑通过）。**第一次看到这个简写会以为是 bug，其实是特性。**

## 自定义属性：枚举的两步写法

边界处理方式是典型的枚举：clamp / zero / wrap。写在 `include/Pix/PixAttrs.td`，分两步。

**第一步，定义枚举本身**（生成一个 C++ `enum class BorderMode`）：

```tablegen
def Pix_BorderMode : I32EnumAttr<"BorderMode", "卷积的边界处理方式", [
      I32EnumAttrCase<"Clamp", 0, "clamp">,  // 取最近的边界像素
      I32EnumAttrCase<"Zero",  1, "zero">,   // 界外当 0
      I32EnumAttrCase<"Wrap",  2, "wrap">    // 环绕到另一侧
    ]> {
  let cppNamespace = "::mlir::pix";
  let genSpecializedAttr = 0;   // 不要顺带生成属性类，下一步我们要更好的那种
}
```

**第二步，把枚举包成一个真正的方言属性**：

```tablegen
def Pix_BorderModeAttr : EnumAttr<Pix_Dialect, Pix_BorderMode, "border"> {
  let assemblyFormat = "`<` $value `>`";
}
```

这一步换来的是：属性有了自己的 mnemonic（`border`）和打印形式 `#pix.border<clamp>`，而不是一个裸整数。**裸整数属性也能用，但它在 IR 里是 `2 : i32`，读的人不知道 2 是什么。**

枚举的 C++ 侧还白拿两个函数：`stringifyBorderMode()` 和 `symbolizeBorderMode()`，在写诊断信息和解析用户输入时很好用。

写错枚举值时的报错也很体贴（实测）：

```
error: custom op 'pix.convolve' expected ::mlir::pix::BorderMode to be one of: clamp, zero, wrap
```

## `add_mlir_dialect` 管不到的地方：手写 `mlir_tablegen`

第 7 章讲过 `add_mlir_dialect(PixOps pix)` 展开成六次 `mlir_tablegen`——注意那六次里**没有属性**。所以属性和枚举要自己加（`include/Pix/CMakeLists.txt`）：

```cmake
add_mlir_dialect(PixOps pix)

# 属性与枚举不在 add_mlir_dialect 的覆盖范围里，所以手写底层三步：
# 设定输入 .td → 逐个生成器跑一遍 → 建一个 TableGen 目标
set(LLVM_TARGET_DEFINITIONS PixAttrs.td)
mlir_tablegen(PixAttrs.h.inc -gen-attrdef-decls -attrdefs-dialect=pix)
mlir_tablegen(PixAttrs.cpp.inc -gen-attrdef-defs -attrdefs-dialect=pix)
mlir_tablegen(PixEnums.h.inc -gen-enum-decls)
mlir_tablegen(PixEnums.cpp.inc -gen-enum-defs)
add_public_tablegen_target(MLIRPixAttrsIncGen)
```

然后在 `lib/Pix/CMakeLists.txt` 的 `DEPENDS` 里加上 `MLIRPixAttrsIncGen`（漏了就是第 7 章那个偶发的"找不到 .inc"）。

方言那边还要开两个开关，否则 `!pix.kernel<…>` 和 `#pix.border<…>` 没人解析：

```tablegen
def Pix_Dialect : Dialect {
  // …
  let useDefaultTypePrinterParser = 1;
  let useDefaultAttributePrinterParser = 1;
  let extraClassDeclaration = [{
    void registerTypes();
    void registerAttributes();
  }];
}
```

`initialize()` 里把它们注册进来——和第 7 章注册 op 是同一个套路：

```cpp-norun
void PixDialect::initialize() {
  addOperations<
#define GET_OP_LIST
#include "Pix/PixOps.cpp.inc"
      >();
  registerTypes();       // 实现在 PixTypes.cpp
  registerAttributes();  // 实现在 PixAttrs.cpp
}
```

<div class="warn">
<strong>踩坑实录二：生成文件的名字还是跟着 <code>add_mlir_dialect</code> 的第一个参数走</strong>
<p>类型的声明在 <strong><code>PixOpsTypes.h.inc</code></strong>（不是 <code>PixTypes.h.inc</code>），因为它由 <code>add_mlir_dialect(<strong>PixOps</strong> pix)</code> 生成。而属性的 <code>.inc</code> 是我们手写 <code>mlir_tablegen</code> 生成的，名字由我们自己定（<code>PixAttrs.h.inc</code>）。<strong>同一个项目里两种命名规则并存</strong>，第一次配的时候特别容易搞混——出现"找不到某个 .inc"时，先去 <code>build/include/Pix/</code> 里 <code>ls</code> 一下实际生成了什么。</p>
</div>

## 用起来：`pix.kernel` 与 `pix.convolve`

```tablegen
def Pix_KernelOp : Pix_Op<"kernel", [Pure, ConstantLike]> {
  let arguments = (ins ElementsAttr:$weights);
  let results = (outs Pix_KernelType:$result);
  let assemblyFormat = "$weights attr-dict `->` type($result)";
}

def Pix_ConvolveOp : Pix_Op<"convolve", [Pure, AllTypesMatch<["image", "result"]>]> {
  let arguments = (ins F32Tensor:$image,
                       Pix_KernelType:$kernel,
                       DefaultValuedAttr<Pix_BorderModeAttr,
                                         "::mlir::pix::BorderMode::Clamp">:$border);
  let results = (outs F32Tensor:$result);
  let assemblyFormat = [{
    $image `,` $kernel (`border` $border^)? attr-dict
    `:` type($kernel) `,` type($result)
  }];
}
```

跑起来（`pix-opt` 的真实输出，注意第二个 `convolve` 没有写 `border`）：

```mlir
// RUN: pix-opt %s
func.func @laplace(%img: tensor<8x8xf32>) -> tensor<8x8xf32> {
  %k = pix.kernel dense<[[0.0, 1.0, 0.0],
                         [1.0, -4.0, 1.0],
                         [0.0, 1.0, 0.0]]> : tensor<3x3xf32> -> !pix.kernel<3 x 3>
  %out = pix.convolve %img, %k border<zero> : !pix.kernel<3 x 3>, tensor<8x8xf32>
  %dfl = pix.convolve %out, %k : !pix.kernel<3 x 3>, tensor<8x8xf32>
  return %dfl : tensor<8x8xf32>
}
```

打印回来是这样：

```
    %0 = pix.kernel dense<[[0.000000e+00, 1.000000e+00, 0.000000e+00], [1.000000e+00, -4.000000e+00, 1.000000e+00], [0.000000e+00, 1.000000e+00, 0.000000e+00]]> : tensor<3x3xf32> -> <3 x 3>
    %1 = pix.convolve %arg0, %0 border <zero> : <3 x 3>, tensor<8x8xf32>
    %2 = pix.convolve %1, %0 : <3 x 3>, tensor<8x8xf32>
```

**`%2` 那行没有 `border`**——因为它取默认值 `clamp`，被 `DefaultValuedAttr` + 可选组一起省掉了。这是个值得学的习惯：**让常见情况在 IR 里消失，读者的注意力才能落在不常见的地方。**

### 踩坑实录三：自定义类型的操作数，类型必须打印出来

我最初把 convolve 的格式写成 `… attr-dict `:` type($result)`（只打印一个类型，像第 8 章的 `pix.scale` 那样）。TableGen 直接拒绝：

```
error: type of operand #1, named 'kernel', is not buildable
       and a buildable type cannot be inferred
```

读法：解析器要构造出 `$kernel` 的类型，但 `!pix.kernel<R x C>` **带参数**——没有一个"默认的 kernel 类型"可以凭空造出来，而 `AllTypesMatch` 只覆盖了 image 和 result。所以必须把它打印出来：`type($kernel) `,` type($result)`。

> 一般规律：**类型不打印的前提是它能被推出来**（靠 `AllTypesMatch`、`TypesMatchWith`、或者那种唯一的无参数类型）。带参数的自定义类型基本都得显式打印。

### 踩坑实录四：`ElementsAttr` 必须配 shaped 类型

`pix.kernel` 的格式我一开始也写成 `$weights attr-dict `:` type($result)`，结果解析时报：

```
error: elements literal must be a shaped type
```

因为那样写等于告诉解析器"用 `!pix.kernel<3 x 3>` 当这个 `dense<…>` 字面量的类型"，而 `DenseElementsAttr` 必须配 shaped 类型（tensor / vector）。修法就是让属性带上自己的类型，再用一个箭头指向结果：

```
pix.kernel dense<…> : tensor<3x3xf32> -> !pix.kernel<3 x 3>
```

**两个类型看着啰嗦，但它们说的是两件事**：`tensor<3x3xf32>` 是那堆权重数据的类型，`!pix.kernel<3 x 3>` 是这个 op 产出的值的类型。第 10 章会加一条 verifier，确保两者的形状一致——因为现在它们可以不一致而无人过问。

## 动手

```bash
# 1. 看类型与属性生成了什么
mlir-tblgen -gen-typedef-decls -typedefs-dialect=pix -I $LLVM_SRC/mlir/include -I include \
  include/Pix/PixOps.td
mlir-tblgen -gen-attrdef-decls -attrdefs-dialect=pix -I $LLVM_SRC/mlir/include -I include \
  include/Pix/PixAttrs.td
mlir-tblgen -gen-enum-decls -I $LLVM_SRC/mlir/include -I include include/Pix/PixAttrs.td

# 2. 构建并跑测试（现在有 4 个测试了）
books/inside-mlir/verify/verify-pix.sh
```

**改一改：**

1. **给 `!pix.kernel` 加第三个参数**，比如 `"bool":$separable`（可分离核，能拆成两次一维卷积）。格式怎么改？想一想这个信息放在**类型**里还是放在 **op 的属性**里更合适——判断标准是"它是数据的属性，还是这个值本身类型的一部分"。
2. **把 `border` 的默认值从 `Clamp` 改成 `Zero`**，重新编译，跑本章那段 IR。哪一行的打印变了？（提示：现在被省略的是 `zero`，而 `clamp` 要显式打印了。）
3. **试试 `!pix.kernel<3x3>`（去掉空格）**，亲眼看 `expected 'x'`。然后想想：如果你就是想要紧凑写法，`hasCustomAssemblyFormat` 那条路要写多少代码？（提示：`parseDimensionList`）
4. **把 `pix.kernel` 的 `ConstantLike` 去掉**，再在同一个函数里写两个一模一样的 `pix.kernel`，跑 `--cse`。合并了吗？加回去再试。这是第 11 章"常量折叠"的预习。
5. **故意让权重形状与类型不符**：`dense<…> : tensor<3x3xf32> -> !pix.kernel<5 x 5>`。跑 `pix-opt`——它**通过了**。这就是第 10 章要修的第一个洞。

---

**这一章的要点**

- 该不该自定义类型，看它**比现成类型多表达了什么约束**。pix 的图像用内建 `tensor`（避免与 `linalg` 对接时的无谓转换），而卷积核值得自定义（尺寸进类型，编译期可知）。
- 自定义类型 = `TypeDef` + `mnemonic` + `parameters` + `assemblyFormat`；`extraClassDeclaration` 是给类型加小方法的正规口子。类型参数**没有默认验证**，要靠 `genVerifyDecl`（第 10 章）。
- 枚举属性两步走：`I32EnumAttr` 定义枚举（`genSpecializedAttr = 0`），再用 `EnumAttr` 包成方言属性，得到 `#pix.border<clamp>` 这种自解释的写法，外加 `stringify`/`symbolize` 两个函数。
- **`add_mlir_dialect` 不管属性**：属性和枚举要自己写 `set(LLVM_TARGET_DEFINITIONS …)` + `mlir_tablegen(…)` + `add_public_tablegen_target(…)`，并把新目标加进 `DEPENDS`。
- 方言要开 `useDefaultTypePrinterParser` / `useDefaultAttributePrinterParser`，并在 `initialize()` 里 `registerTypes()` / `registerAttributes()`。
- 四个真实的坑：**`<3x3>` 会被词法器切成 `3` + `x3`**（要写 `<3 x 3>`，或自己写 parser）；**生成文件的名字两套规则并存**（`PixOpsTypes.h.inc` vs `PixAttrs.h.inc`）；**带参数的自定义类型当操作数时，类型必须打印**（否则 `not buildable`）；**`ElementsAttr` 必须配 shaped 类型**（所以 `pix.kernel` 要写两个类型）。
- 用 `DefaultValuedAttr` + 可选组，让**常见情况在 IR 里消失**——读者的注意力就能落在不常见的地方。

**pix 进度**：9 个 op、1 个自定义类型（`!pix.kernel<R x C>`）、1 个枚举属性（`#pix.border`），4 个 lit 测试全绿。但已经攒下三个"没人检查"的洞：转置的形状关系、pipeline 的 yield 对齐、kernel 权重形状与类型是否一致。

下一章专门补洞：**verifier 与不变式**。我们会手写 `verify()`、给类型加 `genVerifyDecl`，还会走另一条路——去实现 `RegionBranchOpInterface`，让通用机制替我们检查 pipeline 的 yield 对齐。两条路走完，你就知道"什么时候写 verifier、什么时候该实现接口"。
