# 第 20 章 linalg：结构化操作、indexing map 与「为什么它好变换」

## 这一章想让你带走什么

<div class="goal-box">
<p>第四部分开始把 pix 一路降到机器上。第一站是 <code>linalg</code>——而这一章要回答的问题不是"怎么用它"，是<strong>为什么绕这一道</strong>。</p>
<p>因为第 16 章我们已经把 pix 降到 <code>arith</code> 了，那条路更短：<code>arith.addf</code> 在 tensor 上本来就是逐点的。但那条路有个致命缺陷——<strong>它把迭代空间丢了</strong>。<code>arith.addf %a, %b : tensor&lt;8x8xf32&gt;</code> 是一个不透明的"整张图加整张图"，没人知道它由哪些循环组成，于是 tile 不了、融合不了、向量化也无从下手。</p>
<p>这一章会用一条实测的报错把这件事钉死：同一个 <code>pix.add</code>，走 linalg 那条路降下来能被 transform 调度 tile 成嵌套循环；走 arith 那条路降下来，transform 直接拒绝——<code>only ops implementing TilingInterface are supported</code>。</p>
<p>核心概念只有一个：<strong>indexing map 把"迭代空间"和"每个点上算什么"分开写。</strong>正因为迭代空间是显式的、可分析的，tiling 和融合才能<strong>通用地</strong>实现，而不必为每个 op 写一遍。这一章会把 pix 的逐点、缩放、归约三类运算全降到 <code>linalg.generic</code>——你会看到<strong>同一个 op</strong>，只换 map 和 iterator 类型，就从逐点变成了归约。</p>
</div>

## 先看结论：两条路的差别

第 16 章那条路和这一章这条路，输入完全相同。

```mlir-norun
// pix.add %a, %b : tensor<8x8xf32>

// 路 A（第 16 章，--pix-to-arith）：
%s = arith.addf %a, %b : tensor<8x8xf32>

// 路 B（这一章，--pix-to-linalg）：
%0 = tensor.empty() : tensor<8x8xf32>
%s = linalg.generic {indexing_maps = [#id, #id, #id],
                     iterator_types = ["parallel", "parallel"]}
     ins(%a, %b : tensor<8x8xf32>, tensor<8x8xf32>) outs(%0 : tensor<8x8xf32>) {
  ^bb0(%x: f32, %y: f32, %out: f32):
    %v = arith.addf %x, %y : f32
    linalg.yield %v : f32
} -> tensor<8x8xf32>
```

路 B 明显啰嗦得多。它多出来的到底是什么？**是那两个属性。** `indexing_maps` 说"迭代点 (i,j) 该读写哪些元素"，`iterator_types` 说"这些维度是可并行的还是归约的"。region 里那三行是"每个点上算什么"。

**两件事被分开了，而分开的那一半正好是 tiling 需要的。**

<div class="keypoint">
<strong>「结构化」的含义就是"迭代空间是显式的"</strong>
<p><code>arith.addf</code> 在 tensor 上是<strong>不透明</strong>的：语义上它等价于一个双重循环，但那个循环只存在于文档里，IR 里找不到。想 tile 它，你得先"知道"它是双重循环——也就是为每一个这样的 op 单独写一遍 tiling 逻辑。</p>
<p><code>linalg.generic</code> 把循环结构写进了 IR（<code>indexing_maps</code> + <code>iterator_types</code>），于是 tiling 变成了对<strong>一个属性</strong>的操作，对所有 linalg op 通用。<code>TilingInterface</code> 就是这份契约的名字。</p>
<p>代价是 IR 变长、可读性下降。<strong>这是一笔明确的交易：用表达上的冗长换取变换上的通用性。</strong>第四部分后面几章（tiling、融合、bufferization、向量化）全都在收这笔交易的利息。</p>
</div>

## indexing map：从迭代点到访存下标的函数

把 `linalg.generic` 拆开只有四样东西：

| 部件 | 说什么 |
| --- | --- |
| `ins` / `outs` | 哪些张量参与。`outs` 同时是**结果的去处**（destination-passing style，下面细说） |
| `indexing_maps` | 每个操作数一个 `AffineMap`：**迭代点 → 这个操作数的下标** |
| `iterator_types` | 每个迭代维度是 `parallel` 还是 `reduction` |
| region | 每个迭代点上做什么（纯标量代码 + `linalg.yield`） |

迭代空间的形状不用写——它由 `indexing_maps` 和操作数的形状**反推**出来。

三个例子摆在一起，差别就清楚了。逐点加法：

```mlir-norun
indexing_maps = [(d0,d1)->(d0,d1),   // lhs
                 (d0,d1)->(d0,d1),   // rhs
                 (d0,d1)->(d0,d1)]   // out
iterator_types = ["parallel", "parallel"]
```

全图归约：

```mlir-norun
indexing_maps = [(d0,d1)->(d0,d1),   // in：逐点读
                 (d0,d1)->()]        // out：**没有下标** —— 两维都被归约掉
iterator_types = ["reduction", "reduction"]
```

转置：

```mlir-norun
indexing_maps = [(d0,d1)->(d1,d0),   // in：**下标交换**
                 (d0,d1)->(d0,d1)]   // out
iterator_types = ["parallel", "parallel"]
```

**三个都是同一个 `linalg.generic`。** 逐点、归约、转置的区别完全在那两个属性里——region 里的标量代码甚至可以一样（转置的 region 就是直接 yield 输入）。

<div class="note">
<strong>`(d0,d1)->()` 这个写法值得多看一眼</strong>
<p>输出的 map 里不出现任何迭代变量，意思是"所有迭代点都写到同一个地方"——这正是归约的定义。配上 <code>iterator_types = ["reduction", ...]</code>，框架就知道这个维度上的迭代<strong>不能并行</strong>、且需要一个累加器。</p>
<p>反过来，如果 map 里少了某个维度但 iterator 写成 <code>parallel</code>，那是个 bug：多个迭代点并行写同一个位置。verifier 会拦住一部分这类错误。</p>
</div>

## 把 pix 降下来

三条 pattern，各演示一个要点。逐点的那条可以用模板覆盖两个 op：

```cpp-norun
/// 逐点二元运算的通用下降。pix.add 和 pix.mul 的区别只在 region 里那一个
/// 标量 op，所以用模板参数传进来。
template <typename PixOp, typename ScalarOp>
struct PointwiseLowering : OpConversionPattern<PixOp> {
  LogicalResult matchAndRewrite(PixOp op, OpAdaptor adaptor,
                                ConversionPatternRewriter &rewriter) const override {
    auto ty = dyn_cast<RankedTensorType>(op.getType());
    if (!ty || !ty.hasStaticShape())
      return rewriter.notifyMatchFailure(op, "需要静态形状的有阶张量");

    Location loc = op.getLoc();
    // outs 要一个"目标张量"——linalg 是 destination-passing style。
    Value init = tensor::EmptyOp::create(rewriter, loc, ty.getShape(),
                                         ty.getElementType());

    AffineMap id = AffineMap::getMultiDimIdentityMap(ty.getRank(),
                                                     rewriter.getContext());
    SmallVector<AffineMap> maps{id, id, id};           // lhs, rhs, out
    SmallVector<utils::IteratorType> iters(
        ty.getRank(), utils::IteratorType::parallel);

    auto generic = linalg::GenericOp::create(
        rewriter, loc, TypeRange{ty},
        ValueRange{adaptor.getLhs(), adaptor.getRhs()}, ValueRange{init}, maps,
        iters,
        [&](OpBuilder &b, Location nested, ValueRange args) {
          // args = (lhs 的一个元素, rhs 的一个元素, out 的一个元素)
          Value s = ScalarOp::create(b, nested, args[0], args[1]);
          linalg::YieldOp::create(b, nested, s);
        });

    rewriter.replaceOp(op, generic.getResults());
    return success();
  }
};
```

`pix.scale` 那条有个小技巧：

```cpp-norun
Value factor = adaptor.getFactor();
auto generic = linalg::GenericOp::create(
    rewriter, loc, TypeRange{ty}, ValueRange{adaptor.getImage()},
    ValueRange{init}, maps, iters,
    [&](OpBuilder &b, Location nested, ValueRange args) {
      // 标量 factor 不在 args 里 —— 直接引用外面那个值
      Value s = arith::MulFOp::create(b, nested, args[0], factor);
      linalg::YieldOp::create(b, nested, s);
    });
```

**标量不进 `ins`，而是在 region 里直接引用外面的值。** 这么写合法，是因为 `linalg.generic` 的 region **不是** `IsolatedFromAbove`（第 13 章那个 trait 第四次出现）。好处很实在：省掉了"把标量 splat 成一整张图"这次实体化——对比第 16 章那条 arith 路径，它就得先造一个 `tensor.splat`。

归约那条最能说明问题：

```cpp-norun
// 输出是 0 阶张量（一个标量），初值必须是 0——归约的单位元。
Value zero = arith::ConstantOp::create(rewriter, loc,
                                       rewriter.getF32FloatAttr(0.0));
Value empty = tensor::EmptyOp::create(rewriter, loc, ArrayRef<int64_t>{},
                                      ty.getElementType());
Value init = linalg::FillOp::create(rewriter, loc, ValueRange{zero},
                                    ValueRange{empty}).getResult(0);

SmallVector<AffineMap> maps{
    AffineMap::getMultiDimIdentityMap(rank, ctx),      // 输入：逐点读
    AffineMap::get(rank, /*symbolCount=*/0, {}, ctx)};  // 输出：() ← 全归约
SmallVector<utils::IteratorType> iters(rank, utils::IteratorType::reduction);
```

注意那个 `linalg.fill`：**累加器必须显式初始化成单位元**。`tensor.empty` 给的是未定义内容，直接拿它当累加器会得到垃圾。这是 destination-passing style 的一个直接后果——

<div class="keypoint">
<strong>destination-passing style：<code>outs</code> 既是"往哪写"也是"初值"</strong>
<p>region 里那个 <code>%out</code> 参数不是占位符，它是<strong>目标张量当前的值</strong>。逐点运算用不到它（每个点只写一次），但归约必须用：<code>arith.addf %in, %out</code> 里的 <code>%out</code> 就是累加器。</p>
<p>为什么这么设计？因为它让"写到哪"变成 IR 里的显式信息，于是<strong>bufferization（第 22 章）能直接读出"这块结果该放进哪块内存"</strong>，不必做复杂的别名分析。代价是所有 linalg op 都得先有一个目标张量，于是 IR 里多出很多 <code>tensor.empty</code> 和 <code>linalg.fill</code>。</p>
<p>这也是初学 linalg 最容易困惑的地方：<strong><code>outs</code> 不是"输出参数"，而是"目标 + 初值"。</strong></p>
</div>

跑一下三条：


## named op 与 `linalg.generic`

上游还有一批 **named op**：`linalg.matmul`、`linalg.conv_2d`、`linalg.fill`、`linalg.add`……它们是什么？

**就是预设好 `indexing_maps` 和 `iterator_types` 的 `linalg.generic`。** `linalg.matmul` 等价于一个三维迭代空间、maps 为 `(m,n,k)->(m,k)`、`(m,n,k)->(k,n)`、`(m,n,k)->(m,n)`、iterator 为 `[parallel, parallel, reduction]` 的 generic。

用哪个？

| | 用 named op | 用 `linalg.generic` |
| --- | --- | --- |
| 什么时候 | 你的计算正好是那个语义 | 语义特殊，或需要自定义 region |
| 好处 | IR 短、可读；有专门的 pattern 认它（比如 matmul 的向量化策略） | 完全自由 |
| 坏处 | 只有上游定义好的那些 | 通用 pattern 认它，但**针对性优化不认** |

实践上的取舍：**如果你的 op 能映射到 named op，就映射过去**——那意味着你能白拿那批针对性优化。pix 的逐点运算其实可以降到 `linalg.add` / `linalg.mul`，但我们这里用 `generic` 是为了把 indexing map 摊开给你看。第 23 章讲向量化时会再碰到这个取舍。

## 把 indexing map 自己跑一遍

上面那些"map 决定一切"的说法，跑一遍最直观。下面这个模型做两件事：把三种 op 的 map 展开成"每个迭代点访问哪些元素"，然后演示 **tiling 为什么只需要切迭代空间**：

```python
# indexing map 到底表达了什么？为什么有了它，tiling 就能**通用地**实现？
# 用一个 40 行的模型回答：map 是"从迭代点到访存下标"的函数，
# 于是 tiling 只需要切迭代空间，访存下标由 map 自动算出来。

def apply_map(m, point):
    """m 是一串下标表达式，每项说"这一维的下标怎么由迭代点算出来"。
       (d0,d1)->(d0,d1) 写成 [0,1]；(d0,d1)->() 写成 []；
       (d0,d1)->(d1,d0) 写成 [1,0]。"""
    return tuple(point[i] for i in m)

def describe(name, iter_space, maps, iters):
    print(f"\n【{name}】")
    print(f"  迭代空间 {iter_space}，iterator_types = {iters}")
    for who, m in maps.items():
        shape = "标量（全被归约掉）" if not m else f"按 {m} 取下标"
        print(f"    {who:6} map={m or '()'}  → {shape}")
    # 列举前几个迭代点，看每个操作数被访问的位置
    pts = [(i, j) for i in range(iter_space[0]) for j in range(iter_space[1])][:4]
    for p in pts:
        cells = {w: apply_map(m, p) or "()" for w, m in maps.items()}
        print(f"    迭代点 {p}: " + "  ".join(f"{w}{c}" for w, c in cells.items()))

# 三种 op，**同一个 linalg.generic**，只是 map 和 iterator 不同
describe("逐点加法 pix.add", (4, 4),
         {"lhs": [0, 1], "rhs": [0, 1], "out": [0, 1]},
         ["parallel", "parallel"])
describe("全图归约 pix.reduce", (4, 4),
         {"in": [0, 1], "out": []},
         ["reduction", "reduction"])
describe("转置 pix.transpose", (4, 4),
         {"in": [1, 0], "out": [0, 1]},
         ["parallel", "parallel"])

# tiling：只切迭代空间，访存下标由 map 自动跟上 —— 这就是"通用"的含义
print("\n" + "=" * 62)
print("tiling = 把迭代空间切块。访存下标不用单独处理，map 自动跟上：")
MAPS = {"lhs": [0, 1], "rhs": [0, 1], "out": [0, 1]}
TILE = (2, 2)
for bi in range(0, 4, TILE[0]):
    for bj in range(0, 4, TILE[1]):
        # 一个 tile 覆盖的迭代点
        pts = [(bi + i, bj + j) for i in range(TILE[0]) for j in range(TILE[1])]
        # 每个操作数要取的切片 = 那些迭代点经过 map 之后的范围
        slices = {}
        for w, m in MAPS.items():
            idx = [apply_map(m, p) for p in pts]
            lo = tuple(min(x[k] for x in idx) for k in range(len(idx[0])))
            hi = tuple(max(x[k] for x in idx) + 1 for k in range(len(idx[0])))
            slices[w] = f"[{lo[0]}:{hi[0]}, {lo[1]}:{hi[1]}]"
        print(f"  tile ({bi},{bj}): " + "  ".join(f"{w}{s}" for w, s in slices.items()))
print("\n  切片范围是**算出来的**，不是为 add 手写的 —— 换成 transpose 的 map")
print("  [1,0]，同一套逻辑会自动给出转置过的切片。这就是为什么 tiling 能对")
print("  所有 linalg op 通用，而不必为每个 op 写一遍。")
```

```
    in     map=[1, 0]  → 按 [1, 0] 取下标
    out    map=[0, 1]  → 按 [0, 1] 取下标
    迭代点 (0, 0): in(0, 0)  out(0, 0)
    迭代点 (0, 1): in(1, 0)  out(0, 1)
    迭代点 (0, 2): in(2, 0)  out(0, 2)
    迭代点 (0, 3): in(3, 0)  out(0, 3)

==============================================================
tiling = 把迭代空间切块。访存下标不用单独处理，map 自动跟上：
  tile (0,0): lhs[0:2, 0:2]  rhs[0:2, 0:2]  out[0:2, 0:2]
  tile (0,2): lhs[0:2, 2:4]  rhs[0:2, 2:4]  out[0:2, 2:4]
  tile (2,0): lhs[2:4, 0:2]  rhs[2:4, 0:2]  out[2:4, 0:2]
  tile (2,2): lhs[2:4, 2:4]  rhs[2:4, 2:4]  out[2:4, 2:4]

  切片范围是**算出来的**，不是为 add 手写的 —— 换成 transpose 的 map
  [1,0]，同一套逻辑会自动给出转置过的切片。这就是为什么 tiling 能对
  所有 linalg op 通用，而不必为每个 op 写一遍。
```

看最后那段 tiling 的输出：**切片范围是由 map 算出来的，不是为 `add` 手写的**。把 map 换成转置的 `[1, 0]`，同一套逻辑会自动给出转置过的切片。

**这就是"通用"的全部含义**，也是 `TilingInterface` 这个接口能存在的原因。对比一下：如果每个 op 的循环结构只存在于文档里，tiling 就得为每个 op 写一遍——那正是路 A 的处境。

## 动手：把 pix.transpose 也降下来

`pix-to-linalg` 现在没处理 `pix.transpose`。它是最能体现 indexing map 表达力的一个——**region 里什么都不算，只把输入 yield 出去，全部工作由 map 完成**：

```cpp-norun
// in 的 map 是 (d0,d1)->(d1,d0)，out 的是 (d0,d1)->(d0,d1)
SmallVector<AffineMap> maps{
    AffineMap::getPermutationMap(ArrayRef<unsigned>{1, 0}, ctx),
    AffineMap::getMultiDimIdentityMap(2, ctx)};
// region：直接 yield 输入元素
[&](OpBuilder &b, Location nested, ValueRange args) {
  linalg::YieldOp::create(b, nested, args[0]);
}
```

加完记得把 `TransposeOp` 加进 `addIllegalOp`，然后跑：

```bash
pix-opt /tmp/l20.mlir --pix-to-linalg
```

**再改一处**（这个更有意思）：把逐点那条 pattern 从 `linalg.generic` 改成 named op `linalg.add`，然后对比两者被 `--linalg-generalize-named-ops` 处理之后的结果。你会发现 named op 只是 generic 的语法糖——但**在被 generalize 之前**，针对 named op 的优化 pattern 认得它，而对 generic 一无所知。这就是前面那张取舍表的实感。

---

**这一章的要点**

- 绕 `linalg` 这一道的理由不是"更规范"，而是**保留迭代空间**。`arith.addf` 在 tensor 上是不透明的："它等价于双重循环"这件事只存在于文档里，IR 里找不到。
- **实测的分界线**：走 linalg 降下来的 IR 能被 `transform.structured.tile_using_for` tile 成嵌套 `scf.for`；走 arith 降下来的直接报 `only ops implementing TilingInterface are supported`。
- `linalg.generic` 只有四样东西：`ins`/`outs`、`indexing_maps`（**迭代点 → 访存下标**）、`iterator_types`（`parallel` / `reduction`）、region（每个点上算什么）。**迭代空间的形状是反推出来的**，不用写。
- **同一个 `linalg.generic`，只换 map 和 iterator，就是完全不同的计算**：逐点、归约（输出 map 是 `(d0,d1)->()`）、转置（输入 map 交换下标）。region 里的标量代码甚至可以一样。
- **tiling 只需要切迭代空间**，访存切片由 map 自动算出来——所以它能对所有 linalg op 通用。这就是 `TilingInterface` 存在的根据。
- **destination-passing style**：`outs` 既是"往哪写"也是"初值"。region 里的 `%out` 是目标张量当前的值——逐点运算用不到，**归约必须用它当累加器**，而且累加器要用 `linalg.fill` 显式初始化成单位元（`tensor.empty` 给的是未定义内容）。这个设计让第 22 章的 bufferization 能直接读出"结果该放哪块内存"。
- **标量操作数不进 `ins`**，直接在 region 里引用外面的值——因为 `linalg.generic` 的 region 不是 `IsolatedFromAbove`。这省掉了一次"splat 成整张图"的实体化。
- **named op 就是预设好 map 和 iterator 的 generic**。能映射过去就映射——那意味着白拿针对它们的优化 pattern；反过来，generalize 成 generic 之后那些优化就不认了。
- 这一章的交易要看清：**用表达上的冗长换取变换上的通用性**。第 21–24 章都在收这笔利息。

**pix 进度**：新增 `pix-to-linalg`（逐点用模板覆盖 `add`/`mul`，`scale` 演示"标量在 region 里直接引用"，`reduce` 演示归约 map 与累加器初始化）与 `to_linalg.mlir`。现在 pix 降下来的 IR 可以被第 18 章的 transform 调度直接 tile —— 第四部分的地基铺好了。`check-pix` 从 16 涨到 17 个文件。

下一章正式做 **tiling 与融合**：tile 的数学（迭代空间切分 + 访存切片，这一章的模拟器已经演示了一半）、`scf.forall` 与并行、producer-consumer 融合为什么能把两个 `linalg.generic` 合成一个，以及 stencil 运算特有的 **halo**——`pix.convolve` 分块时边界要多取几行，那是 tiling 里最容易出错的地方。
