# 第 23 章 vector 方言：向量化、mask 与按目标宽度展开

## 这一章想让你带走什么

<div class="goal-box">
<p>第 21 章把计算切成了 tile，第 22 章把 tensor 变成了 memref。现在 tile 里面还是"逐元素算一遍"的循环。这一章把它变成<strong>向量指令</strong>。</p>
<p>三件事。<strong>一、向量化怎么发生</strong>：一行 <code>transform.structured.vectorize</code>，<code>linalg.generic</code> 的 region 里那个标量 <code>arith.addf</code> 变成 <code>vector&lt;4x4xf32&gt;</code> 上的 <code>arith.addf</code>——<strong>同一个 op，换了类型</strong>。读写则变成 <code>vector.transfer_read/write</code>。</p>
<p><strong>二、mask 为什么必须存在。</strong>这是 vector 方言最不像"普通 SIMD"的地方。向量宽度是固定的，数据边界不是——8 除以 3 除不尽，最后一块是残缺的。我们会用 tile 4 和 tile 3 两次实测对照：前者 <code>in_bounds = [true, true]</code> 干干净净，后者冒出 <code>vector.create_mask</code> 和 <code>vector.mask { ... }</code>。</p>
<p><strong>三、为什么还要 unroll，而且必须在向量化之后。</strong><code>vector&lt;4x4xf32&gt;</code> 是一个<strong>逻辑</strong>形状，没有哪台机器有"4×4 寄存器"。把它落到具体宽度是另一步（<code>--convert-vector-to-scf</code> 等），这一步分开做的好处很实在：同一份向量化结果能面向不同宽度的目标各自展开。</p>
</div>

## 向量化：一行调度

接着第 21 章那条调度往下加一句：

```mlir-norun
%tiled, %l:2 = transform.structured.tile_using_for %g tile_sizes [4, 4] : …
// vector_sizes 要和 tile 大小对上 —— 向量化是在 tile 内部做的
transform.structured.vectorize %tiled vector_sizes [4, 4] : !transform.any_op
```

```mlir-lower
// RUN: pix-opt %s --pix-to-linalg --transform-interpreter --canonicalize
module attributes {transform.with_named_sequence} {
  func.func @vec(%a: tensor<8x8xf32>, %b: tensor<8x8xf32>) -> tensor<8x8xf32> {
    %s = pix.add %a, %b : tensor<8x8xf32>
    return %s : tensor<8x8xf32>
  }
  transform.named_sequence @__transform_main(%root: !transform.any_op {transform.readonly}) {
    %g = transform.structured.match ops{["linalg.generic"]} in %root
      : (!transform.any_op) -> !transform.any_op
    %tiled, %l:2 = transform.structured.tile_using_for %g tile_sizes [4, 4]
      : (!transform.any_op) -> (!transform.any_op, !transform.any_op, !transform.any_op)
    transform.structured.vectorize %tiled vector_sizes [4, 4] : !transform.any_op
    transform.yield
  }
}
```

运行结果（函数部分）：

```
  func.func @vec(%arg0: tensor<8x8xf32>, %arg1: tensor<8x8xf32>) -> tensor<8x8xf32> {
    %0 = ub.poison : f32
    %c4 = arith.constant 4 : index
    %c8 = arith.constant 8 : index
    %c0 = arith.constant 0 : index
    %1 = tensor.empty() : tensor<8x8xf32>
    %2 = scf.for %arg2 = %c0 to %c8 step %c4 iter_args(%arg3 = %1) -> (tensor<8x8xf32>) {
      %3 = scf.for %arg4 = %c0 to %c8 step %c4 iter_args(%arg5 = %arg3) -> (tensor<8x8xf32>) {
        %extracted_slice = tensor.extract_slice %arg0[%arg2, %arg4] [4, 4] [1, 1] : tensor<8x8xf32> to tensor<4x4xf32>
        %extracted_slice_0 = tensor.extract_slice %arg1[%arg2, %arg4] [4, 4] [1, 1] : tensor<8x8xf32> to tensor<4x4xf32>
        %extracted_slice_1 = tensor.extract_slice %arg5[%arg2, %arg4] [4, 4] [1, 1] : tensor<8x8xf32> to tensor<4x4xf32>
        %4 = vector.transfer_read %extracted_slice[%c0, %c0], %0 {in_bounds = [true, true]} : tensor<4x4xf32>, vector<4x4xf32>
        %5 = vector.transfer_read %extracted_slice_0[%c0, %c0], %0 {in_bounds = [true, true]} : tensor<4x4xf32>, vector<4x4xf32>
        %6 = arith.addf %4, %5 : vector<4x4xf32>
        %7 = vector.transfer_write %6, %extracted_slice_1[%c0, %c0] {in_bounds = [true, true]} : vector<4x4xf32>, tensor<4x4xf32>
        %inserted_slice = tensor.insert_slice %7 into %arg5[%arg2, %arg4] [4, 4] [1, 1] : tensor<4x4xf32> into tensor<8x8xf32>
        scf.yield %inserted_slice : tensor<8x8xf32>
      }
      scf.yield %3 : tensor<8x8xf32>
    }
    return %2 : tensor<8x8xf32>
  }
```

**`linalg.generic` 不见了。** 取而代之的是三步：

```mlir-norun
%4 = vector.transfer_read %extracted_slice[%c0, %c0], %0 {in_bounds = [true, true]} : tensor<4x4xf32>, vector<4x4xf32>
%6 = arith.addf %4, %5 : vector<4x4xf32>
%7 = vector.transfer_write %6, %extracted_slice_1[%c0, %c0] {in_bounds = [true, true]} : vector<4x4xf32>, tensor<4x4xf32>
```

注意中间那行：**`arith.addf` 还是 `arith.addf`，只是类型从 `f32` 变成了 `vector<4x4xf32>`。** 这是 MLIR 的一个设计选择——算术 op 在标量和向量上是同一个 op，靠类型区分。所以"向量化"对计算本身几乎不需要做什么，真正的工作全在**读写**那两头。

<div class="keypoint">
<strong><code>vector.transfer_read/write</code> 是这个方言的核心，不是 <code>load/store</code> 的花哨版</strong>
<p>它们解决的是一个具体问题：<strong>从多维的、可能不连续、可能越界的内存里，搬出一块规整的向量</strong>。三件事都由它处理——</p>
<p><strong>① 多维到一维的重排</strong>：它带一个 permutation map（这里被省略了，因为是恒等），能表达"读的时候顺便转置"。<strong>② 边界</strong>：<code>in_bounds</code> 或 mask（下一节）。<strong>③ 填充值</strong>：那个 <code>%0 = ub.poison : f32</code> 就是越界时填什么。</p>
<p>把这三件事收在一个 op 里，是为了让向量化的 pattern 只需要生成"逻辑意图"，具体怎么落到 <code>load</code>/<code>maskedload</code>/<code>gather</code> 交给后面的 lowering。这和第 20 章 linalg 的思路一样：<strong>先把意图写清楚，再分步降级。</strong></p>
</div>

## mask：向量宽度固定，数据边界不固定

上面那个例子很干净，因为 **8 能被 4 整除**——每个 tile 都是满的 4×4，所以 `in_bounds = [true, true]`。

把 tile 改成 3：

```mlir-norun
%tiled, %l:2 = transform.structured.tile_using_for %g tile_sizes [3, 3] : …
transform.structured.vectorize %tiled vector_sizes [3, 3] : !transform.any_op
```

运行结果（循环体内那几行）：

```
        %6 = vector.create_mask %4, %5 : vector<3x3xi1>
        %7 = vector.mask %6 { vector.transfer_read %extracted_slice[%c0, %c0], %0 {in_bounds = [true, true]} : tensor<?x?xf32>, vector<3x3xf32> } : vector<3x3xi1> -> vector<3x3xf32>
        %8 = vector.mask %6 { vector.transfer_read %extracted_slice_0[%c0, %c0], %0 {in_bounds = [true, true]} : tensor<?x?xf32>, vector<3x3xf32> } : vector<3x3xi1> -> vector<3x3xf32>
        %9 = arith.addf %7, %8 : vector<3x3xf32>
        %10 = vector.mask %6 { vector.transfer_write %9, %extracted_slice_1[%c0, %c0] {in_bounds = [true, true]} : vector<3x3xf32>, tensor<?x?xf32> } : vector<3x3xi1> -> tensor<?x?xf32>
```

三处变化：

**切片类型变成了 `tensor<?x?xf32>`。** 因为最后一块只有 2 行/2 列，形状不再静态。

**多了一个 `vector.create_mask %4, %5 : vector<3x3xi1>`。** `%4`/`%5` 是这一块的**实际**尺寸（运行时算出来的），mask 就是"哪些通道是有效的"。

**读写都被包进了 `vector.mask { ... }`。** 这个 op 把一个操作和一个 mask 绑在一起：mask 为 false 的通道，读取返回填充值、写入被丢弃。

<div class="warn">
<strong>别把 <code>in_bounds = [true, true]</code> 当成"没有 mask 就一定安全"</strong>
<p>注意 masked 版本里的 <code>transfer_read</code> <strong>仍然</strong>标着 <code>in_bounds = [true, true]</code>——因为在 <code>vector.mask</code> 的保护下，它确实不会越界。两个机制是<strong>叠加</strong>的，不是二选一：</p>
<p><code>in_bounds</code> 是给 lowering 的<strong>承诺</strong>（"你可以直接用普通 load，不必生成边界检查"）；<code>vector.mask</code> 是<strong>运行时</strong>的通道选择。看到 <code>in_bounds = [true]</code> 时要先看它有没有被 mask 包着——单独看那个属性会得出错误结论。</p>
</div>

<div class="keypoint">
<strong>mask 的代价，以及为什么 tile 大小该配合向量宽度</strong>
<p>mask 不是免费的：多一次 <code>create_mask</code>（要算实际尺寸）、读写走的是 masked 指令（在很多架构上比普通 load/store 慢）、而且残缺块里有一部分通道是白算的。</p>
<p>所以实践上有一条朴素但有效的规则：<strong>让 tile 大小是向量宽度的整数倍，并尽量整除数据尺寸。</strong>整除不了的时候，常见做法是"主循环 + 收尾"——主体用不带 mask 的满向量跑，残缺部分单独处理（<code>transform.structured.pad</code> 或专门的 peeling）。这一章的模拟器会把"除不尽有多糟"算给你看。</p>
</div>

## 两条向量化的路

MLIR 里向量化有两条路，用途不同：

| | linalg vectorizer | 手写 vector pattern |
| --- | --- | --- |
| 怎么用 | `transform.structured.vectorize`，或对应的 pass | 自己写 `RewritePattern` 生成 `vector.*` |
| 适用 | `linalg` op（有 indexing map，迭代空间清楚） | 任何 op，包括你自己方言的 |
| 好处 | 一行搞定，permutation map 自动从 indexing map 推出 | 完全可控，能表达 vectorizer 想不到的模式 |
| 坏处 | 只认结构化 op；能做的变换是固定的那套 | 要自己处理边界、填充、permutation，容易写错 |

**默认走第一条。** 第 20 章那笔"用冗长换通用性"的交易，在这里又收了一次利息：因为 pix 已经降成了 `linalg.generic`，向量化只要一行；如果我们当初停在 `arith.addf` 上（第 16 章那条路），这里就得自己写 pattern。

第二条路的正当用途是**特殊模式**——比如某个架构有"一条指令做 4×4 转置"的支持，vectorizer 不知道，你得手写一个 pattern 把 `linalg.transpose` 直接变成那条指令。第 25 章看 GPU、第 26 章看 Triton 时会见到大量这类手写 pattern。

## unroll：从逻辑形状到机器宽度

`vector<4x4xf32>` 是个**逻辑**形状。没有哪台机器有 4×4 的寄存器——x86 的 AVX2 是 8×f32 一条，AVX-512 是 16×f32，ARM NEON 是 4×f32。所以还得有一步把逻辑形状落到机器宽度。

标准管线里这一步由 `--convert-vector-to-scf` 之类完成（它把 N 维 transfer 展成"循环 + 一维 transfer"）：

```bash
mlir-opt u23.mlir --convert-vector-to-scf
```

运行结果（截取）：

```
  func.func @unroll(%arg0: memref<8x8xf32>, %arg1: memref<8x8xf32>, %arg2: memref<8x8xf32>) {
    %c1 = arith.constant 1 : index
    %c4 = arith.constant 4 : index
    %0 = ub.poison : f32
    %c0 = arith.constant 0 : index
    %alloca = memref.alloca() : memref<vector<4x4xf32>>
    %alloca_0 = memref.alloca() : memref<vector<4x4xf32>>
    %alloca_1 = memref.alloca() : memref<vector<4x4xf32>>
    %1 = vector.type_cast %alloca : memref<vector<4x4xf32>> to memref<4xvector<4xf32>>
    scf.for %arg3 = %c0 to %c4 step %c1 {
      %7 = vector.transfer_read %arg0[%arg3, %c0], %0 {in_bounds = [true]} : memref<8x8xf32>, vector<4xf32>
      memref.store %7, %1[%arg3] : memref<4xvector<4xf32>>
    }
    %2 = memref.load %alloca[] : memref<vector<4x4xf32>>
    %3 = vector.type_cast %alloca_0 : memref<vector<4x4xf32>> to memref<4xvector<4xf32>>
    scf.for %arg3 = %c0 to %c4 step %c1 {
```

二维的 `transfer_read` 变成了**一个循环，每次读一个 `vector<4xf32>`**，中间用一块栈上的 `memref<4xvector<4xf32>>` 暂存（那个 `vector.type_cast` 就是把它重新解释成"4 个一维向量的数组"）。

<div class="keypoint">
<strong>为什么 unroll 必须在向量化<em>之后</em></strong>
<p>因为两件事关心的是不同的东西：<strong>向量化关心"逻辑上一次算多少"</strong>（由 tile 大小和 indexing map 决定），<strong>unroll 关心"这台机器一条指令能算多少"</strong>（由目标决定）。</p>
<p>分开做的收益很直接：<strong>同一份向量化结果，能面向不同宽度的目标各自展开。</strong>把两者合成一步（直接向量化成机器宽度）意味着换目标就要重新向量化，而向量化是个涉及 mask、permutation、边界的复杂变换——重做的成本远高于重做 unroll。</p>
<p>这是 MLIR "渐进下降"思路的又一个实例，和第 20 章（先 linalg 再循环）、第 22 章（先 tensor 再 memref）是同一个道理：<strong>每一步只决定一件事，把决定推迟到信息最充分的时候。</strong></p>
</div>

## 把两个不匹配算出来

mask 和 unroll 各对应一个"不匹配"。下面这个模型把两者都量化——尤其是"除不尽有多糟"：

```python
# 向量化要处理两个不匹配：
#   ① 数据边界 vs 固定向量宽度  → mask
#   ② 逻辑向量形状 vs 目标寄存器宽度 → unroll
# 这个模型把两者都算出来。

def tiles(n, t):
    """把长度 n 按 t 切块，返回每块的 (起点, 实际长度)。"""
    out = []
    i = 0
    while i < n:
        out.append((i, min(t, n - i)))
        i += t
    return out

def show_masking(n, t):
    print(f"\n【{n}x{n} 图，tile {t}x{t}，向量宽度固定为 {t}】")
    need_mask = False
    for (r0, rl) in tiles(n, t):
        row = []
        for (c0, cl) in tiles(n, t):
            full = (rl == t and cl == t)
            need_mask |= not full
            row.append(f"{rl}x{cl}{'' if full else '*'}")
        print("    " + "  ".join(row))
    print(f"    带 * 的是残缺块 → {'需要 mask' if need_mask else '不需要 mask'}"
          + ("（每次读写都要带上 create_mask）" if need_mask else "（in_bounds 全 true）"))
    return need_mask

show_masking(8, 4)      # 整除
show_masking(8, 3)      # 除不尽
show_masking(8, 5)      # 除不尽且更糟

# ② unroll：逻辑上的 vector<4x4xf32> 在只有 128 位寄存器（vector<4xf32>）的机器上
print("\n" + "=" * 62)
LOGICAL = (4, 4)
for reg_lanes in (4, 8, 16):
    total = LOGICAL[0] * LOGICAL[1]
    n_ops = -(-total // reg_lanes)          # 向上取整
    waste = n_ops * reg_lanes - total
    print(f"  vector<{LOGICAL[0]}x{LOGICAL[1]}xf32>（{total} 个元素）在 "
          f"{reg_lanes} 通道的寄存器上：")
    print(f"    展成 {n_ops} 条向量指令"
          + (f"，最后一条浪费 {waste} 个通道" if waste else "，刚好整除"))
print("\n  所以 unroll **必须在向量化之后**：向量化只关心「逻辑上一次算多少」，")
print("  unroll 才关心「这台机器一条指令能算多少」。两件事分开，同一份")
print("  向量化结果就能面向不同宽度的目标各自展开。")
```

运行结果：

```

【8x8 图，tile 4x4，向量宽度固定为 4】
    4x4  4x4
    4x4  4x4
    带 * 的是残缺块 → 不需要 mask（in_bounds 全 true）

【8x8 图，tile 3x3，向量宽度固定为 3】
    3x3  3x3  3x2*
    3x3  3x3  3x2*
    2x3*  2x3*  2x2*
    带 * 的是残缺块 → 需要 mask（每次读写都要带上 create_mask）

【8x8 图，tile 5x5，向量宽度固定为 5】
    5x5  5x3*
    3x5*  3x3*
    带 * 的是残缺块 → 需要 mask（每次读写都要带上 create_mask）

==============================================================
  vector<4x4xf32>（16 个元素）在 4 通道的寄存器上：
    展成 4 条向量指令，刚好整除
  vector<4x4xf32>（16 个元素）在 8 通道的寄存器上：
    展成 2 条向量指令，刚好整除
  vector<4x4xf32>（16 个元素）在 16 通道的寄存器上：
    展成 1 条向量指令，刚好整除

  所以 unroll **必须在向量化之后**：向量化只关心「逻辑上一次算多少」，
  unroll 才关心「这台机器一条指令能算多少」。两件事分开，同一份
  向量化结果就能面向不同宽度的目标各自展开。
```

看那三组 masking：**tile 4 时 4 块全满；tile 3 时 9 块里 5 块残缺；tile 5 时 4 块里 3 块残缺。** 残缺块越多，mask 的开销占比越高，白算的通道越多。这就是前面那条"让 tile 大小整除数据尺寸"的量化依据。

下半部分的 unroll 算术说明了分层的价值：**同一个 `vector<4x4xf32>`，在 4/8/16 通道的机器上分别展成 4/2/1 条指令**，而向量化那一步完全不需要知道这件事。

## 动手：找出 mask 的临界点

把 `tile_sizes` 和 `vector_sizes` 一起改（两者必须一致），跑这条命令数 mask：

```bash
for t in 2 3 4 5 8; do
  echo -n "tile $t: "
  sed "s/\[4, 4\]/[$t, $t]/g" v23.mlir \
    | pix-opt /dev/stdin --pix-to-linalg --transform-interpreter --canonicalize \
    | grep -c vector.create_mask
done
```

**只有 2、4、8 会得到 0。** 自己确认一下为什么——然后回头看第 21 章那张"tile 大小 vs halo 冗余"的表：**tile 大小同时受三个因素约束**（cache 容量、halo 冗余、向量宽度整除性），而它们的最优点往往不一致。这就是自动调优（第 18 章末尾提过）要解决的问题。

**再改一处**：把 `transform.structured.vectorize` 的 `vector_sizes` 故意写成和 tile 不一致（比如 tile `[4, 4]` 但 vector `[2, 2]`），看会发生什么。**报错信息本身值得读**——它会告诉你向量化对形状的要求。

---

**这一章的要点**

- 向量化之后，**算术 op 没变，只是类型从 `f32` 变成了 `vector<4x4xf32>`**。MLIR 让算术 op 在标量和向量上共用同一个 op，所以"向量化"的真正工作全在读写两头。
- **`vector.transfer_read/write` 是这个方言的核心**，一个 op 同时处理三件事：多维到一维的重排（permutation map）、边界（`in_bounds` / mask）、越界填充值。把意图收在一个 op 里，具体落到 `load`/`maskedload`/`gather` 交给后续 lowering——和 linalg 一样的思路。
- **mask 存在的根本原因：向量宽度固定，数据边界不固定。** tile 能整除时 `in_bounds = [true, true]` 干净利落；除不尽时切片变成 `tensor<?x?xf32>`，并冒出 `vector.create_mask` + `vector.mask { ... }`。
- **`in_bounds` 和 `vector.mask` 是叠加的，不是二选一。** masked 版本里 `transfer_read` 仍标着 `in_bounds = [true, true]`——因为在 mask 保护下它确实不越界。单独看那个属性会得出错误结论。
- **mask 有代价**：多一次 `create_mask`、走 masked 指令（很多架构更慢）、残缺块有通道白算。所以**让 tile 大小是向量宽度的整数倍并尽量整除数据尺寸**；实在不行就"主循环 + 收尾"。
- 两条向量化的路：**默认用 linalg vectorizer**（一行调度，permutation map 从 indexing map 自动推出）；**手写 pattern 留给特殊模式**（某架构的专用指令、vectorizer 想不到的模式）。pix 能走第一条，靠的是第 20 章那次"降到 linalg"的投资。
- **`vector<4x4xf32>` 是逻辑形状，没有机器有这种寄存器。** unroll 是另一步：同一份向量化结果在 4/8/16 通道的目标上分别展成 4/2/1 条指令。
- **unroll 必须在向量化之后**，因为两者关心的东西不同：向量化关心"逻辑上一次算多少"，unroll 关心"一条指令能算多少"。分开的收益是同一份向量化结果可面向多目标——这是第 20、22 章那个"渐进下降"原则的又一次体现。
- tile 大小同时受三个因素约束：**cache 容量、halo 冗余、向量宽度整除性**，而它们的最优点往往不一致——这正是自动调优要解决的问题。
