# 第 15 章 声明式重写：DRR 与 PDLL，以及什么时候别用它们

## 这一章想让你带走什么

<div class="goal-box">
<p>第 14 章那条 pattern 写了三十行 C++，而它做的事——"看到 <code>transpose(transpose(x))</code> 就换成 <code>x</code>"——用一句话就说完了。MLIR 提供两套声明式方案来消掉这些样板：<strong>DRR</strong>（Declarative Rewrite Rule，写在 TableGen 里的 <code>Pat&lt;&gt;</code>）和 <strong>PDLL</strong>（一门专门的小语言，编译成 <code>pdl</code> 方言的 IR）。</p>
<p>这一章两样都真跑一遍：给 pix 写四条 <code>Pat&lt;&gt;</code>，接上一个 <code>pix-drr</code> pass，效果和第 11、14 章的手写版逐字一致；再写一份 <code>.pdll</code>，用 <code>mlir-pdll</code> 编出来看它到底变成了什么。</p>
<p>但这一章最重要的产出不是语法，而是<strong>一条界线</strong>。我们会按"从最舒服到最别扭"的顺序排四条 pattern，让天花板自己显形：<strong>匹配</strong>永远表达得出来，<strong>构造结果</strong>才是卡点。第三条就撞上了 <code>mlir-tblgen</code> 的一句拒绝，第四条只能用 <code>NativeCodeCall</code> 逃回 C++。看完你会有一个不含糊的判据，知道什么时候老老实实写 C++。</p>
</div>

## DRR：四条 `Pat<>`，从舒服到别扭

DRR 写在 `.td` 里，放 `lib/` 而不是 `include/`——这些 pattern 是实现细节，没人需要 include 它们（上游 `mlir/lib/Dialect/Shape/IR/ShapeCanonicalization.td` 也这么放）。

### ① 纯结构改写：DRR 的主场

```tablegen
def TransposeTwiceIsNop : Pat<
  (Pix_TransposeOp (Pix_TransposeOp $x)),
  (replaceWithValue $x)>;
```

读法：左边是要匹配的 **DAG**（外层 `transpose` 套内层 `transpose`），`$x` 是捕获变量；右边 `replaceWithValue` 表示"用这个已有的值替换整个匹配"。

**这三行等价于第 11 章那十几行的 `TransposeOp::fold`。** 收益非常直接。

### ② 加约束：仍然舒服

上面那条其实不够严谨——两次转置的结果类型得和原输入一致才能替换。第 11 章的 `fold` 里我们手写了一个 `if`，DRR 里写成一个 `Constraint`：

```tablegen
def SameTypeAs : Constraint<
  CPred<"$0.getType() == $1.getType()">, "两个值类型相同">;

def TransposeTwiceChecked : Pat<
  (Pix_TransposeOp:$outer (Pix_TransposeOp $x)),
  (replaceWithValue $x),
  [(SameTypeAs $x, $outer)]>;
```

`Pat<>` 的第三个参数是约束列表。`:$outer` 这个写法是给匹配到的 op 起个名字，好在约束里引用它。`CPred` 里就是一句 C++ 表达式，`$0`、`$1` 按位置替换。

### ③ 第一道摩擦：目标 op 带着你手里没有的参数

合并两层 `scale` 需要造一个 `arith.mulf`。照直觉写：

```tablegen
def MergeScalesDRR : Pat<
  (Pix_ScaleOp (Pix_ScaleOp $x, $a), $b),
  (Pix_ScaleOp $x, (Arith_MulFOp $a, $b))>;
```

`mlir-tblgen` 拒绝：

```
error: op 'arith.mulf' argument number mismatch: 2 in pattern vs. 4 in definition
```

因为 `arith.mulf` 的 `arguments` 是**四个**：`lhs`、`rhs`、`fastmath`、`roundingmode`（`mlir/include/mlir/Dialect/Arith/IR/ArithOps.td:101`）。**DRR 建目标 op 时必须按 ODS 里的 `arguments` 给全**，哪怕后两个有默认值、哪怕你根本不关心它们。

上游怎么绕的？看 `ArithCanonicalization.td:550`——它们把源 pattern 里捕获到的 `$fmf, $rm` 转发过去。可我们是**凭空造**一个 mulf，手里没有这两个属性。于是只能逃回 C++ 一行：

```tablegen
def MakeMulF : NativeCodeCall<
  "::mlir::arith::MulFOp::create($_builder, $_builder.getUnknownLoc(), $0, $1)">;

def MergeScalesDRR : Pat<
  (Pix_ScaleOp (Pix_ScaleOp $x, $a), $b),
  (Pix_ScaleOp $x, (MakeMulF $a, $b))>;
```

`NativeCodeCall` 里 `$_builder` 是当前 rewriter，`$0`/`$1` 按位置替换成传进来的参数。这一行正好用上 `arith.mulf` 自带的三参数 builder，把 `fastmath`/`roundingmode` 交给默认值。

**这是 DRR 第一次不划算**：声明式的可读性开始被样板抵消，而且你已经需要同时懂 TableGen 的 DAG 语法和 C++ 两套东西了。

### ④ 天花板：要凭空造一个常量

`add(%x, %x)` → `scale(%x, 2.0)`。那个 `2.0` 不在输入里，DRR 的 DAG 语法**表达不出"造一个 f32 常量 2.0"**：

```tablegen
def MakeF32Two : NativeCodeCall<"$_builder.getF32FloatAttr(2.0)">;
def SameValue : Constraint<CPred<"$0 == $1">, "两个值是同一个">;

def AddSelfToScaleDRR : Pat<
  (Pix_AddOp:$op $x, $y),
  (Pix_ScaleOp $x, (Arith_ConstantOp (MakeF32Two))),
  [(SameValue $x, $y)]>;
```

注意 `(MakeF32Two)` 外面那对括号——`NativeCodeCall` 当 DAG **节点**用时要带括号，当**叶子**用时不带。少写会得到 `referencing unbound symbol ''`，一句毫无线索的报错。我撞过。

到这一步，一条 `Pat<>` 里有两处 `NativeCodeCall`、一个 `Constraint`，加起来的行数和第 14 章的 C++ 版差不多，**可读性反而更差**——因为逻辑散在 TableGen 和 C++ 字符串两边。

### 效果和手写版逐字一致

四条 `Pat<>` 装进一个 pass，一条 C++ pattern 都不用写：

```cpp-norun
struct PixDRRPass : impl::PixDRRBase<PixDRRPass> {
  void runOnOperation() override {
    RewritePatternSet patterns(&getContext());
    populateWithGenerated(patterns);   // ← 一句话装完所有 Pat<>
    if (failed(applyPatternsGreedily(getOperation(), std::move(patterns))))
      signalPassFailure();
  }
};
```

`populateWithGenerated()` 是 `mlir-tblgen -gen-rewriters` 顺带生成的。跑起来：

```mlir-lower
// RUN: pix-opt %s --pix-drr
func.func @twice(%img: tensor<4x8xf32>) -> tensor<4x8xf32> {
  %t1 = pix.transpose %img : tensor<4x8xf32> to tensor<8x4xf32>
  %t2 = pix.transpose %t1 : tensor<8x4xf32> to tensor<4x8xf32>
  return %t2 : tensor<4x8xf32>
}
func.func @nested(%img: tensor<4x4xf32>, %a: f32, %b: f32) -> tensor<4x4xf32> {
  %s1 = pix.scale %img, %a : tensor<4x4xf32>
  %s2 = pix.scale %s1, %b : tensor<4x4xf32>
  return %s2 : tensor<4x4xf32>
}
func.func @self(%img: tensor<4x4xf32>) -> tensor<4x4xf32> {
  %r = pix.add %img, %img : tensor<4x4xf32>
  return %r : tensor<4x4xf32>
}
```

运行结果：

```
module {
  func.func @twice(%arg0: tensor<4x8xf32>) -> tensor<4x8xf32> {
    return %arg0 : tensor<4x8xf32>
  }
  func.func @nested(%arg0: tensor<4x4xf32>, %arg1: f32, %arg2: f32) -> tensor<4x4xf32> {
    %0 = arith.mulf %arg1, %arg2 : f32
    %1 = pix.scale %arg0, %0 : tensor<4x4xf32>
    return %1 : tensor<4x4xf32>
  }
  func.func @self(%arg0: tensor<4x4xf32>) -> tensor<4x4xf32> {
    %cst = arith.constant 2.000000e+00 : f32
    %0 = pix.scale %arg0, %cst : tensor<4x4xf32>
    return %0 : tensor<4x4xf32>
  }
}
```

和第 11 章的 fold/canonicalizer、第 14 章的手写 pattern 输出**完全一样**。声明式和手写式是等价的，差别只在写起来的体感。

投入产出比也可以量一下：**86 行 `.td`（含大量注释）里的 4 条 `Pat<>`，生成了 236 行 C++、4 个 pattern 结构体。**

<div class="note">
<strong>一个观察：pattern 匹配的是内层</strong>
<p>三条链式转置 <code>t3(t2(t1(x)))</code> 跑 <code>--pix-drr</code>，结果剩<strong>一条</strong>：pattern 在内层那一对 <code>(t2, t1)</code> 上触发，把它们消掉，剩下 <code>t3(x)</code>。所以奇数条必然剩一条、偶数条必然全消。<strong>DAG 匹配的形状和 greedy driver 的遍历顺序是两件独立的事</strong>，写测试时别把两者的效果混在一起断言。</p>
</div>

## PDLL：把 pattern 本身变成 IR

PDLL 是一门独立的小语言，语法比 TableGen 的 DAG 好读得多。同一条改写：

```
#include "Pix/PixOps.td"

Pattern TransposeTwiceIsNop {
  let inner = op<pix.transpose>(x: Value);
  let outer = op<pix.transpose>(inner);
  replace outer with x;
}
```

和 DRR 那三行比，**这个读起来像人话**：声明两个 op、说清嵌套关系、替换。没有括号嵌套的 DAG，没有 `$` 前缀。

关键在它编译成什么。`mlir-pdll -x mlir`：

```bash
mlir-pdll -x mlir -I $LLVM/mlir/include -I code/pix/include pix.pdll
```

运行结果（截取第一条）：

```
module {
  pdl.pattern @TransposeTwiceIsNop : benefit(0) {
    %0 = operand
    %1 = types
    %2 = operation "pix.transpose"(%0 : !pdl.value)  -> (%1 : !pdl.range<type>)
    %3 = results of %2
    %4 = types
    %5 = operation "pix.transpose"(%3 : !pdl.range<value>)  -> (%4 : !pdl.range<type>)
    rewrite %5 {
      replace %5 with(%0 : !pdl.value)
    }
  }
}
```

**pattern 变成了 IR。** 这是个很 MLIR 的想法：既然一切都是 op，那"重写规则"为什么不能也是 op？`pdl` 就是这么一个方言，PDLL 是它的前端语法。第 18 章的 transform 方言走的是同一条思路——把"怎么变换"本身写成 IR。

<div class="warn">
<strong>PDLL 的默认 benefit 是 0，不是 1</strong>
<p>注意上面那行 <code>benefit(0)</code>。而 C++ 的 <code>OpRewritePattern</code> 默认是 1，DRR 的 <code>Pat&lt;&gt;</code> 也从 1 起算。<strong>混用三种写法时这个差异会咬人</strong>：你以为两条 pattern 平级，实际 PDLL 那条永远排在后面。PDLL 里要显式写：<code>Pattern Name with benefit(10) { … }</code>（<code>mlir/docs/PDLL.md:289</code>）。</p>
</div>

### 代价：它是解释执行的

`mlir-pdll -x cpp` 生成的东西很说明问题：

```cpp-norun
struct TransposeTwiceIsNop : ::mlir::PDLPatternModule {
  template <typename... ConfigsT>
  TransposeTwiceIsNop(::mlir::MLIRContext *context, ConfigsT &&...configs)
    : ::mlir::PDLPatternModule(::mlir::parseSourceString<::mlir::ModuleOp>(
R"mlir(pdl.pattern @TransposeTwiceIsNop : benefit(0) {
  …
} )mlir", context), std::forward<ConfigsT>(configs)...) {
```

它**把 PDL IR 当字符串嵌进 C++，运行时再 parse 一遍**。之后由 `PDLByteCode`（`mlir/lib/Rewrite/ByteCode.h:129`）解释执行。

所以三种写法的执行方式根本不同：

| | 写在哪 | 最终怎么执行 |
| --- | --- | --- |
| 手写 C++ | `.cpp` | 原生代码，直接调你的 `matchAndRewrite` |
| DRR | `.td` | `mlir-tblgen` 生成**原生 C++ pattern 类**，和手写的一样快 |
| PDLL | `.pdll` | 编成 `pdl` IR → **字节码解释器**执行 |

PDLL 慢一些换来的是别的东西：**pattern 可以在运行时加载**。IR 就是数据，可以从文件读进来、可以由程序生成、可以不重编译就换一套规则。做"用户可扩展的编译器"时这一点非常值钱；做一个固定的方言时，它只是成本。

## 边界在哪：匹配从不是问题，构造结果才是

把四条 pattern 的"能不能声明式表达"排一排，规律就出来了。下面这个 DAG 匹配器足够跑完四条规则的匹配，然后看结果构造这一侧：

```python
# 声明式 pattern 的表达力边界在哪？用一个 DAG 匹配器把它量出来。
# 三种写法（DRR / PDLL / 手写 C++）的差别不在"能不能匹配"，
# 而在"匹配之后能不能把结果**声明**出来"。

class Node:
    """一个 op：名字 + 若干输入（其他 Node 或 '%x' 这样的叶子）。"""
    def __init__(self, name, *inputs): self.name, self.inputs = name, inputs
    def __repr__(self):
        return self.name if not self.inputs else f"{self.name}({', '.join(map(repr, self.inputs))})"

def match(pat, node, binds):
    """DAG 匹配：pat 里以 $ 开头的是捕获变量，其余按 op 名逐层对。"""
    if isinstance(pat, str):
        if pat.startswith("$"):
            if pat in binds and repr(binds[pat]) != repr(node):
                return False          # 同名变量必须绑到同一个东西
            binds[pat] = node
            return True
        return isinstance(node, str) and pat == node
    if isinstance(node, str) or pat.name != node.name or len(pat.inputs) != len(node.inputs):
        return False
    return all(match(p, n, binds) for p, n in zip(pat.inputs, node.inputs))

# 四条改写，按"声明式能表达多少"排序
RULES = [
    ("① 纯结构：transpose(transpose(x)) → x",
     Node("pix.transpose", Node("pix.transpose", "$x")),
     lambda b: b["$x"],                       # 结果只是一个已绑定的值
     "声明式完全够用：右边就是 $x"),
    ("② 换个 op：add(x, x) → mul(x, x)",
     Node("pix.add", "$x", "$x"),

     lambda b: Node("pix.scale", b["$x"], Node("arith.mulf", b["$a"], b["$b"], "fastmath?", "rm?")),
     "开始别扭：DRR 要求按 ODS 给全 4 个参数，只能 NativeCodeCall 逃回 C++"),

     Node("pix.add", "$x", "$x"),

     "声明式表达不出来：那个 2.0 不在输入里，必须 NativeCodeCall"),
]

INPUTS = [Node("pix.transpose", Node("pix.transpose", "%img")),
          Node("pix.add", "%img", "%img"),
          Node("pix.scale", Node("pix.scale", "%img", "%a"), "%b"),
          Node("pix.add", "%a", "%b")]

for title, pat, build, verdict in RULES:
    print(f"\n【{title}】")
    print(f"  判定：{verdict}")
    for inp in INPUTS:
        binds = {}
        if match(pat, inp, binds):
            print(f"    {inp}  →  {build(binds)}")
        else:
            print(f"    {inp}  →  （不匹配）")
```

<div class="keypoint">
<strong>什么时候用声明式，什么时候写 C++</strong>
<p><strong>用 DRR</strong>：改写结果只由"匹配到的东西"重新组合而成——换 op、改嵌套、丢掉一层、转发操作数。这类 pattern 在真实方言里占多数，DRR 能省掉大量样板，而且 <code>.td</code> 放在 op 定义旁边，改 op 时不容易漏改 pattern。</p>
<p><strong>写 C++</strong>：只要出现下面任一条，直接写 C++，别在 TableGen 里挣扎——</p>
<p>① 结果里有<strong>凭空造出来的值</strong>（常量、属性、新类型）；② 要<strong>算</strong>什么（形状推导、indexing map 变换、代价比较）；③ 匹配条件是<strong>过程性</strong>的（要遍历、要查分析、要看支配关系）；④ 产出**多个** op 且彼此有非平凡的数据流；⑤ 你需要 <code>notifyMatchFailure</code> 说清为什么没匹配上（第 14 章那个调试利器，DRR 里给不出）。</p>
<p><strong>用 PDLL</strong>：你要的是"pattern 可以在运行时换"这个能力——面向用户可扩展的编译器、或者做规则的自动搜索。纯粹为了语法好看而选它，不值得那点解释执行的开销和一套额外的构建依赖。</p>
</div>

一个实践上的补充：**别在一条 `Pat<>` 里塞两个以上 `NativeCodeCall`**。那是个信号——说明这条规则的重心已经在 C++ 那边了，把它整条搬过去会更好读。我们那条 `AddSelfToScaleDRR` 就在这条线上，留着是为了让你看见界线长什么样。

---

**这一章的要点**

- **DRR 的主场是"结果只由匹配到的东西重新组合而成"**。这类 pattern 写成 `Pat<>` 能省掉大量样板：4 条 `Pat<>` 生成了 236 行 C++、4 个 pattern 类。
- `Pat<源 DAG, 结果 DAG, [约束列表]>`。`:$name` 给匹配到的 op 起名，`replaceWithValue` 表示"用已有的值替换"，`Constraint<CPred<"…">>` 里就是一句 C++ 表达式。
- **DRR 建目标 op 时必须按 ODS 的 `arguments` 给全参数**，哪怕有默认值。`arith.mulf` 有 4 个（含 `fastmath`、`roundingmode`），只给 2 个会被 `mlir-tblgen` 拒掉。
- **`NativeCodeCall` 是逃生门，也是信号**。当 DAG 节点用要带括号、当叶子用不带（少写括号会得到 `referencing unbound symbol ''` 这种毫无线索的报错）。一条 `Pat<>` 里超过两个 `NativeCodeCall`，就该整条搬回 C++。
- **PDLL 语法好读得多，但它编译成 `pdl` 方言的 IR，由 `PDLByteCode` 解释执行**（`-x cpp` 生成的是把 IR 当字符串嵌进去、运行时 parse 的 `PDLPatternModule`）。换来的是"pattern 能在运行时加载"，代价是解释开销。
- **PDLL 的默认 benefit 是 0**，而 C++ 和 DRR 都从 1 起算。三种写法混用时这个差异会静悄悄地改变优先级。
- 判据一句话：**匹配从来不是瓶颈，构造结果才是。** 结果里要凭空造值、要算东西、要走过程性判断、或者你想要 `notifyMatchFailure` 的调试信息——写 C++。
- **DAG 匹配的形状和 driver 的遍历顺序是两件事**：三条链式转置只会剩一条，因为 pattern 在内层那一对上触发。写测试时别把两者的效果混着断言。
