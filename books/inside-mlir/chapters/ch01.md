# 第 1 章 为什么还要一层 IR：LLVM IR 的天花板与 MLIR 的答案

## 这一章想让你带走什么

<div class="goal-box">
<p>你已经有 LLVM IR 了。它跨语言、跨芯片、能落盘、有一整套优化管线——按第一直觉，再造一层中间表示是多余的。这一章要说明白：<strong>LLVM IR 的问题不是它不好，而是它站得太低</strong>。当你要表达「一次张量加法」「这个循环可并行」「这块内存归谁」时，LLVM IR 已经把这些信息拆成标量指令和分支了，而拆解是不可逆的。</p>
<p>读完你会拿到三样东西：一，能说清 LLVM IR 的三个具体天花板（过早下降、类型系统固定、每个领域都在重造基础设施），并亲手用一个浏览器里能跑的小程序量出「同一个优化决定在高层和低层分别要证明几个条件」；二，MLIR 对这三点的回答——<strong>可扩展的 op、多方言共存、渐进下降</strong>；三，一个贯穿全书的认识：<strong>MLIR 不是一种 IR，而是造 IR 的框架</strong>，所以读任何 MLIR 项目的第一个问题都是「它有哪些方言、每层是什么抽象」。</p>
</div>

## 先看一眼：同一个计算，两种高度

不铺垫概念，先看东西。下面这段 MLIR 描述的是「两张 4×4 的图相加，再整体乘 2」：

```mlir
func.func @add_then_scale(%a: tensor<4x4xf32>, %b: tensor<4x4xf32>) -> tensor<4x4xf32> {
  %sum = arith.addf %a, %b : tensor<4x4xf32>
  %two = arith.constant dense<2.0> : tensor<4x4xf32>
  %out = arith.mulf %sum, %two : tensor<4x4xf32>
  return %out : tensor<4x4xf32>
}
```

注意 `tensor<4x4xf32>` 是**类型**，`arith.addf` 作用在整张 4×4 上——「对应位置相加」这件事是 op 的语义，没有循环，没有下标，没有内存。

同一个计算，下降一层之后是这样（循环显式了，值变成了内存）：

```mlir
func.func @add_then_scale(%a: memref<4x4xf32>, %b: memref<4x4xf32>, %out: memref<4x4xf32>) {
  %c0 = arith.constant 0 : index
  %c1 = arith.constant 1 : index
  %c4 = arith.constant 4 : index
  %two = arith.constant 2.0 : f32
  scf.for %i = %c0 to %c4 step %c1 {
    scf.for %j = %c0 to %c4 step %c1 {
      %av = memref.load %a[%i, %j] : memref<4x4xf32>
      %bv = memref.load %b[%i, %j] : memref<4x4xf32>
      %s = arith.addf %av, %bv : f32
      %m = arith.mulf %s, %two : f32
      memref.store %m, %out[%i, %j] : memref<4x4xf32>
    }
  }
  return
}
```

两段都是合法的 MLIR，都能被同一个 `mlir-opt` 读进来、验证、打印出去。**这就是 MLIR 与 LLVM IR 最表层的区别：抽象层不是固定的一层，而是你可以选的一叠。** 第二段已经很接近 LLVM IR 了（再降一步就是分支和裸指针）；第一段在 LLVM IR 里根本没法表达——它没有 `tensor` 类型，也没有「整张相加」这个指令。

这个差别听起来只是"方便"，但它决定了优化能不能做。下面这一节说清为什么。

## 天花板一：过早下降，信息是不可逆地丢的

把上面第一段变成第二段，是一个**下降（lowering）**动作。下降永远在丢信息：形状、逐点语义、"这个中间结果只被用一次"都从类型和 def-use 关系里，掉到了循环上下界、下标表达式、内存读写里。

丢了信息，优化就得"考古"把它挖回来。挖，就得证明。看一个最普通的优化：把两趟遍历**融合**成一趟（少一次写、少一次读、少一块中间存储）。

在高层，这个决定几乎是免费的：`%sum` 的类型写着形状，def-use 边上写着"只有一个消费者"，两条就够。在标量循环上，同样的决定要靠循环分析和依赖分析逐条证明：嵌套深度、上下界步长、归纳变量、下标表达式、有没有别的读者、会不会别名。下面这段代码把两边要证明的条件**数出来**——直接点运行：

```python
# 同一个优化决定（把两趟遍历融合成一趟），在"高层 IR"和"标量循环"上分别要付多少代价。
# 这段代码不依赖任何库，直接跑。

# ---------- 高层：语义就摆在 op 上 ----------
# addf(A, B) -> T1 ；mulf(T1, two) -> OUT ，都是整张 4x4 张量上的一次运算
high = [
    {"op": "arith.addf", "ins": ["A", "B"],    "out": "T1",  "shape": (4, 4)},
    {"op": "arith.mulf", "ins": ["T1", "two"], "out": "OUT", "shape": (4, 4)},
]

def can_fuse_high(ops):
    prod, cons = ops[0], ops[1]
    users = [o for o in ops if prod["out"] in o["ins"]]
    return [
        ("两个 op 的形状一致", prod["shape"] == cons["shape"]),
        ("中间结果只有一个消费者", len(users) == 1),
    ]

# ---------- 低层：同一段计算被拆成标量循环之后 ----------
# for i in 0..4: for j in 0..4: T1[i][j] = A[i][j] + B[i][j]
# for i in 0..4: for j in 0..4: OUT[i][j] = T1[i][j] * 2.0
def loop(bounds, reads, write, idx):
    return {"bounds": bounds, "reads": reads, "write": write, "idx": idx}

nest1 = loop([(0, 4, 1), (0, 4, 1)], ["A", "B"], "T1", ("i", "j"))
nest2 = loop([(0, 4, 1), (0, 4, 1)], ["T1"],     "OUT", ("i", "j"))

def can_fuse_low(n1, n2, extra_readers=()):
    # 这些正是真实编译器里 loop fusion 必须逐条证明的前提
    same_depth = len(n1["bounds"]) == len(n2["bounds"])
    same_trip = n1["bounds"] == n2["bounds"]
    same_idx = n1["idx"] == n2["idx"]
    # 生产者写进 T1 的下标 和 消费者读 T1 的下标必须逐维相同，否则不是"逐点"关系
    same_subscript = n1["idx"] == n2["idx"]
    no_other_reader = n1["write"] not in extra_readers
    # 是否可能与别的数组重叠（真实编译器要靠别名分析；这里假设已知不重叠）
    no_alias = n2["write"] not in (n1["reads"] + [n1["write"]])
    return [
        ("两个循环嵌套深度相同", same_depth),
        ("每一层的上下界与步长都相同", same_trip),
        ("归纳变量的使用方式相同", same_idx),
        ("写 T1 的下标 == 读 T1 的下标（逐点依赖）", same_subscript),
        ("T1 没有循环之外的其它读者", no_other_reader),
        ("OUT 不与 A/B/T1 别名重叠", no_alias),
    ]

def report(title, checks):
    print(f"{title}：需要证明 {len(checks)} 个条件")
    for name, ok in checks:
        print(f"  {'✓' if ok else '✗'} {name}")
    print("  => " + ("可以融合" if all(ok for _, ok in checks) else "放弃融合（保守处理）"))
    print()

report("高层（tensor 上的两个 op）", can_fuse_high(high))
report("低层（两个标量循环嵌套）", can_fuse_low(nest1, nest2))

# 现在让别处也读一次 T1——比如调试打印、或者另一个函数拿走了它
report("低层，且 T1 在别处也被读了一次", can_fuse_low(nest1, nest2, extra_readers=("T1",)))
print("注意最后一种情况：高层 IR 里'谁用了这个值'是 def-use 边上一眼可见的；")
print("而在标量循环里，这件事得靠别名分析和依赖分析去'考古'才能知道。")
```

运行结果：

```
高层（tensor 上的两个 op）：需要证明 2 个条件
  ✓ 两个 op 的形状一致
  ✓ 中间结果只有一个消费者
  => 可以融合

低层（两个标量循环嵌套）：需要证明 6 个条件
  ✓ 两个循环嵌套深度相同
  ✓ 每一层的上下界与步长都相同
  ✓ 归纳变量的使用方式相同
  ✓ 写 T1 的下标 == 读 T1 的下标（逐点依赖）
  ✓ T1 没有循环之外的其它读者
  ✓ OUT 不与 A/B/T1 别名重叠
  => 可以融合

低层，且 T1 在别处也被读了一次：需要证明 6 个条件
  ✓ 两个循环嵌套深度相同
  ✓ 每一层的上下界与步长都相同
  ✓ 归纳变量的使用方式相同
  ✓ 写 T1 的下标 == 读 T1 的下标（逐点依赖）
  ✗ T1 没有循环之外的其它读者
  ✓ OUT 不与 A/B/T1 别名重叠
  => 放弃融合（保守处理）

注意最后一种情况：高层 IR 里'谁用了这个值'是 def-use 边上一眼可见的；
而在标量循环里，这件事得靠别名分析和依赖分析去'考古'才能知道。
```

**6 比 2 不是重点，重点是这 6 条里每一条都可能证不出来。** 真实代码里上下界是动态的、下标带 `%` 和 `/`、指针来自参数无法确定别名——任何一条失败，优化就保守放弃。而在高层，这些信息压根没丢过，不需要证明。

<div class="keypoint">
<strong>核心观念：优化的能力上限，由 IR 保留了多少语义决定。</strong>
<p>「先降到一个低层 IR，再靠强大的分析把结构恢复出来」是过去三十年的主流路线，代价是分析越写越复杂、结论越来越保守。MLIR 的路线相反：<strong>在还知道语义的那一层就把变换做掉</strong>，然后再往下降一点。这就是后面会反复出现的<strong>渐进下降（progressive lowering）</strong>。</p>
</div>

## 天花板二：类型和指令集是固定的

LLVM IR 的类型系统是机器视角的：整数、浮点、指针、定长向量、结构体、数组。指令集也是固定的一张表（`add`、`load`、`br`、`call`……），你不能"注册"一条新指令。

于是当你想表达领域概念时，只剩三种绕法，每种都难受：

- **靠 intrinsic**：`llvm.matrix.multiply.*`、`llvm.vector.reduce.*` 这类。能塞进去，但每加一个都要改 LLVM 本体，且优化器对它基本是黑盒。
- **靠 metadata**：`!llvm.loop.parallel_accesses` 这种挂在指令上的注解。问题是 metadata **可以被合法地丢掉**——它的语义是"提示"，不是"事实"，所以优化器不能完全信任它，一次不小心的变换就把它抹了。
- **靠命名约定**：把信息编码进函数名，前端和后端约定好。脆，且完全没有验证。

三种绕法的共同点是：**领域语义在 IR 里没有一等公民的地位**。它没有类型、没有验证、没有打印格式、没有折叠规则。

## 天花板三：于是每个领域都在重造同一套基础设施

这才是真正推动 MLIR 诞生的那个观察。既然没法在 LLVM IR 里表达领域概念，各家就在 LLVM IR **上面**各造一层自己的 IR：

| 项目 | 自建的中间表示 | 为什么需要它 |
| --- | --- | --- |
| Swift | SIL | 要做所有权、协议派发、专门化 |
| Rust | MIR | 要做借用检查、drop 插入 |
| TensorFlow / XLA | HLO | 要做图级别的算子融合、布局选择 |
| Halide / TVM | 自己的调度 IR | 要把"算什么"和"怎么算"分开 |
| Fortran（flang） | FIR | 要保留数组语义、等价声明 |

每一层都要重新实现同一堆东西：SSA 值与 def-use 链、基本块与 CFG、pass 管理与调度、常量折叠、CSE、位置信息（报错要指到源码行）、文本格式与序列化、verifier、还有测试工具。**这些代码和领域无关，但每个项目都得写一遍。**

MLIR 的出发点就是把这一层"IR 的通用基础设施"抽出来，做成可复用的库——你只定义**自己领域的 op 和类型**，SSA、region、pass 管线、打印解析、验证、诊断、测试工具全是现成的。

## MLIR 的三个回答

### 回答一：没有固定的指令集，op 是注册进来的

LLVM IR 里"有哪些指令"是写死在 `Instruction.def` 里的。MLIR 反过来：**核心不认识任何具体的 op**，它只知道"op 有操作数、有结果、有属性、有 region"这个骨架。具体的 `arith.addf`、`scf.for`、`memref.load` 都是各自的**方言（dialect）**注册进来的，和你自己将要写的 `pix.convolve` 地位完全平等——没有内建 op 与自定义 op 的等级差。

想看这个骨架，把上面第一段代码用**通用格式（generic form）**打印出来：

```bash
mlir-opt add_then_scale.mlir --mlir-print-op-generic
```

运行结果：

```
"builtin.module"() ({
  "func.func"() <{function_type = (tensor<4x4xf32>, tensor<4x4xf32>) -> tensor<4x4xf32>, sym_name = "add_then_scale"}> ({
  ^bb0(%arg0: tensor<4x4xf32>, %arg1: tensor<4x4xf32>):
    %0 = "arith.addf"(%arg0, %arg1) <{fastmath = #arith.fastmath<none>}> : (tensor<4x4xf32>, tensor<4x4xf32>) -> tensor<4x4xf32>
    %1 = "arith.constant"() <{value = dense<2.000000e+00> : tensor<4x4xf32>}> : () -> tensor<4x4xf32>
    %2 = "arith.mulf"(%0, %1) <{fastmath = #arith.fastmath<none>}> : (tensor<4x4xf32>, tensor<4x4xf32>) -> tensor<4x4xf32>
    "func.return"(%2) : (tensor<4x4xf32>) -> ()
  }) : () -> ()
}) : () -> ()
```

这段输出里有三件事值得停下来看：

1. **一切都是 op**。函数是一个 op（`"func.func"`），**模块本身也是一个 op**（`"builtin.module"`）。没有"顶层容器"这种特殊结构——第 2 章会讲这带来的巨大好处：pass 可以跑在任何 op 上。
2. **每个 op 的写法是统一的**：`"方言.op名"(操作数) <{属性}> ({嵌套的 region}) : (输入类型) -> 输出类型`。你平时看到的 `arith.addf %a, %b : tensor<4x4xf32>` 只是这个统一形式的**自定义简写**（第 3 章、第 8 章会讲这个简写是怎么来的）。
3. `%0` 这些值、`^bb0` 这个块、块参数 `%arg0`——SSA 那套东西都在，但没有 `phi` 指令。MLIR 用**块参数**代替 phi，第 2 章细讲。

### 回答二：方言可以共存在同一个模块里

这是很多人第一次读 MLIR 时的困惑来源：一个函数里为什么既有 `linalg` 的 op，又有 `scf` 的循环，还有 `llvm` 的调用？

因为 MLIR **不要求一个模块里的 op 属于同一个方言**。这不是妥协，而是设计目标：只有允许高层和低层 op 共存，才可能一步一步地降——每一步替换掉一部分 op，剩下的暂时不动。中间状态是"混着的"，但它仍然是**合法的、可验证的、能打印出来的 IR**。

于是编译过程不再是"前端 → IR → 后端"三段跳，而是一串小步：

## 一个要尽早接受的事实：MLIR 不是一种 IR

你可以准确地说「LLVM IR 长什么样」——它有固定的类型系统和指令表。但**你没法说「MLIR 长什么样」**，只能说：

- MLIR 的**骨架**长什么样：Operation / Region / Block / Value，加上属性和类型的唯一化（第 2、4 章）；
- 你**选了哪些方言**，以及它们各自的抽象层次。

所以读任何一个 MLIR 项目，第一个问题永远是：**它定义了哪些方言，每层代表什么抽象，边界在哪里？** Triton 的答案是 `tt` → `ttg`（第 26 章），IREE 的答案是 `flow` → `stream` → `hal`（第 27 章），flang 的答案是 `hlfir` → `fir`（第 27 章）。问对了这个问题，几十万行代码就有了骨架。

<strong>名字的由来</strong>
<p>MLIR 最初是 <em>Multi-Level IR</em>（多层 IR）的缩写——"多层"正是它的全部主张。后来官方把它解释成"MLIR 就叫 MLIR"，因为它早已不只用于机器学习或某个特定层次；但记住"多层"这个原意，对理解设计最有帮助。</p>

## 代价：这一层不是白拿的

这本书会老实讲代价，因为不讲的话你迟早自己踩到：

- **IR 变啰嗦。** 通用格式那段输出你已经看到了。自定义格式能救回可读性，但那是你要**自己写**的（第 8 章）。
- **语义要你自己定义。** 造了 `pix.convolve` 之后，它的验证规则、折叠规则、能不能被 CSE、有没有副作用，全得你告诉框架（第 10、11 章，以及第 5 章的 trait/interface）。LLVM IR 的 `add` 这些语义是现成的，你的 op 没有。
- **概念负担重。** trait、interface、pattern、conversion、bufferization、transform——一堆词，且互相咬合。本书第一、二部分就是为了把这堆词变成手感。
- **编译时间与内存。** 多层表示、频繁的 pattern 重写、字符串化的 op 名，都有成本。真实项目里 pass 管线的组织方式会直接决定编译时间（第 13 章）。
- **生态仍在动。** pass 名改、接口调整、文档跟不上代码，是常态（附录 A 第 0 节的版本基线就是为此而立）。

**什么时候值得付这个代价？** 判断标准很简单：你的领域有没有"降到标量循环之后就丢掉、且优化真的需要"的语义。张量形状、并行性、内存所有权、数值语义——有，就值得；如果你只是要把一门普通命令式语言编译到 CPU，LLVM IR 直接用就好。

## 动手：三分钟把手感建起来

三条命令，都在本章的第一段代码上跑。没装 MLIR 也行——点代码块右上角的 **🔗 在 Compiler Explorer 打开（mlir-opt）** 就是同一件事（见附录 A）。

```bash
# 1. 什么 pass 都不跑：解析 → 验证 → 打印回来。这一步过不了，说明 IR 本身有问题
mlir-opt add_then_scale.mlir

# 2. 看统一的骨架：所有自定义简写都还原成 "方言.op名"(...) 的形式
mlir-opt add_then_scale.mlir --mlir-print-op-generic

# 3. 跑一个真变换：把乘 1.0 这种废操作折掉
mlir-opt redundant.mlir --canonicalize
```

第 3 条用下面这段（把系数从 2.0 改成 1.0，让它变成一次无意义的乘法）：

```mlir
// RUN: mlir-opt %s --canonicalize
func.func @redundant(%a: tensor<4x4xf32>, %b: tensor<4x4xf32>) -> tensor<4x4xf32> {
  %sum = arith.addf %a, %b : tensor<4x4xf32>
  %one = arith.constant dense<1.0> : tensor<4x4xf32>
  %out = arith.mulf %sum, %one : tensor<4x4xf32>
  return %out : tensor<4x4xf32>
}
```

运行结果：

```
module {
  func.func @redundant(%arg0: tensor<4x4xf32>, %arg1: tensor<4x4xf32>) -> tensor<4x4xf32> {
    %0 = arith.addf %arg0, %arg1 : tensor<4x4xf32>
    return %0 : tensor<4x4xf32>
  }
}
```

乘法和那个常量都不见了——`arith.mulf` 自己带的折叠规则认出了"乘 1.0 等于没乘"。**注意这件事发生在 `tensor<4x4xf32>` 上，不是标量上**：整张图的乘法一次就折掉了，不需要先展开成 16 次标量乘法再逐个折。这就是"在还知道语义的那一层做变换"最小的一个例子。

**改一改，看看会怎样：**

1. 把 `dense<1.0>` 改成 `dense<0.0>`，再跑 `--canonicalize`。乘 0 被折掉了吗？想一想为什么浮点乘 0 不能随便折（提示：`NaN`、`-0.0`）——这正是第 11 章要讲的"折叠规则必须是保语义的"。
2. 把两个 `tensor<4x4xf32>` 改成 `tensor<?x4xf32>`（动态维度）。还能过 verifier 吗？形状检查放宽到什么程度？第 4 章讲类型，第 10 章讲验证。
3. 把 `arith.addf` 换成 `arith.addi`，但类型仍写 `tensor<4x4xf32>`。跑一下，报错会是 `operand #0 must be signless-non-zero-bitwidth-integer-like, but got 'tensor<4x4xf32>'`——**这句话不是手写的检查，而是 `arith.addi` 在它的 ODS 定义里声明的类型约束自动生成的**。第 8 章你会亲手写这种约束，第 10 章讲它和 verifier 的关系。

---

**这一章的要点**

- LLVM IR 的天花板不在"不好"，而在"站得低"：**过早下降会不可逆地丢掉语义**，优化只能靠分析去考古，而考古随时会失败——你已经亲手数过 2 个条件 vs 6 个条件的差别。
- 它的类型系统与指令集是固定的，领域概念只能靠 intrinsic / metadata / 命名约定硬塞，都没有一等公民地位。
- 结果是每个领域（Swift、Rust、XLA、Halide、Fortran）都自建一层 IR，把 SSA、pass 管线、打印解析、verifier、测试工具重写一遍。MLIR 把这套基础设施抽成库，**你只定义自己的 op 和类型**。
- MLIR 的三个回答：**op 是注册进来的**（连 module 和 func 都是 op）、**方言可以共存**、**渐进下降**（每一级都是可验证可打印的完整 IR）。
- **MLIR 不是一种 IR，是造 IR 的框架。** 读任何 MLIR 项目先问：有哪些方言、每层什么抽象、边界在哪。
- 代价是真实的：IR 啰嗦、语义要自己定义、概念负担重、编译开销、生态在动。值不值得，看你的领域有没有"降下去就丢、但优化需要"的语义。

下一章我们把骨架本身拆开：**Operation / Region / Block / Value** 到底是什么数据结构，`%0` 和 `^bb0` 在内存里长什么样，为什么 MLIR 不需要 `phi` 指令——并与你熟悉的 LLVM IR 逐项对照。
