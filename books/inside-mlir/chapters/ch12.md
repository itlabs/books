## 补上最后一个语义缺口：`pix.reduce` 的归约方式

第 8 章定义 `pix.reduce` 时把语义写死成"求和"，`.td` 里留了一句注释："归约方式先固定为求和；以后用枚举属性把它扩展成 sum/max/min。"现在兑现。

枚举属性的写法第 9 章已经走过一遍（`#pix.border<clamp|zero|wrap>`），照抄就是——**这正是要点：这套东西是有套路的，第二个枚举应该毫无悬念。**

```tablegen
def Pix_ReduceKind : I32EnumAttr<"ReduceKind", "全图归约的方式", [
      I32EnumAttrCase<"Sum", 0, "sum">,
      I32EnumAttrCase<"Max", 1, "max">,
      I32EnumAttrCase<"Min", 2, "min">
    ]> {
  let cppNamespace = "::mlir::pix";
  let genSpecializedAttr = 0;
}

def Pix_ReduceKindAttr : EnumAttr<Pix_Dialect, Pix_ReduceKind, "reduce_kind"> {
  let assemblyFormat = "`<` $value `>`";
}
```

### 关键一招：`DefaultValuedAttr` 保住老 IR

真正值得学的在 op 这边。直接往 `arguments` 里塞一个必填属性，**所有已经写好的 `pix.reduce` 立刻全部解析失败**——包括本书前面几章的示例、`roundtrip.mlir` 里的用例、以及读者自己攒的文件。

用 `DefaultValuedAttr` 就没这个问题：

```tablegen
def Pix_ReduceOp : Pix_Op<"reduce", [Pure]> {
  let arguments = (ins F32Tensor:$image,
                       DefaultValuedAttr<Pix_ReduceKindAttr,
                                         "ReduceKind::Sum">:$kind);
  let results = (outs F32:$result);

  // kind 走 attr-dict 打印：默认值（sum）时整个字典是空的，IR 一个字都不多。
  let assemblyFormat = "$image attr-dict `:` type($image) `->` type($result)";
  let hasFolder = 1;
}
```

两件事合起来才管用：**`DefaultValuedAttr` 让属性可以不写**，而**把它交给 `attr-dict` 打印**让默认值不会被打印出来。实测：

```mlir-lower
// RUN: pix-opt %s
func.func @old_syntax() -> f32 {
  %img = arith.constant dense<[[1.0, 5.0], [3.0, 2.0]]> : tensor<2x2xf32>
  %s = pix.reduce %img : tensor<2x2xf32> -> f32
  return %s : f32
}

func.func @as_max() -> f32 {
  %img = arith.constant dense<[[1.0, 5.0], [3.0, 2.0]]> : tensor<2x2xf32>
  %s = pix.reduce %img {kind = #pix.reduce_kind<max>} : tensor<2x2xf32> -> f32
  return %s : f32
}
```

运行结果（只看那两行 op）：

```
    %0 = pix.reduce %cst : tensor<2x2xf32> -> f32
    %0 = pix.reduce %cst {kind = #pix.reduce_kind<max>} : tensor<2x2xf32> -> f32
```

老写法进去、老写法出来，**一个字符都没多**。想要 max/min 才写属性。

<div class="keypoint">
<strong>给已有 op 加属性的三条规矩</strong>
<p>一、<strong>能给默认值就给</strong>（<code>DefaultValuedAttr</code>），别让老 IR 解析失败。二、<strong>默认值交给 <code>attr-dict</code> 打印</strong>，不要在 <code>assemblyFormat</code> 里显式写 <code>$kind</code>——那样默认值也会被打印出来，round-trip 虽然仍成立，但所有现存文件的<strong>输出</strong>都变了，别人的 FileCheck 测试会一片红。三、<strong>默认值要选"和原来行为一致的那个"</strong>。我们选 <code>Sum</code> 不是因为它排第一，而是因为第 8 章的语义就是求和。</p>
</div>

### folder 按 kind 分三种算法

第 11 章的 `ReduceOp::fold` 只会求和，现在要分情况。有意思的是 splat 那条捷径对三种 kind 都成立，但**理由不同**：

```cpp-norun
OpFoldResult ReduceOp::fold(FoldAdaptor adaptor) {
  auto dense = dyn_cast_or_null<DenseFPElementsAttr>(adaptor.getImage());
  if (!dense)
    return {};
  // 空图的 max/min 没有定义（min 该返回什么？），直接不折。
  if (dense.getNumElements() == 0)
    return {};

  const ReduceKind kind = getKind();

  if (dense.isSplat()) {
    APFloat v = dense.getSplatValue<APFloat>();
    APFloat r = kind == ReduceKind::Sum
                    ? v * APFloat(static_cast<float>(dense.getNumElements()))
                    : v;                       // max/min 全都一样，就是它自己
    return FloatAttr::get(getResult().getType(), r);
  }

  auto values = dense.getValues<APFloat>();
  APFloat acc = *values.begin();
  bool first = true;
  for (APFloat v : values) {
    if (first) {
      first = false;
      if (kind == ReduceKind::Sum)
        acc = v;
      continue;
    }
    switch (kind) {
    case ReduceKind::Sum: acc = acc + v;        break;
    case ReduceKind::Max: acc = maxnum(acc, v); break;
    case ReduceKind::Min: acc = minnum(acc, v); break;
    }
  }
  return FloatAttr::get(getResult().getType(), acc);
}
```

那个 `getNumElements() == 0` 的早退值得一说：**空图的 max/min 没有正确答案**。返回 0？返回正无穷？都是编出来的。第 11 章说过"别把化简写得太贪"，这是同一条原则的另一面——**答不出来就别答**，把 op 原样留着，让运行时或后面的 pass 去处理。

`switch` 上不写 `default` 也是故意的：以后往枚举里加一种归约方式（比如 `Prod`），编译器会因为 `switch` 没覆盖全而**警告**，直接把你领到该改的地方。写了 `default:` 就把这个提醒关掉了。

用一张 `[[1, 5], [3, 2]]` 验三种 kind——三个答案互不相同，所以这组测试真的能区分三种算法：

```mlir-lower
// RUN: pix-opt %s --canonicalize
func.func @sum() -> f32 {
  %img = arith.constant dense<[[1.0, 5.0], [3.0, 2.0]]> : tensor<2x2xf32>
  %s = pix.reduce %img : tensor<2x2xf32> -> f32
  return %s : f32
}
func.func @max() -> f32 {
  %img = arith.constant dense<[[1.0, 5.0], [3.0, 2.0]]> : tensor<2x2xf32>
  %s = pix.reduce %img {kind = #pix.reduce_kind<max>} : tensor<2x2xf32> -> f32
  return %s : f32
}
func.func @min() -> f32 {
  %img = arith.constant dense<[[1.0, 5.0], [3.0, 2.0]]> : tensor<2x2xf32>
  %s = pix.reduce %img {kind = #pix.reduce_kind<min>} : tensor<2x2xf32> -> f32
  return %s : f32
}
```

运行结果：

```

    %cst = arith.constant 1.100000e+01 : f32
    return %cst : f32
  }
  func.func @max() -> f32 {
    %cst = arith.constant 5.000000e+00 : f32
    return %cst : f32
```

## `--pix-simplify`：给方言一个公开入口

第 11 章之后，"把 pix 化简干净"要敲三个开关：`--canonicalize --cse --symbol-dce`。把它包成一个名字：

```cpp-norun
static void buildPixSimplifyPipeline(mlir::OpPassManager &pm) {
  pm.addPass(mlir::createCanonicalizerPass());
  pm.addPass(mlir::createCSEPass());
  pm.addPass(mlir::createSymbolDCEPass());
}

int main(int argc, char **argv) {
  mlir::registerAllPasses();

  static mlir::PassPipelineRegistration<> pixSimplify(
      "pix-simplify", "把 pix IR 化简干净：canonicalize + cse + symbol-dce",
      buildPixSimplifyPipeline);
  // …注册方言，然后交给 MlirOptMain
}
```

注册完它就和内建 pass 平起平坐，`--help` 里也有：

```
--pix-simplify    -   把 pix IR 化简干净：canonicalize + cse + symbol-dce
```

<div class="note">
<strong>"管线"不是"pass"</strong>
<p>这里<strong>一个 Pass 类都没写</strong>，只是把现成的三个串起来起了个名。<code>PassPipelineRegistration</code> 注册的是一个"往 <code>OpPassManager</code> 里加 pass 的函数"，它和 <code>PassRegistration&lt;MyPass&gt;</code>（注册一个真正的 pass，第 13 章讲）是两套东西。上游 <code>--sparsifier</code>、<code>--gpu-lower-to-nvvm-pipeline</code> 都是这一类。</p>
<p>为什么值得起名？因为这个名字是<strong>给使用者的接口</strong>。以后管线里加了 pix 自己的 pass、或者调整了顺序，用 <code>--pix-simplify</code> 的人不用改命令，测试也不用改。把"我方言该怎么化简"这个知识<strong>收在方言一侧</strong>，而不是散在每个调用者的命令行里。</p>
</div>

跑一下，三件事一次做完：

```mlir-lower
// RUN: pix-opt %s --pix-simplify
func.func @everything_collapses(%img: tensor<4x4xf32>) -> tensor<4x4xf32> {
  %one = arith.constant 1.0 : f32
  %a = pix.scale %img, %one : tensor<4x4xf32>   // 系数 1 → fold
  %b = pix.add %img, %img : tensor<4x4xf32>     // 和下面重复 → cse
  %c = pix.add %img, %img : tensor<4x4xf32>
  %d = pix.add %b, %c : tensor<4x4xf32>         // 没人用 → DCE
  return %a : tensor<4x4xf32>
}
```

运行结果：

```
module {
  func.func @everything_collapses(%arg0: tensor<4x4xf32>) -> tensor<4x4xf32> {
    return %arg0 : tensor<4x4xf32>
  }
}
```

几个容易踩的点：

**真正的入口是生成的那个文件。** `lit.site.cfg.py.in` 里全是 `@LLVM_TOOLS_DIR@` 这种占位符，`configure_lit_site_cfg` 在 cmake 阶段把它们换成真路径，生成 `build/test/lit.site.cfg.py`；这个生成的文件最后一句才是 `load_config(…, "…/test/lit.cfg.py")`。**所以配置是两级的**：生成的那个负责"路径是什么"，你手写的那个负责"规则是什么"。想知道路径对不对，直接看生成的文件：

```bash
cat $BUILD/test/lit.site.cfg.py
```

**`%s` 不是 shell 的东西**，是 lit 的替换。`use_default_substitutions()` 装的一批里最常用的三个：`%s`＝当前测试文件的路径，`%t`＝一个专属的临时文件名（要写中间文件时用它，避免并行测试互相踩），`%S`＝测试文件所在目录。

**RUN 行里为什么能写裸 `pix-opt`**：`add_tool_substitutions(["pix-opt", "mlir-opt"], tool_dirs)` 把这些名字换成构建目录里的绝对路径。这一句的价值是**保证测的是刚编出来的那个**，而不是你 `PATH` 里碰巧存在的另一个版本——这个坑一旦踩上极难发现。

**`DEPENDS` 少一个就全崩。** 我这次就撞了：`FileCheck` 没编，报错是

```
llvm-lit: …/subst.py:137: fatal: Did not find FileCheck in /…/build/./bin
```

它不说"你忘了编 FileCheck"，只说找不到。`test/CMakeLists.txt` 里那个 `PIX_TEST_DEPENDS`（`FileCheck count not pix-opt`）就是为此存在的。

**两个目标，粒度不同。** `add_lit_testsuite` 建了 `check-pix`（跑全套），`add_lit_testsuites(PIX …)` 额外按目录建了细粒度目标——我们只有一个子目录，所以是 `check-pix-pix`。改一个 op 时只跑相关目录，比全套快得多。

### 测试文件怎么分

pix 现在 8 个测试文件，命名对着上游 `mlir/test/Dialect/<方言>/` 的惯例：

| 文件 | 管什么 | RUN 行 |
| --- | --- | --- |
| `roundtrip.mlir` | 自定义格式打印出来还能解析回去 | `pix-opt %s` |
| `types_attrs.mlir` | 自定义类型与属性的语法 | `pix-opt %s` |
| `invalid.mlir` | **解析**就该失败的写法 | `--verify-diagnostics` |
| `invalid_verifiers.mlir` | 解析得过、但 **verifier** 该拦的 | `--split-input-file --verify-diagnostics` |
| `canonicalize.mlir` | fold 与 canonicalize pattern | `--canonicalize \| FileCheck` |
| `reduce_kind.mlir` | 枚举属性三种 kind + 老写法兼容 | `--canonicalize \| FileCheck` |
| `cse.mlir` | `Pure` 换来的通用 CSE | `--cse \| FileCheck` |
| `pix_simplify.mlir` | 那条命名管线 | `--pix-simplify \| FileCheck` |

`invalid.mlir` 和 `invalid_verifiers.mlir` 分成两个文件不是啰嗦：**parser 报错和 verifier 报错发生在不同阶段**，而 parser 一旦失败就不会走到 verifier（第 10 章那个"parser 先于 verifier 报错"的实测就是这么来的）。混在一个文件里，一处语法错会把后面所有用例的验证都跳过。

<strong>一条朴素但有效的规矩：每个化简都配一对测试</strong>
<p>「该折的折了」和「不该动的没动」。<code>canonicalize.mlir</code> 里 <code>scale_by_one</code> 配 <code>scale_by_two_stays</code>、<code>add_zero</code> 配 <code>add_nonzero_stays</code>、<code>double_transpose</code> 配 <code>single_transpose_stays</code>。只写前一半的测试有个典型失效方式：某天有人把 <code>fold</code> 写成无条件返回操作数，测试<strong>全绿</strong>，而你的方言已经算错了。</p>

## FileCheck：把 CHECK 那套语义弄准

本书一直在用它，现在拆开。指令一共这几种（名字来自 `llvm/lib/FileCheck/FileCheck.cpp` 里的 `Check::Check*` 枚举）：

| 指令 | 语义 |
| --- | --- |
| `CHECK` | 从上次匹配之后，往下**任意位置**找 |
| `CHECK-NEXT` | 必须在上次匹配的**紧接下一行** |
| `CHECK-SAME` | 必须在**同一行**的后面（用来把一行拆成几条断言写） |
| `CHECK-NOT` | 这一段区间里**不许出现** |
| `CHECK-DAG` | 一组断言，**顺序随意**（多个结果的顺序不稳定时用） |
| `CHECK-LABEL` | 分段锚点：把输入切成互不干扰的块 |
| `CHECK-EMPTY` | 下一行必须是空行 |
| `CHECK-COUNT-n` | 连续匹配 n 次 |

`CHECK-LABEL` 值得单独说。它不只是"匹配一行"，而是**把整个输入按它切段，每段里的 CHECK 只在本段内匹配**。所以 `// CHECK-LABEL: func.func @foo` 这个写法有个实际好处：函数 A 的断言绝不会意外匹配到函数 B 的输出里去——文件里有十几个函数时，这条差别很要紧。

变量捕获是 `[[名字:正则]]` 定义、`[[名字]]` 引用：

```
// CHECK: %[[C:.*]] = arith.constant 6.000000e+00 : f32
// CHECK: pix.scale %arg0, %[[C]] :
```

它的价值是**对 SSA 名字改动免疫**。MLIR 的 `%0`、`%cst`、`%cst_0` 是打印时按顺序生成的，你在函数里多插一个 op，后面所有编号都变。如果测试里硬写 `%cst`，这种无关改动会让一片测试变红。捕获之后，只要"定义处和引用处是同一个值"这个**关系**成立就行。

### 写一个 mini-FileCheck，顺手抓出一个真陷阱

上面这些讲一遍不如跑一遍。下面 45 行实现了 `CHECK` / `CHECK-NEXT` / `CHECK-NOT` 和变量捕获——够覆盖本书用到的全部：

```python
# 一个 45 行的 mini-FileCheck，够覆盖本书用到的四种指令 + 变量捕获。
# 目的是把 CHECK-NEXT 和 [[VAR]] 的语义弄清楚——这两个最容易想当然。
import re

def compile_pattern(pat, bound):
    """把 CHECK 行里的 [[NAME:regex]] 与 [[NAME]] 翻译成 Python 正则。"""
    out, i = "", 0
    for m in re.finditer(r"\[\[(\w+)(?::([^\]]+))?\]\]", pat):
        out += re.escape(pat[i:m.start()])
        name, regex = m.group(1), m.group(2)
        if regex:                              # 定义：[[C:.*]] —— 捕获它
            out += f"(?P<{name}>{regex})"
        else:                                  # 引用：[[C]] —— 必须和先前捕获的一致
            out += re.escape(bound.get(name, "\0<未定义>"))
        i = m.end()
    return out + re.escape(pat[i:])

def filecheck(directives, text):
    lines, bound, cursor = text.splitlines(), {}, 0
    for kind, pat in directives:
        rx = re.compile(compile_pattern(pat, bound))
        if kind == "NOT":
            for l in lines[cursor:]:
                if rx.search(l):
                    return f"✗ CHECK-NOT 失败：不该出现的 {pat!r} 出现在 {l.strip()!r}"
            continue
        # CHECK 从 cursor 往后任意位置找；CHECK-NEXT 只许紧挨着上一处
        search_range = range(cursor, len(lines)) if kind == "CHECK" else range(cursor, min(cursor + 1, len(lines)))
        for j in search_range:
            if (m := rx.search(lines[j])):
                bound.update({k: v for k, v in m.groupdict().items() if v is not None})
                cursor = j + 1
                break
        else:
            where = "紧接的下一行" if kind == "NEXT" else f"第 {cursor+1} 行之后"
            return f"✗ CHECK-{kind} 失败：{where}找不到 {pat!r}"
    return "✓ 全部匹配；捕获到的变量：" + (str(bound) if bound else "（无）")

GOOD = """\
  func.func @f(%arg0: tensor<4x4xf32>) -> tensor<4x4xf32> {
    %cst = arith.constant 6.000000e+00 : f32
    %0 = pix.scale %arg0, %cst : tensor<4x4xf32>
    return %0 : tensor<4x4xf32>
  }"""
# 多插了一行 pix.add，且常量名换成 %cst_0
BAD = GOOD.replace("    %0 = pix.scale", "    %junk = pix.add %arg0, %arg0 : tensor<4x4xf32>\n    %0 = pix.scale") \
          .replace("%cst", "%cst_0")

DIRECTIVES = [("CHECK", "func.func @f"),
              ("CHECK", "%[[C:.*]] = arith.constant 6.000000e+00"),
              ("NEXT",  "pix.scale %arg0, %[[C]]"),
              ("NOT",   "pix.add")]

print("CHECK 序列：")
for k, p in DIRECTIVES:
    print(f"  // CHECK{'' if k=='CHECK' else '-'+k}: {p}")
# 整体改名：捕获对它免疫，因为定义处和引用处一起变了
RENAMED = GOOD.replace("%cst", "%cst_42")
# 只改引用处：定义是 %cst，使用的却是 %cst_9 —— 这才是捕获要抓的
INCONSISTENT = GOOD.replace("pix.scale %arg0, %cst", "pix.scale %arg0, %cst_9")

for label, text in [("正常输出", GOOD),
                    ("常量整体改名 %cst → %cst_42", RENAMED),
                    ("定义是 %cst，引用却写成 %cst_9", INCONSISTENT),
                    ("多插了一行 pix.add", BAD)]:
    print(f"\n【{label}】")
    print(filecheck(DIRECTIVES, text))
```

运行结果：

```
CHECK 序列：
  // CHECK: func.func @f
  // CHECK: %[[C:.*]] = arith.constant 6.000000e+00
  // CHECK-NEXT: pix.scale %arg0, %[[C]]
  // CHECK-NOT: pix.add

【正常输出】
✓ 全部匹配；捕获到的变量：{'C': 'cst'}

【常量整体改名 %cst → %cst_42】
✓ 全部匹配；捕获到的变量：{'C': 'cst_42'}

【定义是 %cst，引用却写成 %cst_9】
✓ 全部匹配；捕获到的变量：{'C': 'cst'}

【多插了一行 pix.add】
✗ CHECK-NEXT 失败：紧接的下一行找不到 'pix.scale %arg0, %[[C]]'
```

四个结果里有三个符合直觉：整体改名照样过（捕获的价值），多插一行被 `CHECK-NEXT` 抓住（相邻性的价值）。

**第三个不对：定义是 `%cst`、引用写成 `%cst_9`，它居然通过了。**

第一反应是我的模拟器写错了。拿真 FileCheck 对一遍：

```bash
$ cat chk.txt
// CHECK: %[[C:.*]] = arith.constant 6.000000e+00
// CHECK-NEXT: pix.scale %arg0, %[[C]]
$ printf '    %%cst = arith.constant 6.000000e+00 : f32\n    %%0 = pix.scale %%arg0, %%cst_9 : tensor<4x4xf32>\n' | FileCheck chk.txt
$ echo $?
0
```

**真 FileCheck 也通过。** 原因是 FileCheck 做的是**子串匹配**：`%cst` 是 `%cst_9` 的前缀，所以 `pix.scale %arg0, %cst` 作为子串确实出现在那一行里。捕获变量没有边界的概念。

补救办法是给引用加个**定界符**——把紧跟在后面的那个字符也写进 CHECK：

```bash
$ cat chk2.txt
// CHECK: %[[C:.*]] = arith.constant 6.000000e+00
// CHECK-NEXT: pix.scale %arg0, %[[C]] :
$ printf '…%%cst_9 : tensor<4x4xf32>\n' | FileCheck chk2.txt
chk2.txt:2:16: error: CHECK-NEXT: expected string not found in input
// CHECK-NEXT: pix.scale %arg0, %[[C]] :
               ^
```

加一个 ` :` 就抓住了。（想更严格可以用 `--match-full-lines`，但那样对空白和整行内容都变敏感，通常过头。）

## 动手：给 `pix.reduce` 加第四种归约

往枚举里加 `Prod`（全图乘积），走一遍完整流程，你会体会到这套东西"改一处、其他地方自动跟上"的程度：

1. `PixAttrs.td` 的 `Pix_ReduceKind` 里加一个 `I32EnumAttrCase<"Prod", 3, "prod">`。
2. 重新构建。**先别改 `fold`** —— 看编译器报什么。`ReduceOp::fold` 里那个 `switch` 没写 `default`，所以你会收到一条"枚举值未覆盖"的警告，正好指到该改的行。这就是不写 `default` 的回报。
3. 补上 `case ReduceKind::Prod: acc = acc * v; break;`，并想清楚 splat 那条捷径该怎么算（提示：不是"就是那个值"，也不是"乘以元素个数"）。
4. 在 `reduce_kind.mlir` 里加一对用例：一个该折的、一个不该动的。用 `[[1, 5], [3, 2]]` 的话答案是 30——注意它和 sum 的 11、max 的 5、min 的 1 都不同，这样测试才区分得开。
5. `ninja check-pix`。

```bash
MLIR_DIR=$LLVM/build/lib/cmake/mlir books/inside-mlir/verify/verify-pix.sh
```

**再改一处**：把 `reduce_kind.mlir` 里任意一个 `%[[C]] :` 的定界符删掉，然后把测试期望的常量值改成一个**前缀相同的更长数字**（比如 `1.100000e+01` 改成 `1.1` 再配合手改输出），看 FileCheck 怎么被骗过去。亲手骗它一次，以后写 CHECK 会更小心。

---

**这一章的要点**

- **给已经在用的 op 加属性**：用 `DefaultValuedAttr` 让它可以不写、交给 `attr-dict` 打印让默认值不出现、默认值选"和原来行为一致的那个"。三条都做到，老 IR 的输入和**输出**都不变，别人的测试不会红。
- **别把答不出来的情形折出一个答案**。空图的 max/min 没有正确值，`fold` 就该原样返回。和第 11 章"别把化简写得太贪"是同一条原则。
- `switch` 覆盖枚举时**不写 `default:`**。以后枚举加成员，编译器的"未覆盖"警告会直接把你领到该改的地方；写了 `default` 就把这个提醒关掉了。
- **命名管线不是 pass**：`PassPipelineRegistration` 注册的是"往 `OpPassManager` 里加 pass 的函数"。给它起名字的意义是**把"我的方言该怎么化简"这个知识收在方言一侧**，管线内容以后能换，用的人不改命令。
- **lit 是两级配置**：`lit.site.cfg.py.in`（占位符）→ cmake 的 `configure_lit_site_cfg` → 生成的 `lit.site.cfg.py`（真路径）→ 它再 `load_config` 你手写的 `lit.cfg.py`（规则）。排查路径问题，直接 `cat` 生成的那个。
- `%s` / `%t` / `%S` 是 **lit 的替换**，不是 shell 的。RUN 行里能写裸 `pix-opt` 靠的是 `add_tool_substitutions`，它保证测的是**刚编出来的那个**，而不是 `PATH` 里碰巧存在的另一个版本。
- `DEPENDS` 少一个就全崩，而报错只说"找不到"不说"你没编"。`FileCheck count not` 这三个测试工具容易漏。
- **`CHECK-LABEL` 是分段锚点**，不只是匹配一行。它保证函数 A 的断言不会意外匹配到函数 B 的输出。
- **变量捕获 `[[C:.*]]` / `[[C]]` 是子串匹配，没有边界**：`%cst` 会匹配上 `%cst_9`，实测真 FileCheck 也如此。引用处要**加定界符**（多写紧跟的那个字符），否则测试可能悄悄失去效力——**这比测试报错危险得多**。
- 每个化简配一对测试：**「该折的折了」和「不该动的没动」**。只写前一半，有人把 `fold` 写成无条件返回操作数时，测试会全绿。

**pix 进度**：第二部分收尾。pix 现在是一个完整的方言——9 个 op、1 个参数化类型、2 个枚举属性、3 处手写 verifier、1 处接口实现、4 组化简、1 条命名管线，`ninja check-pix` 一条命令跑 8 个测试文件。它从第 7 章一行 ODS 长到这里，每一步都是被一个具体问题逼出来的。
