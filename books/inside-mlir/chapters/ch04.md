# 第 4 章 类型与属性：唯一化、MLIRContext 与内建类型

## 这一章想让你带走什么

<div class="goal-box">
<p>op、region、block 是 MLIR 的骨架，<strong>类型（Type）与属性（Attribute）</strong>是它的另一半：骨架描述"计算怎么连"，类型和属性描述"数据是什么、常量是多少"。这一章的核心是一个反直觉的设计：<strong>它们不是对象，而是不可变的、全局唯一化的值</strong>——<code>tensor&lt;4x4xf32&gt;</code> 在一个 <code>MLIRContext</code> 里只存一份，你手上的 <code>Type</code> 只是个指针大小的句柄。</p>
<p>你会用一个能跑的迷你唯一化器亲手验证这件事，并看清它带来的三个后果：类型比较是<strong>指针比较</strong>、类型能直接当哈希表键、以及 <strong><code>MLIRContext</code> 为什么必须贯穿所有 API</strong>。然后是一遍内建类型巡览，重点讲 MLIR 一个最容易踩坑的决定：<strong>整数类型是无符号性的（signless）</strong>——<code>i32</code> 不告诉你有没有符号，符号语义在 op 上。</p>
</div>

## 类型是值，不是对象

先记三条性质，后面全部由它们推导：

1. **不可变（immutable）**：类型一旦造出来就不能改。想"把元素类型换成 f64"，只能造一个新类型。
2. **唯一化（uniqued）**：内容相同的类型在一个 context 里**只有一份存储**。
3. **句柄很轻**：`mlir::Type` 内部就是一个指向存储的指针，按值传递、放进容器都很便宜。

源码能直接看出第 3 条（`mlir/include/mlir/IR/Types.h`）：

```cpp-norun
// mlir/include/mlir/IR/Types.h
class Type {
public:
  template <typename ConcreteType, typename BaseType, typename StorageType,
            template <typename T> class... Traits>
  using TypeBase = detail::StorageUserBase<ConcreteType, BaseType, StorageType,
                                           detail::TypeUniquer, Traits...>;

  using ImplType = TypeStorage;      // ← 真正的存储在这里，Type 只是它的句柄
  using AbstractTy = AbstractType;
  constexpr Type() = default;
```

而唯一化本身由 `mlir/include/mlir/Support/StorageUniquer.h` 里的 `StorageUniquer` 实现——它是一张"参数 → 存储"的哈希表，住在 `MLIRContext` 里。属性走的是同一套机制。

下面这段代码把这套机制照搬成 50 行 Python。点运行，注意最后统计的那两个数字：

```python
# MLIR 的类型和属性都是"唯一化（uniqued）"的不可变值：
# 同样的类型在一个 MLIRContext 里只存一份，句柄只是一个指针。
# 下面把这套机制照搬成 50 行，看它省下了什么、又强迫你接受什么。

class Context:
    """对应 MLIRContext：唯一化表就住在它里面（所以所有 API 都要能拿到 context）。"""
    def __init__(self):
        self.storages = {}     # (kind, params) -> storage id
        self.get_calls = 0

    def unique(self, kind, params):
        self.get_calls += 1
        key = (kind, params)
        if key not in self.storages:
            self.storages[key] = len(self.storages)   # 第一次见：真的分配一份
        return self.storages[key]


class Type:
    """对应 mlir::Type：一个轻量句柄（内部就是 TypeStorage*），按值传递。"""
    __slots__ = ("ctx", "sid", "text")

    def __init__(self, ctx, kind, params, text):
        self.ctx, self.text = ctx, text
        self.sid = ctx.unique(kind, params)

    # 相等与哈希都只看存储 id —— 这就是"指针比较"
    def __eq__(self, other):
        return isinstance(other, Type) and self.sid == other.sid

    def __hash__(self):
        return hash(self.sid)

    def __repr__(self):
        return self.text


def f32(ctx):
    return Type(ctx, "float", (32,), "f32")

def i(ctx, w):
    return Type(ctx, "int", (w,), f"i{w}")

def tensor(ctx, shape, elem):
    return Type(ctx, "tensor", (shape, elem.sid), f"tensor<{'x'.join(map(str, shape))}x{elem}>")

def vector(ctx, shape, elem):
    return Type(ctx, "vector", (shape, elem.sid), f"vector<{'x'.join(map(str, shape))}x{elem}>")


ctx = Context()

# 在两个"完全无关"的地方各自构造同一个类型
t1 = tensor(ctx, (4, 4), f32(ctx))
t2 = tensor(ctx, (4, 4), f32(ctx))
print(f"t1 = {t1}   存储 id = {t1.sid}")
print(f"t2 = {t2}   存储 id = {t2.sid}")
print(f"t1 == t2 ? {t1 == t2}   （一次整数比较，不是逐字段递归比较）")
print()

# 于是类型可以直接当字典键 / 集合元素用——MLIR 里到处这么干
seen = {t1: "第一次见到它时记的笔记"}
print("拿 t2 去查以 t1 为键的字典：", seen[t2])
print()

# 嵌套类型共享内部存储：tensor<4x4xf32> 和 vector<4x4xf32> 里的 f32 是同一份
v = vector(ctx, (4, 4), f32(ctx))
print(f"{v} 与 {t1} 的元素类型共享存储：{f32(ctx).sid == f32(ctx).sid}")
print()

# 不可变：想"改一改类型"，只能造一个新的；老的谁在用都不受影响
t_f64_like = tensor(ctx, (4, 4), Type(ctx, "float", (64,), "f64"))
print(f"把元素类型换成 f64 → 得到新类型 {t_f64_like}（id {t_f64_like.sid}），")
print(f"而 {t1}（id {t1.sid}）一点没变——这正是'类型是值'的含义。")
print()

types = [t1, t2, v, f32(ctx), i(ctx, 32), i(ctx, 32), t_f64_like]
print(f"一共调用 unique() {ctx.get_calls} 次，实际只分配了 {len(ctx.storages)} 份存储：")
for (kind, params), sid in ctx.storages.items():
    print(f"  id={sid}  {kind:<7} {params}")
print()
print("代价：任何一个类型/属性都必须能找到 context，所以 MLIR 的 API 里 context、")
print("builder、op 三者总是形影不离——这不是啰嗦，是唯一化的必然结果。")
```

运行结果：

<div class="warn">
<strong>两个由此而来的真实陷阱</strong>
<p><strong>一，不要跨 <code>MLIRContext</code> 混用类型。</strong>两个 context 各有自己的唯一化表，即使内容一样也是两份不同的存储，比较会不相等。多 context（比如并行编译多个模块）时这是经典 bug 来源。</p>

## 内建类型巡览

`builtin` 方言提供了一批"大家都要用"的类型。先看一眼全家福，这段 IR 把常用的都摆出来了：

```mlir
// RUN: mlir-opt %s --verify-roundtrip
func.func @zoo(
    %i: i32, %si: si32, %ui: ui32, %ix: index,
    %f: f32, %bf: bf16,
    %v: vector<4x8xf32>, %sv: vector<[4]xf32>,
    %t: tensor<4x?xf32>, %ut: tensor<*xf32>,
    %m: memref<4x8xf32, strided<[8, 1], offset: 0>>,
    %ms: memref<4xf32, 1>,
    %c: complex<f32>) {
  return
}
```

`mlir-opt` 打回来的结果里有个细节值得注意——`strided<[8, 1], offset: 0>` 变成了 `strided<[8, 1]>`：offset 为 0 是默认值，打印器省略了它。**同一个类型的文本可以有多种等价写法，但唯一化保证它们指向同一份存储。**

| 类型 | 要点 |
| --- | --- |
| `i8` / `i32` / `i1` … | **无符号性（signless）**，见下一节。`i1` 就是布尔 |
| `si32` / `ui32` | 显式带符号/无符号。**存在，但 `arith` 不收**，见下一节 |
| `index` | 平台相关宽度的整数，专门用于下标、循环变量、尺寸。**不是 i64** |
| `f16` / `bf16` / `f32` / `f64` / `f8E4M3…` | 浮点家族，低精度格式一应俱全 |
| `vector<4x8xf32>` | **定长**、可多维；`vector<[4]xf32>` 是可伸缩向量（SVE/RVV 那种运行时确定长度） |
| `tensor<4x?xf32>` | 张量，`?` 是动态维；`tensor<*xf32>` 是**未定阶（unranked）** |
| `memref<4x8xf32, strided<[8,1]>, 1>` | 内存缓冲：形状 + **布局（layout）** + **内存空间（memory space）** |
| `complex<f32>` / `tuple<…>` / `none` | 复数、元组、"没有值" |
| `(i32) -> i32` | 函数类型（`func.func` 的 `function_type` 属性就是它） |

两个必须讲清的区分：

**`index` 不是 `i64`。** 它代表"这台机器上的一个下标/尺寸"，具体宽度在下降到 LLVM 时才定（第 24 章）。循环边界、`memref.load` 的下标、`memref.dim` 的结果全是 `index`。把 `index` 和 `i64` 混用是新手最常见的类型错误之一——需要转换时用 `arith.index_cast`。

**`tensor` 与 `memref` 的区别不是"形状"，是语义。** `tensor` 是**值**：它没有地址，不能被写，两个 `tensor` 相等就是内容相等，SSA 规则完全适用。`memref` 是**内存**：它有地址、有布局、有内存空间，可以被 `memref.store` 修改，因此涉及别名与顺序。从前者到后者的那一步叫 **bufferization**，是第 22 章一整章的主题。

## 重点：整数是"无符号性的"（signless）

这是 MLIR 一个刻意的、并且最容易让人踩坑的决定：**`i32` 只说"32 位宽的一堆比特"，不说这些比特是有符号还是无符号。**

符号语义不在类型上，而在**操作**上：

```mlir
// RUN: mlir-opt %s --verify-roundtrip
func.func @sign(%a: i32, %b: i32) -> (i32, i32) {
  %s = arith.divsi %a, %b : i32     // 按有符号除
  %u = arith.divui %a, %b : i32     // 按无符号除
  return %s, %u : i32, i32
}
```

同一个 `i32`，两条不同语义的除法：`divsi`（signed）和 `divui`（unsigned）。加法、比较也是同样的套路（`arith.cmpi slt` vs `ult`）。

那 `si32` / `ui32` 是干什么的？它们**存在**，给需要表达"这个前端的类型系统里有符号"的方言用（比如从 TensorFlow 或某门源语言导入时）。但 `arith` 方言坚决不收它们——实测拿 `si32` 去做 `arith.divsi`：

```
error: 'arith.divsi' op operand #0 must be signless-non-zero-bitwidth-integer-like, but got 'si32'
```

<div class="keypoint">
<strong>为什么这么设计？</strong>
<p>因为"符号"属于<strong>源语言的约定</strong>，不属于机器上的那堆比特。C 的 <code>unsigned</code>、Java 的全有符号、某个 DSL 的饱和无符号——各家规则不同。如果把符号编进类型，每个前端都得先把自己的符号观强加给公共 IR，然后公共 IR 里的每个 op 都要处理各种组合。MLIR 的选择是：<strong>类型只管比特宽度，语义由 op 承担</strong>；需要保留源语言符号信息的方言，可以用 <code>si</code>/<code>ui</code> 在自己那一层表达，下降到 <code>arith</code> 时转成 signless + 选对的 op。官方 <code>mlir/docs/Rationale/Rationale.md</code> 的 "integer signedness semantics" 一节专门论证了这个权衡。</p>
</div>

对你写自己方言的影响（第 9 章会用到）：**如果 `pix` 的图像元素需要区分有符号/无符号，就在 `pix` 层用 `si8`/`ui8` 表达，下降时再决定用哪个 `arith` op。** 别指望 `i8` 帮你记住这件事。

## 属性：编译期就定下来的数据

属性是挂在 op 上的**常量数据**。和类型一样：不可变、唯一化、句柄很轻。

| 属性 | 写法 | 用途 |
| --- | --- | --- |
| `IntegerAttr` / `FloatAttr` | `42 : i64`、`3.0 : f32` | 数值。**注意属性自己带类型** |
| `StringAttr` | `"hello"` | 名字、标签 |
| `ArrayAttr` | `[8, 16]` | 一串属性 |
| `DictionaryAttr` | `{a = 1, b = "x"}` | op 的属性字典本身就是它 |
| `DenseElementsAttr` | `dense<3.0> : tensor<2x2xf32>` | **常量张量**。全同值有 splat 优化 |
| `DenseResourceAttr` | `dense_resource<blob> : tensor<…>` | 大块常量数据（权重），不塞进文本 |
| `TypeAttr` | `f32` | 把类型当数据存 |
| `SymbolRefAttr` | `@my_func` | 引用一个符号（函数名等） |
| `UnitAttr` | 只写名字，没有值 | 布尔开关。见下面的 `flag` |
| `AffineMapAttr` | `affine_map<(d0, d1) -> (d1, d0)>` | 索引映射（第 20 章的主角） |

一段把它们塞满的 IR（`pix.mark` 是未注册 op，所以要加 `--allow-unregistered-dialect`）：

```mlir
// RUN: mlir-opt %s --allow-unregistered-dialect
#map = affine_map<(d0, d1) -> (d1, d0)>

func.func @attrs() attributes {pix.entry, pix.tile_sizes = [8 : i64, 16 : i64]} {
  %a = arith.constant dense<3.0> : tensor<2x2xf32>
  %b = arith.constant dense<3.0> : tensor<2x2xf32>
  %c = arith.constant dense<[[1.0, 2.0], [3.0, 4.0]]> : tensor<2x2xf32>
  "pix.mark"() {perm = #map, name = "hello", flag} : () -> ()
  return
}
```

运行结果：

```
#map = affine_map<(d0, d1) -> (d1, d0)>
module {
  func.func @attrs() attributes {pix.entry, pix.tile_sizes = [8, 16]} {
    %cst = arith.constant dense<3.000000e+00> : tensor<2x2xf32>
    %cst_0 = arith.constant dense<3.000000e+00> : tensor<2x2xf32>
    %cst_1 = arith.constant dense<[[1.000000e+00, 2.000000e+00], [3.000000e+00, 4.000000e+00]]> : tensor<2x2xf32>
    "pix.mark"() {flag, name = "hello", perm = #map} : () -> ()
    return
  }
}
```

四个观察：

1. **`pix.entry` 和 `flag` 是 `UnitAttr`**：只有名字没有值，"在不在"就是全部信息。用它表达布尔开关比 `= true` 更地道。
2. **`[8 : i64, 16 : i64]` 打印成了 `[8, 16]`**：`i64` 是整数属性的默认类型，打印器省略。但它确实是有类型的——写 `8 : i32` 就会打印出来。
3. **属性字典被排序了**（`flag, name, perm`）：字典属性的顺序不是语义，所以打印时按名字排。别依赖顺序。
4. **`#map` 被提成了别名**：打印器把重复用到的属性提取成 `#name = ...` 的形式，IR 更短。第 3 章看到的 `#loc` 是同一个机制。

### 唯一化的一个可观察后果

上面那段 IR 里有两个一模一样的 `dense<3.0>` 常量。让它们都被用到，然后跑 `--cse`：

```mlir
// RUN: mlir-opt %s --cse
func.func @twice(%x: tensor<2x2xf32>) -> tensor<2x2xf32> {
  %a = arith.constant dense<3.0> : tensor<2x2xf32>
  %b = arith.constant dense<3.0> : tensor<2x2xf32>
  %p = arith.addf %x, %a : tensor<2x2xf32>
  %q = arith.mulf %p, %b : tensor<2x2xf32>
  return %q : tensor<2x2xf32>
}
```

运行结果：

```
module {
  func.func @twice(%arg0: tensor<2x2xf32>) -> tensor<2x2xf32> {
    %cst = arith.constant dense<3.000000e+00> : tensor<2x2xf32>
    %0 = arith.addf %arg0, %cst : tensor<2x2xf32>
    %1 = arith.mulf %0, %cst : tensor<2x2xf32>
    return %1 : tensor<2x2xf32>
  }
}
```

两个常量合成了一个。**CSE 之所以敢这么干、而且判断得飞快，就是因为属性唯一化**：判断"这两个 `arith.constant` 是不是同一个东西"只需要比较属性句柄（一次指针比较），不需要逐元素对比两张 2×2 的张量。如果常量是一张 1024×1024 的权重，这个差别就是天壤之别。

<div class="note">
<strong>大常量：别把权重塞进文本</strong>
<p><code>DenseElementsAttr</code> 把数据存在属性里，打印时会**全部**打成文本。一张几 MB 的权重这样打印出来，文件巨大、解析极慢。MLIR 为此提供了 <strong>resource</strong> 机制（<code>dense_resource&lt;…&gt;</code>）：数据存在模块尾部的资源区（或外部文件），属性里只留一个引用。做端到端 AI 编译（第 27 章的 IREE）时这是必需品。</p>
</div>

## 动手：亲手验证唯一化与 signless

```bash
# 1. 两个"看起来不同写法"的同一类型，是不是同一个？
#    把 memref<4x8xf32, strided<[8,1], offset: 0>> 和 memref<4x8xf32> 都写进函数签名，
#    看 mlir-opt 打印回来变成了什么
mlir-opt zoo.mlir --verify-roundtrip

# 2. signless：把 arith.divsi 的操作数类型改成 si32，看报错
mlir-opt sign.mlir --verify-roundtrip

# 3. 属性唯一化的威力：把 dense<3.0> 改成一个 8x8 的显式列表，两份一样的，再跑 cse
mlir-opt twice.mlir --cse
```

**改一改：**

1. 把 `%p = arith.addf %x, %a` 里的 `%a` 和 `%b` 改成**不同**的值（比如 `dense<3.0>` 和 `dense<4.0>`），再跑 `--cse`。这次合并不了——CSE 只合并"完全相同"的 op，而相同性的判断落在属性句柄上。
2. 写 `%c = arith.constant dense<[[1.0, 2.0], [3.0, 4.0]]> : tensor<2x2xf32>`，再写一个 `dense<1.0>` 的 splat 版本。用 `--mlir-print-op-generic` 看两者的属性打印形式有什么不同（提示：splat 只存一个值）。
3. 把某个 `index` 类型的值直接喂给需要 `i64` 的地方，看报错。然后用 `arith.index_cast` 修好它。记住这个错误的样子——你以后会反复遇到。
4. 试着把 `tensor<4x?xf32>` 的动态维改成 `tensor<4x8xf32>` 但函数体里仍按动态处理，看 verifier 是否抓得住。这是第 10 章"类型推断与验证"的预习。

---

**这一章的要点**

- 类型与属性是**不可变、唯一化的值**，`Type` / `Attribute` 只是指向存储的轻量句柄；存储由 `MLIRContext` 里的 `StorageUniquer` 管。
- 三个后果：**比较 = 指针比较**（O(1)，与类型复杂度无关）、可直接当哈希表键、**构造任何类型都要 context**（这就是 MLIR API 里 context/builder 无处不在的原因）。
- 两个陷阱：**不要跨 context 混用**类型；类型属性的寿命等于 context 的寿命。
- `index` 不是 `i64`；`tensor` 是**值**、`memref` 是**内存**，两者之间那一步叫 bufferization（第 22 章）。
- **整数是 signless 的**：`i32` 不带符号语义，符号在 op 上（`divsi` vs `divui`）。`si32`/`ui32` 存在，但 `arith` 不收——需要保留源语言符号信息时，在你自己那一层用它们。
- 属性是编译期常量数据，**自己带类型**（`8 : i64`）。`UnitAttr` 是最地道的布尔开关；打印器会把重复属性提成 `#name` 别名；大块权重应该走 resource 而不是塞进文本。
- 属性唯一化不是抽象美感：**CSE 能靠一次指针比较合并两个 1024×1024 的常量**，你已经在 `--cse` 的输出里看到了。
