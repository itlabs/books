## 逐层点名

不求背下来，求看到名字能立刻定位它在塔的哪一层。

### 结构层：`builtin` / `func`

`builtin` 提供最基础的东西：`builtin.module`（第 2 章讲过，它就是个 op）、内建类型（`tensor`、`memref`、`vector`、`index`……）、内建属性、以及 `builtin.unrealized_conversion_cast`——第 17 章讲类型转换时那个"临时桥"。

`func` 提供 `func.func`、`func.call`、`func.return`。注意它**不是唯一的函数方言**：`gpu.func`、`llvm.func` 都是"函数"，都实现 `FunctionOpInterface`（第 5 章的接口机制），所以通用的符号处理、内联框架对它们一视同仁。

### 计算层：`arith` / `math` / `complex` / `index`

`arith` 是标量与逐元素算术：`addi`/`addf`/`mulf`/`cmpi`/`cmpf`/`select`/`constant`/`index_cast`。第 4 章讲的 signless 规则就在这里落地（`divsi` vs `divui`）。它也能作用在 `vector` 和 `tensor` 上（第 1 章第一个例子就是）。

`math` 是超越函数：`exp`/`log`/`sqrt`/`fma`/`erf`。分开是因为它们往往要走库函数或特殊指令，下降策略与基本算术不同。

`index` 方言专门处理 `index` 类型上的运算（`index.add`、`index.mul`），在需要与目标位宽解耦时用。

### 控制流层：`scf` / `cf` / `affine`

`scf`（structured control flow）是**结构化**控制流：`scf.for`、`scf.while`、`scf.if`、`scf.forall`（并行）、`scf.yield`。特点是"循环还是循环"——第 2 章看到的 region + 块参数 + yield 那一套。

`cf`（control flow）是**非结构化**的：`cf.br`、`cf.cond_br`、`cf.switch`。这就是 LLVM IR 那种基本块 + 分支的世界。

`affine` 也是结构化循环，但它要求下标与边界都是**仿射表达式**，于是能用多面体方法做精确的依赖分析和变换。它比 `scf` 强，但要求也更严。

### 数据层：`tensor` / `memref` / `vector` / `bufferization`

`tensor` 是不可变的值：`tensor.empty`、`tensor.extract`、`tensor.insert_slice`、`tensor.expand_shape`。注意 `tensor.insert_slice` **不是**原地写——它产生一个新张量（语义上），这正是值语义的体现。

`memref` 是内存：`memref.alloc`/`alloca`/`dealloc`/`load`/`store`/`subview`/`collapse_shape`。类型里带布局与内存空间（第 4 章）。

`vector` 是"宽度已定"的向量运算：`vector.transfer_read`/`transfer_write`（带 mask 的搬运，第 23 章的主角）、`vector.contract`、`vector.broadcast`、`vector.shape_cast`。

`bufferization` 是那条边本身：`bufferization.to_memref`、`to_tensor`、`alloc_tensor`，以及 one-shot bufferize 用到的接口（第 22 章）。

### 结构化计算层：`linalg` / `tosa` / `sparse_tensor` / `shape`

`linalg` 是第四部分的枢纽：`linalg.generic` 加一串 named op（`linalg.matmul`、`linalg.fill`、`linalg.copy`……）。它的核心是用 **indexing map** 把"迭代空间 → 每个操作数的访存下标"写成属性，于是 tiling、融合、向量化能被**通用地**实现（第 20 章）。

`tosa` 是一套标准化的算子集，常用作前端入口（从 TensorFlow/TFLite/ONNX 进来）。`sparse_tensor` 提供稀疏张量的编码与自动稀疏化。`shape` 处理动态形状的推理与断言。

### 设备与目标层：`gpu` / `nvvm` / `rocdl` / `spirv` / `llvm` / `emitc`

`gpu` 是**与厂商无关**的设备抽象：`gpu.module`、`gpu.func`、`gpu.launch_func`、`gpu.thread_id`、`gpu.barrier`。第 25 章会从它分叉到三个出口：`nvvm`（NVIDIA，对应 PTX 内建）、`rocdl`（AMD）、`spirv`（Vulkan/OpenCL/Intel GPU）。

`llvm` 方言是 LLVM IR 在 MLIR 里的镜像：`llvm.func`、`llvm.load`、`llvm.getelementptr`、`!llvm.ptr`、`!llvm.struct<…>`。**它仍然是 MLIR**（下一节细说这条边界）。

`emitc` 反方向走：把 IR 变成 C/C++ 源码，给只能吃 C 的工具链用。

### 横切方言：不在塔里，但很重要

`transform` 把"怎么做变换"写成 IR（第 18 章）；`pdl`/`pdl_interp` 把"匹配什么模式"写成 IR（第 15 章）；`irdl` 把"方言本身的定义"写成 IR；`ub` 显式表达未定义行为（`ub.poison`）；`async`、`omp`、`acc` 提供并发/卸载模型；`quant` 管量化参数。

<strong>方言多到什么程度？</strong>
<p>本书基线版本的 <code>mlir/lib/Dialect/</code> 下有四十多个目录，除了上面点到的，还有 <code>ArmNeon</code>、<code>ArmSME</code>、<code>ArmSVE</code>、<code>X86</code>、<code>AMDGPU</code>、<code>XeGPU</code>（Intel GPU）、<code>NVGPU</code> 这类硬件专用方言，以及 <code>MPI</code>、<code>Shard</code>（分布式）、<code>SMT</code>（求解器）、<code>WasmSSA</code>、<code>MLProgram</code>、<code>Ptr</code>、<code>DLTI</code>（数据布局）等等。想知道你这份二进制注册了哪些，敲 <code>mlir-opt --show-dialects</code>——接手一个陌生的 <code>xxx-opt</code> 时，这是第一个该跑的命令。</p>

## 四条最容易混的边界

### 1. `scf` 与 `cf`：一条单向的门

`scf` → `cf` 很容易（`--convert-scf-to-cf`），反过来**极难**：从一堆分支里认出"这是个 for 循环"就是第 1 章讲的那种考古。

**所以：该在结构化层做的变换（tiling、融合、并行化），必须在下降到 `cf` 之前做完。** 这条原则决定了真实管线的顺序，也是"渐进下降"最实际的意义。

### 2. `tensor` 与 `memref`：值语义与内存语义

不是"抽象 vs 具体"，是**两套完全不同的推理规则**。`tensor` 上 SSA 规则够用：一个值定义一次，谁读都一样。`memref` 上你必须操心别名、读写顺序、生命周期。

跨过这条边的那一步（bufferization）是第 22 章一整章，因为它要回答"哪些张量可以就地复用同一块内存"这个本质困难的问题。

### 3. `affine` 与 `scf`：本书为什么走 `scf`

`affine` 更强：仿射约束让依赖分析精确，能做多面体调度。但它要求所有下标和边界都是仿射表达式——一旦出现数据相关的下标（`a[b[i]]`）或运行时形状，就掉出这个世界。

本书第四部分走 **`linalg` + `scf` + `transform`** 这条线，因为它是当下 AI 编译栈（Triton、IREE）实际走的路，也更容易和你自己的方言对接。`affine` 在第 21 章会作为对照出现一次。

### 4. `llvm` 方言 ≠ LLVM IR

这条最容易被忽略，但很关键：

- `llvm` **方言**是 MLIR 的一个方言，它的 op 是 `Operation`，住在 region 和 block 里，遵守 MLIR 的一切规则——你可以对它跑 `--canonicalize`、可以写 pattern、可以打印成 `.mlir`。
- LLVM **IR** 是 LLVM 自己那套 `Module`/`Function`/`Instruction`。

两者之间由 **`mlir-translate --mlir-to-llvmir`** 连接（第 24 章）。这一步是纯粹的"换数据结构"，不做优化。**"降到 llvm 方言"和"变成 LLVM IR"是两件事，差着一个工具。**

## 实验：让同一段 IR 走完四层

下面这段 `linalg.generic` 做的事很简单：把输入 buffer 每个元素乘一个系数，写进输出 buffer。注意 `indexing_maps` 那个 `(d0) -> (d0)`——它说明输入输出都按同一个下标访问，也就是"逐点"。

```mlir
// RUN: mlir-opt %s --verify-roundtrip
#id = affine_map<(d0) -> (d0)>
func.func @scale(%in: memref<8xf32>, %out: memref<8xf32>, %f: f32) {
  linalg.generic {indexing_maps = [#id, #id], iterator_types = ["parallel"]}
      ins(%in : memref<8xf32>) outs(%out : memref<8xf32>) {
  ^bb0(%a: f32, %b: f32):
    %m = arith.mulf %a, %f : f32
    linalg.yield %m : f32
  }
  return
}
```

**第一步：降掉 `linalg`。**

```bash
mlir-opt scale.mlir --convert-linalg-to-loops
```

运行结果：

```
module {
  func.func @scale(%arg0: memref<8xf32>, %arg1: memref<8xf32>, %arg2: f32) {
    %c0 = arith.constant 0 : index
    %c8 = arith.constant 8 : index
    %c1 = arith.constant 1 : index
    scf.for %arg3 = %c0 to %c8 step %c1 {
      %0 = memref.load %arg0[%arg3] : memref<8xf32>
      %1 = arith.mulf %0, %arg2 : f32
      memref.store %1, %arg1[%arg3] : memref<8xf32>
    }
    return
  }
}
```

`linalg.generic` 变成了 `scf.for` + `memref.load/store`。**注意迭代空间的信息去哪了**：原来在 `indexing_maps` 属性里，现在变成了循环边界和下标表达式——这就是第 1 章讲的"下降即丢信息"，而 `0 to 8 step 1` 恰好还能读懂，是因为这个例子太简单。

**第二步：把结构化循环拆成基本块。**

```bash
mlir-opt scale.mlir --convert-linalg-to-loops --convert-scf-to-cf
```

运行结果：

```
module {
  func.func @scale(%arg0: memref<8xf32>, %arg1: memref<8xf32>, %arg2: f32) {
    %c0 = arith.constant 0 : index
    %c8 = arith.constant 8 : index
    %c1 = arith.constant 1 : index
    cf.br ^bb1(%c0 : index)
  ^bb1(%0: index):  // 2 preds: ^bb0, ^bb2
    %1 = arith.cmpi slt, %0, %c8 : index
    cf.cond_br %1, ^bb2, ^bb3
  ^bb2:  // pred: ^bb1
    %2 = memref.load %arg0[%0] : memref<8xf32>
    %3 = arith.mulf %2, %arg2 : f32
    memref.store %3, %arg1[%0] : memref<8xf32>
    %4 = arith.addi %0, %c1 : index
    cf.br ^bb1(%4 : index)
  ^bb3:  // pred: ^bb1
    return
  }
```

循环没了，变成三个基本块加一个回边。归纳变量成了 `^bb1` 的块参数 `%0`（第 2 章讲的块参数替代 phi，这里活生生出现了）。**"这是一个从 0 到 8 的循环"这件事，现在只能靠分析恢复。**

**第三步：一路到 `llvm` 方言。**

```bash
mlir-opt scale.mlir --convert-linalg-to-loops --convert-scf-to-cf --convert-to-llvm
```

运行结果（截取开头）：

```
module {
  llvm.func @scale(%arg0: !llvm.ptr, %arg1: !llvm.ptr, %arg2: i64, %arg3: i64, %arg4: i64, %arg5: !llvm.ptr, %arg6: !llvm.ptr, %arg7: i64, %arg8: i64, %arg9: i64, %arg10: f32) {
    %0 = llvm.mlir.poison : !llvm.struct<(ptr, ptr, i64, array<1 x i64>, array<1 x i64>)>
    %1 = llvm.insertvalue %arg5, %0[0] : !llvm.struct<(ptr, ptr, i64, array<1 x i64>, array<1 x i64>)> 
    %2 = llvm.insertvalue %arg6, %1[1] : !llvm.struct<(ptr, ptr, i64, array<1 x i64>, array<1 x i64>)> 
    %3 = llvm.insertvalue %arg7, %2[2] : !llvm.struct<(ptr, ptr, i64, array<1 x i64>, array<1 x i64>)> 
    %4 = llvm.insertvalue %arg8, %3[3, 0] : !llvm.struct<(ptr, ptr, i64, array<1 x i64>, array<1 x i64>)> 
    %5 = llvm.insertvalue %arg9, %4[4, 0] : !llvm.struct<(ptr, ptr, i64, array<1 x i64>, array<1 x i64>)> 
```

<div class="keypoint">
<strong>这段输出里藏着第 24 章的主题。</strong>
<p>原来函数只有三个参数（两个 <code>memref</code> 加一个 <code>f32</code>），现在变成了<strong>十一个</strong>。因为一个 <code>memref&lt;8xf32&gt;</code> 在 LLVM 那边没有对应类型，它被展开成一个<strong>描述符结构体</strong>：<code>(分配指针, 对齐指针, offset, sizes 数组, strides 数组)</code>——就是那个 <code>!llvm.struct&lt;(ptr, ptr, i64, array&lt;1 x i64&gt;, array&lt;1 x i64&gt;)&gt;</code>。那一串 <code>llvm.insertvalue</code> 是在把散开的参数重新装配成描述符。</p>
<p>这是一次 <strong>1 对 N 的类型转换</strong>（第 17 章的难点之一）：一个高层类型对应多个低层值。看懂这件事，你就明白为什么 dialect conversion 需要 <code>TypeConverter</code> 和"物化（materialization）"这套机制。</p>
</div>

## 用一段代码判断"我现在在哪一层"

真实项目里管线一卡住，第一个要回答的问题就是"现在这段 IR 在哪几层、下一步该跑什么"。把上面四步的 op 列表喂给下面这个小程序，它会告诉你答案：

```python
# 给一段 IR 里出现的 op 名，判断它"现在在哪几层"，并建议下一步该跑哪个下降 pass。
# 真实项目里你会反复做这个判断：管线卡住时，先问"我现在在哪一层"。

# 方言 → (层号, 层名)。层号越小越抽象，越大越贴近机器。
LAYER = {
    "tosa": (0, "算子图 / 前端入口"),

def analyze(title, ops):
    dialects = []
    for op in ops:
        d = op.split(".")[0]
        if d not in dialects:
            dialects.append(d)
    known = [d for d in dialects if d in LAYER]
    unknown = [d for d in dialects if d not in LAYER]
    lo = min(LAYER[d][0] for d in known)
    hi = max(LAYER[d][0] for d in known)

    print(f"【{title}】")
    print("  出现的方言：" + "、".join(dialects) + ("（未登记：" + "、".join(unknown) + "）" if unknown else ""))
    for d in sorted(known, key=lambda x: LAYER[x][0]):
        print(f"    层 {LAYER[d][0]}  {d:<8} {LAYER[d][1]}")
    print(f"  跨度：层 {lo} → 层 {hi}" + ("（混着好几层，这在渐进下降的中途是正常的）" if hi - lo >= 2 else ""))
    nxt = [(s, t, p) for s, t, p in EDGES if s in known and t not in known]
    if nxt:
        print("  下一步可以：")
        for s, t, p in nxt:
            print(f"    {s} → {t}\t{p}")
    else:
        print("  已经到底了（llvm 方言之后交给 mlir-translate，见第 24 章）")
    print()
```

**改一改：**

1. **调换下降顺序**：先 `--convert-scf-to-cf` 再 `--convert-linalg-to-loops`。输出里**仍然有 `scf.for`**——因为 `scf→cf` 那趟跑的时候，`linalg` 还没降下来，一个 `scf` op 都还不存在，那趟等于空跑。**管线是一个有序过程，不是 pass 的集合**，而且顺序错了不会报错，只会悄悄少做事（第 3 章那个 anchor 的坑是同一类问题）。
2. 把 `memref<8xf32>` 改成 `memref<?xf32>`（动态大小），重跑第一步。循环上界从哪来了？（提示：`memref.dim`）这就是动态形状的代价。
3. 只跑 `--convert-linalg-to-loops --convert-to-llvm`，**跳过** `--convert-scf-to-cf`。你可能以为会报错，但它**成功退出**，给你一个混着的 IR：外面是 `llvm.func`，里面的算术和访存全变成了 `llvm.*`，可中间那个 **`scf.for` 还立着**（在输出里搜 `scf.` 就能找到它）。原因是 `--convert-to-llvm` 覆盖的是一批"声明了到 LLVM 怎么降"的方言，`scf` 不在其中。这个坑的真正代价在第 24 章才浮现：`mlir-translate` 要求**所有** op 都在 `llvm` 方言里，剩一个 `scf.for` 就翻译不出 LLVM IR。**"没报错"不等于"降完了"。**
4. 把 `iterator_types = ["parallel"]` 改成 `["reduction"]`，看 verifier 抱怨什么。这是第 20 章 `linalg` 语义的预习。

---

**这一章的要点**

- 方言的"分层"是**使用者的心智模型**，不是框架强制的；但它决定了管线顺序，必须建立起来。
- 塔从上到下：入口层（`tosa`/你的方言）→ 结构化计算（`linalg`/`tensor`）→ 循环与内存（`scf`/`affine`/`memref`）→ 标量与向量（`arith`/`math`/`vector`）→ 非结构化控制流（`cf`/`func`）→ 目标层（`llvm`/`nvvm`/`spirv`）。横切的还有 `transform`、`pdl`、`ub`、`async` 等。
- 四条边界：**`scf`→`cf` 是单向门**（结构化变换必须在过门之前做完）；**`tensor` vs `memref` 是两套推理规则**（那条边叫 bufferization）；**`affine` 更强但要求更严**，本书走 `linalg`+`scf`；**`llvm` 方言不是 LLVM IR**，中间隔着 `mlir-translate`。
- 实验结论：同一段 IR 四步下降，`linalg.generic` → `scf.for`+`memref` → `cf`+块参数 → `llvm` 方言；**一个 `memref` 参数在最后展开成了五个值组成的描述符结构体**，这是 1 对 N 类型转换的活样本（第 17、24 章）。
- 任何时候想知道"我在哪一层、下一步跑什么"，先列出 IR 里出现的方言——你已经有一个能干这件事的小工具了。
