# 第 26 章 Triton：Python DSL 到 PTX，layout 系统是它的核心创造

## 这一章想让你带走什么

<div class="goal-box">
<p>第五部分看真实项目。Triton 是 MLIR 上最成功的产品之一——几乎所有现代 LLM 推理栈里都有它编译出来的 kernel。</p>
<p>这一章<strong>不教 Triton 语言怎么写</strong>（`@triton.jit`、`tl.load`、`tl.dot` 那些，《GPU 编程》讲过）。这一章看的是：<strong>它在 MLIR 上做了什么别人没做的事。</strong></p>
<p>答案是 <strong>layout 系统</strong>。Triton 的分层（<code>tt</code> → <code>ttg</code> → LLVM）本身很常规，你读完前 25 章就能猜到；真正的原创在于它给张量类型挂了一个 <strong>encoding 属性</strong>，用来精确描述"这个张量的每个元素住在哪个线程的哪个寄存器里"。这个东西前 25 章完全没出现过——我们的 pix 从 <code>tensor</code> 一路降到 PTX，中间**从来没有表达过"数据在线程间怎么分布"**。</p>
<p>为什么这是性能的钥匙：GPU 上最贵的操作往往不是计算，而是<strong>数据在线程之间搬动</strong>。layout 把这件事变成了类型系统里的信息，于是"两个算子的数据分布是否一致"成了编译器能检查、能优化的事——而不是程序员脑子里的事。</p>
<p>所有 op 名、属性名、设计动机都锚在 <code>triton-lang/triton</code> 的 <code>84fa223</code>（2026-09-21）上。</p>
</div>

## 分层：三个方言，前缀就是它们的名字

Triton 的方言命名很朴素，`let name` 直接就是 IR 里的前缀：

| 方言 | 前缀 | 管什么 |
| --- | --- | --- |
| `Triton` | `tt` | 与硬件无关的张量计算：`tt.load`、`tt.store`、`tt.dot`、`tt.addptr` |
| `TritonGPU` | `ttg` | **带 layout 的** GPU 表示：`ttg.convert_layout`、`ttg.local_alloc`、异步拷贝 |
| `TritonNvidiaGPU` | `ttng` | NVIDIA 专有：TMA、TMEM 那些 |
| `TritonInstrument` | `tti` | 插桩/调试 |
| `Gluon` | `gluon` | 较新的一层，暂不展开 |

对应两个转换目录：`Conversion/TritonToTritonGPU/` 和 `Conversion/TritonGPUToLLVM/`。所以主干是：

```
Python（@triton.jit）→ tt → ttg → LLVM 方言 → PTX
```

**这个分层的形状你应该觉得眼熟**：`tt` 相当于我们的 pix（领域语义、与硬件无关），`ttg` 相当于第 25 章 outlining 之后那一层（已经知道 GPU 层级但还没到指令），最后落 LLVM。第 20 章那个"每一步只决定一件事"的原则，Triton 遵守得很彻底。

**但 `tt` → `ttg` 这一步做的事和我们完全不同。** 我们那一步（第 20 章 pix → linalg）加的是**迭代空间**；Triton 这一步加的是 **layout**。

## layout：类型上的一个属性

Triton 给张量类型挂了一个 **encoding 属性**。`TritonGPUAttrDefs.td` 里定义了十几种，分两大类：

**寄存器里的分布**——`BlockedEncodingAttr`（`#ttg.blocked_layout`）、`NvidiaMmaEncodingAttr`、`AMDMfmaEncodingAttr`、`AMDWmmaEncodingAttr`、`LinearEncodingAttr`……

**shared memory 里的布局**——`SwizzledSharedEncodingAttr`、`PaddedSharedEncodingAttr`、`NVMMASharedEncodingAttr`、`AMDRotatingSharedEncodingAttr`……

看最基础的 `blocked`。上游文档里那张图值得原样引用（`TritonGPUAttrDefs.td:757`）：

```
Example 1, a row-major coalesced layout may partition a 16x16 tensor over 2 warps (i.e. 64 threads) as follows:

[ 0  0  1  1  2  2  3  3  ; 32 32 33 33 34 34 35 35 ]
[ 0  0  1  1  2  2  3  3  ; 32 32 33 33 34 34 35 35 ]
[ 4  4  5  5  6  6  7  7  ; 36 36 37 37 38 38 39 39 ]
[ 4  4  5  5  6  6  7  7  ; 36 36 37 37 38 38 39 39 ]
...
[ 28 28 29 29 30 30 31 31 ; 60 60 61 61 62 62 63 63 ]
[ 28 28 29 29 30 30 31 31 ; 60 60 61 61 62 62 63 63 ]

for

#ttg.blocked_layout<{
  sizePerThread = {2, 2}
  threadsPerWarp = {8, 4}
  blocked = {{0, 1}}
}>
```

**图里的数字是线程号。** 读法：第 0 号线程拥有左上角 2×2 那四个元素（`sizePerThread = {2, 2}`），一个 warp 的 32 个线程排成 8×4（`threadsPerWarp = {8, 4}`），第二个 warp（线程 32–63）接着排在右边。

三个参数的含义（文档原话："three tuples -- thread tile size, warp tile size, and block tile size"）：**一个线程拥有多少元素、一个 warp 里线程怎么排、一个 CTA 里 warp 怎么排。**

<div class="keypoint">
<strong>为什么这值得放进<em>类型</em>里</strong>
<p>因为它决定两件性能上最要紧的事。</p>
<p><strong>① 访存是否合并（coalescing）。</strong>文档那句 "used to promote memory coalescing in LoadInst and StoreInst" 就是说：相邻线程读相邻地址，一次内存事务能服务整个 warp；layout 排错了，同一个 warp 的 32 个线程可能落在 32 个不同的 cache line 上——带宽利用率掉到 1/32。</p>
<p><strong>② 能不能直接喂给 tensor core。</strong><code>tt.dot</code> 要用 MMA 指令，而 MMA 对"哪个线程持有哪个元素"有<strong>硬性要求</strong>。这就是 <code>NvidiaMmaEncodingAttr</code> 存在的理由——它不是一种"优化过的布局"，而是"硬件规定的布局"。</p>
<p>前 25 章我们的 pix 从头到尾没表达过这件事。CPU 上不需要：向量化（第 23 章）只关心"一次算几个元素"，不关心"哪个核持有哪个"。<strong>GPU 上 layout 是一等信息，这是 CPU 与 GPU 编译最本质的差别之一。</strong></p>
</div>

## `ttg.convert_layout`：成本被显式化了

两个算子要的 layout 不一致怎么办？插一个转换：

```cpp-norun
def TTG_ConvertLayoutOp : TTG_Op<"convert_layout",
                                 [SameOperandsAndResultShape,
                                  SameOperandsAndResultElementType,
                                  Pure]> {
  let summary = "convert layout";
  let arguments = (ins TT_Tensor:$src, UnitAttr:$force_warp_shuffle);
  let results = (outs TT_Tensor:$result);
  let hasVerifier = 1;
  let hasCanonicalizer = 1;
}
```

注意这个 op 的 trait：`SameOperandsAndResultShape`、`SameOperandsAndResultElementType`、`Pure`。**形状一样、元素类型一样、纯函数——从语义上它什么都没做。** 变的只有 encoding。

但它在运行时是**很贵的**：数据要经过 shared memory 或 warp shuffle 重新分发。那个 `force_warp_shuffle` 属性就是让你强制走 shuffle 而不是 shared memory。

<div class="keypoint">
<strong>Triton 优化的核心命题：消掉 convert_layout</strong>
<p>把上面几件事连起来，Triton 的性能工程就有了清晰的形状：</p>
<p><strong>① layout 是类型的一部分</strong>，所以"两个算子的数据分布是否一致"是编译器能<strong>检查</strong>的（<code>hasVerifier = 1</code>）。</p>
<p><strong>② 不一致的代价被显式化成一个 op</strong>，所以它是编译器能<strong>看见、能计数、能优化</strong>的（<code>hasCanonicalizer = 1</code>）。</p>
<p><strong>③ 于是优化目标变得可操作</strong>：让相邻算子的 layout 尽量一致，好让 <code>convert_layout</code> 被消掉或至少减少。<code>TritonGPU/Transforms/</code> 下一大批 pass 干的就是这件事。</p>
<p>对比手写 CUDA：数据分布在你脑子里，"这里要不要走一次 shared memory 重排"靠经验判断，改一处可能破坏另一处。<strong>Triton 把它变成了编译器的工作。</strong>这才是它相对手写 kernel 的真正优势——不是"生成的代码更聪明"，而是<strong>"这类决策能被系统性地优化"</strong>。</p>
</div>

## linear layout：把十几种 encoding 统一成一个数学对象

十几种 encoding 意味着 N² 级别的两两转换逻辑。Triton 后来的解法很漂亮，在 `include/triton/Tools/LinearLayout.h` 里。

头文件开头的注释把思想说得非常清楚（原话）：

> In Triton, a linear layout (LL) is a function that maps from a **"hardware location"** to a **"logical tensor index"**.
>
> For example, suppose we have a 2D tensor T stored in GPU registers. T's layout (i.e., L) is the function that, given a "hardware location" tuple of (thread-id, warp-id), returns an index (x,y) into T. In other words, if `L(t,w) = (x,y)` is our linear layout func, then a register in thread t in warp w contains the value `T[x,y]`.

**一个函数：硬件位置 → 逻辑下标。** 所有 encoding 都只是这个函数的不同写法。

关键的那一步是"linear"：

> The key fact about LLs is, the mapping from (t,w) to (x,y) is not arbitrary. We only need to specify the value of L(t,w) at certain special points (namely, the values L(t,0) and L(0,w) where t and w are powers of 2), and from those we can compute all the other values of L.

**只需要指定 2 的幂次处的值**，其余全部由线性性推出——而这里的"线性"是 GF(2) 上的，加法就是 **XOR**（源码注释：*"All other values of L are computed by xor'ing bases together, using the linearity rule"*）。

一个 4 warp × 4 thread 的布局，只需要四个基向量：`L(1,0)`、`L(2,0)`、`L(0,1)`、`L(0,2)`。

<div class="note">
<strong>这个设计的来源与代价</strong>
<p>源码注释里点了名：<em>"The idea for linear layouts is due to Adam P. Goucher."</em></p>
<p>收益是结构性的：<strong>N 种 encoding 的两两转换，从 N² 份特例代码变成了"都转成 LL 再做通用运算"。</strong>LL 之间可以复合、求逆、判等——这些都是纯粹的线性代数，而不是针对每对 layout 手写的逻辑。</p>
<p>注释里还顺带和 CuTe 做了对比（<code>LinearLayout.h:313</code>）：<em>"CuTe requires a CUDA compiler such as nvcc; LLs do not."</em> LL 是编译器内部的数据结构，不依赖任何厂商工具链。</p>
<p>代价也要说：<strong>LL 只能表达"2 的幂次 + XOR"这一类布局。</strong>幸运的是 GPU 的硬件布局几乎都是这种形式（warp 大小、tile 尺寸都是 2 的幂），所以这个限制在实践中很少咬人。这是一个"选对了抽象"的漂亮例子——<strong>限制恰好和硬件的实际形状对齐。</strong></p>
</div>

## 把 layout 与它的代价算出来

linear layout 的两件事——XOR 推导规则、以及转换代价——都能直接算。下面这个模型实现了那条推导规则（只给基向量，其余靠 XOR），然后量化"换一种 layout 要搬多少数据"：

```python
# linear layout 是什么？一个从「硬件位置」到「逻辑张量下标」的函数。
# 关键事实（引自 Triton 的 include/triton/Tools/LinearLayout.h）：
#   只需指定 2 的幂次处的值，其余全部由 **XOR 线性性** 推出。
# 这个模型把那条推导规则实现出来，于是 layout 转换的代价也能算。

def build(bases, out_rank=2):
    """bases[dim][i] = L(...,该维=2^i,...)。其余位置由 XOR 组合得出。"""
    def L(**loc):
        acc = [0] * out_rank
        for dim, v in loc.items():
            i = 0
            while v:
                if v & 1:                       # 这一位是 1 → 把对应的基向量 XOR 进来
                    b = bases[dim][i]
                    acc = [a ^ x for a, x in zip(acc, b)]
                v >>= 1
                i += 1
        return tuple(acc)
    return L

# 一个 4x4 张量，4 个 warp x 4 个线程。只需指定 4 个基向量：
#   L(t=1,w=0), L(t=2,w=0), L(t=0,w=1), L(t=0,w=2)
row_major = build({"t": [(0, 1), (0, 2)],       # 线程沿列走
                   "w": [(1, 0), (2, 0)]})      # warp 沿行走
col_major = build({"t": [(1, 0), (2, 0)],       # 线程沿行走 —— 只换了这两行
                   "w": [(0, 1), (0, 2)]})

def dump(name, L):
    print(f"\n【{name}】L(thread, warp) → (x, y)")
    print("        w=0     w=1     w=2     w=3")
    for t in range(4):
        cells = [f"{L(t=t, w=w)}" for w in range(4)]
        print(f"  t={t}  " + "  ".join(cells))

dump("row-major：线程沿列、warp 沿行", row_major)
dump("col-major：两组基向量对调", col_major)

# layout 转换的代价：有多少元素需要跨线程搬动？
print("\n" + "=" * 62)
print("从 row-major 换到 col-major 要付多少代价？")
moved = same = 0
for t in range(4):
    for w in range(4):
        if row_major(t=t, w=w) == col_major(t=t, w=w):
            same += 1
        else:
            moved += 1
print(f"  16 个 (thread, warp) 位置里，{same} 个拿到的还是同一个元素，"
      f"{moved} 个变了")
print(f"  → 这 {moved} 个就是 ttg.convert_layout 要生成的数据搬运")
print("  搬运走 shared memory 或 warp shuffle，是 Triton 里最贵的操作之一。")
print("\n所以 Triton 的优化核心是：**尽量让相邻算子的 layout 一致**，")
print("好让 convert_layout 能被消掉。它的 canonicalizer 和一大批 pass")
print("干的就是这件事 —— layout 不是元数据，是性能本身。")
```

运行结果：

```

【row-major：线程沿列、warp 沿行】L(thread, warp) → (x, y)
        w=0     w=1     w=2     w=3
  t=0  (0, 0)  (1, 0)  (2, 0)  (3, 0)
  t=1  (0, 1)  (1, 1)  (2, 1)  (3, 1)
  t=2  (0, 2)  (1, 2)  (2, 2)  (3, 2)
  t=3  (0, 3)  (1, 3)  (2, 3)  (3, 3)

【col-major：两组基向量对调】L(thread, warp) → (x, y)
        w=0     w=1     w=2     w=3
  t=0  (0, 0)  (0, 1)  (0, 2)  (0, 3)
  t=1  (1, 0)  (1, 1)  (1, 2)  (1, 3)
  t=2  (2, 0)  (2, 1)  (2, 2)  (2, 3)
  t=3  (3, 0)  (3, 1)  (3, 2)  (3, 3)

==============================================================
从 row-major 换到 col-major 要付多少代价？
  16 个 (thread, warp) 位置里，4 个拿到的还是同一个元素，12 个变了
  → 这 12 个就是 ttg.convert_layout 要生成的数据搬运
  搬运走 shared memory 或 warp shuffle，是 Triton 里最贵的操作之一。

所以 Triton 的优化核心是：**尽量让相邻算子的 layout 一致**，
好让 convert_layout 能被消掉。它的 canonicalizer 和一大批 pass
干的就是这件事 —— layout 不是元数据，是性能本身。
```

两处值得看：

**row-major 和 col-major 的定义只差两行**——把线程的基向量和 warp 的基向量对调。layout 的表达力就来自这里：改几个基向量就是完全不同的数据分布。

**16 个位置里 12 个变了。** 这 12 个就是 `ttg.convert_layout` 要生成的数据搬运。**代价是算得出来的**，所以编译器能据此决策——这正是"把成本显式化"的意义。

## 从 Triton 身上该学什么

这一章最该带走的不是 Triton 的细节，是三条可迁移的设计经验。

**一、把性能关键的信息放进类型。** layout 影响访存合并和能否用 tensor core——都是数量级级别的影响。放进类型意味着：verifier 能检查、pattern 能匹配、转换代价能显式表达。反过来看我们的 pix：第 9 章把卷积核尺寸放进 `!pix.kernel<R x C>`，第 21 章算 halo 时直接受益——**同一个道理，小得多的规模。**

**二、把隐性成本做成一个 op。** `convert_layout` 语义上什么都不做（`Pure`、形状和元素类型都不变），存在的唯一理由是**让代价可见**。这是一个很值得借鉴的手法：如果你的下降过程中有"某些情况下要付一笔额外开销"，**做成 op 比藏在 pattern 里好**——藏起来的成本没法优化。

**三、找一个能统一特例的数学结构。** 从"十几种 encoding 两两转换"到"都转成 linear layout 再做线性代数"，是一次抽象层级的提升。判断这类机会的标志是：**特例数量在平方级增长，而它们看起来都在做同一类事。**

<div class="warn">
<strong>Triton 也有它的代价，别只看优点</strong>
<p><strong>layout 的选择很难。</strong>编译器要在"访存合并友好"和"tensor core 要求"之间权衡，而这两者经常冲突（这正是 <code>convert_layout</code> 消不掉的原因）。Triton 有一批启发式 pass 在做这件事，但调不好性能可能差几倍——<strong>它把决策从程序员转给了编译器，但没有消灭决策的难度。</strong></p>
<p><strong>编译时间。</strong><code>TritonGPU/Transforms/</code> 下那批 pass（<code>Pipeline</code>、<code>ScheduleLoops</code>、<code>AutomaticWarpSpecialization</code>、<code>PartitionLoops</code>……）不便宜。JIT 场景里首次编译的延迟是真实痛点。</p>
<p><strong>抽象泄漏。</strong><code>ttng</code>（TritonNvidiaGPU）的存在本身说明问题：TMA、TMEM 这些 NVIDIA 专有特性没法塞进通用的 <code>ttg</code>。<strong>"一套 IR 覆盖所有厂商"在最前沿的硬件特性上做不到</strong>——这不是 Triton 的失误，是现实。第 28 章会把这类诚实的观察收拢起来。</p>
</div>

## 动手：读一段真实的 ttg IR

Triton 能把中间 IR 打出来。装好 Triton 之后：

```bash
# 把各阶段的 IR 都 dump 出来
MLIR_ENABLE_DUMP=1 python your_kernel.py 2>&1 | head -200
# 或者只看 ttgir
TRITON_ALWAYS_COMPILE=1 python -c "
import triton, triton.language as tl
@triton.jit
def add(x_ptr, y_ptr, out_ptr, n, BLOCK: tl.constexpr):
    pid = tl.program_id(0)
    offs = pid * BLOCK + tl.arange(0, BLOCK)
    m = offs < n
    tl.store(out_ptr + offs, tl.load(x_ptr + offs, mask=m) + tl.load(y_ptr + offs, mask=m), mask=m)
print(add.cache_key)
"
```

拿到 `.ttgir` 之后做三件事：**① 数一下有几个 `ttg.convert_layout`**；**② 找出每个张量类型上的 encoding，看相邻算子是否一致**；**③ 把 `BLOCK` 改成不同的值，看 layout 参数怎么变。**

（对比第 23 章那个实验——我们在 CPU 上改 tile 大小看 mask 数量，这里在 GPU 上改 BLOCK 看 layout。**同一种方法论：改一个参数，数一个可观测量。**）

**再改一处**：写一个带 `tl.dot` 的 kernel，对比它的 ttgir 和纯逐点 kernel 的。**`tl.dot` 那个会出现 `#ttg.nvidia_mma` 之类的 encoding，而且前后很可能各有一个 `convert_layout`**——因为 MMA 要求的布局和访存友好的布局不一致。这就是前面说的那个"消不掉的冲突"，亲眼看一次比读十遍解释有用。

---

**这一章的要点**

- Triton 的**分层很常规**：`tt`（与硬件无关）→ `ttg`（带 layout 的 GPU 表示）→ LLVM → PTX，外加 `ttng` 装 NVIDIA 专有特性。形状和我们的 pix → linalg → LLVM 是同一类。
- **原创在于 `tt` → `ttg` 这一步加的是 layout，而不是迭代空间。** 我们那一步（第 20 章）加的是 indexing map；Triton 加的是"数据在线程间怎么分布"。
- **layout 是类型上的 encoding 属性**。`#ttg.blocked_layout<{sizePerThread, threadsPerWarp, blocked}>` 三个参数分别说"一个线程几个元素、warp 内怎么排、CTA 内 warp 怎么排"。
- **为什么值得进类型**：它决定①访存能否合并（排错了带宽掉到 1/32）②能否直接喂 tensor core（MMA 对布局有硬性要求，这是 `NvidiaMmaEncodingAttr` 存在的理由）。前 25 章我们的 pix 从没表达过这件事——**CPU 上不需要，GPU 上是一等信息**。
- **`ttg.convert_layout` 语义上什么都不做**（`Pure`，形状和元素类型都不变），存在的唯一理由是**让代价可见**。有 verifier 也有 canonicalizer——能查、能优化。
- **Triton 优化的核心命题就是消掉 `convert_layout`**：让相邻算子的 layout 一致。对比手写 CUDA——数据分布在程序员脑子里，改一处可能破坏另一处。**Triton 的优势不是"生成的代码更聪明"，是"这类决策能被系统性优化"。**
- **linear layout 是一次漂亮的抽象提升**：所有 encoding 都是一个"硬件位置 → 逻辑下标"的函数；**只需指定 2 的幂次处的基向量，其余靠 XOR 推出**。N² 份两两转换代码变成通用线性代数。限制（只能表达 2 的幂 + XOR）恰好和 GPU 硬件的实际形状对齐——**选对抽象的标志**。
- 三条可迁移的经验：**把性能关键信息放进类型**（pix 把核尺寸放进 `!pix.kernel<R x C>` 是同一个道理）；**把隐性成本做成一个 op**（藏在 pattern 里的成本没法优化）；**找能统一特例的数学结构**（信号是特例平方级增长且都在做同一类事）。
- 代价也要看清：**layout 选择本身很难**（合并友好与 MMA 要求经常冲突，这正是 `convert_layout` 消不掉的原因）；**编译时间不便宜**；**`ttng` 的存在说明"一套 IR 覆盖所有厂商"在最前沿特性上做不到**。
