# 第 21 章 tiling 与 fusion：把 pix 的逐点与 stencil 变成分块循环

## 这一章想让你带走什么

<div class="goal-box">
<p>第 20 章把 pix 降到了 <code>linalg</code>，并证明了"降过去才能 tile"。这一章真正去 tile，而且把三件事做实：</p>
<p><strong>一、串行与并行两种 tiling。</strong><code>tile_using_for</code> 出 <code>scf.for</code>，<code>tile_using_forall</code> 出 <code>scf.forall</code> —— 后者带 <code>shared_outs</code> 和 <code>tensor.parallel_insert_slice</code>，是通往 GPU（第 25 章）的形式。</p>
<p><strong>二、producer-consumer 融合。</strong>两步逐点运算 <code>add</code> 然后 <code>scale</code>，融合之后<strong>中间那张整图彻底消失</strong>——`scale` 直接吃 `add` 在同一个 tile 里产出的结果。这是第四部分最有价值的一次变换，而我们一行融合逻辑都不用写。</p>
<p><strong>三、halo。</strong>stencil 运算分块时，输出 tile 是 4×4，输入 tile 必须是 6×6——多出的两圈就是 halo。这一章会给 <code>pix.convolve</code> 写下降（一个 4 维迭代空间的 <code>linalg.generic</code>），然后 tile 它，看那个 <code>6×6</code> 是<strong>怎么被自动算出来的</strong>。halo 是手写 tiling 时最容易错的地方；这里它是 indexing map 的一个推论。</p>
</div>

## tiling 的两种形式

第 18 章已经见过 `tile_using_for`：它生成嵌套的 `scf.for`，循环之间串行，用 `iter_args` 串起累积的张量。

并行版本换一个 op：

```mlir-norun
%tiled, %loop = transform.structured.tile_using_forall %g tile_sizes [4, 4]
  : (!transform.any_op) -> (!transform.any_op, !transform.any_op)
```

跑一遍（输入是 `pix.add` 降下来的 generic）：

```bash
pix-opt fa21.mlir --pix-to-linalg --transform-interpreter --canonicalize
```

运行结果（函数部分）：

```
  func.func @parallel_tile(%arg0: tensor<8x8xf32>, %arg1: tensor<8x8xf32>) -> tensor<8x8xf32> {
    %0 = tensor.empty() : tensor<8x8xf32>
    %1 = scf.forall (%arg2, %arg3) in (2, 2) shared_outs(%arg4 = %0) -> (tensor<8x8xf32>) {
      %2 = affine.apply #map(%arg2)
      %3 = affine.apply #map(%arg3)
      %extracted_slice = tensor.extract_slice %arg0[%2, %3] [4, 4] [1, 1] : tensor<8x8xf32> to tensor<4x4xf32>
      %extracted_slice_0 = tensor.extract_slice %arg1[%2, %3] [4, 4] [1, 1] : tensor<8x8xf32> to tensor<4x4xf32>
      %extracted_slice_1 = tensor.extract_slice %arg4[%2, %3] [4, 4] [1, 1] : tensor<8x8xf32> to tensor<4x4xf32>
      %4 = linalg.generic {indexing_maps = [#map1, #map1, #map1], iterator_types = ["parallel", "parallel"]} ins(%extracted_slice, %extracted_slice_0 : tensor<4x4xf32>, tensor<4x4xf32>) outs(%extracted_slice_1 : tensor<4x4xf32>) {
      ^bb0(%in: f32, %in_2: f32, %out: f32):
        %5 = arith.addf %in, %in_2 : f32
        linalg.yield %5 : f32
      } -> tensor<4x4xf32>
      scf.forall.in_parallel {
        tensor.parallel_insert_slice %4 into %arg4[%2, %3] [4, 4] [1, 1] : tensor<4x4xf32> into tensor<8x8xf32>
      }
    }
    return %1 : tensor<8x8xf32>
  }
```

和 `scf.for` 版本比，三处不同，每处都有含义：

| | `scf.for` 版 | `scf.forall` 版 |
| --- | --- | --- |
| 迭代空间 | `%c0 to %c8 step %c4`（**元素坐标**） | `in (2, 2)`（**tile 编号**），偏移用 `affine.apply` 算 |
| 结果怎么传 | `iter_args` 串行累积 | `shared_outs`：所有迭代共享同一个目标 |
| 怎么写回 | `tensor.insert_slice` + `scf.yield` | `scf.forall.in_parallel { tensor.parallel_insert_slice }` |

`in (2, 2)` 那个写法值得注意：**`scf.forall` 的归纳变量是 tile 的编号，不是元素下标**。这让"把每个 tile 映射到一个 GPU block"变成一件自然的事——第 25 章会用到。

`tensor.parallel_insert_slice` 是它的关键：它声明"这些写入互不重叠"，于是并行是安全的。如果 tile 之间真的有重叠写，verifier 拦不住你，但结果是错的——**这个保证由 tiling 的正确性负责，不由 IR 检查**。

<div class="note">
<strong>什么时候用哪个</strong>
<p>规则很简单：<strong>被切的维度全是 <code>parallel</code> 就能用 <code>forall</code></strong>。归约维不能这么切——多个迭代要累加到同一个位置，`parallel_insert_slice` 的"互不重叠"假设就破了。真实管线里常见的做法是：并行维用 <code>forall</code> 切（映射到线程/块），归约维用 <code>for</code> 切（在每个线程内串行累加）。</p>
</div>

## 融合：让中间结果不落地

这是第四部分最有价值的一次变换。

考虑两步逐点运算：`%s = pix.add %a, %b` 然后 `%m = pix.scale %s, %f`。降到 linalg 之后是两个 `linalg.generic`，各自跑一遍 8×8 的迭代空间。**中间那个 `%s` 是一整张 8×8 的图**——要分配、要写满、再读一遍。

融合的目标：把它们合成**一个**循环嵌套，中间结果只在一个 tile 内存在。

```mlir-norun
%prod, %cons = transform.split_handle %gs
  : (!transform.any_op) -> (!transform.any_op, !transform.any_op)
%fused, %loops:2 = transform.structured.fuse %cons tile_sizes [4, 4]
  : (!transform.any_op) -> (!transform.any_op, !transform.any_op, !transform.any_op)
```

读法很重要：**`fuse` 的对象是消费者。** 它先 tile 消费者，然后把生产者"拉进"每个 tile。这个方向不是随意的——见下面那个 keypoint。

```bash
pix-opt f21.mlir --pix-to-linalg --transform-interpreter --canonicalize --cse
```

运行结果：

```
  func.func @two_steps(%arg0: tensor<8x8xf32>, %arg1: tensor<8x8xf32>, %arg2: f32) -> tensor<8x8xf32> {
    %c4 = arith.constant 4 : index
    %c8 = arith.constant 8 : index
    %c0 = arith.constant 0 : index
    %0 = tensor.empty() : tensor<8x8xf32>
    %1 = scf.for %arg3 = %c0 to %c8 step %c4 iter_args(%arg4 = %0) -> (tensor<8x8xf32>) {
      %2 = scf.for %arg5 = %c0 to %c8 step %c4 iter_args(%arg6 = %arg4) -> (tensor<8x8xf32>) {
        %extracted_slice = tensor.extract_slice %arg0[%arg3, %arg5] [4, 4] [1, 1] : tensor<8x8xf32> to tensor<4x4xf32>
        %extracted_slice_0 = tensor.extract_slice %arg1[%arg3, %arg5] [4, 4] [1, 1] : tensor<8x8xf32> to tensor<4x4xf32>
        %extracted_slice_1 = tensor.extract_slice %0[%arg3, %arg5] [4, 4] [1, 1] : tensor<8x8xf32> to tensor<4x4xf32>
        %3 = linalg.generic {indexing_maps = [#map, #map, #map], iterator_types = ["parallel", "parallel"]} ins(%extracted_slice, %extracted_slice_0 : tensor<4x4xf32>, tensor<4x4xf32>) outs(%extracted_slice_1 : tensor<4x4xf32>) {
        ^bb0(%in: f32, %in_3: f32, %out: f32):
          %5 = arith.addf %in, %in_3 : f32
          linalg.yield %5 : f32
        } -> tensor<4x4xf32>
        %extracted_slice_2 = tensor.extract_slice %arg6[%arg3, %arg5] [4, 4] [1, 1] : tensor<8x8xf32> to tensor<4x4xf32>
        %4 = linalg.generic {indexing_maps = [#map, #map], iterator_types = ["parallel", "parallel"]} ins(%3 : tensor<4x4xf32>) outs(%extracted_slice_2 : tensor<4x4xf32>) {
        ^bb0(%in: f32, %out: f32):
          %5 = arith.mulf %in, %arg2 : f32
          linalg.yield %5 : f32
        } -> tensor<4x4xf32>
        %inserted_slice = tensor.insert_slice %4 into %arg6[%arg3, %arg5] [4, 4] [1, 1] : tensor<4x4xf32> into tensor<8x8xf32>
        scf.yield %inserted_slice : tensor<8x8xf32>
      }
      scf.yield %2 : tensor<8x8xf32>
    }
    return %1 : tensor<8x8xf32>
  }
```

三件事值得逐一确认：

**只有一对 `scf.for`。** 两个 generic 现在住在同一个循环嵌套里。

**`%4` 的 `ins(%3 : tensor<4x4xf32>)`** —— 消费者直接吃生产者在**这个 tile 内**产出的 4×4 结果。

**那张 8×8 的中间图不见了。** 原来的 `%1`（整图 add）被 canonicalize 清掉了，因为再没人用它。

<div class="keypoint">
<strong>为什么融合是"从消费者往回拉"，而不是"从生产者往前推"</strong>
<p>因为<strong>只有消费者知道自己需要输入的哪一块</strong>。tile 消费者时，框架用它的 indexing map 算出"这个输出 tile 需要输入的哪个切片"，然后要求生产者只生产那一块。反过来——先 tile 生产者，再问"谁用得上这块"——需要反向求解 map，一般无解。</p>
<p>这也解释了 <code>transform.structured.fuse</code> 的签名为什么把 tile 大小和融合写在一起：<strong>融合的边界就是 tile 的边界</strong>，两件事本质上是一件事。</p>
</div>

<div class="warn">
<strong><code>transform.structured.fuse</code> 的语法是 <code>tile_sizes [4, 4]</code>，不是属性字典</strong>
<p>我第一次写成 <code>transform.structured.fuse %cons {tile_sizes = [4, 4]}</code>，得到一句相当误导的报错：</p>
<p><code>error: 'transform.structured.fuse' op expects 0 loop results</code></p>
<p>它不是在说 loop 结果数写错了，而是那个属性字典没被当成 <code>tile_sizes</code>（真正的 <code>tile_sizes</code> 是<strong>操作数</strong>加一个 <code>static_tile_sizes</code> 属性，由自定义 assembly 格式拼起来），于是框架认为"没有 tile 大小 → 不产生循环 → 你却声明了两个 loop 结果"。<strong>transform 方言的 op 大量使用自定义 assembly 格式，别照属性字典的直觉写</strong>——去 <code>mlir/test/Dialect/Linalg/transform-op-*.mlir</code> 里找一个真实用例抄，比读 ODS 快。</p>
</div>

## halo：stencil 分块的那两圈

逐点运算的 tiling 很干净：输出 tile 4×4，输入 tile 也是 4×4。**stencil 不是这样**——算一个输出点要读它周围一圈，所以输入 tile 必须更大。多出来的那部分叫 **halo**（也叫 ghost cells）。

手写 tiling 时 halo 是最容易错的地方：差一圈就是越界或算错边界。而在 linalg 里，它是 indexing map 的一个**推论**。

先给 `pix.convolve` 写下降。关键就是那三个 map：

```cpp-norun
// 四个迭代维：d0/d1 走输出的行列，d2/d3 走卷积核窗口
auto d0 = getAffineDimExpr(0, ctx), d1 = getAffineDimExpr(1, ctx);
auto d2 = getAffineDimExpr(2, ctx), d3 = getAffineDimExpr(3, ctx);
SmallVector<AffineMap> maps{
    AffineMap::get(4, 0, {d0 + d2, d1 + d3}, ctx), // 输入：**带偏移** → halo 的来源
    AffineMap::get(4, 0, {d2, d3}, ctx),           // 权重
    AffineMap::get(4, 0, {d0, d1}, ctx)};          // 输出
SmallVector<utils::IteratorType> iters{
    utils::IteratorType::parallel, utils::IteratorType::parallel,
    utils::IteratorType::reduction, utils::IteratorType::reduction};
```

**输入的下标是 `d0 + d2`**：输出点 `(d0, d1)` 要读输入的 `(d0+d2, d1+d3)`，其中 `d2, d3` 扫过整个卷积核窗口。这一个表达式包含了 stencil 的全部访存信息。

`pix.convolve` 是 "same" 语义（输入输出同形），所以要先 pad 一圈半径：

```cpp-norun
// 卷积核的尺寸从**类型**里读——第 9 章把尺寸放进 !pix.kernel<R x C> 的回报
int64_t kr = kty.getRows(), kc = kty.getCols();
int64_t rr = kr / 2, rc = kc / 2;
auto pad = tensor::PadOp::create(rewriter, loc, padTy, adaptor.getImage(),
                                 SmallVector<int64_t>{rr, rc},
                                 SmallVector<int64_t>{rr, rc},
                                 ValueRange{}, ValueRange{});
```

第 9 章决定"把卷积核尺寸放进类型"时，理由是"第 21 章算 halo 时直接读类型就有了"。**现在兑现了**：`kty.getRows()` 一句话拿到，不必去分析权重数据。

降完是这样：

```mlir-lower
// RUN: pix-opt %s --pix-to-linalg
func.func @stencil(%img: tensor<8x8xf32>) -> tensor<8x8xf32> {
  %k = pix.kernel dense<[[0.0, 1.0, 0.0], [1.0, -4.0, 1.0], [0.0, 1.0, 0.0]]> : tensor<3x3xf32> -> !pix.kernel<3 x 3>
  %c = pix.convolve %img, %k : !pix.kernel<3 x 3>, tensor<8x8xf32>
  return %c : tensor<8x8xf32>
}
```

**输出切片 `[4, 4]`，输入切片 `[6, 6]`。** 那多出来的两圈就是 halo，而**没有任何一行代码是为 halo 写的**——框架从 `(d0+d2, d1+d3)` 这个 map 和 `d2, d3` 的范围（3×3 核）算出来的。

<div class="keypoint">
<strong>halo 大小 = 归约维的长度 − 1</strong>
<p>3×3 核 → 每边多 1 圈，输入 tile 比输出大 2；5×5 核 → 每边多 2 圈，大 4。这个关系直接来自 <code>d0 + d2</code>：<code>d0</code> 走 tile 的 4 个值，<code>d2</code> 走核的 3 个值，合起来覆盖 <code>4 + 3 - 1 = 6</code> 个输入下标。</p>
<p><strong>把核尺寸放进类型，这一步就是查表；放进数据，就得做分析。</strong>第 9 章那个设计决定在这里收到了回报——这也是"什么该做成类型"的一个具体判据：<strong>后续变换需要在编译期知道的信息，就该在类型里。</strong></p>
</div>

## 把 halo 与融合的收益算出来

两件事都能从 indexing map 直接推。下面这个模型算 halo（结果和真 `mlir-opt` 的 `[6, 6]` 对得上），并量化融合省下多少：

```python
# tiling 的两件事都能从 indexing map 算出来：halo 有多大、融合省多少内存。
# 这个模型把两者都量化，数字和真 mlir-opt 的输出对得上。

def slice_range(map_exprs, tile_lo, tile_hi, red_extents):
    """给定一个 tile（并行维的范围）和归约维的全长，算出某个操作数要取的切片。
       map_exprs 里每项是 (并行维下标 or None, 归约维下标 or None)，
       表示这一维的下标 = 那个并行维 + 那个归约维。"""
    lo, hi = [], []
    for par, red in map_exprs:
        a = tile_lo[par] if par is not None else 0
        b = tile_hi[par] if par is not None else 1
        if red is not None:
            b += red_extents[red] - 1        # 邻域把上界往外推
        lo.append(a); hi.append(b)
    return [(l, h) for l, h in zip(lo, hi)]

def show(title, maps, tile, red_extents):
    print(f"\n【{title}】tile = {tile}，归约维长度 = {red_extents}")
    lo = [0, 0]; hi = list(tile)
    for who, m in maps.items():
        rng = slice_range(m, lo, hi, red_extents)
        size = [h - l for l, h in rng]
        extra = ""
        if who == "输入" and size != list(tile):
            halo = [(s - t) // 2 for s, t in zip(size, tile)]
            extra = f"   ← 比输出大 {[s-t for s,t in zip(size,tile)]}，每边 halo = {halo}"
        print(f"    {who:4} 切片 {['%d:%d' % r for r in rng]} 尺寸 {size}{extra}")

# 逐点：输入下标不含归约维 → 切片和 tile 一样大
show("逐点 add：无 halo", {"输入": [(0, None), (1, None)], "输出": [(0, None), (1, None)]},
     (4, 4), [])
# stencil：输入下标是 d0+d2 → 切片被推大
show("stencil convolve（3x3 核）：有 halo",
     {"输入": [(0, 0), (1, 1)], "输出": [(0, None), (1, None)]}, (4, 4), [3, 3])
show("同一个 stencil，换 5x5 核", 
     {"输入": [(0, 0), (1, 1)], "输出": [(0, None), (1, None)]}, (4, 4), [5, 5])

# 融合省多少：两步逐点运算，8x8 图
print("\n" + "=" * 60)
N, T = 8, 4
print(f"融合的收益（{N}x{N} 图，两步逐点运算，tile {T}x{T}）：")
print(f"  不融合：中间结果要一整张图      = {N*N} 个元素的临时存储")
print(f"  融合后：中间结果只在一个 tile 内 = {T*T} 个元素")
print(f"  省下 {N*N - T*T} 个元素，比例 {(1 - T*T/(N*N))*100:.0f}%")
print(f"  更关键的是**局部性**：{T*T} 个元素能待在 cache 里，{N*N} 个未必。")
print("  这就是为什么融合常常比单纯 tile 更有效 —— 它消掉的是内存往返，不只是空间。")
```

运行结果：

```

【逐点 add：无 halo】tile = (4, 4)，归约维长度 = []
    输入   切片 ['0:4', '0:4'] 尺寸 [4, 4]
    输出   切片 ['0:4', '0:4'] 尺寸 [4, 4]

【stencil convolve（3x3 核）：有 halo】tile = (4, 4)，归约维长度 = [3, 3]
    输入   切片 ['0:6', '0:6'] 尺寸 [6, 6]   ← 比输出大 [2, 2]，每边 halo = [1, 1]
    输出   切片 ['0:4', '0:4'] 尺寸 [4, 4]

【同一个 stencil，换 5x5 核】tile = (4, 4)，归约维长度 = [5, 5]
    输入   切片 ['0:8', '0:8'] 尺寸 [8, 8]   ← 比输出大 [4, 4]，每边 halo = [2, 2]
    输出   切片 ['0:4', '0:4'] 尺寸 [4, 4]

============================================================
融合的收益（8x8 图，两步逐点运算，tile 4x4）：
  不融合：中间结果要一整张图      = 64 个元素的临时存储
  融合后：中间结果只在一个 tile 内 = 16 个元素
  省下 48 个元素，比例 75%
  更关键的是**局部性**：16 个元素能待在 cache 里，64 个未必。
  这就是为什么融合常常比单纯 tile 更有效 —— 它消掉的是内存往返，不只是空间。
```

注意第三组：**同一个 stencil，把核换成 5×5，halo 自动变成每边 2 圈**。这就是"halo 是 map 的推论"的意思——换核不用改任何 tiling 代码。

最后那段关于融合的数字要看清重点：省 75% 的临时存储是次要的，**关键是局部性**。16 个元素能待在 cache 里，64 个未必。融合消掉的是**内存往返**，不只是空间——这也是为什么它常常比单纯 tile 更有效。

## 动手：改 tile 大小，观察 halo 的比例

halo 是**开销**：tile 越小，halo 占的比例越高。拿 3×3 核算一下：

| tile | 输入 tile | 多读的元素 | 冗余比例 |
| --- | --- | --- | --- |
| 2×2 | 4×4 | 16 − 4 = 12 | 300% |
| 4×4 | 6×6 | 36 − 16 = 20 | 125% |
| 8×8 | 10×10 | 100 − 64 = 36 | 56% |

把 `tile_sizes` 依次改成 `[2, 2, 0, 0]`、`[8, 8, 0, 0]`，跑

```bash
pix-opt halo21.mlir --pix-to-linalg --transform-interpreter --canonicalize | grep extract_slice
```

自己确认那张表。**这就是 stencil 的 tile 大小选择为什么和逐点运算完全不同**——逐点运算 tile 越小越贴合 cache，stencil 则要在局部性和 halo 冗余之间折中。

**再改一处**：把 `transform.structured.fuse` 换成 `tile_using_forall` + `transform.structured.fuse_into_containing_op`，看能不能得到并行版的融合。（提示：第 18 章那条 handle 失效的规矩在这里会反复咬你——每一步都要用新 handle。）

---

**这一章的要点**

- **两种 tiling 形式**：`tile_using_for` → `scf.for`（迭代空间是元素坐标，`iter_args` 串行累积）；`tile_using_forall` → `scf.forall`（迭代空间是 **tile 编号**，`shared_outs` + `tensor.parallel_insert_slice`）。**被切的维全是 `parallel` 才能用 `forall`**。
- `scf.forall` 的归纳变量是 tile 编号而不是元素下标，这让"每个 tile 一个 GPU block"变得自然——第 25 章的形式。
- **融合是"从消费者往回拉"**，因为只有消费者知道自己需要输入的哪一块（正向用 map 算切片很容易，反向求解一般无解）。所以 `transform.structured.fuse` 把 tile 大小和融合写在一起：**融合的边界就是 tile 的边界**。
- 融合的收益**主要不是省空间，是省内存往返**。中间结果从一整张图缩到一个 tile，于是能待在 cache 里。实测：中间那张 8×8 图在融合后被 DCE 彻底清掉。
- **halo = 归约维长度 − 1**。3×3 核 → 输入 tile 比输出大 2（每边 1 圈）；5×5 → 大 4。这个关系直接来自输入 map 里的 `d0 + d2`，**没有一行代码是为 halo 写的**，换核尺寸也不用改 tiling 代码。
- stencil 的下降关键就是那个 `(d0+d2, d1+d3)`：四维迭代空间，前两维 `parallel` 走输出，后两维 `reduction` 走核窗口。"same" 语义要先 `tensor.pad` 一圈半径。
- **把核尺寸放进类型的回报在这里兑现**：`kty.getRows()` 一句话，不必分析权重数据。判据可以记住——**后续变换需要在编译期知道的信息，就该在类型里**。
- halo 是**开销**，所以 stencil 的 tile 大小选择和逐点运算完全不同：逐点越小越贴 cache，stencil 要在局部性与 halo 冗余之间折中（2×2 tile 的冗余高达 300%）。
- **transform 方言的 op 大量用自定义 assembly 格式**，别照属性字典的直觉写。`fuse %op {tile_sizes = [4,4]}` 会得到一句毫不相干的 `expects 0 loop results`。去 `mlir/test/Dialect/Linalg/transform-op-*.mlir` 抄一个真实用例最快。

**pix 进度**：`pix-to-linalg` 补上 `pix.convolve` 的下降（4 维 stencil + `tensor.pad`），于是 pix 的三类计算（逐点、归约、邻域）全部有了 linalg 形式。新增 `tile_fuse.mlir`：一段调度同时驱动融合与 halo 两个实验，断言"只有一对循环"和"输入切片 6×6 / 输出切片 4×4"。`check-pix` 从 17 涨到 18 个文件。

下一章是第四部分最难的一关：**bufferization**，从 tensor 的值语义走到 memref 的内存语义。难点不在 API，在于这一步要回答三个此前一直被回避的问题——谁拥有这块内存、什么时候能就地更新、别名怎么判。那一章也会解释你在本章输出里看到的那些 `tensor.empty` 最终变成了什么。
