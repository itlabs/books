# 第 27 章 IREE 与 flang：端到端 AI 编译栈与 Fortran 前端的两种用法

## 这一章想让你带走什么

<div class="goal-box">
<p>上一章看的是 Triton 在 MLIR 上<strong>造了什么新东西</strong>。这一章换一个问题，一个你真要做项目时第一天就会撞上的问题：</p>
<p><strong>我该造几层方言？</strong></p>
<p>这一章把两个都很成功、但答案完全相反的项目摆在一起：<strong>IREE</strong> 自造了九个方言，一路管到自带的运行时；<strong>flang</strong> 只造了两个（<code>fir</code> 和 <code>hlfir</code>），而且连上游的 <code>linalg</code>、<code>tensor</code> 都一个没用。</p>
<p>如果"层数越多越好"或者"越少越好"里有一个是对的，那这两个项目里应该有一个是失败的。但它们都不是——flang 已经是 LLVM 的正式 Fortran 前端，IREE 是工业界端到端部署栈里被抄得最多的设计。</p>
<p>所以真正要提炼的是：<strong>层数不是风格问题，是"有多少个独立决策要做"的结果。</strong>这一章把这句话展开成四个可以逐条对答案的问题，并且——这是最舒服的一点——<strong>flang 自己的设计文档把加一层的理由写下来了</strong>，我们不用猜。</p>
<p>所有方言名、op 名、pass 名、设计动机都锚在两处真实源码：<code>iree-org/iree</code> 的 <code>6ef606b</code>（2026-09-19），以及 LLVM <strong>23.1.2</strong> 的 <code>flang/</code>。引用的设计文档原文出自 <code>flang/docs/HighLevelFIR.md</code>。</p>
</div>

## 先把差距摆出来

两个项目的自造方言清单，都是从源码里数出来的。

IREE 的方言目录（`compiler/src/iree/compiler/Dialect/`）：

```
Encoding  Flow  HAL  LinalgExt  Stream  TensorExt  Util  VM  VMVX
```

九个。flang 的（`flang/include/flang/Optimizer/`）：

```
Dialect/   -> fir
HLFIR/     -> hlfir
```

两个。这不是我按某种标准归类出来的数字，是 `let name` 的数量：

```
$ grep -rhoE 'let name = "[a-z]+"' \
      flang/include/flang/Optimizer/Dialect/FIRDialect.td \
      flang/include/flang/Optimizer/HLFIR/HLFIROpBase.td | sort -u
let name = "fir"
let name = "hlfir"
```

比数量更能说明问题的是**复用面**。前面二十几章我们一直在讲"降到 `linalg` 就白拿整条链"（第 20 章），那 flang 用了多少上游方言？答案在 `FIRDialect.td` 里：

```tablegen
let dependentDialects = [
  // Arith dialect provides FastMathFlagsAttr
  // supported by some FIR operations.
  "mlir::arith::ArithDialect",
  // TBAA Tag types
  "mlir::LLVM::LLVMDialect"
];
```

两个，而且理由都极小：一个是为了借 `FastMathFlagsAttr` 这个属性，一个是为了借 TBAA 的类型。加上 CodeGen 那一步用到的（`grep` 出来只有 `arith`、`cf`、`func`、`LLVM` 四个），flang 的上游方言面**就是 MLIR 最底下那四个最基础的方言**。

`linalg`？`tensor`？一个都没有：

```
$ grep -rl "linalg" flang/include/flang/Optimizer/
（无输出）
```

这件事第一次看到是会愣一下的。Fortran 是**为数组计算而生**的语言，`linalg` 是 MLIR 里**专门表示数组计算**的方言，两者看起来天造地设——结果 flang 一行都没用。

这就是这一章要解释的东西。

## IREE：每一层对应一个"必须有人拍板"的决策

IREE 的分层不用我总结，`Stream` 方言的 `description` 自己画了图：

```
+--------+    +----------+    +-------+
| flow.* | -> | stream.* | -> | hal.* |
+--------+    +----------+    +-------+
```

而且它把三层各管什么逐条写清了（以下是 `StreamBase.td` 里 `description` 的原文）：

- `flow` — "models tensor programs by separating work into dispatchable functions in order to isolate the main host program data flow and the dense tensor compute operations."
- `stream` — "models explicitly scheduled asynchronous programs by partitioning..."
- `hal` — "models a low-level hardware abstraction layer used to manage buffers and issue asynchronous work across a variety of device types. **The dialect is largely 1:1 with the IREE HAL C API.**"

把这三句翻成"每层引入了什么上一层表达不了的决策"：

| 层 | 新引入的决策 | 上一层为什么表达不了 |
| --- | --- | --- |
| `flow` | 哪些计算打包成一个可派发的函数、包之间怎么传数据 | `linalg` 只说"算什么"，没有"派发边界"这个概念 |
| `stream` | 放到哪个设备、哪些能并发、张量编码成什么设备资源 | `flow` 里还没有"设备"这个概念 |
| `hal` | 具体的 buffer / command buffer / executable | `stream` 是抽象调度，不绑定任何一家的 API |
| `vm` | 字节码、宿主侧胶水 | 前面都在描述计算，这一层描述"怎么被加载执行" |

最后一句里的 `hal` 那条特别值得停一下。`hal` 之所以存在，**不是因为它是一个更好的编译器抽象**——它的 `description` 直说了是跟 IREE 的 HAL C API 一比一对应的。也就是说：

> **`hal` 是运行时 ABI 照进 IR 里的影子。**

这一下就解释了 IREE 和 flang 的分歧从哪来。IREE **自带一个运行时**，所以它必须在 IR 里表达那个运行时的接口；flang 的"运行时接口"就是 LLVM IR 加几个 libc/Fortran runtime 调用，LLVM 已经帮它表达好了，所以它一层都不用造。

**要不要造 `hal` 这样的一层，取决于你下游交给谁。** 这不是品味问题。

### 一个容易漏掉的观察：分层不一定要新方言

`Stream` 的 `description` 接着写了它内部怎么走：

> "At entry `stream.tensor.*` ops are used to capture the source tensor encoding information (data type, shapes, etc) and then lowered into `stream.async.*` ops that model the asynchronous workloads on the opaque resources. The asynchronous operations are then partitioned, allocated, and scheduled for execution using the `stream.cmd.*` ops."

数一下：`stream.tensor.*` → `stream.async.*` → `stream.cmd.*`。**这是三层**，从"带形状的张量"到"不透明资源上的异步任务"到"具体命令"，转换的性质和 `flow`→`stream`→`hal` 那几步没有本质区别。

但它们**共用一个方言**，只用 op 名前缀区分。

这条很实用。你想给自己的编译器加一层，第一反应往往是"再开一个 dialect"，那意味着一套新的 `.td`、新的 `CMakeLists`、新的注册、新的 `dependentDialects`、新的类型转换。IREE 在自己项目里给出的对照答案是：**如果两层的类型系统基本一致、只是 op 的抽象层次不同，op 名前缀就够了。**

判断依据也很清楚：**新方言的真正成本在类型和属性**。`stream.tensor.*` 和 `stream.cmd.*` 用的是同一套 `!stream.resource` 类型，所以不值得分家；而 `flow` 用值语义 `tensor`、`hal` 用 `!hal.buffer_view`，类型系统整个换掉了，那就该分。

回头看我们的 pix：第 20 章 `pix` → `linalg` 是类型系统不变（都是 `tensor`）、抽象层次变了。按这个标准，如果 `linalg` 不存在，我们**本来可以**用 `pix.generic` 这样的 op 名在同一个方言里做那一步，而不必新开一个方言。我们之所以真的换了方言，理由不是分层，而是第 20 章反复说的那个：换到 `linalg` 能白拿 tiling、融合、bufferization 一整条上游链。

**为了分层而分方言，和为了复用而换方言，是两件不同的事。** 前者常常不必要，后者几乎总是值得。

### 另外五个方言是干什么的

前面只讲了 `flow`/`stream`/`hal`/`vm` 这条主链，剩下五个也数一下，因为它们代表另一类"为什么造方言"：

| 方言 | 性质 |
| --- | --- |
| `Util` | 跨层共用的基础设施（全局变量、列表、buffer 之类），不属于任何一层 |
| `LinalgExt` | **上游 `linalg` 的扩展**——上游表达不了的那些（比如某些 scan/sort/topk 类算子） |
| `Encoding` / `TensorExt` | 张量编码/布局相关的补充表达 |
| `VMVX` | `vm` 的一个具体后端（VM 上的向量扩展） |

`LinalgExt` 是很有代表性的一类：**你不是想另造一层，你是发现上游那一层缺了几个 op。** 这种情况下正确做法不是重写 `linalg`，而是在旁边加一个扩展方言，让两者在同一层混用。我们的 pix 如果将来发现 `linalg.generic` 表达不了某种图像算子（比如非规则的邻域采样），该走的也是这条路——**加一个 `pix_ext`，而不是把 `linalg` 那一层重做一遍。**

## flang：两层，而且第二层是后来才加的

flang 这边有个特别好的地方：**它加第二层的时候，把理由写成了文档。**

FIR 最初是唯一的一层。`flang/docs/HighLevelFIR.md` 开头交代了当时的状态：

> "The approach of FIR and lowering design so far was to start with the minimal set of IR operations that could allow implementing the core aspects of Fortran (like memory allocations, array addressing, runtime descriptors, and structured control flow operations). One notable aspect of the current FIR is that array and character operations are **buffered** (some storage is allocated for the result, and the storage is addressed to implement the operation)."

注意 "buffered" 这个词。FIR 是**内存语义**的：数组表达式一落到 FIR，结果就已经有一块存储了。用我们第 22 章的话说，FIR 相当于直接从前端跳到了 `memref` 那一侧，中间没有 `tensor` 那一段。

然后是症状：

> "While this proved functional so far, the code lowering expressions and assignments from the front-end representations (the `evaluate::Expr` and parser nodes) to FIR **has significantly grown in complexity** while it still lacks some F95 features around character array expressions or FORALL. This is mainly explained by the fact that **the representation level gap is big, and a lot is happening in lowering**."

这两句是这一章最值钱的引文。它给出的加层理由不是"分层更优雅"，而是一个**可观测的工程症状**：

> **降的那一步代码复杂到失控，而且开始装不下某些语言特性——说明跨度太大了。**

这个判断标准很好用，因为它是事后可验证的，不需要你在第一天就预见到全部结构。你先按最少的层数开工；等某个 lowering 的 `.cpp` 长到没人敢碰、里面开始出现"如果当前在 FORALL 上下文里就走另一条路"这种分支，那就是该加一层的信号。

对照我们自己的书：第 16 章 `pix` → `arith` 那条路径，和第 20 章 `pix` → `linalg`，差别正是这个。第 16 章那条最短，但它**在下降的那一步里把迭代空间丢了**，于是 tile 和融合都没法做。当时我在 `PixToLinalg.cpp` 开头写的是：

```
// 那条路最短，但**丢掉了迭代空间**：arith.addf 在 tensor 上是一个不透明的
// "整张图加整张图"，没人知道它由哪些循环组成，于是 tile 不了、融合不了。
```

和 flang 遇到的是同一类问题的两种表现：跨度太大时，要么信息丢了，要么复杂度全堆在那一步里。

### HLFIR 的三条原则

文档接着列了新设计的三条原则，逐条都能对到我们前面的章节：

> - Make expression lowering **context independent** and rather naive
> - **Do not materialize temporaries** while lowering to FIR
> - **Preserve Fortran semantics/information** for high-level optimizations

第一条"上下文无关"是说：不管这个表达式是在普通赋值里、数组赋值里，还是在 `FORALL` 里，降的方式**完全一样**。原来的 FIR 做不到，因为它必须当场决定临时存储怎么分配，而那件事是依赖上下文的。

第二条最直接：**不实体化临时量**。这一条我们的代码里正好有一个现成的例子。第 20 章的 `ScaleToLinalg` 处理 `pix.scale %img, %f`——`%f` 是个标量。天真的做法是先把 `%f` splat 成一整张 4×4 的图，再逐点相乘；`ScaleToLinalg` 没这么干：

```mlir
// RUN: pix-opt %s --pix-to-linalg
// flang 的三条原则之一："Do not materialize temporaries while lowering to FIR"。
// 第 20 章的 ScaleToLinalg 就是这么写的：标量 %f 不 splat 成整张图，
// 直接在 region 里引用。看输出里有没有那个 4x4 的临时张量。
func.func @scale(%img: tensor<4x4xf32>, %f: f32) -> tensor<4x4xf32> {
  %r = pix.scale %img, %f : tensor<4x4xf32>
  return %r : tensor<4x4xf32>
}
```

运行结果：

```
#map = affine_map<(d0, d1) -> (d0, d1)>
module {
  func.func @scale(%arg0: tensor<4x4xf32>, %arg1: f32) -> tensor<4x4xf32> {
    %0 = tensor.empty() : tensor<4x4xf32>
    %1 = linalg.generic {indexing_maps = [#map, #map], iterator_types = ["parallel", "parallel"]} ins(%arg0 : tensor<4x4xf32>) outs(%0 : tensor<4x4xf32>) {
    ^bb0(%in: f32, %out: f32):
      %2 = arith.mulf %in, %arg1 : f32
      linalg.yield %2 : f32
    } -> tensor<4x4xf32>
    return %1 : tensor<4x4xf32>
  }
}
```

`%arg1` 直接出现在 region 里（`arith.mulf %in, %arg1`），`ins` 只有一个操作数。没有 splat，没有多出来的 4×4 常量张量——`tensor.empty` 是 destination-passing style 要的目标（第 20 章讲过），不是标量的临时副本。

能这么写的前提是 `linalg.generic` 的 region **不是** `IsolatedFromAbove`（第 13 章那个 trait）。这不是巧合：**"值语义的高层表示" + "region 可以引用外面的值"，正是让"不实体化临时量"这条原则能落地的两个机制。** HLFIR 和 `linalg` 各自独立地要到了这两样东西。

第三条"保留 Fortran 语义供高层优化"——这条的回报在下一节。

### 加一层的回报：12 个 pass 里只有 4 个在做下降

HLFIR 这一层带来了什么？把它的 pass 全列出来最直观：

```
$ grep -hoE 'def [A-Za-z]+ : Pass' flang/include/flang/Optimizer/HLFIR/Passes.td
ConvertHLFIRtoFIR
BufferizeHLFIR
OptimizedBufferization
LowerHLFIRIntrinsics
LowerHLFIROrderedAssignments
SimplifyHLFIRIntrinsics
ExpressionSimplification
InlineElementals
SeparateAllocatableAssign
InlineHLFIRAssign
InlineHLFIRCopy
PropagateFortranVariableAttributes
```

十二个。其中只有 `ConvertHLFIRtoFIR`、`BufferizeHLFIR`、`LowerHLFIRIntrinsics`、`LowerHLFIROrderedAssignments` 是**往下降**；剩下八个全是**在 HLFIR 这一层做的优化**：简化表达式、内联 elemental、内联赋值与拷贝、传播 Fortran 变量属性……

**这八个 pass 就是加这一层的回报。** 它们在 FIR 上根本写不出来——一旦 buffer 已经分配好、下标已经算成地址，"这个数组表达式能不能就地算"这种问题就已经问不出来了。

这里还有一个 MLIR 老读者会立刻认出的东西：`BufferizeHLFIR`。HLFIR 的 `description` 是这么说的：

> "A bufferization pass transforms `hlfir.expr` values into FIR temporary in memory, and its translation pass to FIR translates high level operations..."

值语义的 `hlfir.expr` → 内存里的临时量。这就是第 22 章那件事——**One-Shot Bufferize 做的 `tensor` → `memref`，和 flang 做的 `hlfir.expr` → FIR 内存，是同一个模式的两个实例。** flang 没有用上游的 bufferization 基础设施（它的类型完全不同），但**问题的形状一模一样**：高层用值语义方便分析和优化，落地前用一个 pass 换成内存语义，那个 pass 的核心工作是决定"哪些地方能就地、哪些必须拷贝"。

`OptimizedBufferization` 这个名字也说明了同一件事：bufferization 的质量是性能问题，不是形式转换——第 22 章讲 in-place 分析和 `copy-before-write` 时是一样的结论。

### HLFIR 故意不完整

这一点单独拎出来，因为它和大多数人的直觉相反。HLFIR 的 `description`：

> "It is **not a complete implementation of Fortran**, for constructs and lower level operations, **FIR should be used directly**."

HLFIR 只覆盖**表达式和赋值**。`hlfir` 的 op 全集是：

```
hlfir.apply  hlfir.assign  hlfir.associate  hlfir.char_extremum
hlfir.copy_in  hlfir.copy_out  hlfir.declare  hlfir.designate
hlfir.destroy  hlfir.elemental  hlfir.elemental_addr  hlfir.elsewhere
hlfir.end_associate  hlfir.eval_in_mem  hlfir.expr  hlfir.forall
hlfir.forall_mask  hlfir.matmul_transpose  hlfir.region_assign
hlfir.shape_of  hlfir.where  hlfir.yield  hlfir.yield_element
```

二十几个，全部围绕"表达式、赋值、以及和它们纠缠的那几个 Fortran 构造（`FORALL`/`WHERE`/`ELSEWHERE`）"。其他一切——过程调用、I/O、模块、`COMMON`、派生类型的布局——**直接用 FIR，不经过 HLFIR**。

于是 HLFIR 和 FIR 在同一个函数里是**混着出现**的。这和我们前面讲的 `applyPartialConversion`（第 17 章）那种"部分转换"是同一个思路，但它是**设计层面**的部分：不是转换转不完，是这一层本来就只打算管一部分。

为什么这是对的？因为**加一层的成本是按 op 数量算的，收益是按"这一层能做的优化"算的**。表达式和赋值是 Fortran 里最需要高层优化的部分（也是原来 lowering 最复杂的部分），把这块提上来，那八个优化 pass 就能写；而给 I/O 语句造一个高层形式，收益接近零——没人要优化 `WRITE` 语句的迭代空间。

**"只在需要优化的地方加高层表示"**，这条对自己做方言的人非常实用。看到一个成功项目有九层，很容易以为自己也要把每个阶段都补齐；HLFIR 的反例说明：**层可以是局部的。**

## 为什么 flang 不用 linalg

现在回到开头那个愣住的地方。

我要先把话说准：**这是一个设计选择，不是一个"flang 做错了"的结论。** 能从源码和文档里确定的事实是这几条：

1. flang 的 IR 里没有 `linalg`、没有 `tensor`（`grep` 结果为空）。
2. `hlfir` 建模的是 **Fortran 自己的构造**：`hlfir.elemental`（逐元素表达式）、`hlfir.forall`、`hlfir.where`、`hlfir.designate`（Fortran 的数组/子串取址规则）。
3. HLFIR 的第三条原则明确是 "**Preserve Fortran semantics/information** for high-level optimizations"。

把三条连起来，flang 的取舍就清楚了。`hlfir.elemental` 和 `linalg.generic` 在**形状**上确实很像（都是"一个迭代空间 + region 里算一个元素"），但 `linalg.generic` 表达一个 Fortran 数组表达式时，会丢掉一批 Fortran 特有的东西：

- **descriptor 语义**：Fortran 的数组参数可能是 assumed-shape 的，形状、步长、下界都在运行时的 descriptor 里；`memref` 的 strided layout 能表达一部分，但 Fortran 还有可分配（`ALLOCATABLE`）、指针关联、`OPTIONAL` 这些状态。
- **下界不从 0 开始**：Fortran 数组可以声明成 `A(-3:5)`。这不是小事——它渗透到每一次取址。
- **字符类型与派生类型**：`hlfir.char_extremum` 这种 op 的存在说明字符数组表达式是一等公民；`linalg` 那一层不管这个。
- **语言级别名规则**：Fortran 的别名保证比 C 强得多（这正是 Fortran 在数值计算上快的一大原因），`flang/docs/AliasingAnalysisFIR.md` 专门讲这个。降到通用方言就得想办法把这些保证一路带下去。

而 flang 要的"高层优化"是什么？看那八个 pass 的名字：`ExpressionSimplification`、`InlineElementals`、`InlineHLFIRAssign`、`PropagateFortranVariableAttributes`——**全是 Fortran 语义层面的优化**，不是 tiling 和融合。

这就对上了第 20 章讲过的那句话的反面。我们当时说"降到 `linalg` 就白拿 tiling / 融合 / bufferization 一整条链"。这句话有个前提：**你要的正是那条链上的东西。** flang 要的是别的，所以那条链对它的吸引力没那么大，而**丢信息的代价**却是实打实的。

顺便说一句，flang 社区并不是不往上游投入——`omp` 和 `acc` 这两个上游 MLIR 方言里就有大量来自 Fortran 侧的贡献。它只是把上游投入放在了 OpenMP/OpenACC，而不是 tensor/linalg 栈。

**复用上游方言不是无条件的好事。判断依据是：上游那一层能不能表达你最需要优化的那些信息。** 能，就复用，白拿整条链；不能，硬降过去只是把信息扔掉换一堆用不上的 pass。

## 把判断标准写成可以对答案的东西

前面的观察可以收成四个问题。下面这个小程序把三个项目（IREE、flang、我们的 pix）各自的层数摆出来，然后逐条对这四个问题——省得你读完只记住"看情况"三个字。

```python
# "该造几层方言？"——IREE 造了九个，flang 只造了两个，两者都成功。
# 这个模型把判断标准变成可计算的：每一层要么引入新的决策，要么不值得存在。

LAYERS = {
    "IREE（把 MLIR 用到极致）": [
        ("linalg", False, "算什么（复用上游，不自己造）"),
        ("flow",   True,  "怎么切分成可调度的区域、区域之间怎么传数据"),
        ("stream", True,  "放到哪个设备、怎么并发、张量怎么编码成设备资源"),
        ("hal",    True,  "具体设备 API（buffer / command buffer / executable）"),
        ("vm",     True,  "字节码与宿主侧胶水——自带运行时"),
    ],
    "flang（只借 MLIR 做中端）": [
        ("hlfir",  True,  "Fortran 表达式与赋值的值语义形式（不分配临时存储）"),
        ("fir",    True,  "内存语义 + Fortran 的 descriptor、数组语义"),
        ("llvm",   False, "（不自己造，直接降到上游的 llvm 方言）"),
    ],
    "pix（本书，教学规模）": [
        ("pix",    True,  "领域语义：逐点 / 邻域 / 归约三类图像运算"),
        ("linalg", False, "（不自己造；第 20 章降过去就白拿整条链）"),
    ],
}

for proj, layers in LAYERS.items():
    own = sum(1 for _, o, _ in layers if o)
    print(f"\n【{proj}】自造 {own} 层，复用 {len(layers) - own} 层")
    for name, o, decision in layers:
        print(f"  [{'自造' if o else '复用'}] {name:8} <- {decision}")

print("\n" + "=" * 62)
print("判断标准（从上面三例反推出的四问）：\n")
tests = [
    ("这一层引入了一个上一层表达不了的决策吗？",
     "flow 要表达『切分』，linalg 里没有这个概念 -> 值得造"),
    ("这个决策会被反复优化吗？",
     "stream 的设备放置与并发要反复重排 -> 值得单独一层"),
    ("上游已经有能表达它的方言了吗？",
     "flang 不自造 llvm 那层；pix 直接降到 linalg -> 不值得造"),
    ("这一层需要完整吗？",
     "hlfir 故意不完整：只覆盖表达式与赋值，其余直接用 fir"),
]
for i, (q, a) in enumerate(tests, 1):
    print(f"  {i}. {q}")
    print(f"     例：{a}")

print("\n一句话：层数不是风格问题，是『有多少个独立决策要做』的结果。")
print("IREE 要管到设备与运行时，决策多；flang 只管到 LLVM 之前，决策少。")
print("照抄 IREE 的层数去做一个只降到 LLVM 的编译器，是纯粹的负担。")
```

运行结果：

```

  [复用] linalg   <- 算什么（复用上游，不自己造）
  [自造] flow     <- 怎么切分成可调度的区域、区域之间怎么传数据

【flang（只借 MLIR 做中端）】自造 2 层，复用 1 层
  [自造] hlfir    <- Fortran 表达式与赋值的值语义形式（不分配临时存储）
  [自造] fir      <- 内存语义 + Fortran 的 descriptor、数组语义
  [复用] llvm     <- （不自己造，直接降到上游的 llvm 方言）

  [复用] linalg   <- （不自己造；第 20 章降过去就白拿整条链）

==============================================================

  1. 这一层引入了一个上一层表达不了的决策吗？
     例：flow 要表达『切分』，linalg 里没有这个概念 -> 值得造
  2. 这个决策会被反复优化吗？
     例：stream 的设备放置与并发要反复重排 -> 值得单独一层
  3. 上游已经有能表达它的方言了吗？
     例：flang 不自造 llvm 那层；pix 直接降到 linalg -> 不值得造
  4. 这一层需要完整吗？
     例：hlfir 故意不完整：只覆盖表达式与赋值，其余直接用 fir

IREE 要管到设备与运行时，决策多；flang 只管到 LLVM 之前，决策少。

```

注意 IREE 那一栏：**它自造 4 层，不是 9 层。** 主链上真正的"层"就是 `flow`/`stream`/`hal`/`vm`；`Util` 是横切的基础设施、`LinalgExt` 是上游的扩展、`Encoding`/`TensorExt` 是补充表达、`VMVX` 是 `vm` 的一个后端。

"九个方言"听起来吓人，拆开看只有四个是分层决策。**数方言目录的数量会高估一个项目的分层复杂度**——这也是我一开始把这两个项目摆在一起时自己踩的坑。

## 代价那一面

四个问题都答"是"也不等于该造。层是有持续成本的，这些成本在项目第一年基本看不见，第三年全会找上来：

- **每一层都要一套完整的配套**。`.td` 定义、verifier、自定义 assembly、canonicalization、往下的 conversion pattern、类型转换、lit 测试。我们这本书里给 pix 加一个 op 要改的地方你已经数过一遍了（第 9 到第 11 章），乘以一整个方言。
- **跨层的信息传递会成为长期负担**。第 17 章讲 `TypeConverter` 的 source/target materialization 时说过，一旦两层类型系统不同，边界上就必须有人负责补转换 op。层越多，这种边界越多。
- **调试路径变长**。第 12 章那些 `--mlir-print-ir-after-all` 的技巧，在一条九层的管线上，输出量是另一个量级。
- **一层加错了，删它比加它难得多**。下游可能已经有人依赖那一层的 op 了。

不过 flang 的 HLFIR 恰好给出了一个反向的好消息。设计文档里有这么一句：

> "As a result of these additions, **it is likely that the `fir.array_load`/`fir.array_merge_store` and related array operations could be removed from FIR** since array assignment analysis could directly happen on the higher-level FIR representation."

加一层，让**下面那层能删掉一批 op**。原来 FIR 必须自己扛数组赋值分析，于是长出了 `fir.array_load`/`fir.array_merge_store` 这套相当复杂的机制；有了 HLFIR，那件事在上面做更自然，下面就可以瘦身。

**加一层的净成本，要减掉它让别处变简单的那部分。** 这条经常被忘掉——只算新增的代码，不算减掉的复杂度，会让人系统性地低估该加层的情形。

## 小结

- **同一个问题（造几层方言），两个成功项目给了相反的答案**：IREE 九个方言目录、自带运行时；flang 两个方言，连上游的 `linalg`/`tensor` 都一个没用。都成功了，所以"层数越多/越少越好"两种说法都不成立。
- **"九个方言"要拆开看**。IREE 主链上真正的分层决策只有 4 个（`flow`/`stream`/`hal`/`vm`）；`Util` 是横切基础设施、`LinalgExt` 是**上游 `linalg` 的扩展**、`Encoding`/`TensorExt` 补充表达、`VMVX` 是 `vm` 的后端。数目录会高估分层复杂度。
- **IREE 每一层对应一个"必须有人拍板"的决策**：`flow` 管切分、`stream` 管设备放置与并发、`hal` 管具体设备 API、`vm` 管字节码与宿主胶水。上一层里根本没有下一层要拍板的那个概念，所以分层是被迫的，不是审美的。
- **`hal` 的存在理由值得单独记**：它的 `description` 自己说是 "largely 1:1 with the IREE HAL C API"——**它是运行时 ABI 照进 IR 里的影子**。IREE 自带运行时所以必须有这一层；flang 交给 LLVM，所以一层都不用造。**要不要这一层，取决于你下游交给谁。**
- **分层不一定要新方言**。`stream` 内部自己就是三层：`stream.tensor.*` → `stream.async.*` → `stream.cmd.*`，共用一个方言、只用 op 名前缀区分。判断依据是**类型系统**：类型一致就用前缀（新方言的真正成本在类型和属性上），类型整个换掉（`tensor` → `!hal.buffer_view`）才值得分家。
- **flang 把加一层的理由写成了文档，那句话是这一章最实用的判断标准**：加层不是因为优雅，而是因为出现了可观测的症状——"the code lowering ... **has significantly grown in complexity**" 且 "**the representation level gap is big, and a lot is happening in lowering**"。等某个 lowering 的 `.cpp` 长到没人敢碰、里面开始出现上下文分支，就是信号。
- **HLFIR 的三条原则都能对到本书前面的章节**：上下文无关的降；**不实体化临时量**（对应第 20 章 `ScaleToLinalg` 那段真实输出——`%arg1` 直接进 region，`ins` 只有一个操作数）；保留领域语义供高层优化。能做到第二条的前提是"值语义的高层表示"加上"region 可以引用外面的值"（`linalg.generic` 不是 `IsolatedFromAbove`），HLFIR 和 `linalg` 各自独立地要到了这两样。
- **加一层的回报要看这一层能写出多少优化**。HLFIR 的 12 个 pass 里只有 4 个在往下降，另外 8 个全是在这一层做的优化（`ExpressionSimplification`、`InlineElementals`、`InlineHLFIRAssign`…）——那 8 个在 FIR 上根本写不出来，因为 buffer 已经分配、下标已经算成地址了。
- **`BufferizeHLFIR` 是第 22 章那件事的另一个实例**：`hlfir.expr` 的值语义 → FIR 的内存临时量。flang 没用上游的 bufferization 基础设施（类型完全不同），但问题形状一模一样，连"质量是性能问题"这个结论都一样（那个 pass 旁边就有个 `OptimizedBufferization`）。
- **层可以是局部的**。HLFIR 的 `description` 明说 "It is **not a complete implementation of Fortran**, for constructs and lower level operations, FIR should be used directly"——它只管表达式和赋值，I/O、过程调用、模块直接走 FIR，两层在同一个函数里混着出现。因为**加层成本按 op 数算，收益按"这一层能做的优化"算**，给 `WRITE` 语句造高层形式的收益接近零。
- **复用上游方言不是无条件的好事**。flang 不用 `linalg` 是取舍而非疏漏：`linalg` 表达不了 Fortran 的 descriptor 语义、非零下界、字符/派生类型、语言级别名保证，而 flang 想要的高层优化全是 Fortran 语义层面的，不是 tiling 和融合。**判断依据是：上游那一层能不能表达你最需要优化的那些信息。** 能就白拿整条链，不能就只是扔掉信息换一堆用不上的 pass。
- **算净成本，不要只算新增代码**。层的持续成本是真的（一整套 `.td`/verifier/pattern/测试、跨层类型转换的边界、更长的调试路径、加错了删不掉）；但 HLFIR 的文档也写着，加了它之后 FIR 里的 `fir.array_load`/`fir.array_merge_store` 那套复杂机制**可以被移除**。**加一层的净成本要减掉它让别处变简单的那部分**——忘了这一项，会系统性地低估该加层的情形。

下一章是最后一章：**ClangIR**——C/C++ 也变成了方言，这件事把 MLIR 的适用边界推到了一个很不一样的地方（一个语义极其复杂、且已有一个成熟且不肯轻易让位的现有实现的语言）。那一章也要把这本书欠的账还掉：**MLIR 还没解决的问题**，以及在什么情况下你不该用它。
