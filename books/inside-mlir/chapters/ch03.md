# 第 3 章 读写 MLIR：通用格式、自定义格式与 mlir-opt 的日常用法

## 这一章想让你带走什么

<div class="goal-box">
<p>这一章是"肌肉记忆"章。前两章讲了 MLIR 是什么形状，这一章让你能自己动手摆弄它：<strong>两种文本格式的关系</strong>（谁是真相、什么时候必须用通用格式）、<strong>为什么每个 op 都必须带 <code>Location</code></strong>（以及它如何记录变换历史）、还有 <code>mlir-opt</code> 那几个你以后每天都要敲的选项。</p>
<p>重点是 <strong>pass 管线字符串</strong>——<code>builtin.module(func.func(canonicalize,cse))</code> 这串东西不是随便写的语法糖，它是一棵<strong>挂在 op 树上的树</strong>。你会用一个能跑的小程序把它套到一棵 IR 上，看清每个 pass 到底作用在哪些 op 上；顺便亲手复现一个真实的坑：<strong>anchor 名字写错一个字母，整串 pass 静默不跑，退出码还是 0</strong>。</p>
</div>

## 两种格式，一个真相

第 2 章你已经见过同一段 IR 的两种写法。把它们并排放：

<div class="compare">
<div class="known">
<div class="compare-head">自定义格式（你平时写的）</div>

```mlir-norun
%4 = scf.for %i = %c0 to %c8 step %c1
      iter_args(%acc = %init) -> (f32) {
  %v = memref.load %buf[%i] : memref<8xf32>
  %next = arith.addf %acc, %v : f32
  scf.yield %next : f32
}
```

</div>
<div class="cpp-side">
<div class="compare-head">通用格式（唯一的真相）</div>

```mlir-norun
%4 = "scf.for"(%0, %2, %1, %3) ({
^bb0(%arg1: index, %arg2: f32):
  %5 = "memref.load"(%arg0, %arg1)
        : (memref<8xf32>, index) -> f32
  %6 = "arith.addf"(%arg2, %5) : (f32, f32) -> f32
  "scf.yield"(%6) : (f32) -> ()
}) : (index, index, index, f32) -> f32
```

</div>
</div>

关系要记准：**通用格式（generic form）表达的是 op 的全部真实内容**——操作数、结果、属性、region、类型，一样不少，而且它的语法是**固定的、与方言无关的**。自定义格式（custom form）只是某个 op **自己实现**的打印/解析逻辑，是糖。

这不只是理论。它有三个直接后果：

1. **任何工具都能读通用格式**，哪怕它完全不认识 `pix` 方言。这是 MLIR 能有统一工具链的根基。
2. **自定义格式可能有 bug**，而通用格式不会骗你。你自己给 op 写 `assemblyFormat`（第 8 章）之后，如果打印出来的东西解析不回去，第一件事就是加 `--mlir-print-op-generic` 看真实内容。
3. **"能不能原样打印回来"是一条可自动检查的正确性标准**，叫 **round-trip**。`mlir-opt --verify-roundtrip` 会把 IR 打印出来、再解析一遍、比对两次是否一致——本书随书校验脚本对每个 `mlir` 代码块默认跑的就是它（见 `books/inside-mlir/verify/README.md`）。

<div class="note">
<strong>一个实用技巧</strong>
<p>调试一个让你困惑的 op 时，问自己："我看到的是真实内容，还是打印器让我看到的样子？"举例：某个属性在自定义格式里根本不打印（<code>assemblyFormat</code> 里漏了），你就会盯着一段"看起来正确"的 IR 找半天 bug。<code>--mlir-print-op-generic</code> 一敲，属性字典全露出来。</p>
</div>

## Location：不可选，而且记得住历史

MLIR 里**每个 op 都必须有 `Location`**。不是"建议加上"，而是创建 op 时的必填参数（第 2 章那个 `Operation::create(Location location, ...)` 的第一个参数就是它）。

平时你看不到它，因为打印器默认省略。加 `--mlir-print-debuginfo` 就全出来了。给一个 op 手写一个位置试试：

```mlir
// RUN: mlir-opt %s --mlir-print-debuginfo
func.func @f(%a: f32) -> f32 {
  %s = arith.addf %a, %a : f32 loc("mysrc.pix":7:3)
  return %s : f32
}
```

运行结果（`example.mlir` 是你传给 `mlir-opt` 的文件名，所以你看到的路径会是你自己的文件）：

```
#loc2 = loc("example.mlir":1:14)
module {
  func.func @f(%arg0: f32 loc("example.mlir":1:14)) -> f32 {
    %0 = arith.addf %arg0, %arg0 : f32 loc(#loc3)
    return %0 : f32 loc(#loc4)
  } loc(#loc1)
} loc(#loc)
#loc = loc("example.mlir":0:0)
#loc1 = loc("example.mlir":1:1)
#loc3 = loc("mysrc.pix":7:3)
#loc4 = loc("example.mlir":3:3)
```

三个观察：

- 连**块参数**都有位置（`%arg0 ... loc(...)`），模块自己也有。
- 我手写的 `loc("mysrc.pix":7:3)` 被原样保留成 `#loc3`——**位置可以来自另一门语言的源文件**。这正是你写自己的前端时要做的事：把 `.pix` 源码的行列号塞进 op，后面任何一层报错都能指回用户写的那一行。
- 位置像属性一样被**唯一化**并以 `#locN` 的形式复用（第 4 章讲唯一化）。

常见的几种位置类型，认识名字就够：

| 类型 | 含义 | 什么时候出现 |
| --- | --- | --- |
| `FileLineColLoc` | 文件 + 行 + 列 | 最常见，前端生成 |
| `NameLoc` | 一个名字（可再包一层位置） | 给变量/算子起名，便于调试 |
| `CallSiteLoc` | 调用点 + 被调用处 | 内联之后保留调用链 |
| `FusedLoc` | **多个位置融合成一个** | 两个 op 被合并时 |
| `UnknownLoc` | 不知道 | 手写 IR、编译器内部生成 |

`FusedLoc` 值得多说一句，因为它体现了 MLIR 对"可调试性"的认真程度：当一个变换把两个 op 合并成一个（比如第 21 章的融合），新 op 的位置是两个旧位置的**融合**。于是这个 op 后面出问题时，诊断能同时指回**两处**用户源码。这件事在"metadata 可以随便丢"的世界里是做不到的。

## mlir-opt：pass 管线是一棵挂在 op 树上的树

现在讲那个最常敲、也最容易误解的东西：

```bash
mlir-opt input.mlir --pass-pipeline='builtin.module(func.func(canonicalize,cse))'
```

括号嵌套**不是分组语法**，而是在说"每个 pass 挂在哪种 op 上"：最外层 `builtin.module` 是这条管线锚定的 op；里面的 `func.func(...)` 意思是"对模块里每一个 `func.func`，跑括号里这些 pass"。

下面这个小程序把管线字符串解析出来、套到一棵 IR 上，打印每个 pass 实际作用的对象。第三个例子故意把 `func.func` 拼成 `func.funk`：

```python
# pass 管线字符串到底是什么意思？它是一棵"挂在 op 树上"的树。
# 下面手写一个解析器 + 匹配器，把管线套到一棵 IR 上，看每个 pass 会跑在哪些 op 上。

def parse(s):
    """把 'a(b(p1,p2),p3)' 解析成 [('a', [('b', ['p1','p2']), 'p3'])]。"""
    items, name, i = [], "", 0
    while i < len(s):
        c = s[i]
        if c == "(":
            depth, j = 1, i + 1
            while depth:
                depth += (s[j] == "(") - (s[j] == ")")
                j += 1
            items.append((name.strip(), parse(s[i + 1:j - 1])))
            name, i = "", j
        elif c == ",":
            if name.strip():
                items.append(name.strip())
            name, i = "", i + 1
        else:
            name, i = name + c, i + 1
    if name.strip():
        items.append(name.strip())
    return items


# 一棵 IR：模块里两个函数，第一个函数里还有个 gpu.module（模拟真实项目的嵌套）
IR = ("builtin.module", "", [
    ("func.func", "@encode", [
        ("scf.for", "", []),
    ]),
    ("func.func", "@decode", []),
    ("gpu.module", "@kernels", [
        ("gpu.func", "@hot_loop", []),
    ]),
])


def label(op):
    return op[0] + (" " + op[1] if op[1] else "")


def apply(pipeline, ops, indent=1):
    """ops 是这一层管线所挂靠的 op 列表。
    - 裸的 pass：跑在 ops 里的每个 op 上
    - 嵌套的 anchor：在 ops 的子 op 里找同名的，再往下套"""
    warnings = []
    for item in pipeline:
        pad = "  " * indent
        if isinstance(item, tuple):
            anchor, inner = item
            matched = [c for o in ops for c in o[2] if c[0] == anchor]
            if not matched:
                print(f"{pad}{anchor}( … )  →  ⚠ 匹配到 0 个 op")
                warnings.append(anchor)
                continue
            print(f"{pad}{anchor}( … )  →  " + "、".join(label(o) for o in matched))
            warnings += apply(inner, matched, indent + 1)
        else:
            print(f"{pad}pass「{item}」  →  跑在 " + "、".join(label(o) for o in ops))
    return warnings


def run(pipeline_str):
    print(f"管线：{pipeline_str}")
    root = ("(顶层)", "", [IR])   # 虚拟父节点，让最外层 anchor 有东西可匹配
    warn = apply(parse(pipeline_str), [root])
    if warn:
        print(f"  ！有 {len(warn)} 个 anchor（{'、'.join(warn)}）没匹配到任何 op：")
        print("    它们里面的 pass 一个都不会跑，而 mlir-opt 退出码仍是 0，什么都不说。")
    print()


run("builtin.module(func.func(canonicalize,cse))")
run("builtin.module(func.func(canonicalize),gpu.module(gpu.func(cse)))")
run("builtin.module(func.funk(canonicalize))")      # 打错一个字母
print("最后这个就是本章那个坑：anchor 拼错 → 静默什么都不做。")
print("想确认 pass 到底跑了没有，用 --mlir-print-ir-after-all：它一行都不打印，就是一个都没跑。")
```

运行结果：

```
管线：builtin.module(func.func(canonicalize,cse))
  builtin.module( … )  →  builtin.module
    func.func( … )  →  func.func @encode、func.func @decode
      pass「canonicalize」  →  跑在 func.func @encode、func.func @decode
      pass「cse」  →  跑在 func.func @encode、func.func @decode

管线：builtin.module(func.func(canonicalize),gpu.module(gpu.func(cse)))
  builtin.module( … )  →  builtin.module
    func.func( … )  →  func.func @encode、func.func @decode
      pass「canonicalize」  →  跑在 func.func @encode、func.func @decode
    gpu.module( … )  →  gpu.module @kernels
      gpu.func( … )  →  gpu.func @hot_loop
        pass「cse」  →  跑在 gpu.func @hot_loop

管线：builtin.module(func.funk(canonicalize))
  builtin.module( … )  →  builtin.module
    func.funk( … )  →  ⚠ 匹配到 0 个 op
  ！有 1 个 anchor（func.funk）没匹配到任何 op：
    它们里面的 pass 一个都不会跑，而 mlir-opt 退出码仍是 0，什么都不说。

最后这个就是本章那个坑：anchor 拼错 → 静默什么都不做。
想确认 pass 到底跑了没有，用 --mlir-print-ir-after-all：它一行都不打印，就是一个都没跑。
```

<div class="warn">
<strong>这个坑是真的，不是我编的</strong>
<p>拿一个"乘 1.0"的函数实测过：<code>--pass-pipeline='builtin.module(func.func(canonicalize))'</code> 折掉了乘法；把 anchor 改成 <code>func.funk</code>（甚至改成完全不存在的 <code>foo.bar</code>），输出<strong>原封不动</strong>，退出码 <strong>0</strong>，没有任何警告。</p>
<p>确认 pass 有没有真的跑，最可靠的办法是 <code>--mlir-print-ir-after-all</code>：它给每个<strong>实际执行过</strong>的 pass 打印一段 IR 头（形如 <code>// -----// IR Dump After CanonicalizerPass: canonicalize{...} //----- //</code>）。anchor 写错时，它<strong>一行都不打印</strong>——这就是最干净的判据。（<code>--mlir-pass-statistics</code> 帮不上忙：没有统计项的 pass 在报告里根本不出现。）</p>
</div>

## 另外几个每天都会用到的选项

**`--mlir-print-ir-after-change`**：只在 IR **真的变了**之后才打印。管线一长，`--mlir-print-ir-after-all` 的输出根本读不完，这个选项能直接把你带到"是哪一步改坏的"。

**`--allow-unregistered-dialect`**：允许解析没注册过的方言。手写实验性 IR 时非常方便——你可以先"假装"已经有了某个 op：

```mlir
// RUN: mlir-opt %s --allow-unregistered-dialect
func.func @f() {
  "my.strange_op"() {my.attr = 42 : i64} : () -> ()
  return
}
```

不加这个开关，报错会明确告诉你怎么做：

```
error: operation being parsed with an unregistered dialect. If this is intended,
please use -allow-unregistered-dialect with the MLIR tool used
```

注意两点：未注册的 op **只能用通用格式**写（没人给它实现自定义格式），而且它对 MLIR 来说是个黑盒——没有 verifier、没有折叠规则、没有副作用信息，所以大多数 pass 会保守地绕开它。这正好反证了第二部分（造方言）的价值。

**`--split-input-file` 配 `--verify-diagnostics`**：一个文件里放多段独立 IR（用 `// -----` 分隔），并且**断言某些错误必须发生**。这是 MLIR 全家的测试写法，第 10、12 章你会天天用：

```mlir-norun
func.func @ok(%x: i32) -> i32 {
  %c0 = arith.constant 0 : i32
  %y = arith.addi %x, %c0 : i32
  return %y : i32
}

// -----

func.func @bad(%x: i32) -> i32 {
  // expected-error @+1 {{'arith.addf' op operand #0 must be}}
  %y = arith.addf %x, %x : i32
  return %y : i32
}
```

跑 `mlir-opt bad_and_good.mlir --split-input-file --verify-diagnostics`：第二段**故意写错**，但因为错误被 `expected-error` 精确预言了，整个命令**退出码是 0**。反过来，如果你的 verifier 哪天不报这个错了，测试立刻失败——这就是给"报错行为"上测试的办法。

**`--show-dialects`**：列出这份二进制注册了哪些方言。接手别人的 `xxx-opt` 时第一个该敲的命令。

**`--emit-bytecode`**：把 IR 写成二进制格式。文本格式适合人读和写测试，字节码适合规模化地存取（快、小、有版本兼容策略）。实测输出的开头是魔数 `ML\xefR` 加一个版本串——你不需要关心细节，只要知道**同一份 IR 有文本和字节码两种等价序列化形态**，`mlir-opt` 两种都能读。

<div class="note">
<strong>Python bindings：探索 IR 的另一条路</strong>
<p>MLIR 自带 Python 绑定（构建时开 <code>-DMLIR_ENABLE_BINDINGS_PYTHON=ON</code>，见附录 A）。它适合交互式地"翻"一份 IR：遍历 op、查属性、跑管线，比写 C++ 快得多。本书正文不用它（因为造方言、写 pattern 仍然是 C++ 的活），但你想快速验证"这段 IR 里有几个 <code>linalg.generic</code>"这类问题时，它比写个 pass 划算。附录 C 有入口指路。</p>
</div>

## 动手：读一段陌生 IR 的标准流程

给你一段完全陌生的 `.mlir`（比如从别人项目里捞出来的），下面这套动作能最快建立理解。用本章任意一段 IR 试：

```bash
# 1. 先确认它是合法的（解析 + verifier + 能原样打回来）
mlir-opt input.mlir --verify-roundtrip

# 2. 看真实内容，别被自定义格式骗了
mlir-opt input.mlir --mlir-print-op-generic | head -40

# 3. 看位置信息：这些 op 是从哪门语言、哪一行来的
mlir-opt input.mlir --mlir-print-debuginfo | head -20

# 4. 这份工具支持哪些方言？（判断这段 IR 需要谁来处理）
mlir-opt --show-dialects

# 5. 跑一个 pass，只在 IR 真变了的时候打印
mlir-opt input.mlir --canonicalize --mlir-print-ir-after-change
```

**改一改：**

**这一章的要点**

- **通用格式是唯一真相**，自定义格式是每个 op 自己实现的糖。调试自己的 op 时，第一件事就是 `--mlir-print-op-generic`。
- **round-trip（打印 → 重新解析 → 一致）是一条可自动检查的正确性标准**，`--verify-roundtrip` 就是它；本书所有 MLIR 代码块都过了这一关。
- **每个 op 必带 `Location`**，位置可以来自你自己的源语言；`FusedLoc` 让"两个 op 合成一个"之后诊断仍能指回两处源码。可调试性在 MLIR 里是硬性设计，不是事后补丁。
- **pass 管线字符串是一棵挂在 op 树上的树**，括号是锚点而不是分组。你已经用模拟器看清了每个 pass 落在哪些 op 上。
- **anchor 写错 → 整串 pass 静默跳过、退出码 0**（实测）。判据是 `--mlir-print-ir-after-all` 一行都不打印。以后 pass 不生效，先怀疑 anchor。
- 日常工具箱：`--mlir-print-ir-after-change`（定位哪步改坏的）、`--allow-unregistered-dialect`（手写实验 IR）、`--split-input-file --verify-diagnostics`（给报错行为写测试）、`--show-dialects`、`--emit-bytecode`。

下一章进入 MLIR 的另一半骨架：**类型与属性**。它们都是**不可变、全局唯一化**的值——`tensor<4x4xf32>` 这个类型在整个进程里只有一份。这个反直觉的设计决定了 MLIR 里比较类型为什么可以用指针相等、也决定了 `MLIRContext` 为什么必须贯穿所有 API。
