## ClangIR 的处境：一块特别硬的地

先把 ClangIR 和前面几章的项目区分开。

Triton、IREE 都是**新建的**：以前没有一个"Python DSL 到 PTX"的标准答案，也没有一个"端到端 AI 部署栈"的既有实现在那儿挡着。flang 也算新建——`f18` 是从头写的 Fortran 前端。

ClangIR 不是。C/C++ 的 clang → LLVM IR 这条路走了二十年，`clang/lib/CodeGen/` 里那些代码经过了天量的实战检验，性能、正确性、边角情况全都磨过。ClangIR 要往这条路中间**插一层**。

所以它面临一个前面几章都没有的约束：**它必须和既有实现输出等价的结果，而且不能要求用户改任何东西。** 这个约束有多硬，从几个源码事实就能看出来。

它确实已经在树里了（LLVM 23.1.2 的 `clang/include/clang/CIR/`），方言名很朴素：

```
$ grep -rhoE 'let name = "[a-z]+"' clang/include/clang/CIR/Dialect/IR/CIRDialect.td
let name = "cir"
```

`summary` 值得读一遍，因为它比"C++ 的 MLIR 方言"这个说法准确得多：

> "A high-level dialect for analyzing and optimizing **Clang supported languages**"

复数——不是只为 C++，是为 clang 支持的所有语言（C、C++、Objective-C/C++、以及 CUDA/OpenCL 这些方言；`CIRCUDAAttrs.td`、`CIROpenCLAttrs.td` 这两个文件就在那儿）。

而**默认是关着的**。`clang/include/clang/Frontend/FrontendOptions.h` 的构造函数初始化列表里写得很清楚：

```cpp
EmitPrettySymbolGraphs(false), GenReducedBMI(false),
UseClangIRPipeline(false), ClangIRDisablePasses(false),
ClangIRDisableCIRVerifier(false), ClangIREnableIdiomRecognizer(false),
ClangIRLibOptEnabled(false), TimeTraceGranularity(500),
```

`UseClangIRPipeline(false)`——你不给 `-fclangir`，走的还是二十年那条老路。而且注意后面两个：`ClangIREnableIdiomRecognizer(false)`、`ClangIRLibOptEnabled(false)`——**即便你开了 CIR，那两个最有意思的 pass（下面会讲，它们是 CIR 存在的核心理由）也还是默认关着的。**

这不是 bug，是一个插在成熟实现中间的项目该有的样子。但它也说明：**读一个项目"在不在树里"远不足以判断它的成熟度，要读它的默认值。**

## 它保留了什么：LLVM IR 里问不出来的那些问题

那 CIR 到底图什么？把它的 op 名列出来，答案就自己浮出来了。`CIROps.td` 里有 125 个 op 定义，挑出跟 C++ 相关的那些，按主题分组：

**继承与虚函数**

```
cir.base_class_addr        cir.derived_class_addr
cir.base_data_member       cir.derived_data_member
cir.base_method            cir.derived_method
cir.get_method             cir.get_runtime_member
cir.vtable.get_vptr        cir.vtable.address_point
cir.vtable.get_virtual_fn_addr    cir.vtable.get_type_info
cir.vtt.address_point      cir.dyn_cast
```

**异常**

```
cir.try                  cir.alloc.exception      cir.begin_catch
cir.end_catch            cir.catch_param          cir.construct_catch_param
cir.init_catch_param     cir.eh.dispatch          cir.eh.initiate
cir.eh.inflight_exception  cir.eh.typeid          cir.eh.terminate
cir.resume               cir.cleanup.scope        cir.begin_cleanup
cir.end_cleanup
```

**对象生命周期**

```
cir.array.ctor    cir.array.dtor    cir.delete_array
cir.local_init    cir.lifetime.start  cir.lifetime.end  cir.launder
```

（`cir.launder` 就是 `std::launder`——连这个都有一个 op。）

**协程**

```
cir.await    cir.co_return    cir.coro.body
```

**结构化控制流**

```
cir.if  cir.switch  cir.scope  cir.break  cir.continue
cir.ternary  cir.condition  cir.yield  cir.goto  cir.label
```

看到 `cir.if`、`cir.scope` 这一组，你应该立刻想到第 24 章。那一章我们把 `scf.for` 降成 `cf.br`——**结构化控制流降成基本块**，而且讲了那一步是不可逆的：降完之后"这是一个循环"这件事只能靠分析重新推，推不一定准。

CIR 里也有完全对应的一步。看它的 pass 列表：

```
$ grep -oE 'def [A-Za-z]+ : Pass<"[a-z-]+"' clang/include/clang/CIR/Dialect/Passes.td
CIRCanonicalize      -> cir-canonicalize
CIRSimplify          -> cir-simplify
HoistAllocas         -> cir-hoist-allocas
CIRFlattenCFG        -> cir-flatten-cfg
GotoSolver           -> cir-goto-solver
CXXABILowering       -> cir-cxxabi-lowering
TargetLowering       -> cir-target-lowering
CIREHABILowering     -> cir-eh-abi-lowering
LoweringPrepare      -> cir-lowering-prepare
IdiomRecognizer      -> cir-idiom-recognizer
LibOpt               -> cir-lib-opt
CallConvLowering     -> cir-call-conv-lowering
```

`cir-flatten-cfg`——就是我们的 `scf` → `cf`。而且 op 列表里那两个带 `.flat` 后缀的（`cir.switch.flat`、`cir.resume.flat`）就是**压平之后的形式**：同一个方言里同时存在结构化版本和压平版本，用后缀区分。这正是第 27 章讲 `stream.tensor.*`/`stream.async.*`/`stream.cmd.*` 时说的那件事——**同一方言内用 op 名分层**，因为类型系统没变。

现在可以回答"CIR 图什么"了。把这些 op 翻成"它保留了哪些 LLVM IR 里已经问不出来的问题"：

```python
# 第 28 章两件事：① 为什么 C++ 值得一个方言 ② 接口如何让一套实现服务两个前端

print("=" * 66)
print("① C++ 的哪些语义活到了哪一层")
print("=" * 66)
# 每行：这条 C++ 事实，在 cir / LLVM IR 里还看得见吗
FACTS = [
    ("这次调用是虚调用",        "cir.vtable.get_virtual_fn_addr", "GEP + load，和普通间接调用没区别"),
    ("这个转换是 dynamic_cast", "cir.dyn_cast",                   "对运行时函数的一次 call"),
    ("这里在析构一个数组",      "cir.array.dtor",                 "一个循环 + 一次 call"),
    ("这是基类子对象的地址",    "cir.base_class_addr",            "一次常量偏移的 GEP"),
    ("这个作用域在退栈时清理",  "cir.cleanup.scope",              "landingpad + 若干基本块"),
    ("这是协程的一个 await 点", "cir.await",                      "已被拆成状态机"),
    ("这个 if 是源码里的 if",   "cir.if（带 region）",            "四个基本块和两条 br"),
]
for fact, in_cir, in_llvm in FACTS:
    print(f"\n  「{fact}」")
    print(f"     cir 里     ：{in_cir}")
    print(f"     LLVM IR 里 ：{in_llvm}")
print("\n  结论：LLVM IR 不是『信息少一点』，是这些问题**问不出来**了。")
print("  想在 C++ 语义层面做分析或优化，就得有一层还留着这些信息。")

print("\n" + "=" * 66)
print("② 一套 OpenACC 实现，两个前端：靠的是接口，不是公共类型")
print("=" * 66)

# acc 方言只认接口。两个前端各自给自己的类型挂上同一个接口的 ExternalModel。
class PointerLikeType:
    """上游 mlir::acc::PointerLikeType —— acc 方言唯一认识的东西"""
    registry = {}          # 类型名 -> 实现（attachInterface 装进来的）
    @classmethod
    def attach(cls, type_name, model):
        cls.registry[type_name] = model
    @classmethod
    def get(cls, type_name):
        return cls.registry.get(type_name)

# flang 侧：FIROpenACCTypeInterfaces.h
PointerLikeType.attach("!fir.ref<!fir.array<10xf32>>",
                       {"owner": "flang", "elem": "!fir.array<10xf32>"})
# ClangIR 侧：CIROpenACCTypeInterfaces.h
PointerLikeType.attach("!cir.ptr<!cir.array<f32 x 10>>",
                       {"owner": "ClangIR", "elem": "!cir.array<f32 x 10>"})
# 上游自己的两个，本章用 mlir-opt 真跑过
PointerLikeType.attach("memref<10xf32>", {"owner": "上游", "elem": "f32"})
PointerLikeType.attach("!llvm.ptr",      {"owner": "上游", "elem": "（不透明，需显式 varType）"})

def acc_copyin(var_type):
    """acc.copyin 的 verifier + lowering 想知道的事。它不认识任何具体类型。"""
    model = PointerLikeType.get(var_type)
    if model is None:
        return f"  ✗ {var_type:<32} 被拒绝：must be any pointer or mappable"
    return (f"  ✓ {var_type:<32} 元素类型 = {model['elem']}"
            f"   （接口由 {model['owner']} 挂上）")

print("\nacc.copyin 对各种类型的反应：")
for t in ["memref<10xf32>", "!llvm.ptr",
          "!fir.ref<!fir.array<10xf32>>", "!cir.ptr<!cir.array<f32 x 10>>", "i32"]:
    print(acc_copyin(t))

print("\n  注意 acc_copyin 里没有一处 if 在判断具体类型。")
print("  加一个新前端 = 写一个 ExternalModel + attachInterface 一次，")
print("  acc 那边一行都不用改。这就是接口和 trait 的根本区别（第 10 章）。")
print("\n  而漏了那次 attachInterface，症状是 verifier 说『这个类型不行』——")
print("  和第 18 章漏了 registerAllExtensions 时『这个 op 不认识』一模一样。")
```

### 一个往上抬抽象的 pass

前面那 12 个 pass 里，有两个和其他的性质不一样。`IdiomRecognizer` 的 `summary`：

> "**Raise** calls to C/C++ libraries to CIR operations"

**Raise**，不是 lower。整本书我们一直在往下降；这个 pass 往上抬。它的 `description`：

> "This pass recognizes idiomatic C++ usage and captures information about C++ standard library containers, library functions calls, and types into CIR operations, attributes and types."

然后 `LibOpt` 在那个抬高的表示上做优化：

> "This pass applies transformations on C/C++ standard library idioms, such as library function calls and structs raised to CIR operations using the `cir-idiom-recognize` pass."

这两个 pass 是 CIR 最有说服力的理由，因为它们做的事**在 LLVM IR 上根本没法做**。一个 `std::find` 在 LLVM IR 里是什么？内联展开之后的一堆指针比较和分支，`std::vector` 的三个指针成员也早被 SROA 拆散了。"这段代码在做 `std::find`"这个信息在 LLVM IR 里不是"难恢复"，是**已经没有了**。

而在 CIR 那一层，类型还在、调用还在，所以"认出这是 `std::find`，把它换成一次 `memchr`"是可写的。

这就是"高层表示值得存在"的最一般形式。第 20 章我们让 `pix.convolve` 降到 `linalg.generic` 而不是直接降到循环，理由是一样的：**一旦降下去，那个决策就再也做不了了。** CIR 把这个道理用在了 C++ 标准库上。

不过前面提过——这两个 pass 默认是关着的。**"这件事原理上做得到"和"这件事现在默认在做"之间，还有很长的路。** 这一点在整本书里都成立，第五部分看的每个项目都有这样的空隙。

## 补讲一个机制：ExternalModel

上面那张图里有一件事前面二十七章没讲过，现在必须补上：**`!fir.ref` 和 `!cir.ptr` 这两个类型，都不是 `acc` 方言定义的。`acc` 也不是 flang 或 ClangIR 定义的。那接口是怎么挂上去的？**

第 10 章讲接口时，我们给 `pix` 的 op 加接口的方式是在 `.td` 里写 `DeclareOpInterfaceMethods<...>`——那是"我拥有这个 op，我在它的定义里声明实现了这个接口"。但 `acc::PointerLikeType` 是上游的接口，`!fir.ref` 是 flang 的类型，两边谁也不能改对方的定义。

MLIR 的答案是 **`ExternalModel`**：把接口的实现从类型定义里**分离出来**，单独写成一个类，运行时挂上去。`mlir/docs/Interfaces.md` 的措辞：

> "External interface implementation for a concrete class. **This does not require modifying the definition of the type class itself.**"

用法分两步。第一步，写一个 model 类：

```cpp
// 摘自 mlir/docs/Interfaces.md 的示例
struct ExternalModelExample
    : public ExampleTypeInterface::ExternalModel<ExternalModelExample,
                                                 IntegerType> {
  static unsigned exampleStaticInterfaceHook() {
    // Implementation is provided here.
    return IntegerType::someStaticMethod();
  }
  // No need to define `exampleInterfaceHook` that has a default implementation
  // in `ExternalModel`. But it can be overridden if desired.
}
```

第二步，在 context 里挂上：

```cpp
int main() {
  MLIRContext context;
  /* ... */;

  // Attach the interface model to the type in the given context before
  // using it. The dialect containing the type is expected to have been loaded
  // at this point.
  IntegerType::attachInterface<ExternalModelExample>(context);
}
```

这两段就是 flang 和 ClangIR 干的事。两边的文件名甚至是对称的：

| 前端 | 文件 | 挂了什么 |
| --- | --- | --- |
| flang | `flang/include/flang/Optimizer/OpenACC/Support/FIROpenACCTypeInterfaces.h` | `OpenACCPointerLikeModel`、`OpenACCMappableModel` |
| ClangIR | `clang/include/clang/CIR/Dialect/OpenACC/CIROpenACCTypeInterfaces.h` | `OpenACCPointerLikeModel` |

两个 `struct` **同名**，都继承 `mlir::acc::PointerLikeType::ExternalModel<...>`。这显然是一边照着另一边写的——而这正是共享基础设施该有的样子。

（顺带一个诚实的细节：ClangIR 那边目前只有 `PointerLikeModel`，`MappableModel` 还没有——flang 两个都有。又一处"CIR 更年轻"的证据。）

挂的动作走的是**扩展注册**机制，和第 18 章那个坑同源：

```cpp
namespace cir::acc {
void registerOpenACCExtensions(mlir::DialectRegistry &registry);
} // namespace cir::acc
```

还记得第 18 章我卡住的那个错误吗——`custom op 'transform.structured.match' is unknown`，原因是漏了 `registerAllExtensions`。`ExternalModel` 的失败模式是同一类，而且文档专门警告过：

> "**Forgetting to register an external model can lead to bugs which are hard to track down.** The `declarePromisedInterface` function can be used to declare that an external model implementation for an operation must eventually be provided."

```cpp
void MyDialect::initialize() {
  declarePromisedInterface<SomeInterface, SomeOp>();
   ...
}
```

`declarePromisedInterface` 是把"你忘了注册"从一个诡异的运行时行为变成一条明确的错误信息。**这个 API 存在本身就说明这个坑踩的人足够多了。** 如果你要用 `ExternalModel`，把它一起用上。

文档还有一条设计建议，值得原文引用：

> "It is strongly encouraged to only use this mechanism if you **'own' the interface** being externally applied. This prevents a situation where neither the owner of the dialect containing the object nor the owner of the interface are aware of an interface implementation, which can lead to duplicate or diverging implementations."

也就是说：外部挂接口这件事，最好由**接口的拥有者**来做，而不是随便第三方。OpenACC 这个案例里，`acc` 方言在上游、FIR/CIR 的类型在各自前端，两边是同一批人在协作维护的，所以这是那条建议说的正当用法，不是钻空子。

### 用真工具验一遍

上面所有话都可以用 `mlir-opt` 当场验证——上游的 `acc` 方言就在我们的构建里。

正面：两个毫无关系的类型都能作为 `varPtr`。

```mlir
// RUN: mlir-opt %s
// 上游 acc 的 varPtr 约束是**接口**，不是类型清单：memref 和 !llvm.ptr
// 这两个毫无关系的类型都能用，因为它们都实现了 acc::PointerLikeType。
// flang 给 !fir.ref 挂了同一个接口，ClangIR 给 !cir.ptr 挂了同一个接口——
// 于是一套 OpenACC 实现同时服务 Fortran 和 C++ 两个前端。
func.func @on_memref(%p: memref<10xf32>) {
  %d = acc.copyin varPtr(%p : memref<10xf32>) -> memref<10xf32>
  acc.parallel dataOperands(%d : memref<10xf32>) {
    acc.yield
  }
  return
}
func.func @on_llvm_ptr(%p: !llvm.ptr) {
  // !llvm.ptr 是不透明指针，自己不带元素类型，所以要显式给 varType
  %d = acc.copyin varPtr(%p : !llvm.ptr) varType(f32) -> !llvm.ptr
  acc.parallel dataOperands(%d : !llvm.ptr) {
    acc.yield
  }
  return
}
```

运行结果：

```
module {
  func.func @on_memref(%arg0: memref<10xf32>) {
    %0 = acc.copyin varPtr(%arg0 : memref<10xf32>) -> memref<10xf32>
    acc.parallel dataOperands(%0 : memref<10xf32>) {
      acc.yield
    }
    return
  }
  func.func @on_llvm_ptr(%arg0: !llvm.ptr) {
    %0 = acc.copyin varPtr(%arg0 : !llvm.ptr) varType(f32) -> !llvm.ptr
    acc.parallel dataOperands(%0 : !llvm.ptr) {
      acc.yield
    }
    return
  }
}
```

反面更能说明问题。换一个没实现那个接口的类型：

```mlir
// RUN: not mlir-opt %s 2>&1 | FileCheck %s
// 约束不是"随便什么类型都行"。i32 没实现 PointerLikeType/MappableType，
// verifier 直接拒绝——而且报错原文就是按接口措辞的。
// 开头那个 not 是 lit 的惯例：这一块**应该失败**，我们要断言的正是报错本身。
// CHECK: must be any pointer or mappable, but got 'i32'
func.func @on_i32(%p: i32) {
  %d = acc.copyin varPtr(%p : i32) -> i32
  return
}
```

实跑的报错原文：

```
acc3.mlir:2:8: error: 'acc.copyin' op operand #0 must be any pointer or mappable, but got 'i32'
  %d = acc.copyin varPtr(%p : i32) -> i32
       ^
```

> **"must be any pointer or mappable"**

这句报错就是第 10 章那段论证的实证。`acc.copyin` 的操作数约束**不是一张类型清单**，而是"实现了这两个接口之一"。你加一个新前端，写一个 `ExternalModel`、`attachInterface` 一次，`acc` 那边一行都不用改。

这是整本书最想让你带走的那件事，在最高层级上的一次兑现：

> **MLIR 的可扩展性不在"你可以定义新 op"上——那只是语法。真正的可扩展性在"不相关的方言可以通过接口共享变换"上。**

想想这件事的规模：**OpenACC 的整套语义（数据子句、`parallel`/`kernels` 区域、归约、异步队列）实现一遍，同时给 Fortran 和 C++ 用。** 在传统编译器架构里，这两个前端之间不可能共享这种层次的东西——gcc 的 Fortran 和 C++ 前端各自实现 OpenACC，能共享的只有最后那点运行时库。

而且注意这条链是怎么接上的：第 27 章说过 flang 把上游投入放在了 `omp`/`acc` 而不是 tensor/linalg 栈。**flang 为自己的需求推动上游建的那个 `acc` 方言，现在 ClangIR 直接拿来用了。** 这是"上游共享层"这个模式真正生效的样子——第一个用户付了大部分成本，第二个用户几乎白拿。

顺便解释一个可能让你意外的事实。`clang/include/clang/Basic/DiagnosticDriverKinds.td` 里有这么一条警告：

```tablegen
def warn_drv_openacc_without_cir
    : Warning<"OpenACC directives will result in no runtime behavior; use "
              "-fclangir to enable runtime effect">,
      InGroup<SourceUsesOpenACC>;
```

翻过来：**clang 里的 OpenACC，不开 `-fclangir` 就没有运行时效果。** 也就是说 CIR 已经有一个"老路做不到"的真实功能了——这比任何架构论证都更有说服力，也解释了 CIR 为什么能进树：**它不只是"把老路重做一遍更漂亮"，它带来了老路给不了的东西。**

## 还账：MLIR 没解决的问题

前面二十七章基本在讲 MLIR 能干什么。这一节讲另一半。我尽量只说有证据的，不做预测。

### 一、"完成一个前端"的工作量被严重低估

ClangIR 自己的代码库里有一份现成的证据。`clang/include/clang/CIR/MissingFeatures.h`，头部注释：

> "As a way to track features that haven't yet been implemented this class explicitly contains a list of static fns that will return false that you can guard against. If and when a feature becomes implemented simply changing this return to true will cause compilation to fail at all the points in which we noted that we needed to address. **This is a much more explicit way to handle "TODO"s.**"

这个技巧本身值得学——**把 TODO 变成一个返回 `false` 的函数**：

```cpp
struct MissingFeatures {
  // Address space related
  static bool addressSpace() { return false; }

  // Unhandled global/linkage information.
  static bool opGlobalThreadLocal() { return false; }
  static bool opGlobalWeakRef() { return false; }
  static bool opGlobalUnnamedAddr() { return false; }
  static bool opGlobalVisibility() { return false; }
  static bool opGlobalDLLImportExport() { return false; }
  ...
```

好在哪？把它改成 `return true` 的那一天，**编译器会在所有需要处理这件事的地方报错**——不用靠 `grep TODO`，也不用靠记性。

数一下有多少条：

```
$ grep -cE '^\s*static bool' clang/include/clang/CIR/MissingFeatures.h
252
```

**252 条。** 分类覆盖了基本上每一个角落：address space、linkage、load/store 属性、`alloca`/`func`/`call` 的处理、`RecordType`、协程、CXXABI、atomic、全局构造函数、调用约定……

这个数字是这一章最实在的一条信息。它不是说 ClangIR 做得不好——恰恰相反，能把 252 个缺口这样明码标出来的项目是靠得住的。它说的是**另一件事**：

> **"我用 MLIR 给我的语言做一个前端"这句话，在 C++ 这种复杂度的语言上，工作量是四位数的工时起。**

MLIR 帮你省掉的是 IR 基础设施（数据结构、pass 框架、pattern 引擎、打印解析、verifier 框架），那部分确实省得很多。但**语言语义本身的复杂度，一分都不会因为换了 IR 框架而减少。** 这是所有"用了 MLIR 一切都会简单"的说法里最大的水分。

### 二、方言碎片化，而且这个问题没有技术解

MLIR 的设计前提是"人人都能造方言"。好处整本书都在讲。代价是：

- 到这一章我们已经数过：上游几十个方言，IREE 九个，Triton 三个，flang 两个，ClangIR 一个。加上各家私有的，总数无从统计。
- **同一件事在不同方言里被表达了多遍。** 最清楚的例子是"结构化控制流降成基本块"这一步：上游是 `scf` → `cf`（第 24 章），ClangIR 是 `cir-flatten-cfg`，两边做的是同一类变换、各写一遍。
- **降下去的路径不是唯一的，选哪条很难判断。** 我们自己书里就有两条：第 16 章 `pix` → `arith`，第 20 章 `pix` → `linalg`。哪条对？取决于你后面要不要 tile——而这件事你在写第一条降级 pattern 的那天往往还不知道。

而这个问题**没有技术解**，因为它是那个设计前提的直接后果。你不可能既要"人人都能造方言"又要"方言不碎片化"。能缓解的只有社会性手段：往上游推、复用接口（这一章的 OpenACC 就是好例子）、写清文档。

第 27 章那四个问题的价值也在这里：**它不能消除碎片化，但能让你不去贡献新的碎片。**

### 三、编译时间

这件事上游自己的工具链里就有痕迹。我们第 12 章讲过的调试手段——`--mlir-print-ir-after-all`、`--mlir-timing`——之所以存在得这么完备，是因为 MLIR 管线真的会长到需要它们。

成本来自哪里，前面各章都遇到过：

- **每一层转换都有开销**：pattern 匹配要遍历、`applyPatternsGreedily` 要跑到不动点（第 14 章讲过 `maxIterations` 和 `maxNumRewrites` 两个上限，以及不收敛时会挂住）。
- **verifier 默认在每个 pass 后都跑**。这是好事（第 11 章那些错误全是 verifier 抓到的），但不免费。
- **层数乘以 pass 数**。一条九层的管线，每层十几个 pass，那是上百个 pass。

上游给了一些工具（`--mlir-disable-threading` 之类的开关、pass 级别的并行），但**"MLIR 管线容易变慢"这件事是结构性的**，不是某个实现问题。

### 四、调试体验仍然是个坑

这一点我在写这本书的过程中反复吃到，而且都写进了对应章节：

| 症状 | 真实原因 | 章 |
| --- | --- | --- |
| `arith.constant created with unregistered dialect` 然后 abort | Dialect 或 Pass 少了 `dependentDialects`——**两个不同机制** | 11、16 |
| fold 返回了属性但 IR 没变，无任何提示 | 少了 `hasConstantMaterializer` | 11 |
| `custom op 'transform.structured.match' is unknown` | 漏了 `registerAllExtensions`，**不是版本问题** | 18 |
| pattern 互逆时**挂住**，而不是报"没收敛" | `maxNumRewrites` 默认无上限 | 14 |
| `expects 0 loop results`（和真正的错误完全无关） | `tile_sizes = [4,4]` 写错了，正确是 `tile_sizes [4, 4]` | 21 |
| `Dialect 'cf' not found` 出现在 **JIT 的解析阶段** | 管线里少了 `--convert-cf-to-llvm` | 24 |
| `missing 'LLVMTranslationDialectInterface' registration` | 少了 `registerAllToLLVMIRTranslations` | 25 |
| 匿名命名空间里的分析类直接 abort | 要 `MLIR_DEFINE_EXPLICIT_INTERNAL_INLINE_TYPE_ID` | 19 |
| `RegionBranchOpInterface` 编译通过但**行为静默错误** | 默认实现返回空，必须显式列进 `DeclareOpInterfaceMethods` | 11 |

把这张表看成一个整体，能看出一个共同的形状：**这些错误信息说的都不是真正的原因。** 有几条甚至根本不报错（fold 静默失效、接口默认实现静默返回空）——那两种最难查。

MLIR 在这方面比几年前好了很多（`declarePromisedInterface` 就是一个专门为此加的 API，本章前面刚讲过），但离"报错直接告诉你该改哪一行"还差得远。**这本书里那么多篇幅花在"我踩了什么坑"上，不是我偏好写坑，是这些坑至今仍然要靠人记。**

### 五、什么情况下你不该用 MLIR

也得说清楚。下面这几种情况，MLIR 大概是负担而不是帮助：

- **你只要做一个简单的解释器或字节码 VM。** MLIR 的全部价值在"多层表示之间的变换"，你只有一层的话，构建时间和学习成本全是白付的。
- **你的语言语义和 LLVM IR 差得不多。** 那直接生成 LLVM IR，省掉一整层。
- **你要优化的信息在 LLVM IR 里还在。** 这条是第 27 章 flang 的那个判断标准反过来用：先问"我想做的优化，在现有的 IR 上问得出来吗"。问得出来就不需要新一层。
- **你的团队规模撑不住。** 一个方言的完整配套（`.td`、verifier、自定义 assembly、canonicalization、conversion pattern、类型转换、lit 测试）我们在第 9 到 11 章走过一遍。乘以你打算造的层数，再乘以长期维护。ClangIR 那 252 条是有一个活跃社区在推的情况下的数字。
- **你需要的东西上游已经有了。** 这条最容易被忽略，因为造一个新方言比读懂一个现有方言有意思得多。

反过来，值得用的信号很集中：**你有一个领域特定的高层表示，它带着的信息在通用 IR 里会丢掉，而且你要在那个信息上做多轮变换。** 这句话正好是这本书里 `pix` 存在的全部理由——`!pix.kernel<3x3>` 把核尺寸放进类型（第 9 章），第 21 章 tile 的时候那个尺寸决定了 halo 是几圈。降到循环之后，这个信息只能靠分析去猜。

## 这本书讲完了什么

最后把二十八章串一遍，不是复述目录，而是把那条主线拎出来。

**第一部分（1–8 章）讲的是"MLIR 是什么"。** 核心是三件事：一切都是 op（有 region、有属性、有类型），一切都可扩展，以及**渐进式下降**——不要一步从源码跳到机器码，每一步只解决一类问题。

**第二部分（9–14 章）讲的是"怎么造一个方言"。** 从 ODS 写 op，到 trait 与 interface 的区别（第 10 章那句"接口让不相关的方言共享变换"在这一章兑现了），到 fold 与 canonicalize 的分工，到 pass 与分析的框架，到 pattern 引擎的工作方式。

**第三部分（15–19 章）讲的是"变换"。** DRR 和 PDLL 让 pattern 变成声明式的，Dialect Conversion 的四态合法性和类型转换是跨方言下降的骨架，Transform 方言把"调度"本身变成了 IR，MLIR 自带的那几样分析（支配、副作用、数据流）是这一切的前提。

**第四部分（20–25 章）讲的是"落地"。** `linalg` 的 indexing map 把迭代空间显式化，于是 tiling 和融合能通用地实现；bufferization 把值语义换成内存语义；vector 处理宽度和 mask；最后落到 LLVM 真的 JIT 跑出 `[[22, 44], [66, 88]]`，或者落到 PTX。

**第五部分（26–28 章）讲的是"真实世界"。** Triton 把性能关键信息（layout）放进类型，并把隐性成本（`convert_layout`）做成一个可优化的 op；IREE 和 flang 给出了"造几层方言"的两个相反答案，以及判断标准；ClangIR 证明了这套东西能用在最硬的地方，同时用 252 条缺口诚实地标出了代价。

如果只能留一句话：

> **MLIR 的价值不是"又一个 IR"，是"让你能在恰当的抽象层级上表达每一个决策，并且让这些决策能被系统性地优化"。**

这句话的每一个部分在这本书里都有具体的兑现。"恰当的层级"——第 20 章 `pix` → `linalg` 而不是 → `arith`；"表达决策"——第 26 章 Triton 把 layout 放进类型、把转换成本做成 op；"系统性优化"——第 18 章 Transform 方言把调度变成 IR，第 21 章 tile 和融合对所有实现了 `TilingInterface` 的 op 一视同仁。

至于代价：**层是有成本的，方言是会碎的，管线是会慢的，错误信息是会骗人的。** 这些不是将来会消失的过渡问题，是这个设计的另一面。知道它们，是用好它的前提。

接下来该做什么？附录 C 是一张源码导览地图——想看某个机制去 `mlir/` 的哪个目录。但更实际的建议是：**挑一个你自己的领域，按第 9 到 11 章的路子造一个最小方言，写三个 op、两个 fold、一条 canonicalize pattern，让 lit 测试跑绿。** 这本书里所有的坑你都会重新踩一遍，但那时候你手上有一张写着它们的表。

## 小结

- **ClangIR 的处境和前面几章的项目性质不同**：C/C++ 已经有一条走了二十年的成熟路，它是往中间插一层，所以必须和既有实现输出等价、不能要求用户改任何东西。看它怎么落地比看它成不成功有价值。
- **读默认值，不要只读"在不在树里"**。`cir` 方言在 LLVM 23.1.2 的树里，但 `FrontendOptions.h` 的初始化列表是 `UseClangIRPipeline(false)`；而且即便开了 `-fclangir`，`ClangIREnableIdiomRecognizer(false)`、`ClangIRLibOptEnabled(false)`——**那两个最能体现 CIR 价值的 pass 也还默认关着**。
- **CIR 的 125 个 op 说明了它图什么**：`cir.vtable.get_virtual_fn_addr`、`cir.dyn_cast`、`cir.array.dtor`、`cir.base_class_addr`、`cir.cleanup.scope`、`cir.await`、`cir.if`——这些 C++ 层面的事实到了 LLVM IR **不是"信息少一点"，是问不出来了**（虚调用变成 GEP + load，`dynamic_cast` 变成一次 call，源码的 `if` 变成四个基本块）。
- **`cir-flatten-cfg` 就是我们的 `scf` → `cf`（第 24 章）**，而 `cir.switch.flat`/`cir.resume.flat` 这两个 `.flat` 后缀是压平后的形式——同一个方言里用 op 名分层，和第 27 章 `stream.tensor/async/cmd` 是同一手法（类型系统没变，就不必分方言）。
- **`cir-idiom-recognizer` 是一个往上抬抽象的 pass**（`summary` 用的词是 "**Raise**"），把 `std::` 容器和库调用认回成 CIR op，再由 `cir-lib-opt` 优化。这在 LLVM IR 上做不了：内联和 SROA 之后，"这是 `std::find`"这个信息**已经没有了**，不是难恢复。这是"高层表示值得存在"的最一般形式——和第 20 章不直接降到循环是同一个理由。
- **本书最重要的兑现：flang 和 ClangIR 共用同一份 OpenACC 实现，耦合点是一个类型接口。** 两边的文件对称（`FIROpenACCTypeInterfaces.h` / `CIROpenACCTypeInterfaces.h`），`struct` 甚至同名（`OpenACCPointerLikeModel`），都继承 `mlir::acc::PointerLikeType::ExternalModel<...>`。第 10 章"接口让不相关的方言共享变换"在这里落地——而且是在**两个生产级前端**的规模上。
- **补讲的机制是 `ExternalModel`**：把接口实现从类型定义里分离出来，`Type::attachInterface<Model>(context)` 运行时挂上，"**does not require modifying the definition of the type class itself**"。这是"上游的接口 + 你的类型"这种组合唯一的接法。配套用 `declarePromisedInterface`——文档明说"forgetting to register an external model can lead to bugs which are hard to track down"，失败模式和第 18 章漏 `registerAllExtensions` 同源。文档也建议这个机制最好由**接口的拥有者**来用。
- **约束按接口措辞，有真实报错为证**：`'acc.copyin' op operand #0 **must be any pointer or mappable**, but got 'i32'`。`memref<10xf32>` 和 `!llvm.ptr` 这两个毫无关系的类型都能当 `varPtr`（本章 `mlir-opt` 跑过），`i32` 被拒。加一个新前端只需写一个 `ExternalModel`，`acc` 那边一行不改。
- **`-fclangir` 已经带来了老路给不了的东西**：`warn_drv_openacc_without_cir` 明说 clang 的 OpenACC 不开 CIR 就"no runtime behavior"。这解释了 CIR 为什么能进树——它不是"把老路重做一遍更漂亮"。而这条链的上游正是第 27 章说的：flang 为自己推动建了 `acc` 方言，ClangIR 几乎白拿。
- **"用 MLIR 做一个前端"的工作量被系统性低估**。`MissingFeatures.h` 有 **252** 条 `static bool ... { return false; }`，覆盖 address space、linkage、协程、CXXABI、atomic、全局构造函数、调用约定。MLIR 省掉的是 IR 基础设施；**语言语义本身的复杂度一分不减**。（这个技巧本身也值得抄：改成 `return true` 的那天，编译器会在所有需要处理的地方报错，比 `grep TODO` 可靠得多。）
- **方言碎片化没有技术解**，它是"人人都能造方言"的直接后果。最清楚的证据是"结构化控制流压平"这件事上游和 ClangIR 各写了一遍。能缓解的只有社会性手段——往上游推、复用接口（本章 OpenACC 就是好例子）。第 27 章那四个问题不能消除碎片化，但能让你不去贡献新的碎片。
- **编译时间和调试体验是结构性的坑**。层数乘 pass 数、pattern 要跑到不动点、verifier 默认每个 pass 后都跑。调试那张表里九条真实错误的共同形状是：**报错说的都不是真正的原因**，其中两种（fold 静默失效、接口默认实现静默返回空）根本不报错。
- **不该用 MLIR 的信号**：只有一层（简单解释器/字节码 VM）；语义和 LLVM IR 差不多；**你要优化的信息在现有 IR 里还在**；团队撑不住一整套方言配套的长期维护；上游已经有了。反过来值得用的信号很集中：**有一个领域特定的高层表示，它带的信息在通用 IR 里会丢，而且你要在那个信息上做多轮变换**——这正是 `!pix.kernel<3x3>`（第 9 章把核尺寸放进类型）到第 21 章 halo 那条线的全部理由。
- **全书一句话**：MLIR 的价值不是"又一个 IR"，是**让你能在恰当的抽象层级上表达每一个决策，并且让这些决策能被系统性地优化**。代价是：层有成本、方言会碎、管线会慢、错误信息会骗人——这些是设计的另一面，不是会消失的过渡问题。
