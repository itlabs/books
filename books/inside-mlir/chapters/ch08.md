# 第 8 章 ODS（一）：用 TableGen 声明 Op、参数、结果与 assemblyFormat

## 这一章想让你带走什么

<div class="goal-box">
<p>第 7 章你写了 8 行 ODS，换来一个能用的 <code>pix.add</code>。这一章把那 8 行拆开，逐项讲清 <strong>ODS（Operation Definition Specification）</strong>：<code>arguments</code> / <code>results</code> 怎么声明类型约束、<code>assemblyFormat</code> 那套小语言怎么写、region 怎么在 ODS 里表达、以及 TableGen 到底替你生成了什么（<strong>七个 op 生成两千多行 C++</strong>，我们会直接把它调出来看）。</p>
<p>同时把 pix 的 op 集补齐：<code>mul</code>、<code>scale</code>、<code>transpose</code>、<code>reduce</code>、以及带 region 的 <code>pipeline</code> + <code>yield</code>。每个 op 都挑了一个不同的知识点——<code>scale</code> 演示"两个操作数类型不同怎么办"，<code>transpose</code> 演示"结果类型和输入不一样"，<code>pipeline</code> 演示 region 与隐式终结符。</p>
<p>最后一节最重要：<strong>ODS 拦得住什么、拦不住什么。</strong>你会看到 <code>pix.transpose</code> 把 4×8 "转置"成 4×8 照样通过验证——这不是 bug，是我们还没写 verifier（第 10 章）。分清"声明能自动保证的"和"必须自己写的"，是用好 ODS 的关键。</p>
</div>

## 一份声明，两千多行 C++

先看投入产出比。pix 现在有 7 个 op，`.td` 文件一百多行。跑一遍 `mlir-tblgen` 看生成了什么规模：

```bash
mlir-tblgen -gen-op-decls -I $LLVM_SRC/mlir/include -I include include/Pix/PixOps.td | wc -l   # 1024
mlir-tblgen -gen-op-defs  -I $LLVM_SRC/mlir/include -I include include/Pix/PixOps.td | wc -l   # 1171
```

两千多行。它们不是模板套话，是实打实的东西。把 `AddOp` 那一段截出来看关键成员：

```cpp-norun
class AddOp : public ::mlir::Op<AddOp, /* 一长串 trait */ ...> {
public:
  static constexpr ::llvm::StringLiteral getOperationName() { … }   // "pix.add"

  // 类型化的访问器：不是 getOperand(0)，而是按名字取，且类型已经收窄
  ::mlir::TypedValue<::mlir::TensorType> getLhs() { … }
  ::mlir::TypedValue<::mlir::TensorType> getRhs() { … }
  ::mlir::OpOperand &getLhsMutable() { … }          // 想改这条 def-use 边时用它

  // 五个 build 重载，从"什么都给"到"能推的都推"
  static void build(OpBuilder &, OperationState &, Type result, Value lhs, Value rhs);
  static void build(OpBuilder &, OperationState &, Value lhs, Value rhs);  // ← 结果类型可推断
  static void build(OpBuilder &, OperationState &, TypeRange resultTypes, Value lhs, Value rhs);
  static void build(OpBuilder &, OperationState &, TypeRange, ValueRange, ArrayRef<NamedAttribute>);
  static void build(OpBuilder &, OperationState &, ValueRange, ArrayRef<NamedAttribute>);

  ::llvm::LogicalResult verifyInvariants();                          // trait 与类型约束的检查
  static ::mlir::ParseResult parse(OpAsmParser &, OperationState &);  // 由 assemblyFormat 生成
  void print(OpAsmPrinter &);                                        // 同上
};
```

三个观察，每个都对应后面要讲的一件事：

1. **访问器带名字也带类型**：`getLhs()` 返回 `TypedValue<TensorType>`，不是裸 `Value`。名字来自 `$lhs`，类型收窄来自 `F32Tensor` 这个约束。写 pattern 时（第 14 章）这一点会让代码干净很多。
2. **有一个不要结果类型的 `build`**：因为 `SameOperandsAndResultType` 声明了"结果类型 = 操作数类型"，TableGen 于是能生成一个"帮你推断"的重载。**trait 不只是检查，它还影响生成什么 API。**
3. **`parse` 和 `print` 是 `assemblyFormat` 编译出来的**——你写的那行格式字符串，变成了两个真正的函数。

## `arguments` 与 `results`：类型约束从哪来

```tablegen
let arguments = (ins F32Tensor:$lhs, F32Tensor:$rhs);
let results = (outs F32Tensor:$result);
```

`(ins …)` / `(outs …)` 里的每一项是 **约束:$名字**。约束这个词要理解准：它不是"类型"，而是**对类型的谓词**。`F32Tensor` 的意思是"元素类型为 f32 的张量"，形状没管；`AnyRankedTensor` 是"有阶的张量，元素类型随意"。

常用的一批都在 `mlir/include/mlir/IR/CommonTypeConstraints.td` 里，值得翻一遍：

| 约束 | 含义 |
| --- | --- |
| `F32` / `AnyFloat` / `AnyInteger` | 标量 |
| `Index` | `index` 类型（第 4 章讲过它不是 `i64`） |
| `F32Tensor` / `AnyTensor` / `AnyRankedTensor` | 张量，逐级放宽 |
| `TensorOf<[F32, F16]>` | 自己组合元素类型 |
| `MemRefOf<[F32]>` | memref |
| `AnyType` | 什么都行（少用，等于放弃检查） |
| `Variadic<F32Tensor>` | 数量不定的同类操作数 |
| `Optional<F32>` | 可有可无的一个操作数 |

属性也写在 `arguments` 里（这点第一次见会觉得奇怪，但它符合 MLIR 的模型：操作数与属性都是 op 的"输入"）：

```tablegen
let arguments = (ins F32Tensor:$image,
                     I64Attr:$radius,                          // 必须给
                     DefaultValuedAttr<I64Attr, "1">:$stride,   // 不给就是 1
                     UnitAttr:$fast);                          // 在/不在就是全部信息
```

### 当操作数类型互不相同：`AllTypesMatch`

`pix.scale` 是"整张图乘一个标量"，两个操作数一个是张量一个是标量，`SameOperandsAndResultType` 显然用不了。换成只约束需要相等的那一对：

```tablegen
def Pix_ScaleOp : Pix_Op<"scale", [Pure, AllTypesMatch<["image", "result"]>]> {
  let arguments = (ins F32Tensor:$image, F32:$factor);
  let results = (outs F32Tensor:$result);
  let assemblyFormat = "$image `,` $factor attr-dict `:` type($result)";
}
```

这条声明是真的在干活。故意写错一个：

```mlir-norun
%s = "pix.scale"(%a, %f) : (tensor<4x8xf32>, f32) -> tensor<8x4xf32>
```

`pix-opt` 的报错（实测）：

```
error: 'pix.scale' op failed to verify that all of {image, result} have same type
```

<div class="note">
<strong>还有一对亲戚：<code>TypesMatchWith</code></strong>
<p>当两个类型不是"相等"而是"能算出来"的关系时（例如"结果是操作数的元素类型"、"结果是操作数去掉最后一维"），用 <code>TypesMatchWith&lt;说明, 源参数, 目标参数, 变换表达式&gt;</code>。它比手写 verifier 划算，因为顺带还能让 <code>assemblyFormat</code> 少打印一个类型。</p>
</div>

## `assemblyFormat`：把糖配出来

第 3 章讲过自定义格式只是糖，而通用格式才是真相。`assemblyFormat` 就是配这个糖的小语言：

```tablegen
let assemblyFormat = "$lhs `,` $rhs attr-dict `:` type($result)";
```

元素表：

| 写法 | 含义 |
| --- | --- |
| `$name` | 打印/解析这个操作数、属性或 region |
| `type($name)` | 那个值的类型 |
| `` `,` `` `` `:` `` `` `to` `` | 反引号里是字面量（标点或关键字） |
| `attr-dict` | 可丢弃属性字典。**几乎必须有**，否则属性没地方打印 |
| `functional-type($ins, $outs)` | 打印成 `(输入类型) -> 输出类型` |
| `(… )?` 与 `^` | 可选组；`^` 标记"锚"，锚有值整组才打印 |

三个例子，对应三种常见情况：

```tablegen
// ① 结果类型与操作数相同 → 只打印一个类型
let assemblyFormat = "$image `,` $factor attr-dict `:` type($result)";

// ② 结果类型与操作数不同 → 两个都要打印，中间用字面量分开
let assemblyFormat = "$image attr-dict `:` type($image) `to` type($result)";

// ③ 操作数可有可无 → 可选组 + 锚
let assemblyFormat = "attr-dict ($values^ `:` type($values))?";
```

① 是 `pix.scale`：只写 `type($result)` 也能解析回来，因为 `AllTypesMatch` 告诉解析器 `image` 的类型与它相同。**约束让 IR 更短，这是声明式的额外红利。**

② 是 `pix.transpose`：`tensor<4x8xf32> to tensor<8x4xf32>`，两个类型都得写，否则无法还原。

③ 是 `pix.yield`：有值时打印 `pix.yield %t : tensor<4x4xf32>`，没值时只打印 `pix.yield`。

<div class="warn">
<strong><code>attr-dict</code> 漏了会怎样</strong>
<p>不会立刻报错，但任何人给你的 op 挂一个可丢弃属性（第 2 章那种 <code>{my_pass.visited = true}</code>）之后，打印出来就丢了——于是 round-trip 失败，而且失败点离真正的原因很远。<strong>写 <code>assemblyFormat</code> 时先把 <code>attr-dict</code> 放进去</strong>，就像写 C 结构体先想好对齐一样。</p>
</div>

什么时候放弃 `assemblyFormat`？当格式依赖运行时信息、或者你要打印派生出来的东西（比如把 indexing map 渲染成人类可读的形式）。那就改用 `let hasCustomAssemblyFormat = 1;` 然后在 `.cpp` 里手写 `parse`/`print`。**能用声明式就别手写**——手写的那两个函数必须互为逆运算，出 bug 的方式非常隐蔽。

## region 在 ODS 里怎么写

`pix.pipeline` 是个容器 op：自己不算任何东西，只把一段处理流程围起来，好让后面的变换把它当整体处理。

```tablegen
def Pix_PipelineOp : Pix_Op<"pipeline", [
    SingleBlockImplicitTerminator<"YieldOp">,
    RecursiveMemoryEffects]> {
  let results = (outs F32Tensor:$result);
  let regions = (region SizedRegion<1>:$body);
  let assemblyFormat = "attr-dict `:` type($result) $body";
}
```

四处都值得说：

- **`let regions = (region SizedRegion<1>:$body)`**：声明一个 region，且它只能有 1 个 block。想要多块就用 `AnyRegion`，想要多个 region 就写多项（`scf.if` 就是两个）。
- **`SingleBlockImplicitTerminator<"YieldOp">`**：单块 + 终结符固定是 `pix.yield`，而且**允许你在文本里省略不写**，框架会替你插。
- **`RecursiveMemoryEffects`**：这个 op 自己没有副作用，它的副作用**取决于 region 里的内容**。少了它，通用 pass 只能假设最坏情况（第 5 章）。
- **它没有 `IsolatedFromAbove`**：所以 body 里可以直接引用外面的值。代价是它不能被直接抽成独立函数——第 25 章做 GPU kernel outlining 时需要那个 trait，到时候会看到区别。

配套的终结符：

```tablegen
def Pix_YieldOp : Pix_Op<"yield", [Pure, ReturnLike, Terminator,
                                   HasParent<"PipelineOp">]> {
  let arguments = (ins Variadic<F32Tensor>:$values);
  let builders = [OpBuilder<(ins), [{ /* 什么都不用做：造一个空的 yield */ }]>];
  let assemblyFormat = "attr-dict ($values^ `:` type($values))?";
}
```

`HasParent<"PipelineOp">` 声明"我只能出现在 pipeline 里"。而那个**零参数 builder** 不是可选的装饰——它是被编译器逼出来的。我第一次写的时候没加，编译直接失败：

```
error: no matching function for call to ‘mlir::pix::YieldOp::build(mlir::OpBuilder&, mlir::OperationState&)’
```

原因是隐式终结符机制要能用 `build(builder, state)` 凭空造一个终结符出来，而我的 yield 要求一个操作数。上游 `scf.yield` 用的是完全一样的招（`let builders = [OpBuilder<(ins), [{ /* nothing to do */ }]>];`）——**遇到这类"框架要求某个重载存在"的报错，去上游找一个同类 op 抄它的写法，比猜快得多。**

### 隐式终结符真的被插进去了

写一个空 body 的 pipeline，自定义格式打印出来是空的：

```mlir-norun
%out = pix.pipeline : tensor<4x4xf32> {
}
```

但通用格式会暴露真相（实测）：

```
    %0 = "pix.pipeline"() ({
      "pix.yield"() : () -> ()
    }) : () -> tensor<4x4xf32>
```

**`pix.yield` 确实存在**，只是自定义格式在打印 region 时把"没有操作数的隐式终结符"省略了。第 3 章那句"通用格式才是真相"，这里又应验一次。

## 补齐后的 pix

现在 7 个 op 都能用了。一段把它们全用上的 IR（`pix-opt` 的真实输出）：

```mlir
// RUN: pix-opt %s
func.func @all_ops(%a: tensor<4x8xf32>, %b: tensor<4x8xf32>, %f: f32)
    -> (tensor<4x8xf32>, tensor<8x4xf32>, f32) {
  %m = pix.mul %a, %b : tensor<4x8xf32>
  %s = pix.scale %m, %f : tensor<4x8xf32>
  %t = pix.transpose %s : tensor<4x8xf32> to tensor<8x4xf32>
  %r = pix.reduce %s : tensor<4x8xf32> -> f32
  return %s, %t, %r : tensor<4x8xf32>, tensor<8x4xf32>, f32
}

func.func @with_pipeline(%a: tensor<4x4xf32>, %b: tensor<4x4xf32>) -> tensor<4x4xf32> {
  %out = pix.pipeline : tensor<4x4xf32> {
    %x = pix.add %a, %b : tensor<4x4xf32>
    %y = pix.mul %x, %x : tensor<4x4xf32>
    pix.yield %y : tensor<4x4xf32>
  }
  return %out : tensor<4x4xf32>
}
```

> 注意这段 IR 里的 `pix.add`、`pix.mul` 在 pipeline 的 region 内部，却直接用了函数的参数 `%a`、`%b`——因为 `pix.pipeline` 不是 `IsolatedFromAbove`。第 2 章讲的"内层 region 可以引用外层值"，在你自己的 op 上生效了。

再确认一次免费的优化。`pix.reduce` 声明了 `Pure`，所以没人用它的结果时它会被删掉（实测）：

```mlir
// RUN: pix-opt %s --canonicalize
func.func @dead_reduce(%a: tensor<4x4xf32>) {
  %r = pix.reduce %a : tensor<4x4xf32> -> f32
  return
}
```

输出里 `pix.reduce` 消失了，只剩一个 `return`。

## 声明拦得住什么，拦不住什么

这是本章最该记住的一节。ODS 的声明能自动生成一批检查，但**边界很清楚**。

**拦得住**（`verifyInvariants()` 里自动生成）：

- 操作数/结果的**类型约束**：`F32Tensor` 不满足 → `operand #0 must be tensor of 32-bit float values, but got 'tensor<4x4xi32>'`
- 操作数/结果的**个数**
- trait 带的结构检查：`SameOperandsAndResultType`、`AllTypesMatch`、`HasParent`、`SingleBlockImplicitTerminator`（单块）
- 属性是否存在、类型对不对

**拦不住**——下面两个实测例子都**通过了验证**，而它们显然是错的：

```mlir-norun
// ① 把 4×8 "转置"成 4×8：形状根本不是转置关系
func.func @bogus_transpose(%a: tensor<4x8xf32>) -> tensor<4x8xf32> {
  %t = pix.transpose %a : tensor<4x8xf32> to tensor<4x8xf32>
  return %t : tensor<4x8xf32>
}
```

```mlir-norun
// ② pipeline 声明返回一张图，但 body 什么都没 yield
func.func @empty_pipeline() -> tensor<4x4xf32> {
  %out = pix.pipeline : tensor<4x4xf32> {
  }
  return %out : tensor<4x4xf32>
}
```

两段都干干净净地过了 `pix-opt`。原因很简单：**没有人声明过这些关系**。

> 这两块标的是 `mlir-norun`，不带"在 Compiler Explorer 打开"的按钮，也不进随书校验——因为它们要的是**第 8 章这一刻**的 pix 方言。`code/pix/` 里放的是全书结束时的终态，第 10 章补上的 verifier 和接口正好会把这两段拦下来（那就是第 10 章 `invalid_verifiers.mlir` 的内容）。想亲手复现"它居然过了"，把 `PixOps.cpp` 里 `verify()` 和 `getSuccessorInputs` 相关的部分注释掉重编即可。

- 例 ①：ODS 只知道两个类型都得是 `F32Tensor`，"结果形状必须是输入形状的逆序"这条语义只在你脑子里。
- 例 ②：`SingleBlockImplicitTerminator` 只管"有没有终结符"，不管"终结符交出的值与 op 的结果对不对齐"。

<div class="keypoint">
<strong>对比第 2 章那个 <code>scf.if</code>：同样的错误，它拦住了。</strong>
<p>回忆第 2 章的实验：<code>scf.if</code> 的 else 分支什么都不 yield 时，报错是 <code>'scf.if' op along control flow edge … region successor needs 1 inputs</code>。为什么 <code>scf.if</code> 能查，<code>pix.pipeline</code> 不能？<strong>因为 <code>scf.if</code> 声明了 <code>RegionBranchOpInterface</code></strong>（第 5 章那张问答图），通用机制于是能问它"你的 region 之间怎么传值"，并据此检查个数与类型。</p>
<p>这就是第 5 章那句话的实际含义再一次显形：<strong>你声明了什么，框架才能替你做什么。</strong>第 10 章我们有两条路可选——手写 <code>verify()</code>，或者去实现 <code>RegionBranchOpInterface</code> 白拿这套检查。两条都会走一遍，然后你就知道该怎么选了。</p>
</div>

## 动手

```bash
# 1. 亲眼看生成的代码（把 $LLVM_SRC 换成你的 llvm-project 路径）
mlir-tblgen -gen-op-decls -I $LLVM_SRC/mlir/include -I include include/Pix/PixOps.td | less

# 2. 只看某个 op 生成了什么
mlir-tblgen -gen-op-decls -I $LLVM_SRC/mlir/include -I include include/Pix/PixOps.td \
  | sed -n '/^class TransposeOp /,/^};/p'

# 3. 顺手生成方言文档（ODS 里的 summary/description 会变成 markdown）
mlir-tblgen -gen-dialect-doc -dialect=pix -I $LLVM_SRC/mlir/include -I include \
  include/Pix/PixOps.td
```

**改一改。** 每一项都会让你对 ODS 的边界更清楚：

1. **删掉 `pix.add` 的 `attr-dict`**，重新编译，然后给它挂个属性试试：`%s = "pix.add"(%a, %b) {my.tag = 1 : i64} : …`，再 round-trip。属性丢了吗？这就是上面那个 `warn` 框在说的事。
2. **给 `pix.scale` 的 `factor` 加一个默认值属性版本**：把 `F32:$factor` 改成属性 `F32Attr:$factor`（于是系数必须是编译期常量），看 `assemblyFormat` 要怎么改、生成的 `build` 重载变成什么样。想一想：什么时候该用属性、什么时候该用操作数？（提示：能不能是运行时算出来的值）
3. **把 `pix.transpose` 的 trait 里加上 `SameOperandsAndResultType`**，重新编译并跑本章那段 `bogus_transpose`。这次拦住了吗？拦住的是"形状必须逆序"还是"形状必须相同"？——**这说明选错 trait 比不选更糟**。
4. **给 `pix.reduce` 去掉 `Pure`**，重跑 `--canonicalize`，看没人用的 reduce 还会不会被删。第 5 章的结论在你自己的 op 上复现一遍。
5. **把 `pix.yield` 的零参数 builder 删掉**，编译，看那条 `no matching function for call to 'YieldOp::build(OpBuilder&, OperationState&)'`。记住它——以后给任何带隐式终结符的 op 写终结符时都会遇到。

---

**这一章的要点**

- ODS 是一份声明，`mlir-tblgen` 把它变成**两千多行 C++**：类型化访问器、多个 `build` 重载、`verifyInvariants()`、以及由 `assemblyFormat` 编译出来的 `parse`/`print`。
- **trait 不只是检查，还影响生成什么 API**：`SameOperandsAndResultType` 让 TableGen 多生成一个"不用给结果类型"的 `build`。
- `arguments`/`results` 里写的是**类型约束**（对类型的谓词），不是具体类型；属性也写在 `arguments` 里。约束表在 `mlir/include/mlir/IR/CommonTypeConstraints.td`。
- 操作数类型互不相同时用 **`AllTypesMatch`**（只约束需要相等的那几个），关系更复杂时用 **`TypesMatchWith`**。约束还能让 `assemblyFormat` 少打印一个类型。
- `assemblyFormat` 里 **`attr-dict` 几乎必须有**，漏了会在很远的地方以 round-trip 失败的形式报复你。
- region 用 `let regions = (region SizedRegion<1>:$body)` 声明；`SingleBlockImplicitTerminator<"YieldOp">` 允许省略终结符，但**终结符会被真的插进 IR**（通用格式可见）；这类终结符**必须提供零参数 builder**，否则编译不过。
- **两套平行的 include 世界**：ODS 里 include 了某个接口的 `.td`，C++ 头文件就要 include 对应的 `.h`。漏了会在生成的 `.inc` 里报"某接口不是 mlir 的成员"，误导性很强。
- **最重要的边界**：ODS 拦得住类型约束、个数、trait 的结构检查；**拦不住你脑子里的语义**。`pix.transpose` 把 4×8 转置成 4×8、`pix.pipeline` 声明有结果却什么都不 yield——两者都顺利通过。而同样的错误 `scf.if` 能拦住，**因为它声明了 `RegionBranchOpInterface`**。

**pix 进度**：7 个 op（add / mul / scale / transpose / reduce / pipeline / yield），涵盖逐点、标量缩放、转置、归约、region 容器五种形态；类型约束与 trait 自动生成的检查已生效，但"形状关系""yield 对齐"这类语义还没人守。

下一章补上 ODS 的另一半：**自定义类型与属性**。我们会给 pix 造一个参数化类型 `!pix.kernel<3x3>`（stencil 权重）和一个枚举属性 `#pix.border<clamp>`（边界处理方式），再用它们定义真正的邻域运算 `pix.convolve`——那是第四部分做 tiling 与向量化时的主角。
