第 2 章 SIMT 与 SIMD：一条指令，一大群线程

这一章想让你带走什么

上一章说 GPU 线程"变笨了"——它们齐步走同一条指令。这一章讲清那个机制到底是什么：SIMT（单指令多线程）。你会看到它和你可能用过的 SIMD（单指令多数据）是什么关系，以及一个绕不开的代价——warp 分歧（divergence）：当一群齐步走的线程遇到 if 各奔东西时会发生什么。

读完你能亲手跑一个浏览器里的模拟器，看到分歧是怎么让代码悄悄变慢一倍的。

最后有一节"反转"：我们拿 Intel GPU 当样本，掀开 SIMT 这层抽象，看看底下那台向量机长什么样——顺便解释一个 CUDA 里根本不存在的变量：SIMD 宽度是编译期选出来的。

你可能已经见过它的哥哥：SIMD

如果你在 CPU 上做过性能优化，也许写过或读过 SIMD 代码。SIMD（Single Instruction, Multiple Data，单指令多数据）的意思是：一条 CPU 指令同时对一排数据做同样的运算。比如 AVX 指令一次能加 8 个 float：

C++ 🔗 在 Compiler Explorer 打开
// CPU 的 SIMD：一条指令加 8 个 float（AVX）
#include <immintrin.h>
#include <cstdio>

int main() {
    float a[8] = {1, 2, 3, 4, 5, 6, 7, 8};
    float b[8] = {10, 20, 30, 40, 50, 60, 70, 80};
    float c[8];

    __m256 va = _mm256_loadu_ps(a);     // 把 8 个 float 装进一个 256 位寄存器
    __m256 vb = _mm256_loadu_ps(b);
    __m256 vc = _mm256_add_ps(va, vb);  // 一条指令，8 个加法同时做
    _mm256_storeu_ps(c, vc);

    for (int i = 0; i < 8; ++i) printf("%.0f ", c[i]);  // 11 22 33 ... 88
    printf("\n");
}
本地编译运行：g++ -std=c++23 -O2 -Wall main.cpp && ./a.out

SIMD 很强，但写起来别扭：你得把数据手动打包进 __m256 这样的向量寄存器，用一套专门的 intrinsic 函数（_mm256_add_ps…），处理不够 8 个的"尾巴"，换个数据宽度还得重写。你写的是向量，不是标量——心智负担全在你身上。

一句话记住 SIMD 一条指令，一个"宽"寄存器里的多个数据，被同一个运算处理。宽度是硬件定死的（AVX 是 8 个 float，AVX-512 是 16 个）。是你（或编译器的自动向量化）负责把标量代码改写成向量形式。

GPU 的做法：SIMT——你写标量，硬件替你并起来

GPU 换了个思路。它让你照常写标量代码——就像上一章那个 c[i] = a[i] + b[i]，一个线程只管一个元素，读起来完全是普通的单线程代码。然后硬件在背后，把一组线程（NVIDIA 叫一个 warp，32 个线程；后面章节细讲）绑在一起，让它们同一时刻执行同一条指令，只是各自作用在自己的数据上。

这就是 SIMT（Single Instruction, Multiple Threads，单指令多线程）。

SIMD：你写向量
C++
// 数据要手动打包成向量
__m256 va = _mm256_loadu_ps(a);
__m256 vc = _mm256_add_ps(va, vb);
// 一个"线程"操作一整排数据
// 宽度写死在指令里
SIMT：你写标量
CUDA C++
// 照常写标量，像单线程
int i = threadIdx.x;
c[i] = a[i] + b[i];
// 硬件把 32 个这样的线程绑成
// 一个 warp，齐步执行同一条指令

结果是：SIMT 写起来像标量，跑起来像向量。 你不用管向量宽度、不用打包数据、不用处理尾巴，只描述"一个线程做什么"，硬件负责把成百上千个这样的线程编成一个个 warp 齐步跑。这就是为什么 GPU 代码看着比 SIMD 干净得多——复杂度被移进了硬件和编译器。

图 2-1　SIMT：你只写"一个线程做什么"，硬件把一组线程绑起来，让它们齐步执行同一条指令，各自作用于自己的数据

SIMT 的代价：warp 分歧

天下没有免费的抽象。SIMT 让你写标量的爽快，是建立在一个硬性约束上的：一个 warp 里的 32 个线程，任一时刻只能执行同一条指令。

那问题来了——如果代码里有 if，warp 里一半线程条件为真、一半为假，怎么办？它们要执行的可是不同的指令啊。

硬件的处理方式简单粗暴：两条分支都执行，但每条分支只让"该走这条路"的线程生效，其余线程暂时"关灯"（掩码屏蔽）。 也就是说，if 和 else 不再是二选一并行跑完，而是先跑 if（else 那批线程干等），再跑 else（if 那批线程干等）——串行化了！这就是 warp 分歧（warp divergence）。

CUDA C++
// 一个会造成 warp 分歧的 kernel
__global__ void diverge(float* x) {
    int i = threadIdx.x;
    if (i % 2 == 0) {        // 偶数线程走这里
        x[i] = expensive_a(x[i]);   // 奇数线程被"关灯"，干等
    } else {                 // 奇数线程走这里
        x[i] = expensive_b(x[i]);   // 换偶数线程"关灯"，干等
    }
    // 结果：这个 warp 的耗时 ≈ 分支A + 分支B，而不是 max(A, B)
}

在 CPU 上，分支预测让 if 几乎免费，你从不为写分支而心虚。在 GPU 上，warp 内的分歧是真金白银的性能损失：分支越多、越"参差不齐"，串行化越严重。这是上一章说的"GPU 直觉和 CPU 相反"的头号例子。

关键限定：分歧只在 warp 内部 才有代价 如果整个 warp 的 32 个线程都走同一条分支（比如按 warp 边界对齐地分工），那就没有分歧——大家还是齐步走，只是走的是同一条路。所以优化的方向不是"消灭所有 if"，而是"让走向不同的线程尽量落在不同的 warp 里"。这个"warp 是 32 个线程"的边界意识，第 6 章会专门讲。

动手：亲眼看分歧让代码变慢

下面这个模拟器能在浏览器里直接跑——点 ▶ 运行。它不真用 GPU，而是用 Python 忠实地模拟 SIMT 的执行规则：一个 warp 一次只能执行一条指令；遇到分支时，先让走 if 的线程执行（其余"关灯"），再让走 else 的执行。我们数"这个 warp 一共花了几个执行步（cycle）"，对比"全员走同一条路"和"参差不齐地分歧"两种数据，你会看到时间差。

Python 
# 模拟 SIMT：一个 warp 遇到 if/else 时如何串行化（warp 分歧）
WARP_SIZE = 8   # 真实 GPU 是 32，这里用 8 方便观察

def run_warp(values, if_cost=3, else_cost=3):
    """模拟一个 warp 执行 if(v>0){花 if_cost 步} else {花 else_cost 步}。
    返回这个 warp 实际消耗的执行步数。"""
    go_if   = [v for v in values if v > 0]     # 会走 if 分支的线程
    go_else = [v for v in values if v <= 0]    # 会走 else 分支的线程

    cost = 0
    if go_if:      # 只要 warp 里有任何线程走 if，整个 warp 就得为 if 花时间
        cost += if_cost
        print(f"  执行 if 分支：{len(go_if)} 个线程干活，{len(go_else)} 个被关灯干等")
    if go_else:    # 只要有任何线程走 else，整个 warp 再为 else 花一次时间
        cost += else_cost
        print(f"  执行 else 分支：{len(go_else)} 个线程干活，{len(go_if)} 个被关灯干等")
    return cost

print("情况一：全员走同一条分支（无分歧）")
uniform = [1, 2, 3, 4, 5, 6, 7, 8]          # 全部 > 0，都走 if
c1 = run_warp(uniform)
print(f"  → 这个 warp 花了 {c1} 步\n")

print("情况二：一半走 if、一半走 else（严重分歧）")
mixed = [1, -1, 2, -2, 3, -3, 4, -4]        # 正负交错
c2 = run_warp(mixed)
print(f"  → 这个 warp 花了 {c2} 步\n")

print(f"结论：同样 8 个线程、同样的活，分歧让耗时从 {c1} 步涨到 {c2} 步，慢了 {c2/c1:.0f} 倍。")
print("原因：if 和 else 被迫串行执行，而不是并行二选一。")

运行结果：

情况一：全员走同一条分支（无分歧）
  执行 if 分支：8 个线程干活，0 个被关灯干等
  → 这个 warp 花了 3 步

情况二：一半走 if、一半走 else（严重分歧）
  执行 if 分支：4 个线程干活，4 个被关灯干等
  执行 else 分支：4 个线程干活，4 个被关灯干等
  → 这个 warp 花了 6 步

结论：同样 8 个线程、同样的活，分歧让耗时从 3 步涨到 6 步，慢了 2 倍。
原因：if 和 else 被迫串行执行，而不是并行二选一。

看到了吗？同样的 8 个线程、同样的工作量，只因为它们走向不同，耗时就翻倍。请动手改一下：把 mixed 改成 [1, 2, 3, 4, 5, 6, 7, -1]（只有一个线程走 else），再运行——你会发现耗时还是 6 步！这揭示了分歧最反直觉的一点：哪怕 warp 里只有一个线程"不合群"，整个 warp 都要为那条分支付出完整代价。这也是为什么后面讲优化时，我们会那么在意"让一个 warp 里的线程尽量走同一条路"。

SIMT ≠ SIMD：三个关键区别

它们思路相通（都是一条指令驱动多份数据），但别混为一谈：

SIMD（CPU 向量） SIMT（GPU）
你写的代码 向量：手动打包、用 intrinsic 标量：像单线程，硬件替你并起来
分支怎么办 你得用掩码手动处理 硬件自动掩码，但会分歧串行化
宽度 写死在指令里（8、16…） 逻辑上任意多线程，硬件按 warp（32）打包调度
访存 通常要求连续 灵活，但合并访问才快（第 7 章）

一句话：SIMD 把并行的复杂度交给你，SIMT 把它藏进硬件——代价是你要理解 warp 这个"隐形的 32 人小队"，否则会在分歧和访存上莫名其妙地慢。 理解这个隐形小队，正是第 6 章的任务。

不过这张表是按"CPU 向量 vs NVIDIA GPU"画的。下一节我们换一家硬件看看——你会发现"宽度"那一行需要重写。

一个反转：Intel GPU 的 SIMT，底下是明写的 SIMD

上面那条分界线——"SIMD 是 CPU 的、SIMT 是 GPU 的"——是个教学用的简化。真相是：没有哪家 GPU 的硬件里真的有"SIMT 单元"。 三家的执行引擎都是向量机 + 执行掩码，SIMT 是硬件、编译器、驱动合起来给你维持的一层抽象。差别不在抽象的厚薄，而在这份维持工作由谁来干。

NVIDIA 把它糊得很严：warp 恒为 32，掩码和重汇聚由硬件自己维护（早期是分支重汇聚栈，Volta 之后换成收敛屏障），你在 SASS 里几乎看不到"宽度"这个概念。Intel 走了另一个极端：它把 SIMD 性质直接写在指令编码里。 所以 Intel GPU 是个特别好的观察样本——透过它，你能看见 SIMT 抽象底下那台向量机。

先把名词对齐

Intel 的 GPU 架构叫 Xe（用在 Arc 独显、集显和数据中心 GPU 上）。它的名词和 NVIDIA 是一一对应的，只是全都换了名字：

概念 NVIDIA 叫法 Intel Xe 叫法
一簇计算单元 + 局部内存 SM（流多处理器） Xe-core
执行向量指令的引擎 warp 调度器 + CUDA 核心 XVE（Xe Vector Engine，旧称 EU／执行单元）
齐步走的那一组 warp，恒 32 线程 一个硬件 thread，宽度 SIMD8／16／32
组内的一条通道 lane（通道） lane
组内共享的高速内存 shared memory SLM（Shared Local Memory）
每组私有的寄存器堆 寄存器文件 GRF（General Register File）

一个 Xe-core 里挂着多个 XVE（各代不同，公开资料里 Xe-HPG 是每 Xe-core 16 个、ALU 8 宽，数据中心的 Xe-HPC 是 8 个、ALU 16 宽），每个 XVE 又挂着若干个硬件 thread 轮转调度来掩盖延迟——在 SIMD 之上还叠了一层 SMT，思路和 CPU 超线程一样。

头号术语陷阱：Intel 说的 "thread" 不是 CUDA 说的 thread 在 Intel 的文档和 profiler 里，thread 指的是"一个 SIMD 宽度的 work-item 捆包"——它对应的是 CUDA 的 warp，不是 CUDA 的 thread。CUDA 的一个 thread 在 Intel 这边对应的是一条 lane（也就是一个 work-item）。看到"每个 XVE 有 8 个 thread"时，别理解成"只有 8 个线程"——那是 8 个 warp，按 SIMD16 算就是 128 个 work-item。

指令长什么样：宽度和掩码都是明文

这是最能说明问题的一处。看同一个 if 在两家的原生指令里留下的痕迹（两边都是示意，不是逐字的编译产物）：

NVIDIA SASS：宽度和掩码看不见
     ISETP.GT.AND P0, PT, R4, RZ, PT
@!P0 BRA `(.L_else)
     // 谓词 P0 只说"走不走"，
     // 32 这个宽度、以及哪些 lane
     // 开灯，都由硬件隐式管理
Intel Xe ISA：三样全写在指令里
       cmp (16|M0) (gt)f0.0 null:f  r4.0<1;1,0>:f  0x0:f
(f0.0) if  (16|M0) L_else L_endif
       // (16|M0) = 执行宽度 16、掩码起点 M0
       // f0.0    = 谓词，逐 lane 的开关
       // <1;1,0> = 寄存器区域描述符

右边这三样东西，任何写过 AVX-512 的人都会觉得眼熟：执行宽度对应 _mm512 那个 512；谓词 flag 对应 AVX-512 的掩码寄存器 k0–k7；寄存器区域描述符 <垂直步长;宽度,水平步长> 干的是 gather/scatter 那类事，让一条指令能按跨步取寄存器里的一片数据。换句话说，Intel GPU 的 ISA 比起 CUDA，更像一条加了显式掩码的 AVX 指令。

核心观念 Intel GPU 的硬件是 SIMD（宽度和掩码是指令字段），暴露给你的模型是 SPMD（你写标量 kernel）。中间那道翻译由编译器完成：它把一批 work-item 横向"缝"进 SIMD lane。文献里这套做法叫 SPMD-on-SIMD（也写作 SIMT-on-SIMD；编译器技术上的名字是整函数向量化，whole-function vectorization）。
别急着下"NVIDIA 也一样，只是不给你看"这个结论 更准确的说法是：维持"SIMT 幻觉"的总工作量是一定的，三家把它切给了不同的人。这份工作至少四件：① 定执行宽度 ② 维护活跃掩码 ③ 分歧后重新汇聚 ④ 保证 lane 的前进性。NVIDIA 把 ① 钉死在硬件（恒 32），又为 ③④ 专门花了硅（收敛屏障和逐 lane 程序计数器），编译器于是几乎不用干活，SASS 看着很"标量"。Intel 和 AMD 把 ①③ 交给编译器（选宽度 + 生成结构化控制流），硬件只提供掩码寄存器和多周期发射，ISA 里于是什么都看得见——AMD 甚至更直白，它的活跃掩码 exec 是一个架构可见的寄存器，编译器明着往里写值，wave 宽度也是按 kernel 在 32/64 里选。

所以这条轴上真正的异类不是 Intel，而是 NVIDIA——它是唯一把这件事藏起来的，而它藏得起，是因为花了硬件去买。ISA 里看不看得见宽度，是这个切分的症状，不是原因。

于是有了一个 CUDA 里不存在的变量：宽度

既然宽度是指令的一个字段，编译器就得替你选一个。Intel 的 GPU 编译器后端（IGC，Intel Graphics Compiler）会为同一份 kernel 选 SIMD8、SIMD16 或 SIMD32——这也是第 6 章会说的"Intel GPU 上 sub-group 可能是 8/16/32"的由来。

这个"自由度"落在哪一层，值得先说清楚。GPU 的工具链是三级的（第 10 章会把这套东西讲透）：源码 →（前端）→ 虚拟 ISA →（后端 JIT）→ 原生 ISA。虚拟 ISA 是那份对外稳定的契约（NVIDIA 的 PTX、跨厂商的 SPIR-V），原生 ISA 才是硬件真正吃的东西（SASS、Xe ISA）。宽度这个自由度就落在最后那道 JIT 上：NVIDIA 那一道由 ptxas 做，根本没有宽度可选；Intel 那一道由 IGC 做，宽度在这里才定下来——甚至会先按 SIMD32 编一遍，发现寄存器溢出太狠再退回 SIMD16 重编。

图 2-2　Intel GPU 上，编译器把 work-item 横向"缝"进 SIMD lane，宽度自己定。宽度越大，一条指令干的活越多，但每个 work-item 能分到的 GRF 越少——这是一笔真实的权衡，不是自由参数

动手：宽度不是"越宽越好"

下面这个模拟器能在浏览器里直接跑——点 ▶ 运行。它给同一个 work-group 算三笔账：需要几个硬件 thread、分支体要发射几条指令、以及每个 work-item 能分到多少寄存器空间。你会看到这三笔账方向并不一致。

Python 
# Intel GPU 的 SIMD 宽度不是常数：换个宽度，三笔账同时变
WORK_ITEMS = 256          # 一个 work-group 里的 work-item 数
GRF_BYTES  = 128 * 32     # 每个硬件 thread 的寄存器堆：128 个 32 字节寄存器 = 4096 B
GROUP      = 8            # 分支每隔多少个连续 work-item 换一次（改我！）

def branch_of(wi):
    """这个 work-item 走哪条分支（0 或 1）"""
    return (wi // GROUP) % 2

print(f"work-group = {WORK_ITEMS} 个 work-item，分支每 {GROUP} 个 work-item 换一次\n")

for simd in (8, 16, 32):
    threads = -(-WORK_ITEMS // simd)        # 向上取整：要几个硬件 thread（= 几个"warp"）
    issues = 0                              # 分支体一共发射几条指令
    for t in range(threads):
        lanes = {branch_of(t * simd + k) for k in range(simd)}
        issues += len(lanes)                # 这个 thread 内出现几条分支，就得跑几遍
    lane_slots = issues * simd              # 发射出去的 lane·指令 槽位总数
    util = 100 * WORK_ITEMS / lane_slots    # 其中真正干活的只有 WORK_ITEMS 个
    regs = GRF_BYTES // simd                # 每个 work-item 能分到多少寄存器空间
    print(f"SIMD{simd:<2}  硬件 thread {threads:>2} 个 | 分支指令 {issues:>2} 条 "
          f"| lane 利用率 {util:5.1f}% | 每 work-item 寄存器预算 {regs:>3} B")

print("\n三笔账互相拉扯：宽度越大，指令越少（好）；但掩码浪费可能变多、")
print("每个 work-item 的寄存器预算成比例缩小（坏）。所以最优宽度取决于 kernel——")
print("这正是 Intel 把宽度交给编译器、而不像 warp 那样写死成 32 的原因。")

每个 work-item 的寄存器预算成比例缩小（坏）。所以最优宽度取决于 kernel——
这正是 Intel 把宽度交给编译器、而不像 warp 那样写死成 32 的原因。

注意 SIMD8 那行：它是唯一 lane 利用率 100% 的——因为分支恰好每 8 个 work-item 换一次，8 条 lane 刚好整齐地落在同一条分支上。窄反而赢了。

现在动手改一行：把 GROUP = 8 改成 GROUP = 32，再运行。三种宽度的利用率全变成 100%，SIMD32 只发 8 条指令——它从"打平"变成"全胜"。同一份 kernel，只因为数据的分歧粒度变了，最优宽度就换了个人。 这就是 Intel 不把宽度写死的理由：它不是硬件偷懒，而是把一个真实的权衡留在了编译期。

如果你确实知道自己要什么（比如你的算法天然按 16 个一组归约），可以直接把宽度钉死：

SYCL / DPC++
// SYCL：强制这个 kernel 用 SIMD16（即 sub-group 大小 = 16）
h.parallel_for(sycl::nd_range<1>{n, 256},
    [=](sycl::nd_item<1> it) [[sycl::reqd_sub_group_size(16)]] {
        size_t i = it.get_global_id(0);
        c[i] = a[i] + b[i];
    });
由此推出一条硬规矩 在 SYCL/OpenCL 代码里，永远不要把 sub-group 大小当成 32。CUDA 里 warpSize 恒为 32，你把它当常量用最多是不优雅；换到 Intel GPU 上，同样的假设直接是 bug——同一份 kernel 换台机器、甚至只改改寄存器用量，宽度就可能从 32 变成 16。要么运行时查询 sg.get_local_range()[0]，要么用 reqd_sub_group_size 明确要求。第 6 章会把这条规矩讲透。

反向证明：Intel 让你直接写向量

如果底层真是 SIMD，那应该有办法绕过 SIMT 抽象、直接对着向量机编程——确实有。Intel 给 SYCL 加了个扩展叫 ESIMD（Explicit SIMD，显式 SIMD），在这个模式下你不再写"一个 work-item 做什么"，而是像写 AVX 一样写 GPU：

SYCL / DPC++
// ESIMD：直接操作 GPU 的向量寄存器（片段，需 Intel GPU）
#include <sycl/ext/intel/esimd.hpp>
using namespace sycl::ext::intel::esimd;

// 每个 work-item 这次负责整整 16 个元素，而不是 1 个
h.parallel_for(sycl::range<1>{n / 16},
    [=](sycl::id<1> i) [[intel::sycl_explicit_simd]] {
        unsigned off = i[0] * 16;
        simd<float, 16> va, vb;          // 一个"宽"寄存器，16 个 float
        va.copy_from(a + off);
        vb.copy_from(b + off);
        (va + vb).copy_to(c + off);      // 一条向量加；尾巴和掩码全归你管
    });

把它和本章开头那段 AVX 代码摆在一起看——simd<float, 16> 就是 __m256／__m512 那一族的 GPU 版本（16 个 float 正好是 512 位），copy_from 就是 _mm256_loadu_ps，连"不够一整个宽度的尾巴要自己处理"这个烦恼都一模一样。这条通道的存在本身就说明：SIMT 是一层可以掀掉的抽象，掀掉之后底下是一台货真价实的向量机。 代价当然是丧失可移植性和 SIMT 的书写便利，所以 ESIMD 只用在库作者手写核心 kernel 这类场景。

分歧呢？一样疼，但少一颗后悔药

这一章的主角 warp 分歧，在 Intel GPU 上代价完全一样：掩码屏蔽 + 两条分支串行。但有一处差别值得记住：

  • NVIDIA（Volta 及之后）有独立线程调度（independent thread scheduling）：每条 lane 有自己的程序计数器，分歧的 lane 可以真正各走各的、稍后再重新汇聚。
  • Intel Xe 没有 per-lane PC：整个硬件 thread 只有一个程序计数器，分歧靠"执行掩码 + 结构化控制流"（编译器生成 if／else／endif 和带跳转目标的分支指令）实现。lane 之间不能真正独立前进。

对你写代码的实际影响：别指望"让分歧的 lane 各跑各的"这种技巧在 Intel GPU 上有效；也因此，那种在 NVIDIA 上靠独立线程调度才成立的细粒度自旋锁、lane 间生产者-消费者模式，移植到 Intel GPU 上可能直接死锁。反过来，这一章教的正道——让走向不同的 work-item 落在不同的 sub-group 里——在三家硬件上都成立，而且都是最优解。

小结与下一步

你现在懂了 GPU"线程齐步走"的机制、它的头号代价，也顺着 Intel Xe 看了一眼这层抽象底下那台向量机。但线程不是凭空齐步走的——它们跑在具体的硬件上：一颗 GPU 有几十个 SM（流多处理器），每个 SM 有一堆计算核心、一块共享内存、还有那个负责调度 warp 的硬件。下一章我们就把 GPU 芯片"拆开"看一眼，建立硬件的心智模型——这样第 4 章开始讲 Grid/Block/Thread 时，你就知道这些软件概念到底落在哪块硅片上。

这一章的要点

  • SIMD（CPU）：你手写向量代码，一条指令处理一"宽"寄存器里的多个数据，宽度写死。
  • SIMT（GPU）：你照常写标量代码，硬件把一组线程（一个 warp = 32 线程）绑起来齐步执行同一条指令——写着像标量，跑着像向量。
  • SIMT 的代价是 warp 分歧：warp 内线程走进不同 if 分支时，各分支被串行执行（该走的干活，其余关灯干等），哪怕只有一个线程不合群也要付全价。
  • 分歧只在 warp 内部才有代价；优化方向是让走向不同的线程落在不同的 warp，而不是消灭所有分支。
  • SIMT 把并行复杂度藏进硬件，代价是你必须理解 warp 这个"隐形的 32 人小队"（第 6 章）。
  • SIMT 底下其实还是 SIMD：三家 GPU 的执行引擎都是"向量机 + 执行掩码"，把标量 kernel 缝进 lane 的做法叫 SPMD-on-SIMD（整函数向量化）。Intel Xe 把执行宽度、掩码、寄存器区域明写在指令编码里，所以它是观察这层抽象的好样本。
  • 但别简化成"NVIDIA 也一样，只是不给你看"：维持 SIMT 幻觉的总工作量一定，三家切给了不同的人。NVIDIA 花硬件（宽度钉死 + 收敛屏障 + 逐 lane PC），编译器就轻；Intel/AMD 花编译器（选宽度 + 结构化控制流），硬件就简单。ISA 里看不看得见宽度，是这个切分的症状，不是原因——这条轴上的异类其实是 NVIDIA。
  • 宽度这个自由度落在**"虚拟 ISA → 原生 ISA"那道 JIT** 上（第 10 章）：ptxas 无宽度可选，IGC 才有。
  • Intel 名词对照：Xe-core ≈ SM、XVE（旧称 EU）是向量引擎、SLM = shared memory、GRF = 寄存器堆；注意 Intel 说的 thread ≈ warp，不是 CUDA 的 thread。
  • Intel 上 SIMD 宽度（= sub-group 大小）是编译器在 8/16/32 里选的，因为它和"每个 work-item 分到多少 GRF"成反比——是个真实权衡。推论：SYCL 代码里绝不能假设 sub-group 是 32，要查询或用 reqd_sub_group_size 钉死。
  • ESIMD 扩展让你在 GPU 上直接写 simd<float,16>（像写 AVX），反向证明了 SIMT 是一层可以掀掉的抽象。
  • Intel Xe 没有 per-lane 程序计数器（NVIDIA Volta+ 的独立线程调度它没有），所以依赖"分歧 lane 各走各的"的技巧移植过去可能死锁；但"让走向不同的线程落在不同 sub-group"这条正道三家通用。
