第 12 章 GEMM 优化（一）：tile 尺寸与执行顺序

这一章想让你带走什么

上一章的 roofline 显示，minillm 的 GEMM 离屋顶还有一截。接下来三章专门优化它，每一节都按同一个节奏：先用模型预测改一个参数会怎样，再测，再解释偏差。这一章动两个最基本的旋钮：tile 有多大（BLOCK_M、BLOCK_N、BLOCK_K，配合 num_warps），以及 program 按什么顺序执行（L2 swizzle）。

读完你会拿到两个能直接用的模型。一是寄存器预算：每个线程要放 BLOCK_M × BLOCK_N ÷（每个 warp 的线程数 × num_warps）个累加器元素。在 Max 1100 上，这个数到了 256 就一定大量溢出，性能从 150 TFLOP/s 掉到 20 几；同一个 128×128 的 tile，只是把 4 个 warp 改成 8 个，就快了 6 倍。二是 L2 复用：同一时刻在跑的 program 要用到多少条 A 和 B。你会先预测 swizzle 在 4096³ 上不起作用，在更大的矩阵上能快 20%–40%，然后看实测是不是这样。最后，minillm 的矩阵乘用上了这两条结论。

旋钮一：tile 有多大

第 7 章的模拟器说过：tile 越大，每搬一个字节能做的运算越多（算术强度 ∝ BM·BN/(BM+BN)）。照这个说法，tile 应该越大越好。但 tile 越大，每个 program 的累加器也越大，而累加器整个循环都待在寄存器里。

先算一笔账。一个 BM×BN 的 fp32 累加器，分给一个 program 的所有线程：

每个线程的累加器元素 = BM × BN ÷（每个 warp 的线程数 × num_warps）

「每个 warp 的线程数」就是 TTGIR 里的 "ttg.threads-per-warp"：NVIDIA 是 32；Intel 上带 tl.dot 的 kernel 是 16（第 2 章）。在 Max 1100 上，第 6 章看到默认每个线程 128 个寄存器，大寄存器模式 256 个。一个 128 个元素的累加器就要占掉 128 个 fp32 寄存器，再加上 A、B 两个操作数、地址和循环变量，256 个也很紧。预测：累加器每线程 128 个左右是能接受的上限，到了 256 个必然大量溢出。

用第 8 章的 descriptor GEMM，扫一遍 tile 和 num_warps：

Triton (Python) 
# arch: sm80 xpu
import torch
import triton
from triton.tools.tensor_descriptor import TensorDescriptor

from minillm import DEVICE
from minillm.kernels.matmul import _matmul_desc_kernel

M = N = K = 4096
a = torch.randn(M, K, device=DEVICE, dtype=torch.bfloat16)
b = torch.randn(K, N, device=DEVICE, dtype=torch.bfloat16)
c = torch.empty(M, N, device=DEVICE, dtype=torch.bfloat16)
ref = a @ b
# TTGIR 里 "ttg.threads-per-warp" 的值：带 tl.dot 的 kernel 在 Intel 上是 16（第 2 章），NVIDIA 上是 32
TPW = 16 if DEVICE.type == "xpu" else 32
print(f"{getattr(torch, DEVICE.type).get_device_name()}，triton {triton.__version__}，bf16 {M}³")
for BM, BN, BK, nw in ((64, 64, 32, 4), (128, 128, 32, 4), (128, 128, 32, 8), (128, 128, 64, 8),
                       (128, 256, 32, 8), (128, 256, 32, 16), (256, 128, 32, 16), (256, 256, 32, 16),
                       (256, 256, 32, 32), (256, 256, 64, 32)):
    descs = (TensorDescriptor.from_tensor(a, [BM, BK]), TensorDescriptor.from_tensor(b, [BK, BN]),
             TensorDescriptor.from_tensor(c, [BM, BN]))
    grid = (triton.cdiv(M, BM), triton.cdiv(N, BN))
    run = lambda: _matmul_desc_kernel[grid](*descs, K, BLOCK_M=BM, BLOCK_N=BN, BLOCK_K=BK, num_warps=nw)
    k = run()                                         # 返回编译好的 kernel：拿 n_regs、n_spills
    torch.testing.assert_close(c, ref, atol=0.5, rtol=0.05)
    ms = triton.testing.do_bench(run)
    acc = BM * BN // (TPW * nw)                       # 每个线程要放的累加器元素
    print(f"  {BM:3}×{BN:3}×{BK:2} num_warps={nw:2}  累加器/线程 {acc:3}  n_regs={k.n_regs:3} "
          f"n_spills={k.n_spills:4}  {2 * M * N * K / ms / 1e9:6.1f} TFLOP/s")

预测完全成立，而且分界线非常干净：

  • 累加器每线程 256 个的那四行，全部溢出 406，性能在 20–27 TFLOP/s，比最好的配置慢 6 倍左右。
  • **累加器每线程 128 个的，溢出 100 左右，性能 130–153 TFLOP/s。**少量的溢出没有造成明显的伤害。
  • 64×64 的 tile 每线程只有 64 个，完全不溢出，但只有 121 TFLOP/s：tile 太小，算术强度低（第 7 章），数据复用少。

最能说明问题的是 128×128×32 那两行：同一个 tile，num_warps 从 4 改成 8，从 20.6 变成 130.1 TFLOP/s。warp 多一倍，每个线程分到的累加器就少一半，正好跨过了那条线。所以 tile 的大小和 num_warps 不能分开选：tile 每大一倍，num_warps 也要跟着大一倍，让每个线程的负担保持不变。

所有 n_regs 都是 256：这些 kernel 在默认的 128 个寄存器下都会溢出，Intel 后端都自动换成了大寄存器模式（第 6 章）。在 NVIDIA 上，每个线程最多 255 个寄存器，分界线的位置会不一样：同样的 128×128 tile 和 4 个 warp，每个线程分到的累加器只有 128 个（一个 warp 32 个线程）。

还有一行我还没有解释清楚：128×128 的 tile、8 个 warp，BLOCK_K 从 32 改成 64，性能从 130 掉到 80，溢出量却几乎没变（100 对 101）；同样的改动放在 256×256 的 tile 上，性能没有变化（150.9 对 152.5）。BLOCK_K 加倍会让每次循环读进来的 A、B 块变大，但这不足以解释一个上一个下。我暂时没有定位到原因，第 22 章读 TTGIR、看编译器的流水和 layout 决定时，会回到这个例子。模型能解释大部分现象，但不是全部，这时候要老实承认，然后去读 IR。

旋钮二：program 按什么顺序执行

tile 定下来以后，还有一个看起来无关紧要的选择：C 的这么多 tile，哪个 program 先算哪个。

默认的二维 grid 是「按行排」：program_id(0) 走得最快。把 grid 改成一维，自己把编号映射到 (pid_m, pid_n)，就可以换一种顺序。Triton 官方教程 03（矩阵乘）用的是分组排（grouped ordering）：GROUP_M 行 tile 为一组，组内一列一列地走。

为什么顺序会影响速度？同一时刻在 GPU 上跑的，是编号相邻的几十到上百个 program。它们要用到的 A 的行、B 的列，如果有重叠，读一次就能被好几个 program 共享（在 L2 里）；如果没有重叠，就要各自从显存读。看一个 8×8 个 tile 的小例子：

图 12-1　两种执行顺序下，C 的 8×8 个 tile 由哪个 program 计算。按行排时，同时在跑的 program 横着排成一行，要用到 B 的很多列；分组排时，它们挤在一个更「方」的区域里，用到的 A 行和 B 列的总数更少，L2 里的数据被更多的 program 共享

图上前 8 个 program，按行排要用到 9 条（A 的 1 行加 B 的 8 列），分组排只要 6 条。矩阵越大、一行的 tile 越多，这个差距越大。这种重新安排执行顺序、让同时在跑的 program 尽量共享 L2 数据的做法，叫 L2 swizzle。minillm 的写法（kernels/matmul.py 的 _matmul_grouped_kernel）：

Triton (Python)
    pid = tl.program_id(0)
    num_m = tl.cdiv(M, BLOCK_M)
    num_n = tl.cdiv(N, BLOCK_N)
    in_group = GROUP_M * num_n                       # 一组里有多少个 program
    first_m = (pid // in_group) * GROUP_M            # 这一组从第几行 tile 开始
    size_m = tl.minimum(num_m - first_m, GROUP_M)    # 最后一组可能不满 GROUP_M 行
    pid_m = first_m + (pid % in_group) % size_m
    pid_n = (pid % in_group) // size_m

先预测

swizzle 有没有用，取决于数据能不能本来就留在 L2 里。如果 A 和 B 加起来放得进 L2，不管什么顺序，每条都只从显存读一次；只有放不下时，顺序才决定一条数据被读几遍。

4096³ 的 bf16 GEMM，A 和 B 合计 64 MiB，Max 1100 的 L2 有 192 MiB。**预测：swizzle 在 4096³ 上不起作用。**要看到效果，得把矩阵放大：16384×16384×4096 时 A、B 合计 256 MiB，16384×16384×8192 时 512 MiB，都放不下。

下面的模型把这件事算出来：同一时刻有一批 program 在跑，它们要用的条从显存读进来，批与批之间按 LRU 留在 L2 里，统计 A、B 一共从显存读了几遍。只用标准库，直接点运行：

Python 
# GEMM 的执行顺序和 L2：按行排 vs 分组排（GROUP_M），A、B 要从显存读几遍。只用标准库。
#
# 每个 program 算 C 的一个 BM×BN tile，要用到 A 的一条行（BM×K）和 B 的一条列（K×BN）。
# 模型（很粗，但抓住了要点）：
#   - 同一时刻有 WAVE 个 program 在跑（一「批」），它们沿着 K 一起往前走；
#   - 一批里如果有好几个 program 用同一条行（或列），这条只从显存读一次；
#   - 批与批之间，缓存按 LRU 保留；容量 L2 是「能有效利用的」那部分，比标称值小（第 1 章见过）。
from collections import OrderedDict


def order(num_m, num_n, group_m):
    for pid in range(num_m * num_n):
        if group_m == 1:                                 # 按行排：先走完 C 的第一行 tile
            yield pid // num_n, pid % num_n
        else:                                            # 分组排：group_m 行一组，组内一列一列地走
            group = pid // (group_m * num_n)
            first = group * group_m
            size = min(num_m - first, group_m)
            yield first + (pid % (group_m * num_n)) % size, (pid % (group_m * num_n)) // size


def dram_reads(M, N, K, BM, BN, l2_bytes, wave, group_m, elem=2):
    strip = {"A": BM * K * elem, "B": K * BN * elem}
    progs = list(order(M // BM, N // BN, group_m))
    cache, used, read = OrderedDict(), 0, 0
    for start in range(0, len(progs), wave):
        need = {("A", pm) for pm, _ in progs[start:start + wave]} | {("B", pn) for _, pn in progs[start:start + wave]}
        for key in sorted(need):
            if key in cache:
                cache.move_to_end(key)
                continue
            read += strip[key[0]]
            cache[key] = strip[key[0]]
            used += strip[key[0]]
            while used > l2_bytes:                          # 放不下：赶走最久没用的（可能是这一批刚读的）
                _, s = cache.popitem(last=False)
                used -= s
    return read / ((M * K + K * N) * elem)               # 相对于「A、B 各读一遍」的倍数


MiB = 2**20
SHAPES = ((4096, 4096, 4096), (16384, 16384, 4096), (16384, 16384, 8192))
for gpu, l2, wave in (("Max 1100", 192 * MiB, 112), ("Max 1100", 96 * MiB, 112), ("A10", 6 * MiB, 72)):
    print(f"{gpu}（有效 L2 按 {l2 // MiB} MiB、每批 {wave} 个 program 算），tile 256×256，A、B 从显存读了几遍：")
    print(f"  {'M×N×K':>18}   GROUP_M=1    =4     =8    =16")
    for M, N, K in SHAPES:
        r = [dram_reads(M, N, K, 256, 256, l2, wave, g) for g in (1, 4, 8, 16)]
        print(f"  {M:>6}×{N}×{K:<5}   {r[0]:7.1f}  {r[1]:6.1f} {r[2]:6.1f} {r[3]:6.1f}")
    print()

再测

import torch
import triton

  • 4096³：四种顺序一样快（148–150 TFLOP/s），预测成立。
  • **16384×16384×4096：分组以后从 155.0 涨到 185.0，快了 19%。**这一档按 192 MiB 的模型说不该有差别，按 96 MiB 的说有。实测支持后者：能被有效利用的 L2 比 192 MiB 少得多，B 的 64 条（128 MiB）留不住。

模型的数字（读 19 遍 vs 2.5 遍）比实测的差距（快 19%–42%）夸张得多，因为它只数了显存流量，而这个 kernel 在分组以后已经不完全受显存带宽限制了（第 11 章：它离矩阵单元的屋顶也不远）。模型告诉你方向和大致的分界线，具体快多少要靠测量。GROUP_M 取 8 或 16 都差不多，minillm 取 8。

在 A10 上会怎样

A10 的 L2 只有 6 MB。上面模型的第三组预测：在 A10 上，连 4096³ 都放不下，按行排要读 2.6 遍，分组排 2.2 遍；到了 16384 这两档，差距是 29.4 遍对 8 遍。所以 swizzle 在 L2 小的 GPU 上更重要。这也是为什么 Triton 官方教程在 NVIDIA 上，4096 这种「不大」的尺寸就能测出 swizzle 的收益。本书还没在 A10 上验证这个预测。

minillm：带 L2 swizzle 的矩阵乘

kernels/matmul.py 新增 _matmul_grouped_kernel 和 matmul_grouped：一维 grid、GROUP_M=8、256×256×32、32 个 warp，descriptor 在 kernel 里创建（这样在 triton_op 里也是安全的，第 10 章）。mm() 和 ops.mm 在 Intel GPU 上都改用它。新的测试检查「最后一组不满 GROUP_M 行」时，编号映射没有漏算或重复（比如 1000 行、BLOCK_M=256 时，只有 4 行 tile）。

动手

  1. 在你的 GPU 上找寄存器的分界线。 跑本章的 tile 扫描。NVIDIA 上一个 warp 32 个线程，每个线程最多 255 个寄存器：哪几个配置开始溢出？分界线还在「累加器每线程 256 个」吗？
  2. 验证 A10 上的 swizzle 预测。 在 A10 上跑本章的 swizzle 实验。4096³ 上 GROUP_M 有没有用？16384 那两档呢？和浏览器里模型的第三组比一比。
  3. 在模型里改一下有效 L2 的大小，比如 48 MiB、128 MiB，看 16384×16384×4096 这一档的预测怎么变。能不能找到一个值，让模型预测的「按行排 / 分组排」的遍数之比，和实测的速度之比最接近？想一想为什么两者不会完全一致。

这一章的要点

  • tile 越大，算术强度越高，但累加器越大。每个线程的累加器元素 = BM × BN ÷（每个 warp 的线程数 × num_warps），NVIDIA 一个 warp 32 个线程，Intel 带 tl.dot 的 kernel 是 16。
  • Max 1100 上实测：累加器每线程 256 个时一律溢出 406，性能 20–27 TFLOP/s；128 个时 130–153 TFLOP/s。同一个 128×128 tile，num_warps 从 4 改成 8，快了 6 倍。tile 和 num_warps 要一起选。
  • 一处尚未解释的现象：128×128、8 个 warp 时，BLOCK_K 从 32 改成 64 会慢下来，溢出量却几乎不变。留到第 22 章读 IR。
  • L2 swizzle：一维 grid，按 GROUP_M 行一组安排 program 的执行顺序，让同时在跑的 program 共享 A 的行和 B 的列。它只在 A、B 放不下 L2 时才有用：Max 1100 上，4096³ 不起作用，16384×16384×4096 快 19%，16384×16384×8192 快 42%。L2 小的 GPU（如 A10，6 MB）上，模型预测它在小得多的矩阵上就开始起作用。
  • 模型给方向和分界线，测量给具体的数：这一章的两个模型都预测对了「什么时候有用」，但都没能准确预测「快多少」。
