第 1 章 为什么是 Triton：从 PyTorch eager 到手写 kernel 之间的鸿沟

这一章想让你带走什么

你每天写的 PyTorch 代码，每一行张量运算背后都是一个现成的 GPU kernel。这套机制好用、灵活，但它有一个结构性的代价：op 和 op 之间的中间结果，都要写回显存，再由下一个 op 读出来。对大多数深度学习算子来说，GPU 的时间花在搬数据上，而不是花在算上。所以这个代价不是几个百分点，而是几倍。

读完这一章，你会拿到三样东西。一是一个能自己复算的判断方法：数一数一个算子要和显存来回几趟，就大致知道它能跑多快，你会在一个 softmax 上亲手量到 4.7 倍的差距，并用一个浏览器里能跑的小模型解释它。二是 torch.compile 的真实位置：它已经会替你把这种算子融合成一个 Triton kernel，但在 attention 这类要改算法才能融合的地方，它会停下来。三是这本书的地图：在 PyTorch eager 和手写 CUDA 之间有好几层，Triton 站在哪一层、把什么交给了编译器、又留了什么给你。

先看一眼：同一个 softmax，四种跑法

不铺垫概念，先测一个最普通的算子。对一个 4096 行的矩阵按行做 softmax：每行减去最大值，取指数，再除以这一行的和。下面的脚本用四种方式实现它，并逐个测时间：

  • eager：照着公式，一步一个 PyTorch op 地写；
  • torch.softmax：PyTorch 自带的实现；
  • torch.compile：把 eager 版交给 PyTorch 的编译器；
  • Triton：手写一个 Triton kernel，一个 program 处理一整行。现在看不懂没关系，第 3、4 章会逐行讲。
Triton (Python) 
# arch: sm80 xpu
import sys

import torch
import triton
import triton.language as tl

DEVICE = triton.runtime.driver.active.get_active_torch_device()


def softmax_eager(x):
    # 照着公式一步一步写：每一行都是一个独立的 PyTorch op，也就是一次 kernel 启动
    m = x.max(dim=1, keepdim=True).values   # 读 x
    z = x - m                               # 读 x，写 z
    e = torch.exp(z)                        # 读 z，写 e
    s = e.sum(dim=1, keepdim=True)          # 读 e
    return e / s                            # 读 e，写 y


@triton.jit
def softmax_kernel(x_ptr, y_ptr, n_cols, BLOCK: tl.constexpr):
    row = tl.program_id(0)                  # 一个 program 负责一整行
    cols = tl.arange(0, BLOCK)
    mask = cols < n_cols
    x = tl.load(x_ptr + row * n_cols + cols, mask=mask, other=-float("inf"))
    x = x - tl.max(x, axis=0)
    e = tl.exp(x)
    y = e / tl.sum(e, axis=0)
    tl.store(y_ptr + row * n_cols + cols, y, mask=mask)


def softmax_triton(x):
    y = torch.empty_like(x)
    n_rows, n_cols = x.shape
    softmax_kernel[(n_rows,)](x, y, n_cols, BLOCK=triton.next_power_of_2(n_cols))
    return y


n_rows, n_cols = 4096, int(sys.argv[1]) if len(sys.argv) > 1 else 16384
x = torch.randn(n_rows, n_cols, device=DEVICE)
ref = torch.softmax(x, dim=1)
impls = {"eager（5 个 op）": softmax_eager, "torch.softmax": lambda t: torch.softmax(t, dim=1),
         "torch.compile": torch.compile(softmax_eager), "Triton（融合）": softmax_triton}
min_bytes = 2 * x.numel() * x.element_size()   # 至少要读一遍 x、写一遍 y
print(f"{getattr(torch, DEVICE.type).get_device_name()}，torch {torch.__version__}，"
      f"triton {triton.__version__}，x: {n_rows}×{n_cols} fp32")
for name, fn in impls.items():
    torch.testing.assert_close(fn(x), ref)
    ms = triton.testing.do_bench(lambda: fn(x))
    print(f"  {name:16} {ms * 1e3:8.1f} us   有效带宽 {min_bytes / ms / 1e6:6.0f} GB/s")
本地运行：python main.py # 需要 NVIDIA sm_80+ 或 Intel GPU（XPU）；环境见附录 A

  eager（5 个 op）      3637.3 us   有效带宽    148 GB/s
  torch.softmax       772.0 us   有效带宽    695 GB/s

  Triton（融合）          856.1 us   有效带宽    627 GB/s

四种实现算的是同一个东西，结果也都通过了 assert_close。但照着公式写的 eager 版慢了 4.7 倍；另外三种落在同一个量级。

「有效带宽」这一列值得解释一下。softmax 至少要把输入读一遍、把输出写一遍，这里就是 2 × 256 MiB。拿这个最少必需的字节数除以耗时，就是有效带宽。它衡量的是「离把数据搬一遍的极限还差多远」。Max 1100 的显存标称带宽约 1.2 TB/s，三种融合实现跑到了它的一半多一点（差距从哪来，第 11 章讲）；eager 版只有 148 GB/s。

慢在哪：不是算得慢，是搬得多

先排除一个直觉：eager 版慢，不是因为它的指数函数算得慢。softmax 对每个元素只做五六次浮点运算，而每个元素要从显存读 4 个字节。GPU 每秒能做几十万亿次浮点运算，却只能从显存搬一万亿字节左右。照这个比例，它在等数据，不在等计算。这类算子叫访存受限（memory-bound）。判断一个 kernel 属于哪一类、离上限还有多远，是第 2 章和第 11 章的主题。

访存受限的算子，耗时大致正比于它和显存之间来回搬了多少字节。那就数一数。eager 版的五行代码是五个独立的 op，每个 op 是一次独立的 kernel 启动。一个 kernel 结束时，它的结果必须完整地写回显存，因为下一个 kernel 只能从显存里拿到它：

图 1-1　灰色箭头是从显存读，橙色箭头是写回显存。eager 版的每个中间结果（z、e）都要整张写回、再整张读出；融合以后，中间结果只活在 kernel 内部（寄存器里），从不落到显存

8 趟对 2 趟，正好 4 倍。实测 4.7 倍，量级对上了。多出来的部分，是 eager 版的五次 kernel 启动、两次归约本身的效率，以及 PyTorch 每个 op 的调度开销。

这就是**算子融合（kernel fusion）**要解决的问题：把多个 op 合进一个 kernel，中间结果留在芯片上，不落显存。torch.softmax 是 PyTorch 工程师手写好的融合 kernel，torch.compile 是自动融合，我们的 Triton 版是手动融合。三者都是 2 趟，所以快得差不多。

先预测，再测量：矩阵小一点会怎样

把列数从 16384 改成 1024，矩阵从 256 MiB 变成 16 MiB。eager 版还是慢 4 倍吗？

先别急着跑。上面数趟数时，默认了一件事：每一趟都真的走到了显存。可 GPU 和 CPU 一样有缓存，Max 1100 的驱动报告它的末级缓存（L2）有 192 MiB。如果中间结果装得进 L2，下一个 kernel 就能直接从缓存里读到它，这一趟就不算显存流量了。下面这个小模型把这件事算出来。它只用标准库，直接点运行；你可以改最下面的参数，看不同的缓存大小下会怎样：

Python 
# softmax 的显存流量：eager（5 个 op，每个 op 一个 kernel）对比融合成 1 个 kernel。
# 只用标准库；改最下面的参数再跑一遍。

MiB = 2**20

# eager 的每一步读哪些整张矩阵、写哪些整张矩阵（每行一个数的 m、s 太小，忽略）
EAGER = [
    ("max", ["x"], []),
    ("sub", ["x"], ["z"]),
    ("exp", ["z"], ["e"]),
    ("sum", ["e"], []),
    ("div", ["e"], ["y"]),
]
FUSED = [("softmax", ["x"], ["y"])]   # 读一遍 x，写一遍 y


def traffic(ops, tensor_bytes, l2_bytes):
    """返回 (显存读字节, 显存写字节)。L2 模型故意做得很粗，只有两条规则：
    1. 读一张矩阵时，如果它还在 L2 里，就不走显存；写一律算显存流量。
    2. 一个 kernel 是边读边写的，它碰到的矩阵**加起来**装得下 L2，跑完才都留在 L2 里；
       装不下，就是一路流过去，什么也留不下。"""
    cache = set()                     # 现在留在 L2 里的矩阵
    rd = wr = 0
    for _, reads, writes in ops:
        rd += sum(tensor_bytes for t in reads if t not in cache)
        wr += tensor_bytes * len(writes)
        touched = set(reads) | set(writes)
        # 只留这一步碰过的（再早的被这一步的数据挤掉了，粗略地当作都不在了）
        cache = touched if len(touched) * tensor_bytes <= l2_bytes else set()
    return rd, wr


def report(gpu, l2_mib, rows, col_list):
    print(f"{gpu}（L2 按 {l2_mib} MiB 算），{rows} 行 fp32：")
    print(f"  {'列数':>6} {'矩阵':>8} {'eager 读+写':>12} {'融合 读+写':>11} {'比值':>5}")
    for cols in col_list:
        size = rows * cols * 4
        er, ew = traffic(EAGER, size, l2_mib * MiB)
        fr, fw = traffic(FUSED, size, l2_mib * MiB)
        print(f"  {cols:>6} {size // MiB:>5} MiB {(er + ew) // MiB:>8} MiB {(fr + fw) // MiB:>7} MiB"
              f" {(er + ew) / (fr + fw):>5.1f}")
    print()


COLS = [1024, 4096, 8192, 16384, 32768]
report("Max 1100", 192, 4096, COLS)   # 驱动报告的 last-level cache 大小
report("A10", 6, 4096, COLS)          # A10 的 L2 是 6 MB
report("没有缓存", 0, 4096, COLS)

模型的预测是：在 Max 1100 上，矩阵装得进 L2 时，eager 只慢 2 倍左右；装不进时，慢 4 倍。在 L2 只有 6 MB 的 A10 上，这几档都装不进，所以一律是 4 倍。

趋势和分界线都对上了：64 MiB 及以下慢 2.7–2.8 倍，256 MiB 及以上慢 4.5–4.7 倍。模型只数字节，不算 kernel 启动和归约的开销，所以实测比值普遍比预测高一点。8192 那一档模型偏乐观：真实的缓存不会把 128 MiB 全部留给同一张矩阵。

这个小实验预告了全书第三部分的节奏：先用一个硬件模型预测，再测量，再解释偏差。模型粗没关系，只要能告诉你「该往哪个方向猜」。两个结论值得记住：

  • 访存受限的算子，看它和显存来回几趟，就知道它大致能跑多快；
  • 同一份代码，在缓存大小不同的 GPU 上，「融合能省多少」可能差一倍。所以本书的性能数字都会注明是哪一台 GPU 测的。

torch.compile 已经替你写了这个 kernel

既然融合这么重要，PyTorch 自然不会坐视不管。torch.compile 的后端 Inductor 会分析整段计算图，把能融合的 op 合并，然后生成 Triton 代码，再交给 Triton 编译。用 TORCH_LOGS=output_code 就能看到它生成了什么。下面是它为 softmax_eager 生成的 kernel（Max 1100 上 dump 出来的，节选：去掉了 import、Inductor 自己的 @triton_heuristics.reduction(...) 装饰器（它负责给 XBLOCK、R0_BLOCK 挑值），以及循环里的初始化和别名赋值）：

Triton (Python)
@triton.jit
def triton_red_fused_div_exp_max_sub_sum_0(in_ptr0, out_ptr2, xnumel, r0_numel, XBLOCK : tl.constexpr, R0_BLOCK : tl.constexpr):
    xnumel = 4096
    r0_numel = 4096
    xoffset = tl.program_id(0) * XBLOCK
    xindex = xoffset + tl.arange(0, XBLOCK)[:, None]
    r0_base = tl.arange(0, R0_BLOCK)[None, :]
    x0 = xindex
    # 第一遍：沿着一行分段读 x，求最大值
    for r0_offset in tl.range(0, r0_numel, R0_BLOCK):
        ...
        tmp0 = tl.load(in_ptr0 + (r0_1 + 4096*x0), r0_mask, eviction_policy='evict_last', other=0.0)
        ...
    # 第二遍：再读一次 x，求 exp(x - max) 的和
    for r0_offset in tl.range(0, r0_numel, R0_BLOCK):
        ...
        tmp3 = tl.load(in_ptr0 + (r0_1 + 4096*x0), r0_mask, eviction_policy='evict_last', other=0.0)
        tmp4 = tmp3 - tmp2
        tmp5 = libdevice.exp(tmp4)
        ...
    tmp7 = tl.sum(_tmp7, 1)[:, None]
    # 第三遍：第三次读 x，算出结果，写一次
    for r0_offset in tl.range(0, r0_numel, R0_BLOCK):
        ...
        tmp9 = tl.load(in_ptr0 + (r0_1 + 4096*x0), r0_mask, eviction_policy='evict_first', other=0.0)
        tmp10 = tmp9 - tmp2
        tmp11 = libdevice.exp(tmp10)
        tmp12 = (tmp11 / tmp7)
        tl.store(out_ptr2 + (r0_1 + 4096*x0), tmp12, r0_mask)

（为了突出结构，这里把省略的行写成了 ...，注释也是我加的。上面这份是 4096 列时 dump 的，所以常数是 4096。）

几件事值得注意：

  • 五个 op 变成了一个 kernel。 kernel 的名字是 Inductor 按「归约（red）+ 融合了哪些 op」拼出来的，拼名字的函数是 PyTorch 源码里 torch/_inductor/utils.py 的 get_fused_kernel_name；生成 Triton 代码的主力是 torch/_inductor/codegen/triton.py 里的 TritonKernel 类。
  • 它是一段地地道道的 Triton 代码：tl.program_id、tl.arange、tl.load 加 mask、tl.sum，用的全是第 4、5 章要讲的东西。学会读 Triton，你就能读懂 torch.compile 到底替你做了什么。
  • 它和我们的手写版做了不同的选择。 我们的版本让一个 program 一次装下一整行（16384 个 float）；Inductor 的版本沿着一行分段，循环三遍，把 x 读了三次，并用 eviction_policy='evict_last' 提示硬件尽量把 x 留在缓存里，等后面两遍再读。在 16384 列时，我们的手写版（627 GB/s）输给了它（700 GB/s）；列数再翻一倍到 32768，手写版更是掉到 382 GB/s，只剩它的一半左右。一行放不进一个 program 时会发生什么、该怎么写，是第 6 章的主题，到时候再测这个差距从哪里来。

所以对 softmax 这种算子，你不需要手写 kernel：torch.compile 写得已经很好了。那这本书为什么还要教你写 Triton？

编译器停下来的地方：attention

换一个算子：attention，softmax(QKᵀ/√d)·V。它是 Transformer 里最重要的算子。照着公式写，还是交给 torch.compile，再和 PyTorch 的 F.scaled_dot_product_attention（SDPA）比：

Triton (Python) 
# arch: sm80 xpu
import torch
import torch.nn.functional as F
import triton

DEVICE = triton.runtime.driver.active.get_active_torch_device()
gpu = getattr(torch, DEVICE.type)          # torch.cuda 或 torch.xpu，两者的显存统计接口相同


def attn_eager(q, k, v):
    s = q @ k.transpose(-1, -2) * q.shape[-1] ** -0.5   # (B·H, N, N) 的分数矩阵
    return torch.softmax(s, dim=-1) @ v


def sdpa(q, k, v):
    return F.scaled_dot_product_attention(q, k, v)


bh, n, d = 16, 4096, 64
q, k, v = (torch.randn(bh, n, d, device=DEVICE, dtype=torch.float16) for _ in range(3))
print(f"{gpu.get_device_name()}，torch {torch.__version__}，q/k/v: {bh}×{n}×{d} fp16，"
      f"分数矩阵 {bh * n * n * 2 / 2**20:.0f} MiB")
for name, fn in {"eager": attn_eager, "torch.compile": torch.compile(attn_eager), "SDPA（融合）": sdpa}.items():
    torch.testing.assert_close(fn(q, k, v), sdpa(q, k, v), atol=2e-3, rtol=2e-3)
    gpu.synchronize(); gpu.reset_peak_memory_stats(); base = gpu.memory_allocated()
    fn(q, k, v); gpu.synchronize()
    extra = (gpu.max_memory_allocated() - base) / 2**20
    ms = triton.testing.do_bench(lambda: fn(q, k, v))
    print(f"  {name:14} {ms:6.2f} ms   额外显存峰值 {extra:5.0f} MiB")
本地运行：python main.py # 需要 NVIDIA sm_80+ 或 Intel GPU（XPU）；环境见附录 A

  torch.compile    4.48 ms   额外显存峰值   520 MiB
  SDPA（融合）         0.79 ms   额外显存峰值     8 MiB

这一次，torch.compile 几乎没帮上忙：时间只少了 2%，而且仍然要 520 MiB 的额外显存。SDPA 快了 5.7 倍，额外显存只有 8 MiB。

看 Inductor 生成的执行计划就明白了（同样来自 TORCH_LOGS=output_code，节选自生成的 call 函数）：

Inductor 把两次矩阵乘交给了库函数（extern_kernels.bmm），把中间的缩放和 softmax 融合成了一个 Triton kernel。它能融的都融了，但 QKᵀ 的结果 buf0（16×4096×4096 个 fp16，512 MiB）还是完整地写进了显存，再由 softmax 读出来。要省掉这 512 MiB，就得把两次矩阵乘和中间的 softmax 融合进同一个 kernel，一边算 QKᵀ 的一小块，一边就地做 softmax，一边乘上 V。

难点在于 softmax 要除以整行的和，而一次只算出了一小块。解法是 online softmax：一边扫，一边维护「到目前为止的最大值和累加和」，每来一块新数据，就把之前的部分结果按新的最大值重新缩放（第 6 章推导）。这已经不是「把几个 op 粘在一起」，而是换了一个算法。按模式匹配做融合的编译器，不会自己发明这个算法。SDPA 之所以快，是因为它背后是专门手写的融合 kernel：NVIDIA 上是 FlashAttention 一系的实现，Intel GPU 上是 oneDNN 的实现。第 17 章，你会用 Triton 自己写一遍。

这就是手写 kernel 的位置：

  • 你的算子是新的。一个新的 attention 变体、一种新的量化格式、一个 MoE 的路由和分组 GEMM，没有现成的库 kernel；
  • 你的算子要改算法才能融合，编译器不会替你改；
  • 你的算子是热点，编译器生成的版本还不够快，你需要知道差在哪、怎么改。

写 kernel 的几种高度

决定手写了，在哪一层写？从 PyTorch eager 到 GPU 指令，中间有好几层，每往下一层，你能控制的就多一些，要写的也多一些：

图 1-2　写 GPU kernel 的几种高度。蓝色是本书覆盖的三层：Triton 是主体，Helion 在它上面（生成 Triton），Gluon 在它下面（和 Triton 共用编译器后端）。橙色箭头：torch.compile 和 Helion 最后都会生成 Triton 代码

最底下是 CUDA（Intel GPU 上对应的是 SYCL）。你写的是一个线程做什么：几万个线程怎么分工、怎么在 shared memory 里交换数据、什么时候同步、访存怎么排才能合并成大块读写，全都自己写。上限最高，代价也最高。一个够快的 softmax 要写 warp 级归约、处理 shared memory 的 bank 冲突，还要为不同行长写不同的版本。

Triton 站在高一层。你写的是一个 program 处理一块数据：上面的 softmax_kernel 里，tl.load 一次读进一整行，tl.max、tl.sum 对整块做归约，没有一行代码在说「第几号线程干什么」。这块数据怎么分给几百个线程、归约怎么在线程之间完成、访存怎么合并，全部由编译器决定。代价是，你拿不到线程级的控制。大多数时候编译器决定得很好；它决定得不好的时候，你需要看懂它的中间表示（第四部分），或者往下走一层到 Gluon（第五部分）。

这块「program」和 CUDA 的「thread block」是什么关系、Triton 的「block」为什么和 CUDA 的「block」不是一回事，第 3 章会用双栏对照讲透。

Triton 的入口就是你在 softmax_kernel 上面看到的那个装饰器。@triton.jit 定义在 Triton 源码的 python/triton/runtime/jit.py，它把一个普通的 Python 函数包成一个 JITFunction 对象。第一次用某组参数启动它时，Triton 把函数体解析成自己的中间表示，一路编译到 GPU 的机器码，并按参数的类型和 tl.constexpr 的取值缓存下来（第 4 章）。

不需要 GPU 也能看到这一路编译出了什么。下面是同一个 softmax_kernel，点按钮会在 Compiler Explorer 里打开三栏：源码、编译器、各级中间表示，默认停在 TTGIR 那一级。现在不必读懂 IR 的每一行，只看两件事：第一行的 #blocked = #ttg.blocked<{...}> 就是编译器替你决定的「这块数据怎么分给线程」，也就是第 20 章要讲的 layout；源码里的每一行和 IR 里对应的几行，CE 会上同样的底色。

Triton → TTGIR 🔬 在 Compiler Explorer 看 IR
import torch
import triton
import triton.language as tl


@triton.jit
def softmax_kernel(x_ptr, y_ptr, n_cols, BLOCK: tl.constexpr):
    row = tl.program_id(0)
    cols = tl.arange(0, BLOCK)
    mask = cols < n_cols
    x = tl.load(x_ptr + row * n_cols + cols, mask=mask, other=-float("inf"))
    x = x - tl.max(x, axis=0)
    e = tl.exp(x)
    y = e / tl.sum(e, axis=0)
    tl.store(y_ptr + row * n_cols + cols, y, mask=mask)


# Compiler Explorer 只编译、不运行，张量是假的，所以这里写 "cuda" 就行（见附录 A 第 8 节）
x = torch.randn(4096, 1024, device="cuda")
y = torch.empty_like(x)
softmax_kernel[(x.shape[0],)](x, y, x.shape[1], BLOCK=1024)
不需要 GPU：CE 只编译不运行（triton_nvidia_370 --arch 86）；Device 面板里可切换 source / TTIR / TTGIR / LLVM IR / PTX / SASS

再往上两层都会生成 Triton。torch.compile 你已经见过了。Helion 是 PyTorch 团队的另一个项目：你写的代码看起来像 PyTorch，只多了一个「按 tile 循环」的结构，它会自动搜索 tile 大小这类参数，最后生成 Triton 代码。往下一层的 Gluon 和 Triton 共用同一套编译器后端，但把 layout、warp 分工这些决定交还给你。

这几层不是互相替代的关系。实际工作中，你多半是这样用的：

  1. 先用 PyTorch eager 写对；
  2. 交给 torch.compile，看它够不够快；
  3. 不够快，或者编译器根本融合不了（像 attention），就用 Triton 手写这个热点；
  4. Triton 自动推导的 layout 或流水不够好，而你确实需要最后那 10–20%，再考虑 Gluon，甚至 CUDA。

这本书的重心在第 3 步：怎么写对、怎么写快、慢了怎么查。第 27 章最后会给一张「什么时候该离开 Triton、往哪走」的决策表。

这一章的要点

  • 深度学习里的大多数算子是访存受限的：GPU 在等数据，不在等计算。数它和显存来回几趟，就知道它大致能跑多快。
  • PyTorch eager 的每个 op 是一次独立的 kernel 启动，中间结果整张写回显存。照着公式写的 softmax 来回 8 趟，融合后 2 趟。在 Max 1100 上，256 MiB 的输入实测慢 4.7 倍。
  • 缓存会改变这笔账：在 L2 有 192 MiB 的 Max 1100 上，矩阵装得进缓存时 eager 只慢 2.7–2.8 倍。同一个优化在不同 GPU 上收益不同，性能数字必须注明是哪一台测的。
  • torch.compile（Inductor）会自动融合，并生成 Triton 代码。对 softmax 这样的算子，它生成的 kernel 已经很好。
  • 它停在要改算法才能融合的地方：attention 需要 online softmax 才能把两次 GEMM 和 softmax 融进一个 kernel。Max 1100 上，手写的融合 kernel（SDPA）比 torch.compile 快 5.7 倍，省掉了 512 MiB 的中间矩阵。新算子、要改算法的融合、不够快的热点，是手写 kernel 的位置。
  • Triton 的抽象是一个 program 处理一块数据：线程映射、访存合并、shared memory 交给编译器，代价是拿不到线程级的控制。Helion 和 torch.compile 在它上面（都生成 Triton），Gluon 在它下面（同一套后端，把 layout 交还给你）。
