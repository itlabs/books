第 8 章 访存的三种写法

这一章想让你带走什么

到目前为止，所有 kernel 都用同一种方式访存：自己算出一个指针张量，每个元素一个地址，交给 tl.load。这是 Triton 最早、也最灵活的写法。但它有一个根本的缺点：编译器看到的只是「一堆地址」，要从这堆地址里反推出「这其实是一个二维矩阵里的一个矩形块」，才能用上硬件的块搬运单元。反推不出来，就只能一个元素一个元素地读。

这一章讲另外两种写法：曾经的 block pointer（Triton 3.9.0 已经移除，只讲怎么迁移），和现在推荐的 tensor descriptor：直接告诉编译器「这是一个 M×K 的矩阵，我要读第几行第几列开始的一个块」。你会看到在 Max 1100 上，同一个 GEMM 只是换了访存写法，就从 13 TFLOP/s 变成了 139 TFLOP/s；打开 IR，看清这 9 倍是从哪里来的；再看同一份 descriptor 代码在 Ampere、Hopper、Intel 三种硬件上分别编成了什么。最后，minillm 的矩阵乘学会根据平台和对齐情况，自动选择写法。

同一个 GEMM，两种访存写法

左边是第 7 章的写法：每个元素一个地址，越界靠 mask。右边是 tensor descriptor：

指针：每个元素一个地址
Triton (Python)
a_ptrs = (a_ptr
    + offs_m[:, None] * stride_am
    + offs_k[None, :] * stride_ak)
...
for k in range(0, K, BK):
    mask = ((offs_m[:, None] < M)
            & (offs_k[None, :] < K - k))
    a = tl.load(a_ptrs, mask=mask,
                other=0.0)
    ...
    a_ptrs += BK * stride_ak
tensor descriptor：描述整个矩阵
Triton (Python)
a_desc = tl.make_tensor_descriptor(
    a_ptr,                 # 基地址
    [M, K],                # 形状
    [stride_am, 1],        # stride
    [BM, BK])              # 每次读的块大小
...
for k in range(0, K, BK):
    # 只给块的左上角；越界自动填 0
    a = a_desc.load([pid_m * BM, k])
    ...

descriptor 版本少了三样东西：没有逐元素的地址计算，没有 mask（越界的部分自动填 0，写的时候自动不写），也没有「指针往前挪一段」。下面把两种写法的完整 GEMM 放在一起，用同样的 tile 和 num_warps 跑：

Triton (Python) 
# arch: sm80 xpu
import torch
import triton
import triton.language as tl

DEVICE = triton.runtime.driver.active.get_active_torch_device()


@triton.jit
def mm_ptr(a_ptr, b_ptr, c_ptr, M, N, K, stride_am, stride_ak, stride_bk, stride_bn, stride_cm, stride_cn,
           BM: tl.constexpr, BN: tl.constexpr, BK: tl.constexpr):
    offs_m = tl.program_id(0) * BM + tl.arange(0, BM)
    offs_n = tl.program_id(1) * BN + tl.arange(0, BN)
    offs_k = tl.arange(0, BK)
    a_ptrs = a_ptr + offs_m[:, None] * stride_am + offs_k[None, :] * stride_ak     # 每个元素一个地址
    b_ptrs = b_ptr + offs_k[:, None] * stride_bk + offs_n[None, :] * stride_bn
    acc = tl.zeros((BM, BN), dtype=tl.float32)
    for k in range(0, K, BK):
        a = tl.load(a_ptrs, mask=(offs_m[:, None] < M) & (offs_k[None, :] < K - k), other=0.0)
        b = tl.load(b_ptrs, mask=(offs_k[:, None] < K - k) & (offs_n[None, :] < N), other=0.0)
        acc = tl.dot(a, b, acc)
        a_ptrs += BK * stride_ak
        b_ptrs += BK * stride_bk
    c_ptrs = c_ptr + offs_m[:, None] * stride_cm + offs_n[None, :] * stride_cn
    tl.store(c_ptrs, acc.to(tl.float16), mask=(offs_m[:, None] < M) & (offs_n[None, :] < N))


@triton.jit
def mm_desc(a_ptr, b_ptr, c_ptr, M, N, K, stride_am, stride_bk, stride_cm,
            BM: tl.constexpr, BN: tl.constexpr, BK: tl.constexpr):
    # 描述三个矩阵：基地址、形状、stride、每次读写的块大小。最后一维必须连续（stride 为 1）
    a_desc = tl.make_tensor_descriptor(a_ptr, [M, K], [stride_am, 1], [BM, BK])
    b_desc = tl.make_tensor_descriptor(b_ptr, [K, N], [stride_bk, 1], [BK, BN])
    c_desc = tl.make_tensor_descriptor(c_ptr, [M, N], [stride_cm, 1], [BM, BN])
    pid_m, pid_n = tl.program_id(0), tl.program_id(1)
    acc = tl.zeros((BM, BN), dtype=tl.float32)
    for k in range(0, K, BK):
        a = a_desc.load([pid_m * BM, k])             # 只给块的左上角坐标；越界的部分自动填 0
        b = b_desc.load([k, pid_n * BN])
        acc = tl.dot(a, b, acc)
    c_desc.store([pid_m * BM, pid_n * BN], acc.to(tl.float16))     # 越界的部分自动不写


M = N = K = 4096
a = torch.randn(M, K, device=DEVICE, dtype=torch.float16)
b = torch.randn(K, N, device=DEVICE, dtype=torch.float16)
ref = a @ b
print(f"{getattr(torch, DEVICE.type).get_device_name()}，triton {triton.__version__}，fp16，{M}×{N}×{K}")
for BM, BN, BK, nw in ((128, 128, 32, 8), (256, 256, 32, 32)):
    grid = (triton.cdiv(M, BM), triton.cdiv(N, BN))
    c = torch.empty_like(ref)
    runs = {
        "指针": lambda: mm_ptr[grid](a, b, c, M, N, K, *a.stride(), *b.stride(), *c.stride(),
                                   BM=BM, BN=BN, BK=BK, num_warps=nw),
        "descriptor": lambda: mm_desc[grid](a, b, c, M, N, K, a.stride(0), b.stride(0), c.stride(0),
                                          BM=BM, BN=BN, BK=BK, num_warps=nw),
    }
    for name, fn in runs.items():
        fn()
        torch.testing.assert_close(c, ref, atol=0.25, rtol=1e-2)
        ms = triton.testing.do_bench(fn)
        print(f"  {BM}×{BN}×{BK}，num_warps={nw:2}  {name:10} {2 * M * N * K / ms / 1e9:6.1f} TFLOP/s")
ms = triton.testing.do_bench(lambda: a @ b)
print(f"  torch.matmul                          {2 * M * N * K / ms / 1e9:6.1f} TFLOP/s")
本地运行：python main.py # 需要 NVIDIA sm_80+ 或 Intel GPU（XPU）；环境见附录 A

运行结果（Max 1100）：

同样的 tile、同样的 num_warps、同样的 tl.dot，只是换了访存写法，快了 9 倍，接近 torch.matmul。第 7 章那个「只有十二分之一」的朴素 GEMM，在 Intel GPU 上主要就输在这里。

编译器看到了什么

图 8-1　两种写法交给编译器的信息不同。指针写法交出的是一堆地址，结构要编译器自己反推；descriptor 直接交出结构，编译器可以直接选用硬件的块搬运指令

两个 kernel 都用上了矩阵单元：TTGIR 里都有 #ttig.dpas，LLVM IR 里都有 33 条 dpas 指令（1024³、128×128×32 的那份）。区别全在访存上。下面是 descriptor 版本在 Max 1100 上的 TTGIR，循环体附近（节选，去掉了 loc(...)）：

TTGIR
#mma = #ttig.dpas<{repeatCount = 8, systolicDepth = 8, executionSize = 16, opsPerChan = 2, threadsPerWarp = 16, warpsPerCTA = [4, 2], repCluster = [4, 2], A = [32, 16], B = [16, 32], C = [32, 32]}>
...
    %ad_0 = tt.make_tensor_descriptor %a_ptr, [%M, %K], [%ad, %c1_i64] : <f16>, <128x32xf16>
...
    %acc_4 = scf.for %acc_5 = %c0_i32 to %K step %c32_i32 iter_args(%acc_6 = %cst) -> (tensor<128x128xf32, #mma>)  : i32 {
      ...
      ttig.descriptor_prefetch %ad_0[%acc, %acc_7] {ttig.block_io = "row_major", ttig.desc_padding = 1 : i32} : !tt.tensordesc<128x32xf16>
      ttig.descriptor_prefetch %bd_1[%acc_7, %acc_3] {ttig.block_io = "row_major", ttig.desc_padding = 1 : i32} : !tt.tensordesc<32x128xf16>
      %acc_8 = tt.descriptor_load %ad_0[%acc, %acc_5] {ttig.block_io = "row_major", ttig.desc_padding = 1 : i32} : !tt.tensordesc<128x32xf16> -> tensor<128x32xf16, #ttg.dot_op<{opIdx = 0, parent = #mma, kWidth = 1}>>
      %acc_9 = tt.descriptor_load %bd_1[%acc_5, %acc_3] {ttig.block_io = "row_major", ttig.desc_padding = 1 : i32} : !tt.tensordesc<32x128xf16> -> tensor<32x128xf16, #ttg.dot_op<{opIdx = 1, parent = #mma, kWidth = 2}>>
      %acc_10 = tt.dot %acc_8, %acc_9, %acc_6, inputPrecision = tf32 : ... -> tensor<128x128xf32, #mma>
      ...
    tt.descriptor_store %cd_2[%acc, %acc_3], %0 {ttig.block_io = "row_major", ttig.desc_padding = 1 : i32} : !tt.tensordesc<128x128xf16>, tensor<128x128xf16, #mma>

三件事：

  • tt.descriptor_load 直接读成了 #ttg.dot_op，也就是矩阵单元要的那种 layout。数据从显存直接进寄存器，中间不经过 shared memory。
  • 每一条读写都带着 ttig.block_io = "row_major"：Intel 后端确认了这是一个二维的行主序块，可以用二维块读写指令。另外，循环里还多了 ttig.descriptor_prefetch：在用这一段之前，先把下一段预取到缓存里。这是 Intel 后端的流水方式。
  • 结果直接从 #mma 写回，连第 7 章那个结尾的 convert_layout 都省了。

指针版本的 TTGIR 走的是另一条路：先用普通的 tt.load 按 #blocked layout 读进来，再 ttg.local_alloc 写进 shared memory（Intel 叫 SLM），再 ttg.local_load 读成 #ttg.dot_op。每一次循环，A 和 B 都要在 SLM 里绕一圈。再往下到 LLVM IR，差别一目了然（同一个 kernel，1024³、128×128×32，Max 1100）：

LLVM IR 里的指令 指针版 descriptor 版
dpas（矩阵乘） 33 33
LSC2DBlockRead（二维块读） 0 5
LSC2DBlockPrefetch（二维块预取） 0 5
LSC2DBlockWrite（二维块写） 0 17
普通的全局读取 224 0

决定这些的是 Intel 后端的两个 pass，都在公开仓库 intel/intel-xpu-backend-for-triton 里（v3.9.0）：third_party/intel/lib/TritonIntelGPUTransforms/MaterializeBlockPointer.cpp 检查 descriptor 的对齐和 stride，给访存打上 ttig.block_io 标记；LowerTo2DBlockLoad.cpp 把带标记的访存改写成二维块读取。LowerTo2DBlockLoad 其实也会处理普通的 tt.load：只要它能从指针表达式里证明出二维的结构，指针写法同样能用上二维块读取。上面这个 kernel，它没能证明出来。descriptor 的意义就在这里：你直接把结构告诉编译器，它不必去猜。

同一份 descriptor，在三种硬件上编成了什么

tensor descriptor 本身不是什么「加速指令」，它只是一种更结构化的描述，让编译器有机会用上硬件的块搬运单元。有没有这样的单元、用不用得上，取决于硬件。我用 3.9.0 把同一个 descriptor GEMM 编到三种目标上（NVIDIA 的两种用附录 A 第 8 节的离线编译，不需要 GPU）：

目标 descriptor 的读取编成了什么 矩阵乘
Intel Max 1100 二维块读写 LSC2DBlockRead / Write，外加预取 dpas
NVIDIA Hopper（sm_90） TMA：cp.async.bulk.tensor（7 条），kernel 里还要现场创建 tensormap wgmma
NVIDIA Ampere（sm_86，A10） kernel 里创建的 descriptor：普通的异步拷贝 cp.async（12 条）；host 端创建的：普通的 ld.global，再一条条写进 shared memory mma.sync

TMA（tensor memory accelerator）是 Hopper 起才有的硬件单元：给它一个描述符和坐标，它自己把一个多维的块从显存搬进 shared memory，不占用线程。Intel 的二维块读写也是类似的思路。Ampere 没有这样的单元，descriptor 只能编成和指针写法差不多的指令，所以在 A10 上，换写法不一定会变快，host 端创建的那种甚至可能更慢（它没用上异步拷贝）。本书还没有在 A10 上实测这两种写法的差距，这是第 13 章和附录里待补的数据。

两种创建方式

上面的 kernel 是在 kernel 里用 tl.make_tensor_descriptor 创建 descriptor 的。另一种方式是在 host 端创建好，作为参数传进去：

Triton (Python)
from triton.tools.tensor_descriptor import TensorDescriptor

a_desc = TensorDescriptor.from_tensor(a, [BLOCK_M, BLOCK_K])     # 形状、stride 从张量里取
...
_matmul_desc_kernel[grid](a_desc, b_desc, c_desc, K, BLOCK_M=..., BLOCK_N=..., BLOCK_K=...)

kernel 里就直接用传进来的 descriptor：a_desc.load([...])。minillm 用的是这种写法（下文）。两种方式的区别：

  • host 端创建：kernel 的参数更少，代码更干净。在 Hopper 上，描述符在 host 端就准备好了。
  • kernel 里创建：形状、stride 可以在 kernel 里算出来（比如按 batch 偏移以后再描述）。代价是在 Hopper 上要现场创建 tensormap，需要一块全局的临时内存。从编译元数据看，上面那个 kernel 编到 sm_90 时 global_scratch_size = 384（3 个 descriptor，每个 128 字节），编到 sm_86 时是 0。这块内存由你提供：调用之前要用 triton.set_allocator(...) 注册一个分配函数，否则启动时会报 Kernel requires a runtime memory allocation, but no allocator was set（python/triton/runtime/_allocation.py）。

不管哪种方式，descriptor 都有硬性的对齐要求。host 端的检查写在 python/triton/tools/tensor_descriptor.py 的 TensorDescriptor.__post_init__ 里：

  • 基地址必须是 16 字节的倍数（base must be 16-byte aligned）；
  • 除最后一维外的 stride，必须是 16 字节的倍数（strides must be 16-byte aligned）；
  • 最后一维必须连续（Last dimension must be contiguous）；
  • 越界部分的填充值只能是 0（默认）或 NaN。

第二条最容易踩到。一个 1000×777 的 fp16 矩阵，行 stride 是 777 × 2 = 1554 字节，不是 16 的倍数，就不能用 descriptor。我在 Max 1100 上试过，TensorDescriptor.from_tensor 直接抛出 AssertionError: strides must be 16-byte aligned。转置视图（最后一维的 stride 不是 1）也不行。遇到这些情况，只能退回指针写法。

block pointer：曾经的第二种写法

如果你读过 Triton 官方教程的旧版本，或者别人两年前写的 kernel，会看到第三种写法：

Triton (Python)
a_bptr = tl.make_block_ptr(a_ptr, shape=(M, K), strides=(stride_am, stride_ak),
                           offsets=(pid_m * BM, 0), block_shape=(BM, BK), order=(1, 0))
for k in range(0, K, BK):
    a = tl.load(a_bptr, boundary_check=(0, 1))
    ...
    a_bptr = tl.advance(a_bptr, (0, BK))

这就是 block pointer，它是 tensor descriptor 的前身，思路一样：描述形状和 stride，让编译器知道这是一个块。它在 Triton 3.9.0 里已经被移除了。python/triton/language/core.py 里的 make_block_ptr 和 advance 只剩下一句 raise NotImplementedError。在 3.9.0 上跑上面的代码（包在一个完整的 kernel 里）：

运行结果（Max 1100，节选）：

    a_bptr = tl.make_block_ptr(a_ptr, shape=(M, K), strides=(stride_am, stride_ak),
             ^
Block pointers have been removed in favor of the tensor descriptor API

迁移到 tensor descriptor 是一一对应的：

block pointer tensor descriptor
tl.make_block_ptr(base, shape, strides, offsets, block_shape, order) tl.make_tensor_descriptor(base, shape, strides, block_shape)，offsets 挪到每次 load 的坐标里
tl.load(bptr, boundary_check=(0, 1)) desc.load([row, col])，边界自动处理
tl.advance(bptr, (0, BK)) 不需要；下一次 load 直接给新坐标
order=(1, 0) 不需要；descriptor 要求最后一维连续

block pointer 的 order 参数允许描述「列主序」的块，descriptor 不行，它要求最后一维连续。原来用 order=(0, 1) 读转置矩阵的代码，迁移时要么先把数据转成连续的，要么改写成 descriptor 读出来以后用 tl.trans 在寄存器里转置。

该用哪种写法

情况 推荐写法 原因
Intel GPU 上的矩阵乘、批量的块读写 tensor descriptor 能编成二维块读写，Max 1100 上快 9 倍
Hopper（sm_90）及以上 tensor descriptor 能编成 TMA，这也是第 15 章 warp specialization 的前提
Ampere（如 A10） 指针，或者 kernel 里创建的 descriptor 没有块搬运单元；host 端 descriptor 编不出异步拷贝。本书尚未实测，以你自己的测量为准
stride 不对齐、最后一维不连续 指针 descriptor 用不了
不规则的访存：gather、按索引读、每个元素不同的 mask 指针 descriptor 只能描述规则的矩形块

逐点和按行归约的 kernel（第 4–6 章）都是一维的连续访存，coalesce pass 已经能处理得很好（第 3 章），用指针写法就够了。

minillm：让矩阵乘自己选写法

这一章往 minillm/kernels/matmul.py 里加了三样东西：

Python
def descriptor_ok(*tensors) -> bool:
    """TensorDescriptor 的要求（python/triton/tools/tensor_descriptor.py）：
    基地址 16 字节对齐、除最后一维外的 stride 是 16 字节的倍数、最后一维连续。"""
    return all(t.data_ptr() % 16 == 0 and t.stride(-1) == 1 and
               all(s * t.element_size() % 16 == 0 for s in t.stride()[:-1]) for t in tensors)


def mm(a: torch.Tensor, b: torch.Tensor) -> torch.Tensor:
    """minillm 默认使用的矩阵乘：能用 descriptor 就用，否则退回指针版。"""
    n = b.shape[1]
    out_ok = n * a.element_size() % 16 == 0       # 输出是新分配的连续张量，它的行 stride 就是 N
    if prefer_descriptor() and a.shape[0] and n and out_ok and descriptor_ok(a, b):
        return matmul_desc(a, b)
    return matmul(a, b)
  • matmul_desc：host 端创建 descriptor 的版本，默认 256×256×32、32 个 warp（上面实测最快的配置）；
  • descriptor_ok：照着 TensorDescriptor 的检查写的对齐判断；
  • mm：minillm 后面的章节默认使用的矩阵乘。prefer_descriptor() 在 Intel GPU 和 Hopper 及以上返回真，其它平台（包括 A10）返回假，理由就是上一节的表。第 7 章的 matmul（指针版）保持不变，作为退路。

新增的测试在 tests/test_matmul.py 的后半段：1000×776×1032 这种不是 tile 整数倍、但行 stride 对齐的形状（检验 descriptor 自己处理边界）；777 列和转置视图会被 descriptor_ok 拒绝；mm 在两种情况下都算对。

这一章的要点

  • Triton 有三种访存写法：指针（每个元素一个地址，最灵活）、block pointer（3.9.0 已移除，make_block_ptr / advance 只会抛 NotImplementedError）、tensor descriptor（描述基地址、形状、stride、块大小，按坐标读写，边界自动处理）。
  • 在 Max 1100 上，同一个 GEMM 只换访存写法就快了 9 倍（13 → 139 TFLOP/s）。descriptor 版本的读取直接编成 ttig.block_io 标记的二维块读写，并且直接读成 #ttg.dot_op，不经过 SLM。指针版本要先读、写进 SLM、再读出来，没有二维块读取。决定这一点的是 Intel 后端的 MaterializeBlockPointer 和 LowerTo2DBlockLoad。
  • descriptor 是一种结构化的描述，不是加速指令：Intel 上编成二维块读写，Hopper 上编成 TMA，Ampere 上只能编成普通的拷贝。用不用它，要看硬件。
  • 硬性要求：基地址和除最后一维外的 stride 都是 16 字节的倍数，最后一维连续。不满足就只能用指针。在 Hopper 上，kernel 里创建 descriptor 需要先 triton.set_allocator。
  • minillm 的 mm 在 Intel 和 Hopper+ 上默认用 descriptor，对齐不满足或其它平台时退回指针版。
