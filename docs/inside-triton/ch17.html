第 17 章 FlashAttention 前向

这一章想让你带走什么

第 1 章留了一个悬念：attention 是 torch.compile 融合不了的，因为要换一个算法才能把两次矩阵乘和中间的 softmax 放进一个 kernel。第 6 章准备好了那个算法的核心，online softmax。这一章把它和第三部分讲过的手段合在一起：tensor descriptor、tile 的选择、寄存器预算、看 IR，写出 minillm 的 FlashAttention 前向，并和 PyTorch 的 scaled_dot_product_attention（SDPA）正面比较。

读完你会拿到四样东西。一是算法本身，用一个只用标准库的模型验证它和教科书公式完全一致，并算出一个意外的结论：FlashAttention 的算术强度恰好等于 BLOCK_M。二是一个 60 行的 kernel，在 Max 1100 上因果 attention 和 SDPA 一样快，非因果达到 SDPA 的 88% 左右。三是两个从 IR 里挖出来的发现：tl.trans(k) 根本没有产生转置，K 被直接按列读进了矩阵单元；Intel 后端默认会把 Q 的读取挪进循环里重读，在因果 attention 上这让 kernel 慢了 19%。四是一个精度陷阱：把缩放因子提前乘到 Q 上看起来更快，但在注意力集中时，误差变成了原来的 8 倍。

教科书写法的问题

attention 的公式是 O = softmax(Q·Kᵀ·scale)·V，scale = 1/√D。Q、K、V、O 的形状都是 (Z, H, N, D)：Z 个样本，每个 H 个头，每个头 N 个 token，每个 token 一个 D 维向量。照着公式写成 PyTorch：

Python
s = q @ k.transpose(-1, -2) * q.shape[-1] ** -0.5     # (Z, H, N, N)：注意力矩阵
o = torch.softmax(s, dim=-1) @ v

问题在中间那个 (Z, H, N, N) 的矩阵。N = 4096、32 个头、4 个样本时，它有 4 × 32 × 4096² 个元素，bf16 就是 4 GiB，softmax 的输出还要再占 4 GiB。更糟的是，它要在显存里走好几趟：矩阵乘写出去，softmax 读进来再写出去，第二次矩阵乘再读进来。第 1 章「数趟数」的方法在这里同样适用。

FlashAttention 的思路是：注意力矩阵一块一块地算，算完一块就用掉，永远不写回显存。一个 program 负责 Q 的 BLOCK_M 行，沿着 N 方向每次读 K、V 的 BLOCK_N 行，算出 BLOCK_M × BLOCK_N 的一小块分数，立刻做 softmax、乘上 V、累加进输出。

图 17-1　FlashAttention 的分块。左：一个 program 拿着 Q 的一块（蓝），依次读 K、V 的每一块（橙），算出一小块分数，用完就丢。右：因果 attention 里第 i 行只看前 i 列，对角线以上的块整块跳过，计算量减半

把 online softmax 用到 attention 上

第 6 章的 online softmax 一边扫一边维护两个量：到目前为止的最大值 m，以及以 m 为基准的指数和 l。每来一块新数据，如果最大值变大了，之前的 l 就要乘上修正因子 α = exp(m − m_new)。

attention 要多维护一样东西：输出的累加器 acc = Σ exp(s_j − m)·v_j。它也是「以 m 为基准」算出来的，所以最大值一变，acc 也要乘上同一个 α。扫完整行以后，acc / l 就是这一行的输出。下面用纯 Python 把两种算法都写一遍，比一比结果；再数一数两者各要从显存搬多少字节。只用标准库，直接点运行：

Python 
# FlashAttention 的两件事，只用标准库：
#   ① 分块 + online softmax 算出来的，和「先算整个注意力矩阵」完全一样；
#   ② 它少搬了多少字节。
import math
import random

random.seed(0)
N, D, BLOCK_M, BLOCK_N = 10, 4, 4, 3            # 故意取不整除的大小：最后一块是不完整的
Q, K, V = ([[random.gauss(0, 1) for _ in range(D)] for _ in range(N)] for _ in range(3))
scale = 1 / math.sqrt(D)
dot = lambda a, b: sum(x * y for x, y in zip(a, b))

# 直接算：每一行先算出整行的 S = q·Kᵀ，softmax，再乘 V
ref = []
for q in Q:
    s = [dot(q, k) * scale for k in K]
    e = [math.exp(x - max(s)) for x in s]
    ref.append([sum(e[j] * V[j][d] for j in range(N)) / sum(e) for d in range(D)])

# FlashAttention：Q 按 BLOCK_M 行一块，K、V 按 BLOCK_N 行一块；每一行只记 m、l、acc 三样东西
out = []
for i0 in range(0, N, BLOCK_M):
    for q in Q[i0:i0 + BLOCK_M]:
        m, l, acc = -math.inf, 0.0, [0.0] * D
        for j0 in range(0, N, BLOCK_N):
            s = [dot(q, k) * scale for k in K[j0:j0 + BLOCK_N]]       # 这一块的 BLOCK_N 个分数
            m_new = max(m, max(s))
            alpha = math.exp(m - m_new)                                 # 旧的累加按新的最大值缩小
            p = [math.exp(x - m_new) for x in s]
            l = l * alpha + sum(p)
            acc = [a * alpha + sum(pj * v[d] for pj, v in zip(p, V[j0:j0 + BLOCK_N])) for d, a in enumerate(acc)]
            m = m_new
        out.append([a / l for a in acc])                                # 最后才除以 l
print(f"① 两种算法的最大差别：{max(abs(a - b) for r, o in zip(ref, out) for a, b in zip(r, o)):.1e}")

# ② 一个头要从显存搬多少字节（bf16，每个元素 2 字节）。
#    naive：S = Q·Kᵀ 写出去，softmax 读 S 写 P，P·V 再读 P；Q、K、V 各读一遍，O 写一遍
#    flash：Q 读一遍、O 写一遍；每一块 Q 都要把整个 K、V 读一遍（不算 L2 命中）
print("② 一个头、head_dim=128：")
print("      N    naive 搬的字节   强度     flash（BLOCK_M=64 / 128 / 256）搬的字节与强度")
D = 128
for n in (1024, 4096, 16384):
    flops = 4 * n * n * D
    naive = 4 * n * n * 2 + 4 * n * D * 2
    cells = []
    for bm in (64, 128, 256):
        flash = 2 * n * D * 2 + 2 * math.ceil(n / bm) * n * D * 2
        cells.append(f"{flash / 2**20:6.0f} MiB {flops / flash:4.0f}")
    print(f"  {n:6} {naive / 2**20:10.0f} MiB {flops / naive:6.0f}     " + "   ".join(cells))

第一部分：两种算法的差别是 10⁻¹⁶，也就是双精度浮点的舍入误差，它们在数学上完全等价。FlashAttention 不是近似算法。

第二部分的结论比较出人意料。naive 写法要来回搬 N × N 的矩阵 4 趟；FlashAttention 不写注意力矩阵，但每一块 Q 都要把整个 K、V 读一遍，一共读 N / BLOCK_M 遍。算一算强度：运算量是 4·N²·D（两次矩阵乘），flash 搬的字节约为 2 × (N / BLOCK_M) × N × D × 2 = 4·N²·D / BLOCK_M，两者一除，强度恰好等于 BLOCK_M。BLOCK_M = 64 时，它搬的字节几乎和 naive 一样多。

第 11 章量过 Max 1100 的拐点：bf16 矩阵单元 172 TFLOP/s ÷ 显存 774 GB/s ≈ 222 FLOP/字节。只有 BLOCK_M = 256 时强度（241–252）才越过拐点；128 只有 124。这是「不算 L2 命中」的最坏情况：同一个头的那十几个 program 大致同时在跑，读的是同一份 K、V，真实的显存流量会少得多。下面会看到，BLOCK_M = 128 和 256 实测差不多。但模型说明了一件事：FlashAttention 最大的收益不是少搬字节，而是不需要 N × N 的显存，以及把三个 kernel 变成了一个。

kernel

minillm 的 kernels/attention.py：

Triton (Python)
@triton.jit
def _attn_fwd_kernel(q_ptr, k_ptr, v_ptr, o_ptr, sm_scale, N_CTX, ROWS,
                     HEAD_DIM: tl.constexpr, BLOCK_M: tl.constexpr, BLOCK_N: tl.constexpr,
                     CAUSAL: tl.constexpr, EVEN_M: tl.constexpr, EVEN_N: tl.constexpr):
    pid_m = tl.program_id(0)
    hz = tl.program_id(1)                          # 第几个 (batch, head)
    # 把 (Z, H, N, D) 看成 (Z·H·N, D) 的二维矩阵：第 hz 个头从第 hz·N 行开始
    q_desc = tl.make_tensor_descriptor(q_ptr, [ROWS, HEAD_DIM], [HEAD_DIM, 1], [BLOCK_M, HEAD_DIM])
    k_desc = tl.make_tensor_descriptor(k_ptr, [ROWS, HEAD_DIM], [HEAD_DIM, 1], [BLOCK_N, HEAD_DIM])
    v_desc = tl.make_tensor_descriptor(v_ptr, [ROWS, HEAD_DIM], [HEAD_DIM, 1], [BLOCK_N, HEAD_DIM])
    base = hz * N_CTX
    offs_m = pid_m * BLOCK_M + tl.arange(0, BLOCK_M)
    q = q_desc.load([base + pid_m * BLOCK_M, 0])
    qk_scale = sm_scale * 1.4426950408889634        # 用 exp2 代替 exp：exp(x) = exp2(x·log2(e))

    m_i = tl.full([BLOCK_M], -float("inf"), tl.float32)   # 每一行到目前为止的最大值
    l_i = tl.zeros([BLOCK_M], tl.float32)                  # 每一行以 m_i 为基准的指数和
    acc = tl.zeros([BLOCK_M, HEAD_DIM], tl.float32)        # 还没除以 l_i 的输出
    # causal：第 i 行只看前 i 列，这一块之后的 K、V 整块跳过
    hi = tl.minimum((pid_m + 1) * BLOCK_M, N_CTX) if CAUSAL else N_CTX
    for start_n in range(0, hi, BLOCK_N):
        k = k_desc.load([base + start_n, 0])
        qk = tl.dot(q, tl.trans(k)) * qk_scale             # BLOCK_M × BLOCK_N，fp32
        offs_n = start_n + tl.arange(0, BLOCK_N)
        if CAUSAL:
            qk = tl.where(offs_m[:, None] >= offs_n[None, :], qk, -float("inf"))
        elif not EVEN_N:
            # 最后一块越过了这个头的末尾：读到的是下一个头的 K（或越界填的 0），要屏蔽掉
            qk = tl.where(offs_n[None, :] < N_CTX, qk, -float("inf"))
        m_new = tl.maximum(m_i, tl.max(qk, 1))
        p = tl.math.exp2(qk - m_new[:, None])
        alpha = tl.math.exp2(m_i - m_new)                  # 最大值变大了：之前的累加要缩小这么多倍
        l_i = l_i * alpha + tl.sum(p, 1)
        v = v_desc.load([base + start_n, 0])
        acc = tl.dot(p.to(v.dtype), v, acc * alpha[:, None])
        m_i = m_new
    o = (acc / l_i[:, None]).to(o_ptr.dtype.element_ty)
    if EVEN_M:
        o_desc = tl.make_tensor_descriptor(o_ptr, [ROWS, HEAD_DIM], [HEAD_DIM, 1], [BLOCK_M, HEAD_DIM])
        o_desc.store([base + pid_m * BLOCK_M, 0], o)
    else:
        # N 不是 BLOCK_M 的整数倍：最后一块的尾巴属于下一个头，descriptor 不知道头的边界，改用带 mask 的 store
        offs_d = tl.arange(0, HEAD_DIM)
        o_ptrs = o_ptr + (base + offs_m)[:, None].to(tl.int64) * HEAD_DIM + offs_d[None, :]
        tl.store(o_ptrs, o, mask=offs_m[:, None] < N_CTX)

逐段看：

  • grid 是二维的：(cdiv(N, BLOCK_M), Z·H)。第一维是这个头里的第几块 Q，第二维是第几个头。每个 program 只读自己那个头的 K、V。
  • descriptor 把四维张量看成二维：连续存放的 (Z, H, N, D) 就是一个 (Z·H·N, D) 的矩阵，第 hz 个头从第 hz·N 行开始。代价是 descriptor 只知道整个矩阵的边界，不知道头和头之间的边界：N 不是块大小的整数倍时，最后一块会读进下一个头的数据。K 那边用 where 把多出来的列设成 −∞（EVEN_N 为假时）；O 那边如果用 descriptor 写，会把下一个头的输出覆盖掉，所以 EVEN_M 为假时改用带 mask 的指针 store。我试过换成三维 descriptor（形状 (Z·H, N, D)，块 (1, BLOCK_M, D)），它知道头的边界，但在 Max 1100 上慢了 2%–4%，所以没用。
  • 两次 tl.dot：第一次是 Q·Kᵀ，得到 fp32 的分数块；第二次是 P·V，P 先转回 bf16（矩阵单元的输入），累加器仍是 fp32。累加器在进入第二次 tl.dot 之前先乘上 α，tl.dot(a, b, acc) 就是 a·b + acc，正好把修正和累加合成一步。
  • exp2 代替 exp：exp(x) = 2^(x·log₂e)。硬件上通常只有以 2 为底的指数指令，tl.exp 本来也要先乘一个 log₂e。把 log₂e 并进 qk_scale，每个元素少一次乘法；m、l 的含义不变，只是换了底。
  • causal 只循环到对角线：hi = (pid_m + 1) · BLOCK_M。对角线以上的块（图 17-1 右边的白色部分）一块也不读，计算量减半；对角线上的块再用 where 逐元素 mask。
  • 除以 l 放在最后：循环里只累加未归一化的 acc，扫完整行才除一次。

attention() 这个包装函数负责选块大小（下一节）、处理 EVEN_M / EVEN_N。tests/test_attention.py 对 N = 1、17、128、1000、1024，D = 64、128，fp16 / bf16，因果 / 非因果的所有组合和 fp32 的 SDPA 比较，共 43 个测试。

和 PyTorch 比

把三种写法放在一起，总 token 数固定为 16384（N = 1024 时 16 个样本，N = 16384 时 1 个），32 个头，D = 128：

Triton (Python) 
# arch: sm80 xpu
import torch
import torch.nn.functional as F
import triton

from minillm import DEVICE
from minillm.kernels.attention import attention

gpu = getattr(torch, DEVICE.type)


def naive(q, k, v, causal):
    """教科书写法：把 N × N 的注意力矩阵整个算出来、存下来。"""
    s = q @ k.transpose(-1, -2) * q.shape[-1] ** -0.5
    if causal:
        n = q.shape[-2]
        s = s.masked_fill(torch.ones(n, n, dtype=torch.bool, device=q.device).triu(1), float("-inf"))
    return torch.softmax(s, dim=-1) @ v


def measure(fn):
    """返回 (毫秒, 除输入以外的峰值显存 GiB)。"""
    gpu.synchronize(); gpu.empty_cache(); gpu.reset_peak_memory_stats()
    base = gpu.memory_allocated()
    fn(); gpu.synchronize()
    peak = (gpu.max_memory_allocated() - base) / 2**30
    return triton.testing.do_bench(fn), peak


H, D = 32, 128
print(f"{gpu.get_device_name()}，triton {triton.__version__}，torch {torch.__version__}，bf16，{H} 个头，head_dim {D}")
for causal in (False, True):
    print(f"causal={causal}：  N      naive（PyTorch 逐步算）       SDPA                 minillm")
    for n in (1024, 4096, 16384):
        z = 16384 // n                                  # 每一行的 token 总数都是 16384
        q, k, v = (torch.randn(z, H, n, D, device=DEVICE, dtype=torch.bfloat16) for _ in range(3))
        torch.testing.assert_close(attention(q, k, v, causal), F.scaled_dot_product_attention(q, k, v, is_causal=causal),
                                   atol=2e-2, rtol=2e-2)
        flops = 4 * z * H * n * n * D * (0.5 if causal else 1)
        cells = []
        # naive 要存下 z·H·N·N 个 bf16 的注意力矩阵（还有 softmax 的输出），先估一下放不放得下
        fits = 3 * z * H * n * n * 2 < 0.8 * gpu.get_device_properties().total_memory
        for fn in (lambda: naive(q, k, v, causal) if fits else None,
                   lambda: F.scaled_dot_product_attention(q, k, v, is_causal=causal),
                   lambda: attention(q, k, v, causal)):
            r = measure(fn) if fits or len(cells) else None
            cells.append("      显存不够       " if r is None else f"{flops / r[0] / 1e9:5.1f} TF/s {r[1]:5.2f} GiB")
        print(f"            {n:6}   " + "   ".join(cells))
        del q, k, v

  • naive 写法慢了约 4 到 12 倍，还要几个 GiB 的显存：N = 4096 时是 8.12 GiB，正好是两个 4 GiB 的 bf16 矩阵（分数和 softmax 的输出）加上输出。N = 16384 时，光分数矩阵就要 16 GiB，算上 softmax 的输出和中间结果放不下，脚本直接跳过了。因果时它更慢，因为 mask 要再写一个 N × N 的矩阵，而且上三角那一半照算不误。
  • SDPA 和 minillm 都只要 0.12 GiB，也就是输出 O 本身的大小。用 PyTorch 的 profiler 看，SDPA 在 Max 1100 上只启动了一个名叫 micro_sdpa 的 kernel，它来自 oneDNN（第 1 章）。
  • 因果 attention，minillm 和 SDPA 一样快（三个长度上互有胜负，差别在 3% 以内）；非因果，minillm 是 SDPA 的 85%–88%。差距在哪里，我没有深究：micro_sdpa 是 oneDNN 专门为这个算子写的 kernel，不是用 Triton 写的，它用了哪些技巧本书没有去读。

这个脚本连着测了几十秒，GPU 的频率会随温度下降。我单独测同一个非因果 kernel：刚开始是 94 TFLOP/s，连续跑几轮以后稳定在 84 左右；SDPA 同样从 113 降到 104。所以只比较同一次运行里相邻的两个数字，不要拿这张表和下面单独测的表直接比。下面那些扫参数的实验，每个配置测量之前都先停 4–5 秒。

head_dim = 64 时（同样 4 × 32 个头、N = 4096），SDPA 非因果 98.1、因果 81.7 TFLOP/s，minillm 分别是 91.1 和 76.7，大约是 SDPA 的 93%。

选 tile：又是寄存器

一个 program 要同时在寄存器里放三样大东西：Q 的一块（BLOCK_M × D，bf16）、累加器（BLOCK_M × D，fp32）、分数块（BLOCK_M × BLOCK_N，fp32）。第 12 章的规则在这里同样成立：寄存器放不下就溢出，溢出就慢。在 Max 1100 上扫一遍（D = 128，非因果，Z = 4、H = 32、N = 4096，num_stages = 2）：

BLOCK_M × BLOCK_N num_warps 每个 warp 几行 累加器/线程 n_spills TFLOP/s
64 × 64 4 16 128 273 55.5
64 × 64 8 8 64 85 54.0
128 × 64 8 16 128 205 74.3
128 × 64 16 8 64 55 94.2
128 × 128 16 8 64 39 74.3
128 × 32 16 8 64 19 81.3
256 × 64 16 16 128 205 90.0
256 × 64 32 8 64 55 94.0
256 × 32 32 8 64 19 81.5
256 × 128 32 8 64 39 102.8

（「累加器/线程」= BLOCK_M × D ÷ (16 × num_warps)，Intel 上一个 warp 16 个线程，第 12 章。）

  • 每个 warp 分 8 行最好。分到 16 行时，累加器每个线程 128 个，加上 Q 和分数块，溢出 200 多；分到 8 行时溢出降到几十。所有 8 行的配置都比 16 行的快。所有配置的 n_regs 都是 256：Intel 后端发现溢出太多时，会自动换成大寄存器模式（第 6 章），这已经是用满大寄存器以后的溢出量。
  • BLOCK_N 不是越小越好。32 的溢出最少，但每读一块 K、V 只做一半的计算，循环的固定开销（求最大值、算 α、缩放累加器）占比变大。
  • BLOCK_M = 128 和 256 差不多，和上一节模型的预测（强度 124 对 252）不一样：同一个头的 program 读同一份 K、V，L2 替我们挡住了大部分重复读取。

因果时，最好的配置换了：256 × 128 的溢出从 39 涨到 368，只有 28.5 TFLOP/s。多出来的那个 BLOCK_M × BLOCK_N 的比较和 where 也要占寄存器。因果时退回 256 × 64。head_dim = 64 时没有任何溢出，256 × 128 也最好。最好的配置随 D、随因果与否而变，这正是第 14 章 autotune 的用武之地。minillm 为了测试快，把这几个配置写成了一张表（launch_config），每一项都有本节的实测为据。

编译器替你做了什么

拿 kernel.asm["ttgir"] 看循环里的几条关键指令（256 × 64，D = 128，去掉了 loc(...)，类型有删节）：

TTGIR
      ttig.descriptor_prefetch %k_desc[%k_11, %c0_i32] {ttig.block_io = "column_major", ...} : !tt.tensordesc<64x128xbf16>
      ttig.descriptor_prefetch %v_desc[%k_11, %c0_i32] {ttig.block_io = "row_major", ...} : !tt.tensordesc<64x128xbf16>
      %k_12 = tt.descriptor_load %k_desc[%k, %c0_i32] {ttig.block_io = "column_major", ...} : !tt.tensordesc<64x128xbf16> -> tensor<128x64xbf16, #ttg.dot_op<{opIdx = 1, parent = #mma, kWidth = 2}>>
      %v = tt.descriptor_load %v_desc[%k, %c0_i32] {ttig.block_io = "row_major", ...} : !tt.tensordesc<64x128xbf16> -> tensor<64x128xbf16, #ttg.dot_op<{opIdx = 1, parent = #mma, kWidth = 2}>>
      %q_13 = tt.descriptor_load %q_desc[%q_4, %c0_i32] {ttig.block_io = "row_major", ...} : !tt.tensordesc<256x128xbf16> -> tensor<256x128xbf16, #ttg.dot_op<{opIdx = 0, parent = #mma, kWidth = 1}>>
      %qk_14 = tt.dot %q_13, %k_12, %cst_3 : tensor<256x128xbf16, ...> * tensor<128x64xbf16, ...> -> tensor<256x64xf32, #mma>
      %acc_29 = tt.dot %acc_28, %v, %acc_27 : tensor<256x64xbf16, ...> * tensor<64x128xbf16, ...> -> tensor<256x128xf32, #mma>

转置去哪了

kernel 里写的是 tl.dot(q, tl.trans(k))，IR 里却没有任何 tt.trans。描述符的块是 64 × 128（BLOCK_N × D，K 在内存里的样子），descriptor_load 出来的却直接是 128 × 64（D × BLOCK_N，矩阵乘要的 Kᵀ），标注 block_io = "column_major"。Intel 的二维块读取指令可以在读的同时转置，编译器把 trans 折进了 load。V 不需要转置，就是 row_major。所以写 attention 的时候不必预先把 K 转置好再存。

在 NVIDIA 上又是另一番样子。用附录 A 第 8 节的离线编译，把同样结构的指针版 kernel（128 × 64，8 个 warp，3 级流水）编到 sm_86，看 TTGIR 的循环体（节选）：

TTGIR
      %qk_75 = ttg.local_load %k_74 token %k_73 : !ttg.memdesc<64x128xf16, #shared, #smem, mutable> -> tensor<64x128xf16, #linear>
      %qk_76 = tt.trans %qk_75 {order = array<i32: 1, 0>} : tensor<64x128xf16, #linear> -> tensor<128x64xf16, #ttg.dot_op<{opIdx = 1, parent = #mma, kWidth = 2}>>
      %q_77 = ttg.local_load %q_20 : !ttg.memdesc<128x128xf16, #shared, #smem> -> tensor<128x128xf16, #ttg.dot_op<{opIdx = 0, parent = #mma, kWidth = 2}>>
      %qk_78 = tt.dot %q_77, %qk_76, %cst_4, inputPrecision = tf32 : ...

K 先用 cp.async 搬进 shared memory（第 13 章的多缓冲），读回寄存器时，编译器专门挑了一个 #linear layout，转置以后正好是矩阵乘要的 dot_op layout。tt.trans 还在，但我推测它只是给寄存器重新编号，不搬数据。第 21 章讲 linear layout 时再验证。

Q 被挪进了循环

再看 %q_13：Q 的 descriptor_load 出现在循环体里面。kernel 里明明是在循环之前读一次 Q。

这是 Intel 后端一个 pass 做的事：ReduceVariableLiveness（third_party/intel/lib/TritonIntelGPUTransforms/ReduceVariableLiveness.cpp）。它发现循环里寄存器压力很大，而 Q 这个 256 × 128 的大张量从循环开始一直活到结束，于是把它的 load 挪到用它的地方，每一轮重新读一次（数据多半还在缓存里）。Q 不必一直占着寄存器，溢出就少了。源码注释里写着，这个变换就是为 attention 这类 kernel 做的。回头看上面 sm_86 的那段 IR，%q_77 = ttg.local_load %q_20 也在循环里：NVIDIA 后端把 Q 放进 shared memory（循环之前的 ttg.local_alloc），每一轮再读回寄存器。两个后端用不同的办法做了同一件事：不让 Q 在整个循环里一直占着寄存器。

它是一个编译选项，默认打开，可以在启动 kernel 时传 reduce_variable_liveness=False 关掉。关掉以后 Q 回到循环外面，对比一下（256 × 64 和 256 × 128，D = 128）：

情形 配置 打开（默认） 关掉
非因果 256 × 128 102.4 TFLOP/s，溢出 39 83.6，溢出 111
非因果 256 × 64 93.8，溢出 55 92.1，溢出 85
因果 256 × 64 78.0，溢出 60 96.4，溢出 91

非因果时，这个 pass 有用，256 × 128 上差了 22%。但因果时正好反过来：关掉它、溢出更多，反而快了 24%。为什么？第 22 章会一步步定位：触发条件是对角线上的那个 mask，不是循环次数；真正的差别在 Triton 下面两级，IGC 的寄存器分配器在一种 IR 上用上了减少 bank 冲突的策略，在另一种上没有。「溢出越少越快」只是一个经验法则：编译器为了减少溢出做的变换，本身也有代价。minillm 在因果、D = 128 时关掉这个 pass。

一个精度陷阱

我最初发现这件事，是因为另一个改动。把缩放因子提前乘到 Q 上：q = (q * qk_scale).to(q.dtype)，循环里就省掉了每个元素一次乘法。Triton 官方教程在 2023 年 7 月到 9 月之间就是这么写的（PR #1917 引入，#2332 改成了在循环里用 fp32 缩放）。我试了一下，因果时快了 19%，非因果时没有变化。仔细一看，原因并不是省了乘法：q * qk_scale 不再是一个 load 了，ReduceVariableLiveness 没法把它挪进循环，Q 就一直留在寄存器里，和上面关掉 pass 是同一个效果。

这个改动还有代价：乘完的 Q 要转回 bf16 才能进矩阵单元，多了一次舍入。拿 fp32 算出来的 SDPA 做参考，比较最大误差和平均误差（Z = 4、H = 32、N = 4096、D = 128）：

输入 SDPA（bf16） minillm：循环里缩放 提前缩放 Q
Q、K ~ N(0, 1) 最大 0.0010，平均 0.00005 0.0010 / 0.00005 0.0017 / 0.00006
Q、K ~ N(0, 9)（注意力集中） 0.0157 / 0.00086 0.0157 / 0.00086 0.0958 / 0.00267

Q、K 的元素放大 3 倍时，分数放大 9 倍，softmax 变得很「尖」：每一行的注意力几乎都集中在少数几个位置上。这时 exp 会把分数上的小误差放大，提前缩放的版本最大误差是参考的 6 倍、平均误差是 3 倍（因果时最大误差是 8 倍）。真实模型里，注意力集中的头并不少见。minillm 在循环里用 fp32 缩放，和 SDPA 的误差一模一样；tests/test_attention.py::test_attention_peaky 专门检查这种情形。

官方教程的一个技巧

Triton 官方教程的 FlashAttention 把因果的循环拆成两段：对角线以前的块不需要 mask，用一个不带 where 的循环；只有对角线上的块用带 mask 的循环。这样大部分块省掉了比较和 where。我在 minillm 的 kernel 上试了一下（因果，256 × 64，D = 128）：

不拆 拆成两段
关掉 ReduceVariableLiveness 95.9 78.4
打开（默认） 78.3 83.7

拆开以后循环体复制了一份，代码变大。在默认设置下它有用（78 → 84），但比不上「不拆、关掉 pass」的 96。优化手段之间会互相影响，一个在 NVIDIA 上有用的技巧，换一个后端、换一组别的选项，可能就变成负的。本书还没在 A10 上验证官方教程这个技巧的效果。

动手

  1. 在你的 GPU 上跑「和 PyTorch 比」。 A10 只有 24 GB 显存，naive 在 N = 4096 时还放得下吗？SDPA 在 A10 上背后是哪个 kernel（用 torch.profiler 看）？minillm 用的是为 NVIDIA 随手挑的 128 × 64、8 个 warp、3 级流水，离 SDPA 有多远？用第 14 章的 autotune 扫一遍 BLOCK_M、BLOCK_N、num_warps、num_stages，能追上多少？
  2. 把对角线那一块拆出来。 照着上一节的描述，把因果的循环拆成「不带 mask」和「带 mask」两段，在你的 GPU 上测一测。在 NVIDIA 上，它有没有官方教程说的那种收益？
  3. 写 FlashAttention 的反向。 前向多存一个每行的 logsumexp（m + log l，形状 (Z, H, N)），反向就能一块一块地重算 P，不必存 N × N 的矩阵。先写 dV 和 dK（一个 program 负责 K、V 的一块，沿 Q 方向循环），再写 dQ。用 tests/test_ops.py 的 test_backward 检查。

这一章的要点

  • FlashAttention：一个 program 负责 Q 的 BLOCK_M 行，沿 N 一块一块地读 K、V，用 online softmax 维护每行的 m、l 和累加器 acc（最大值一变，l 和 acc 都乘上同一个 α），扫完才除以 l。N × N 的注意力矩阵从来不写回显存。它和教科书公式在数学上完全等价。
  • 不算 L2 时，FlashAttention 的算术强度恰好等于 BLOCK_M：它省掉的主要是 N × N 的显存和 kernel 的数量，搬的字节不一定少。实测 L2 挡住了大部分 K、V 的重复读取。
  • Max 1100 上，因果 attention 和 SDPA 一样快，非因果约为 SDPA 的 85%–88%；naive 写法慢 4–12 倍，N = 4096 时要 8 GiB 显存。
  • 选 tile 还是看寄存器：每个 warp 分 8 行最好。最好的配置随 head_dim、因果与否而变（256 × 128 在非因果时最快，在因果时溢出到只剩 28 TFLOP/s）。
  • 读 IR 的收获：tl.trans(k) 被折进了按列的二维块读取，不产生数据搬运；Intel 的 ReduceVariableLiveness pass 把 Q 的读取挪进了循环，非因果时快 22%，因果时慢 19%，可以用 reduce_variable_liveness=False 关掉。溢出更少不一定更快。
  • 精度：把缩放提前乘到 Q 上多了一次 bf16 舍入，注意力集中时最大误差变成 6–8 倍。缩放放在 fp32 的分数上。
