第 10 章 接入 PyTorch

这一章想让你带走什么

到目前为止，minillm 的 kernel 都是普通的 Python 函数：能算，但 PyTorch 不认识它们。不能求梯度，torch.compile 遇到它们会怎样也不清楚，torch.export 更是无从谈起。这一章用 torch.library 把它们注册成真正的 PyTorch 算子，补上反向传播，并用 torch.compile(fullgraph=True) 把一个 MLP block 整图编译。

读完你会拿到三样东西。一是三种接法的区别：直接调用、triton_op、custom_op，各自让 torch.compile 看到什么，以 Inductor 生成的代码为证。二是一个完整、通过 opcheck 的算子库 minillm/ops.py，以及两个真实踩到的坑：在算子里取 data_ptr() 会让 opcheck 失败；在 triton_op 里给 kernel 传 host 端的 TensorDescriptor，torch.compile 以后结果变成 NaN，而且不报任何错。三是一个关于性能的诚实结论：对手写好的 kernel，torch.compile 不会替你融合，Inductor 只是原样启动它们。

三种接法

把一个 Triton kernel 接进 PyTorch，有三种做法：

  1. 直接调用。 不注册任何东西，在函数里照常 kernel[grid](...)。torch.compile 能追踪进去（这叫 user-defined Triton kernel），把它原样放进生成的代码里。
  2. torch.library.triton_op。 注册成一个有名字、有 schema 的算子（比如 minillm::silu_mul），函数体里的 kernel 要用 torch.library.wrap_triton(...) 包一层。它是一个真正的算子：能注册反向、能 torch.export、能被 opcheck 检查；同时 torch.compile 还是看得见里面的 kernel。
  3. torch.library.custom_op。 也注册成算子，但对 torch.compile 不透明：编译器不会追踪进去，只把它当成一次外部调用。代价是要自己提供一个 fake 实现（告诉编译器输出的形状和类型）。

PyTorch 的文档（torch.library.triton_op 的 docstring）给的建议很直接：能直接调用就直接调用，那是最简单的；只有当你需要它表现得像一个 PyTorch 内建算子时，比如要注册反向、要支持 tensor subclass 或 torch.export，才用 triton_op；custom_op 是给不能被追踪的实现准备的。

minillm/ops.py：用 triton_op 注册算子

minillm 选第二种。minillm/ops.py 把 add、silu_mul、rmsnorm、softmax、mm 都注册成了 minillm:: 命名空间下的算子。以 silu_mul 为例：

Python
@triton_op("minillm::silu_mul", mutates_args=())
def silu_mul(gate: torch.Tensor, up: torch.Tensor) -> torch.Tensor:
    gate, up = gate.contiguous(), up.contiguous()
    out = torch.empty_like(gate)
    if gate.numel():
        wrap_triton(_pw._silu_mul_kernel)[_grid1d(gate.numel())](gate, up, out, gate.numel(), BLOCK=BLOCK)
    return out

几条规则：

  • 名字是 命名空间::算子名。注册以后，minillm.ops.silu_mul(...) 和 torch.ops.minillm.silu_mul(...) 是同一个东西。
  • 类型标注不能省：PyTorch 根据它们推出算子的 schema（(Tensor gate, Tensor up) -> Tensor）。
  • mutates_args=() 声明这个算子不修改任何输入。如果你的 kernel 是就地写入某个输入的，必须在这里列出来，否则编译器可能做出错误的优化（本章最后那个坑，本质上就是编译器以为某次写入不存在）。
  • 函数体里只能有 PyTorch 的算子和用 wrap_triton 包起来的 kernel。.contiguous()、torch.empty_like 都是 PyTorch 算子，可以用；直接写 _silu_mul_kernel[grid](...) 不行。

反向传播

注册反向用 register_autograd(backward, setup_context=...)：setup_context 在前向结束时运行，决定要为反向保存什么；backward 拿到输出的梯度，返回每个输入的梯度。

silu_mul 的反向值得写成 Triton kernel：它是逐点的，读 3 个张量（输出的梯度、gate、up）、写 2 个，融合成一个 kernel 最划算。设 s = sigmoid(g)，那么 silu(g) = g·s，对 g 求导是 s + g·s·(1 − s) = s·(1 + g·(1 − s))：

Triton (Python)
@triton.jit
def _silu_mul_bwd_kernel(grad_ptr, gate_ptr, up_ptr, dgate_ptr, dup_ptr, n, BLOCK: tl.constexpr):
    pid = tl.program_id(0)
    offs = pid * BLOCK + tl.arange(0, BLOCK)
    mask = offs < n
    dy = tl.load(grad_ptr + offs, mask=mask).to(tl.float32)
    g = tl.load(gate_ptr + offs, mask=mask).to(tl.float32)
    u = tl.load(up_ptr + offs, mask=mask).to(tl.float32)
    s = tl.sigmoid(g)
    tl.store(dup_ptr + offs, (dy * g * s).to(dup_ptr.dtype.element_ty), mask=mask)
    tl.store(dgate_ptr + offs, (dy * u * s * (1 + g * (1 - s))).to(dgate_ptr.dtype.element_ty), mask=mask)

它本身也注册成一个 triton_op（minillm::silu_mul_backward），反向函数调用它：

Python
def _silu_mul_setup(ctx, inputs, output):
    ctx.save_for_backward(*inputs)                 # 反向要用 gate 和 up，不保存输出


def _silu_mul_bwd(ctx, grad):
    gate, up = ctx.saved_tensors
    return silu_mul_backward(grad, gate, up)


silu_mul.register_autograd(_silu_mul_bwd, setup_context=_silu_mul_setup)

其余几个算子的反向：

  • add：梯度原样传给两个输入。
  • mm：dA = dC · Bᵀ，dB = Aᵀ · dC，直接调用 mm 自己。转置视图的最后一维不连续，mm 会自动退回指针版（第 8 章）。
  • rmsnorm、softmax：先用 PyTorch 在 fp32 里写。rmsnorm 的公式是 dx = r·(g·w) − x·r³·mean(g·w·x)，dw = Σ g·x·r，其中 r 是前向里的 1/√(mean(x²)+ε)。把它们写成 Triton kernel，是本章的练习之一。

opcheck：算子合不合格

注册完的算子要用 torch.library.opcheck 检查一遍。它默认跑四项测试（看它的签名就知道：test_schema、test_autograd_registration、test_faketensor、test_aot_dispatch_dynamic），检查 schema 是否和实际行为一致、反向是否注册对了、在 FakeTensor 上（torch.compile 追踪时用的「只有形状没有数据」的张量）能不能运行、在动态形状下能不能被 AOT 编译。

我在写 ops.mm 时踩了一个坑。第 8 章的 descriptor_ok 里调用了 t.data_ptr() 来检查地址对齐，搬进 triton_op 以后，opcheck 失败了。下面是一个最小的复现（一个在算子里取 data_ptr() 的 add），运行结果（Max 1100，节选）：

OpCheckError
opcheck(op, ...): test_aot_dispatch_dynamic failed with Cannot access data pointer of Tensor (e.g. FakeTensor, FunctionalTensor). If you're using torch.compile/export/fx, it is likely that we are erroneously tracing into a custom kernel. To fix this, please wrap the custom kernel into an opaque custom op. Please see the following for details: https://pytorch.org/tutorials/advanced/custom_ops_landing_page.html (scroll up for stack trace)

torch.compile 追踪时，传进算子的是 FakeTensor，它没有真正的内存，取不到地址。ops.py 里的做法是改查 storage_offset()：PyTorch 分配的存储本身是对齐的，只要视图的偏移量对齐，地址就对齐。triton_op 的函数体里，凡是要看「具体数据」的事情都不能做：取地址、读张量的值、根据数据走不同的分支，都不行。能看的只有形状、stride、dtype、设备。

torch.compile 看到了什么

tests/test_ops.py 用这些算子拼了一个 MLP 半层，也就是 minillm 后面要用的结构：

Python
def mlp_block(x, w_norm, w1, w3, w2):
    """minillm 的 MLP 半层：h = x + W2 · (silu(W1 · rmsnorm(x)) ⊙ (W3 · rmsnorm(x)))"""
    h = ops.rmsnorm(x, w_norm, 1e-6)
    return ops.add(x, ops.mm(ops.silu_mul(ops.mm(h, w1), ops.mm(h, w3)), w2))

torch.compile(mlp_block, fullgraph=True) 能整图编译（fullgraph=True 的意思是不允许 graph break：任何一处编译器处理不了，都直接报错，而不是悄悄退回 eager），前向和反向的结果都和 eager 一致。生成的执行计划是这样的（Max 1100，节选，去掉了分配缓冲区的行和 stream= 参数）：

Inductor 自己生成了 rmsnorm 和 silu * mul 两个融合 kernel，矩阵乘交给库函数，最后一次矩阵乘和残差加法合成了一个 addmm：在矩阵乘的结尾顺手加上 x，省掉了一个单独的加法 kernel，也省掉了一趟读写。

在真实的尺寸上测一下这四种跑法（8B 级别模型的一层 MLP，4096 个 token，bf16）：

Triton (Python) 
# arch: sm80 xpu
import torch
import torch.nn.functional as F
import triton

import minillm.ops as ops
from minillm import DEVICE


def mlp_minillm(x, w_norm, w1, w3, w2):
    h = ops.rmsnorm(x, w_norm, 1e-6)
    return ops.add(x, ops.mm(ops.silu_mul(ops.mm(h, w1), ops.mm(h, w3)), w2))


def mlp_torch(x, w_norm, w1, w3, w2):
    h = F.rms_norm(x, (x.shape[-1],), w_norm, 1e-6)
    return x + (F.silu(h @ w1) * (h @ w3)) @ w2


tokens, hidden, inter = 4096, 4096, 14336            # 8B 级别模型的一层 MLP
torch.manual_seed(0)
x = torch.randn(tokens, hidden, device=DEVICE, dtype=torch.bfloat16)
ws = (torch.randn(hidden, device=DEVICE, dtype=torch.bfloat16),
      torch.randn(hidden, inter, device=DEVICE, dtype=torch.bfloat16) * 0.02,
      torch.randn(hidden, inter, device=DEVICE, dtype=torch.bfloat16) * 0.02,
      torch.randn(inter, hidden, device=DEVICE, dtype=torch.bfloat16) * 0.02)
flops = 2 * tokens * hidden * inter * 3
ref = mlp_torch(x, *ws)
print(f"{getattr(torch, DEVICE.type).get_device_name()}，torch {torch.__version__}，triton {triton.__version__}，"
      f"MLP {tokens}×{hidden}→{inter}，bf16")
for name, fn in (("PyTorch eager", mlp_torch), ("minillm eager", mlp_minillm),
                 ("torch.compile(PyTorch)", torch.compile(mlp_torch)),
                 ("torch.compile(minillm)", torch.compile(mlp_minillm, fullgraph=True))):
    torch.testing.assert_close(fn(x, *ws), ref, atol=0.1, rtol=0.05)
    ms = triton.testing.do_bench(lambda: fn(x, *ws))
    print(f"  {name:24} {ms:6.2f} ms   {flops / ms / 1e9:6.1f} TFLOP/s")
本地运行：python main.py # 需要 NVIDIA sm_80+ 或 Intel GPU（XPU）；环境见附录 A

几个结论，都不太讨喜，但都是真的：

  • minillm 的 eager 已经和 PyTorch eager 差不多快：三次矩阵乘占了绝大部分时间，第 8 章的 descriptor GEMM 已经接近 oneDNN。
  • torch.compile 没有让 minillm 变快，甚至稍慢：它只是原样启动我们的 kernel，没有可以融合的东西，还多了一点调度开销。
  • torch.compile 包 PyTorch 原生写法是最快的。

最后一条的那一截差距从哪来？只看上面的执行计划，很容易以为是融合，特别是把残差加法合进 addmm 的那一步。我把 MLP 拆成单个 kernel 分别测了一遍（同样的尺寸，Max 1100）：

部分 minillm torch.matmul / PyTorch
两次 4096×4096×14336 的矩阵乘 2 × 2.618 ms 2 × 2.459 ms
一次 4096×14336×4096 的矩阵乘 2.987 ms 2.604 ms
silu_mul 0.382 ms （Inductor 也要做一次）
rmsnorm 0.140 ms （Inductor 也要做一次）
残差加法 0.159 ms 0（合进了 addmm）

三次矩阵乘，minillm 比 PyTorch 背后的 oneDNN 合计慢了 0.70 ms；残差加法那个单独的 kernel 只有 0.16 ms。差距的大头在 GEMM 本身，不在融合。 我还试过把残差加法融进 minillm 的矩阵乘（在 store 之前把残差读进来加上，就是本章的练习 2）：在 Max 1100 上，MLP 的时间不降反升，从 8.83 ms 变成了 8.99 ms。收尾时多读的那一块残差，让 GEMM 自己慢了下来，抵掉了省下的那个 kernel。

两个教训：

  • 当你决定手写 kernel 时，融合就成了你自己的事：Inductor 会原样启动你的 kernel，不会替你把前后的运算融进去。
  • 融合不是免费的，先测清楚时间花在哪。 对一个 GEMM 占九成时间的层来说，先让 GEMM 本身追上 oneDNN（第三部分：tile、执行顺序、流水、autotune），比琢磨省掉一个 0.16 ms 的加法重要得多。反过来，对已经被 Inductor 处理得很好的部分（逐点、按行归约），手写 kernel 的收益本来就很小；手写的价值在 Inductor 做不到的地方，比如第 1 章的 attention。

一个坑：triton_op 里的 host 端 TensorDescriptor

最后讲一个我在写 ops.mm 时遇到的、最危险的坑，因为它不报错，只给出错误的结果。

第 8 章 minillm 的 matmul_desc 是在 host 端用 TensorDescriptor.from_tensor 创建 descriptor，再传给 kernel。把这段代码原样搬进 triton_op，eager 模式下完全正确；但被 torch.compile 编译以后，在 torch 2.15.0+xpu、triton-xpu 3.9.0 上，结果变成了 NaN：

eager 0.03125
compile nan

（第一行是 eager 模式下和 a @ b 的最大误差，fp16 的正常范围；第二行是 torch.compile(lambda a, b: mm(a, b) + 1) 的最大误差。）打开生成的代码，原因一目了然：

Python
buf1 = empty_strided_xpu((512, 512), (512, 1), torch.float16)
# Topologically Sorted Source Nodes: [add], Original ATen: [aten.add]
triton_poi_fused_add_0.run(buf1, 262144, stream=raw_stream0)

矩阵乘的 kernel 根本没有被调用。Inductor 分配了一块输出缓冲区，就直接在这块没有初始化的内存上做 + 1。它显然认为那次 kernel 调用没有任何效果，于是把它当成死代码删掉了。Inductor 分析用户 kernel 读写了哪些张量的代码在 PyTorch 的 torch/_higher_order_ops/triton_kernel_wrap.py 里（它认得 tt.descriptor_store，host 端 descriptor 另有一个 maybe_unpack_host_tma_descriptor 处理），具体是哪一步在这个组合下漏掉了输出，我没有进一步定位。

我又试了另外三种组合：

写法 torch.compile 以后
triton_op + host 端 TensorDescriptor 结果是 NaN，不报错
直接调用 + host 端 TensorDescriptor 报错：Unsupported: Observed exception
triton_op + kernel 里 tl.make_tensor_descriptor 正确
直接调用 + kernel 里 tl.make_tensor_descriptor 正确

所以 ops.mm 改用了一个在 kernel 里创建 descriptor 的版本（kernels/matmul.py 的 _matmul_desc_dev_kernel），测试 tests/test_ops.py::test_compile_mlp_block 会在每次运行时检查编译以后的结果。这个问题在 NVIDIA 上是否存在，我还没有验证。教训比具体的修法更重要：接进 torch.compile 的算子，一定要有一个「编译以后结果还对」的测试，因为编译器的优化可能悄悄删掉你的 kernel。

动手

  1. 把 rmsnorm 的反向写成 Triton kernel。 照着 _silu_mul_bwd_kernel 的样子，一个 program 处理一行：先算 r 和 mean(g·w·x)，再写出 dx。dw 要对所有行求和，可以先让每个 program 写出自己那一行的 g·x·r，最后用 PyTorch 求和（或者用 tl.atomic_add，想想它的代价）。用 opcheck 和 test_backward 检查。
  2. 把残差加法融进矩阵乘。 给 _matmul_desc_dev_kernel 加一个输入 residual，在 c_desc.store 之前用一个 descriptor 把它读进来加上。再用它重写 mlp_block 的最后一步。在 Max 1100 上这样做反而慢了（正文那张表下面）；在你的 GPU 上呢？用第 2 章的「数趟数」解释你看到的结果：省掉了什么，又多搬了什么。
  3. 复现那个坑。 用 host 端的 TensorDescriptor 写一个 triton_op，在你的 GPU 上 torch.compile 一下，看结果对不对；再用 TORCH_LOGS=output_code 看生成的代码里有没有你的 kernel。

这一章的要点

  • 三种接法：直接调用（最简单，torch.compile 能追踪进去，但不是算子）；triton_op（真正的算子，能注册反向、opcheck、export，编译器还看得见 kernel，kernel 要用 wrap_triton 包起来）；custom_op（对编译器不透明，要自己写 fake 实现）。minillm 用 triton_op。
  • 反向用 register_autograd(backward, setup_context=...) 注册。逐点算子的反向值得写成融合的 Triton kernel（silu_mul 的反向读 3 写 2，一个 kernel）。
  • torch.library.opcheck 检查 schema、autograd 注册、FakeTensor、动态形状。triton_op 的函数体里不能看具体数据：调用 data_ptr() 会让 test_aot_dispatch_dynamic 失败。
  • torch.compile 不会融合你手写的 kernel：它原样启动它们，融合是你自己的事。Max 1100 上，同一个 MLP 层，torch.compile(PyTorch 原生) 最快，但拆开测发现，差距的大头是三次 GEMM（minillm 比 oneDNN 慢 0.70 ms），而不是融合（残差加法只有 0.16 ms，把它融进 GEMM 实测反而更慢）。先测清楚时间花在哪，再决定融合什么。
  • 在 torch 2.15.0+xpu、triton-xpu 3.9.0 上，triton_op 里传 host 端 TensorDescriptor 的 kernel 会在 torch.compile 后被删掉，结果是 NaN 且不报错；改成在 kernel 里创建 descriptor 就正常。接进 torch.compile 的算子，一定要测编译以后的结果。
