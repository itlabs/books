第 21 章 Layout 系统（二）：linear layout 与 convert_layout

这一章想让你带走什么

第 20 章讲了五种 layout，每种有自己的参数：sizePerThread、instrShape、vec/perPhase……编译器要在它们之间转换，难道要为每一对写一套代码？Triton 的答案是 linear layout：所有 layout 都换算成同一种形式，一组「基」，转换、判断、优化都只对这一种形式做（include/triton/Tools/LinearLayout.h）。

读完你会拿到三样东西。一是 linear layout 是什么：硬件位置的每一个二进制位对应一个坐标，其余靠异或推出来；读得懂 TTGIR 里的 #ttg.linear<{register = [[0, 1], ...], lane = ..., warp = ...}>，包括「基是 [0, 0]」意味着什么。二是 convert_layout 的三种实现，从源码（lib/Analysis/Utility.cpp）到实测：只换寄存器的编号，不花时间；在 warp 内换线程，用 shuffle，每次 1.1 微秒；跨 warp，经过 shared memory，每次 19.0 微秒，贵 17 倍（Max 1100，64 MiB 的数据；用 Gluon 精确地指定 layout 测出来的）。三是一个浏览器里的模拟器，判断任意两个 layout 之间的转换属于哪一种；它会告诉你，为什么第 17 章的 FlashAttention 在 Ampere 上，把 softmax 的结果喂给第二次 tl.dot 不需要搬任何数据。

用「基」描述一个 layout

LinearLayout.h 开头有一大段注释，第一句话就是定义：

a linear layout (LL) is a function that maps from a "hardware location" to a "logical tensor index".

硬件位置是一个三元组：第几个寄存器、第几个线程（lane）、第几个 warp（还有一维 block，多 CTA 时才用，本书不涉及）。逻辑坐标就是张量的下标 (行, 列)。layout 就是从前者到后者的函数。

关键在「线性」：不需要把整张表列出来，只要给出每个二进制位对应的坐标，其余的位置用异或算出来。比如 lane 5 = 二进制 101 = lane 1 ⊕ lane 4，它持有的坐标就是「lane 1 的坐标 ⊕ lane 4 的坐标」。每一维有几个二进制位，就给几个基（basis）。

拿第 20 章那个 tile2d 的 #blocked<sizePerThread = [1, 8], threadsPerWarp = [4, 8], warpsPerCTA = [4, 1], order = [1, 0]>（64×64）换算一下：

  • 寄存器：一个线程有 8 个连续的列，是 3 个二进制位，基是 (0, 1)、(0, 2)、(0, 4)；沿行重复 4 轮（第 0、16、32、48 行），又是 2 个位，基是 (16, 0)、(32, 0)。一共 5 个基，32 个寄存器。
  • 线程：一行 8 个线程，每个往右 8 列：(0, 8)、(0, 16)、(0, 32)；4 行线程：(1, 0)、(2, 0)。一共 5 个基，32 个线程。
  • warp：4 个 warp 沿行排开，每个往下 4 行：(4, 0)、(8, 0)。

检查一下：线程 w0.9（第 0 个 warp 的 9 号线程，9 = 1 + 8）持有的第一个元素在 (0, 8) ⊕ (1, 0) = (1, 8)，对照第 20 章模拟器的图，第 1 行、第 8 列开始的那一格正是 w0.9。

TTGIR 里的 #ttg.linear 就是直接把这些基写出来。第 17 章的 FlashAttention 编到 sm_86，K 读进寄存器时用的是：

TTGIR
#linear = #ttg.linear<{register = [[0, 1], [0, 8], [0, 16], [0, 32], [0, 64], [8, 0], [16, 0], [32, 0]], lane = [[0, 2], [0, 4], [1, 0], [2, 0], [4, 0]], warp = [[0, 0], [0, 0], [0, 0]], block = []}>

一个 64×128 的块：8 个寄存器基（256 个寄存器）、5 个线程基（32 个线程）、3 个 warp 基（8 个 warp）。注意 warp 的三个基全是 [0, 0]：不管哪个 warp，坐标都不变。也就是说，8 个 warp 持有完全相同的数据。这正是 FlashAttention 需要的：8 个 warp 各算 Q 的不同行，但每个 warp 都要用到整块 K。「基是零」就是 linear layout 表示「复制」的方式；第 20 章 #slice 里「8 个线程持有同一个结果」，换成 linear layout，也是有 3 个线程基为零。

为什么要用异或？因为 GPU 上的映射几乎都是 2 的幂上的位操作，而第 20 章的 swizzle（列号和行号异或）恰好也是线性的。于是寄存器、shared memory、mma、swizzle，全都能写成同一种形式。toLinearLayout()（lib/Dialect/TritonGPU/IR/LinearLayoutConversions.cpp）负责把每一种具体的 layout 换算成基。

两个 layout 之间要搬什么

有了统一的形式，「从 layout A 转到 layout B 要搬哪些数据」就变成了一个代数问题。minimalCvtLayout（还是 LinearLayoutConversions.cpp）先算出 dst.invertAndCompose(src)，也就是 src⁻¹ ∘ dst（LinearLayout.h 的定义：A.invertAndCompose(B) 是 B⁻¹ ∘ A）：对 dst 的每一个硬件位置，它要的那个元素现在在 src 的哪个硬件位置。再从最慢的维度（warp）开始，把「位置没变」的维度去掉。剩下的维度，就是这次转换真正要动的地方。lib/Analysis/Utility.cpp 据此分成三种：

剩下的维度 判断函数 怎么实现
没有，或者只有 register cvtReordersRegisters 只是寄存器换个编号：编译器在生成代码时直接用另一个寄存器，不产生任何指令
lane（但没有 warp） cvtNeedsWarpShuffle warp 内的线程交换数据：shuffle 指令
warp cvtNeedsSharedMemory 跨 warp：先写进 shared memory，同步，再按新 layout 读出来

（shuffle 那一档还有额外的条件：两个 layout 都得是「置换」，也就是没有复制；分解出来的交换步数不能太多。不满足就退回 shared memory。）

在浏览器里试一试。下面的模拟器用基描述 layout，暴力地对 src 的每一个硬件位置，查它的元素在 dst 里由谁持有，看看动了哪几个维度，和 minimalCvtLayout 的思路一样（方向反过来，结论相同）。只用标准库，直接点运行：

Python 
# linear layout：用「基」描述一个 layout，再判断一次 convert_layout 要搬到哪一级。只用标准库。
#
# 一个 layout 把硬件位置（第几个寄存器、第几个线程、第几个 warp）映射到张量坐标 (行, 列)。
# 线性的意思是：位置的每一个二进制位对应一个「基」坐标，位置的坐标 = 所有为 1 的位的基做异或。
from itertools import product

DIMS = ("register", "lane", "warp")


def apply(layout, hw):
    r = c = 0
    for dim in DIMS:
        for bit, (br, bc) in enumerate(layout[dim]):
            if hw[dim] >> bit & 1:
                r ^= br
                c ^= bc
    return r, c


def positions(layout):
    sizes = [range(1 << len(layout[d])) for d in DIMS]
    return [dict(zip(DIMS, p)) for p in product(*sizes)]


def classify(src, dst):
    """仿照 lib/Analysis/Utility.cpp：数据要不要换寄存器、换线程、换 warp。"""
    holders = {}                                       # 坐标 → dst 里持有它的所有位置
    for hw in positions(dst):
        holders.setdefault(apply(dst, hw), []).append(hw)
    moved = set()
    for hw in positions(src):
        options = holders[apply(src, hw)]
        best = min(options, key=lambda h: (h["warp"] != hw["warp"], h["lane"] != hw["lane"], h["register"] != hw["register"]))
        for dim in DIMS:
            if best[dim] != hw[dim]:
                moved.add(dim)
    if "warp" in moved:
        return "跨 warp：要经过 shared memory"
    if "lane" in moved:
        return "在 warp 内换线程：用 shuffle"
    if "register" in moved:
        return "只是寄存器重新编号：不用搬数据"
    return "完全一样：什么都不用做"


def L(register, lane, warp):
    return {"register": register, "lane": lane, "warp": warp}


# ① 第 21 章 Gluon 实验里的四种转换（64×64，4 个 warp，每个 warp 32 个线程）
REG = [(0, 1), (0, 2), (0, 32), (16, 0), (32, 0)]
LANE = [(0, 4), (0, 8), (0, 16), (1, 0), (2, 0)]
WARP = [(4, 0), (8, 0)]
SRC = L(REG, LANE, WARP)
print("① 从基准 layout 转到：")
for name, dst in (("同一个 layout", SRC),
                  ("只换寄存器的顺序", L([REG[1], REG[0]] + REG[2:], LANE, WARP)),
                  ("寄存器和线程交换一维", L([LANE[0]] + REG[1:], [REG[0]] + LANE[1:], WARP)),
                  ("线程和 warp 交换一维", L(REG, LANE[:3] + [WARP[0]] + LANE[4:], [LANE[3]] + WARP[1:]))):
    print(f"  {name:12} → {classify(SRC, dst)}")

# ② FlashAttention（第 17 章）在 sm_86 上的两次 convert_layout。
# mma.sync m16n8 的累加器（PTX ISA）：线程 t 持有第 t/4 行、第 2·(t%4) 和 +1 列，以及下面第 8 行。
# 16×16 的 P 由两条 m16n8 拼成：第三个寄存器基是「右边那一条」。
ACC_16x16 = L([(0, 1), (8, 0), (0, 8)], [(0, 2), (0, 4), (1, 0), (2, 0), (4, 0)], [])
# mma.sync m16n8k16 的 A 操作数（fp16，PTX ISA）：a0..a7 依次是 (行, 列)、(行, 列+1)、(行+8, …)、(…, 列+8)
A_16x16 = L([(0, 1), (8, 0), (0, 8)], [(0, 2), (0, 4), (1, 0), (2, 0), (4, 0)], [])
print("② FlashAttention 里 P 从累加器变成第二次 tl.dot 的 A 操作数：" + classify(ACC_16x16, A_16x16))
# 输出从 #mma（warpsPerCTA = [8, 1]，每个 warp 16 行）转成 store 用的 #blocked<[1,8],[2,16],[8,1]>，128×128
MMA_OUT = L([(0, 1), (8, 0), (0, 8), (0, 16), (0, 32), (0, 64)], [(0, 2), (0, 4), (1, 0), (2, 0), (4, 0)],
            [(16, 0), (32, 0), (64, 0)])
BLOCKED_OUT = L([(0, 1), (0, 2), (0, 4), (16, 0), (32, 0), (64, 0)], [(0, 8), (0, 16), (0, 32), (0, 64), (1, 0)],
                [(2, 0), (4, 0), (8, 0)])
print("   输出从 #mma 转成 #blocked 再写回显存：" + classify(MMA_OUT, BLOCKED_OUT))

运行结果：

① 从基准 layout 转到：
  同一个 layout   → 完全一样：什么都不用做
  只换寄存器的顺序     → 只是寄存器重新编号：不用搬数据
  寄存器和线程交换一维   → 在 warp 内换线程：用 shuffle
  线程和 warp 交换一维 → 跨 warp：要经过 shared memory
② FlashAttention 里 P 从累加器变成第二次 tl.dot 的 A 操作数：完全一样：什么都不用做
   输出从 #mma 转成 #blocked 再写回显存：跨 warp：要经过 shared memory

第 ① 部分是四种人为构造的转换：基准 layout 每个线程 4 个相邻的列，32 个线程排成 4 行 × 8 列，4 个 warp 沿行排开；然后分别交换两个寄存器基、交换一个寄存器基和一个线程基、交换一个线程基和一个 warp 基。下一节在真机上测它们。

第 ② 部分是第 17 章那个编到 sm_86 的指针版 FlashAttention（128 × 64，8 个 warp），最终 TTGIR 里仅剩的两次 convert_layout：

TTGIR
%acc_94 = ttg.convert_layout %acc_90 : tensor<128x64xf16, #mma> -> tensor<128x64xf16, #ttg.dot_op<{opIdx = 0, parent = #mma, kWidth = 2}>>
%9 = ttg.convert_layout %8 : tensor<128x128xf16, #mma> -> tensor<128x128xf16, #blocked>
  • 第一次在循环里：softmax 的结果 P 还在第一次 tl.dot 的累加器 layout（#mma）上，要变成第二次 tl.dot 的 A 操作数（#dot_op）。模拟器按 PTX 指令集手册里 mma.sync m16n8k16 的 fragment 排布写出两个 layout 的基，结论是完全一样：两条相邻的 m16n8 指令的累加器，拼起来恰好就是一条 m16n8k16 的 A 操作数（fp16，kWidth = 2）。所以这次转换什么都不用做。这是 FlashAttention 能在 Ampere 上高效运行的一个关键巧合：如果这里要经过 shared memory，循环里每一轮都要多一次往返。
  • 第二次在循环外，把输出转成写回显存用的 #blocked：warp 的基从「每个 warp 16 行」变成了「每个 warp 2 行」，要跨 warp，经过 shared memory。但它只在最后做一次，代价摊得很薄。

真机上测三种转换

第 ① 部分那四种转换，能在真机上测吗？用 Triton 写不行：layout 是编译器选的，你没法指定「我要这个 layout」。但 Gluon（第 24、25 章）可以：它是 Triton 的下一层，layout 由你写明。下面先借用一下，用 ttgl.DistributedLinearLayout 直接给出基，让一个张量在两个 layout 之间来回转 64 次，每次中间加 1，免得被编译器优化掉：

Gluon (Python) 
# arch: sm80 xpu
import re
import time

import torch
import triton
from triton.experimental import gluon
from triton.experimental.gluon import language as ttgl
from minillm import DEVICE

N = 64


@gluon.jit
def roundtrip(x_ptr, y_ptr, SRC: ttgl.constexpr, DST: ttgl.constexpr, N: ttgl.constexpr, REPS: ttgl.constexpr):
    base = ttgl.program_id(0) * N * N
    r = ttgl.arange(0, N, layout=ttgl.SliceLayout(1, SRC))
    c = ttgl.arange(0, N, layout=ttgl.SliceLayout(0, SRC))
    offs = base + r[:, None] * N + c[None, :]
    x = ttgl.load(x_ptr + offs)
    for _ in range(REPS):
        x = ttgl.convert_layout(ttgl.convert_layout(x, DST) + 1.0, SRC)   # 去一趟、加 1、再回来
    ttgl.store(y_ptr + offs, x)


def ll(reg, lane, warp):
    return ttgl.DistributedLinearLayout(reg_bases=reg, lane_bases=lane, warp_bases=warp, block_bases=[], shape=[N, N])


# 基准 layout：每个线程 4 个相邻的列；一个 warp 32 个线程排成 4 行 × 8 列；4 个 warp 沿行排开
REG = [[0, 1], [0, 2], [0, 32], [16, 0], [32, 0]]
LANE = [[0, 4], [0, 8], [0, 16], [1, 0], [2, 0]]
WARP = [[4, 0], [8, 0]]
SRC = ll(REG, LANE, WARP)
DSTS = {
    "同一个 layout": SRC,
    "只换寄存器的顺序": ll([REG[1], REG[0]] + REG[2:], LANE, WARP),
    "寄存器和线程交换一维": ll([LANE[0]] + REG[1:], [REG[0]] + LANE[1:], WARP),
    "线程和 warp 交换一维": ll(REG, LANE[:3] + [WARP[0]] + LANE[4:], [LANE[3]] + WARP[1:]),
}
progs = 4096                                   # 4096 个 program，每个 64×64 个 fp32：一共 64 MiB
print(f"{getattr(torch, DEVICE.type).get_device_name()}，triton {triton.__version__}，64×64 fp32，4 个 warp，{progs} 个 program")
x = torch.randn(progs * N * N, device=DEVICE)
y = torch.empty_like(x)
for name, dst in DSTS.items():
    ts = {}
    for reps in (0, 64):
        f = lambda: roundtrip[(progs,)](x, y, SRC, dst, N, reps, num_warps=4)
        k = f()
        torch.testing.assert_close(y, x + reps)
        time.sleep(1)
        ts[reps] = triton.testing.do_bench(f)
    shuffles = len(re.findall(r"shuffle|shfl", k.asm["llir"], flags=re.I))
    per = (ts[64] - ts[0]) / (64 * 2) * 1e3                  # 一次 convert_layout（加上一次加法），微秒
    print(f"  {name:12}  shared memory {k.metadata.shared:5} 字节  LLVM IR 里 shuffle {shuffles:3} 处  "
          f"每次 {per:6.2f} 微秒", flush=True)
本地运行：python main.py # 需要 NVIDIA sm_80+ 或 Intel GPU（XPU）；Gluon 在 triton.experimental 下，API 随版本变

运行结果（Max 1100）：

Intel(R) Data Center GPU Max 1100，triton 3.9.0，64×64 fp32，4 个 warp，4096 个 program
  同一个 layout    shared memory     0 字节  LLVM IR 里 shuffle   0 处  每次   0.13 微秒
  只换寄存器的顺序      shared memory     0 字节  LLVM IR 里 shuffle   0 处  每次   0.10 微秒
  寄存器和线程交换一维    shared memory     0 字节  LLVM IR 里 shuffle  35 处  每次   1.12 微秒
  线程和 warp 交换一维  shared memory  2048 字节  LLVM IR 里 shuffle   0 处  每次  18.96 微秒

和模拟器的判断一致，三档的代价差了两个数量级：

  • 只换寄存器的编号和「同一个 layout」一样快。0.1 微秒左右是循环里那次加法的时间，转换本身没有代价，LLVM IR 里也找不到任何搬数据的指令。
  • warp 内换线程：LLVM IR 里出现了 35 处 shuffle，每次 1.1 微秒，大约是加法的 10 倍。
  • 跨 warp：用了 2048 字节的 shared memory，每次 19.0 微秒，比 shuffle 又贵了 17 倍。（2048 字节比整个张量小得多：编译器分几批交换，每批用同一块缓冲区。）这次转换搬的是 64 MiB 的数据，相当于读一遍、写一遍显存的时间的十分之一左右。在一个访存受限的 kernel 里多一次这样的转换，可能就是 10% 的性能。

同样的四个 kernel 用 3.9.0 离线编到 sm_86，分类完全相同：第二种 PTX 里没有 shuffle 也没有 shared memory；第三种有 32 条 shfl.sync；第四种用 2048 字节 shared memory，16 条 st.shared。

编译器怎样减少转换

既然跨 warp 的转换这么贵，编译器就要想办法少做。主力是 tritongpu-remove-layout-conversions（Intel 有自己的一份 TritonIntelGPURemoveLayoutConversions）。它做的事情大致是：从那些 layout 定死了的 op（tt.dot 的结果必须是 #mma，tt.load 最好是 coalesce 选的那个）出发，把 layout 沿着数据流向前、向后传播，让中间的逐元素运算直接在需要的 layout 上算；必要时把一些便宜的运算重算一遍（rematerialization），而不是把结果转过去。

在同一个 FlashAttention kernel（sm_86）上，用 MLIR_ENABLE_DUMP（第 18 章）数一数每个 pass 之前 IR 里有多少个 ttg.convert_layout：

时机 convert_layout 的个数
convert-triton-to-tritongpu 之后 31
coalesce 之后 39
第一次 remove-layout-conversions 之后 7
accelerate-matmul 之后（tt.dot 换成 #mma，插入到 #dot_op 的转换） 15
第二次 remove-layout-conversions 之后 5
最终的 TTGIR 2

convert-triton-to-tritongpu 和 coalesce、accelerate-matmul 这些 pass 只管「我这个 op 想要什么 layout」，不管全局，需要时就插一个转换；remove-layout-conversions 再回过头来清理。sm_86 的流水线里它一共跑了四次。最终剩下的两个，就是上一节分析的那两个：一个不用搬数据，一个在循环外只做一次。

这也给了一个读 IR 的检查清单：看 TTGIR 里还剩哪些 convert_layout，它们在不在循环里，属于三档中的哪一档。在循环里、又要经过 shared memory 的那种，最值得怀疑。下一章用这个思路，回到第 17 章那个没有解释的现象。

动手

  1. 在模拟器里构造一个 shuffle 不了的转换。 让 dst 有一个线程基为 [0, 0]（两个线程持有同一个数据，也就是复制），从 SRC 转过去，模拟器怎么判断？Utility.cpp 里 isPermutationMatrixLayout 那个条件是在防什么？
  2. 测 shuffle 和 shared memory 的分界。 在 Gluon 实验里，把「寄存器和线程交换一维」改成交换两维、三维（把更多的寄存器基和线程基对调）。shuffle 的条数怎么变？交换到第几维时，编译器改用了 shared memory？
  3. 找你自己 kernel 里的转换。 用第 12 章的 _matmul_grouped_kernel 或者第 6 章的 softmax，在你的 GPU 上看最终的 TTGIR 里有几个 convert_layout，各在哪里，用模拟器的思路判断它们属于哪一档。

这一章的要点

  • linear layout（include/triton/Tools/LinearLayout.h）：把（寄存器, 线程, warp）映射到张量坐标，每个二进制位一个「基」，其余位置靠异或。所有 layout（blocked、slice、mma、dot_op、swizzled shared）都能换算成它（toLinearLayout()）。基为 [0, 0] 表示复制：第 17 章 sm_86 上 K 的 #linear 里 warp 基全是零，8 个 warp 持有同一块 K。
  • convert_layout 的三档（lib/Analysis/Utility.cpp）：算出 src⁻¹ ∘ dst、去掉不变的维度之后，只剩寄存器 → 不产生指令；剩下线程 → warp 内 shuffle；剩下 warp → 经过 shared memory。Max 1100 上实测（64 MiB，Gluon 指定 layout）：约 0、1.1、19.0 微秒；sm_86 上的分类相同。
  • FlashAttention 在 Ampere 上：P 从 #mma 累加器转成 #dot_op 的 A 操作数，基完全相同，不用搬数据；输出转 #blocked 要跨 warp，但只在循环外做一次。
  • remove-layout-conversions 沿数据流传播 layout、必要时重算，把转换压到最少：FlashAttention 在 sm_86 上从 39 个降到 2 个。读 TTGIR 时，留意循环里那些要经过 shared memory 的转换。
