第 20 章 Layout 系统（一）

这一章想让你带走什么

第 18 章看到，从 TTIR 到 TTGIR，op 几乎不变，变的是张量的类型：tensor<256xf32> 变成了 tensor<256xf32, #blocked>。后面那个 #blocked 就是 layout：它说明这个张量的每一个元素放在哪个 warp、哪个线程的哪个寄存器里（或者 shared memory 的哪个位置）。TTIR 里的「一块」只是一个数学上的数组，TTGIR 里它才真正落到硬件上。

读完你会拿到三样东西。一是五种 layout 各自描述了什么：#blocked（逐元素运算和访存）、#slice（归约以后）、#mma / #ttig.dpas（矩阵单元的累加器）、#dot_op（矩阵单元的输入）、#shared（shared memory 里的排布），每种都配一个 3.9.0 的真实例子，sm_86 和 Max 1100 并排。二是一个浏览器里能跑的模拟器：把 TTGIR 里的参数抄进去，画出每个元素归谁；它会告诉你一个 64×64 的 fp16 块，每个线程恰好读 16 字节；tl.max(x, axis=1) 的结果被 8 个线程同时持有；NVIDIA 和 Intel 的矩阵单元，累加器的分法截然不同。三是 swizzle：同样是读 8 行，不做 swizzle 时 8 行全挤在同一个 bank 上，做了以后一个 bank 一行。

为什么需要 layout

GPU 上没有「一个 1024 个元素的张量」这种东西，只有线程和它们的寄存器。一个 program 有 num_warps × 每个 warp 的线程数 个线程（第 2 章），张量的每一个元素都必须落在其中某个（或某几个）线程的某个寄存器里，或者放在 shared memory 里。layout 就是这个映射：给定一个元素的坐标，说出它在哪个 warp、哪个线程、第几个寄存器。

为什么要把它写进 IR，而不是在最后生成代码时再定？因为它决定了几乎所有的性能：

  • 访存：一个线程持有的元素在内存里连不连续，决定了能不能用一条向量指令读 16 字节（第 5 章的合并访存）。
  • 矩阵单元：mma.sync、wgmma、DPAS 都规定了输入、输出必须以什么方式分布在线程上，错了就用不了。
  • 归约：沿某一维求和，参与的线程是在同一个 warp 里（用 shuffle，很快），还是跨 warp（要经过 shared memory）。

不同的 op 想要不同的 layout，而 layout 不同的两个张量不能直接运算，中间要插一个 ttg.convert_layout 搬数据，这是要花代价的（第 21 章）。所以编译器要在整个 kernel 的范围内权衡：给每个张量选一个 layout，让需要转换的地方尽量少。这正是 TTGIR 这一级存在的理由。

下面这个 kernel 有三个函数，分别对应本章的三类 layout：

Triton → TTGIR 🔬 在 Compiler Explorer 看 IR
# IR: ttgir
import torch
import triton
import triton.language as tl


@triton.jit
def tile2d(x_ptr, y_ptr, stride, BM: tl.constexpr, BN: tl.constexpr):
    r = tl.arange(0, BM)[:, None]
    c = tl.arange(0, BN)[None, :]
    tl.store(y_ptr + r * stride + c, tl.load(x_ptr + r * stride + c) * 2)


@triton.jit
def rowmax(x_ptr, y_ptr, stride, BM: tl.constexpr, BN: tl.constexpr):
    r = tl.arange(0, BM)
    c = tl.arange(0, BN)
    x = tl.load(x_ptr + r[:, None] * stride + c[None, :])
    tl.store(y_ptr + r, tl.max(x, axis=1))


@triton.jit
def dot(a_ptr, b_ptr, c_ptr, M: tl.constexpr, N: tl.constexpr, K: tl.constexpr):
    m = tl.arange(0, M)
    n = tl.arange(0, N)
    k = tl.arange(0, K)
    a = tl.load(a_ptr + m[:, None] * K + k[None, :])
    b = tl.load(b_ptr + k[:, None] * N + n[None, :])
    tl.store(c_ptr + m[:, None] * N + n[None, :], tl.dot(a, b))


t = torch.empty(64, 64, device="cuda", dtype=torch.float16)
c = torch.empty(64, 64, device="cuda", dtype=torch.float32)
tile2d[(1,)](t, t, 64, BM=64, BN=64)
rowmax[(1,)](t, t, 64, BM=64, BN=64)
dot[(1,)](t, t, c, M=64, N=64, K=64)
不需要 GPU：CE 只编译不运行（triton_nvidia_370 --arch 86）；Device 面板里可切换 source / TTIR / TTGIR / LLVM IR / PTX / SASS

用 3.9.0 编到 sm_86（离线），并在 Max 1100 上运行，从两边的 TTGIR 里把 layout 的定义抄出来，下面逐个讲。

#blocked：逐元素运算和访存

tile2d 读一个 64×64 的 fp16 块。两个后端给出的 layout 一模一样：

TTGIR
#blocked = #ttg.blocked<{sizePerThread = [1, 8], threadsPerWarp = [4, 8], warpsPerCTA = [4, 1], order = [1, 0]}>

四个参数，每个都是「每一维各多少」：

  • sizePerThread = [1, 8]：一个线程持有 1 行 × 8 列的一小块。
  • threadsPerWarp = [4, 8]：一个 warp 的 32 个线程排成 4 行 × 8 列。
  • warpsPerCTA = [4, 1]：4 个 warp 沿行方向排开。
  • order = [1, 0]：给线程编号时，第 1 维（列）变化最快。这一点决定了线程 0 和线程 1 是左右相邻，还是上下相邻。

三者相乘，一轮能覆盖 (1·4·4) × (8·8·1) = 16 × 64 个元素，这叫一个 CTA tile。张量是 64 × 64，比它大，于是沿行方向重复 4 轮：同一个线程在第 0、16、32、48 行各拿一块。张量比 CTA tile 小的那一维则反过来，好几个线程会拿到同一个元素（复制）。

在浏览器里画出来看。下面的模拟器只用标准库，参数都是照着 TTGIR 抄的，直接点运行：

Python 
# layout 模拟器：每个元素归哪个 warp、哪个线程。只用标准库，参数照着 TTGIR 抄。


def blocked(shape, size_per_thread, threads_per_warp, warps_per_cta, order):
    """#ttg.blocked：返回 {(行, 列): (warp, 线程)}。"""
    owners = {}
    for idx in _all_indices(shape):
        coord_t, coord_w = [], []
        for d in range(len(shape)):
            # 一个 CTA tile 是 size_per_thread · threads_per_warp · warps_per_cta 个元素；
            # 张量更大时，同一批线程再来一轮（每个线程多用几个寄存器），所以先对 tile 取模
            x = idx[d] % (size_per_thread[d] * threads_per_warp[d] * warps_per_cta[d])
            coord_t.append((x // size_per_thread[d]) % threads_per_warp[d])
            coord_w.append((x // (size_per_thread[d] * threads_per_warp[d])) % warps_per_cta[d])
        owners[idx] = (_linear(coord_w, warps_per_cta, order), _linear(coord_t, threads_per_warp, order))
    return owners


def _all_indices(shape):
    if len(shape) == 1:
        return [(i,) for i in range(shape[0])]
    return [(i, j) for i in range(shape[0]) for j in range(shape[1])]


def _linear(coord, sizes, order):
    """order[0] 是变化最快的那一维。"""
    lin, mul = 0, 1
    for d in order:
        lin += coord[d] * mul
        mul *= sizes[d]
    return lin


def slice_owners(parent, dim, i):
    """#ttg.slice<dim, parent>：沿 dim 归约以后，第 i 个元素归 parent 里「那一行（列）」的所有线程。"""
    return sorted({o for idx, o in parent.items() if idx[1 - dim] == i})


def show(title, rows, cols, label, col_step=1):
    print(title)
    for r in range(rows):
        print("  " + " ".join(f"{label(r, c):>6}" for c in range(0, cols, col_step)))

     "前 16 行，每格 8 列（w 号.线程号）", 16, 64, lambda r, c: "w%d.%d" % own[(r, c)], col_step=8)

# ⑤ shared memory 的 swizzle：#swizzled_shared<vec=8, perPhase=1, maxPhase=8>，64×64 的 fp16，一行 128 字节
def bank(r, c, swizzle):
    if swizzle:
        phase = (r // 1) % 8
        c = ((c // 8) ^ phase) * 8 + c % 8                  # 以 8 个元素（16 字节）为单位，和行号做异或
    byte = r * 64 * 2 + c * 2
    return (byte // 4) % 32                                   # 32 个 bank，每个 4 字节


for swz in (False, True):
    # ldmatrix 一次读 8 行 × 8 个 fp16（每行 16 字节），8 行同时读：看它们落在哪些 bank 上
    banks = [bank(r, 0, swz) for r in range(8)]
    worst = max(banks.count(b) for b in banks)
    print(f"⑤ {'有' if swz else '没有'} swizzle：读第 0–7 行的第 0–7 列，起始 bank 是 {banks}，最多 {worst} 行挤在同一个 bank 上")

#slice：归约以后

rowmax 对同一个 64×64 的块沿第 1 维（每一行）求最大值。结果是 64 个数，它的类型是：

TTGIR
}) : (tensor<64x64xf32, #blocked1>) -> tensor<64xf32, #ttg.slice<{dim = 1, parent = #blocked1}>>

#ttg.slice<{dim = 1, parent = #blocked1}> 的意思是：把 parent 那个二维 layout 的第 1 维「切掉」。第 r 个结果，归 parent 里持有第 r 行的所有线程。模拟器的第 ② 条算出来：第 0 行被 8 个线程（w0.0 到 w0.7）分着读，归约以后，这 8 个线程每一个都持有同一个结果。

这说明了归约是怎么做的：8 个线程先各自对自己的 8 个元素求最大值，再在 warp 内用 shuffle 两两交换、比较，三轮以后，8 个线程手里都是整行的最大值。因为这 8 个线程在同一个 warp 里，整个归约不需要 shared memory。如果 threadsPerWarp 和 warpsPerCTA 把一行分到了几个 warp 上，就得经过 shared memory 了，这正是第 6 章 softmax 里 num_warps 影响性能的原因之一。

#slice 也出现在相反的方向上：tl.arange(0, 64)[:, None]。tl.arange 生成的一维张量是 tensor<64xi32, #ttg.slice<{dim = 1, parent = #blocked1}>>，[:, None]（tt.expand_dims）把它变成 tensor<64x1xi32, #blocked1>。编译器在 TTIR 到 TTGIR 时就给 arange 挑好了 slice layout，使得 expand 之后不需要搬任何数据。

#mma 和 #dot_op：矩阵单元

dot 做一个 64×64×64 的 tl.dot。这里两个后端分道扬镳：

TTGIR
// sm_86
#mma = #ttg.nvidia_mma<{versionMajor = 2, versionMinor = 0, warpsPerCTA = [2, 2], instrShape = [16, 8]}>
// Max 1100
#mma = #ttig.dpas<{repeatCount = 8, systolicDepth = 8, executionSize = 16, opsPerChan = 2, threadsPerWarp = 16, warpsPerCTA = [2, 2], repCluster = [4, 2], A = [32, 16], B = [16, 32], C = [32, 32]}>

#mma 描述的是累加器（tl.dot 的结果）怎样分布：它不是由「每个线程几个、每个 warp 几个线程」这种自由参数决定的，而是由矩阵指令的硬件规定决定的。

  • sm_86 的 nvidia_mma version 2 对应 Ampere 的 mma.sync.m16n8k16。instrShape = [16, 8]：一条指令算一个 16×8 的累加器块。这 128 个 fp32 在一个 warp 的 32 个线程里怎么分，是 PTX 指令集手册规定的。模拟器的第 ③ 张图：线程 t 持有第 t/4 行和第 t/4 + 8 行、第 2·(t%4) 和 2·(t%4)+1 列，一共 4 个数。warpsPerCTA = [2, 2]：4 个 warp 排成 2×2，每个 warp 负责 32×32 的一块，也就是 2×4 = 8 条指令的结果。
  • Intel 的 ttig.dpas 对应 DPAS 指令。executionSize = 16：一条指令的 N 是 16，正好是一个 warp（16 个线程）；repeatCount = 8：M 是 8。模拟器的第 ④ 张图：线程 i 持有第 i 列的全部 8 行，每一行在一个寄存器里。repCluster = [4, 2]：每个 warp 一次做 4×2 = 8 条 DPAS，拼成 32×32 的块（C = [32, 32]）。

两种分法截然不同：NVIDIA 一个线程拿两行、每行两个相邻的数；Intel 一个线程拿一整列。这直接影响 tl.dot 之后的运算：比如第 17 章 FlashAttention 里沿行求最大值（tl.max(qk, 1)），在 Intel 的 DPAS layout 上，一行的 16 个数分在 16 个线程里，要做 warp 内的归约；在 NVIDIA 的 layout 上，一行的 8 个数只分在 4 个线程里。

#dot_op 描述 tl.dot 的两个输入。第 15、17 章的 IR 里见过：

TTGIR
tensor<256x128xbf16, #ttg.dot_op<{opIdx = 0, parent = #mma, kWidth = 1}>>     // A：opIdx = 0
tensor<128x64xbf16, #ttg.dot_op<{opIdx = 1, parent = #mma, kWidth = 2}>>      // B：opIdx = 1

它总是挂在一个 #mma 上（parent = #mma）：输入怎么分布，完全由「输出要怎么分布」和指令的规定推出来，opIdx 说明是左边还是右边的操作数，kWidth 说明每个线程沿 K 方向连续持有几个元素。所以一个 tl.dot 的三个张量，layout 是一起决定的，选好 #mma，另外两个就确定了。这件事由 tritongpu-accelerate-matmul（Intel 上是 TritonIntelGPUAccelerateMatmul）完成：它把 tt.dot 的结果从 #blocked 换成 #mma，在输入前插入到 #dot_op 的 convert_layout。

在 Max 1100 上，dot 的 TTGIR 里没有任何 #blocked：两次 load 直接读成了 #dot_op layout。Intel 的 2D block IO 能按 DPAS 要的方式把数据直接读进寄存器（第 8 章）。sm_86 上则还有两个 #blocked（给 load 用）和一个 #shared：数据先按 #blocked 读进来，存进 shared memory，再按 #dot_op 读出来。为什么要绕这一圈？下一节。

#shared：shared memory 里的排布

sm_86 的 dot 里还有一个：

TTGIR
#shared = #ttg.swizzled_shared<{vec = 8, perPhase = 1, maxPhase = 8, order = [1, 0]}>

前面的 layout 描述的都是寄存器。#shared 描述的是一个块在 shared memory 里怎么摆，它挂在 !ttg.memdesc<64x64xf16, #shared, #smem> 这种类型上（memdesc 是「一块内存的描述」，不是寄存器里的张量）。

为什么要专门描述？因为 shared memory 分成 32 个 bank，每个 bank 4 字节宽，同一时刻每个 bank 只能服务一个地址。mma.sync 的输入要用 ldmatrix 从 shared memory 读：一次读 8 行，每行 16 字节（8 个 fp16）。如果 64×64 的块按行原样存放，一行 64 × 2 = 128 字节，正好 32 个 bank 一圈，每一行的第 0 列都落在 bank 0 上。8 行同时读，全挤在同一组 bank 上，只能一行一行地排队（8 路 bank conflict）。

swizzle 的办法是：存的时候，把每一行以 vec 个元素（这里 8 个 fp16，16 字节）为单位，和行号做异或，打乱位置：

实际列 = ((列 / vec) ⊕ ((行 / perPhase) mod maxPhase)) · vec + 列 mod vec

第 0 行不变，第 1 行的每个 16 字节块和 1 异或（第 0 块和第 1 块互换），第 2 行和 2 异或……模拟器的第 ⑤ 条算出来：不 swizzle 时，读第 0–7 行的第 0–7 列，8 行的起始 bank 全是 0；swizzle 以后是 0、4、8、……、28，8 行落在 8 组不同的 bank 上，一次就能读完。vec、perPhase、maxPhase 就是这个公式的三个参数，编译器根据元素大小、行宽和读的方式（ldmatrix 还是别的）来选。

Hopper 上的 #ttg.nvmma_shared<{swizzlingByteWidth = 128, ...}>（第 15 章）是同一个思路，只是 swizzle 的方式由 TMA 和 wgmma 的硬件规定，参数换成了「按多少字节做 swizzle」。Intel 后端在这个 kernel 里不需要 shared memory，第 15 章那个 persistent 的坑里出现过的 local_alloc，就是 block IO 丢了以后不得不走 shared local memory 的结果。

还有一种第 17 章里出现过、这一章没有讲的：#ttg.linear（sm_86 上 K 的转置用到了它）。它是一种「什么分布都能表示」的通用形式，前面这几种都能写成它。第 21 章专门讲它，以及 convert_layout 什么时候便宜、什么时候贵。

动手

  1. 在模拟器里换参数。 把第 ① 张图的 order 改成 [0, 1]，同一个线程的 8 个元素还连续吗？对一个按行存放的矩阵，这样的 layout 读起来会怎样？再把 sizePerThread 改成 [1, 4]，看每一行要几个线程。
  2. 看归约跨不跨 warp。 用本章的 rowmax，把块换成 64×256、num_warps=4，在 Compiler Explorer 里看 #blocked1 变成了什么，第 0 行被几个 warp 分着读？TTGIR 后面的 LLVM IR 里有没有出现 shared memory？
  3. 换一个 bank 宽度。 在模拟器的第 ⑤ 条里把元素换成 fp32（一行 256 字节），vec 应该取几，swizzle 才能让 8 行落在不同的 bank 上？

这一章的要点

  • layout 是「张量的元素放在哪个 warp、哪个线程、哪个寄存器（或 shared memory 的哪里）」的映射，写在张量类型上（tensor<64x64xf16, #blocked>）。TTIR 没有它，TTGIR 有，这是两级 IR 的本质区别。
  • #blocked：sizePerThread × threadsPerWarp × warpsPerCTA 是一个 CTA tile，order 决定线程编号的方向；张量更大就重复，更小就复制。coalesce 按「最内维连续、每个线程 16 字节」来选：fp32 是 4 个，fp16 是 8 个。
  • #slice<dim, parent>：归约的结果，被 parent 里同一行的所有线程同时持有；同一行在一个 warp 内时，归约只要 shuffle。
  • #mma 由矩阵指令决定：sm_86 的 mma.sync m16n8 一个线程拿两行两列共 4 个数；Intel DPAS 一个线程拿一整列 8 个数。#dot_op 由 #mma 推出，三者一起由 accelerate-matmul 选定。Max 1100 上 load 直接读成 #dot_op，sm_86 上要经过 #shared。
  • #shared：shared memory 32 个 bank，一行 128 字节时不 swizzle 会 8 路冲突；vec、perPhase、maxPhase 定义了「以 vec 个元素为单位和行号异或」的 swizzle，让 8 行落在 8 组 bank 上。
