第 14 章 autotune

这一章想让你带走什么

前两章手工扫了 tile 大小、num_warps、GROUP_M、num_stages，每换一台 GPU、每换一种矩阵形状，最优值都可能不一样。@triton.autotune 把这件事交给机器：你列出候选配置，它在第一次调用时逐个测一遍，记住最快的那个。

但 autotune 不是免费的，也不是万无一失的。读完你会拿到四样东西：一是它的完整工作流程（缓存键是什么、跑不起来的配置怎么处理），以源码为证；二是调优本身的代价，实测：一次调优要几秒，如果 key 里放了一个经常变化的参数，每遇到一个新值都要重来一遍；三是 prune_configs_by：用第 12 章的寄存器模型剪掉注定溢出的配置。在本书的 Max 1100 上，这一步还避开了一个会让整个进程崩溃的编译器问题；四是缓存到磁盘，让下一个进程不必重新调优。最后，minillm 有了一个按 M 分档调优的矩阵乘。

autotune 怎么工作

用法是在 @triton.jit 外面再套一层 @triton.autotune：

Triton (Python)
@triton.autotune(configs=[triton.Config({"BLOCK_M": 128, "BLOCK_N": 128, "BLOCK_K": 32}, num_warps=8),
                          triton.Config({"BLOCK_M": 256, "BLOCK_N": 256, "BLOCK_K": 32}, num_warps=32)],
                 key=["M", "N", "K"])
@triton.jit
def mm(a_ptr, b_ptr, c_ptr, M, N, K, ..., BLOCK_M: tl.constexpr, BLOCK_N: tl.constexpr, BLOCK_K: tl.constexpr):
    ...

调用的时候，BLOCK_M 这些参数不再由你传，而是由 autotune 填进去。所以 grid 必须写成第 4 章提过的函数形式：grid = lambda meta: (triton.cdiv(M, meta["BLOCK_M"]) * ...,)，meta 里就是 autotune 这次选中的配置。

每次调用发生了什么，写在 python/triton/runtime/autotuner.py 的 Autotuner.run 里：

图 14-1　一次带 autotune 的调用。绿色是快路径；橙色那两步只在遇到一个新的缓存键时才走，耗时以秒计

几个细节都来自源码：

  • 缓存键 = key 里各参数的值 + 所有张量参数的 dtype。key=["N", "K"] 时，N 和 K 都相同、dtype 也相同的两次调用，共用同一个调优结果，哪怕 M 不同。
  • 测量用的是 do_bench，取 20%、50%、80% 三个分位数，按中位数选最快的。
  • 跑不起来的配置不会报错：编译时 shared memory 超出（OutOfResources，第 13 章）、编译期断言失败、ptxas 出错，都被捕获下来，记为无穷大，自动跳过。所以候选配置里放几个「可能跑不起来」的，autotune 本身不会挂。但下一节会看到一个例外。
  • 调用以后，kernel.best_config 是选中的配置，kernel.bench_time 是这次调优花了多少秒，kernel.configs_timings 是每个配置测出的时间。

实测：调优要花多久

下面的 kernel 就是第 12 章的 _matmul_grouped_kernel，配置空间取第 12 章扫过的 9 个配置。它分别用 key=["M", "N", "K"] 和 key=["N", "K"] 各包一次，测第一次调用、第二次调用，再换 8 个不同的 M：

Triton (Python) 
# arch: sm80 xpu
import time

import torch
import triton
import triton.language as tl

from minillm import DEVICE

gpu = getattr(torch, DEVICE.type)
triton.runtime.driver.active.get_current_target()      # 先把 driver 初始化掉，别算进调优时间
CONFIGS = [triton.Config({"BLOCK_M": bm, "BLOCK_N": bn, "BLOCK_K": bk, "GROUP_M": 8}, num_warps=nw, num_stages=2)
           for bm, bn, bk, nw in ((64, 64, 32, 4), (128, 128, 32, 4), (128, 128, 32, 8), (128, 256, 32, 8),
                                  (128, 256, 32, 16), (256, 128, 32, 16), (256, 256, 32, 16), (256, 256, 32, 32),
                                  (256, 256, 64, 32))]


def register_prune(configs, named_args, **kwargs):
    """第 12 章的寄存器模型：每个线程的累加器超过 128 个，Max 1100 上必然大量溢出，不用测。"""
    tpw = 16 if DEVICE.type == "xpu" else 32
    return [c for c in configs
            if c.kwargs["BLOCK_M"] * c.kwargs["BLOCK_N"] // (tpw * c.num_warps) <= 128]


def make_kernel(key, prune):
    @triton.autotune(configs=CONFIGS, key=key,
                     prune_configs_by={"early_config_prune": register_prune} if prune else None)
    @triton.jit
    def mm(a_ptr, b_ptr, c_ptr, M, N, K, stride_am, stride_bk, stride_cm,
           BLOCK_M: tl.constexpr, BLOCK_N: tl.constexpr, BLOCK_K: tl.constexpr, GROUP_M: tl.constexpr):
        pid = tl.program_id(0)
        num_n = tl.cdiv(N, BLOCK_N)
        in_group = GROUP_M * num_n
        first_m = (pid // in_group) * GROUP_M
        size_m = tl.minimum(tl.cdiv(M, BLOCK_M) - first_m, GROUP_M)
        pid_m = first_m + (pid % in_group) % size_m
        pid_n = (pid % in_group) // size_m
        a_desc = tl.make_tensor_descriptor(a_ptr, [M, K], [stride_am, 1], [BLOCK_M, BLOCK_K])
        b_desc = tl.make_tensor_descriptor(b_ptr, [K, N], [stride_bk, 1], [BLOCK_K, BLOCK_N])
        c_desc = tl.make_tensor_descriptor(c_ptr, [M, N], [stride_cm, 1], [BLOCK_M, BLOCK_N])
        acc = tl.zeros((BLOCK_M, BLOCK_N), dtype=tl.float32)
        for k in range(0, K, BLOCK_K):
            acc = tl.dot(a_desc.load([pid_m * BLOCK_M, k]), b_desc.load([k, pid_n * BLOCK_N]), acc)
        c_desc.store([pid_m * BLOCK_M, pid_n * BLOCK_N], acc.to(c_desc.dtype))
    return mm


def call(kernel, a, b):
    M, K = a.shape
    N = b.shape[1]
    c = torch.empty(M, N, device=a.device, dtype=a.dtype)
    grid = lambda meta: (triton.cdiv(M, meta["BLOCK_M"]) * triton.cdiv(N, meta["BLOCK_N"]),)   # BLOCK 由 autotune 定
    kernel[grid](a, b, c, M, N, K, a.stride(0), b.stride(0), c.stride(0))
    return c


def timed(fn):
    gpu.synchronize(); t = time.perf_counter(); fn(); gpu.synchronize()
    return time.perf_counter() - t


b = torch.randn(4096, 4096, device=DEVICE, dtype=torch.bfloat16)
for label, key, prune in (("key=[M, N, K]", ["M", "N", "K"], True),
                          ("key=[N, K]", ["N", "K"], True)):
    kernel = make_kernel(key, prune)
    a = torch.randn(4096, 4096, device=DEVICE, dtype=torch.bfloat16)
    t_first = timed(lambda: call(kernel, a, b))
    t_second = timed(lambda: call(kernel, a, b))
    ms = triton.testing.do_bench(lambda: call(kernel, a, b))
    best = kernel.best_config
    print(f"{label}（按寄存器模型剪枝）")
    print(f"  第一次调用 {t_first:6.2f} s，其中调优 {kernel.bench_time:5.2f} s（测了 {len(kernel.configs_timings)} 个配置）；"
          f"第二次 {t_second * 1e3:6.2f} ms")
    print(f"  选中 {best.kwargs['BLOCK_M']}×{best.kwargs['BLOCK_N']}×{best.kwargs['BLOCK_K']}，num_warps={best.num_warps}，"
          f"do_bench 复测 {2 * 4096**3 / ms / 1e9:.1f} TFLOP/s")
    # 换 8 个不同的 M：key 里有 M 就会重新调优 8 次
    t = sum(timed(lambda m=m: call(kernel, torch.randn(m, 4096, device=DEVICE, dtype=torch.bfloat16), b))
            for m in (1000, 1008, 1016, 1024, 2000, 2048, 3000, 4000))
    print(f"  再换 8 个不同的 M：一共 {t:6.2f} s")
本地运行：python main.py # 需要 NVIDIA sm_80+ 或 Intel GPU（XPU）；环境见附录 A

运行结果（Max 1100，用一个空的 TRITON_CACHE_DIR）：

key=[M, N, K]（按寄存器模型剪枝）
  第一次调用   4.22 s，其中调优  4.22 s（测了 6 个配置）；第二次   1.04 ms
  选中 256×256×64，num_warps=32，do_bench 复测 151.4 TFLOP/s
  再换 8 个不同的 M：一共   6.63 s
key=[N, K]（按寄存器模型剪枝）
  第一次调用   0.77 s，其中调优  0.76 s（测了 6 个配置）；第二次   1.02 ms
  选中 256×256×64，num_warps=32，do_bench 复测 151.2 TFLOP/s
  再换 8 个不同的 M：一共   0.01 s
  • 第一次调用要几秒。 第一组的 4 秒多里，大部分是把 6 个配置各编译一遍（磁盘缓存是空的）；第二组的 kernel 源码一样，编译结果已经在磁盘缓存里了，剩下的 0.76 秒基本是测量本身：6 个配置，每个 do_bench 一次。之后的调用和不调优的 kernel 一样快。
  • key 里有 M，换一个 M 就要重新调优一次：8 个不同的 M 花了 6.6 秒，其中几个 M 还因为能不能被 16 整除不同，要多编译一个特化版本（第 4 章）。key 里没有 M，8 个 M 一共 0.01 秒。

推理服务里，batch 里的 token 数（也就是 M）几乎每次都不一样。把 M 放进 key，每来一个新的 M 就卡几秒；完全不放，M=1（decode）和 M=4096（prefill）又只能共用一个配置，而它们的最优配置往往差别很大。常见的折中是分档：key 里放的不是 M，而是 M 向上取到 2 的幂以后的值。minillm 的 matmul_tuned 就是这么做的（本章最后一节）。

上面两组最后都选中了 256×256×64、32 个 warp，但我在写这一章时跑过一次，第二组选的是 128×256×32、16 个 warp，复测只有 142 TFLOP/s。原因是几个配置的速度很接近，do_bench 的测量噪声就足以让排名颠倒。autotune 选出来的不一定是最好的，只是「这一次测下来最快的」；候选配置之间差得越少，结果越不稳定。如果你在意可复现性，调优完以后，把选中的配置写死进代码。

prune_configs_by：剪枝

候选配置越多，调优越慢。prune_configs_by 让你在测量之前先删掉一部分：

  • early_config_prune：一个函数，接收配置列表和这次调用的参数，返回要保留的配置。适合写「一看就知道不行」的规则；
  • perf_model + top_k：一个性能模型，给每个配置估一个时间，只测估得最快的前 k 个。

上面的例子用的是 early_config_prune，规则就是第 12 章的寄存器模型：每个线程的累加器超过 128 个就会大量溢出，不必测：

Python
def register_prune(configs, named_args, **kwargs):
    """第 12 章的寄存器模型：每个线程的累加器超过 128 个，Max 1100 上必然大量溢出，不用测。"""
    tpw = 16 if DEVICE.type == "xpu" else 32
    return [c for c in configs
            if c.kwargs["BLOCK_M"] * c.kwargs["BLOCK_N"] // (tpw * c.num_warps) <= 128]

9 个配置剪掉了 3 个，调优就少测了三分之一。在 Max 1100 上，这一步还有一个比省时间更重要的作用。

一个会让进程崩溃的坑

我第一次写这个例子时没有剪枝，结果 Python 进程直接段错误退出，一行输出都没有。逐个排查以后发现：那几个寄存器严重溢出的配置（比如 128×128×32 配 4 个 warp），会让 GPU 驱动里的编译器（IGC）在编译时内部崩溃。Intel 后端会自动用大寄存器模式重试，第一次能救回来：

L0 build module failed. Log: IGC: Internal Compiler Error: Segmentation violation

(I): Build failure recovered by retrying with large GRF mode for "_matmul_grouped_kernel"

但同一个进程里再遇到一次这样的崩溃，就救不回来了，整个进程段错误退出（退出码 139）。我在 Max 1100 上用两个这样的配置依次编译，稳定地复现了这一点；每个配置单独在一个进程里编译，都能成功。autotune 恰好会在同一个进程里把所有候选配置都编译一遍。

这是本书所用驱动版本上的问题，换一个驱动版本可能就没有了。但它说明了两件事：autotune 的「跑不起来的配置自动跳过」只管得住 Python 层面能捕获的错误，管不住驱动里的崩溃；而一个好的剪枝规则，能让你连碰都不去碰那些注定不行的配置。

缓存到磁盘

调优结果默认只存在进程的内存里，进程一退出就没了，下次启动又要重新测。@triton.autotune(..., cache_results=True)，或者设置环境变量 TRITON_CACHE_AUTOTUNING=1，会把结果写进 Triton 的缓存目录（文件名形如 mm.autotune.json）。再设 TRITON_PRINT_AUTOTUNING=1，autotune 每次真正调优时都会打印过程（python/triton/knobs.py 的 autotuning_knobs）。用同一个缓存目录连着跑两个进程，调用同一个 key=["N", "K"] 的 kernel：

和 Helion 比一比

@triton.autotune 只搜你列出来的那几个配置，搜索空间完全由你决定。第 26 章的 Helion 走的是另一条路：它自己生成配置空间，可调的维度多得多。Helion 1.5.2 的 helion.Config 有几十个字段，除了 block_sizes、num_warps、num_stages，还有循环的顺序（loop_orders）、L2 分组（l2_groupings）、program 编号的映射方式（pid_type）、访存方式（indexing）等等，然后用搜索算法在里面找。代价是调优时间也长得多。那时我们再比较「自己列配置」和「让工具搜」各自的得失。

minillm：按 M 分档调优的矩阵乘

kernels/matmul.py 新增 matmul_tuned：

Triton (Python)
@triton.autotune(configs=_TUNE_CONFIGS, key=["M_BUCKET", "N", "K"],
                 prune_configs_by={"early_config_prune": _register_prune})
@triton.jit
def _matmul_tuned_kernel(a_ptr, b_ptr, c_ptr, M, N, K, stride_am, stride_bk, stride_cm, M_BUCKET,
                         BLOCK_M: tl.constexpr, BLOCK_N: tl.constexpr, BLOCK_K: tl.constexpr,
                         GROUP_M: tl.constexpr, HINT_ALIGN: tl.constexpr):
    # 在 @triton.jit 函数里可以直接调用另一个 @triton.jit 函数（HINT_ALIGN 是第 15 章加的）
    _matmul_grouped_kernel(a_ptr, b_ptr, c_ptr, M, N, K, stride_am, stride_bk, stride_cm,
                           BLOCK_M, BLOCK_N, BLOCK_K, GROUP_M, HINT_ALIGN)
  • 配置空间就是第 12 章的 9 个配置，用寄存器模型剪枝；
  • M_BUCKET 是调用方传进来的 triton.next_power_of_2(M)，只用在 key 里，kernel 本身不用它。M 在同一档里变化时（比如 3000、3500、4000 都落在 4096 这一档）不会重新调优；
  • kernel 体直接调用第 12 章的 _matmul_grouped_kernel：在 @triton.jit 函数里，可以像调用普通函数一样调用另一个 @triton.jit 函数，它会被当作设备函数编译进来。我第一次写成了 _matmul_grouped_kernel.fn(...)，Triton 报 Unsupported function referenced：kernel 里引用的必须是 @triton.jit 对象本身。

mm() 和 ops.mm 暂时还用第 12 章固定的配置：在 Max 1100 上，它和 autotune 选出来的配置性能一样，还省掉了每个进程第一次调用时的调优时间。新增的测试检查同一个 M 分档里的两次调用只调优一次。测试共 139 个。

动手

  1. 看一看调优在你的 GPU 上要多久。 跑本章的调优实验，设 TRITON_PRINT_AUTOTUNING=1。在 NVIDIA 上，剪枝规则里的 tpw 是 32，按同样的「每线程 128 个」，9 个配置一个都不会被剪掉：先算一算是不是这样。第一次调用要多久，选中了哪个？256×256 那几个配置测出来多快？如果它们在你的 GPU 上溢出严重，128 这条线该怎么改？
  2. 写一个 perf_model。 用第 7 章的 tile 模型，给每个配置估一个时间（比如 max(搬的字节 / 带宽, 运算 / 峰值)，搬的字节按「每个 program 都从显存读」算），配上 top_k=3，只测估得最快的 3 个。选出来的配置和全部测一遍时一样吗？
  3. 把 M 放进 key。 把 matmul_tuned 的 key 改成 ["M", "N", "K"]，写一个循环，依次用 M = 1, 2, …, 64 调用它，记下总耗时。再改回分档，比一比。

这一章的要点

  • @triton.autotune(configs, key, ...) 在遇到一个新的缓存键时，把（剪枝后的）每个配置都编译一遍、用 do_bench 测一遍，按中位数选最快的。缓存键 = key 里各参数的值 + 张量参数的 dtype。grid 要写成 lambda meta: ...。
  • 跑不起来的配置（OutOfResources、编译期断言、ptxas 出错）记为无穷大，自动跳过；但驱动里的崩溃管不住。在本书的 Max 1100 上，同一个进程里第二次碰到 IGC 的内部错误，进程会段错误退出。
  • 调优的代价：Max 1100 上，6 个配置第一次要 4 秒多（含编译），之后每次重新调优约 0.8 秒。key 里有 M 时，换 8 个 M 花了 6.6 秒；没有 M 时 0.01 秒。推理场景里，把 M 分档后再放进 key。
  • 配置之间速度接近时，测量噪声会让 autotune 的选择不稳定（同一个配置空间，两次分别选了 256×256×64 和 256×256×32）。要可复现，就把选中的配置写死。
  • prune_configs_by={"early_config_prune": ...} 用规则提前剪掉配置，第 12 章的寄存器模型就是一个好规则；cache_results=True 或 TRITON_CACHE_AUTOTUNING=1 把结果存到磁盘，下一个进程不必重新调优；TRITON_PRINT_AUTOTUNING=1 打印调优过程。
