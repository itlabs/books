第 4 章 第一个 kernel：vector add 的完整生命周期

这一章想让你带走什么

前三章里，你已经见过好几次 add_kernel[grid](x, y, out, n, BLOCK=1024) 这一行。它看起来像一次普通的函数调用，背后却走了一条很长的路：算一个「特化键」，查内存里的缓存，查磁盘上的缓存，都没有的话就把这个 Python 函数编译成 GPU 机器码，最后才启动。这一章把这条路从头走一遍。

读完你会拿到三样东西。一是 kernel 里每一样东西的确切含义：@triton.jit、grid、tl.program_id、mask 与 other、tl.constexpr。二是一份实测的账单：在 Max 1100 上，第一次编译、命中磁盘缓存、命中内存缓存分别花多少时间，以及哪些参数变化会触发重新编译。这件事直接关系到推理服务里的冷启动和「为什么我的 kernel 隔一会儿就卡一下」。三是 minillm 项目的第一批 kernel：add 和 silu_mul，带测试，带性能测量。

一个 kernel 的一生

先看全貌。从你写下 @triton.jit 到 GPU 上真的跑起来，中间经过这些步骤：

图 4-1　一次 kernel[grid](...) 调用的完整路径。绿色是快路径，橙色是慢路径。时间都是 Max 1100 上实测的量级（本章后面有完整输出）。特化键相同的调用，只会走一次橙色那条路

下面先把 kernel 本身逐行讲清楚，再用实测把这张图上的每一个时间验证一遍。

逐行读 vector add

还是这个 kernel：

Triton (Python)
@triton.jit
def add_kernel(x_ptr, y_ptr, out_ptr, n, BLOCK: tl.constexpr):
    pid = tl.program_id(0)
    offs = pid * BLOCK + tl.arange(0, BLOCK)
    mask = offs < n
    x = tl.load(x_ptr + offs, mask=mask)
    y = tl.load(y_ptr + offs, mask=mask)
    tl.store(out_ptr + offs, x + y, mask=mask)

@triton.jit。它定义在 python/triton/runtime/jit.py，把函数包成一个 JITFunction 对象。定义的时候什么也不编译，连函数体里有没有语法错误都不检查。被 @triton.jit 修饰的函数只能在 Triton 里调用：它的函数体会被 Triton 自己的前端解析，而不是由 Python 解释器执行。所以里面只能用 tl.* 的运算和有限的 Python 语法（if、for、while、算术），不能调用 NumPy，也不能调用任意的 Python 函数。

参数。调用时传进来的 PyTorch 张量会变成指针：x_ptr 在 kernel 里的类型是 *fp32（指向 fp32 的指针），指向这个张量的第一个元素。Triton 只拿走了地址，不知道张量的形状和 stride。所以 kernel 必须自己知道要读多少个元素（这里是 n）、怎么排布（这里假设是连续的，任意 stride 的写法在第 5 章）。整数参数（n）在 kernel 里是 i32 或 i64 的标量。

tl.program_id(0)。返回这个 program 在第 0 维上的编号。grid 最多有三维，所以 program_id 的参数可以是 0、1、2。

tl.arange(0, BLOCK)。产生一个长度为 BLOCK 的张量 [0, 1, …, BLOCK-1]。它的长度必须是 2 的幂，并且必须是编译时常量。这就是 BLOCK 要声明成 tl.constexpr 的原因。

tl.constexpr。标了 tl.constexpr 的参数是编译时常量：它的值在编译时就确定，直接写进生成的机器码，所以可以拿来决定张量的形状、展开循环。代价是每一个不同的值都要单独编译一次（下一节实测）。把 BLOCK 设成 1000 会怎样？

Triton (Python)
add_kernel[(triton.cdiv(x.numel(), 1000),)](x, y, out, x.numel(), BLOCK=1000)

运行结果（节选，去掉了前面的 traceback）：

triton.compiler.errors.CompilationError: at 3:25:
def add_kernel(x_ptr, y_ptr, out_ptr, n, BLOCK: tl.constexpr):
    pid = tl.program_id(0)
    offs = pid * BLOCK + tl.arange(0, BLOCK)
                         ^
arange's range must be a power of 2

这是一个编译期错误，发生在第一次调用、Triton 解析函数体的时候，而且精确地指出了源码里的位置。Triton 的报错大多长这样（第 9 章会专门整理常见的报错）。

mask 与 other。offs < n 产生一个布尔张量，标出哪些下标在界内。tl.load(ptr, mask=mask) 只读 mask 为真的位置；tl.store(ptr, value, mask=mask) 只写 mask 为真的位置。为什么必须有它？因为数据长度几乎从来不是 BLOCK 的整数倍：

图 4-2　mask 覆盖的边界块。97 个 program 里，前 96 个的 mask 全是 True；只有最后一个越过了 n，它的后 896 个元素被 mask 掉。没有 mask，这个 program 就会读写到张量后面不属于它的显存

被 mask 掉的位置，tl.load 返回 other 参数给的值；不给 other，那些位置的值是未定义的（tl.load 的文档原话：「If other is None, the masked-out value is undefined」）。在 vector add 里这无所谓，因为那些位置也不会被写出去。但如果后面要对整块做归约，就一定要给一个不影响结果的 other：第 1 章的 softmax 在求最大值之前，写的是 other=-float("inf")。

grid。add_kernel[grid] 的 grid 是一个元组，表示每一维启动多少个 program：(triton.cdiv(n, BLOCK),) 是一维，向上取整。它也可以是一个函数，接收这次调用的参数（一个 dict），返回元组：

Triton (Python)
grid = lambda meta: (triton.cdiv(n, meta["BLOCK"]),)
add_kernel[grid](x, y, out, n, BLOCK=1024)

现在看不出这种写法有什么好处。到第 14 章，BLOCK 由 autotune 替你挑，调用的时候你还不知道它是多少，就必须用这种写法。

实测：一次调用到底发生了什么

下面这个脚本用 Triton 提供的一个钩子 triton.knobs.runtime.jit_cache_hook：每当内存里的缓存没命中、要去编译（或从磁盘缓存加载）之前，Triton 会调用它。我们在钩子里打印这次的特化键，再测每一次调用的耗时。它依次换长度、换 dtype、换 BLOCK：

Triton (Python) 
# arch: sm80 xpu
import time

import torch
import triton
import triton.language as tl

t0 = time.perf_counter()
DEVICE = triton.runtime.driver.active.get_active_torch_device()   # 第一次用到 driver：初始化它
gpu = getattr(torch, DEVICE.type)
triton.runtime.driver.active.get_current_target()
print(f"初始化 driver：{(time.perf_counter() - t0) * 1e3:.0f} ms")


@triton.jit
def add_kernel(x_ptr, y_ptr, out_ptr, n, BLOCK: tl.constexpr):
    pid = tl.program_id(0)
    offs = pid * BLOCK + tl.arange(0, BLOCK)
    mask = offs < n
    x = tl.load(x_ptr + offs, mask=mask)
    y = tl.load(y_ptr + offs, mask=mask)
    tl.store(out_ptr + offs, x + y, mask=mask)


def on_compile(compile, **kw):
    """内存里的缓存没命中、要去编译（或者从磁盘缓存加载）之前，Triton 会调用这个钩子。"""
    sig, consts, attrs = compile["signature"], compile["constants"], compile["configs"][0]
    parts = []
    for i, name in enumerate(sig):
        if (i,) in consts:
            parts.append(f"{name}={consts[(i,)]}")
        else:
            div16 = ["tt.divisibility", 16] in attrs.get((i,), [])
            parts.append(f"{name}: {sig[name]}{'（16 的倍数）' if div16 else ''}")
    print("      编译 " + ", ".join(parts))
    return False                       # 返回 False 表示「照常编译」


triton.knobs.runtime.jit_cache_hook = on_compile


def call(label, n, dtype=torch.float32, BLOCK=1024):
    x = torch.randn(n, device=DEVICE, dtype=dtype); y = torch.randn_like(x); out = torch.empty_like(x)
    gpu.synchronize()
    print(f"  {label}")
    t = time.perf_counter()
    add_kernel[(triton.cdiv(n, BLOCK),)](x, y, out, n, BLOCK=BLOCK)
    gpu.synchronize()
    print(f"      耗时 {(time.perf_counter() - t) * 1e3:.2f} ms")


call("n=98432", 98432)
call("再调一次", 98432)
call("n=1048576（换了长度，但也是 16 的倍数）", 1048576)
call("n=98433（不是 16 的倍数）", 98433)
call("fp16", 98432, torch.float16)
call("BLOCK=256", 98432, BLOCK=256)
call("n=1", 1)
本地运行：python main.py # 需要 NVIDIA sm_80+ 或 Intel GPU（XPU）；环境见附录 A

逐条对照图 4-1：

  • 第一次运行时，「初始化 driver」花了几秒。 这是 Intel 后端特有的：driver 第一次运行时要现场编几段 C++ 胶水代码（附录 A 第 3.3 节），编好的 .so 也放进缓存目录。第二次运行，同一个缓存目录里已经有了，只要几十毫秒。NVIDIA 后端也有类似的胶水代码（启动 kernel 用的 launcher），开销小一些。
  • 「再调一次」和「n=1048576」都没有触发编译，只花了零点几毫秒，走的是内存里的缓存。注意 1048576 和 98432 是不同的长度，但它们都是 16 的倍数，特化键相同，于是用同一份编译结果。长度本身不是特化键的一部分，长度能不能被 16 整除才是。
  • n=98433、fp16、BLOCK=256、n=1 各触发了一次编译。 看钩子打印的特化键：n=98433 少了「16 的倍数」；fp16 的指针类型变成了 *fp16；BLOCK=256 换了常量；n=1 直接被当成常量 n=1 编进了 kernel。第一次运行时，每次编译 0.1 秒左右。第二次运行时，同样这几次「编译」只要一两毫秒，因为是从磁盘缓存加载的。
  • **两次运行里，第一次调用 add_kernel 都要 1 秒左右，**哪怕第二次时磁盘缓存里早就有了。我用 cProfile 看过，这 1 秒几乎全部花在 python/triton/runtime/cache.py 的 triton_key() 上：它给 Triton 自己算一个指纹，要哈希 compiler、backends、language 目录下的源码，再把整个 libtriton.so 读一遍。缓存的键里包含这个指纹，Triton 一升级，旧缓存就自动作废。它带着 @functools.lru_cache()，每个进程只算一次。Intel 的 libtriton.so 有 1.2 GB；PyPI 上 NVIDIA 版的 triton 3.9.0 只有 477 MB，这笔开销会小一些。
推理服务里的冷启动

上面这几笔开销加起来，就是「服务刚启动时，前几个请求特别慢」的来源：每个进程都要算一次 Triton 的指纹，每种新的特化键都要编译或加载一次。如果第一个请求的序列长度恰好不是 16 的倍数，第二个是，那第二个请求还会再触发一次编译。生产环境里常见的做法是：启动时先用各种可能的形状把 kernel 都调一遍（预热），并且把 TRITON_CACHE_DIR 放在持久化的盘上，让磁盘缓存在重启之间保留下来。

特化：哪些变化会触发重新编译

把上面的实测总结成规则。Triton 3.9.0 为每次调用算一个特化键，键里有：

参数 键里记什么 源码位置
张量（指针） 元素类型（*fp32、*bf16…）；地址是不是 16 字节的倍数 python/triton/backends/compiler.py 的 get_tensor_specialization
整数 等于 1 时记成常量；否则记类型（i32，超出 32 位范围是 i64），以及是不是 16 的倍数 python/src/specialize.cc 的 handle_long_type
tl.constexpr 值本身
启动参数 num_warps、num_stages 等

能被 16 整除这件事为什么这么重要，第 3 章已经看到了：它决定了编译器敢不敢做向量化访存。

如果某个整数参数变化得很频繁，而且你不在乎向量化，可以关掉对它的特化：@triton.jit(do_not_specialize=["n"])。这样 n 能不能被 16 整除、是不是 1，都不会再触发编译。代价是编译器永远不知道 n 的对齐，第 3 章那个例子的 PTX 里就一律是 16 条标量 load。

推理服务里，同一个 kernel 会被各种长度调用。它到底会被编译几次？下面的模型按上面的规则算特化键，只用标准库，直接点运行；你可以改 lengths：

Python 
# Triton 怎么决定「这次调用要不要重新编译」：按 Triton 3.9.0 的规则算特化键。只用标准库。
#
# 对整数参数（python/src/specialize.cc 的 handle_long_type）：
#   等于 1        -> 当成常量编进 kernel（键里记下值 1）
#   16 的倍数     -> 键里记 "D"（divisibility = 16），编译器可以放心向量化
#   其它          -> 键里只记类型（i32 或 i64）
# 对指针参数：地址是 16 的倍数就记 "D"（PyTorch 分配的张量基本都是）。
# tl.constexpr 参数：值本身就是键的一部分。


def int_key(v, specialize=True):
    if specialize and v == 1:
        return ("const", 1)
    ty = "i32" if -2**31 <= v < 2**31 else "i64"
    return (ty, "D" if specialize and v % 16 == 0 else "")


def count_compiles(calls, specialize_n=True):
    seen = []
    for dtype, n, block in calls:
        key = (dtype, int_key(n, specialize_n), block)   # 指针都按 16 字节对齐处理
        if key not in seen:
            seen.append(key)
    return seen


# 一次推理服务里，同一个逐点 kernel 被这些长度调用（dtype 和 BLOCK 不变）
lengths = [1, 1, 7, 128, 129, 4096, 4097, 1, 31, 512, 2**31]
calls = [("bf16", n, 1024) for n in lengths]

for spec in (True, False):
    keys = count_compiles(calls, specialize_n=spec)
    print(f"specialize n = {spec}：{len(lengths)} 次调用，编译 {len(keys)} 次")
    for k in keys:
        print("   ", k)
    print()

# 再换一个 dtype、一个 BLOCK：每一种组合都是新的特化
calls += [("fp32", 4096, 1024), ("bf16", 4096, 256)]
print(f"再加上 fp32 和 BLOCK=256：编译 {len(count_compiles(calls))} 次")

运行结果：

specialize n = True：11 次调用，编译 4 次
    ('bf16', ('const', 1), 1024)
    ('bf16', ('i32', ''), 1024)
    ('bf16', ('i32', 'D'), 1024)
    ('bf16', ('i64', 'D'), 1024)

specialize n = False：11 次调用，编译 2 次
    ('bf16', ('i32', ''), 1024)
    ('bf16', ('i64', ''), 1024)

再加上 fp32 和 BLOCK=256：编译 6 次

11 种长度只编译了 4 次。n 在特化键里只有四种「样子」：等于 1、普通的 i32、16 的倍数的 i32、16 的倍数的 i64。关掉特化以后只剩两种，因为 i32 和 i64 总是要区分的。所以对逐点 kernel 来说，长度变化不会引起「编译风暴」。真正危险的是把一个经常变化的值标成 tl.constexpr，那样每一个新的值都是一次编译。第 14 章讲 autotune 时，你会看到它的 key 参数是怎么利用、又是怎么约束这件事的。

缓存目录里有什么

磁盘缓存默认在 ~/.triton/cache，可以用 TRITON_CACHE_DIR 改到别处；~ 这一级可以用 TRITON_HOME 改（都定义在 python/triton/knobs.py）。每个特化键对应一个子目录，目录名是哈希值。里面的文件就是各级编译产物。在纯 CPU 的机器上把 add_kernel 编到 NVIDIA sm_86（附录 A 第 8 节的离线编译），得到的是：

add_kernel.source        # 第 0 级：从 Python AST 生成、还没优化的 TTIR
add_kernel.ttir          # Triton IR，硬件无关
add_kernel.ttgir         # TritonGPU IR，带 layout，第 3 章看过
add_kernel.llir          # LLVM IR
add_kernel.ptx           # NVIDIA 的虚拟汇编
add_kernel.cubin         # 真正加载到 GPU 上的二进制
add_kernel.json          # 元数据
__grp__add_kernel.json   # 这一组文件的清单

Intel 后端的最后两级换成了 add_kernel.spv（SPIR-V），由 GPU 驱动在加载时再编成机器码。缓存目录的根上还会多出几个 .so，就是 driver 第一次运行时编的那些胶水模块。

add_kernel.json 里记着这次编译的全部选项和结果，几个最常用的字段（sm_86 的那份）：

"name": "add_kernel", "num_warps": 4, "num_stages": 3, "shared": 0,
"target": {"backend": "cuda", "arch": 86, "warp_size": 32}, "enable_fp_fusion": true

shared 是这个 kernel 用了多少字节 shared memory（vector add 不用，是 0；第 3 章的 softmax 是 16）。以后你想知道「编译器到底给我的 kernel 选了什么」，第一个该看的就是这个文件。顺带一提，Intel 后端的 num_stages 默认是 2，NVIDIA 是 3：同一个 kernel，不同后端的默认值也不一样。

这些文件也是第四部分的主要材料：第 19 章会按顺序读一遍 .source → .ttir → .ttgir → .llir，看每一级做了什么。

minillm 起步：add 与 silu_mul

现在开始全书的贯穿项目 minillm：一个用 Triton 写的、简化的 decoder-only Transformer 层。代码在本书仓库的 books/inside-triton/code/minillm/，是一个能 pip install -e 的小包（附录 A 第 9 节）。这一章往里加两个逐点 kernel，都在 minillm/kernels/pointwise.py：

  • add：就是本章的 vector add。Transformer 层里的残差连接 h = x + attn(x) 用得到它。
  • silu_mul：silu(gate) * up。现在主流模型的 MLP 用的是 SwiGLU：输入分别乘两个权重矩阵得到 gate 和 up，再算 silu(gate) * up，然后乘第三个矩阵。中间这一步是纯逐点的。

silu_mul 的 kernel 和 vector add 几乎一样，只多了两件事：

Triton (Python)
@triton.jit
def _silu_mul_kernel(gate_ptr, up_ptr, out_ptr, n, BLOCK: tl.constexpr):
    """out = silu(gate) * up，SwiGLU MLP 中间那一步。"""
    pid = tl.program_id(0)
    offs = pid * BLOCK + tl.arange(0, BLOCK)
    mask = offs < n
    # 输入可能是 fp16 / bf16：在 fp32 里算 sigmoid，最后再转回输出的类型
    g = tl.load(gate_ptr + offs, mask=mask).to(tl.float32)
    u = tl.load(up_ptr + offs, mask=mask).to(tl.float32)
    out = g * tl.sigmoid(g) * u
    tl.store(out_ptr + offs, out.to(out_ptr.dtype.element_ty), mask=mask)
  • 在 fp32 里算。 模型的激活值通常是 bf16。bf16 只有 8 位有效数字，直接在 bf16 里算 exp 和除法，误差会明显变大。所以先 .to(tl.float32)，算完再转回去。转换发生在寄存器里，不多搬一个字节。
  • out_ptr.dtype.element_ty：指针指向的元素类型。用它来决定存回去的类型，这个 kernel 就对 fp32、fp16、bf16 都适用。别忘了，每种 dtype 都会单独编译一次。

外面再包一层普通的 Python 函数，负责检查输入、分配输出、算 grid：

Python
def silu_mul(gate: torch.Tensor, up: torch.Tensor, BLOCK: int = 1024) -> torch.Tensor:
    _check(gate, up)                          # 形状、dtype、设备相同，并且是连续张量
    out = torch.empty_like(gate)
    n = gate.numel()
    if n:                                     # grid 不能是 0
        _silu_mul_kernel[(triton.cdiv(n, BLOCK),)](gate, up, out, n, BLOCK=BLOCK)
    return out

动手

  1. 看看你的机器上第一次调用有多贵。 把「实测」那一节的脚本存成 life.py，按上面的两条命令跑两次。在 NVIDIA GPU 上，「初始化 driver」和第一次调用的耗时分别是多少？和 Max 1100 比，哪一笔差得最多，为什么？
  2. 关掉对 n 的特化。 把 @triton.jit 改成 @triton.jit(do_not_specialize=["n"])，再跑一次。预测：n=98433 和 n=1 那两行不会再触发编译，其余几行照旧。然后用附录 A 第 8 节的 triton_ir_local.py 看一眼 PTX 里的 ld.global 指令，和第 3 章的表比一比，这个改动的代价是什么？
  3. 在浏览器的模型里，把 lengths 换成「1 到 4096 的所有整数」（list(range(1, 4097))），会编译几次？再把 BLOCK 也改成随长度变化（比如 min(4096, triton.next_power_of_2(n)) 那样，自己用 Python 写一个），又会编译几次？

这一章的要点

  • @triton.jit 把函数包成 JITFunction，定义时什么也不做。每次 kernel[grid](...)：算特化键 → 查内存缓存 → 查磁盘缓存 → 都没有才编译。
  • 在 Max 1100 上实测：编译一个特化版本约 0.1 秒，从磁盘缓存加载约 1–3 毫秒，命中内存缓存约 0.05–0.2 毫秒。每个进程第一次调用还要多花约 1 秒，用来给 Triton 自己算指纹（triton_key()，要把 1.2 GB 的 libtriton.so 哈希一遍）。
  • 特化键包括：张量的元素类型和 16 字节对齐、整数是否等于 1 以及是否是 16 的倍数、tl.constexpr 的值、num_warps 等启动参数。长度本身不在键里，所以长度变化不会引起编译风暴；把经常变化的值标成 tl.constexpr 才会。
  • tl.arange 的长度必须是 2 的幂，并且是编译时常量。mask 掉的位置，tl.load 返回 other；不给 other，值是未定义的，后面要做归约时必须给。
  • 磁盘缓存在 ~/.triton/cache（TRITON_CACHE_DIR、TRITON_HOME 可改），每个特化版本一个目录，里面是每一级 IR、二进制和一份 .json 元数据。服务上线前用各种形状预热一遍，并把缓存目录放在持久化的盘上。
