第 3 章 块级编程：一个 program 处理一块数据

这一章想让你带走什么

CUDA 让你写一个线程做什么；Triton 让你写一个 program 处理一块数据做什么。这一章把同一个向量加法用两种方式并排写出来，然后打开 Triton 的编译产物，看清中间那一层是谁做的：这一块数据怎么分给几百个线程、访存怎么合并成大块读写、归约怎么在线程之间完成，全部是编译器替你决定的，而且这些决定都明明白白地写在 IR 里。

读完你会拿到三样东西。一是一个必须讲透的撞名：Triton 的 BLOCK 是数据的形状，CUDA 的 block 是一组线程，前者对应的是后者处理的那块数据，执行它的线程数由另一个参数 num_warps 决定。二是 Triton 编译器的第一个「决定」：#ttg.blocked layout。你会用一个浏览器里能跑的小模型，预测 12 种参数组合下生成的访存指令条数，并和真实的 PTX 逐条核对。三是一张诚实的账单：Triton 替你做了什么，又拿走了什么。

同一个向量加法，两种写法

先看 kernel 本身。左边是 CUDA，右边是 Triton，算的都是 out = x + y：

CUDA：写一个线程做什么
CUDA C++
__global__ void add_kernel(
        const float* x, const float* y,
        float* out, int n) {
    // 我是第几个线程？
    int i = blockIdx.x * blockDim.x
          + threadIdx.x;
    // 我负责第 i 个元素；
    // 多出来的线程什么也不做
    if (i < n)
        out[i] = x[i] + y[i];
}
Triton：写一个 program 处理哪一块
Triton (Python)
@triton.jit
def add_kernel(x_ptr, y_ptr, out_ptr, n,
               BLOCK: tl.constexpr):
    # 我是第几个 program？
    pid = tl.program_id(0)
    # 我负责一整块：BLOCK 个元素的下标
    base = pid * BLOCK
    offs = base + tl.arange(0, BLOCK)
    mask = offs < n
    x = tl.load(x_ptr + offs, mask=mask)
    y = tl.load(y_ptr + offs, mask=mask)
    tl.store(out_ptr + offs, x + y,
             mask=mask)

两边长得很像，但变量的「形状」完全不同：

  • CUDA 里的 i 是一个整数。每个线程有自己的 i，几万个线程同时执行这段代码，各算各的一个元素。
  • Triton 里的 offs 是一个张量：tl.arange(0, BLOCK) 产生 [0, 1, …, BLOCK-1]，加上 pid * BLOCK 以后，就是这个 program 要处理的那一整块元素的下标。x、y、mask 也都是长度为 BLOCK 的张量，x + y 是整块相加。

所以 Triton 里没有「线程」这个概念。你写的代码描述的是一整块数据上的运算，读起来更像 NumPy，而不是 CUDA。这一块数据最后由哪些线程、按什么方式算，是编译器的事。

再看两边各自怎么启动。CUDA 要你决定每个 block 有几个线程（这里是 256），再算出要几个 block：

CUDA C++ 🔗 在 Compiler Explorer 打开（看 PTX）
#include <cstdio>
#include <cuda_runtime.h>

// 每个线程负责一个元素：你要自己算出「我是第几个线程」，再决定处理哪个元素
__global__ void add_kernel(const float* x, const float* y, float* out, int n) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;   // 全局线程号 = 第几个 block × block 大小 + block 内的线程号
    if (i < n)                                        // 最后一个 block 可能有多出来的线程
        out[i] = x[i] + y[i];
}

int main() {
    const int n = 98432;
    float *x, *y, *out;
    cudaMallocManaged(&x, n * sizeof(float));         // 统一内存：CPU 和 GPU 都能直接访问
    cudaMallocManaged(&y, n * sizeof(float));
    cudaMallocManaged(&out, n * sizeof(float));
    for (int i = 0; i < n; ++i) { x[i] = i; y[i] = 2 * i; }

    const int threads = 256;                           // 一个 block 里的线程数，由你决定
    add_kernel<<<(n + threads - 1) / threads, threads>>>(x, y, out, n);
    cudaDeviceSynchronize();

    int bad = 0;
    for (int i = 0; i < n; ++i) bad += out[i] != 3.0f * i;
    printf("n = %d，%d 个 block × %d 个线程，错误 %d 个\n", n, (n + threads - 1) / threads, threads, bad);
    cudaFree(x); cudaFree(y); cudaFree(out);
}
本地运行：nvcc -std=c++20 -O3 -arch=sm_90 main.cu -o app && ./app

Triton 要你决定每个 program 处理多大一块数据（BLOCK），再算出要几个 program。[grid] 里写的就是 program 的个数：

Triton (Python) 
# arch: sm80 xpu
import torch
import triton
import triton.language as tl

DEVICE = triton.runtime.driver.active.get_active_torch_device()


@triton.jit
def add_kernel(x_ptr, y_ptr, out_ptr, n, BLOCK: tl.constexpr):
    pid = tl.program_id(0)                       # 我是第几个 program
    offs = pid * BLOCK + tl.arange(0, BLOCK)     # 我负责的这一整块元素的下标
    mask = offs < n                              # 最后一块可能越界
    x = tl.load(x_ptr + offs, mask=mask)
    y = tl.load(y_ptr + offs, mask=mask)
    tl.store(out_ptr + offs, x + y, mask=mask)


n = 98432
x = torch.arange(n, device=DEVICE, dtype=torch.float32)
y = 2 * x
out = torch.empty_like(x)
BLOCK = 1024
grid = (triton.cdiv(n, BLOCK),)                  # 向上取整：98432 / 1024 = 96.125，要 97 个 program
add_kernel[grid](x, y, out, n, BLOCK=BLOCK)
bad = (out != 3 * x).sum().item()
print(f"n = {n}，{grid[0]} 个 program × BLOCK {BLOCK}，错误 {bad} 个")
本地运行：python main.py # 需要 NVIDIA sm_80+ 或 Intel GPU（XPU）；环境见附录 A

运行结果（Max 1100；A10 上相同）：

n = 98432，97 个 program × BLOCK 1024，错误 0 个

撞名：Triton 的 block 不是 CUDA 的 block

这是初学 Triton 时最容易绕晕的一点，值得单独讲清楚。

是什么 由谁决定 上面的例子
CUDA 的 block（thread block） 一组线程 <<<grid, threads>>> 里的 threads 256 个线程
Triton 的 program 一个执行单位，对应 CUDA 的一个 thread block [grid] 里的个数 97 个
Triton 的 BLOCK（块，block） 一个 program 处理的数据的形状 你传的 tl.constexpr 参数 1024 个元素
执行一个 program 的线程数 num_warps × 32 启动参数 num_warps，默认 4 128 个线程

也就是说，一个 Triton program 会被编译成一个 CUDA thread block（在 Intel 上是一个 work-group），由 num_warps 个 warp 来执行；它要处理的数据有 BLOCK 个元素。BLOCK 和线程数是两个独立的参数：上面的例子里，128 个线程处理 1024 个元素，每个线程 8 个。本书后面说「块」或者「block」时，指的都是 Triton 的那个数据块；说到 CUDA 的线程块，会写全「thread block」。

图 3-1　从 program 到线程的映射。蓝色是 Triton 层面的概念（program、数据块），灰色是硬件层面的（warp、线程）。最后一个 program 只有一小部分元素落在 n 以内，其余靠 mask 跳过（第 4 章）。线程的分配方式由编译器决定，你在 Triton 源码里看不到

Triton 替你做了什么（一）：把一块数据分给线程

图 3-1 里那张分配表，是编译器的第一个决定。它就写在 TTGIR 里。下面是 Triton 3.9.0 为上面的 add_kernel（BLOCK=1024，num_warps=4）编到 sm_86 时生成的 TTGIR，去掉了行号信息 loc(...)，其余原样（用附录 A 第 8 节的 triton_ir_local.py 取的，不需要 GPU）：

TTGIR
#blocked = #ttg.blocked<{sizePerThread = [4], threadsPerWarp = [32], warpsPerCTA = [4], order = [0]}>
module attributes {"ttg.num-ctas" = 1 : i32, "ttg.num-warps" = 4 : i32, ttg.target = "cuda:86", "ttg.threads-per-warp" = 32 : i32, "ttng.two-ctas" = false} {
  tt.func public @add_kernel(%x_ptr: !tt.ptr<f32> {tt.divisibility = 16 : i32}, %y_ptr: !tt.ptr<f32> {tt.divisibility = 16 : i32}, %out_ptr: !tt.ptr<f32> {tt.divisibility = 16 : i32}, %n: i32 {tt.divisibility = 16 : i32}) attributes {noinline = false} {
    %c1024_i32 = arith.constant 1024 : i32
    %offs = tt.get_program_id x : i32
    %offs_0 = arith.muli %offs, %c1024_i32 : i32
    %offs_1 = tt.make_range {end = 1024 : i32, start = 0 : i32} : tensor<1024xi32, #blocked>
    %offs_2 = tt.splat %offs_0 : i32 -> tensor<1024xi32, #blocked>
    %offs_3 = arith.addi %offs_2, %offs_1 : tensor<1024xi32, #blocked>
    %mask = tt.splat %n : i32 -> tensor<1024xi32, #blocked>
    %mask_4 = arith.cmpi slt, %offs_3, %mask : tensor<1024xi32, #blocked>
    %x = tt.splat %x_ptr : !tt.ptr<f32> -> tensor<1024x!tt.ptr<f32>, #blocked>
    %x_5 = tt.addptr %x, %offs_3 : tensor<1024x!tt.ptr<f32>, #blocked>, tensor<1024xi32, #blocked>
    %x_6 = tt.load %x_5, %mask_4 : tensor<1024x!tt.ptr<f32>, #blocked>
    %y = tt.splat %y_ptr : !tt.ptr<f32> -> tensor<1024x!tt.ptr<f32>, #blocked>
    %y_7 = tt.addptr %y, %offs_3 : tensor<1024x!tt.ptr<f32>, #blocked>, tensor<1024xi32, #blocked>
    %y_8 = tt.load %y_7, %mask_4 : tensor<1024x!tt.ptr<f32>, #blocked>
    %0 = tt.splat %out_ptr : !tt.ptr<f32> -> tensor<1024x!tt.ptr<f32>, #blocked>
    %1 = tt.addptr %0, %offs_3 : tensor<1024x!tt.ptr<f32>, #blocked>, tensor<1024xi32, #blocked>
    %2 = arith.addf %x_6, %y_8 : tensor<1024xf32, #blocked>
    tt.store %1, %2, %mask_4 : tensor<1024x!tt.ptr<f32>, #blocked>
    tt.return
  }
}

现在还不必读懂每一行（第 19 章会逐行讲），只看三件事：

  • 每一行 IR 都能指回一行源码。 SSA 值的名字直接取自你的 Python 变量名：%offs_1 = tt.make_range 是 tl.arange(0, BLOCK)，%mask_4 = arith.cmpi slt 是 offs < n，%x_6 = tt.load 是第一个 tl.load。
  • 每个张量的类型后面都挂着 #blocked。 tensor<1024xf32, #blocked> 的意思是「1024 个 fp32，按 #blocked 这张分配表分给线程」。这就是 layout（布局，TTGIR 里叫 encoding）：它是类型的一部分，描述张量的每个元素放在哪个线程的哪个寄存器里。第 20、21 章会专门讲它。
  • 参数上的 tt.divisibility = 16：Triton 发现传进来的指针和 n 都能被 16 整除，于是把这个信息记进了 IR。下面会看到它有什么用。

#blocked 里的三个数就是图 3-1：每个线程拿 4 个连续元素（sizePerThread = [4]），一个 warp 32 个线程（threadsPerWarp = [32]），一个 program 4 个 warp（warpsPerCTA = [4]）。一轮覆盖 4 × 32 × 4 = 512 个元素，1024 个元素就排两轮。

为什么是 4？算这个数的代码在 Triton 源码 lib/Dialect/TritonGPU/Transforms/Utility.cpp 的 getNumElementsPerThread 里。它取三者的最小值：指针能保证的对齐、下标的连续性、一条访存指令能装下几个元素（128 位，也就是 4 个 fp32）。然后 CoalesceUtils.cpp 的 buildCoalescedEncoding 再把它限制在「总元素数 ÷ 总线程数」以内。这个 pass 叫 coalesce（合并访问），名字说明了它的目的：让一个 warp 的访存落在连续的地址上。

规则不复杂，可以自己预测。下面的模型实现了这张分配表，并用同样的规则算出：换不同的 BLOCK 和 num_warps，每个线程要发几条 load 指令。只用标准库，直接点运行：

Python 
# 一维 blocked layout：BLOCK 个元素怎么分给 num_warps × 32 个线程。只用标准库。
#
# Triton 的规则（第 20 章细讲）：每个线程拿 size_per_thread 个**连续**元素，
# 一个 warp 的 32 个线程依次排开，warp 再依次排开；一轮排不完 BLOCK 个，就从头再来一轮。


def owner(e, spt, tpw, wpc):
    """第 e 个元素归谁：返回 (warp, 线程, 这个线程的第几个寄存器)。"""
    tile = spt * tpw * wpc                     # 一轮能覆盖的元素数
    rep, pos = divmod(e, tile)
    t = pos // spt                             # 在整个 program 里是第几个线程
    return t // tpw, t % tpw, rep * spt + pos % spt


def show(block, spt, tpw, wpc):
    print(f"BLOCK={block}，sizePerThread={spt}，threadsPerWarp={tpw}，warpsPerCTA={wpc}：")
    row = []
    for e in range(block):
        w, t, r = owner(e, spt, tpw, wpc)
        row.append(f"w{w}t{t}r{r}")
    for i in range(0, block, 8):
        print("  " + " ".join(f"{x:>7}" for x in row[i:i + 8]))
    print()


# 1) 一个缩小版，方便看清：16 个元素，2 个 warp，每个 warp 4 个线程
show(16, spt=2, tpw=4, wpc=2)


# 2) 预测真实的 add_kernel 会生成几条 load 指令（x、y 两个张量）
def predict_loads(block, num_warps, elem_bytes=4):
    threads = 32 * num_warps
    per_thread = max(block // threads, 1)            # 每个线程分到几个元素
    vec = min(per_thread, 16 // elem_bytes)          # 一条指令最多读 16 字节
    return 2 * (per_thread // vec), vec


print("预测 add_kernel 的 load 指令（每个线程，x 和 y 合计）：")
print("  BLOCK  num_warps  每线程元素  向量宽度  load 指令")
for block in (128, 256, 1024, 4096):
    for nw in (1, 4, 8):
        n, vec = predict_loads(block, nw)
        print(f"  {block:5}  {nw:9}  {max(block // (32 * nw), 1):10}  {vec:8}  {n:9}")
print()


# 3) 合并访问：一个 warp 发一条 load，32 个线程各要一段地址。
#    硬件不是按字节取数据的，而是按固定大小的一段（GRAIN 字节）去取：
#    NVIDIA 从 L2 / 显存取数据的单位是 32 字节的 sector；Max 1100 上实测大约是 64 字节（见本章「动手」）。
def coalescing(name, addr_of_lane, bytes_per_lane, grain):
    segs = {a // grain for lane in range(32)
            for a in range(addr_of_lane(lane), addr_of_lane(lane) + bytes_per_lane)}
    useful = 32 * bytes_per_lane
    print(f"  {name:22} 取 {len(segs):3} 段（{len(segs) * grain:4} 字节），"
          f"有用 {useful:3} 字节，利用率 {useful / (len(segs) * grain):4.0%}")


for grain in (32, 64):
    print(f"一条 warp 级 load 指令（fp32），按 {grain} 字节一段取：")
    coalescing("线程 i 读第 i 个", lambda i: 4 * i, 4, grain)
    coalescing("线程 i 读第 4i..4i+3 个", lambda i: 16 * i, 16, grain)
    for stride in (2, 4, 8, 16, 32):
        coalescing(f"线程 i 读第 {stride}i 个", lambda i, s=stride: 4 * s * i, 4, grain)
    print()

12 行全部对上。注意 BLOCK=128, num_warps=8 这一行：256 个线程只有 128 个元素，有一半线程拿到的是重复的元素。这是允许的，只是浪费。BLOCK 太小、num_warps 太大，线程就会闲着。

Triton 替你做了什么（二）：合并访问与向量化

上面的 PTX 里，Triton 版的 load 是 ld.global.v4.b32：一条指令读 4 个 fp32，16 字节。CUDA 版的 PTX（点 CUDA 代码块的按钮，在 CE 里就能看到）用的是 ld.global.f32：一条指令读 1 个 fp32。下面是 Triton 版 PTX 里所有的访存指令（BLOCK=1024，num_warps=4，节选）：

LLVM IR
	mov.u32 	%r28, %tid.x;
	...
	@%p1 ld.global.v4.b32 { %r1, %r2, %r3, %r4 }, [ %rd1 + 0 ];
	@%p2 ld.global.v4.b32 { %r5, %r6, %r7, %r8 }, [ %rd2 + 0 ];
	@%p1 ld.global.v4.b32 { %r9, %r10, %r11, %r12 }, [ %rd3 + 0 ];
	@%p2 ld.global.v4.b32 { %r13, %r14, %r15, %r16 }, [ %rd4 + 0 ];
	...
	@%p1 st.global.v4.b32 [ %rd5 + 0 ], { %r17, %r18, %r19, %r20 };
	@%p2 st.global.v4.b32 [ %rd6 + 0 ], { %r21, %r22, %r23, %r24 };

有两个细节值得看：%tid.x（线程号）在你的源码里从来没出现过，它是编译器插进来的；@%p1 是谓词，「%p1 为真才执行这条指令」，它就是你的 mask。每个线程两个谓词，因为每个线程的 8 个元素分在两轮。

两边都做到了合并访问（coalesced access）：一个 warp 的 32 个线程读的是一段连续地址，硬件可以把它们合成几次大块读取。区别在于 Triton 还做了向量化：每个线程一次读 16 字节，发出的指令少了 4 倍。对向量加法这种纯访存的 kernel，指令少意味着同样多的在途访存请求，需要的线程更少（回想第 2 章的 Little 定律）。

向量化有一个前提，它正是 tt.divisibility = 16 存在的原因。如果把上面例子里的 n 改成一个奇数，比如 1048577：

  • TTIR 里 %n 的 tt.divisibility = 16 消失了，因为 Triton 不能再保证 n 是 16 的倍数；
  • TTGIR 里的 layout 没有变，仍然是 sizePerThread = [4]，每个线程还是拥有 4 个连续元素；
  • 但 PTX 里的 4 条 ld.global.v4.b32 变成了 16 条 ld.global.b32。mask 的边界不再落在 4 个元素的整数倍上，同一个线程的 4 个元素可能一部分在界内、一部分在界外，没法一条指令读完。限制向量宽度的代码在 third_party/nvidia/lib/TritonNVIDIAGPUToLLVM/LoadStoreOpToLLVM.cpp，它用 getMaskAlignment(mask) 取 mask 的对齐。

Triton 会根据每次调用的实际参数（指针和整数能不能被 16 整除、是不是等于 1）特化出不同版本的 kernel，再分别缓存。这是第 4 章的主题。现在先记住一个实用的结论：张量的长度、stride 尽量是 16 的倍数，否则你可能在不知情的情况下丢掉向量化。

Triton 替你做了什么（三）：线程之间的协作

向量加法里，每个线程只管自己的元素，线程之间不需要交流。归约就不一样了。第 1 章的 softmax_kernel 里有一句 tl.max(x, axis=0)：一整行 1024 个元素分在 128 个线程手里，要求出它们的最大值，线程之间必须交换数据。

在 CUDA 里，这要你自己写：先在每个 warp 内部用 shuffle 指令两两交换、折半归约，再把每个 warp 的结果写进 shared memory，同步一次，最后由一个 warp 读出来再归约一次。在 Triton 里，你只写了一个 tl.max 和一个 tl.sum。把那个 kernel 用 3.9.0 编到 sm_86（BLOCK=1024，num_warps=4），PTX 里有：

指令 条数 用途
shfl.sync.bfly 14 warp 内的蝶形交换：每次归约 5 轮（32 → 1）在 warp 内，2 轮（4 个 warp → 1）在 warp 之间
st.shared.b32 / ld.shared.b32 各 2 把每个 warp 的部分结果写进 shared memory，再读出来
bar.sync 3 等所有 warp 都写完 / 读完

编译元数据里记着这个 kernel 用了 16 字节 shared memory：4 个 warp，每个 warp 放一个 fp32 的部分结果。这些全部是编译器生成的。你没写一行 shared memory 的代码，也没写一次同步。

Triton 拿走了什么

替你做决定是有代价的。用 Triton，你放弃了：

  • 线程号。 你拿不到「我是第几个线程」，所以不能让不同线程走不同的代码路径。所有分支都必须写成整块上的 tl.where 或 mask。逐元素的、数据相关的控制流（比如每个元素循环次数不同），在 Triton 里写起来别扭，跑起来也未必快。
  • warp 级的原语。 没有 shuffle、没有 warp vote，也不能指定「这个 warp 干这件事，那个 warp 干那件事」。归约和扫描由 tl.sum、tl.max、tl.cumsum 这些整块操作提供，编译器决定怎么实现。
  • shared memory 的控制权。 你不能决定什么数据放进 shared memory、放成什么形状、怎么避免 bank 冲突。编译器在需要的时候自己分配（归约、convert_layout、矩阵乘的流水线）。
  • program 之间的同步。 不同 program 之间没有同步手段，只有原子操作（tl.atomic_add 等）。这一点和 CUDA 的 thread block 一样。

前三项，正是 CUDA 高手用来榨干最后 10–20% 性能的手段。大多数时候，Triton 的编译器做得足够好；它做得不好的地方，你可以看懂它的 IR，然后调整写法（第四部分），或者下到 Gluon，把 layout 和 warp 分工拿回来（第 24、25 章）。

动手：看一眼合并访问的代价

上面的模型说：相邻线程读的地址隔得越远，一条访存指令取回来的数据里，有用的就越少。在真机上测一下。下面的 kernel 每次都只读 16 Mi 个有用的 fp32，但相邻线程读的地址相隔 STRIDE 个元素：

Triton (Python) 
# arch: sm80 xpu
import torch
import triton
import triton.language as tl

DEVICE = triton.runtime.driver.active.get_active_torch_device()


@triton.jit
def gather_kernel(x_ptr, y_ptr, n, STRIDE: tl.constexpr, BLOCK: tl.constexpr):
    offs = tl.program_id(0) * BLOCK + tl.arange(0, BLOCK)
    mask = offs < n
    x = tl.load(x_ptr + offs * STRIDE, mask=mask)   # 相邻线程读的地址相隔 STRIDE 个元素
    tl.store(y_ptr + offs, x, mask=mask)            # 写总是连续的


n = 16 * 2**20                                      # 每次都只搬 16 Mi 个有用的 fp32
y = torch.empty(n, device=DEVICE)
print(f"{getattr(torch, DEVICE.type).get_device_name()}，triton {triton.__version__}，每次读 {n // 2**20} Mi 个 fp32")
for stride in (1, 2, 4, 8, 16, 32):
    x = torch.randn(n * stride, device=DEVICE)
    ms = triton.testing.do_bench(lambda: gather_kernel[(triton.cdiv(n, 1024),)](x, y, n, STRIDE=stride, BLOCK=1024))
    print(f"  STRIDE={stride:2}  {ms:6.3f} ms  有用的带宽 {2 * n * 4 / ms / 1e6:5.0f} GB/s")
    del x
本地运行：python main.py # 需要 NVIDIA sm_80+ 或 Intel GPU（XPU）；环境见附录 A

运行结果（Max 1100）：

Intel(R) Data Center GPU Max 1100，triton 3.9.0，每次读 16 Mi 个 fp32
  STRIDE= 1   0.258 ms  有用的带宽   519 GB/s
  STRIDE= 2   0.370 ms  有用的带宽   363 GB/s
  STRIDE= 4   0.585 ms  有用的带宽   229 GB/s
  STRIDE= 8   1.022 ms  有用的带宽   131 GB/s
  STRIDE=16   1.848 ms  有用的带宽    73 GB/s
  STRIDE=32   1.789 ms  有用的带宽    75 GB/s

先用模型预测，再对照。假设耗时正比于实际搬运的字节：写总是 1 份；读在跨步为 s 时要多取 min(s, 段长 ÷ 4) 倍（取数一次取一整段，跨步超过一段以后，每个元素都独占一段，不会更糟）。按 Max 1100 上 64 字节一段算，相对于 STRIDE=1 的耗时应当是：

STRIDE 模型预测 实测
2 1.5× 1.43×
4 2.5× 2.27×
8 4.5× 3.96×
16 8.5× 7.16×
32 8.5× 6.93×

趋势完全对得上：跨步每翻一倍，耗时也接近翻一倍；到 16 以后就不再变慢了。16 个 fp32 正好是 64 字节，这说明 Max 1100 上「一次取一段」的那一段大约是 64 字节。实测都比预测好一点，因为缓存会帮忙：相邻 program 读到的那些「没用」的数据，有一部分正好是别的 program 要用的。

接下来请你做两件事：

  1. 在你的 GPU 上跑一遍，看平台从哪里开始。 NVIDIA GPU 从显存和 L2 取数据的单位是 32 字节的 sector，所以模型预测 A10 上的平台从 STRIDE=8 就开始了。对不对？把浏览器里那个模型最后一部分的 grain 改成你测出来的值，看看利用率表。
  2. 把 BLOCK=1024 改成 BLOCK=128，再加上 num_warps=8（写在启动参数里：gather_kernel[grid](..., BLOCK=128, num_warps=8)）。先用模型预测这会让每个线程分到几个元素，再跑一下，STRIDE=1 那一行的带宽会变吗？

这一章的要点

  • CUDA 写一个线程做什么；Triton 写一个 program 处理一块数据做什么。Triton 里的变量是整块的张量，没有线程号。
  • 撞名：Triton 的 BLOCK 是数据块的形状；一个 program 编译成一个 CUDA thread block（Intel 上是 work-group），由 num_warps × 32 个线程执行。两者是独立的参数。
  • 一块数据怎么分给线程，写在 TTGIR 的 layout 里：#ttg.blocked<{sizePerThread, threadsPerWarp, warpsPerCTA, order}>。coalesce pass 按对齐、连续性和 128 位访存宽度选 sizePerThread。规则简单到可以预测，12 种组合的 load 指令条数和真实 PTX 全部吻合。
  • Triton 自动做到了合并访问和向量化（ld.global.v4），前提是它知道你的指针和长度对齐。它按参数能否被 16 整除来特化 kernel：长度是奇数时，同一个 kernel 的 load 指令会从 4 条向量指令变成 16 条标量指令。
  • 归约中线程之间的协作（warp shuffle、shared memory、同步）也由编译器生成。代价是你拿不到线程号、warp 级原语和 shared memory 的控制权。需要它们的时候，去看 IR（第四部分），或者下到 Gluon（第五部分）。
  • 合并访问的代价是实打实的：Max 1100 上，相邻线程跨 16 个元素读数据，有用的带宽从 519 GB/s 掉到 73 GB/s。
