第 23 章 三个后端

这一章想让你带走什么

同一份 Triton kernel，可以编到 NVIDIA、AMD、Intel 三家的 GPU 上。前面二十多章一直在两个后端之间来回对照：A10（NVIDIA）和 Max 1100（Intel），AMD 只在 CE 的链接里露过面。这一章把三个后端并排放：它们怎样接进 Triton，ttgir 之后各走什么路，以及同一个 kernel 换一个后端时，哪些东西会悄悄地变。

读完你会拿到三样东西。一是后端的结构：每个后端就是一对 compiler.py + driver.py，通过 Python 的 entry point 注册，NVIDIA、AMD 在 Triton 的主仓库里，Intel 在一个公开的下游仓库里。二是一张实测的对照表：默认的 num_warps、num_stages、warp 宽度、fp32 tl.dot 的默认精度、tl.dot 的最小形状、支持的 fp8 格式、编译的各段、每段的 pass 数，以及同一个 kernel 在三边编出来的 layout 和 shared memory。三是一张可移植性清单：比如 num_warps=4 在 NVIDIA 上是 128 个线程，在 AMD 上是 256 个，在 Intel 上做矩阵乘时是 64 个；同一个 fp32 的 tl.dot，在 AMD 上默认按 IEEE fp32 算，在另外两家默认是 TF32。

后端是怎么接进来的

triton.backends 这个包在导入时调用 _discover_backends()（python/triton/backends/__init__.py），找出所有后端：

Python
    # Default path: discover via entry points for out-of-tree/downstream plugins.
    for ep in entry_points().select(group="triton.backends"):
        compiler = importlib.import_module(f"{ep.value}.compiler")
        driver = importlib.import_module(f"{ep.value}.driver")
        backends[ep.name] = Backend(_find_concrete_subclasses(compiler, BaseBackend),  # type: ignore
                                    _find_concrete_subclasses(driver, DriverBase))  # type: ignore

每个后端就是两个模块：

  • compiler.py 里一个 BaseBackend 的子类，负责编译：parse_options（默认选项）、add_stages（第 19 章那几段）、get_codegen_implementation（前端生成 TTIR 时要问后端的几件事，比如 tl.dot 的最小形状）、hash（进缓存键）。
  • driver.py 里一个 DriverBase 的子类，负责运行：检测这台机器上有没有这种 GPU、加载编译好的二进制、启动 kernel、提供 do_bench 用的计时器和清缓存的办法。

triton.runtime.driver.active 选的是「检测到有 GPU 的那个」驱动，compile() 再根据它报告的 GPUTarget 用 make_backend 挑出对应的编译器。所以第 15、16 章那种「在 Intel 的机器上编 sm_90」的离线编译能成立：编译器只要一个 GPUTarget，不需要真的有这块 GPU。

三个后端的源码位置：

后端 位置 维护方式
NVIDIA Triton 主仓库的 third_party/nvidia/ 树内（in-tree）
AMD Triton 主仓库的 third_party/amd/ 树内
Intel GitHub 上的 intel/intel-xpu-backend-for-triton，third_party/intel/ 树外（out-of-tree）：一个跟着主仓库同步的下游分支

「树外」意味着 Intel 后端不在 Triton 的主仓库里，而是一个完整的 Triton 分支加上自己的 third_party/intel/。本书用的 triton-xpu 3.9.0 就是从它构建的，所以它同时带着 nvidia、amd、intel 三个后端，这也是本书能在 Max 1100 上离线编 NVIDIA、AMD 代码的原因。主仓库里的公共部分（TTIR、TTGIR 的大部分 pass）三家共用，第 22 章那张表里「各有一份」的 pass，是后端在公共版本之外又写了自己的。

默认值对照

下面的脚本不需要任何 GPU 也能跑（只要装的 Triton 带着这几个后端）：对三个目标各构造一个编译器对象，打印它的默认选项，最后再加上当前机器上的 GPU。

Triton (Python) 
# arch: any
import dataclasses

import triton
import triton.language as tl
from triton.backends import backends
from triton.backends.compiler import GPUTarget, Language
from triton.compiler.compiler import make_backend

print(f"triton {triton.__version__}，装好的后端：{', '.join(backends)}")
current = triton.runtime.driver.active.get_current_target()
targets = [("NVIDIA sm_86", GPUTarget("cuda", 86, 32)), ("NVIDIA sm_90", GPUTarget("cuda", 90, 32)),
           ("AMD gfx942", GPUTarget("hip", "gfx942", 64)), (f"当前的 GPU（{current.backend}）", current)]
for name, target in targets:
    backend = make_backend(target)                 # 不需要这个 GPU：只是构造编译器对象
    opts = backend.parse_options({})               # 不传任何选项时的默认值
    stages = {}
    backend.add_stages(stages, opts, Language.TRITON)
    min_dot = backend.get_codegen_implementation(opts)["min_dot_size"]
    d = dataclasses.asdict(opts)
    print(f"{name}")
    print(f"  warp 宽度 {target.warp_size}，num_warps {d['num_warps']}，num_stages {d['num_stages']}，"
          f"fp32 tl.dot 默认精度 {d['default_dot_input_precision']}")
    print(f"  各段：{' → '.join(stages)}")
    print("  tl.dot 的最小形状 (M, N, K)：" + "，".join(f"{t} {min_dot(t, t)}" for t in (tl.bfloat16, tl.float32, tl.int8)))
    print(f"  支持的 fp8：{', '.join(d['supported_fp8_dtypes'])}")
本地运行：python main.py # 需要 GPU（不限厂商）；环境见附录 A

逐行看差别：

  • warp 宽度：NVIDIA 32，AMD 64（AMD 叫 wavefront）。Intel 这里报告 32，但第 12 章说过，有 tl.dot 的 kernel 用 16（module 属性 "ttg.threads-per-warp" = 16），其它 kernel 用 32。
  • num_stages：NVIDIA 默认 3，AMD 和 Intel 默认 2。同一个参数在三边的含义也不同（第 13 章）：NVIDIA 是 shared memory 的缓冲区份数加一，Intel 是提前几轮发预取。
  • fp32 tl.dot 的默认精度：NVIDIA 和 Intel 默认 TF32，AMD 默认 IEEE fp32。同一个 fp32 的矩阵乘，在 AMD 上算得更准、也更慢（第 7 章讲过 TF32 的精度）。
  • 最后几段：NVIDIA ptx → cubin，AMD amdgcn → hsaco，Intel 只到 spv（机器码在加载时由驱动生成，第 19 章）。
  • tl.dot 的最小形状：前端用 min_dot_size 检查 tl.dot 的形状（第 7 章）。NVIDIA 只限制 K（bf16 至少 16，int8 至少 32），AMD 什么都不限制，Intel 只限制 int8（N ≥ 16，K ≥ 32），其余形状太小时退回普通的乘加（第 7 章）。
  • fp8：列表是「前端接受哪些 fp8 类型」，不是「哪些有硬件支持」。sm_86 不接受 e4m3（fp8e4nv），第 16 章那个报错就是这么来的；Intel 接受 e4m3，但第 16 章看到，它是先转成 fp16 再算的。AMD gfx942 多了 fp8e4b8、fp8e5b16 两种，是 MI300 自己的 fp8 变体（指数偏置不同）。

ttgir 之后：三条路

第 19 章按段数过 row_sum 的 pass，加上 AMD（gfx942，离线编译）：

段 sm_86 gfx942 Max 1100
ttir 10 11 20
ttgir 44 35 32
llir 19 20 19
最后几段 ptx：LLVM 的 NVPTX 后端；cubin：ptxas amdgcn：LLVM 的 AMDGPU 后端；hsaco：用 lld 链接（amd.link_hsaco） spv：LLVM IR 翻译成 SPIR-V（LLVMSPIRVLib，即 SPIRV-LLVM-Translator）

ttgir 段里各家都有自己的 pass。AMD 那 35 个里，有 TritonAMDGPUAccelerateMatmul（选 MFMA 指令）、TritonAMDGPUPipeline（流水）、TritonAMDGPUConvertToBufferOps（把指针访存换成 AMD 的 buffer 指令）、TritonAMDGPUBlockPingpong（两组 warp 交替做计算和访存）、TritonAMDGPUInThreadTranspose 等；Intel 的见第 22 章那张表。

llir 段的结构三家相同：先把 scf 变成 cf、分配 shared memory，再把 tt / ttg / 后端方言的 op 换成 LLVM 方言，最后转成 LLVM IR、跑 LLVM 的优化。区别在于换成什么：NVIDIA 用 NVVM 的 intrinsic（llvm.nvvm.*），AMD 用 ROCDL（llvm.amdgcn.*），Intel 先经过自己的 TritonGEN 方言（ConvertTritonGENToLLVM），换成 Intel GPU 的内建函数和 SPIR-V 的扩展指令。

同一个 kernel，三种 layout

第 20 章那几个小 kernel，在三个后端上编一遍（sm_86、gfx942 离线编译，Max 1100 上实际运行）。下面的链接打开的是 AMD 的版本（CE 上的 triton_amd_370，gfx942），把编译器换成 triton_nvidia_370 就是 NVIDIA：

Triton → TTGIR 🔬 在 Compiler Explorer 看 IR
# CE: triton_amd_370
# IR: ttgir
import torch
import triton
import triton.language as tl


@triton.jit
def copy1d(x_ptr, y_ptr, BLOCK: tl.constexpr):
    offs = tl.program_id(0) * BLOCK + tl.arange(0, BLOCK)
    tl.store(y_ptr + offs, tl.load(x_ptr + offs))


@triton.jit
def tile2d(x_ptr, y_ptr, stride, BM: tl.constexpr, BN: tl.constexpr):
    r = tl.arange(0, BM)[:, None]
    c = tl.arange(0, BN)[None, :]
    tl.store(y_ptr + r * stride + c, tl.load(x_ptr + r * stride + c) * 2)


@triton.jit
def rowmax(x_ptr, y_ptr, stride, BM: tl.constexpr, BN: tl.constexpr):
    r = tl.arange(0, BM)
    c = tl.arange(0, BN)
    x = tl.load(x_ptr + r[:, None] * stride + c[None, :])
    tl.store(y_ptr + r, tl.max(x, axis=1))


@triton.jit
def dot(a_ptr, b_ptr, c_ptr, M: tl.constexpr, N: tl.constexpr, K: tl.constexpr):
    m = tl.arange(0, M)
    n = tl.arange(0, N)
    k = tl.arange(0, K)
    a = tl.load(a_ptr + m[:, None] * K + k[None, :])
    b = tl.load(b_ptr + k[:, None] * N + n[None, :])
    tl.store(c_ptr + m[:, None] * N + n[None, :], tl.dot(a, b))


h = torch.empty(4096, device="cuda", dtype=torch.float16)
t = torch.empty(64, 64, device="cuda", dtype=torch.float16)
c = torch.empty(64, 64, device="cuda", dtype=torch.float32)
copy1d[(4,)](h, h, BLOCK=1024)
tile2d[(1,)](t, t, 64, BM=64, BN=64)
rowmax[(1,)](t, t, 64, BM=64, BN=64)
dot[(1,)](t, t, c, M=64, N=64, K=64)
不需要 GPU：CE 只编译不运行（triton_amd_370）；Device 面板里可切换 source / TTIR / TTGIR / LLVM IR / AMDGCN

结果（3.9.0）：

sm_86 gfx942 Max 1100
warp 宽度（threads-per-warp） 32 64 32；dot 是 16
copy1d（1024 个 fp16，4 个 warp）每个线程几个元素 8（16 字节） 4（8 字节） 8（16 字节）
tile2d（64×64 fp16）的 threadsPerWarp [4, 8] [8, 8] [4, 8]
dot 的累加器 layout nvidia_mma v2，instrShape = [16, 8] amd_mfma v3，instrShape = [32, 32, 8] ttig.dpas，8×16
dot 的 shared memory 16384 字节 8192 字节 0
rowmax 的 shared memory 128 字节 128 字节 128 字节

几个值得注意的地方：

  • copy1d 在 AMD 上每个线程只有 4 个元素。1024 个元素分给 4 × 64 = 256 个线程，每人只能分到 4 个，一次只读 8 字节，而不是 NVIDIA、Intel 上的 16 字节。BLOCK = 1024, num_warps = 4 这组参数是按 32 线程的 warp 挑的，到了 64 线程的 warp 上，同样的块就「不够分」了。要读满 16 字节，AMD 上要么把 BLOCK 翻倍，要么把 num_warps 减半。
  • 矩阵指令的形状差别很大：NVIDIA mma.sync 一条算 16×8，AMD MFMA 一条算 32×32，Intel DPAS 一条算 8×16。tile 太小时，AMD 的一条指令就盖过了整个 tile 的一大块；第 12 章那套「每个线程多少个累加器」的算法，在三边要用不同的数。
  • shared memory：NVIDIA 两个操作数都要经过 shared memory（16 KiB）；AMD 用了 8 KiB，TTGIR 里有两个 shared layout，其中一个是 AMD 自己的 #ttg.amd_rotating_shared，8 KiB 只放得下一个 64×64 的 fp16 操作数，两个操作数怎样复用这块空间我没有细看；Intel 直接用 2D block IO 读进寄存器，一点都不用（第 20 章）。

可移植性清单

把前面二十多章遇到的、和后端有关的差别列在一起。写一个要在多家 GPU 上跑的 kernel 时，这些是要检查的地方：

方面 NVIDIA AMD Intel 本书哪里讲过
warp 宽度，num_warps=4 时的线程数 32，128 个 64，256 个 32 / 16（有 tl.dot 时），128 / 64 个 第 2、12 章
每个线程的累加器元素数 = BM·BN ÷（warp 宽度 · num_warps） 按 32 算 按 64 算 按 16 算 第 12 章
shared memory 上限 A10 每个 block 约 99 KB；H100 约 227 KB MI300 每个 CU 64 KB Max 1100 每个 work-group 128 KiB 第 13 章
num_stages 的含义和默认值 多缓冲 + cp.async / TMA，默认 3 流水，默认 2 提前预取，默认 2 第 13 章
fp32 tl.dot 的默认精度 TF32 IEEE TF32 第 7 章、本章
访存的快速路径 Hopper+ 的 TMA（descriptor） buffer 指令 2D block IO（descriptor，要能证明对齐） 第 8、15 章
后端自己的编译选项 maxnreg 等 waves_per_eu、kpack、matrix_instr_nonkdim 等 grf_mode、reduce_variable_liveness 等 第 17、22 章
最后的机器码在哪里生成 compile() 里（ptxas） compile() 里（lld） 加载时（驱动里的 IGC），另有驱动的缓存 第 19 章

由此得出几条实用的规则：

  • 不要把 num_warps、BLOCK_* 写死成一组数。它们的「合适值」由 warp 宽度、寄存器数、shared memory 上限共同决定，每家都不一样。第 14 章的 autotune、或者像 minillm 那样按 DEVICE.type 分开配置（attention.launch_config、lowp._config），是最简单的办法。
  • 后端专有的选项只传给对应的后端。把 reduce_variable_liveness 传给 NVIDIA 后端，会报 KeyError: 'Keyword argument reduce_variable_liveness was specified but unrecognised'。minillm 只在 DEVICE.type == "xpu" 时加这个选项。
  • 数值结果要在每个后端上分别验证。TF32 和 IEEE 的默认值不同，fp8 是硬件支持还是软件模拟也不同（第 16 章），同一个测试的容差可能要按后端调。
  • 性能结论不能跨后端照搬。本书里「一个后端上有用、另一个上没用甚至有害」的例子：软件流水的级数（第 13 章）、persistent kernel（第 15 章）、对角线单独一个循环（第 17 章）、ReduceVariableLiveness（第 17、22 章）。

动手

  1. 在 A10 上跑本章的默认值脚本。 「当前的 GPU」那一组和 sm_86 一样吗？它的 warp_size 是 32，get_current_target() 返回的 arch 是什么？
  2. 在 CE 上把第 4 章的 add kernel 编到 AMD。 用 BLOCK = 1024, num_warps = 4，看 #blocked 的 sizePerThread；再把 num_warps 改成 2，它变成几？对照本章的表解释。
  3. 写一个「三家通用」的配置函数。 仿照 attention.launch_config，给第 6 章的 softmax 写一个按后端返回 num_warps 的函数，规则是「每个线程 16 字节」。用本章脚本里的 target.warp_size 和元素大小算出来，不要写死 32。

这一章的要点

  • 后端 = compiler.py（BaseBackend：默认选项、各段、前端要的信息、缓存哈希）+ driver.py（DriverBase：检测、加载、启动、计时），通过 triton.backends 这个 entry point 组注册（python/triton/backends/__init__.py）。NVIDIA、AMD 在主仓库，Intel 是公开的下游分支 intel-xpu-backend-for-triton。编译器只需要一个 GPUTarget，所以能离线编别家的 GPU。
  • 默认值（3.9.0）：warp 宽度 32 / 64 / 32（Intel 的 dot kernel 用 16）；num_stages 3 / 2 / 2；fp32 tl.dot 默认 TF32 / IEEE / TF32；最后几段 ptx → cubin / amdgcn → hsaco / spv；tl.dot 的最小形状 NVIDIA 限 K、AMD 不限、Intel 只限 int8；fp8 列表是「接受」不是「硬件支持」。
  • 同一个 kernel：copy1d（1024 个 fp16，4 个 warp）在 AMD 上每个线程只有 8 字节，因为 64 线程的 warp 让块「不够分」；矩阵指令 16×8 / 32×32 / 8×16；矩阵乘的 shared memory 16 KiB / 8 KiB / 0。
  • 可移植的写法：块大小和 num_warps 按后端配置或交给 autotune；后端专有选项只传给对应后端；数值和性能结论都要在每个后端上分别验证。

第四部分到此结束：从 MLIR 的基本概念，到编译流水线、layout、关键 pass，再到三个后端。下一部分往 Triton 的上一层和下一层看：Gluon 把 layout 等决定交还给你，Helion 在 Triton 之上又加了一层自动化。
