第 13 章 GEMM 优化（二）：软件流水

这一章想让你带走什么

GEMM 的循环每一轮都要先把 A、B 的一段从显存搬进来，再交给矩阵单元算。如果「搬」和「算」一前一后地做，矩阵单元有一大半时间在等数据。软件流水（software pipelining）就是让它们重叠：算这一段的同时，后面几段的数据已经在路上了。Triton 里控制它的只有一个参数：num_stages。

读完你会拿到三样东西。一是 num_stages 在两种硬件上到底变成了什么：在 NVIDIA 上，它是 num_stages − 1 份 shared memory 缓冲区加上异步拷贝；在 Intel 上，它是「提前几轮发出预取」，shared memory 一个字节也不用。两者都有真实的 IR 为证。二是 stage 为什么不是越多越好：NVIDIA 上每多一级就多 16 KiB 的 shared memory，一个 SM 上能同时驻留的 program 随之变少，你会在浏览器里看到 4 级比 5 级更快的情形；Intel 上，实测 2 级最快，再加反而变慢。三是超出预算时的真实报错：OutOfResources: out of resource: shared memory。

不流水的时候

先看最朴素的执行方式：每一轮读一段 A、B，等数据到齐了再算，算完再读下一段。读一段要等几百个周期（显存延迟，第 2 章），算一段只要几十个。于是时间线是这样的：

图 13-1　软件流水的时间线（读一段的时间按算一段的两倍画）。灰色是从显存读一段 A、B，蓝色是用矩阵单元算这一段。上面不流水：矩阵单元三分之二的时间在等。下面 num_stages = 3：开始算第 i 段的同时，就发出第 i+2 段的读取，两段读取总在路上，矩阵单元几乎不停

流水的思想很简单：开始算第 i 段的时候，就把第 i + (S−1) 段的读取发出去，S 是 stage 的级数。只要同时在路上的读取足够多，矩阵单元每算完一段，下一段已经到了。这和第 2 章「warp 越多越能藏延迟」是同一个道理，只是这里在一个 program 内部做。

NVIDIA：shared memory 缓冲区 + 异步拷贝

在 NVIDIA 上，「同时在路上的读取」需要地方放：数据先异步地搬进 shared memory，等用的时候再读进寄存器。把 minillm 的指针版 GEMM（fp16，128×128×32，8 个 warp）用 3.9.0 编到 sm_86，num_stages 从 1 到 6，看编译出来的东西（附录 A 第 8 节的离线编译，不需要 GPU）：

num_stages shared memory 缓冲区份数 TTGIR 里的 async_copy_global_to_local PTX 里的 cp.async
1 32 KiB 0 0 0
2 32 KiB 1 4 8
3 32 KiB 2 6 12
4 48 KiB 3 8 16
5 64 KiB 4 10 20
6 80 KiB 5 12 24
  • 缓冲区份数 = num_stages − 1，每份放一段 A 和一段 B：(128×32 + 32×128) × 2 字节 = 16 KiB。第 7 章看到的 ttg.local_alloc : () -> !ttg.memdesc<2x128x32xf16, ...> 里的那个 2，就是 num_stages = 3 的两份缓冲区。
  • cp.async 是 Ampere 的异步拷贝指令：线程发出拷贝请求以后不必等数据到，可以继续往下执行，数据由硬件直接搬进 shared memory。TTGIR 里对应的是 ttg.async_copy_global_to_local、ttg.async_commit_group、ttg.async_wait。负责这一变换的是 Triton 的 pipeliner pass（lib/Dialect/TritonGPU/Transforms/Pipeliner/ 目录，第 22 章细讲）。
  • num_stages 为 1 到 3 时 shared memory 都是 32 KiB，大于缓冲区本身的用量。我推测是 kernel 结尾那个 convert_layout（第 7 章）也要经过 shared memory，它需要的暂存空间（128×128 个 fp16 正好是 32 KiB）比两份缓冲区还大，编译器按两者中较大的那个分配。

NVIDIA 后端 num_stages 的默认值是 3（CUDAOptions 里的 num_stages: int = 3）。

stage 为什么不是越多越好

每多一级就多 16 KiB 的 shared memory。shared memory 是每个 SM 上所有 program 共用的（第 2 章），一个 program 用得越多，一个 SM 上能同时驻留的 program 就越少，而同时驻留的 program，本身也是在互相藏延迟。

下面的模型把两件事放在一起算：一个 program 内部，stage 越多，流水越满；但 A10 每个 SM 只有 100 KB 的 shared memory，stage 越多，能放下的 program 越少。只用标准库，直接点运行：

Python 
# 软件流水：S 级 stage 时，一个 program 沿 K 循环的时间线。只用标准库。
#
# 每一轮：先把这一段 A、B 从显存搬进来（延迟 LOAD 个单位，不占计算单元），再用矩阵单元算（COMPUTE 个单位）。
# 有 S 级 stage，就有 S-1 份缓冲区：最多可以提前 S-1 轮发出读取，一边算这一轮，一边等后面几轮的数据。
# 一段数据从缓冲区读进寄存器、开始计算的那一刻，这份缓冲区就可以给后面的读取用了。
# S = 1 表示不流水：读完才算，算完才读下一段。


def run(stages, n_iter, load, compute):
    ahead = max(stages - 1, 1)            # 最多同时在路上的读取（S=1 时也得有 1 份缓冲区）
    compute_start = [0.0] * n_iter
    compute_end = 0.0
    for i in range(n_iter):
        if stages == 1:
            issue = compute_end           # 不流水：上一段算完才读这一段
        else:
            # 缓冲区在「开始计算」时就空出来了（数据已经读进寄存器），可以立刻发出下一次读取
            issue = 0.0 if i < ahead else compute_start[i - ahead]
        arrive = issue + load
        compute_start[i] = max(arrive, compute_end)          # 数据到了、上一段也算完了，才能算
        compute_end = compute_start[i] + compute
    return compute_end


N_ITER = 128                              # 4096 / BLOCK_K(32) 轮
STAGE_KB = 16                             # 每份缓冲区：128×32 + 32×128 个 fp16 = 16 KiB（第 13 章的 sm_86 数据）
SMEM_PER_SM_KB = 100                      # A10（sm_86）每个 SM 的 shared memory
for load, compute in ((8, 1), (4, 1)):
    print(f"读一段要 {load} 个单位、算一段要 {compute} 个单位：")
    print("  stages   单个 program 的利用率   shared/program   每个 SM 能放几个   合计（粗估）")
    for s in range(1, 8):
        t = run(s, N_ITER, load, compute)
        smem = max(s - 1, 1) * STAGE_KB
        util, fit = N_ITER * compute / t, SMEM_PER_SM_KB // smem
        # 同一个 SM 上的几个 program 轮流用矩阵单元：合计 ≈ min(1, 单个的利用率 × 个数)
        print(f"  {s:6}   {util:19.0%}   {smem:11} KiB   {fit:14}   {min(1.0, util * fit):9.0%}")
    print()

第一组是读延迟比较长的情形：单个 program 的利用率随 stage 一路上升，但到了 5 级，每个 program 要 64 KiB，一个 SM 只放得下一个，「合计」反而从 74% 掉到了 49%。第二组读得快一些，3、4 级就已经能把矩阵单元喂饱，再加 stage 毫无收益，只是白白占了 shared memory。最好的 stage 数取决于读延迟和计算时间的比例，也取决于 shared memory 和寄存器的预算，这正是第 14 章要交给 autotune 去搜索的东西之一。这个模型只算了 shared memory 对驻留数的限制，真实 GPU 上寄存器也会限制它（第 12 章）。

超出预算

shared memory 有硬性的上限。Triton 在加载 kernel 时检查它（python/triton/compiler/compiler.py），超出就抛 OutOfResources。在 Max 1100 上用指针版 GEMM 配一个很大的 tile（256×256×256），每个 program 需要 256 KiB，上限是 128 KiB：

运行结果（Max 1100）：

OutOfResources out of resource: shared memory, Required: 262144, Hardware limit: 131072. Reducing block sizes or `num_stages` may help.

报错直接给出了需要多少、上限多少，以及该调哪两个参数。A10（sm_86）每个 block 能用的 shared memory 上限是 99 KB 左右（Triton 用的是驱动报告的 MAX_SHARED_MEMORY_PER_BLOCK_OPTIN）。按上面那张表推算，128×128×32 的 tile 在 A10 上最多能开到 num_stages = 7（96 KiB），8 级就会报这个错。本书还没在 A10 上验证这个预测。

Intel：提前几轮发出预取

在 Max 1100 上，第 8 章的 descriptor GEMM 根本不用 shared memory：数据直接从显存读进寄存器。那 num_stages 还有什么用？扫一遍看看：

Triton (Python) 
# arch: sm80 xpu
import torch
import triton

from minillm import DEVICE
from minillm.kernels.matmul import _matmul_grouped_kernel

M = N = K = 4096
a = torch.randn(M, K, device=DEVICE, dtype=torch.bfloat16)
b = torch.randn(K, N, device=DEVICE, dtype=torch.bfloat16)
c = torch.empty(M, N, device=DEVICE, dtype=torch.bfloat16)
grid = (triton.cdiv(M, 256) * triton.cdiv(N, 256),)
print(f"{getattr(torch, DEVICE.type).get_device_name()}，triton {triton.__version__}，bf16 {M}³，256×256×32，32 个 warp")
for ns in (1, 2, 3, 4, 5, 6):
    run = lambda: _matmul_grouped_kernel[grid](a, b, c, M, N, K, a.stride(0), b.stride(0), c.stride(0),
                                               BLOCK_M=256, BLOCK_N=256, BLOCK_K=32, GROUP_M=8,
                                               num_warps=32, num_stages=ns)
    k = run()
    torch.testing.assert_close(c, a @ b, atol=0.5, rtol=0.05)
    ms = triton.testing.do_bench(run)
    ttgir = k.asm["ttgir"]
    print(f"  num_stages={ns}  descriptor_prefetch {ttgir.count('descriptor_prefetch'):2} 条  "
          f"async_copy {ttgir.count('async_copy_global_to_local'):2} 条  shared={k.metadata.shared:6}  "
          f"{2 * M * N * K / ms / 1e9:6.1f} TFLOP/s")
本地运行：python main.py # 需要 NVIDIA sm_80+ 或 Intel GPU（XPU）；环境见附录 A

时间线和图 13-1 下半部分一模一样，只是「放数据的地方」不同：进入循环之前，先预取第 0 段（k = 0）和第 1 段（k = 32）；循环里每一轮，先对 k + 64（两轮之后的那一段）发出预取，再读这一轮的第 k 段。预取总是提前 num_stages − 1 轮。预取指令只是告诉硬件「把这块数据先拉进缓存」，不占用寄存器，也不需要 shared memory；等到真正 descriptor_load 的时候，数据多半已经在缓存里了。

性能上，2 级最快（150.2 TFLOP/s），这正是 Intel 后端的默认值（第 4 章：Intel 默认 num_stages = 2，NVIDIA 默认 3）。不预取时掉到 122.7；预取得更深反而越来越慢，6 级时 138.0。预取太早，数据进了缓存却要等好几轮才用，中间可能被别的数据挤出去，还白白占了访存带宽。和 NVIDIA 一样，stage 不是越多越好，只是在 Intel 上，限制它的不是 shared memory 预算，而是缓存的容量和带宽。

动手

  1. 在 A10 上扫 num_stages。 用本章的指针版 GEMM（128×128×32，8 个 warp），num_stages 从 1 扫到 8。哪一级最快？第 8 级是不是报了 OutOfResources？报错里的 Hardware limit 是多少？
  2. 在模型里找最优的 stage 数。 把浏览器里模型的 load 改成 16（更慢的显存），最优的 stage 数变成几？再把 STAGE_KB 改成 32（相当于 BLOCK_K = 64），最优值又怎么变？
  3. 看一看 Intel 的指针版 GEMM 怎么流水。 用 kernel.asm["ttgir"] 看第 7 章的指针版 GEMM 在 Max 1100 上 num_stages = 2 和 num_stages = 4 时的 TTGIR：它用的是预取、async_copy，还是别的？shared memory 的用量随 stage 变化吗？

这一章的要点

  • 软件流水：开始算第 i 段时，就发出第 i + (S−1) 段的读取，让「搬」和「算」重叠。Triton 里只有一个参数：num_stages（S）。
  • NVIDIA：num_stages − 1 份 shared memory 缓冲区，配合 Ampere 的异步拷贝 cp.async（TTGIR 里是 ttg.async_copy_global_to_local / async_wait），由 pipeliner pass 生成。128×128×32 的 fp16 GEMM 每多一级多 16 KiB。默认 num_stages = 3。
  • stage 不是越多越好：shared memory 是 SM 上所有 program 共用的，一个 program 用得越多，能同时驻留的越少。浏览器模型里，4 级（合计 74%）比 5 级（49%）还快。超出上限时，加载 kernel 会抛 OutOfResources: out of resource: shared memory, Required: …, Hardware limit: …。
  • Intel：num_stages 变成了「提前 num_stages − 1 轮发出 ttig.descriptor_prefetch」，shared memory 一个字节也不用。Max 1100 上 2 级最快（默认值），不预取慢 18%，预取太深也会变慢。
  • 同一个参数，在两个后端上是两套完全不同的机制。调参之前先看 IR，知道它到底变成了什么。

minillm 进度：本章没有修改 minillm 的代码：Intel 上 matmul_grouped 用的默认 num_stages = 2 已经是最快的。测试仍为 138 个。
