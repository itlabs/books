第 10 章 verifier 与不变式：把「不该出现的 IR」挡在门外

这一章想让你带走什么

第 8、9 章结尾我们攒下了三个洞：pix.transpose 可以把 4×8「转置」成 4×8；pix.kernel 的权重形状可以和 !pix.kernel<R x C> 说的不一致；pix.pipeline 可以声明有结果却什么都不 yield。三段荒唐的 IR 都干干净净地通过了验证——因为没人声明过这些规则。这一章把它们全堵上。

但比"怎么写 verifier"更重要的是两条路的选择：手写 verify()，还是去实现一个接口让通用机制替你查？两条我们都走一遍——pipeline 那个洞，我们只写了 两个接口方法、二十来行，检查就白拿到了，报错和第 2 章 scf.if 那条除了 op 名一个字都不差。

另外三件实用的事：验证的执行顺序（以及由此而来的一条硬规矩：verify() 里不能碰嵌套 op）、类型参数怎么验（它发生在还没有 op 的时候，所以报错方式不同）、以及怎么给"报错行为"写测试。

先看清验证是怎么跑的

打开 mlir/lib/IR/Verifier.cpp，整个验证器是一次树的遍历，每个 op 有两个钩子——进门时和出门时：

图 10-1　验证的两个钩子。选错钩子的后果很实际：在 `verify()` 里遍历 region 内容，遇到畸形 IR 时可能直接崩溃，而且崩在一个和真实错误毫无关系的地方

两个 ODS 开关对应这两个钩子：

开关 生成的方法 什么时候跑 用它查什么
let hasVerifier = 1; LogicalResult verify() 进门（子 op 还没验） 只涉及本 op 自己：操作数/结果类型的关系、属性的取值范围
let hasRegionVerifier = 1; LogicalResult verifyRegions() 出门（子 op 都验完了） 需要看 region 内部：terminator 交出什么、region 里有没有必须存在的 op

「进门时子 op 还没验」这句话的分量，跑一遍就清楚了。下面这段照 Verifier.cpp 的结构走同一棵树，让 pix.pipeline 在两个钩子里各偷看同一个子 op 一次：

Python 
# 照 mlir/lib/IR/Verifier.cpp 的结构走一遍：进门 → 递归 → 出门。
# 重点看"在 verify() 里碰嵌套 op"为什么危险。

class Op:
    def __init__(self, name, kids=(), payload=None):
        self.name, self.kids, self.payload = name, list(kids), payload
        self.verified = False          # 这个 op 自己验过了吗

    # ① 进门：只许看自己。此时 self.kids 里的 op 都还没验。
    def verify(self):
        if self.name == "pix.pipeline":
            kid = self.kids[-1]
            print(f"    [verify] pix.pipeline 偷看了子 op {kid.name}："
                  f"verified={kid.verified}，payload={kid.payload!r}")
            if kid.payload is None:                  # 畸形数据，真实 C++ 里这就是崩点
                print("    [verify] ← 它的 payload 还是 None。真实代码在这里解引用就崩了，"
                      "而且崩在和真正错误无关的地方")
        return None

    # ③ 出门：子 op 全验完了，这时候看 region 是安全的
    def verifyRegions(self):
        if self.name == "pix.pipeline":
            kid = self.kids[-1]
            print(f"    [verifyRegions] 同一个子 op：verified={kid.verified}，"
                  f"payload={kid.payload!r} —— 已经可信")
            if kid.payload != 1:
                return "pix.pipeline 交出的值个数不对"
        return None

def run_verifier(op, depth=0):
    pad = "  " * depth
    print(f"{pad}① 进门 {op.name}")
    if (err := op.verify()):
        return err
    for kid in op.kids:                              # ② 递归
        if (err := run_verifier(kid, depth + 1)):
            return err
    op.payload = op.payload if op.payload is not None else 1   # 假装"验证顺带补全了信息"
    op.verified = True
    print(f"{pad}③ 出门 {op.name}")
    return op.verifyRegions()

tree = Op("builtin.module", [
    Op("func.func", [
        Op("pix.pipeline", [Op("pix.add", payload=1), Op("pix.yield")])   # yield 的 payload 缺
    ])
])

err = run_verifier(tree)
print("\n验证结果：", err or "通过")
print("注意两处 [verify] / [verifyRegions] 看到的是同一个 pix.yield，"
      "但可信程度完全不同 —— 这就是两个钩子存在的全部理由。")

运行结果：

① 进门 builtin.module
  ① 进门 func.func
    ① 进门 pix.pipeline
    [verify] pix.pipeline 偷看了子 op pix.yield：verified=False，payload=None
    [verify] ← 它的 payload 还是 None。真实代码在这里解引用就崩了，而且崩在和真正错误无关的地方
      ① 进门 pix.add
      ③ 出门 pix.add
      ① 进门 pix.yield
      ③ 出门 pix.yield
    ③ 出门 pix.pipeline
    [verifyRegions] 同一个子 op：verified=True，payload=1 —— 已经可信
  ③ 出门 func.func
③ 出门 builtin.module

验证结果： 通过
注意两处 [verify] / [verifyRegions] 看到的是同一个 pix.yield，但可信程度完全不同 —— 这就是两个钩子存在的全部理由。

同一个 pix.yield：进门时 verified=False、数据还是 None；出门时 verified=True、数据齐了。真实的 C++ 在进门那一刻解引用这种半成品，就是一次崩溃——而且崩的位置和真正的错误毫无关系，这是这类 bug 最难查的地方。把模拟器里 verify() 那段挪到 verifyRegions() 里，两个钩子的差别立刻消失，这也正是选对钩子的全部意义。

补洞一：手写 verify()（pix.transpose）

ODS 里开个开关：

TableGen / ODS
def Pix_TransposeOp : Pix_Op<"transpose", [Pure]> {
  // …
  let hasVerifier = 1;
}
生成代码：mlir-tblgen -gen-op-decls -I $(llvm-config --includedir) PixOps.td

然后在 lib/Pix/PixOps.cpp 里实现。注意三件事：走到这里时 ODS 的检查已经过了（不用再判断"是不是 F32Tensor"）、动态维要放过、报错信息要给出足够的上下文：

C++
LogicalResult TransposeOp::verify() {
  auto inTy = cast<RankedTensorType>(getImage().getType());
  auto outTy = cast<RankedTensorType>(getResult().getType());

  if (inTy.getRank() != 2 || outTy.getRank() != 2)
    return emitOpError("只支持二维图像，收到 ") << inTy << " 和 " << outTy;

  ArrayRef<int64_t> in = inTy.getShape(), out = outTy.getShape();
  // 动态维（?）无从比较，放过；静态维必须逐对交换
  for (auto [i, o] : {std::pair{in[0], out[1]}, std::pair{in[1], out[0]}}) {
    if (!ShapedType::isDynamic(i) && !ShapedType::isDynamic(o) && i != o)
      return emitOpError("结果形状必须是输入形状的逆序：输入 ")
             << inTy << "，结果应为 " << out[1] << "x" << out[0]
             << "，实际是 " << outTy;
  }
  return success();
}

现在那段荒唐的 IR 被拦住了（真实报错）：

error: 'pix.transpose' op 结果形状必须是输入形状的逆序：输入 'tensor<4x8xf32>'，结果应为 8x4，实际是 'tensor<4x8xf32>'
  %t = pix.transpose %a : tensor<4x8xf32> to tensor<4x8xf32>
       ^
note: see current operation: %0 = "pix.transpose"(%arg0) : (tensor<4x8xf32>) -> tensor<4x8xf32>
诊断的三个习惯

一，用 emitOpError() 而不是 emitError()：前者自动带上 op 名（'pix.transpose' op …）和位置。

二，别在消息里重复 op 名：emitOpError("pix.transpose 的形状不对") 会打印成 'pix.transpose' op pix.transpose 的形状不对。

三，把"实际值"和"期望值"都写进去。<< 可以直接接 Type、Value、Attribute、整数——这是第 4 章那些类型能被打印的好处。需要指向另一处代码时，用 emitOpError(…).attachNote(otherOp->getLoc()) << "…"，诊断里会多一条 note——第 2 章那个支配关系报错就是这么做的。

补洞二：属性与类型的一致性（pix.kernel）

权重存在属性里、尺寸存在类型里，两者必须一致：

C++
LogicalResult KernelOp::verify() {
  auto kernelTy = getResult().getType();          // !pix.kernel<R x C>
  auto weightsTy = dyn_cast<ShapedType>(getWeights().getType());
  if (!weightsTy || weightsTy.getRank() != 2)
    return emitOpError("权重必须是二维的 elements 属性");

  if (weightsTy.getDimSize(0) != kernelTy.getRows() ||
      weightsTy.getDimSize(1) != kernelTy.getCols())
    return emitOpError("权重形状与卷积核类型不一致：权重是 ")
           << weightsTy.getDimSize(0) << "x" << weightsTy.getDimSize(1)
           << "，而类型说的是 " << kernelTy.getRows() << "x" << kernelTy.getCols();
  return success();
}

真实报错：

error: 'pix.kernel' op 权重形状与卷积核类型不一致：权重是 3x3，而类型说的是 5x5

这类"两处信息必须一致"的检查在真实方言里非常多（属性 vs 类型、静态形状 vs 动态尺寸操作数、编译期常量 vs 运行时值）。它们没法靠声明表达，因为涉及两个不同来源的数据。

补洞三：类型参数的验证（!pix.kernel<R x C>）

卷积核的边长应该是正奇数。这条规则属于类型自己，与任何 op 无关——所以它不能写在 op 的 verifier 里（否则一个只出现在函数签名里的坏类型就漏掉了）。

ODS 侧开 genVerifyDecl：

TableGen / ODS
def Pix_KernelType : Pix_Type<"Kernel", "kernel"> {
  let parameters = (ins "int64_t":$rows, "int64_t":$cols);
  let genVerifyDecl = 1;
}
生成代码：mlir-tblgen -gen-op-decls -I $(llvm-config --includedir) PixOps.td

实现的签名和 op 的 verifier不一样，值得看清：

C++
// 第一个参数是"怎么报错"的回调。类型验证发生在还没有 op 的时候
// （类型可以独立存在），所以不能用 emitOpError，只能用框架给的这个发射器。
LogicalResult KernelType::verify(function_ref<InFlightDiagnostic()> emitError,
                                 int64_t rows, int64_t cols) {
  if (rows <= 0 || cols <= 0)
    return emitError() << "卷积核的行列必须是正数，收到 " << rows << "x" << cols;
  if (rows % 2 == 0 || cols % 2 == 0)
    return emitError() << "卷积核的行列必须是奇数（才有明确的中心点），收到 "
                       << rows << "x" << cols;
  return success();
}

效果是连函数签名里的坏类型都拦得住（真实报错，注意插入符直接指向类型本身）：

error: 卷积核的行列必须是奇数（才有明确的中心点），收到 2x4
func.func @f(%k: !pix.kernel<2 x 4>) {
                            ^
类型验证发生在"构造类型"的那一刻

不是在某个 op 上，而是在 KernelType::get(ctx, 2, 4)（或解析到这个类型文本）时。这与第 4 章"类型是唯一化的不可变值"是一致的：既然类型可以脱离 op 独立存在，它的不变式就必须在构造时守住——**坏类型根本不该被造出来**。

补洞四：不写 verifier，改为实现接口（pix.pipeline）

最后一个洞：pipeline 声明返回一张图，body 却什么都不 yield。

按第 8 章的分析，SingleBlockImplicitTerminator 只管"有没有终结符"，不管"终结符交出的值与 op 的结果对不对齐"。现在有两条路：

路一：手写 verifyRegions()。 大约十几行：取出 body 的 terminator、比较操作数个数与类型、逐个报错。直观，但这套逻辑每个带 region 的 op 都要重写一遍。

路二：声明自己实现 RegionBranchOpInterface，让通用机制来查。 第 5 章讲过，"通用变换能为你做什么"取决于你声明了什么——验证也一样。

我们走路二。ODS 里加一行：

TableGen / ODS
def Pix_PipelineOp : Pix_Op<"pipeline", [
    SingleBlockImplicitTerminator<"YieldOp">,
    RecursiveMemoryEffects,
    DeclareOpInterfaceMethods<RegionBranchOpInterface,
                              ["getSuccessorInputs"]>]> {
生成代码：mlir-tblgen -gen-op-decls -I $(llvm-config --includedir) PixOps.td

C++ 里实现两个方法。第一个描述控制流怎么在"本 op"与"它的 region"之间流动：

C++
void PipelineOp::getSuccessorRegions(RegionBranchPoint point,
                                     SmallVectorImpl<RegionSuccessor> &regions) {
  // 从 pipeline 自己出发 → 进入 body
  if (point.isParent()) {
    regions.push_back(RegionSuccessor(&getBody()));
    return;
  }
  // 从 body 出来 → 回到 pipeline
  regions.push_back(RegionSuccessor(getOperation()));
}

第二个说清每条边的落点接收哪些值。这一步不能省：RegionSuccessor 只记"落在哪"（一个 region，还是本 op），它不带值，所以框架得另外问你一次：

C++
ValueRange PipelineOp::getSuccessorInputs(RegionSuccessor successor) {
  // 落在本 op 上 → 接收方是本 op 的结果，这正是 yield 要对齐的目标
  if (successor.isOperation())
    return getOperation()->getResults();
  // 落在 body 上 → body 没有块参数
  return {};
}

getSuccessorInputs 在接口里带默认实现（返回空），所以 ODS 那行必须把它显式列进覆盖名单，否则你写的版本不会被调用——框架会以为这条边上一个值都不接收，于是合法的 pix.yield %c 反而被判成错。

二十行代码，换来的报错是这样的（真实输出）：

error: 'pix.pipeline' op along control flow edge from Operation pix.yield to Operation pix.pipeline: region branch point has 0 operands, but region successor needs 1 inputs
  %out = pix.pipeline : tensor<4x4xf32> {
         ^
note: region branch point

对比第 2 章我们在 scf.if 上看到的那条：

error: 'scf.if' op along control flow edge from Operation scf.yield to Operation scf.if: region branch point has 0 operands, but region successor needs 1 inputs

把两条放在一起看：除了 op 名，一个字都不差。你的 op 现在和内建 op 走的是同一条代码路径，报错由同一个函数打印（mlir/lib/Interfaces/ControlFlowInterfaces.cpp 里那段边检查）。而且这个接口的回报远不止验证：第 19 章的数据流分析、第 13 章某些 pass 的正确性，都建立在它之上。

接口方法的签名会随版本变

这个接口本身就是活例子。早先的 RegionSuccessor 是连值一起带的，构造时就把"落点接收哪些值"塞进去（RegionSuccessor(Operation::result_range) 之类）；基线 23.1 把这件事拆开了——RegionSuccessor 只记落点，值改由单独的 getSuccessorInputs 回答。照老写法只实现 getSuccessorRegions 的代码在 23.1 上不会编译失败，而是静悄悄地行为不对：默认实现说"这条边不接收任何值"，于是空 pipeline 不报错了，合法的 yield 倒被判错——这种失败最难查。实现任何接口前，先打开你手上那份头文件，把方法列表和默认实现一起看过；带默认实现的方法尤其要留意，漏了它编译器不会提醒你。附录 A 第 0 节那条"以你手上的版本为准"就是为它准备的。

该写 verifier 还是该实现接口？

一张判断表，是这一章最该带走的东西：

情况 怎么做 例子
类型/形状之间的固定关系 ODS 约束（AllTypesMatch、TypesMatchWith）或 trait pix.scale 的 image = result
只涉及本 op 的自定义关系 手写 verify() pix.transpose 的形状逆序
属性与类型两处信息一致 手写 verify() pix.kernel 的权重形状
类型参数本身的不变式 类型的 genVerifyDecl + verify() 卷积核边长为正奇数
需要看 region 内部 hasRegionVerifier + verifyRegions() region 里必须含某个 op
region 之间的控制流与传值 实现 RegionBranchOpInterface pipeline 的 yield 对齐
想要通用变换也能用同一信息 实现接口，别写 verifier 循环类 op 实现 LoopLikeOpInterface

判断原则很简单：如果这条信息除了"验证"之外还能被别的地方用到，就把它做成接口；如果它纯粹是本 op 的私事，就写 verifier。 接口的成本高一点（要读文档、实现方法），但它是可复用的声明，而 verifier 只是一次性的检查。

给报错行为写测试

verifier 写完不测，等于没写——它最容易在后续重构里悄悄失效。测试写法就是第 3 章那套 --split-input-file --verify-diagnostics：

MLIR（pix 方言） 
// RUN: pix-opt %s --split-input-file --verify-diagnostics

func.func @transpose_not_reversed(%a: tensor<4x8xf32>) -> tensor<4x8xf32> {
  // expected-error @+1 {{结果形状必须是输入形状的逆序}}
  %t = pix.transpose %a : tensor<4x8xf32> to tensor<4x8xf32>
  return %t : tensor<4x8xf32>
}

// -----

func.func @pipeline_yields_nothing() -> tensor<4x4xf32> {
  // 这条检查不是手写的：实现了 RegionBranchOpInterface 之后由通用机制给出。
  // 通用机制除了报错还附一条 note 指出"边的起点在哪"，--verify-diagnostics
  // 要求 note 也得预期，漏了它测试同样算失败。
  // expected-error @+2 {{region branch point has 0 operands, but region successor needs 1 inputs}}
  // expected-note @+1 {{region branch point}}
  %out = pix.pipeline : tensor<4x4xf32> {
  }
  return %out : tensor<4x4xf32>
}

// -----

// expected-error @+1 {{卷积核的行列必须是奇数}}
func.func @even_kernel(%k: !pix.kernel<2 x 4>) {
  return
}
本地运行：pix-opt --split-input-file --verify-diagnostics input.mlir

三个写法要点：

  • @+1 表示"错误发生在下一行"。也可以写 @-1（上一行）、@+2，或者不带偏移（本行）。
  • {{…}} 里是正则，不必写全文。只匹配最稳定的那一段——把整句话抄进去，以后改个措辞测试就红了。
  • // ----- 分隔的每一段独立解析（配 --split-input-file）。类型验证那种"错误发生在函数签名上"的情况，必须这样隔开，否则整段都过不了解析。
别忘了测"合法的也得过"

verifier 写紧了比写松了更难发现——一段本该合法的 IR 被拒绝，往往要等到很久以后有人写出那种 IR 才暴露。我们的测试文件最后一段专门放一堆合法的 op（正确的转置、匹配的卷积核、正常 yield 的 pipeline），确保新加的检查没有误伤。

测试文件的最后一段就是这个"合法也得过"的对照组，它同时也是本章成果的一次总检阅—— 四条新不变式全部生效，而这些写法一个都不能被误伤：

MLIR（pix 方言） 
// RUN: pix-opt %s
func.func @all_legal(%a: tensor<4x8xf32>, %img: tensor<8x8xf32>) -> tensor<8x4xf32> {
  %t = pix.transpose %a : tensor<4x8xf32> to tensor<8x4xf32>       // 形状确实逆序
  %k = pix.kernel dense<1.0> : tensor<3x3xf32> -> !pix.kernel<3 x 3>  // 权重与类型一致，边长为奇数
  %c = pix.convolve %img, %k : !pix.kernel<3 x 3>, tensor<8x8xf32>
  %p = pix.pipeline : tensor<8x8xf32> {
    pix.yield %c : tensor<8x8xf32>                                  // yield 与结果对齐
  }
  return %t : tensor<8x4xf32>
}

动手

改一改：

  1. 把 TransposeOp::verify() 里"动态维放过"的逻辑删掉（直接比较 in[0] != out[1]），然后跑 pix.transpose %a : tensor<?x8xf32> to tensor<8x?xf32>。会误报吗？ShapedType::isDynamic 这个判断在真实方言里到处都要写，忘了它就是"verifier 写太紧"的典型。
  2. 把 pix.kernel 的 verifier 挪到 verifyRegions() 里（把 ODS 开关换成 hasRegionVerifier）。还能正常工作吗？想一想：这个 op 根本没有 region，那个钩子会被调用吗？
  3. 在 PipelineOp 上手写一个 verifyRegions()，做与接口相同的检查（取 terminator、比较个数与类型）。写完对比一下：你的报错信息和通用机制给的哪个更有用？多少行？
  4. 给 !pix.kernel 加一条"边长不超过 15"的限制，然后写一个 expected-error 测试。注意报错位置——它指向类型，还是指向用这个类型的 op？
  5. 故意让 expected-error 的正则写得过死（把整句话抄进去），然后改一个字的报错措辞，看测试怎么失败。这是"测试该测什么"的一堂实践课。

这一章的要点

  • 验证是一次树遍历，每个 op 有两个钩子：进门跑 ODS 的 verifyInvariants() 和你的 verify()（此时嵌套 op 还没验过，不能碰），出门跑 verifyRegions()（这时才能安全地看 region 内部）。
  • 对应两个 ODS 开关：hasVerifier → verify()；hasRegionVerifier → verifyRegions()。
  • 诊断三习惯：用 emitOpError()（自动带 op 名与位置）、消息里别重复 op 名、把期望值与实际值都写进去；要指向别处用 attachNote。
  • 类型参数的不变式用类型自己的 genVerifyDecl + verify()，签名里第一个参数是 emitError 回调——因为类型验证发生在"构造类型"那一刻，还没有 op 可言。它连函数签名里的坏类型都拦得住。
  • 能做成接口的，就别写 verifier：pipeline 的 yield 对齐，我们只实现了 getSuccessorRegions 与 getSuccessorInputs 两个方法、二十来行，就白拿到和 scf.if 同级的控制流验证，而且同一个接口还会被第 13、19 章的分析复用。判断原则：这条信息只用于验证，还是也能被别人用？
  • 给报错行为写测试：--split-input-file --verify-diagnostics + expected-error @+1 {{正则}}。正则只匹配最稳定的片段；别忘了同时测"合法的仍然通过"，否则 verifier 写紧了没人知道。
  • 顺带的一个印证：验证器在"出门"那一步用 parallelForEach 并发验证带 IsolatedFromAbove 的子 op——第 2 章那句"这个 trait 是并发的前提"，在这里第一次兑现。

pix 进度：三个洞全补上（transpose 形状、kernel 权重与类型一致、pipeline yield 对齐），外加一条类型级不变式（边长为正奇数）。5 个 lit 测试全绿，其中一个专门守报错行为。
