第 17 章 Dialect Conversion（二）：物化、1:N 展开与读懂「failed to legalize」

这一章想让你带走什么

第 16 章结尾我们故意撞了一面墙：

error: failed to legalize unresolved materialization from ('tensor<3x3xf32>') to ('!pix.kernel<3 x 3>') that remained live after conversion

这一章把它拆干净。四件事：物化（materialization）到底在补什么洞、addSourceMaterialization 与 addTargetMaterialization 方向怎么分、函数签名为什么需要专门一条 pattern（外加一条动态合法规则）、以及 1:N 展开——一个值变成好几个值时会发生什么。

最后给一套读 failed to legalize 的系统方法：这句话有好几种变体，每一种都精确对应第 16 章那个四态模型里的一个位置。学会从报错反推是哪一态出了问题，这一章就值了。

落地物：给 pix 加两个 cast op（物化必须有 op 可用——框架不会替你发明），把物化钩子装上，那面墙就通了。

物化在补什么洞

一句话：转换是逐步的，所以任何时刻 IR 里都可能同时存在新旧两种类型。

第 16 章那个例子里，KernelLowering 把 pix.kernel 的结果从 !pix.kernel<3 x 3> 换成了 tensor<3x3xf32>。但 pix.convolve 是 Unknown（我们没标它非法），partial 模式放它过去——它还在等一个 !pix.kernel。

driver 遇到这种"接不上"时不会立刻报错，而是插一个占位：

%1 = "builtin.unrealized_conversion_cast"(%0) : (tensor<3x3xf32>) -> !pix.kernel<3 x 3>

这个 op 的名字就说明了一切——unrealized，还没兑现。转换结束时如果它还在，就是那句报错。物化钩子就是兑现它的办法。

先得有一个 op 能表达这个转换

这是最容易忽略的一步：框架不会替你发明 op。物化钩子的职责是"造一个 op 把这组值转成那个类型"，所以你的方言里必须有这么个 op。给 pix 加两个：

TableGen / ODS
def Pix_ToKernelOp : Pix_Op<"to_kernel", [Pure]> {
  let summary = "把一张权重张量看作一个卷积核（用于 source 物化）";
  let arguments = (ins F32Tensor:$weights);
  let results = (outs Pix_KernelType:$result);
  let assemblyFormat = "$weights attr-dict `:` type($weights) `->` type($result)";
}

def Pix_FromKernelOp : Pix_Op<"from_kernel", [Pure]> {
  let summary = "把一个卷积核看作权重张量（用于 target 物化）";
  let arguments = (ins Pix_KernelType:$kernel);
  let results = (outs F32Tensor:$result);
  let assemblyFormat = "$kernel attr-dict `:` type($kernel) `->` type($result)";
}
生成代码：mlir-tblgen -gen-op-decls -I $(llvm-config --includedir) PixOps.td

两个方向都要有。它们是纯粹的表示转换、不做任何计算，所以都标 Pure。真实方言里这类 op 很常见（memref.cast、tensor.cast、llvm.bitcast），builtin.unrealized_conversion_cast 只是它们的通用占位版。

两个方向：source 还是 target

这是本章最容易记混的一点。先看官方注释怎么说（mlir/include/mlir/Transforms/DialectConversion.h:194）：

source: "registers a materialization that will be called when converting a replacement value back to its original source type. This is used when some uses of the original value persist beyond the main conversion."

target: "registers a materialization that will be called when converting a value to a target type according to a pattern's type converter."

记法很简单：看你要造出来的那个类型属于哪一侧。

要造的类型 什么场景
addSourceMaterialization 旧类型（转换前的） 新值已经产出，但还有老使用者活到了转换之后
addTargetMaterialization 新类型（转换后的） 手里是老值，而某条 pattern 需要新类型的操作数

我们那个例子要造的是 !pix.kernel（旧类型），所以是 source：

C++
addSourceMaterialization([](OpBuilder &b, KernelType want,
                            ValueRange inputs, Location loc) -> Value {
  if (inputs.empty())
    return nullptr;
  if (!isa<RankedTensorType>(inputs.front().getType()))
    return nullptr;            // 不是我该管的，返回 nullptr 让框架去试别的钩子
  return ToKernelOp::create(b, loc, want, inputs.front());
});

addTargetMaterialization([](OpBuilder &b, RankedTensorType want,
                            ValueRange inputs, Location loc) -> Value {
  if (inputs.size() != 1)
    return nullptr;
  if (!isa<KernelType>(inputs.front().getType()))
    return nullptr;
  return FromKernelOp::create(b, loc, want, inputs.front());
});

回调签名是固定的 Value(OpBuilder &, T want, ValueRange inputs, Location)，其中 T 是你要造的类型（框架据此做重载分发）。返回 nullptr 表示"我物化不了，去试别的钩子"——不是错误，是协作机制。

装上之后，第 16 章那面墙通了：

MLIR（pix 方言） 
// RUN: pix-opt %s --pix-to-arith=lower-kernels=true
func.func @kernel_used(%img: tensor<8x8xf32>) -> tensor<8x8xf32> {
  %k = pix.kernel dense<1.0> : tensor<3x3xf32> -> !pix.kernel<3 x 3>
  %c = pix.convolve %img, %k : !pix.kernel<3 x 3>, tensor<8x8xf32>
  return %c : tensor<8x8xf32>
}
本地运行：pix-opt --pix-to-arith=lower-kernels=true input.mlir

运行结果：

module {
  func.func @kernel_used(%arg0: tensor<8x8xf32>) -> tensor<8x8xf32> {
    %cst = arith.constant dense<1.000000e+00> : tensor<3x3xf32>
    %0 = pix.to_kernel %cst : tensor<3x3xf32> -> <3 x 3>
    %1 = pix.convolve %arg0, %0 : <3 x 3>, tensor<8x8xf32>
    return %1 : tensor<8x8xf32>
  }
}

pix.kernel 降成了 arith.constant，中间自动插入的 pix.to_kernel 把它接回 pix.convolve。注意我们没写任何代码去插那个 op——是 driver 在需要的位置调了我们的钩子。

那些 cast op 会一直留着吗

不会——只要下游也降完就没了。pix.to_kernel(pix.from_kernel(%x)) 这种一来一回，给它们配一对 fold（第 11 章那种"返回已有的值"）就会自动消掉。真实下降管线结束时通常一个 cast 都不剩；剩下的那些恰好指出"这条路还没降完"，是很有用的信号。

函数签名：为什么要单独一条 pattern

签名里的类型不是任何 op 的操作数——函数的参数类型写在 func.func 的 function_type 属性里，块参数的类型跟着它。所以前面那些 OpConversionPattern 碰不到它们。

上游给了现成的 pattern，但配套那一步更关键：

C++
populateFunctionOpInterfaceTypeConversionPattern<func::FuncOp>(patterns, converter);

// 配套的关键一步：把 func.func 标成**动态合法**。
// 签名还没转完时它非法，转完了就合法。
target.addDynamicallyLegalOp<func::FuncOp>([&converter](func::FuncOp fn) {
  return converter.isSignatureLegal(fn.getFunctionType());
});
签名转换 = 一条 pattern + 一条动态合法规则，缺一不可

只加 pattern 不加动态合法规则：func.func 会被 addLegalDialect<func::FuncDialect>() 判成静态合法，driver 根本不会去处理它，签名原样不动，pattern 白写。

只加动态合法规则不加 pattern：func.func 被判非法，而没人能改它，于是 failed to legalize operation 'func.func'。

这是第 16 章讲的 addDynamicallyLegalOp 最典型的用法："合法"取决于转换进行到哪一步，只有动态规则表达得出来。

实测：

MLIR（pix 方言） 
// RUN: pix-opt %s --pix-to-arith=convert-signatures=true
func.func @takes_kernel(%k: !pix.kernel<3 x 3>, %img: tensor<8x8xf32>) -> tensor<8x8xf32> {
  %c = pix.convolve %img, %k : !pix.kernel<3 x 3>, tensor<8x8xf32>
  return %c : tensor<8x8xf32>
}
本地运行：pix-opt --pix-to-arith=convert-signatures=true input.mlir

运行结果：

module {
  func.func @takes_kernel(%arg0: tensor<3x3xf32>, %arg1: tensor<8x8xf32>) -> tensor<8x8xf32> {
    %0 = pix.to_kernel %arg0 : tensor<3x3xf32> -> <3 x 3>
    %1 = pix.convolve %arg1, %0 : <3 x 3>, tensor<8x8xf32>
    return %1 : tensor<8x8xf32>
  }
}

参数类型换了，而 source 物化自动把块参数接回 !pix.kernel 给 pix.convolve 用。两个机制配合起来，一行胶水代码都不用写。

1:N 展开：一个值变成好几个

真实下降里这个场景极常见。最典型的是第 24 章要讲的 memref descriptor——一个 memref<8xf32> 展成"基址、对齐地址、偏移、尺寸、步长"一串标量。

addConversion 的 1:N 形式，回调多一个输出参数（DialectConversion.h:154 的注释写得很清楚）：

C++
// 1:N：往 out 里塞几个类型就展成几个值。塞 0 个表示"这个类型直接消失"。
addConversion([](KernelType kty,
                 SmallVectorImpl<Type> &out) -> std::optional<LogicalResult> {
  MLIRContext *ctx = kty.getContext();
  out.push_back(RankedTensorType::get({kty.getRows(), kty.getCols()},
                                      Float32Type::get(ctx)));
  out.push_back(IndexType::get(ctx));   // 半径
  return success();
});

（动机是真的：降成循环之后，边界处理需要半径当循环边界。）

配合签名转换跑一下：

MLIR（pix 方言） 
// RUN: pix-opt %s --pix-to-arith='convert-signatures=true one-to-n=true'
func.func @takes_kernel(%k: !pix.kernel<3 x 3>, %img: tensor<8x8xf32>) -> tensor<8x8xf32> {
  %c = pix.convolve %img, %k : !pix.kernel<3 x 3>, tensor<8x8xf32>
  return %c : tensor<8x8xf32>
}
本地运行：pix-opt --pix-to-arith='convert-signatures=true one-to-n=true' input.mlir

运行结果：

module {
  func.func @takes_kernel(%arg0: tensor<3x3xf32>, %arg1: index, %arg2: tensor<8x8xf32>) -> tensor<8x8xf32> {
    %0 = pix.to_kernel %arg0 : tensor<3x3xf32> -> <3 x 3>
    %1 = pix.convolve %arg2, %0 : <3 x 3>, tensor<8x8xf32>
    return %1 : tensor<8x8xf32>
  }
}

一个参数变成了两个，原来的 %img 被挤到第三位（%arg2）。物化钩子收到两个输入，取第一个装回 kernel。

1:N 会让你的物化钩子收到多个输入

我第一版钩子里写的是 if (inputs.size() != 1) return nullptr;，看起来很稳妥。开了 1:N 之后立刻报错：

failed to legalize unresolved materialization from ('tensor<3x3xf32>', 'index') to ('!pix.kernel<3 x 3>')

报错里那个类型列表就是线索——括号里有两个类型，说明这是个 1:N 物化，而你的钩子只认 1 个输入。写物化钩子时，别用 size() != 1 当卫语句，要按"我认得哪些输入"来判断。

另一个连带影响：1:N 之后参数编号全变了。测试里硬写 %arg1 的地方会莫名失败——用第 12 章讲的 %[[NAME:.*]] 捕获能免疫这类改动。

把物化的四种命运跑一遍

上面四个场景（没钩子 / 有钩子 / 1:N 但钩子不认 / 1:N 且钩子能处理）可以在一个模型里连着看。它打出来的两句失败信息和真 pix-opt 的格式完全一致：

Python 
# 物化到底在解决什么？用一个"类型账本"模型看清楚。
# 核心观念：转换是**逐步**的，所以任何时刻 IR 里都可能同时存在新旧两种类型，
# driver 用 unrealized_conversion_cast 占位，等你注册的钩子来兑现。

class Driver:
    def __init__(self, type_rule, source_mat=None, target_mat=None):
        self.type_rule = type_rule          # 旧类型 -> 新类型列表（1:N）
        self.source_mat, self.target_mat = source_mat, target_mat
        self.casts = []                     # 未兑现的占位

    def convert_value(self, name, old_ty):
        new = self.type_rule(old_ty)
        if new is None:
            return [(name, old_ty)]
        print(f"    {name}: {old_ty} → {', '.join(new)}"
              + ("（1:N 展开）" if len(new) > 1 else ""))
        return [(f"{name}#{i}", t) for i, t in enumerate(new)]

    def need(self, values, want_ty, who):
        """有人（who）需要 want_ty，但手里是 values。凑不上就要物化。"""
        types = [t for _, t in values]
        if types == [want_ty]:
            print(f"    {who} 拿到的正是 {want_ty}，不用物化")
            return
        print(f"    {who} 要 {want_ty}，手里是 ({', '.join(types)}) —— 需要物化")
        # 方向判断：want 是"原始的源类型" → source 物化；是"目标类型" → target 物化
        hook = self.source_mat if want_ty.startswith("!") else self.target_mat
        kind = "source" if want_ty.startswith("!") else "target"
        if hook is None:
            self.casts.append((types, want_ty))
            print(f"      没注册 {kind} 物化钩子 → 插一个 "
                  f"unrealized_conversion_cast({', '.join(types)}) -> {want_ty} 占位")
            return
        made = hook(types, want_ty)
        if made is None:
            self.casts.append((types, want_ty))
            print(f"      {kind} 钩子返回 nullptr（它不认这组输入）→ 仍是占位")
            return
        print(f"      {kind} 物化成功：插入 {made}")

    def finish(self):
        if not self.casts:
            return "转换成功"
        bad = self.casts[0]
        return ("失败：failed to legalize unresolved materialization from "
                f"({', '.join(repr(t) for t in bad[0])}) to ('{bad[1]}')")

KERNEL = "!pix.kernel<3x3>"

def rule_1to1(ty):  return ["tensor<3x3xf32>"] if ty == KERNEL else None
def rule_1toN(ty):  return ["tensor<3x3xf32>", "index"] if ty == KERNEL else None

def src_only_1(types, want):
    return f"pix.to_kernel(%0)" if len(types) == 1 else None
def src_any(types, want):
    return f"pix.to_kernel(%0)" if types and types[0].startswith("tensor") else None

CASES = [
    ("① 不注册任何物化钩子", rule_1to1, None, None),
    ("② 注册 source 物化", rule_1to1, src_only_1, None),
    ("③ 换成 1:N，但 source 钩子只认 1 个输入", rule_1toN, src_only_1, None),
    ("④ 1:N + 能处理多输入的 source 钩子", rule_1toN, src_any, None),
]
for title, rule, sm, tm in CASES:
    print(f"\n【{title}】")
    d = Driver(rule, sm, tm)
    vals = d.convert_value("%k", KERNEL)          # pix.kernel 的结果被换了类型
    d.need(vals, KERNEL, "pix.convolve（还等旧类型）")
    print(f"  → {d.finish()}")

运行结果：


【① 不注册任何物化钩子】
    %k: !pix.kernel<3x3> → tensor<3x3xf32>
    pix.convolve（还等旧类型） 要 !pix.kernel<3x3>，手里是 (tensor<3x3xf32>) —— 需要物化
      没注册 source 物化钩子 → 插一个 unrealized_conversion_cast(tensor<3x3xf32>) -> !pix.kernel<3x3> 占位
  → 失败：failed to legalize unresolved materialization from ('tensor<3x3xf32>') to ('!pix.kernel<3x3>')

【② 注册 source 物化】
    %k: !pix.kernel<3x3> → tensor<3x3xf32>
    pix.convolve（还等旧类型） 要 !pix.kernel<3x3>，手里是 (tensor<3x3xf32>) —— 需要物化
      source 物化成功：插入 pix.to_kernel(%0)
  → 转换成功

【③ 换成 1:N，但 source 钩子只认 1 个输入】
    %k: !pix.kernel<3x3> → tensor<3x3xf32>, index（1:N 展开）
    pix.convolve（还等旧类型） 要 !pix.kernel<3x3>，手里是 (tensor<3x3xf32>, index) —— 需要物化
      source 钩子返回 nullptr（它不认这组输入）→ 仍是占位
  → 失败：failed to legalize unresolved materialization from ('tensor<3x3xf32>', 'index') to ('!pix.kernel<3x3>')

【④ 1:N + 能处理多输入的 source 钩子】
    %k: !pix.kernel<3x3> → tensor<3x3xf32>, index（1:N 展开）
    pix.convolve（还等旧类型） 要 !pix.kernel<3x3>，手里是 (tensor<3x3xf32>, index) —— 需要物化
      source 物化成功：插入 pix.to_kernel(%0)
  → 转换成功

③ 和 ④ 的差别只在钩子的一个 if，而报错里那个类型列表 ('tensor<3x3xf32>', 'index') 就是告诉你"这是 1:N"的唯一线索。

读懂 failed to legalize：一套系统方法

这句话有几种变体，每一种精确对应第 16 章那个四态模型里的一个位置。

报错 真正的含义 先查什么
failed to legalize operation 'X' X 是 Illegal，但没有 pattern 能换掉它 你写了 X 的 pattern 吗？它注册进 patterns 了吗？matchAndRewrite 是不是提前 return failure() 了？
failed to legalize operation 'builtin.module'（或别的外层 op） 通常是 full 模式下某个内层 op 是 Unknown 把 full 换成 partial 看还报不报。报错指向外层 = 问题在里面
failed to legalize unresolved materialization from (T1) to (T2) 类型换了，但没人把它接回去 要造的 T2 是旧类型还是新类型？据此决定注册 source 还是 target 钩子
同上，但括号里有多个类型 这是 1:N 物化 钩子里是不是用 size() != 1 把它挡掉了
failed to legalize operation 'func.func' 签名被判非法，却没有签名转换 pattern 加 populateFunctionOpInterfaceTypeConversionPattern
签名根本没变，也不报错 func.func 被静态判成合法了 加 addDynamicallyLegalOp<func::FuncOp> + isSignatureLegal

光看报错还不够时，上 --debug-only=dialect-conversion（需要开断言的构建）。它给出逐 op 的判定与理由：

终端
pix-opt k16.mlir --pix-to-arith='lower-kernels=true no-materialize=true' \
  --debug-only=dialect-conversion

运行结果（截取几段）：

[dialect-conversion:1] Legalizing operation : 'func.func' (0x...) {
[dialect-conversion:1] } -> SUCCESS : operation marked legal by the target
[dialect-conversion:1] Legalizing operation : 'pix.kernel' (0x...) {
[dialect-conversion:1]   * Fold {
[dialect-conversion:1]   } -> FAILURE : unable to fold
[dialect-conversion:1]   * Pattern : 'pix.kernel -> ()' {
[dialect-conversion:1]     ** Insert  : 'arith.constant' (0x...) (was detached)
[dialect-conversion:1]     ** Replace : 'pix.kernel'(0x...)

判定词汇只有四种，各自的含义值得记住：

判定 含义
SUCCESS : operation marked legal by the target 这个 op 在 target 里被判合法，driver 没碰它
SUCCESS : pattern applied successfully 某条 pattern 换掉了它
FAILURE : no matched legalization pattern 它被判非法，但一条 pattern 都没匹配上
FAILURE : unable to fold driver 先试了常量折叠（这一步在 pattern 之前！），折不动

最后那条顺带解释了第 16 章那个 ConstantLike 断言为什么会在 dialect conversion 里炸：driver 对每个非法 op 都会先试一次 fold，而 ConstantLike 的 op 必须 foldable。

排查顺序：从四态开始，不是从 pattern 开始

大多数人卡住时第一反应是去检查 pattern 有没有写对。但实践中一半以上的 failed to legalize 根本不是 pattern 的问题，而是：这个 op 在 target 里到底是哪一态？

按这个顺序问：① 它是 Illegal 还是 Unknown？（决定了 partial 会不会放它过去）② 我用的是 partial 还是 full？③ 类型变了吗？（变了就要想物化）④ 才轮到 pattern 有没有注册、会不会匹配。

把 `--debug-only=dialect-conversion` 的输出和这四个问题对着看，绝大多数问题在两分钟内能定位。

动手：把两个 cast op 消掉

C++
// pix.to_kernel(pix.from_kernel(%k)) → %k
OpFoldResult ToKernelOp::fold(FoldAdaptor adaptor) {
  if (auto inner = getWeights().getDefiningOp<FromKernelOp>())
    if (inner.getKernel().getType() == getType())
      return inner.getKernel();
  return {};
}

这一章的要点

  • 物化补的洞是"转换逐步进行，新旧类型会共存"。driver 在接不上的地方插 builtin.unrealized_conversion_cast 占位（名字里的 unrealized 就是"还没兑现"），转换结束时还在就报错。
  • 前提是你的方言里有能表达这个转换的 op——框架不会替你发明。我们为此给 pix 加了 pix.to_kernel / pix.from_kernel，两个方向都要有。
  • 方向判据：看你要造出来的那个类型。 造旧类型 → addSourceMaterialization（新值已产出、老使用者还活着）；造新类型 → addTargetMaterialization（手里是老值、pattern 要新类型）。
  • 钩子签名 Value(OpBuilder &, T want, ValueRange inputs, Location)，返回 nullptr 表示"我不管"，框架会去试别的钩子——这是协作机制，不是错误。
  • 签名转换要两样一起：populateFunctionOpInterfaceTypeConversionPattern 这条 pattern，加上 addDynamicallyLegalOp<func::FuncOp>(isSignatureLegal)。只加 pattern，func.func 被静态判合法、签名根本不会变；只加动态规则，得到 failed to legalize operation 'func.func'。
  • 1:N 用 addConversion 的两参数形式（往 SmallVectorImpl<Type>& 里塞几个就展成几个，塞 0 个表示类型消失）。它会让你的物化钩子收到多个输入——别拿 size() != 1 当卫语句。1:N 还会让参数编号全变，测试里用 %[[NAME:.*]] 捕获而不是硬写 %arg1。
  • 读 failed to legalize 的方法：从四态反推，不是从 pattern 开始。 依次问：它是 Illegal 还是 Unknown → 我用的 partial 还是 full → 类型变了吗 → 最后才是 pattern。报错里的类型列表告诉你是不是 1:N；报错指向外层 op 通常意味着 full 模式下有内层 Unknown。
  • --debug-only=dialect-conversion 给逐 op 判定，四种判定词各有精确含义。其中 FAILURE : unable to fold 说明 driver 对每个非法 op 都会先试一次 fold——这解释了第 16 章那个 ConstantLike 断言为什么在这里炸。
