第 2 章 IR 的形状：Operation / Region / Block / Value 与 LLVM IR 对照

这一章想让你带走什么

上一章说 MLIR「没有固定的指令集，只有骨架」。这一章就把骨架拆开：Operation、Region、Block、Value 四个概念，加上把它们连起来的 OpOperand。你会看到 Operation 在内存里是怎么一次性分配出来的、为什么 MLIR 不需要 phi 指令、为什么「一个函数」和「一个模块」在 MLIR 里都只是普通的 op。

拿走三样东西：一张能对着 LLVM IR 逐项翻译的对照表；一个浏览器里能跑的迷你 IR，你会亲手实现 replaceAllUsesWith——所有 pattern 重写背后的那个原子动作（第 14 章会用真家伙再做一遍）；以及一个此后天天要用的判断力：看到一段 MLIR，能立刻说出它有几层 region、哪些值跨了 region 边界、谁是 terminator。

先摆一张对照表

你已经有 LLVM IR 的心智模型了，最快的路是逐项翻译。先记结论，后面逐条展开：

LLVM IR MLIR 差别在哪
Module builtin.module op 模块不是特殊容器，就是一个普通 op
Function func.func op 函数也是 op；它的函数体是它的 region
BasicBlock Block 概念一致，但 block 可以有参数
Instruction Operation 指令集不固定；op 可以嵌套 region
Value Value 一致：SSA 值。来源只有两种（op 结果 / 块参数）
Use / User OpOperand 一致：一条 def-use 边是个对象
phi 指令 块参数 + terminator 传参 MLIR 没有 phi
固定的类型系统 方言可注册类型 tensor、memref、!pix.kernel 平等
metadata（可丢） 属性（固有属性不可丢） 语义有保证，见本章最后一节
intrinsic 就是普通 op 不需要"特殊指令"这个概念

一句话总结这张表：MLIR 把 LLVM IR 里那些"特殊的东西"（模块、函数、phi、intrinsic）全部化归成了同一个东西——op。

Operation：唯一的主角

MLIR 里几乎所有东西都是 Operation。一个 op 身上挂着这些部分：

  • 名字（OperationName）："arith.addf" 这样的字符串，前缀就是方言名。注意名字是运行时数据，不是 C++ 枚举——这正是 op 可扩展的前提。
  • 操作数（operands）：一串 Value，每个操作数对应一条 def-use 边。
  • 结果（results）：一串 Value。可以是 0 个（func.return）、1 个、或多个。
  • 属性 / 属性存储（attributes、properties）：编译期常量数据，比如常量的值、函数名、fastmath 标志。
  • region：0 到 N 个。这是 MLIR 与 LLVM IR 结构上最大的不同。
  • 后继块（successors）：只有分支类 op 才有。
  • 位置（Location）：不可选。每个 op 都带位置信息，报错才能指回源码。
  • 以及它在哪个 Block 里。

这些东西在内存里不是一堆独立的 std::vector，而是紧跟在 Operation 对象后面一次性分配出来的。源码里这行类声明就是证据（mlir/include/mlir/IR/Operation.h）：

C++
// mlir/include/mlir/IR/Operation.h
class alignas(8) Operation final
    : public llvm::ilist_node_with_parent<Operation, Block>,
      private llvm::TrailingObjects<Operation, detail::OperandStorage,
                                    detail::OpProperties, BlockOperand, Region,
                                    OpOperand> {
public:
  static Operation *create(Location location, OperationName name,
                           TypeRange resultTypes, ValueRange operands, ...);

读法：TrailingObjects<Operation, A, B, C…> 是 LLVM 里一个常用手法——把若干个变长数组接在对象自己后面，一次 malloc 搞定。所以一个 op 的操作数存储、属性存储、后继块、region 列表、以及结果对应的 OpOperand，全都在同一块内存里。ilist_node_with_parent<Operation, Block> 则说明 op 是侵入式链表的节点，它天生知道自己的父 block，在链表里插入删除都是 O(1)。

图 2-1　Operation 的内存布局。理解这张图能解释很多现象：为什么 op 没有"构造函数"只有 `create`（要先算出变长部分的大小）、为什么改变操作数个数的 API 很少、以及为什么 MLIR 能在一个 IR 里容纳成千上万种 op
三个要尽早接受的"都是 op"

模块是 op（builtin.module）：所以 pass 可以跑在模块上，也可以跑在任何 op 上，没有"顶层特殊处理"。函数是 op（func.func）：所以一个方言可以定义自己的"函数"（比如 gpu.func），不需要改框架。常量是 op（arith.constant）：MLIR 里没有"立即数操作数"这种东西，常量必须先由一个 op 产生出一个值——这点第 11 章讲折叠时会变得很关键。

Value 与 def-use：边也是对象

Value 就是 SSA 值。它的来源只有两种（mlir/include/mlir/IR/Value.h）：

  • OpResult：某个 op 的第 n 个结果。
  • BlockArgument：某个 block 的第 n 个参数。

没有第三种。函数参数不是特例——它们就是函数体 region 首块的块参数。

把值和 op 连起来的是 OpOperand：一条 def-use 边。关键点在于边是一个对象，不是一根裸指针。每个 OpOperand 知道自己属于哪个 op、是第几个操作数、指向哪个值；而每个值维护一条侵入式链表，串起所有指向它的 OpOperand（mlir/include/mlir/IR/UseDefLists.h 里的 IRObjectWithUseList，成员就叫 firstUse）。

这个设计带来一个极其常用的能力：Value::replaceAllUsesWith(newValue)——把「所有用我的地方」一次性改成用别人，代价与使用次数成正比，不需要扫整个函数。MLIR 里几乎所有变换最后都落到这一句上。

下面这段代码把 Value / OpOperand / Operation 三者照搬成 60 行 Python，然后做一次 replaceAllUsesWith，把第 1 章那个「乘 1.0」折掉。点运行，看 use list 怎么变：

Python 
# 一个迷你 IR：把 MLIR 的 Value / OpOperand / Operation 三者的关系照搬出来，
# 然后做一次 replaceAllUsesWith——这是所有 pattern 重写背后的那个原子动作。

class Value:
    """SSA 值。它记着'谁在用我'（use list），而不只是'我被谁定义'。"""
    def __init__(self, name, defining_op=None):
        self.name = name
        self.defining_op = defining_op   # None 表示它是块参数（比如函数入口参数）
        self.uses = []                   # 元素是 OpOperand；MLIR 里这是一条侵入式链表

    def replace_all_uses_with(self, new_value):
        # MLIR 里这一句就是 Value::replaceAllUsesWith(newValue)
        moved = list(self.uses)
        for use in moved:
            use.set(new_value)           # 每条边改指向，顺手维护两端的 use list
        return len(moved)

    def __repr__(self):
        return self.name


class OpOperand:
    """一条 def-use 边。它是个对象，不是裸指针——它知道自己属于哪个 op 的第几个操作数。"""
    def __init__(self, owner, index, value):
        self.owner, self.index, self.value = owner, index, None
        self.set(value)

    def set(self, value):
        if self.value is not None:
            self.value.uses.remove(self)
        self.value = value
        value.uses.append(self)


class Operation:
    def __init__(self, name, operands, num_results=1):
        self.name = name
        self.operands = [OpOperand(self, i, v) for i, v in enumerate(operands)]
        short = name.split(".")[-1]
        self.results = [Value(f"%{short}{i}", self) for i in range(num_results)]

    def ins(self):
        return [o.value for o in self.operands]

    def __repr__(self):
        outs = ", ".join(r.name for r in self.results)
        lhs = outs + " = " if outs else ""
        return f"{lhs}{self.name} {', '.join(v.name for v in self.ins())}"


def dump(title, values, ops):
    print(f"--- {title} ---")
    for op in ops:
        print("  " + repr(op))
    print("  use list（谁在用这个值）：")
    for v in values:
        users = [f"{u.owner.name}#{u.index}" for u in v.uses]
        print(f"    {v.name:>8} -> {users if users else '（没人用）'}")
    print()


# 构造：%sum = addf %a, %b ; %out = mulf %sum, %one ; return %out
a, b, one = Value("%a"), Value("%b"), Value("%one")
addf = Operation("arith.addf", [a, b])
sum_v = addf.results[0]
mulf = Operation("arith.mulf", [sum_v, one])
out_v = mulf.results[0]
ret = Operation("func.return", [out_v], num_results=0)
ops = [addf, mulf, ret]
watch = [a, b, one, sum_v, out_v]
dump("构造完成", watch, ops)

# 做"乘 1.0 等于没乘"这个折叠：把 mulf 的结果，全部换成它的第一个操作数
n = out_v.replace_all_uses_with(sum_v)
print(f"replaceAllUsesWith：改写了 {n} 条 def-use 边")
print()
dump("折叠之后（mulf 还在，但已经没人用它的结果）", watch, ops)


def erase(op, ops):
    if any(r.uses for r in op.results):
        print(f"  {op.name} 的结果还有人用，不能删")
        return
    for use in list(op.operands):
        use.value.uses.remove(use)
    ops.remove(op)
    print(f"  删掉 {op.name}")


print("清理死代码：")
erase(mulf, ops)
print()
dump("最终 IR", watch, ops)
print("注意 %one 的 use list 也空了——定义它的那个常量 op 于是也成了死代码，")
print("会被同一趟清理顺手带走。这就是为什么 MLIR 里'折叠'和'删死代码'总是成对出现。")

这段输出就是第 1 章那条 --canonicalize 命令内部发生的事。 真正的 mlir-opt 只是把「折叠 + RAUW + 删死 op」放进了一个带 worklist 的驱动器里反复跑（第 14 章）。

两个细节值得注意

一，折叠之后 arith.mulf 还在 IR 里，只是没人用它的结果了——"改写"与"删除"是两个独立动作。二，判断一个 op 能不能删，不只看"有没有用户"，还要看它有没有副作用：一个没人用结果的 memref.store 绝不能删。这个信息由第 5 章的 MemoryEffects 接口提供，而 Pure 这个 trait 就是"无副作用 + 可推测执行"的简写。

Region 与 Block：嵌套是一等公民

现在到了 MLIR 与 LLVM IR 结构上真正分岔的地方。

  • Block = 一串 op + 一组块参数 + 最后一个 op 是 terminator。
  • Region = 一串 Block。
  • 一个 op 可以有 0 到 N 个 region。

于是 IR 是一棵树：op 里有 region，region 里有 block，block 里又有 op……一路嵌套下去。LLVM IR 只有「函数 → 基本块 → 指令」这固定三层，且指令内部不能再套东西。

看一个真实的三层嵌套。这段代码求和，用 scf.for 带 iter_args（相当于循环携带的累加器）：

MLIR 🔗 在 Compiler Explorer 打开（mlir-opt）
func.func @sum(%buf: memref<8xf32>) -> f32 {
  %c0 = arith.constant 0 : index
  %c1 = arith.constant 1 : index
  %c8 = arith.constant 8 : index
  %init = arith.constant 0.0 : f32
  %total = scf.for %i = %c0 to %c8 step %c1 iter_args(%acc = %init) -> (f32) {
    %v = memref.load %buf[%i] : memref<8xf32>
    %next = arith.addf %acc, %v : f32
    scf.yield %next : f32
  }
  return %total : f32
}
本地运行：mlir-opt input.mlir

把它用通用格式打印出来，嵌套结构就全露出来了：

终端

运行结果：

逐条对着看，有五个信息量很大的点：

  1. 三层 region 清晰可见：builtin.module 的 region 里装着 func.func，func.func 的 region 里装着循环，scf.for 的 region 里装着循环体。
  2. 归纳变量 %i 和累加器 %acc 都是块参数：^bb0(%arg1: index, %arg2: f32)。循环体不是"知道自己是循环体"的特殊结构，它只是一个带参数的 block。
  3. scf.yield 是 terminator，它把这一轮的累加值交回给 scf.for；scf.for 的结果 %4 就是最后一轮 yield 的值。
  4. %arg0（那个 memref）被循环体直接引用了——它定义在外层 region，但在内层可见。这是 MLIR 允许的：内层 region 能引用外层已定义的值，不必像函数调用那样把所有东西当参数传进去。
  5. scf.for 的操作数是 (%0, %2, %1, %3)，即 lower/upper/step/init——自定义格式里那套漂亮的 %i = %c0 to %c8 step %c1 语法只是打印出来的糖（第 3 章、第 8 章讲它从哪来）。
图 2-2　上一段 IR 的树形结构。`scf.for` 不是"控制流指令"，它是一个**带 region 的普通 op**——这就是为什么 MLIR 能在保留循环结构的前提下做变换，而不必先拆成分支再靠分析认回来

为什么不需要 phi：块参数

LLVM IR 里合并控制流要用 phi：

LLVM IR：phi 指令
LLVM IR
define i32 @select_max(i32 %a, i32 %b) {
entry:
  %c = icmp sgt i32 %a, %b
  br i1 %c, label %bb1, label %bb2
bb1:
  br label %merge
bb2:
  br label %merge
merge:
  %r = phi i32 [ %a, %bb1 ], [ %b, %bb2 ]
  ret i32 %r
}
MLIR：块参数 + 分支传参
MLIR 🔗 在 Compiler Explorer 打开（mlir-opt）
func.func @select_max(%a: i32, %b: i32) -> i32 {
  %c = arith.cmpi sgt, %a, %b : i32
  cf.cond_br %c, ^bb1, ^bb2
^bb1:
  cf.br ^merge(%a : i32)
^bb2:
  cf.br ^merge(%b : i32)
^merge(%r: i32):
  return %r : i32
}
本地运行：mlir-opt input.mlir

两边语义完全一样，但 MLIR 这边没有 phi 这种"必须在块开头、与前驱一一对应"的特殊指令。值是由分支像函数调用一样"传"进目标块的，块参数就是形参。

这不只是审美问题。phi 在真实编译器里制造了一大堆特例：删一个前驱块要同步改所有 phi；phi 的"并行赋值"语义容易写错；函数参数又是另一套机制。改成块参数后，这些特例全没了——函数参数就是首块的块参数，删前驱就是删一条分支的实参。官方 mlir/docs/Rationale/Rationale.md 里 "block arguments vs phi nodes" 一节专门讲这个权衡，值得一读。

跑一下上面那段 MLIR，注意 mlir-opt 打印回来时把 ^merge 规范化成了 ^bb3，并自动标注了前驱：

  ^bb3(%1: i32):  // 2 preds: ^bb1, ^bb2
    return %1 : i32

两种 region：SSACFG 与 Graph

Region 分两类（mlir/include/mlir/IR/RegionKindInterface.h 的 enum class RegionKind）：

  • SSACFG：普通的控制流语义，要求支配关系成立（定义必须支配使用）。函数体、循环体都是这种。
  • Graph：没有控制流概念，op 之间只有数据依赖，不要求支配——所以可以互相引用、可以有环。硬件描述、数据流图这类方言会用它。

绝大多数时候你打交道的都是 SSACFG。但知道 Graph 存在很重要：它解释了为什么 MLIR 的很多工具（比如支配关系分析）要先问一句"这个 region 是什么类型"。

一个跨 region 的关键规则：IsolatedFromAbove

上面第 4 点说"内层 region 可以引用外层的值"。但有个例外，而且极其重要：带 IsolatedFromAbove 这个 trait 的 op，它的 region 不允许引用外部的值——所有输入必须显式传进来。

func.func 就带这个 trait（函数体不能随便引用别的函数里的值，这符合直觉），builtin.module 也带。这条规则有两个大后果：

  • pass 可以并发跑。第 13 章会讲：正因为每个 func.func 与外界隔离，pass 管理器才能安全地把多个函数丢给多个线程同时处理。
  • outlining 才可能。第 25 章把循环体抽成 GPU kernel（一个 gpu.func），前提就是先把它引用的外部值都变成显式参数。

源码里它叫 OpTrait::IsIsolatedFromAbove（mlir/include/mlir/IR/OpDefinition.h），ODS 里写作 IsolatedFromAbove（第 8 章你会亲手给 op 加 trait）。

属性：<{...}> 与 {...} 不是一回事

回头看通用格式的输出，你会注意到两种括号：

MLIR
// 尖括号：固有属性（存在 properties 里）
%6 = "arith.addf"(%arg2, %5) <{fastmath = #arith.fastmath<none>}> : (f32, f32) -> f32

// 花括号：可丢弃属性（存在通用字典里）
%7 = "arith.addf"(%arg2, %5) {my_pass.visited = true} : (f32, f32) -> f32

区别是语义责任归谁：

  • 固有属性（inherent attribute）：是 op 定义的一部分，op 的语义依赖它。arith.constant 的 value、func.func 的 sym_name 和 function_type 都是。它们必须存在且合法，verifier 会查（第 10 章）。采用了 properties 存储的方言，这些属性存在 op 自己的内联存储里，打印成 <{...}>。
  • 可丢弃属性（discardable attribute）：语义定义在 op 之外，谁都能挂，丢了不影响 IR 合法性。典型用途是 pass 之间传信息、打标记。
别把重要语义放在可丢弃属性里

这正是第 1 章批评 LLVM metadata 的那个问题——可丢弃的东西不能承载"必须成立"的语义，因为任何一次变换都可以合法地把它抹掉。如果某个信息丢了会让程序算错，它就该是固有属性、或者干脆体现在类型里（第 4 章）、或者用一个专门的 op 表达。

动手：把一段 IR 的骨架读出来

下面这段 IR 有点绕：一个 scf.if 嵌在 scf.for 里，还引用了外层的值。先不要运行，自己回答四个问题，再跑一遍核对：

MLIR 🔗 在 Compiler Explorer 打开（mlir-opt）
// RUN: mlir-opt %s --mlir-print-op-generic
func.func @clamp_sum(%buf: memref<8xf32>, %limit: f32) -> f32 {
  %c0 = arith.constant 0 : index
  %c1 = arith.constant 1 : index
  %c8 = arith.constant 8 : index
  %zero = arith.constant 0.0 : f32
  %total = scf.for %i = %c0 to %c8 step %c1 iter_args(%acc = %zero) -> (f32) {
    %v = memref.load %buf[%i] : memref<8xf32>
    %too_big = arith.cmpf ogt, %v, %limit : f32
    %clamped = scf.if %too_big -> (f32) {
      scf.yield %limit : f32
    } else {
      scf.yield %v : f32
    }
    %next = arith.addf %acc, %clamped : f32
    scf.yield %next : f32
  }
  return %total : f32
}
本地运行：mlir-opt --mlir-print-op-generic input.mlir
  1. 一共有几个 region？分别属于哪个 op？（提示：数 op，不是数缩进）
  2. %limit 被用在了第几层 region 里？它跨了几层 region 边界？为什么这是合法的？
  3. 这段 IR 里哪些 op 是 terminator？一共几个？
  4. scf.if 有两个 region（then 和 else），它们各有几个 block？块参数有几个？

跑 mlir-opt clamp_sum.mlir --mlir-print-op-generic 对答案。数清楚了，你对 MLIR 的结构就有手感了。

再改一改。 这三处改动的报错都有点出人意料，正好把"谁在检查什么"这件事分清楚：

  1. 把 scf.yield %limit : f32 改成 scf.yield %too_big : f32。报错是 use of value '%too_big' expects different type than prior uses: 'f32' vs 'i1'——注意措辞：这是**解析器（parser）**抓到的，不是 verifier。因为 %too_big 在前面已经有类型了，文本格式里同一个名字不能有两种类型。verifier 还没来得及上场。
  2. 删掉 else 里的 scf.yield，只留一个空的 else。你可能以为会看到"block 缺 terminator"，但实际报错是 'scf.if' op along control flow edge from Operation scf.yield to Operation scf.if: region branch point has 0 operands, but region successor needs 1 inputs。为什么会冒出一个 scf.yield？因为 scf.if 声明了隐式 terminator——你不写，它替你插一个空的 scf.yield，于是错误变成了"yield 了 0 个值，但 scf.if 要 1 个结果"。这条检查来自 RegionBranchOpInterface（第 5 章讲接口，第 10 章讲验证顺序）。
  3. 想看真正的支配关系报错，scf.if 这个例子办不到——你甚至没法在外面写出那个名字（报错只会是 use of undeclared SSA value name，因为文本格式里 SSA 名字是按 region 作用域的）。换成显式控制流才能触发：
MLIR
func.func @dom2(%c: i1) -> i32 {
  cf.cond_br %c, ^bb1, ^bb2
^bb1:
  %x = arith.constant 1 : i32
  cf.br ^bb3
^bb2:
  cf.br ^bb3
^bb3:
  return %x : i32        // %x 只在 ^bb1 里定义，不支配 ^bb3
}

跑它会得到：error: operand #0 does not dominate this use，还附带一条 note: operand defined here (op in the same region) 指向定义处。这才是 SSACFG region 那条"定义必须支配使用"规则的执行者。 顺便体会一下 MLIR 诊断的质量：错误 + note 指向两处，都带位置——这是第 10 章要教你为自己的 op 做到的。

这一章的要点

  • MLIR 把 LLVM IR 里所有"特殊的东西"化归成了 op：模块是 op、函数是 op、常量是 op。名字是运行时字符串，这才有了可扩展性。
  • Operation 用 TrailingObjects 一次分配：操作数存储、属性存储、后继块、region、结果的 use 边全在同一块内存里；op 同时是侵入式链表节点，插删 O(1)。
  • Value 只有两种来源：OpResult 与 BlockArgument。函数参数不是特例，它是首块的块参数。
  • def-use 的边 OpOperand 是对象，值维护一条 use 链表——于是有了 replaceAllUsesWith，你已经亲手实现过一遍：所有 pattern 重写最后都落到它身上。
  • Region 让 IR 成为一棵树：op → region → block → op。循环、条件都是"带 region 的普通 op"，结构不用先拆掉再认回来。
  • 没有 phi：块参数 + 分支传参，消掉了一堆特例。
  • IsolatedFromAbove 是"region 不能引用外部值"的声明，它是 pass 并发与 kernel outlining 的前提。
  • 属性分固有（<{...}>，语义必需、verifier 查）与可丢弃（{...}，随时可丢）。别把关键语义放进可丢弃属性——那就是 LLVM metadata 的老问题。
