第 7 章 起一个 out-of-tree 方言：目录、CMake 与 mlir-tblgen 构建链

这一章想让你带走什么

第一部分全是"读"，从这一章开始"写"。目标很具体：在 LLVM 源码树之外建一个自己的项目，里面有一个叫 pix 的方言、一个叫 pix.add 的 op、一个叫 pix-opt 的命令行工具，以及三个 lit 测试。做完你就有了本书后面所有章节的工作台。

但这一章的重点不是把文件抄一遍，而是讲清那条构建链：一行 add_mlir_dialect(PixOps pix) 到底生成了哪六个文件、#define GET_OP_CLASSES 这个宏把戏为什么必须这么写、find_package(MLIR) 带来了什么。搞不清这条链，以后每次改 .td 都是在碰运气；搞清了，你会发现 MLIR 的工程结构其实非常规整。

还有一个免费的惊喜在等着：我们一行优化代码都不会写，但 pix.add 直接就能被 --cse 优化——因为第 5 章那套 trait 声明。

先说结果

这一章结束时，你的项目长这样（完整工程在随书代码 books/inside-mlir/code/pix/）：

pix/

然后这两条命令能跑通：

ninja -C build && ninja -C build check-pix

另外，上游 mlir/examples/standalone/ 是官方维护的 out-of-tree 模板（还带 Python 绑定、C API 和 plugin 示例）。本章这套骨架就是照它裁剪的——以后 MLIR 改了构建约定，去对一下那个模板，它永远是最新的。

那条构建链

先看全局。从你写的三种源文件到最后的 pix-opt，中间经过 mlir-tblgen 这一道代码生成：

图 7-1　out-of-tree 方言的构建链。左边三类源文件你都要写；中间六个 `.inc` 一个字都不用写，但**你得知道它们叫什么、在哪里**，否则 include 路径写不对

第一句秘密：find_package(MLIR REQUIRED CONFIG)

顶层 CMakeLists.txt 的核心只有这一句：

cmake
find_package(MLIR REQUIRED CONFIG)

list(APPEND CMAKE_MODULE_PATH "${MLIR_CMAKE_DIR}")
list(APPEND CMAKE_MODULE_PATH "${LLVM_CMAKE_DIR}")

include(TableGen)          # mlir_tablegen / add_public_tablegen_target
include(AddLLVM)           # add_llvm_executable
include(AddMLIR)           # add_mlir_dialect / add_mlir_dialect_library
include(HandleLLVMOptions) # 让本项目用与 LLVM 一致的编译选项

find_package(MLIR REQUIRED CONFIG) 会去 MLIR_DIR 指定的目录找 MLIRConfig.cmake，然后一次性给你三样东西：

  1. 头文件与库的位置：MLIR_INCLUDE_DIRS、LLVM_INCLUDE_DIRS、LLVM_BUILD_LIBRARY_DIR，以及所有 MLIR 库的 CMake 目标名（MLIRIR、MLIROptLib……）。
  2. CMake 函数：add_mlir_dialect、add_mlir_dialect_library、mlir_tablegen 这些不是 CMake 内建的，是 MLIR 提供的模块（所以要先把 MLIR_CMAKE_DIR 加进 CMAKE_MODULE_PATH 再 include）。
  3. 一致的编译选项：HandleLLVMOptions 让你的项目用和 LLVM 一样的 C++ 标准、RTTI/异常设置、警告级别。这一条经常被忽略，但后果很严重——LLVM 默认关掉 RTTI，如果你的项目开着 RTTI 去链接它，会得到一堆莫名其妙的链接错误。

配置时把 MLIR_DIR 指到安装树或构建树里的 lib/cmake/mlir：

终端
cmake -G Ninja -S . -B build \
  -DMLIR_DIR=$HOME/llvm-project/build/lib/cmake/mlir \
  -DLLVM_DIR=$HOME/llvm-project/build/lib/cmake/llvm \
  -DCMAKE_BUILD_TYPE=Release

一行 CMake 生成六个文件

include/Pix/CMakeLists.txt 只有一行有效内容：

cmake
add_mlir_dialect(PixOps pix)

这一行到底做了什么？直接去看它的定义（mlir/cmake/modules/AddMLIR.cmake）：

cmake
function(add_mlir_dialect dialect dialect_namespace)
  set(LLVM_TARGET_DEFINITIONS ${dialect}.td)
  mlir_tablegen(${dialect}.h.inc -gen-op-decls)
  mlir_tablegen(${dialect}.cpp.inc -gen-op-defs)
  mlir_tablegen(${dialect}Types.h.inc -gen-typedef-decls -typedefs-dialect=${dialect_namespace})
  mlir_tablegen(${dialect}Types.cpp.inc -gen-typedef-defs -typedefs-dialect=${dialect_namespace})
  mlir_tablegen(${dialect}Dialect.h.inc -gen-dialect-decls -dialect=${dialect_namespace})
  mlir_tablegen(${dialect}Dialect.cpp.inc -gen-dialect-defs -dialect=${dialect_namespace})
  add_mlir_dialect_tablegen_target(MLIR${dialect}IncGen)
endfunction()

一目了然：两个参数分别是"td 文件名"和"方言名"，然后以 PixOps.td 为输入跑六次 mlir-tblgen，每次换一个生成器（-gen-op-decls、-gen-dialect-defs……），最后建立一个名叫 MLIRPixOpsIncGen 的目标。

第一个坑：生成文件的名字跟着第一个参数走

我们写的是 add_mlir_dialect(PixOps pix)，所以方言类的声明在 PixOpsDialect.h.inc，而不是你可能以为的 PixDialect.h.inc——即使方言定义写在 PixDialect.td 里也一样。原因看函数定义就明白：所有生成文件都用 ${dialect} 当前缀，而那就是第一个参数。

所以 PixDialect.h 里要写 #include "Pix/PixOpsDialect.h.inc"。这个不对称让很多人第一次配置时卡住，记住"名字跟着 td 文件走"就不会错。

另外注意它总是生成 Types 那两个文件，哪怕你还没定义任何自定义类型（我们第 9 章才加 !pix.kernel）。生成了不用它，没有任何坏处。

想更细的控制？把它展开写

add_mlir_dialect 只是个便利封装。如果你只想生成其中几样、或者要加自定义的生成器（比如第 15 章的 DRR 规则、第 13 章的 pass 声明），就直接用底层写法：

set(LLVM_TARGET_DEFINITIONS PixPasses.td) → mlir_tablegen(PixPasses.h.inc --gen-pass-decls) → add_public_tablegen_target(MLIRPixPassesIncGen)。第 13 章给 pix 加 pass 时就会这么写。

#define GET_OP_CLASSES：把生成代码缝进你的头文件

这是 MLIR 里最容易让人困惑的惯用法。PixOps.h 的核心就三行：

C++
// include/Pix/PixOps.h
#define GET_OP_CLASSES
#include "Pix/PixOps.h.inc"

为什么不是直接 #include 一个正常的头文件？因为同一个 .inc 文件里装了好几段内容，靠宏来决定展开哪一段。生成出来的文件大致长这样：

C++
#ifdef GET_OP_LIST
#undef GET_OP_LIST
::mlir::pix::AddOp            // ← 只要 op 类名的列表（注册时用）
#endif  // GET_OP_LIST

#ifdef GET_OP_CLASSES
#undef GET_OP_CLASSES
// ← 完整的 op 类声明/定义（几百行）
#endif  // GET_OP_CLASSES

于是同一个文件被两处用到，各取所需：

  • PixOps.h 里 #define GET_OP_CLASSES → 拿到 op 类的声明；
  • PixDialect.cpp 里 #define GET_OP_LIST → 拿到 op 类名的逗号列表，正好塞进 addOperations<…>() 的模板参数里。
C++
// lib/Pix/PixDialect.cpp —— 方言唯一必须手写的部分
void PixDialect::initialize() {
  addOperations<
#define GET_OP_LIST
#include "Pix/PixOps.cpp.inc"
      >();
}

读法：addOperations< 后面那个 include 展开成 ::mlir::pix::AddOp（以后有几十个 op 就是几十个名字），最后 >(); 收尾。第一次见确实怪，但它省掉了"加一个 op 要在三处手工登记"的苦差事——你只改 .td，注册列表自动跟上。

光看还是别扭，不如把那个预处理过程自己跑一遍。下面这 25 行只实现 #ifdef / #undef / #endif 三件事，够看清"同一个文件切出两种内容"了——点运行，然后试着把 #undef 那一行的处理删掉，看会发生什么：

Python 
# 一个 25 行的"预处理器"，只实现 #ifdef / #undef / #endif 这三件事，
# 用来看清同一个 .inc 被不同宏切出不同内容。

GENERATED_INC = """\
#ifdef GET_OP_LIST
#undef GET_OP_LIST
::mlir::pix::AddOp
#endif  // GET_OP_LIST

#ifdef GET_OP_CLASSES
#undef GET_OP_CLASSES
class AddOp : public ::mlir::Op<AddOp, ...> {
  // …几百行：builder、parser、printer、verifyInvariants
};
#endif  // GET_OP_CLASSES
"""

def preprocess(text, defined):
    defined, out, keep = set(defined), [], True
    for line in text.splitlines():
        if line.startswith("#ifdef "):
            keep = line.split()[1] in defined
        elif line.startswith("#endif"):
            keep = True
        elif line.startswith("#undef "):
            defined.discard(line.split()[1])      # 宏用完就撤，所以能重复 include
        elif keep and line.strip():
            out.append(line)
    return out, defined

for macro, where in [("GET_OP_CLASSES", "PixOps.h 里"),
                     ("GET_OP_LIST",    "PixDialect.cpp 的 addOperations< 中间")]:
    lines, left = preprocess(GENERATED_INC, {macro})
    print(f"#define {macro}  ({where}) 展开出：")
    for l in lines:
        print("   ", l)
    print(f"    展开后 {macro} 还定义着吗？{'是' if macro in left else '否 —— 被 #undef 撤掉了'}\n")

print("同一个文件，两处 include，各取所需 —— 加 op 只改 .td，注册列表自动跟上。")

运行结果：

#define GET_OP_CLASSES  (PixOps.h 里) 展开出：
    class AddOp : public ::mlir::Op<AddOp, ...> {
      // …几百行：builder、parser、printer、verifyInvariants
    };
    展开后 GET_OP_CLASSES 还定义着吗？否 —— 被 #undef 撤掉了

#define GET_OP_LIST  (PixDialect.cpp 的 addOperations< 中间) 展开出：
    ::mlir::pix::AddOp
    展开后 GET_OP_LIST 还定义着吗？否 —— 被 #undef 撤掉了

同一个文件，两处 include，各取所需 —— 加 op 只改 .td，注册列表自动跟上。

留意那个 #undef：宏用完立刻被撤掉。正因为如此，同一个 .inc 才能在一个翻译单元里被 include 多次而不重复展开同一段——这个细节容易被当成噪音跳过，其实是整套惯用法能成立的关键。

"注册"到底是什么意思？

addOperations<AddOp>() 做的事，是让 MLIRContext 知道"pix.add 这个字符串对应哪个 C++ 类、它有哪些 trait 与接口实现、怎么解析和打印"。回想第 2 章：op 名是运行时数据，不是枚举——注册就是把字符串和实现挂钩的那一步。这也解释了第 3 章那个 --allow-unregistered-dialect：不注册也能解析通用格式，但 MLIR 对它一无所知，只能当黑盒。

方言与第一个 op

方言声明本身很短（include/Pix/PixDialect.td）：

TableGen / ODS
def Pix_Dialect : Dialect {
  // 这个名字就是 IR 里的前缀：pix.add、pix.convolve……
  let name = "pix";
  let summary = "一个小型图像处理方言（《深入 MLIR》贯穿案例）";
  // 生成的 C++ 类会放进这个命名空间：mlir::pix::PixDialect
  let cppNamespace = "::mlir::pix";
}

// 本方言所有 op 的基类。省去每个 op 重复写方言参数。
class Pix_Op<string mnemonic, list<Trait> traits = []>
    : Op<Pix_Dialect, mnemonic, traits>;
生成代码：mlir-tblgen -gen-op-decls -I $(llvm-config --includedir) PixOps.td

第一个 op 也很短（include/Pix/PixOps.td）。第 8 章会把 ODS 的每个部分拆开细讲，这里只求跑通：

TableGen / ODS
def Pix_AddOp : Pix_Op<"add", [Pure, Commutative, SameOperandsAndResultType]> {
  let summary = "两张图逐点相加";

  let arguments = (ins F32Tensor:$lhs, F32Tensor:$rhs);
  let results = (outs F32Tensor:$result);

  // 自定义格式：让 IR 读起来像 `pix.add %a, %b : tensor<4x4xf32>`
  let assemblyFormat = "$lhs `,` $rhs attr-dict `:` type($result)";
}
生成代码：mlir-tblgen -gen-op-decls -I $(llvm-config --includedir) PixOps.td

四行信息量很大，对着第一部分的知识点读：

  • Pure（第 5 章）：声明"不碰内存、结果只由操作数决定"。这一个词就解锁了 CSE、DCE、以及把它移出循环的资格。
  • Commutative：两个操作数可交换。
  • SameOperandsAndResultType：操作数与结果类型必须一致——这条验证由 trait 自动生成，我们不写一行 verifier。
  • F32Tensor：类型约束，来自 mlir/include/mlir/IR/CommonTypeConstraints.td（那里还有 AnyRankedTensor、AnyTensor、MemRefOf<…> 等等）。约束不满足时的报错，就是第 1 章你见过的那种 operand #0 must be tensor of 32-bit float values。
  • assemblyFormat：自定义格式（第 3 章讲的"糖"）。attr-dict 是必须留的位置——不写它，可丢弃属性就没地方打印，round-trip 会失败。

pix-opt：你自己的 mlir-opt，一共十几行

C++
// pix-opt/pix-opt.cpp
#include "mlir/IR/DialectRegistry.h"
#include "mlir/InitAllDialects.h"
#include "mlir/InitAllPasses.h"
#include "mlir/Tools/mlir-opt/MlirOptMain.h"
#include "Pix/PixDialect.h"

int main(int argc, char **argv) {
  // 1. 注册 pass：内建的那些（--canonicalize、--cse……）拿来就用
  mlir::registerAllPasses();

  // 2. 注册方言：registry 决定这个工具"能解析哪些 op"
  mlir::DialectRegistry registry;
  registry.insert<mlir::pix::PixDialect>();
  mlir::registerAllDialects(registry);   // 让 pix 能和 arith/tensor/func 混用

  return mlir::asMainReturnCode(
      mlir::MlirOptMain(argc, argv, "pix optimizer driver\n", registry));
}

MlirOptMain 是 mlir-opt 的全部主体：命令行解析、--pass-pipeline 的解释、--split-input-file / --verify-diagnostics / --mlir-print-ir-after-all 这些选项，统统在里面。你写的工具和官方 mlir-opt 的差别只是 registry 里多了一个方言。

为什么要 registerAllDialects？因为 pix 不会孤立存在——IR 里会同时有 func.func、arith.constant、tensor 类型（第 6 章的"方言共存"）。不注册它们，解析 func.func 时就会报 unregistered dialect。代价是二进制变大、链接变慢；等你的项目定型了，可以只 insert 真正用到的那几个。

报错是 /bin/sh: 1: <你的构建目录>/bin/llvm-lit: not found。原因：add_lit_testsuite 默认去自己的构建目录找 bin/llvm-lit，而那个脚本只存在于 LLVM 本身的构建树里——out-of-tree 项目没有它。

解法是配置时告诉它 lit 在哪：

cmake -S . -B build -DLLVM_EXTERNAL_LIT=<llvm-build>/bin/llvm-lit

（源码树里的 llvm/utils/lit/lit.py 也可以直接用。）随书的 verify-pix.sh 会替你探测并传这个参数，所以用脚本时不会遇到。这个坑与本书内容无关、纯属工程配置，但几乎每个人都会撞一次。

搭这个工程时我真撞到的四个错

这四个报错不是编的，是把本章这个工程从零编出来的过程中实际遇到的。它们的共同点是报错位置离真正的原因很远，所以值得记住样子：

报错 真正的原因 修法
fatal error: Pix/PixOps.h.inc: No such file or directory add_mlir_dialect_library 漏了 DEPENDS MLIRPixOpsIncGen，编译跑在了代码生成之前（只在并行构建时偶发） 加上 DEPENDS
一堆 incomplete type 'mlir::OpAsmParser' used in nested name specifier，全部指向生成的 .inc assemblyFormat 生成的 parse/print 用到 OpAsmParser/OpAsmPrinter，而头文件没 include 它们的声明 在 PixOps.h 里 #include "mlir/IR/OpImplementation.h"
'RegionBranchTerminatorOpInterface' is not a member of 'mlir' ODS 里 include 了某个接口的 .td（这里是 ControlFlowInterfaces.td 带来的 ReturnLike），但 C++ 头文件没 include 对应的 .h 两套平行的 include 世界：.td 加了什么，.h 就要跟一个

一条通用的排查经验

MLIR 的编译错误常常指向 build/ 里生成的 .inc。别在那里找 bug——生成的代码基本不会错。真正的原因几乎总在三个地方之一：.td 写漏了 include、.h 写漏了对应的 include、或者 CMake 漏了 DEPENDS。遇到看不懂的模板报错，先按这三处过一遍。

动手

先跑通，再破坏。 下面四个改动都能让你更懂那条构建链——建议真的做一遍，报错长什么样比读描述有用得多：

  1. 改 .td，看生成的代码变了什么。 把 pix.add 的 assemblyFormat 改成 $lhs ,$rhs attr-dict: type($lhs)（把 type($result) 换成 type($lhs)），重新 ninja。IR 打印有变化吗？为什么没有？（提示：SameOperandsAndResultType + 类型推断）
  2. 删掉 DEPENDS MLIRPixOpsIncGen，rm -rf build 重新构建几次。可能好几次都没事，然后某次报 fatal error: Pix/PixOps.h.inc: No such file or directory——这就是图 7-1 里说的那个偶发竞争。记住这个报错的样子，它是漏 DEPENDS 的特征。
  3. 把 registry.insert<mlir::pix::PixDialect>() 注释掉，重新编译后跑 pix-opt test/Pix/roundtrip.mlir。报错会是 error: operation being parsed with an unregistered dialect（第 3 章见过）——注册的意义就在这一行。
  4. 亲手看生成的代码。直接跑 mlir-tblgen，不经过 CMake：
终端
mlir-tblgen -gen-op-decls -I <llvm-src>/mlir/include -I include include/Pix/PixOps.td | head -60

你会看到生成出来的 AddOp 类：builder、getLhs()/getRhs()、parser、printer、verifier 骨架，几百行。这些都是你写那 8 行 ODS 换来的。 第 8 章会精读其中几段。

这一章的要点

  • out-of-tree 项目的全部秘密是 find_package(MLIR REQUIRED CONFIG) + MLIR_DIR，它带来头文件、库、CMake 函数，以及与 LLVM 一致的编译选项（HandleLLVMOptions，漏了会有诡异的链接错误）。
  • add_mlir_dialect(PixOps pix) = 六次 mlir-tblgen + 一个 IncGen 目标。生成文件的名字跟着第一个参数走，所以是 PixOpsDialect.h.inc——这是第一次配置最常卡住的地方。
  • #define GET_OP_CLASSES / GET_OP_LIST 是宏切片：同一个 .inc 按需展开成"类声明"或"类名列表"。于是加 op 只改 .td，注册列表自动跟上。
  • DEPENDS MLIRPixOpsIncGen 不能漏，否则并行构建时偶发"找不到 .inc"。
  • "注册方言"的含义是：让 context 知道 op 名这个字符串 对应哪个 C++ 类、有哪些 trait 与接口。
  • pix-opt 与官方 mlir-opt 的差别只是 registry 里多一个方言，主体逻辑全在 MlirOptMain 里。
  • 最重要的一条：Pure + SameOperandsAndResultType 两个声明，换来了免费的 CSE 和免费的类型验证。第 5 章那句"trait 是承诺，不是标签"，你现在在自己的 op 上看到了回报。

pix 进度：方言注册成功，一个 op（pix.add），pix-opt 可用，三个 lit 测试（round-trip / CSE / 报错行为）全绿。
