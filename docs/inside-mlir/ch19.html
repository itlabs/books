第 19 章 分析与副作用：支配关系、MemoryEffects 与数据流框架

这一章想让你带走什么

第三部分收尾。第 13 章我们写过一个分析，但那是自己 walk 一遍数出来的。这一章用 MLIR 自带的三样东西，每样都在 pix 上真跑：支配关系（DominanceInfo）、副作用查询（isPure 那一族）、以及稀疏数据流框架（DataFlowSolver + 一个我们自己写的格）。

中间那一块最重要，而且最容易被当成"文档里的说法"。这一章给 pix 加一个有副作用的 op（pix.trace），然后拿通用的 --cse --canonicalize 跑同一份输入：pix.add 被合并、被删除，pix.trace 一动不动。区别只在 ODS 里那一行声明。没有副作用建模，编译器不敢动任何可能碰内存的东西——这就是它的分量。

三个查询函数 isPure / isMemoryEffectFree / wouldOpBeTriviallyDead 问的是三件不同的事，混用会写出微妙的错误，这一章把它们的差别讲清。

最后写一个真的稀疏前向数据流分析（"这个值是不是已知全零的图"）。它能推出单看一个 op 看不出来的结论——pix.mul %未知, %零 的结果是零。写这个分析时撞到一个只在运行时才炸的坑，报错措辞和 TypeID 有关。

副作用：区别只在那一行声明

先看分量。给 pix 加一个有副作用的 op：

TableGen / ODS
def Pix_TraceOp : Pix_Op<"trace", [MemoryEffects<[MemWrite]>]> {
  let summary = "把一张图输出出去（调试用），有可观察的副作用";
  let arguments = (ins F32Tensor:$image);
  let assemblyFormat = "$image attr-dict `:` type($image)";
}
生成代码：mlir-tblgen -gen-op-decls -I $(llvm-config --includedir) PixOps.td

和前面所有 pix op（都是 Pure）的唯一区别就是那个 trait 列表。拿通用 pass 跑：

MLIR（pix 方言） 
// RUN: pix-opt %s --canonicalize --cse
func.func @pure_ops(%a: tensor<4x4xf32>, %b: tensor<4x4xf32>) -> tensor<4x4xf32> {
  %x = pix.add %a, %b : tensor<4x4xf32>
  %y = pix.add %a, %b : tensor<4x4xf32>
  %dead = pix.mul %a, %b : tensor<4x4xf32>
  return %x : tensor<4x4xf32>
}
func.func @effecting(%a: tensor<4x4xf32>) {
  pix.trace %a : tensor<4x4xf32>
  pix.trace %a : tensor<4x4xf32>
  return
}
本地运行：pix-opt --canonicalize --cse input.mlir

运行结果：

module {
  func.func @pure_ops(%arg0: tensor<4x4xf32>, %arg1: tensor<4x4xf32>) -> tensor<4x4xf32> {
    %0 = pix.add %arg0, %arg1 : tensor<4x4xf32>
    return %0 : tensor<4x4xf32>
  }
  func.func @effecting(%arg0: tensor<4x4xf32>) {
    pix.trace %arg0 : tensor<4x4xf32>
    pix.trace %arg0 : tensor<4x4xf32>
    return
  }
}

上面那个函数：两个相同的 pix.add 合并成一个，没人用的 pix.mul 被删掉。下面那个函数：两个完全相同的 pix.trace 一个都没动——因为对有副作用的 op，次数和顺序都是语义的一部分。

副作用建模是变换的前提，不是文档里的修辞

编译器的每一个"敢"都建立在"我知道这个 op 不碰外部世界"之上：敢合并（CSE）、敢删除（DCE）、敢挪位置（LICM、调度）、敢并发（第 13 章）。你不声明，它就不敢。

反过来也成立，而且更危险：你声明错了，它就敢做错事。给一个真的会写内存的 op 标上 Pure，CSE 会把两次写合并成一次，而且没有任何报错——第 16 章讲过"trait 多数是契约"，这是其中后果最严重的一个。

三个查询函数，三件不同的事

mlir/include/mlir/Interfaces/SideEffectInterfaces.h 里有一族查询函数，名字很像，问的不是一回事：

函数 问的是什么 官方定义的要点
isMemoryEffectFree(op) 不碰内存 实现了 MemoryEffectOpInterface 且报告无内存效应；或有 HasRecursiveMemoryEffects 且所有嵌套 op 都无效应
isSpeculatable(op) 可以提前执行（没有 UB） 由 ConditionallySpeculatable 接口的 getSpeculatability 回答
isPure(op) 上面两条都满足 文档原话："is speculatable that does not touch memory"，是 Pure trait 的 C++ 等价物
wouldOpBeTriviallyDead(op) 没人用的话可以删吗 注意：终结符和 symbol 永远不算 trivially dead

两个容易踩的差别：

isMemoryEffectFree 不等于 isPure。 一个 op 可以不碰内存但不可推测——典型例子是整数除法：它不读不写内存，但除零是 UB，所以不能被提到条件分支外面。这种 op isMemoryEffectFree 为真而 isPure 为假。想做代码移动（把 op 挪到循环外、挪进分支）时，要问的是 isSpeculatable，不是 isMemoryEffectFree。

wouldOpBeTriviallyDead 有额外的例外。 终结符和 symbol 无论如何都不算"可删"——即使它们无副作用。想手写 DCE 时直接用这个函数，别自己拿 isPure 拼，否则会删掉 func.return。

把三个都数一遍，差别就看见了：

MLIR（pix 方言） 
// RUN: pix-opt %s --pix-analyze
func.func @effects(%a: tensor<4x4xf32>) -> tensor<4x4xf32> {
  %x = pix.add %a, %a : tensor<4x4xf32>
  pix.trace %x : tensor<4x4xf32>
  return %x : tensor<4x4xf32>
}
本地运行：pix-opt --pix-analyze input.mlir

运行结果（函数头那一行）：

  func.func @effects(%arg0: tensor<4x4xf32>) -> tensor<4x4xf32> attributes {pix.dominators = 1 : i64, pix.effect_free = 1 : i64, pix.known_zero = 0 : i64, pix.pure = 1 : i64, pix.trivially_dead = 1 : i64} {

函数里有 2 个 pix op（add 和 trace），但三个计数都是 1——那个 1 就是 pix.add。pix.trace 三项全不满足。

支配关系：DominanceInfo

概念读者已经熟（这本书假设你懂支配关系），所以只讲 MLIR 里的两个实际要点。

C++
DominanceInfo dom(fn);
// a 是否严格支配 c
dom.properlyDominates(a, c);

要点一：它是按"最近的 IsolatedFromAbove 祖先"建的。 第 13 章那个 trait 第三次出现了——它划分的不只是 pass 的调度单位，也是支配关系的计算范围。这也解释了为什么 DominanceInfo 构造起来不贵：它只在一个隔离区域内工作。

要点二：region 让"支配"比 CFG 时代复杂。 一个 op 可能在嵌套 region 里，properlyDominates 会正确处理跨 region 的情况（外层的 op 支配内层的所有 op），但代价是你要想清楚问的到底是什么。DominanceInfo 还有 PostDominanceInfo 这个对偶版本。

我们的 pix-analyze 用它数一件具体的事：有多少个 pix op 支配着函数里所有其他 pix op——也就是"放在它后面一定安全"的那些。@zeros 里有 transpose 和 mul 两个 pix op，transpose 支配 mul 而反之不然，所以答案是 1。

写一个真的数据流分析

前面两样是"用现成的"。这一节是"自己造一个"，也是这一章最实在的部分。

问题：这个值是不是已知的全零图？ 为什么值得分析——因为一旦知道，一大批化简就成立了（乘零直接返回零图、加零直接消去）。而这个结论跨 op 才能得到：pix.mul %未知, %零 的结果是零，单看这个 op 看不出来。

格（lattice）

格是数据流分析的骨架。我们的格只有四层：

     unknown          ← 最保守：什么都不知道
    /       \
  zero    nonzero     ← 有结论
    \       /
     uninit           ← 还没算

值类型要满足的契约就是几个成员函数（照 mlir/include/mlir/Analysis/DataFlow/ConstantPropagationAnalysis.h 里的 ConstantValue 抄）：operator==、print、getUninitialized、isUninitialized、join。

C++
/// join 是格的核心：两条路径汇合时取"更保守"的那个。
/// 偏序是 uninit < zero/nonzero < unknown。
static ZeroState join(const ZeroState &a, const ZeroState &b) {
  if (a.isUninitialized()) return b;
  if (b.isUninitialized()) return a;
  if (a == b)              return a;
  return getUnknown();     // 结论不一致 → 只能说不知道
}

join 必须是保守的——这是数据流分析正确性的全部来源。两条路径给出不同结论时，只能承认不知道；如果这里"择一而从"，分析就会给出错误结论，而基于它的变换会生成错代码。

传递函数

这是分析的实质内容：由操作数的格值算出结果的格值。

C++
LogicalResult visitOperation(Operation *op,
                            ArrayRef<const ZeroLattice *> operands,
                            ArrayRef<ZeroLattice *> results) override {
  // pix.add：两边都是零才是零
  if (isa<AddOp>(op)) {
    bool allZero = llvm::all_of(operands, [](const ZeroLattice *l) {
      return !l->getValue().isUninitialized() && l->getValue().isZero();
    });
    setAll(allZero ? ZeroState::getZero() : ZeroState::getUnknown());
    return success();
  }

  // pix.mul / pix.scale：**任意一边**是零，结果就是零（0 × 任何 = 0）
  // 这条是这个分析最有价值的地方。
  if (isa<MulOp, ScaleOp>(op)) {
    bool anyZero = llvm::any_of(operands, [](const ZeroLattice *l) {
      return !l->getValue().isUninitialized() && l->getValue().isZero();
    });
    setAll(anyZero ? ZeroState::getZero() : ZeroState::getUnknown());
    return success();
  }
  // …transpose、常量、以及兜底的 unknown
}

另一个必须写对的是入口状态：

C++
/// 函数参数之类我们一无所知的值，一律"未知"。
/// 保守的起点保证分析结果可信。
void setToEntryState(ZeroLattice *lattice) override {
  propagateIfChanged(lattice, lattice->join(ZeroState::getUnknown()));
}

跑它

C++
DataFlowSolver solver;
solver.load<dataflow::DeadCodeAnalysis>();   // ← 这一句不能省
solver.load<ZeroAnalysis>();
if (failed(solver.initializeAndRun(fn)))
  return signalPassFailure();

// 查询某个值的结论

  if (!l->getValue().isUninitialized() && l->getValue().isZero())
    ++knownZero;
DeadCodeAnalysis 几乎总要一起加载

它负责算"哪些块可达、哪些分支会走"。少了它，不可达代码里的格值会参与 join，把结论污染成 unknown——分析仍然"正确"（保守），但会白白失去精度。绝大多数稀疏分析都把它当前置依赖。

实测：

MLIR（pix 方言） 
// RUN: pix-opt %s --pix-analyze
func.func @zeros(%img: tensor<4x4xf32>) -> tensor<4x4xf32> {
  %z = arith.constant dense<0.0> : tensor<4x4xf32>
  %t = pix.transpose %z : tensor<4x4xf32> to tensor<4x4xf32>
  %m = pix.mul %img, %t : tensor<4x4xf32>
  return %m : tensor<4x4xf32>
}
本地运行：pix-opt --pix-analyze input.mlir

运行结果（函数头那一行）：

  func.func @zeros(%arg0: tensor<4x4xf32>) -> tensor<4x4xf32> attributes {pix.dominators = 1 : i64, pix.effect_free = 2 : i64, pix.known_zero = 3 : i64, pix.pure = 2 : i64, pix.trivially_dead = 2 : i64} {

known_zero = 3：常量、transpose 的结果、以及 mul 的结果。最后那个是关键——%img 完全未知，但 0 × 任何 = 0，所以 %m 是零。这个结论单看 pix.mul 这一个 op 是得不到的。

匿名命名空间里的类要显式定义 TypeID

第一次跑这个 pass，编译通过、运行直接 abort：

LLVM ERROR: TypeID::get<...::ZeroAnalysis>(): Using TypeID on a class with an anonymous namespace requires an explicit TypeID definition.

原因：DataFlowSolver 拿类型的 TypeID 当键，而匿名命名空间里的类名在不同翻译单元里不保证唯一，隐式的按名字回退不安全。报错本身把该用的宏名都告诉你了——在类里加一行 MLIR_DEFINE_EXPLICIT_INTERNAL_INLINE_TYPE_ID(ZeroAnalysis) 就好。lattice 类也要加。

上游同类代码就是这么写的（mlir/lib/Dialect/XeGPU/Transforms/XeGPUPropagateLayout.cpp:158）。这个坑只在运行时暴露，而且只在你把分析类放进匿名命名空间时——照惯例这么放是对的，所以基本人人会撞一次。

把不动点迭代自己跑一遍

格、传递函数、join、不动点——这几个概念串起来才成立。下面这个模型把它们全放进 40 行，并打出每一轮变了什么：

Python 
# 一个稀疏前向数据流分析的完整模型：格、传递函数、join、不动点迭代。
# 分析的问题："这个值是不是已知的全零图？"
# 看点是它能推出**单看一个 op 看不出来**的结论。

UNINIT, ZERO, NONZERO, UNKNOWN = "uninit", "zero", "nonzero", "unknown"

def join(a, b):
    """格的核心。偏序：uninit < zero/nonzero < unknown。
       两条路径汇合时取更保守的——这保证了分析永不给出错误结论。"""
    if a == UNINIT: return b
    if b == UNINIT: return a
    return a if a == b else UNKNOWN

def transfer(op, ins):
    """传递函数：由操作数的格值算出结果的格值。分析的全部内容就在这。"""
    if op == "const.zero":     return ZERO
    if op == "const.other":    return NONZERO
    if op == "pix.add":        return ZERO if all(i == ZERO for i in ins) else UNKNOWN
    # 关键一条：任意一边是零，乘积就是零 —— 哪怕另一边完全未知
    if op == "pix.mul":        return ZERO if any(i == ZERO for i in ins) else UNKNOWN
    if op == "pix.transpose":  return ins[0] if ins and ins[0] in (ZERO, NONZERO) else UNKNOWN
    return UNKNOWN

def solve(ir, entry):
    """不动点迭代：反复跑传递函数，直到没有格值再变。"""
    state = dict(entry)                       # 已知的入口状态
    for name, _, _ in ir:
        state.setdefault(name, UNINIT)
    for rnd in range(1, 20):
        changed = []
        for name, op, args in ir:
            ins = [state[a] for a in args]
            if any(i == UNINIT for i in ins) and op.startswith("pix."):
                continue                      # 操作数还没算出来，这轮跳过
            new = join(state[name], transfer(op, ins))
            if new != state[name]:
                state[name] = new
                changed.append(f"{name}={new}")
        print(f"    第 {rnd} 轮：" + (", ".join(changed) if changed else "无变化 → 到达不动点"))
        if not changed:
            return state
    return state

IR = [
    ("%z", "const.zero",    []),
    ("%t", "pix.transpose", ["%z"]),
    ("%m", "pix.mul",       ["%img", "%t"]),   # %img 完全未知！
    ("%s", "pix.add",       ["%m", "%m"]),
]
print("【IR】")
for n, op, a in IR:
    print(f"    {n} = {op}({', '.join(a) or ''})")
print("【入口状态】%img 是函数参数，一无所知 → unknown（保守起点）")
final = solve(IR, {"%img": UNKNOWN})
print("\n【结论】")
for n, _, _ in IR:
    mark = "  ← 单看这一个 op 看不出来" if n in ("%m", "%s") else ""
    print(f"    {n}: {final[n]}{mark}")
print(f"\n  已知全零的值共 {sum(1 for n,_,_ in IR if final[n]==ZERO)} 个")
print("  %m 是零，因为 0 × 任何 = 0；%s 是零，因为零加零。")
print("  这两条都需要**跨 op 传播**才能得到 —— 这就是数据流分析的价值。")

运行结果：

【IR】
    %z = const.zero()
    %t = pix.transpose(%z)
    %m = pix.mul(%img, %t)
    %s = pix.add(%m, %m)
【入口状态】%img 是函数参数，一无所知 → unknown（保守起点）
    第 1 轮：%z=zero, %t=zero, %m=zero, %s=zero
    第 2 轮：无变化 → 到达不动点

【结论】
    %z: zero
    %t: zero
    %m: zero  ← 单看这一个 op 看不出来
    %s: zero  ← 单看这一个 op 看不出来

  已知全零的值共 4 个
  %m 是零，因为 0 × 任何 = 0；%s 是零，因为零加零。
  这两条都需要**跨 op 传播**才能得到 —— 这就是数据流分析的价值。

注意两点。第一轮就全部收敛，因为这段 IR 是直线代码；有循环时会迭代多轮，每轮靠 join 把回边上的信息并进来。%m 和 %s 的结论都需要跨 op 传播——这就是为什么需要一个框架，而不是在每个 op 的 fold 里各自判断。

分析和变换怎么接上

分析本身不改 IR。上面那个 known_zero 算出来之后能干什么？

最直接的用法：写一个 pattern，在 matchAndRewrite 里查分析结论，把 pix.mul %未知, %零 直接替换成那个零图。这比第 11 章的 fold 强——fold 只能看操作数是不是字面常量，而分析能看到"沿着 def-use 链传播过来的结论"。

代价也要说清楚：跑一次数据流分析比跑一个 fold 贵得多，而且第 13 章讲过，pass 改了 IR 之后分析默认全部作废。所以实践上的取舍是：能用 fold 解决的别上分析；需要跨 op 推理时才上，而且尽量让一个 pass 里的多个 pattern 共享同一次分析结果。

  1. 在 AnalyzePass.cpp 里，跑完 solver 之后遍历所有 op，找出"结果已知为零、但本身不是常量"的 pix.mul；
  2. 用 OpBuilder 造一个 arith.constant dense<0.0>，replaceAllUsesWith 掉它；
  3. 跑 --pix-analyze --canonicalize，看那条 pix.mul 是不是连带整条链都消失了。

注意别忘了：改了 IR 就不能再 markAllAnalysesPreserved()（第 13 章那笔账）。

再改一处：给 pix.trace 换个 effect 试试。把 MemWrite 改成 MemRead，重新构建，跑 --cse。两个相同的 pix.trace 会被合并吗？想清楚为什么——读操作之间没有顺序依赖，所以 CSE 敢合并两次相同的读。这个实验能让你对"effect 的种类不只是有无"有实感。

这一章的要点

  • 副作用建模是所有变换的前提，而且是可观测的：同一份输入、同一个 --cse --canonicalize，Pure 的 pix.add 被合并被删除，声明了 MemWrite 的 pix.trace 一动不动。区别只在 ODS 里那一行。
  • 更危险的是反面：声明错了，编译器就敢做错事。给会写内存的 op 标 Pure，CSE 会把两次写合并成一次，没有任何报错。
  • 三个查询函数问三件事：isMemoryEffectFree（不碰内存）、isSpeculatable（可提前执行、无 UB）、isPure（两者都满足）。整数除法就是"不碰内存但不可推测"的例子——做代码移动要问 isSpeculatable。
  • wouldOpBeTriviallyDead 有额外例外：终结符和 symbol 永远不算可删。手写 DCE 直接用它，别拿 isPure 自己拼。
  • DominanceInfo 按最近的 IsolatedFromAbove 祖先建——第 13 章那个 trait 的第三次现身。它划的不只是 pass 调度单位，也是支配关系的计算范围。
  • 写数据流分析要四样：格（值类型的契约是 == / print / getUninitialized / isUninitialized / join）、传递函数（visitOperation）、入口状态（setToEntryState，必须保守）、solver。
  • join 必须保守——两条路径结论不一致时只能承认"不知道"。这是分析正确性的全部来源；这里"择一而从"会让基于它的变换生成错代码。
  • DataFlowSolver 几乎总要一起 load<DeadCodeAnalysis>()。少了它不影响正确性，但不可达代码的格值会污染 join，白白失去精度。
  • 匿名命名空间里的分析/格类要加 MLIR_DEFINE_EXPLICIT_INTERNAL_INLINE_TYPE_ID。DataFlowSolver 拿 TypeID 当键，隐式的按名字回退在匿名上下文里不安全。这个坑只在运行时 abort，而按惯例把这些类放进匿名命名空间是对的，所以基本人人会撞一次。
  • 分析的价值在于跨 op 推理：pix.mul %未知, %零 的结果是零，这个结论 fold 得不到（它只看字面常量）。代价是贵、且改 IR 后默认作废——能用 fold 解决的别上分析。

pix 进度：新增 pix.trace（第一个有副作用的 op，专门用来做对照）与 pix-analyze pass（三样分析各用一遍，结果写成属性）。analyze.mlir 两条 RUN 行：一条断言分析结论，一条用通用 pass 证明副作用真的在管事。check-pix 从 15 涨到 16 个文件。
